## 한 줄 요약

**Slack 발췌에 따르면 이 글은 에이전트 개발에서 혼용되는 "워크플로우"와 "하네스", "Context"와 "Memory", "MCP"와 "A2A"라는 세 쌍의 개념을 원문과 실무 사례로 명확히 구분하려는 시도다 — 원문을 직접 확보하지 못해 정확한 정의·사례는 확인할 수 없으므로, 이 노트는 원문 평가 대신 이 가든이 이미 확보한 관련 개념들을 정리하고 D2 글이 다룬다고 알려진 세 쌍의 구분선이 무엇일지 배경지식으로 재구성한다.**

## 핵심 포인트 (Slack 발췌 원문 그대로, 확인 불가 표시 포함)

- **개념 정의가 목적** — 에이전트 개발 시 ***혼용되는 워크플로우와 하네스 등의 핵심 개념***을 "원문과 실무 사례"를 통해 명확히 정의한다고 Slack 발췌는 전한다. 어떤 실무 사례인지는 확인하지 못했다.
- **Context vs Memory, MCP vs A2A** — Context와 Memory의 차이점, 그리고 MCP와 A2A 스펙을 ***기존 REST API와 비교***해 상세히 분석한다고 언급된다. 비교의 구체적 결론(예: MCP·A2A가 REST API와 무엇이 다르다고 결론지었는지)은 원문 미확보로 확인하지 못했다.
- **사내 기술 세미나 콘텐츠** — Slack 발췌는 이 글이 ***사내 기술 세미나에서 공유된 에이전트 관련 지식과 개념 정립 과정을 담은 기술 콘텐츠***라고 설명한다. 즉 외부 공개용으로 처음부터 작성된 글이 아니라 사내 발표를 정리해 D2에 게시한 형태로 추정된다(추정, 확인 불가).

## 배경지식 재구성 — 세 쌍의 구분선 (D2 원문이 아니라 이 가든의 기존 지식 기반)

이 절은 D2 글의 내용이 아니라, ***이 가든이 이미 다른 노트에서 확보·검증한 개념***과 업계 일반 정의를 정리한 것이다. D2 글이 실제로 이렇게 구분했는지는 확인할 수 없다.

- **워크플로우 vs 하네스** — [[2026-06-08-harness-engineering-jaehong]]가 정리했듯, 이 가든이 이미 확보한 정의로는 하네스는 ***"모델이 아닌 모든 것"*** — 시스템 프롬프트·도구 정의·샌드박스·오케스트레이션·피드백 루프·메모리·훅을 아우르는 상위 개념이다. 워크플로우는 그 하네스 안에서 ***결정적으로 정의된 실행 순서***(어떤 단계를 언제, 순차로 또는 병렬로 실행할지)에 가깝다 — [[2026-05-09-agents-need-control-flow]]가 짚은 "결정적 스캐폴딩" 개념과 겹친다. 즉 하네스가 에이전트를 감싸는 전체 환경이라면, 워크플로우는 그 환경 안에 있는 하나의 결정적 실행 경로라는 것이 통념에 가깝다.
- **Context vs Memory** — 업계 일반 구분으로는 Context는 ***현재 실행 중인 하나의 세션·요청 안에서 모델에 주어지는 정보***(현재 대화, 방금 호출한 도구의 출력 등 휘발성)이고, Memory는 ***세션을 넘어 지속되는 정보***(과거 대화 요약, 학습된 선호, 장기 저장된 사실)다. [[2026-06-08-harness-engineering-jaehong]]가 다룬 "컨텍스트 부패(Context Rot)" 문제는 정확히 전자(Context)가 길어질수록 성능이 떨어지는 현상을 가리킨다.
- **MCP vs A2A** — MCP(Model Context Protocol)는 ***에이전트가 도구·데이터 소스에 접근***하는 표준 인터페이스이고, A2A(Agent2Agent)는 ***에이전트끼리 서로 통신***하는 표준 프로토콜이다 — 전자는 "에이전트-도구" 축, 후자는 "에이전트-에이전트" 축이라는 점에서 역할이 다르다. 이 가든은 이미 [[2026-09-22-mcp-was-always-a-bad-idea]]·[[2026-05-29-mcp-is-dead-cli-skills]]에서 "코드 실행 능력이 강한 모델에게는 MCP 재포장이 불필요해지지만, 접근 통제가 필요한 상황에는 여전히 유효하다"는 논쟁을 다뤘다 — REST API와의 비교라면 아마 "MCP는 REST API 위에 표준화된 발견(discovery)·스키마 레이어를 얹은 것"이라는 방향일 가능성이 높지만, 이는 이 가든의 추정이지 D2 원문 확인이 아니다.

## 내 생각 · 적용점

### 핵심 전이 1 — "하네스" 개념이 이 가든에서 이미 가장 많이 다뤄진 용어인데, 그 정의를 처음 한국어로 체계화한 원 출처와 나란히 놓을 수 있다

가든에는 [[2026-06-08-harness-engineering-jaehong]]을 비롯해 하네스를 다룬 노트가 십수 개 쌓여 있다 — "Agent = Model + Harness"라는 공식이 이 가든의 방법론 계열 전체를 관통한다. D2 글이 실제로 이 정의를 어떻게 재구성했는지는 확인하지 못했지만, ***"워크플로우와 하네스를 혼용한다"***는 Slack 발췌의 문제의식 자체는 타당하다 — 실제로 "하네스"라는 말이 이 가든 안에서도 때로는 "전체 실행 환경"(박재홍 정의)을, 때로는 "하나의 구체적 오케스트레이션 패턴"(Pipeline·Fan-out 같은 Harness 프레임워크의 용법)을 가리키며 쓰이는 걸 볼 수 있다. D2 글이 이 모호함을 정리하려 했다면, 그 자체가 이 가든이 이미 겪고 있는 용어 혼란에 대한 직접적인 답이 될 수 있다 — 다만 원문을 못 읽어 실제로 어떻게 정리했는지는 다음에 확인이 필요하다.

### 핵심 전이 2 — MCP 논쟁의 "거버넌스 예외"가 REST API 비교로 이어질 법한 지점

[[2026-09-22-mcp-was-always-a-bad-idea]]는 "코드 실행 에이전트에는 MCP 재포장이 불필요해지지만, 접근 통제가 필요한 엔터프라이즈 상황에서는 여전히 MCP가 유효하다"는 절충안을 다뤘다. Slack 발췌가 언급한 "MCP·A2A를 REST API와 비교"라는 방향은, 아마 "MCP가 REST API 대비 무엇을 표준화했는가"(발견 가능성, 스키마, 인증 흐름)를 다뤘을 가능성이 높다 — 이건 이 가든이 이미 확보한 논쟁(MCP는 죽었다 vs 통제가 필요하면 유효하다)에 "그래서 애초에 REST API와 뭐가 다른가"라는 더 기초적인 질문을 던지는 셈이다. 원문 확보 시 이 지점을 우선 대조할 가치가 있다.

## 호스피탈리티 / CRS 적용 포인트

원문을 확보하지 못해 이 글 고유의 CRS 적용점을 구체적으로 제시하기는 어렵다. 다만 이 가든이 이미 확보한 배경지식 수준에서 원칙만 남긴다면, CRS·PMS 연동 에이전트를 설계할 때 "워크플로우(결정적 실행 순서)"와 "하네스(전체 환경·권한·도구)"를 구분해 문서화하는 습관은 실무적으로 유용하다 — 예컨대 "예약 취소 처리"라는 워크플로우(결제 환불 → 재고 반영 → 알림 발송의 결정적 순서)와, 그 워크플로우가 실행되는 하네스(에이전트가 접근 가능한 API 범위, 실패 시 재시도 정책, 감사 로그)를 분리해서 설계 문서에 적으면 [[2026-05-09-agents-need-control-flow]]가 강조한 "결정적 영역과 비결정적 영역의 분리"가 자연스럽게 따라온다. Context와 Memory의 구분도 마찬가지로, CRS 문의 응대 에이전트를 만들 때 "이번 대화 세션 안의 정보(Context)"와 "이 고객의 과거 예약 이력·선호(Memory)"를 서로 다른 저장소·수명주기로 관리해야 한다는 원칙으로 이어진다 — 단, 이 모두는 D2 원문의 구체적 처방이 아니라 이 가든의 기존 지식에서 끌어온 일반 원칙임을 다시 한 번 밝힌다.
