## 한 줄 요약

**n3r 운영팀의 "Care AI 에이전트"가 1부의 지식그래프 위에서, MCP 서버 응답 구조를 최적화해 모델 입력 한도 문제를 풀고, 탐색·판단은 모델이 하되 코드 실행과 최종 판정은 분리해 신뢰성을 올렸다는 2부작의 완결편이다.**

## 핵심 포인트

- **MCP 서버 응답 최적화로 입력 한도 해결** — MCP가 돌려주는 응답이 너무 크면 모델 컨텍스트를 금방 채운다는, 실무에서 흔한 문제를 서버 쪽 응답 구조 설계로 풀었다고 서술. ***구체적으로 무엇을 어떻게 잘랐는지(필드 선택? 페이지네이션? 요약?)는 Slack 불릿에 나오지 않아 확인 불가.***
- **탐색·판단과 실행·확정의 역할 분리** — 모델이 ***탐색과 판단***을 수행하고, 코드(비-LLM 로직)가 ***검증과 최종 판정***을 담당하도록 나눠, "모델이 혼자 다 하는" 구조보다 신뢰성을 높였다는 설계.
- **운영자 응답 방식의 표준화** — 상태·원인·조치 사항을 구조화된 형식으로 전달하도록 설계해, 운영자가 매번 다른 포맷의 답변을 해석하는 비용을 줄였다고 주장.
- **정량 효과 공개 없음** — 1부와 마찬가지로 "시간을 아끼는"이라는 제목의 핵심 주장을 뒷받침할 구체 수치(단축 시간·정확도 개선율)는 Slack 발췌에도, WebSearch에도 없다.

## 내 생각 · 적용점

### 핵심 전이 — 1부와의 완결 구조

[[2026-11-25-naver-care-agent-rca-knowledge-graph]](1부)는 과거 RCA·Q&A를 Neo4j 지식그래프로 "축적"하는 쪽을 다뤘다. 이 2부는 그 지식그래프를 MCP로 "노출"하고 에이전트가 "탐색·판단"하게 만드는 쪽이다 — 축적(1부)과 서빙(2부)이 한 파이프라인의 앞뒤 단계로 맞물린다. 이 2부작을 합치면 "지식 누적 → MCP 노출 → 역할 분리 에이전트"라는 완결된 사내 운영 에이전트 아키텍처 템플릿이 나온다.

### 적용점

"모델이 탐색·판단, 코드가 검증·확정"이라는 역할 분리는 이 레포가 반복해서 만나는 원칙([[2026-11-24-evals-underrated-ai-engineering-skill]]의 "검증은 과소평가된 역량"과 같은 축)이다. MCP 응답이 너무 크면 컨텍스트를 먹어치운다는 문제도 실무에서 자주 부딪히는 지점이라, "서버 쪽에서 미리 걸러주는" 설계를 참고할 만하다.

## 호스피탈리티 / CRS 적용 포인트

**적용 가능성 높음.** CRS 상담 에이전트가 PMS·요금 시스템을 MCP로 조회할 때도 똑같은 문제(응답이 너무 커서 컨텍스트를 채움)를 만난다. "모델은 탐색·판단만, 최종 확정은 코드가 담당"하는 역할 분리는 요금 오류 같은 고위험 판정에 그대로 적용 가능한 원칙이다. [[2026-11-25-naver-care-agent-rca-knowledge-graph]]의 CRS 적용점(RCA 지식그래프 축적)과 합치면 "조회 효율화 + 지식 누적 + 역할 분리"라는 3단 설계가 완성된다.
