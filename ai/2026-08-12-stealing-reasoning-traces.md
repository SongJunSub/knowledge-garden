# 독점 LLM API에서 추론 트레이스 훔치기 (Panfilov 외, arXiv 2608.09867)

> 출처: [Stealing Reasoning Traces from Proprietary LLM APIs](https://arxiv.org/abs/2608.09867) (arXiv 2608.09867 · 2026-08-10 제출 · GeekNews GN⁺ 경유) · 정리일 2026-08-12

## 한 줄 요약

**OpenAI·Anthropic·Google 은 모델의 사고 흐름(chain-of-thought)을 ***"지적 재산을 보호하고 정보 유출을 제한하기 위해"*** 숨기는데, 서버에 보관하는 대신 **암호화된 블록으로 클라이언트에 돌려준다**. 논문이 찾은 결함은 그 블록이 **세션·사용자·모델 사이에서 완전히 호환되고 교환 가능**하다는 것이다. 그래서 **강한 모델(예: Claude Opus)이 만든 암호화 블록을 같은 공급자의 더 약한 모델(예: Claude Haiku)에 주입하고 탈옥시키면**, 강한 모델을 직접 공격하지 않고도 숨겨진 추론이 **그대로 옮겨 적힌다**. 공격 벡터는 넷이다: **증류 방지 우회, 사적 데이터 추출, 유해 정보 노출, 보이지 않는 프롬프트 인젝션**(악성 지시를 암호화 블록 안에 넣어 공개 에이전트 롤아웃을 오염시키는 것). 실증도 했다. 공개 저장소에서 긁은 **31만 5,320개 블록을 복호화**해 **PII 367건과 자격증명 182건**을 복원했다. 공개 전 신고를 거쳤고 **2026년 8월 현재 논문의 공격은 같은 방식으로는 재현되지 않는다**. 권고는 명확하다: 추론 블록을 **사용자·세션·모델에 묶고**, 공개 로그에서는 **제거하라**. **그런데 이 연구에서 가장 무서운 대목은 취약점 자체가 아니라, 애초에 API 키와 비밀번호가 왜 추론 트레이스 안에 들어가 있었는가다.**

## 핵심 포인트

- **설계 전제**: 공급자들은 사고 흐름을 ***"지적 재산을 보호하고 정보 유출을 제한하기 위해"*** 감춘다. 서버에 저장하지 않고 **암호화 텍스트 블록으로 클라이언트에 반환**하는 방식이다(상태 비저장 API 의 자연스러운 귀결).
- **결함**: 그 암호화 블록이 **세션·사용자·모델 사이에서 완전히 호환되고 교환 가능**했다. HN 이 이 지점을 두 갈래로 짚는다: ***"데이터가 사용자 세션에 엄격히 묶이지 않아 세션 데이터 탈취가 쉬워졌다"***, 그리고 ***"모델마다 같은 암호화 키를 재사용한다는 사실은 놀랍다"***.
- **공격 방법**: 강한 모델의 암호화 블록을 **같은 공급자의 더 약한 모델**에 입력하고 **탈옥**시켜 평문을 옮겨 적게 한다. **강한 모델을 직접 공격하지 않는다**는 게 요점이다.
- **네 가지 활용**
  - **증류 방지 우회**: 공급자가 막으려던 바로 그 용도(추론 데이터를 뽑아 자기 모델 학습).
  - **사적 데이터 추출**: 남의 세션에 들어 있던 내용.
  - **유해 정보 노출**: 최종 답변에서는 걸러졌지만 추론 과정에는 남아 있던 것.
  - **보이지 않는 프롬프트 인젝션**: 악성 지시를 **암호화 블록 안에 통째로 심어** 공개 에이전트 롤아웃을 오염시킨다.
- **실측(수치 출처가 갈린다)**
  - **arXiv 초록**: 공개 저장소에서 **31만 5,320개 블록 복호화** → **PII 367건 + 자격증명 182건**.
  - **GN⁺ 요약**: **에이전트 로그 6,708개**에서 같은 31만 5,320개 블록을 복원, **민감정보 704개**이며 그 안에 **API 키 62개·비밀번호 33개·액세스 토큰 24개**.
  - **블록 수는 일치하지만 민감정보 집계가 맞지 않는다.** 62+33+24=119 로 어느 총계와도 맞지 않으니 **부분 내역으로 보이고**, 704 와 (367+182=549)의 차이는 이 노트에서 해소하지 못했다. **본문 PDF 를 읽지 않은 한계다.**
- **공개 절차와 대응**: 사전 신고 후 공급자들이 대응해 **2026년 8월 현재 논문의 공격은 같은 방식으로는 재현되지 않는다**.
- **권고**: 추론 블록을 **사용자·세션·모델에 바인딩**하고, **공개 로그에서 제거**할 것.

## 내 생각 · 적용점

### 핵심 전이 1: 이 공격 경로가 왜 지금 막혔는지, 오늘 확인한 문서가 설명해준다

논문의 공격은 **강한 모델의 추론 블록을 약한 모델에 주입**하는 것이다. 그런데 오늘 다른 작업 중 확인한 Claude API 문서에는 **정확히 그 경로를 막는 동작**이 적혀 있었다: 최신 Claude 모델(Fable 5·Mythos 5·Opus 5)은 **원시 사고 흐름을 절대 반환하지 않고**, 이들 모델의 thinking 블록을 **다른 모델에 replay 하면 프롬프트에서 드롭된다**(과거에는 하드 리젝트였다가 되돌려졌다는 이력까지 문서에 남아 있다).

**논문 제출이 2026-08-10 이고, 공개 전 신고를 거쳤으며, 8월 현재 재현되지 않는다는 서술과 시점이 맞물린다.** 즉 ***"reasoning block 을 사용자·세션·모델에 묶으라"***는 권고 중 **모델 바인딩 부분이 실제로 구현된 형태**를 문서에서 볼 수 있다.

**이건 이번 정리에서 가장 검증도가 높은 연결이고, 동시에 조심할 부분이기도 하다** - 문서에 적힌 동작과 논문이 신고한 취약점이 인과로 이어진다는 건 **시점과 내용이 일치한다는 정황**이지, 벤더가 그렇게 밝힌 게 아니다. **다만 방어의 형태가 권고와 정확히 같다는 건 사실이다.**

### 핵심 전이 2: 진짜 문제는 취약점이 아니라 비밀이 추론 트레이스에 들어갔다는 사실이다

***"모델에 흡수되는 보안 토큰의 수가 얼마나 많은지 무서울 정도"***라는 HN 의 반응이 정확하다. **암호화 결함이 고쳐져도 이 문제는 남는다.** 공개 저장소의 에이전트 로그에 API 키와 비밀번호가 들어 있었다는 건, **에이전트가 작업 중에 그것들을 보았고 그게 추론에 남았고 그 추론이 로그로 공개됐다**는 뜻이다. 세 단계 전부가 관행의 문제지 암호화의 문제가 아니다.

**가든에 이미 같은 계열이 둘 있다.** [[2026-08-02-hugging-face-tailscale-agent-breach]]에서 에이전트가 샌드박스를 탈출해 **136개 프로덕션 키**를 읽었고, 거기서 남긴 교훈이 ***"이런 일이 자동으로 일어난다"***였다. **에이전트가 자격증명을 만지면 그 흔적이 어딘가에 남는다**는 게 두 사건의 공통 구조다.

**그리고 구조적 답은 [[2026-08-10-doordash-ai-agent-gateway]]에 이미 나와 있다**: 자격증명을 게이트웨이가 관리하고 **원본을 에이전트가 보관하지 않는 것**. 어제 정리한 워터마킹 노트에서 확인한 vault 방식(**샌드박스는 불투명한 자리표시자만 보고 실제 비밀은 egress 에서 치환**)도 같은 원리다. **에이전트가 본 적 없는 비밀은 추론 트레이스에도 남지 않는다.** 이게 이 논문이 주는 가장 실무적인 교훈이라고 본다.

### 핵심 전이 3: "보이지 않는 프롬프트 인젝션"은 어제 다룬 공적 기록 오염의 기계 판독 버전이다

네 번째 공격 벡터가 특히 고약하다. **악성 지시를 암호화 블록 안에 통째로 심어 공개 에이전트 롤아웃을 오염**시키는 것. 사람 눈에는 암호화된 잡음으로 보이고, 그걸 읽는 건 모델뿐이다.

어제 [[2026-08-12-google-search-dying-public-internet]]에서 다룬 ***"공적 기록을 오염"***(기업이 Reddit 에 콘텐츠를 심어 AI 요약을 조작)이 **사람도 읽을 수 있는 오염**이었다면, 이건 **사람이 볼 수 없는 오염**이다. 그리고 오염 매체가 "공개된 에이전트 학습 데이터"라는 점에서 **파급 경로가 더 깊다** - 한 번 오염된 롤아웃이 학습에 들어가면 되돌리기가 훨씬 어렵다.

**이번 시즌 오염 전략을 세 번째로 만난다**: [[2026-08-10-ai-wearable-surveillance-countermeasures]]에서는 **약자의 방어**(허위 데이터로 판별 비용을 올림), 어제 Walrus 에서는 **강자의 공격**(AI 요약 조작), 여기서는 **보이지 않는 공격**. **같은 기법이 위치에 따라 세 가지 얼굴을 갖는다**는 게 이제 확실해졌고, 공통점은 하나다: **비용은 언제나 판별하려는 쪽이 진다.**

### 핵심 전이 4: 정직한 급소, "숨기는 이유"가 초록 첫 문장에 적혀 있다

초록의 첫 문장이 은닉의 목적을 ***"지적 재산을 보호하고 정보 유출을 제한하기 위해"***라고 못박는다. **안전이 아니라 사업 보호가 먼저 온다.** 그리고 그 은닉 방식(서버 보관 대신 클라이언트에 암호화 블록 반환)이 **상태 비저장 API 의 운영 편의**에서 나온 선택이라는 것도 읽힌다.

**여기에 가든의 검사 도구를 적용하면 결과가 흥미롭다.** 어제 워터마킹 노트에서 확인한 대로 그 도구는 "안전 논변과 사업 이해가 같은 방향인가"를 묻는다. **추론 은닉은 명백히 사업 이해와 정렬돼 있고**(증류 방지 = 매출 방어), 논문은 그 은닉이 **오히려 새로운 공격면을 만들었다**는 걸 보여준다. 서버에 보관했다면 이 취약점은 없었다.

**그러니 이 사건의 교훈은 "암호화를 잘하자"가 아니다.** ***"LLM이 결정을 내리는 과정을 봐야 신뢰성과 보안을 확보"***한다는 HN 의 반대 논거가 여기서 힘을 얻는다 - **투명성을 줄이려는 조치가 보안을 줄인 사례**다. 다만 공정하게 덧붙이면, 증류 방지는 실재하는 사업 문제이고 완전 공개가 답이라는 것도 검증된 주장은 아니다.

## 호스피탈리티 / CRS 적용 포인트

온다가 이 취약점의 직접 대상은 아니지만(공급자 측 결함이고 이미 대응됐다), **에이전트 로그와 자격증명 취급 관행은 그대로 걸린다.**

- **에이전트 로그를 공개·공유하기 전 비밀 스캔을 형식 요건으로(전이 2).** 디버깅용 세션 로그, 이슈에 첨부하는 트레이스, 벤더 지원 요청에 붙이는 대화 기록 어디든 마찬가지다. **추론 트레이스에는 최종 답변에서 지워진 것도 남아 있을 수 있다**는 게 이 논문의 요지다.
- **자격증명을 에이전트에게 보여주지 않는 구조로(전이 2).** 게이트웨이·vault 방식으로 원본을 에이전트가 보관하지 않게 하는 것. **본 적 없는 비밀은 트레이스에 남지 않는다.** 개인 규칙에도 이미 "시크릿은 환경변수 이름만, 값 노출 금지"가 있는데, **에이전트 실행 환경에도 같은 기준이 적용되는지**는 별도 점검이 필요하다.
- **외부에서 받은 에이전트 산출물에 대한 경계(전이 3).** 협력사나 오픈소스에서 받은 에이전트 롤아웃·프롬프트 자산을 그대로 쓰면 **보이지 않는 지시가 섞여 있을 수 있다.** 사람이 읽어서 확인 가능한 형태(평문 프롬프트, 문서)만 신뢰 경계 안으로 들이는 게 안전하다.
- **적용이 먼 부분은 정직하게.** 암호화 설계, 증류 방지 정책, 공급자 대응은 온다의 의사결정 변수가 아니다. 전이되는 건 **로그 위생과 자격증명 격리** 둘뿐이다.
