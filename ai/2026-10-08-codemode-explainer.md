# Codemode란 무엇인가 - AI의 도구 호출을 코드로 묶기

> 출처: GeekNews 토픽 (원문 매체·저자 특정 실패) · GeekNews(id=34952) 경유 · 정리일 2026-10-08

> **출처 한계**: `news.hada.io` egress 차단으로 원문에 접근하지 못했다. WebSearch로 "Codemode", "Pi 1.0", "Jev 분류 모델" 등을 조합해 여러 차례 검색했지만, 이 정확한 제목의 설명형 원문(저자·매체)을 특정하지 못했다 — pi.dev 공식 문서(`pi.dev/docs/latest/codemode`)가 가장 유력한 1차 후보였으나 이 또한 egress 차단으로 직접 열람하지 못했다. 다만 **Slack 발췌가 설명하는 내용(JavaScript 샌드박스에서 Codemode 실행, 이미지 생성 모델·Jev 분류 모델·MCP 도구 활용) 자체는 이 가든이 이미 [[2026-10-01-pi-mcp-codemode]]와 [[2026-10-02-pi-1-0-release-minimal-terminal-coding-agent]]에서 GitHub PR·Releases 1차 문서로 깊게 확인해둔 내용과 정확히 일치**한다. 이 노트는 그 선행 노트들을 기반으로, 오늘 자 발췌가 추가하는 "개념 설명"과 "구체적 활용 예시"만 새로 더하는 방식으로 작성했다. hada 댓글 수, 이 글이 Pi 공식 자료를 재설명한 2차 해설인지 완전히 새로운 소스인지는 확인하지 못했다.

## 한 줄 요약

**Codemode는 AI가 도구를 하나씩 호출하는 대신, 여러 호출을 묶는 코드를 작성해 실행하는 방식이다 — 반복·병렬 처리와 결과 가공을 코드에 맡기고 필요한 결과만 모델에 전달해, 도구가 반환한 대량 데이터를 컨텍스트 창에 그대로 쌓지 않을 수 있다. Pi 1.0이 QuickJS 샌드박스에서 이 방식을 실행하며, 이미지 생성 모델과 Jev 같은 분류 모델, MCP 도구를 같은 코드 블록 안에서 엮어 쓴다.**

## 핵심 포인트

- **핵심 아이디어 — "도구 하나씩 호출" 대신 "호출을 묶는 코드 한 번"** — Slack 발췌: "Codemode는 AI가 도구를 하나씩 호출하는 대신, 여러 호출을 묶는 코드를 작성해 실행하는 방식임. 반복·병렬 처리와 결과 가공을 코드에 맡기고, 필요한 결과만 모델에 전달함." [[2026-10-01-pi-mcp-codemode]]가 1차 문서(PR #10040)로 확인한 바로는, 이게 Pi에서는 QuickJS(wasm) 샌드박스 안에서 모델이 작성한 JavaScript가 `tools.<name>(args)` 형태로 여러 도구를 비동기 호출·연결하는 구조로 구현됐다.
- **중간 결과를 컨텍스트에 안 쌓는다** — "도구가 반환한 데이터를 모두 컨텍스트 창에 넣지 않고 처리할 수 있으며, 중간 결과를 저장해 다음 호출에서도 재사용 가능." 이는 [[2026-10-01-pi-mcp-codemode]]가 밝힌 구체적 수치와 맞아떨어진다 — Pi는 50KB 또는 2,000줄을 넘는 결과를 JSON 임시 파일로 저장해 컨텍스트에 그대로 쌓이지 않게 한다.
- **Pi 1.0의 구현 — 별도 JS 샌드박스 + 이미지 생성 + Jev + MCP** — "Pi 1.0은 별도의 JavaScript 샌드박스에서 Codemode를 실행하며, 이미지 생성 모델과 Jev 같은 분류 모델, MCP 도구를 함께 활용함." [[2026-10-02-pi-1-0-release-minimal-terminal-coding-agent]]가 확인한 바로는 1.0에서 스크립트가 `models.generateImages()`를 호출해 이미지 생성 도구까지 코드 안에서 조합할 수 있게 됐다 — 오늘 발췌의 "이미지 생성 모델" 언급이 이 기능을 가리키는 것으로 보인다.
- **구체적 활용 예시 — 이슈 분류, 게임 상태 확인** — "GitHub 이슈를 일괄 분류하고 불만이 큰 항목만 추리거나, 게임 상태 확…" (발췌 절단). 이 예시는 [[2026-10-01-pi-mcp-codemode]]가 든 "Linear MCP + Jev" 조합 예시(이슈를 가져와 같은 코드 블록 안에서 Jev 분류기에 넘겨 감정 점수를 매기는 것)와 본질적으로 같은 패턴이다 — 다수 건을 MCP로 조회하고, 그 결과를 코드 안에서 즉시 Jev 같은 저비용 분류기에 넘겨 필터링한 뒤, 추려진 소수만 모델(사람이 보는 요약)에 전달한다.

## 내 생각 · 적용점

### 핵심 전이 1 — 이 가든에 이미 깊게 쌓인 Codemode 계열에 "개념 입문판"이 추가된다

[[2026-10-01-pi-mcp-codemode]]는 "왜 MCP를 반대하던 Pi가 결국 MCP를 끌고 들어왔는가"라는 **사건 중심** 기록이었고, [[2026-10-02-pi-1-0-release-minimal-terminal-coding-agent]]는 "그 기능이 1.0에서 얼마나 안정화·경량화됐는가"라는 **릴리스 중심** 기록이었다. 오늘 글은 둘 중 어느 쪽도 아니고 "Codemode가 뭔지 처음 설명하는" **개념 중심** 글로 보인다 — 다만 그 설명이 가리키는 구체적 구현(샌드박스, 50KB 임계값, exposure 속성 등)은 이미 앞선 두 노트가 먼저 확보해둔 것이라, 세 노트를 사건→릴리스→개념의 순서로 겹쳐 읽으면 Codemode라는 하나의 기능이 발표부터 안정화, 그리고 일반화된 설명으로 퍼져나가는 전체 궤적이 드러난다.

### 핵심 전이 2 — Jev가 "판단 모델"에서 "코드 안의 호출형 분류기"로 자리잡는 흐름의 재확인

[[2026-09-21-jev-field-guide-system-one-model]]은 Jev의 실제 상품성이 "정확도"가 아니라 "0.4초라는 응답 속도를 파는 것"이라고 짚었다. 오늘 글의 "GitHub 이슈를 일괄 분류하고 불만이 큰 항목만 추리기" 예시는 정확히 그 포지셔닝을 보여준다 — 수백 개 이슈를 사람이나 고가 모델로 하나씩 판단하면 느리고 비싸지만, Codemode 안에서 Jev를 호출형 분류기로 쓰면 "싸고 빠른 1차 필터 → 추려진 소수만 정교한 모델로" 흐름이 성립한다. Jev는 독립된 "모델"이 아니라 **코드 안에서 함수처럼 호출되는 판단기**로 쓰이는 사례가 이 가든에 또 하나 쌓인다.

### 핵심 전이 3 — "도구 정의가 컨텍스트를 먹는다"는 선행 비판의 해법 축과 다시 만남

[[2026-05-29-mcp-is-dead-cli-skills]]가 지적한 "77개 도구 정의만으로 21,077토큰 소모"라는 문제의 해법은 두 갈래였다 — 프로토콜을 고치거나(MCP 로드맵의 progressive discovery), 실행 환경 자체를 코드 샌드박스로 바꾸거나(Codemode). 오늘 글의 "필요한 결과만 모델에 전달"이라는 설명은 후자의 핵심을 한 문장으로 요약한 것이라, 이 가든의 MCP 비용 논쟁 계열에 같은 결론이 다시 한번 확인되는 셈이다.

## 호스피탈리티 / CRS 적용 포인트

이 패턴은 CRS 업무에 비교적 직접 적용 가능하다. [[2026-10-01-pi-mcp-codemode]]에서 이미 낸 결론과 같지만, 오늘의 "이슈 일괄 분류" 예시로 한 번 더 구체화하면: CRS 운영팀이 Claude Code에 PMS·채널매니저 MCP를 붙여 **"지난 한 달 예약 변경 요청 전체를 조회하고, 그중 환불 분쟁 소지가 큰 건만 추려서 보고서로 달라"** 같은 작업을 시킬 때, 수백 건의 예약 데이터를 전부 모델 컨텍스트에 올리는 대신 코드로 조회·필터링하고 분쟁 가능성이 높은 소수만 모델에 넘기는 흐름이 바로 이 글의 "GitHub 이슈 분류" 예시와 동형이다. Jev 같은 전용 분류 모델이 없더라도, Claude Code의 서브에이전트나 저비용 모델을 같은 역할로 쓸 수 있다.
