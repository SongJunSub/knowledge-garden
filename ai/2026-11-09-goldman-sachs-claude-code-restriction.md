# 골드만 삭스, 은행원과 트레이더의 Claude Code 사용 제한

> 출처: 원문 미확인 (GeekNews 경유, id=36827, 원 보도는 Bloomberg로 추정) · 정리일 2026-11-09

> **출처 한계.** `news.hada.io`가 egress 차단되어 GeekNews 글 자체는 못 읽었다. 다만 WebSearch로 dealroom.co, Crowdfund Insider, FStech, AIWeekly 등 **다수의 독립 2차 매체가 같은 사실(Bloomberg 보도 기반으로 추정)을 일관되게 보도**하고 있어, 사건의 실재와 핵심 윤곽은 신뢰도 높게 교차확인됐다고 판단한다. 다만 영향받은 인원수는 매체마다 다르거나(일부 "약 10,000명" 언급, 일부 미기재) 생략되어 있어 정확한 규모는 확정하지 않는다.

## 한 줄 요약

**Goldman Sachs가 생산성과 위험 검토를 거쳐 Claude Code와 GitHub(Copilot) 사용을 엔지니어·퀀트 "스트랫(strats)" 중심으로 제한하면서, 대부분의 은행원과 트레이더가 업무에서 두 도구에 접근할 수 없게 됐다 — 불과 7월까지 CIO가 비기술 직원의 바이브 코딩을 긍정적으로 평가했던 것과 대비된다.**

## 핵심 포인트

- Goldman Sachs가 **생산성과 위험 검토**를 거쳐 Claude Code와 GitHub 사용을 **엔지니어 중심으로 제한**하여, 대부분의 은행원과 트레이더가 업무에서 두 도구를 사용할 수 없게 됐다(Slack 발췌).
- 제한 대상은 **스스로 코드를 작성하고 실행하는 외부 에이전트**이며, 여러 회사의 모델을 활용하는 **사내 AI 비서는 계속 전사적으로 이용 가능**하다(Slack 발췌) — 즉 "AI 자체"가 아니라 "스스로 코드를 실행하는 자율 에이전트"라는 특정 범주만 좁힌 제한이다.
- 트레이더들은 이 도구로 **고객 거래 흐름 추적과 시장·포지션 모델링** 등을 수행해 왔으며, **7월까지만 해도 CIO가 비기술 직원의 AI 도구 개발을 긍정적으로 평가**했다(Slack 발췌).
- WebSearch 교차확인: 접근이 유지되는 대상은 **소프트웨어 엔지니어와, 트레이딩과 개발을 잇는 전문가인 퀀트 "스트랫(strats)"**이다.
- WebSearch 교차확인: 이 변화는 **10월 사내 지침**과 연결된 것으로 보도되며, Goldman은 "실험 단계가 끝났다"는 취지로 생산성·리스크 우려를 이유로 들었다.
- WebSearch로 확인된 불확실 지점: 영향받은 정확한 인원수(일부 매체는 "약 10,000명의 은행원·트레이더"로 추정하나 다른 매체는 숫자를 언급하지 않음), 그리고 **비엔지니어 직원에게 대체 도구가 제공됐는지는 불명확**하다.

## 인상 깊은 문장

## 내 생각 · 적용점

### 핵심 전이 1 — [[2026-07-03-alibaba-bans-claude-code-backdoor-risk]]와 대조: "보안 우려"와 "생산성·리스크 검토"는 다른 축의 제한 논리

Alibaba의 Claude Code 금지는 "중국 연계 사용자 식별 기능"이라는 **보안·주권 우려**가 직접적 트리거였다. Goldman의 제한은 그와 달리 **내부 생산성·리스크 관리 관점**(비전문가가 자율 코드 실행 도구를 다루는 데서 오는 운영 리스크)에서 나온 것으로 보인다 — 같은 "Claude Code 사용 제한"이라는 결과가 전혀 다른 두 위협 모델(외부 보안 vs 내부 통제)에서 나올 수 있음을 보여주는 대조 사례다.

### 핵심 전이 2 — [[2026-11-03-aws-claude-enterprise-dlp-bedrock-guardrails]]와 연결: "전면 금지" 대 "가드레일로 제어"라는 두 가지 엔터프라이즈 대응

그 노트는 Bedrock Guardrails로 DLP 정책을 Claude Enterprise에 적용해 **사용은 허용하되 특정 데이터 유출을 판정 서버가 막는** 접근을 다뤘다. Goldman은 반대로 **범주 자체를 좁혀 비전문가의 접근을 끊는** 접근을 택했다. 두 사례를 겹쳐 보면, 엔터프라이즈가 자율 코딩 에이전트의 리스크를 다루는 방식이 "기술적 가드레일"과 "조직적 접근 제한" 두 축으로 나뉘고 있음을 알 수 있다 — Goldman이 왜 가드레일이 아니라 접근 제한을 택했는지는 이 자료들로는 알 수 없지만, 금융권처럼 **규제 민감도가 극히 높은 도메인에서는 기술적 가드레일보다 조직적 차단이 먼저 작동**할 수 있음을 시사한다.

## 호스피탈리티 / CRS 적용 포인트

**적용 가능성 있음(제한적).** CRS/채널매니저 환경에서도 비개발 직군(세일즈·운영)이 AI 코딩 에이전트에 직접 접근해 요금 로직이나 연동 스크립트를 "스스로 실행"하게 두는 것은 Goldman이 우려한 것과 같은 리스크(검증되지 않은 자율 실행이 실거래에 영향)를 안고 있다. 다만 "사내 AI 비서는 전사 허용, 자율 코드 실행 에이전트는 엔지니어로 제한"이라는 **범주 구분**은 CRS 조직에도 바로 참고할 만한 원칙이다 — AI를 금지하는 게 아니라, "스스로 실행까지 하는 에이전트"와 "조언·초안만 주는 비서"를 분리해서 권한을 설계하는 것.
