# 항상 작동하는 에이전트 구축하기 (Anthropic) — 에이전트 루프가 아니라 이벤트 인박스가 진실 공급원이어야 하고, 메모리는 '다시 조회 못하는 것'만 담아야 한다

> 출처: [Building always-on agents](https://claude.com/blog/building-always-on-agents) (Anthropic) · 정리일 2026-11-21

## 한 줄 요약

**상시 작동하는 에이전트는 새로운 에이전트 루프가 필요한 게 아니라, 이벤트 인박스·타이머·아웃박스·권한·메모리라는 다섯 가지 평범한 시스템 설계 요소를 제대로 배치하는 문제다 — 대부분은 세션 간 맥락을 기다리다가 이벤트가 발생하면 짧게 실행되는 구조이고, 각 요소를 "조용히 시작해 점점 신뢰를 얻는" 방향으로 설계하라는 것이 핵심 조언이다.**

## 핵심 포인트

- **이벤트 인박스가 단일 진실 공급원**이다. 웹훅·스케줄·백그라운드 작업을 먼저 DB 테이블에 적재하고, 워커 하나만 활성화해 처리한다. "**The inbox should be the source of truth**"— 에이전트가 직접 외부 신호를 받는 게 아니라 인박스를 거치게 한다.
- **타이머**는 두 종류로 나눈다 — follow-up(짧은 후속 체크)과 schedule(정해진 주기). 별도 저장소에 두고, 스케줄러가 만기된 타이머를 다시 인박스로 밀어넣는 구조.
- **아웃박스**는 발송 조절이나 오류 복구가 실제로 필요할 때만 도입한다 — 처음부터 복잡하게 짓지 않는다.
- **권한**: 자격증명은 에이전트 코드 밖의 프록시가 주입하고, 분류기가 고위험 행동을 미리 차단하며, 판단이 애매한 도구 호출은 사용자 승인을 기다리는 "보류" 상태로 둔다.
- **메모리**: 파일 디렉터리 + DB/오브젝트 스토리지 조합. "**memory should only hold what the agent can't look up again**" — 다시 조회할 수 있는 정보는 저장하지 말고, '드리밍'(주기적 정리 루틴)으로 오래된 메모리를 정리한다.
- 반복되는 설계 원칙: "**start quiet and then earn more of the user's attention over time**" — 새 기능은 조용히 시작해서 신뢰가 쌓인 뒤에야 사용자의 주의를 더 가져간다. 시스템 프롬프트·도구 정의·메모리는 매 실행마다 드는 고정비용이므로 간결하게 유지하고 프롬프트 캐싱으로 상쇠한다.

## 내 생각 · 적용점

### 핵심 전이 1 — "자격증명은 에이전트 밖, 승인은 보류 상태로" = 이미 다른 벤더에서도 반복된 패턴

권한 설계(프록시가 자격증명 주입 + 분류기 사전 차단 + 보류 도구호출)는 [[2026-11-04-aws-bedrock-managed-agents-openai]]에서 본 "에이전트 구현 대신 IAM과 CloudTrail만 남는다"는 AWS Bedrock Managed Agents의 설계와 정확히 같은 축이다. 서로 다른 두 벤더(Anthropic·AWS)가 독립적으로 "에이전트 내부에 권한 로직을 넣지 말고 밖의 레이어로 뺀다"는 같은 결론에 도달했다는 건, 이게 특정 벤더의 선호가 아니라 **에이전트 보안 설계의 수렴된 정답**에 가깝다는 신호다.

### 핵심 전이 2 — "이벤트 인박스"는 결국 [[2026-10-20-harness-engineering-101-python-300-lines]]의 "실패 → 최소 수정 → 비용" 순서를 시스템 레벨로 확장한 것

하네스 설계를 다룬 이전 노트는 에이전트 한 번의 실행 안에서의 점진적 설계를 다뤘는데, 이 글은 그걸 "여러 번의 비동기 실행을 어떻게 연결할지"로 확장한다. 인박스 패턴은 사실 메시지 큐·이벤트 소싱이라는 전통적인 분산 시스템 패턴을 에이전트에 그대로 가져온 것 — **에이전트 설계의 다음 단계는 결국 평범한 백엔드 아키텍처 원칙의 재적용**이라는 걸 보여준다.

### 핵심 전이 3 — "조용히 시작해 신뢰를 쌓는다"는 UX 원칙이 자동화 범위 확장의 기본값이어야

이 원칙은 롤아웃 전략으로서 중요하다. 상시 작동 에이전트가 처음부터 사용자 주의를 과도하게 끄는(알림 폭탄, 과도한 승인 요청) 설계를 하면 신뢰를 잃는다 — [[2026-11-04-postman-silent-agent-plugin-install]]의 "벤더가 심은 훅이 개발자 모르게 실행된다"는 반대 사례(동의 없이 침투)와 대조하면, "조용히 시작"은 사용자 동의·투명성과는 별개로 **처음엔 위험도 낮은 행동만 하고 점진적으로 권한을 넓힌다**는 뜻이지 몰래 하라는 뜻이 아님을 분명히 구분해야 한다.

## 호스피탈리티 / CRS 적용 포인트

**적용 가능성 높음.** CRS에 상시 작동 에이전트(예: 예약 변경 알림 처리, 결제 실패 재시도, 야간 문의 자동 응대)를 두려면 이 다섯 요소가 거의 그대로 체크리스트가 된다 — 웹훅(PMS 연동, 결제 게이트웨이 콜백)을 먼저 인박스 테이블에 적재하고, 자격증명은 에이전트 밖 프록시가 주입하며, 환불·취소처럼 고위험 행동은 분류기로 사전 차단하거나 보류 상태로 사람 승인을 기다리게 한다. "메모리는 다시 조회 못하는 것만" 원칙도 PMS·CRS를 그대로 조회할 수 있는 정보(현재 재고·요금)는 저장하지 말고 조회 시점에 받아오라는 설계 가이드로 직접 쓸 수 있다.
