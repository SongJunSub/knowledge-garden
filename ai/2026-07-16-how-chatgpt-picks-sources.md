# ChatGPT는 실제로 어떻게 출처를 고르는가 (Suganthan Mohanadasan) — 네트워크 트래픽 1,240건 분석: 모델은 '가져오기(fetch)'와 '인용(cite)'을 분리하고, 사실은 네 페이지에서·의견은 남의 페이지에서 읽으며, 애초에 검색할 가치가 있을 때만 검색한다

> 출처: [How ChatGPT Picks Sources](https://suganthan.com/blog/how-chatgpt-picks-sources/) (Suganthan Mohanadasan / GeekNews GN⁺ 요약) · 정리일 2026-07-16

## 한 줄 요약

**한 연구자가 ChatGPT Pro 세션의 브라우저 네트워크 응답(약 1,240개 소스 레코드)을 뜯어 검색 파이프라인을 역설계했다. 세 가지가 핵심이다. ①ChatGPT는 질문의 *표현*을 보고 버킷으로 분류해 "검색할 가치가 있을 때만" 검색하며, 최신성이 중요한 고위험 질문(예: 최신 당뇨 치료지침)조차 `text`로 분류돼 학습데이터로 답하기도 한다. ②페이지를 컨텍스트에 로드하는 '가져오기(fetch)'와 특정 문장의 근거로 붙는 '인용(cite)'은 완전히 다른 사건이다 — Reddit은 278번 가져와 11번 인용(3.96%), YouTube는 201번 가져와 0번 인용(트랜스크립트 없이 메타데이터만). ③모델은 사실(가격·스펙)은 네 페이지에서 읽고 평판·의견은 제3자 페이지에서 읽으며, 스스로를 인용하지 못한다. 그래서 저자의 결론은 "ChatGPT는 검색엔진이 아니니 SEO를 멈춰라 — 읽히게 쓰되, 추천은 다른 곳에서 벌어라."**

## 핵심 포인트

- **방법론: 패킷 스니핑이 아니라 DevTools 네트워크 탭** — TLS 암호화로 페이로드를 직접 못 읽어, 브라우저에서 TLS 복호화된 JSON 응답을 분석. **Pro 계정 1명 · 며칠 · 쿼리 수십 개 · 소스 레코드 ~1,240개**. 저자는 **구조적 사실(높은 신뢰)**과 **빈도 관찰(방향성만)**을 명시적으로 구분한다(작은 표본 자인).
- **`result_source` = 데이터가 어느 파이프라인에서 왔는가 (4분류)** —
  - **serp**: 오픈웹 기본선(Yahoo, StreetInsider 등, 뉴스 중심).
  - **labrador**: *라이선스 계약된 출판사 화이트리스트*(Reuters·가디언·WSJ·FT·Wikipedia·arXiv). 스니펫 ~1,080자로 **거의 전문 추출**. 진입 불가에 가까운 닫힌 클럽.
  - **bright**: Bright Data 상업 스크래퍼. **쇼핑·금융·날씨·로컬 지배**(Reddit·Forbes·rtings 포함).
  - **oxylabs**: 경쟁 스크래퍼. 지역·로컬 언론(중동 Khaleej Times·Gulf News 등).
- **질의 분류(`turn_use_case`) — 검색을 아예 건너뛰기도 한다** — 6버킷 중 **`text`는 웹 접근 없이 학습데이터로 답변**("타이어 교체법", "Python 함수"). **위험: "제2형 당뇨병 최신 치료지침" 같은 시의적 고위험 질문도 `text`로 분류돼 미검색.** 테스트한 최신성 질문 10개 중 3개가 검색 없이 처리. **"주제가 아니라 표현(wording)이 버킷을 정한다"** — "best coffee near me"→local, "best 4K TVs to buy"→shopping, "…with reviews"→일반 검색.
- **팬아웃(fan-out): 하나의 질문 → 여러 하위 검색** — 빠른 모델은 재표현 1개, **thinking 모델은 ~15~40개 하위 쿼리**. 3가지 행동: ①`site:vendor.com/pricing` 직접 프로브, ②**가격을 추정 검색한 뒤 페이지에서 `$`·`€`·`99` 문자를 grep해 검증**, ③원 질문에 없던 도구(예: Scrunch AI)도 자동 발견·추격.
- **가져오기 ≠ 인용 ≠ 언급 (세 개의 별개 상태)** — **fetch**(컨텍스트 로드, 사용자 미확인) / **cite**(특정 문장의 근거, 클릭 가능한 각주) / **mention**(브랜드명만 노출, 출처 아님). 수치: **Reddit 278 fetch → 11 cite(3.96%, 최고)**, **YouTube 201 fetch → 0 cite(0%, 트랜스크립트 없이 메타데이터만)**. 외부 검증(Ahrefs 140만 프롬프트): Reddit 1.93% · YouTube 0.51%. **인용은 특정 문장에 바인딩(주제 연관성만으론 부족)**, 도메인별 중복제거(**약한 20페이지 = 강한 1페이지**), 그리고 **"자기 자신은 인용 불가"** — 평판 주장은 반드시 제3자 페이지에서.
- **파싱: 평문 HTML이 아니면 안 보인다** — 사실·숫자·가격은 순수 텍스트여야 하고 **JS 동적 로딩·PDF 내장·이미지 텍스트는 실패**. 실제 CoT 기록: *"가격이 검색결과에 없음, 아마 JavaScript로 숨김"* → 모델이 **원본 사이트를 포기하고 G2 제3자 리뷰로 폴백**.
- **저자의 실무 결론(AEO)** — ①질문이 *애초에 검색을 하는지* 먼저 확인, ②labrador 계층은 닫혔으니 PR·제3자 커버리지·Reddit으로 스크래퍼 도달 페이지에 진입, ③사실은 평문 HTML, ④**클레임 1개당 강한 페이지 1개**, ⑤의견·추천은 Reddit·리뷰허브(rtings·TechRadar)에서. 요약: **"사실은 네 페이지, 의견은 남의 페이지, 검색은 그럴 가치가 있을 때만."**
- **부수 발견** — 로컬은 `local_results_limit: 2`(**"상위 2개 아니면 미노출"**), `personal_sources`로 과거 대화·Gmail·파일이 자동 포함돼 **같은 질문도 사용자마다 다른 답**(가시성 점수가 흔들림), 순위 로직은 서버측(불가시). 저자는 이를 시각화하는 Chrome 확장 **FanoutFox** 공개.

## 댓글

**댓글 0개.** GN⁺가 원문 블로그(suganthan.com)를 직접 한국어로 요약한 신규 포스트(게시 ~53분)로, hada 댓글도 HN·Lobste.rs 큐레이션 블록도 없다(본문·댓글 패스 2회 확인). 데이터의 한계도 저자 스스로 밝힌 그대로 안고 읽어야 한다 — **표본 n=1(1인·1세션·며칠), JSON에서 역설계한 필드명, 빈도 수치는 방향성일 뿐 권위 아님**. 게다가 저자는 이 파이프라인을 시각화하는 확장(FanoutFox)을 파는 SEO 업계 인물이라 **경미한 이해관계**가 있다. 그럼에도 *구조적 사실*(fetch≠cite, self-can't-cite, 평문 HTML 요구, 검색 스킵 버킷)은 파이프라인의 존재 자체를 드러내므로 표본 크기와 무관하게 유효하다.

## 내 생각 · 적용점

### 핵심 전이 1 — fetch ≠ cite = 어제 글의 "도달 ≠ 전환"과 정확히 같은 구조

이 글의 가장 강한 발견은 **가져오기(fetch)와 인용(cite)의 분리**다. YouTube 201 fetch / 0 cite는 극단적 사례 — *많이 읽혔다고 근거로 채택되는 게 아니다.* 이건 어제 정리한 [[2026-07-16-build-and-scale-consumer-apps]]의 **"도달(조회수) ≠ 전환"**, 그리고 [[2026-07-13-how-to-kill-churn]]의 **"평균은 서로 다른 코호트를 숨긴다"**와 정확히 같은 데이터 리터러시다. 세 글의 공통 교훈: **퍼널 상단의 큰 숫자(노출·fetch·트래픽)는 거짓말을 한다 — 측정은 아래 레이어(전환·cite)에서 해야 한다.** 브랜드가 "AI 답변에 우리 사이트가 몇 번 fetch됐다"를 지표로 삼으면 YouTube의 함정에 빠진다. 의미 있는 KPI는 **cite율**이고, 그건 특정 문장에 바인딩되는 파싱 가능성이 좌우한다.

### 핵심 전이 2 — "모델을 1차 독자로" 담론에 드디어 기계적 디테일이 붙었다

[[2026-07-13-short-form-video-b2b-search-and-ai-answers]]는 *"사람이 아니라 모델을 1차 독자로 삼아 콘텐츠를 구조화하라"*, [[2026-06-08-search-market-fit-aeo-seo]]는 *"검색량이 아니라 의도에서 출발하라"*고 했다. 둘 다 방향은 옳지만 추상적이었다. 이 글은 **모델이 실제로 어떻게 읽는가**의 구체를 준다: 평문 HTML만 파싱, 인용은 문장 단위 바인딩, 도메인 중복제거, `$`/`€` grep, `site:` 프로브. 즉 **AEO는 신비주의가 아니라 접근성·시맨틱 HTML·프로그레시브 인핸스먼트 체크리스트의 재발견**이다 — 모델은 사실상 "돈을 쓰게 만드는 스크린리더"이고, JS 뒤에 가격을 숨긴 사이트는 접근성에서 지던 것을 이제 매출에서도 진다.

### 핵심 전이 3 — 가장 무서운 발견: 확률적 라우터가 "검색할지"를 조용히 틀리게 결정한다

고위험 시의적 질문("최신 당뇨 치료지침")이 `text` 버킷으로 분류돼 **사용자에게 알리지 않고 학습데이터(구식)로 답할 수 있다**는 게 이 글에서 가장 중요한 경고다. 이건 **LLM 위임 경계 문제**(시스템 방법론 §7)의 실물 사례다 — *비결정적 라우터가 "지금 접지(grounding)가 필요한가"라는, 하필 접지가 가장 필요한 질문에서 틀린다.* [[2026-07-13-i-love-llms-i-hate-hype]]의 "가치 창출과 가치 포획은 다르다"와 결이 다른, **신뢰성**의 문제다. 실무 함의: ChatGPT 검색 위에 무언가를 얹는다면 **"모델이 검색했는가"를 절대 가정하지 말고**, 실시간·고위험 사실은 결정적 경로로 별도 접지해야 한다. 사용자에게 "이건 검색 없이 답한 것"이라는 신호가 없다는 점이 특히 위험하다.

### 핵심 전이 4 — "자기 자신은 인용 불가" = 신뢰는 빌리는 것, 자기주장이 아니다

**self-can't-cite**(평판 주장은 제3자 페이지에서만)는 얕은 파싱 규칙처럼 보이지만 실은 깊은 구조다 — **모델에게 당신은 스스로의 평판을 보증할 수 없다.** 이건 어제 글 [[2026-07-16-build-and-scale-consumer-apps]]의 **"인플루언서 = 청중과 이미 쌓인 신뢰를 빌리는 것"**과 같은 원리의 기계 버전이다: *신뢰·평판은 제3자로부터 빌려오는 것이지 자기가 선언하는 게 아니다.* 그래서 AEO의 절반은 내 페이지를 읽히게 만드는 일(사실)이고, 나머지 절반은 Reddit·리뷰허브에 제3자 커버리지를 만드는 일(의견)이다. [[2026-05-18-system-of-record-to-system-of-intelligence-a16z]]식으로 말하면, 사실은 내가 소유한 기록시스템에서 나오지만 신뢰는 네트워크가 부여한다.

## 호스피탈리티 / CRS 적용 포인트

이 글은 온다(호스피탈리티/CRS)에 **이례적으로 직접적**이다 — 숙박·예약 콘텐츠가 바로 스크래퍼(bright/oxylabs)가 지배하는 *쇼핑·로컬·가격* 카테고리이고, JS로 가격을 숨기는 관행이 여행업에 만연하기 때문이다.

- **가격·객실 정보를 JS 뒤에 숨기면 모델에게 안 보인다.** 날짜 피커·동적 요금 위젯 뒤의 가격은 파싱 실패 → 모델이 **OTA·제3자로 폴백**한다(위 G2 폴백과 동일). CRS/호텔 페이지가 ChatGPT 답변에 직접 인용되려면 **핵심 요금·정책을 평문 HTML로도** 노출해야 한다.
- **로컬은 "상위 2개 아니면 미노출"**(`local_results_limit: 2`). 지역 숙박 질의에서 노출 경쟁이 극단적으로 좁다는 뜻 — 로컬 SEO/AEO의 판돈이 크다.
- **평판은 자기 사이트로 못 만든다.** "우리 호텔이 최고"는 self-can't-cite로 걸러진다 → Reddit·리뷰허브·업계 커버리지 같은 제3자 신뢰 자산이 필요(위 핵심 전이 4).
- **실시간 사실을 ChatGPT에 의존하지 말 것.** 게스트가 "지금 예약 가능?/현재 요금?"을 물으면 모델이 검색 없이 구식 답을 줄 수 있다 — 실시간 재고·요금은 온다 자체 채널(결정적 경로)이 진실의 원천이어야 한다.
