# Amazon Bedrock 기반 PolicyGuard — 코딩 어시스턴트를 위한 Pre-Model Semantic DLP

> 출처: [Amazon Bedrock 기반 PolicyGuard: 코딩 어시스턴트를 위한 Pre-Model Semantic DLP 프레임워크](https://aws.amazon.com/ko/blogs/tech/amazon-bedrock-based-sematic-dlp/) (AWS 한국 기술 블로그) · 정리일 2026-08-24

> **출처 한계 먼저 밝힌다**: `aws.amazon.com`이 이 세션의 네트워크 egress 정책상 차단돼 원문을 한 줄도 읽지 못했다. Slack이 전달한 요약 불릿(잘림)만으로는 부족해 WebSearch로 보강했고, 그 결과 같은 이름의 프레임워크를 다룬 **arXiv 논문 "PolicyGuard: Prompt-Configurable Semantic DLP for LLM Coding Agents" (arXiv 2608.02687)**과 **AWS 공식 샘플 저장소 `aws-samples/sample-policy-driven-code-assistant-guardrails`**를 찾아 그 두 곳의 내용으로 이 노트를 재구성했다. 아래 핵심 포인트·수치·아키텍처는 **AWS 블로그 원문이 아니라 이 논문·샘플 저장소에서 확인한 것**이다 — 이름·문제의식·수치가 정확히 맞아떨어져 같은 연구를 다룬 것으로 보이지만, **AWS 블로그가 정확히 이 논문을 어떤 프레이밍으로 소개했는지는 검증하지 못했다.** 참고로 arXiv에는 이름이 겹치는 **다른 논문**("PolicyGuard: A Dialogue-Grounded Sub-Agent Verifier for Policy Adherence in LLM Agents", arXiv 2606.29225)도 존재한다 — 이건 코딩 에이전트 DLP와 무관한 별개 논문이라 이 노트에서 배제했다.

## 한 줄 요약

**PolicyGuard는 코딩 에이전트에 입력된 프롬프트가 외부 LLM에 전달되기 전(pre-model) 가로채, 정규식이 아니라 자연어로 쓴 정책 문서를 기준으로 LLM 스스로 분류·차단하는 프레임워크다. 핵심은 "policy-as-prompt" — DLP 판단 기준이 코드가 아니라 평문 정책 파일에 있어서, 엔지니어가 아닌 보안·컴플라이언스 담당자도 재학습 없이 파일 수정만으로 조직별 정책을 바꿀 수 있다. 2,000개 다국어 프롬프트 평가에서 차단율(EBR) 96.5%·오탐률(FPR) 3.0%를 보고했고, 같은 정책을 4개의 서로 다른 LLM에 그대로 적용해도 86.4~96.5% 차단율이 유지됐다는 "정책의 모델 간 이식성"이 두 번째 핵심 주장이다.**

## 핵심 포인트

- **문제의식** — 코딩 에이전트는 자유 형식 자연어 프롬프트를 받는다. 사용자가 디버깅·예시 작성 중 **자격증명·PII·사내 기밀을 프롬프트에 무심코 포함시킬 수 있다.** 기존 DLP는 *"경직된 정규식 패턴, 모델 파인튜닝, 커스터마이징이 제한적인 벤더 종속 분류기"* 중 하나에 의존한다는 게 논문이 짚는 한계다.
- **Pre-model interception** — PolicyGuard는 프롬프트가 실제 코딩 어시스턴트 모델(Claude 등)에 도달하기 **전** 별도의 "세이프가드 에이전트"가 먼저 프롬프트 의도를 자연어 정책 문서와 대조해 분류한다. AWS 샘플 저장소 기준 실제 아키텍처는 **4계층**이다 — ①IDE의 코드 어시스턴트 에이전트(예: Claude Code) → ②Anthropic 호환 Messages API로 요청 라우팅 → ③**세이프가드 에이전트**(`gpt-oss-safeguard-120b` 모델이 정책 문서와의 일치도를 분류해 위험 요청 차단) → ④통과한 요청만 Claude + Amazon Bedrock Guardrails(PII·금지 주제 등 결정론적 필터)로 전달. **Claude Code 연동은 `ANTHROPIC_BASE_URL`을 로컬 프록시로 돌리는 방식**이어서, 기존 코딩 어시스턴트 워크플로를 바꾸지 않고 앞단에 검사 레이어를 끼워 넣는 구조다.
- **Policy-as-prompt 패러다임** — DLP 분류 기준 전체가 **평문 정책 문서**로 정의된다. 코드 변경도, 모델 재학습도 없이 **비엔지니어(보안 엔지니어·컴플라이언스 담당자·개발자)가 텍스트 파일만 고치면 정책이 바뀐다.** 샘플 저장소의 실제 정책 파일 예시: `out-of-scope.md`(코딩 어시스턴트 범위 밖 요청 차단), `pii-phi-protection.md`(개인정보·의료정보 생성 방지), `prompt-injection.md`(프롬프트 인젝션·탈옥 탐지), `risk-classification.md`(저/중/고/치명적 위험도 분류).
- **평가 방법론** — 저자들은 *"sealed evaluation protocol"*(템플릿-패밀리 단위 데이터 분할·숨겨진 홀드아웃·고정된 테스트셋)로 일반화 성능을 엄격히 측정했다고 주장한다. **927개 프롬프트로 구성된 고정 테스트셋에서 96.5% EBR·3.0% FPR**, 별도 **217개 숨겨진 홀드아웃에서는 100% 정확도**를 보고했다(2,000개 다국어 프롬프트 전체 평가 중 일부).
- **모델 간 이식성** — 같은 정책 문서를 수정 없이 **4개의 서로 다른 LLM**에 적용해도 **86.4~96.5% EBR**을 유지했다는 게 두 번째 주요 주장 — 특정 벤더 모델에 종속되지 않는다는 근거로 제시된다.
- **저자** — WebSearch로 확인한 바로는 **박규태(Kyutae Park, AWS)**, **김정원(Jungwon Kim)**·**심대열(Daeyeol Shim, 이상 OpenAI 소속으로 추정)** — **AWS와 OpenAI 소속 연구자가 함께 이름을 올린 논문**으로 보인다. 이 구성이 사실이라면 통상 경쟁 관계로 다뤄지는 두 회사가 코딩 에이전트 보안이라는 문제에서는 공동 연구를 했다는 뜻인데, **이 저자 정보 자체는 검색 스니펫으로 확인한 것이라 확정적이지 않다.**

## 댓글

**GeekNews 경유가 아니라 Slack "TechArticles" 봇이 AWS 블로그를 직접 링크한 경로**라 hada 댓글 자체가 존재하지 않는다. HN/Lobsters 큐레이션 여부도 확인할 수단이 없다 — WebSearch로 이 AWS 블로그 URL이나 "PolicyGuard" 키워드를 겨냥한 HN 스레드를 찾지 못했다(코딩 에이전트 DLP를 다루는 인접 논문들만 여럿 검색됐을 뿐).

**읽을 때 감안**
- ①**이 노트의 근거 대부분이 AWS 블로그 원문이 아니라 arXiv 논문·GitHub 샘플이다.** 블로그가 이 연구를 그대로 소개했는지, 아니면 다른 각도(예: 실제 도입 사례·수치 업데이트)로 재구성했는지 확인 못 했다 — **"AWS 블로그가 말한 것"과 "내가 다른 경로로 확인한 것"을 섞지 않으려 애썼지만, 완전히 분리하지 못했을 위험이 있다.**
- ②**성능 수치는 저자 자체 보고다.** 96.5% EBR·3.0% FPR·100% 홀드아웃 정확도는 **독립 3자 재현 검증이 없는 저자 자체 평가**다. "sealed evaluation protocol"이라는 방법론적 방어 장치가 있다는 게 다른 벤더 주장([[2026-08-02-openai-codex-security-oss]]에서 지적한 재현 불가능한 능력 주장)보다는 낫지만, **여전히 저자가 설계하고 저자가 채점한 평가**라는 한계는 남는다.
- ③**AWS와 OpenAI가 공저했다는 정보가 특히 검증도가 낮다.** WebSearch 요약 문장에서 뽑아낸 것이라, 소속·이름 표기가 정확한지 원문 논문 PDF로 재확인하지 못했다.
- ④**"AWS 공식 블로그가 자사 Bedrock 위에서 도는 프레임워크를 소개한다"는 구도 자체가 발행자 이익과 정렬돼 있다** — Bedrock 사용을 늘리는 방향의 서사일 가능성을 감안해야 한다(단, 실제로 GitHub 샘플 코드가 공개돼 있어 검증 가능성 자체는 열려 있다는 점은 다르다).
- ⑤**927·217·2,000이라는 숫자가 정확히 일치하는지 재확인이 필요하다** — 두 차례 WebSearch에서 같은 숫자가 반복 등장해 신뢰도를 어느 정도 높였지만, 원문 표·정확한 소수점까지 대조하지는 못했다.

## 내 생각 · 적용점

### 핵심 전이 1 — DoorDash의 게이트웨이가 "나가는 도구 호출"을 통제했다면, PolicyGuard는 "나가는 프롬프트"를 통제한다 — 같은 문제의 대칭축

[[2026-08-10-doordash-ai-agent-gateway]]는 에이전트가 **외부 도구·API를 호출할 때** 자격증명·권한·감사를 중앙 게이트웨이로 강제하는 구조였다 — *"호출자 인증 → 권한 확인 → 승인된 도구 노출 → 자격증명 주입 → MCP 서버 전달 → 사용 기록."* PolicyGuard는 방향이 반대다. 에이전트가 **외부 LLM에 프롬프트를 보낼 때** 그 콘텐츠 자체가 안전한지 먼저 검사한다. 하나는 "무엇을 할 수 있는가"(도구 접근), 다른 하나는 "무엇을 말할 수 있는가"(콘텐츠)를 통제한다는 점에서, 에이전트가 조직 경계를 넘나드는 두 개의 서로 다른 표면을 각각 다루는 사례다. DoorDash 노트가 확인한 원칙 — *"통제된 경로가 셀프서비스가 아니면 팀은 우회하게 된다"* — 은 PolicyGuard에도 그대로 걸린다. 3.0% 오탐률이 실무에서 얼마나 거슬리느냐에 따라, 개발자들이 이 pre-model 검사를 우회할 방법(다른 엔드포인트 직접 호출 등)을 찾을지가 이 프레임워크의 실질적 시험대일 것이다.

### 핵심 전이 2 — "평문 정책 파일로 비엔지니어가 직접 수정"은, 최근 확인한 "불투명화 vs 감사 가능성" 축에서 명확히 투명성 쪽에 선다

[[2026-07-15-codex-encrypting-subagent-prompts-audit-gap]]는 Codex가 서브에이전트 간 통신을 암호화하면서 **사람이 읽을 수 있는 감사 로그가 사라진** 사례였다 — 벤더의 IP 보호 유인과 사용자의 감사·이해 유인이 정면으로 충돌한 사례로 정리했다. PolicyGuard의 설계는 정확히 반대 방향을 택한다 — DLP 판단 기준 자체를 **평문 정책 문서**로 만들어, 코드를 못 읽는 보안 담당자도 정책을 직접 읽고 고칠 수 있게 열어둔다. 같은 "에이전트 사이 또는 에이전트-모델 사이 무언가를 가로챈다"는 설계인데, 하나는 그 내용을 암호화로 숨기는 쪽으로, 다른 하나는 정책 자체를 평문으로 공개하는 쪽으로 갔다 — **가로채는 레이어를 만들 때 그 레이어의 판단 기준을 누가 검사할 수 있게 할 것인가**는 설계자가 명시적으로 선택해야 하는 문제라는 걸 두 사례가 양쪽에서 보여준다.

### 핵심 전이 3 — 정직한 급소: "정규식보다 낫다"는 주장이 정말로 검증됐는지는 이 노트도 판단을 유보한다

논문이 내세우는 핵심 차별점은 "정규식은 경직적이고 맥락을 못 읽지만, LLM 기반 의미 분류는 맥락을 이해한다"는 것이다. 방향성은 합리적이지만, **저자 자체 평가로 만든 96.5%/3.0%라는 숫자가 실제 프로덕션 환경(다양한 코드베이스·언어·팀 문화)에서도 유지되는지는 이 논문 하나로 확정할 수 없다.** 특히 세이프가드 자체가 별도 LLM 호출이라는 점에서 — [[2026-08-02-openai-codex-security-oss]]에서 지적했던 "LLM 기반 보안 도구는 코드 규모에 비례해 토큰 비용이 든다"는 우려가 여기도 그대로 적용된다. 모든 프롬프트마다 세이프가드 모델 호출이 하나 더 붙는 구조이므로, **지연시간·비용이 실제 개발자 워크플로에 얼마나 거슬리는지는 이 노트가 확보한 자료에 나오지 않는다.**

## 호스피탈리티 / CRS 적용 포인트

**이번 배치 다른 AWS 노트들보다 직접 적용 가능성이 높은 편이다 — 단, 실제 검토·도입 사례는 없다는 걸 분명히 한다.**

- **문제 자체가 온다에 실재한다.** 온다 CRS 엔지니어가 Claude Code 같은 코딩 어시스턴트로 디버깅할 때, 실제 예약 데이터·결제 정보·파트너 PMS 인증키를 예시로 붙여 넣는 상황은 충분히 일어날 수 있다. 규정집이나 코드 리뷰로 사후에 잡기보다, **프롬프트가 외부 LLM API로 나가기 전에 자동으로 걸러지는 레이어**가 있다면 사고를 사전에 막는다.
- **정규식보다 나은 지점이 실제로 있다.** 온다가 연동하는 파트너사 PMS·채널매니저마다 예약번호·객실코드·요금 형식이 제각각이라, 정규식으로 "이건 실제 예약번호처럼 보인다"를 파트너사별로 유지보수하는 건 현실적으로 비용이 크다. **의미 기반 분류(맥락상 이게 실제 고객 데이터인지 예시 더미 데이터인지 판단)**라는 방향성은, 형식이 파트너마다 다른 CRS 도메인에 특히 잘 들어맞는 문제 정의다.
- **정책이 코드가 아니라는 점도 CRS 조직 구조에 맞는다.** "어떤 게 카드번호·게스트 PII·파트너 API 키로 취급돼야 하는가"는 보안팀·법무팀이 판단할 문제이지 엔지니어가 코드로 하드코딩할 문제가 아니다. Policy-as-prompt 구조라면 **그 판단 기준을 보안 담당자가 직접 텍스트로 관리**할 수 있다는 게 [[2026-08-14-tiro-kiro-iso27001-security-infrastructure]]가 확인한 "가드레일은 도구가 아니라 방법론"이라는 원칙과도 맞아떨어진다.
- **다만 과장하지 않는다.** 이건 arXiv 논문 + AWS 샘플 저장소 수준이지, 검증된 GA 프로덕트가 아니다. 96.5%/3.0%라는 수치도 저자 자체 평가다. 온다가 실제로 이런 레이어를 도입하려면 **자체 프롬프트·데이터로 다시 평가해야 한다** — 이 논문의 숫자를 그대로 우리 환경에 대입할 근거는 없다. 그리고 [[2026-08-10-doordash-ai-agent-gateway]]의 교훈대로, 오탐률이 개발자 워크플로를 자주 막으면 우회 경로가 생긴다는 점도 도입 전에 설계해둬야 한다.
