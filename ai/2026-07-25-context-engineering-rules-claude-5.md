# Claude 5 세대를 위한 새 컨텍스트 엔지니어링 규칙 — 규칙을 쌓지 말고 인터페이스를 설계하라

> 출처: [New context engineering rules for Claude 5 models](https://x.com/trq212/status/2080710971228918066) (x.com/trq212 · GeekNews GN⁺ 요약) · 정리일 2026-07-25
> **출처 한계**: x.com은 봇 차단으로 원문 확인 불가 — **GeekNews 요약 불릿에만 근거**한다. 저자 정체(Anthropic 소속 여부)도 확인하지 못했으니, 아래는 "공식 가이드"가 아니라 **한 실무자의 관찰**로 읽는 게 맞다.

## 한 줄 요약

**핵심 주장 한 줄: Claude Opus 5 / Fable 5에서 **시스템 프롬프트를 80% 이상 줄이고도 성능 저하가 없었다**. 그동안 우리가 프롬프트에 쌓아온 것 — "반드시", "절대", 예시 열 개, 방어적 규칙 목록 — 상당수는 *약한 모델을 통제하기 위한 비계*였고, 모델이 맥락을 읽게 되면 그 비계가 오히려 **노이즈로 성능을 깎는다**는 것이다. 대안은 세 가지 축으로 정리된다. ①**점진적 공개(progressive disclosure)** — 모든 것을 항상 컨텍스트에 넣지 말고, *필요한 순간에 필요한 정보만* 로드한다. CLAUDE.md는 짧게 유지하고 긴 지침은 **Skills로 분리**, 고정 규칙은 **자동 메모리**로 이관, 크기는 `/doctor`·`claude doctor`로 관리. ②**규칙 대신 인터페이스** — *"예시를 늘리기보다 표현력 있는 인터페이스를 설계하라"*, *"반복되는 지침은 도구 설명(tool description)에 통합하라"*. 같은 말을 프롬프트에서 열 번 반복하는 대신, **도구가 스스로 자기 사용법을 설명하게** 만든다. ③**참조 자료를 풍부하게** — HTML 아티팩트, 테스트 스위트, 평가 기준표(rubric) 같은 *검증 가능한 산출물*을 주는 편이 산문 규칙보다 낫다. 요약하면 프롬프트 엔지니어링에서 **인터페이스·환경 설계로의 이동**이고, 작업의 성격이 *쓰기*에서 **지우기**로 바뀐다.**

## 핵심 포인트

- **80% 감축, 성능 유지** — Claude Opus 5·Fable 5에서 *"시스템 프롬프트를 80% 이상 줄이고도 성능 저하 없음"*. 이 한 줄이 나머지 전부의 근거다. (단, 어떤 태스크·어떤 측정으로 확인했는지는 **불릿에 없다** — 아래 정직성 항목 참조.)
- **점진적 공개(progressive disclosure)** — 필요한 순간에 필요한 정보만 제공. 항상 로드되는 컨텍스트는 **비용이자 노이즈**다.
- **CLAUDE.md는 짧게, 긴 지침은 Skills로** — 프로젝트 상시 컨텍스트에는 *진짜 항상 필요한 것*만. 무거운 절차·체크리스트는 **온디맨드 스킬**로 밀어낸다.
- **크기를 측정하라** — `/doctor` 및 `claude doctor`로 컨텍스트 크기를 확인·조정. *재지 않으면 줄일 수 없다.*
- **고정 규칙보다 맥락 기반 판단** — 하드코딩된 if-then 규칙 목록보다, 모델이 상황을 보고 판단하게 두는 편이 낫다.
- **예시보다 표현력 있는 인터페이스** — 예시를 열 개 붙이는 것보다 **인터페이스 자체가 오해할 수 없게** 설계하는 게 낫다. (프롬프트 버전의 "좋은 API는 잘못 쓰기 어렵다.")
- **반복 지침 → 도구 설명으로 통합** — 시스템 프롬프트에서 반복하는 *"X할 때는 Y 도구를 써라"*를 **그 도구의 description 안에** 넣는다. 규칙이 사용 지점에 붙어 있게.
- **CLAUDE.md → 자동 메모리로 전환** — 정적 문서에 적어두는 대신, 세션을 넘겨 축적되는 메모리로.
- **풍부한 참조 자료** — HTML 아티팩트, 테스트 스위트, **평가 기준표(rubric)**. 산문 규칙보다 *검증 가능한 산출물*이 낫다.
- **삭제가 작업이다** — 불필요한 규칙·반복·정보를 지워 컨텍스트를 단순화. 컨텍스트 엔지니어링은 채우기가 아니라 **덜어내기**.

## 내 생각 · 적용점

### 핵심 전이 1 — 이건 이 가든의 "신뢰성 게이트" 주장과 **정확히 반대 방향에서 같은 결론**이다

내 방법론(strict.md)에는 이런 조항이 있다: *"프롬프트에 '반드시·절대·MUST'가 많이 등장하면 그 부분은 사실상 LLM 신뢰성의 한계 지점이다. 진짜 신뢰성은 프롬프트의 어조가 아니라 결정적 코드/hook으로만 만들어진다."* 이 글은 **같은 진단, 다른 처방**을 낸다:

| | 내 신뢰성 게이트 | 이 글 |
|---|---|---|
| 진단 | 강제 표현 = 신뢰성 한계 지점 | 강제 규칙 = 약한 모델용 비계 |
| 처방 | 규칙을 **hook/CI로 외부화** | 규칙을 **도구 설명·인터페이스로 흡수** |

둘은 경쟁하지 않고 **분업한다.** 되돌릴 수 없는 일(커밋 전 린트, 시크릿 스캔, dry-run 게이트)은 hook으로 굳히고, *판단이 필요한 일*(언제 이 도구를 쓸지, 어떤 스타일로 쓸지)은 프롬프트에서 빼서 **도구 설명·인터페이스**로 옮긴다. 남는 건 진짜 판단뿐이다. 이 프레임이 맞다면 내 CLAUDE.md에서 지울 후보가 꽤 명확해진다 — **"반드시 X하라"인데 hook으로도 도구 설명으로도 옮길 수 있는 문장**들.

### 핵심 전이 2 — 내 methodology는 이미 절반은 이 방향으로 왔다 (그리고 나머지 절반은 아직 안 왔다)

strict.md에는 이미 **온디맨드 스킬** 구조가 있다: Trivial/Small은 코어 표만으로 처리하고, Medium/Large에서만 `mangolove-spec`·`mangolove-large-review`·`mangolove-cicd`를 로드한다. 이건 정확히 이 글의 **점진적 공개**다. 그런데 나머지 절반은 정반대다 — **코어 CLAUDE.md/strict.md 자체가 매우 길다**. 트랙 판정표, LLM 위임 경계, dry-run 게이트, 마이그레이션 전략, 메모리 루프, 자가수정 루프, 경계면 교차검증… 이 중 **매 세션 항상 필요한 건 몇 개인가?**

이 글 기준으로 하면 정직한 답은 *"트랙 판정과 승인 게이트 정도"*이고, 나머지는 **트리거될 때 로드되는 스킬**이어야 한다. 예를 들어 dry-run 게이트는 *DB 마이그레이션·force push·외부 write를 감지했을 때* 로드되면 충분하다. 즉 **strict.md를 "항상 읽는 코어"와 "감지되면 로드되는 절차"로 한 번 더 쪼갤 여지**가 있다. 이건 [[2026-07-13-harness-token-overhead-instrument-your-own-boundary]]가 말한 *"내 경계의 토큰을 직접 계측하라"*의 후속 작업이다 — `/doctor`로 재고, 큰 덩어리부터 스킬로 밀어낸다.

### 핵심 전이 3 — "예시보다 인터페이스" = [[2026-07-12-good-tools-are-invisible]]의 프롬프트판

*"예시를 늘리기보다 표현력 있는 인터페이스를 설계하라"*와 *"반복 지침을 도구 설명으로 통합하라"*는, 코드에서 오래된 원칙 두 개의 재발견이다:

- **"좋은 API는 올바르게 쓰기 쉽고 잘못 쓰기 어렵다"** — 주석으로 사용법을 설명해야 하는 API는 대개 시그니처가 틀렸다.
- **[[2026-07-12-write-code-like-a-human-will-maintain-it]]** — 규칙을 **사용 지점**에 두라. 문서가 아니라 타입에.

에이전트 시대의 번역: **시스템 프롬프트에 반복해서 쓰고 있는 지침은, 그 도구의 description이 부실하다는 신호다.** 내가 `Skill` 도구·서브에이전트 프롬프트에서 같은 설명을 반복하고 있었다면, 그건 **도구 쪽을 고쳐야 할 냄새**다. 이 진단법은 즉시 쓸 수 있고 비용이 0이다 — *같은 문장을 두 군데 이상에서 반복하고 있는가?*

### 핵심 전이 4 — 정직한 급소: "덜어내라"는 조언은 **덜어냈을 때 뭘 잃는지를 측정한 사람만** 할 수 있다

이 글의 약점은 [[2026-07-24-everyone-should-know-simd]]에서 HN이 지적한 것과 같은 종류다 — *"측정이 먼저다."* 80% 삭감이 안전했다는 건 **누군가의 프롬프트, 누군가의 태스크**에서였다. 내 프롬프트에서 그 80%가 무엇을 막고 있었는지는 **평가 세트가 있어야만** 알 수 있다.

그래서 이 글의 조언 중 가장 값진 항목은 사실 화려한 쪽(80% 삭감)이 아니라 **"평가 기준표(rubric)를 참조 자료로 주라"**다. rubric이 있으면 삭감의 안전성을 *결정적으로* 검증할 수 있고, 그건 내 방법론의 **DoD 게이트**(선언한 완료 조건을 실행 가능한 체크로 외부화)와 동일한 물건이다. **순서는 이렇다: rubric 먼저, 삭감은 그 다음.** rubric 없이 프롬프트를 80% 지우는 건 테스트 없이 리팩토링하는 것과 같다.

## 호스피탈리티 / CRS 적용 포인트

이 글은 개발 도구 사용법이라 온다 제품에 직접 적용되지는 않는다. 전이 가능한 것만:

- **우리 팀의 CLAUDE.md 다이어트, 단 rubric 먼저.** 프로젝트 CLAUDE.md에서 "항상 필요한 것"과 "특정 작업에서만 필요한 것"을 나누고, 후자는 `.claude/commands/`·스킬로 이관. 다만 **삭감 전에 "이 프로젝트에서 에이전트가 반드시 지켜야 할 것" 체크리스트를 실행 가능한 형태로 먼저 만든다**(빌드·린트·테스트·시크릿 스캔). 그게 있으면 삭감이 안전하고, 없으면 도박이다.
- **반복 지침 탐지 = 도구 결함 탐지.** 사내 MCP 도구·슬래시 명령에서 *"이 도구는 이럴 때 쓰세요"*를 프롬프트로 반복하고 있다면, **도구 description을 고칠 신호**다. 온다 내부 도구(`ondadb` 같은 헬퍼)에도 동일하게 적용된다 — 사용 조건을 도구 자체에 적어둔다.
- **CRS 도메인의 "고정 규칙 vs 맥락 판단" 경계는 그대로 유지.** 이 글이 *"고정 규칙보다 맥락 기반 판단"*을 권하지만, **결제·재고·권한**은 예외다. 그쪽은 맥락 판단이 아니라 **결정적 코드**여야 한다 — 프롬프트를 줄이는 것과 **판단을 LLM에 넘기는 것**은 다른 일이다. 이 구분을 놓치면 "컨텍스트 최적화"라는 이름으로 위임 경계가 허물어진다.
- **`/doctor`로 실측부터.** 줄이자는 논의보다 **현재 크기를 재는 것**이 먼저다.
