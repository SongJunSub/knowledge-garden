# RAG는 생각보다 단순하다

> 출처: [RAG Is Simpler Than You Think](https://www.lighthousenewsletter.com/p/rag-is-simpler-than-you-think) (Lighthouse Newsletter) · 정리일 2026-08-27

## 한 줄 요약

**많은 RAG 시스템이 처음부터 임베딩·벡터 DB·재순위화 파이프라인을 도입하지만, 상당수 검색 문제는 ***BM25와 질의 재작성***만으로 해결된다는 게 이 글의 핵심 주장이다.** 데이터 신선도, 문서 변경률, 질의 유형, 검색량, 팀 역량이라는 다섯 축에 따라 **최소부터 정교함까지 이어지는 여섯 단계의 검색 구조**를 단계적으로 선택하고, ***복잡도는 그것이 필요하다는 걸 데이터가 입증할 때만*** 높여야 한다고 말한다. BM25 검색은 10ms 미만으로 빠르고 청킹·임베딩 모델 비용이 전혀 없으며, 대화형 질의나 어휘 불일치("찾을 수 있는 문서인데도 못 찾는다"는 흔한 불만) 문제는 건당 약 **$0.001의 LLM 질의 재작성**으로, 재인덱싱 없이 보완할 수 있다. 그래도 진짜 의미 검색이 필요하다고 판단되면, 그때는 **BM25로 50~100개 후보를 먼저 추리고 임베딩으로 상위 10개만 재순위화**하는 2단계 구조로 넘어가라는 게 처방이다 — "검색 없음 → 처음부터 벡터 DB"로 건너뛰지 말라는 것.

## 핵심 포인트

- **핵심 주장** — RAG를 "임베딩 + 벡터 DB + 재순위화"로 등치시키는 건 흔한 과잉설계다. 검색이 아예 없다면 **BM25부터 먼저 구축**하라.
- **BM25의 장점** — **10ms 미만** 응답, **청킹·임베딩 모델 비용이 없음**, 어휘가 정확히 일치하는 질의(특히 고유명사·도메인 전문 용어)에서는 의미 검색보다 오히려 정확할 수 있다.
- **선택 기준(5축)** — **데이터 신선도**(실시간 갱신이 필요한지), **문서 변경률**, **질의 유형**(키워드형 vs 대화형), **검색량**, **팀 역량**. 이 다섯 축의 조합에 따라 6단계 중 어디서 시작할지가 갈린다.
- **6단계 검색 구조**(원문 6개 항목의 정확한 명칭·경계는 미확인, "최소→정교" 스펙트럼이라는 틀만 확인) — BM25 단독에서 시작해 필요에 따라 질의 재작성 → 하이브리드(BM25+임베딩) → 재순위화 → 완전한 임베딩/벡터 DB 파이프라인까지 점진적으로 얹어가는 구조로 추정된다.
- **질의 재작성** — 건당 **약 $0.001**, 재인덱싱 불필요. "문서가 분명히 있는데 못 찾는다"는 불만이 나오면 임베딩 도입보다 먼저 시도해볼 저비용 옵션으로 제시된다.
- **의미 검색이 필요할 때의 처방** — 처음부터 전체 코퍼스를 임베딩하지 말고, **BM25로 50~100개 후보를 1차로 추린 뒤 임베딩으로 상위 10개만 재순위화**하는 2단계(하이브리드) 구조를 권장. BM25가 빠르고 값싸게 후보군을 좁혀주고, 임베딩은 그 좁은 후보군 안에서만 의미 유사도를 계산하므로 비용이 통제된다.
- **원칙** — 복잡도는 "있으면 좋을 것 같아서"가 아니라 **"필요성을 입증하는 데이터가 있을 때만"** 높인다 — 단계마다 데이터로 다음 단계 도입 여부를 검증하라는 프로세스적 처방.

## 인상 깊은 문장

> "If you don't have search at all, build BM25 first."

## 내 생각 · 적용점

### 핵심 전이 1 — [[2026-08-25-sqlite-for-everything]]가 주장한 "SQLite 하나로 검색엔진까지"와 이 글의 "BM25부터 시작하라"가 정확히 같은 지점에서 만난다

며칠 전 정리한 SQLite 노트는 `FTS5`(SQLite의 전문 검색 확장, 사실상 BM25 계열 랭킹 함수를 내장한다)로 **별도 검색 서버(Elasticsearch 등) 없이 애플리케이션 프로세스 안에서 전문 검색을 처리**할 수 있다고 주장했다. 이 글의 "검색이 없다면 BM25부터 구축하라"는 처방과 겹쳐 놓으면, **"BM25 계열 검색 → SQLite `FTS5` 하나로 시작 가능"**이라는 구체적 실행 경로가 나온다. 두 글 다 "복잡한 인프라(벡터 DB, 별도 검색 서버)를 먼저 놓지 말라"는 같은 원칙을 다른 계층(하드웨어/인프라 축 vs 알고리즘/파이프라인 축)에서 말하고 있다는 점이 핵심 전이다.

### 핵심 전이 2 — "복잡도는 필요성이 입증될 때만 추가"는 [[2026-08-06-pi-minimalism-coding-harness]]의 하네스 설계 원칙과 도메인만 다를 뿐 동일한 명제다

Pi 하네스 노트에서 짚었던 결론 — ***"복잡성은 필요성이 확인될 때만 추가하는 편이 유리하다"*** — 은 코딩 에이전트 하네스 설계에 관한 이야기였다. 이 RAG 글은 **정확히 같은 원칙을 검색 아키텍처 설계에 적용**한다: BM25 단독 → 질의 재작성 → 하이브리드 → 완전한 임베딩 파이프라인이라는 단계적 승격 경로 자체가, Pi의 "기본 도구 4개, 필요하면 확장 추가"와 같은 모양이다. 서로 다른 시기·다른 저자가 검색과 에이전트 하네스라는 다른 도메인에서 같은 결론에 도달했다는 건, 이게 특정 기술의 유행이 아니라 **"복잡도는 최후에, 데이터로 정당화된 뒤에" 라는 일반적인 엔지니어링 원칙**임을 보여준다.

## 호스피탈리티 / CRS 적용 포인트

- **CRS 접점이 이번 배치 중 가장 직접적이다.** CS 티켓 검색, 객실·시설 설명 검색, 파트너 문서 검색처럼 온다가 실제로 다룰 법한 검색 문제에 이 글의 처방을 그대로 적용할 수 있다 — 임베딩·벡터 DB부터 도입하기 전에, **먼저 BM25(예: PostgreSQL `tsvector`나 SQLite `FTS5`)로 베이스라인을 재고, 어휘 불일치가 실제로 문제라면 저비용 LLM 질의 재작성부터 시도**하는 순서가 합리적이다.
- **"데이터 신선도·문서 변경률·질의 유형·검색량·팀 역량" 5축 체크리스트는 내부 검색 기능(어떤 것이든)을 설계할 때 그대로 가져다 쓸 수 있는 실무 프레임이다.** 벡터 DB 도입을 검토하는 회의에서 "이 다섯 축 중 실제로 벡터 검색을 요구하는 축이 있는가?"를 먼저 물어보는 습관으로.
- 다만 6단계 구조의 정확한 명칭·경계는 이번 노트가 확인하지 못했으므로, 실제 도입 전에는 원문을 직접 대조해 단계 정의를 확정할 필요가 있다.
