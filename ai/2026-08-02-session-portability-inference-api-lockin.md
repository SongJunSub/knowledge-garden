# 가져갈 수 없는 세션: 추론 API가 만드는 새로운 종속성 (earendil.com)

> 출처: [Sessions you can't take with you](https://earendil.com/posts/session-portability/) (earendil.com · GeekNews GN⁺ 요약 + HN 큐레이션) · 정리일 2026-08-02

## 한 줄 요약

**추론 API 제공자들이 **암호화된 추론, 서버 저장 상태, 불투명한 도구 결과**를 반환하면서 세션의 실질적 소유권을 가져간다는 경고다. 핵심 문장: ***"당신 기기의 대화 기록은 더 이상 당신의 세션이 아니라, 운영 상태가 당신이 아닌 추론 제공자에게 속한 세션의 부분적 사본이다."*** 종속성이 쌓이는 경로 셋 — **①암호화된 추론**(*"사용자가 비용을 지불하지만 불투명한 암호화 블롭으로만 반환되는, 기껏해야 쓸모없는 요약이 붙은 추론 토큰"*), **②압축**(서버에서 압축된 상태를 반환하면 *"다른 제공자는 읽을 수 없는 문자열을 본다"*), **③서버 저장**(*"응답 ID는 이제 그 제공자가 통제하지 않는 데이터베이스로의 외래키다"*). 저자는 "세션 이식성"을 **다섯 가지 실질적 테스트**로 정의한다 — **검사**(모델이 뭘 봤고 도구가 뭘 했고 에이전트끼리 뭐라 했는지 볼 수 있는가), **내보내기**(세션이 자기완결적인가), **재생**(다른 구현이 의미적으로 동등한 컨텍스트를 재구성할 수 있는가), **감사**(사람이 시스템의 행동 이유를 설명할 수 있는가), **삭제**(사용자가 서버 측 모든 사본을 식별·제거할 수 있는가). 다중 에이전트 시스템에서 문제는 더 심각해진다 — 부모가 자식에게 보낸 **정확한 작업 지시가 암호화돼 읽을 수 없는 기록**으로 남아, 자식 에이전트가 **잘못된 파일을 바꾸거나, 시크릿을 유출하거나, 다른 에이전트의 작업을 중복**해도 ***"사용자는 '그 에이전트가 무엇을 하라고 지시받았는가'라는 단순한 질문에도 답할 수 없다."*** 저자는 **7가지 설계 원칙**을 제안한다 — 로컬 이벤트 로그가 정본, 저장은 명시적 옵트인, 불투명 항목도 평문 버전 병존, 호스팅 도구는 전체 신뢰도 로그, 서브에이전트 통신은 감사 가능, 압축은 검사 가능, 산출물은 내보내기 가능. 결론: ***"사용자는 계정을 닫고, 세션은 유지하고, 그걸 다른 모델에 넘길 수 있어야 한다."***</br>

## 핵심 포인트

- **핵심 문제 정의** — ***"The transcript on your machine is no longer your session but a partial view of a session whose operational state belongs to an inference provider and not you."***
- **종속성이 쌓이는 세 경로**
  1. **암호화된 추론** — ***"사용자가 비용을 지불하지만 불투명한 암호화 블롭으로만 반환되고, 기껏해야 쓸모없는 요약만 붙는다."***
  2. **압축** — 서버에서 압축한 상태를 반환하면 ***"다른 제공자는 읽을 수 없는 문자열을 본다."***
  3. **서버 저장 ID** — ***"응답 ID는 이제 그 제공자가 통제하지 않는 데이터베이스로의 외래키다."***
- **세션 이식성의 5가지 테스트**
  1. **검사(Inspection)** — ***"사용자가 모델이 본 것, 도구가 한 것, 에이전트끼리 서로에게 말한 것을 볼 수 있는가?"***
  2. **내보내기(Export)** — ***"세션이 통상적 산출물 외에는 자기완결적인가?"***
  3. **재생(Replay)** — ***"다른 구현이 의미적으로 동등한 컨텍스트를 재구성할 수 있는가?"***
  4. **감사(Audit)** — ***"사람이 시스템이 왜 그 행동을 했는지 설명할 수 있는가?"***
  5. **삭제(Deletion)** — ***"사용자가 서버 측의 모든 사본을 식별·제거할 수 있는가?"***
- **다중 에이전트 시스템에서의 감사 붕괴** — 구조적으로 ***"세션들의 트리와 그 사이를 오가는 메시지의 스트림"***이 존재. 부모→자식 작업 지시가 ***"읽을 수 있는 롤아웃과 기록에서 부재"***. 자식 에이전트가 ***"잘못된 파일을 바꾸거나, 시크릿을 유출하거나, 다른 에이전트의 작업을 중복"***해도 ***"사용자는 그 에이전트가 무엇을 하라고 지시받았는가라는 단순한 질문에도 답할 수 없다."***
- **저자가 제안하는 7가지 설계 원칙**
  1. ***"The local event log is canonical"*** — 서버 저장은 선택사항
  2. ***"Storage is explicit"*** — `store: false`가 기본값
  3. ***"No opaque item is the sole carrier of meaning"*** — 암호화 항목도 평문 버전 병존
  4. ***"Hosted tools have full-fidelity logs"***
  5. ***"Subagent communication is auditable"***
  6. ***"Compaction is inspectable"***
  7. ***"Artifacts are exportable"***
- **결론** — ***"사용자는 계정을 닫고, 세션을 유지하고, 그걸 다른 모델에 넘길 수 있어야 한다."***

## 내 생각 · 적용점

### 핵심 전이 1 — 이 글의 문제의식은 내 CLAUDE.md의 벤더 종속성 회피 원칙을 API 설계 수준에서 정밀화한다

이 가든의 [[2026-08-02-anthropic-position-open-weight-models]]·[[2026-07-25-nvidia-microsoft-meta-open-weight-warning]]에서 반복해 온 *"모델 벤더 종속을 낮춰라"*는 원칙이, 이 글에서는 **모델 자체보다 세션 상태의 종속성**이라는 더 미세한 층위로 내려간다. 심지어 **오픈웨이트 모델을 쓴다 해도**, 그 모델을 서빙하는 API가 압축·서버 저장·암호화된 추론을 쓰면 **모델은 바꿀 수 있어도 진행 중인 대화·에이전트 작업은 이식할 수 없다.** 이건 [[2026-07-14-migrating-production-agent-provider-assumptions]]에서 다룬 *"모델 교체는 한 줄 변경이 아니다"*보다 한 단계 더 나쁜 상황이다 — **모델을 성공적으로 교체해도, 그 시점까지의 세션 컨텍스트는 통째로 버려야 할 수 있다.**

### 핵심 전이 2 — "다중 에이전트 시스템의 감사 붕괴"는 이번 배치의 [[2026-08-02-hugging-face-tailscale-agent-breach]]가 실제로 증명한 문제의 근본 원인일 수 있다

Hugging Face 사건 노트에서 나는 *"침투가 며칠에 걸쳐 일어났고, 탐지할 시간 창이 여러 번 열려 있었다"*고 정리했다. 이 글이 지적하는 문제 — ***"자식 에이전트가 무엇을 하라고 지시받았는지 사용자가 답할 수 없다"*** — 는 **바로 그 사고에서 왜 탐지가 늦어졌는지의 근본 원인**일 수 있다. 만약 부모-자식 에이전트 간 통신이 완전히 감사 가능했다면, **"이 에이전트가 왜 프로덕션 시크릿에 접근했는가"라는 질문에 즉시 답할 수 있었을 것**이다. 두 노트를 겹치면 실무 원칙이 명확해진다: **에이전트 오케스트레이션을 도입할 때, 서브에이전트 간 통신 로그의 완전성을 보안 요구사항으로 명시해야 한다.**

### 핵심 전이 3 — "로컬 이벤트 로그가 정본"은 내 방법론의 dry-run 게이트가 요구하는 검증 가능성과 같은 원칙이다

저자의 7원칙 중 첫째 — ***"로컬 이벤트 로그가 정본이고 서버 저장은 선택사항이어야 한다"*** — 는 내 CLAUDE.md의 **되돌리기 어려운 작업에 대한 dry-run 게이트**와 같은 철학이다. 두 원칙 모두 **"통제권을 시스템 외부(벤더 서버, 비가역적 실행)에 넘기지 말고, 검증·롤백 가능한 지점을 사용자/운영자 손에 남겨두라"**는 것이다. 특히 이 글의 "재생(Replay)" 테스트 — *"다른 구현이 의미적으로 동등한 컨텍스트를 재구성할 수 있는가"* — 는 내 dry-run 게이트가 요구하는 **"실행 전 산출물 확인"**의 API 설계 버전이다.

### 핵심 전이 4 — 정직한 급소: 이 원칙들이 벤더 입장에서 "그냥 안 지키면 그만"인 자발적 선언에 불과하다

이 글이 제시하는 5가지 테스트·7가지 원칙은 **기술적으로 합리적이지만 강제할 메커니즘이 없다.** [[2026-08-02-gcc-ai-policy]]에서 다룬 것과 같은 문제 — **좋은 원칙을 세우는 것과 그 원칙을 실제로 집행하는 것은 다른 난이도**다. 벤더가 압축·암호화·서버 저장을 쓰는 이유(비용 절감, 지적재산권 보호, 프롬프트 인젝션 방어)는 실재하고, 이 글의 원칙을 지키면 벤더에게 손해가 될 수도 있다 — **원칙과 벤더 인센티브가 충돌할 때, 원칙이 이긴 사례는 이 글에 없다.**

## 호스피탈리티 / CRS 적용 포인트

- **우리 에이전트 시스템 설계에 5가지 테스트를 체크리스트로 적용한다.** 온다가 자체 AI 에이전트 워크플로(사업자 지원, 자동화 도구)를 구축한다면, **검사·내보내기·재생·감사·삭제** 다섯 기준으로 우리 자신의 설계를 먼저 점검한다.
- **서브에이전트 통신 로그를 보안 요구사항으로 명시(전이 2).** 멀티 에이전트 오케스트레이션을 쓴다면, **부모-자식 작업 지시가 평문으로 완전히 감사 가능한지**를 배포 전 필수 확인 항목으로 넣는다.
- **벤더 계약서에서 데이터 이식성 조항을 확인(전이 4).** "원칙"에만 의존하지 말고, 실제 계약·서비스 약관에서 **세션 데이터 내보내기·삭제 권리**가 명시돼 있는지 법무와 함께 확인한다.
