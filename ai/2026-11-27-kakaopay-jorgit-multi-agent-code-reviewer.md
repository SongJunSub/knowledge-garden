# Agentic AI, 멀티 에이전트로 신뢰와 비용 효율을 설계하다 (카카오페이)

## 한 줄 요약

**카카오페이가 AI 코드 리뷰 병목을 풀기 위해 'jorgit'이라는 멀티 에이전트 시스템을 만들었는데, 핵심은 역할을 쪼갠 것 자체가 아니라 에이전트 간 상호 검증 구조로 신뢰성을 올리면서 토큰 비용도 같이 관리한 설계다.**

## 핵심 포인트

- **단일 거대 에이전트 대신 역할 분리** — 코드 분석, 컨벤션 검토 등 리뷰 기능을 ***독립된 역할 기반 에이전트***로 나눠 각자 맡게 했다. 하나의 프롬프트에 모든 리뷰 기준을 욱여넣는 방식의 한계를 역할 분리로 풀었다는 서술이다.
- **상호 검증 구조로 신뢰성 확보** — 에이전트들의 결과를 서로 검증하게 하는 구조를 도입해 ***AI 코드 리뷰의 신뢰성***을 높였다는 것이 이 글의 핵심 주장. 단일 에이전트의 판단을 그대로 믿지 않고 교차 확인 단계를 둔 것으로 읽힌다.
- **토큰 비용도 설계 변수로 다룸** — 신뢰성만 쫓지 않고 ***토큰 비용 최적화***를 같은 설계 축에 넣었다는 서술 — 상호 검증 단계가 늘면 비용도 늘어나는 트레이드오프를 인지하고 전략적으로 배분했다는 의미로 읽힌다.
- **대상 범위**: "AI가 생성한 방대한 코드"를 효율적으로 검토하는 것이 출발점 — AI 코딩 도구 확산으로 리뷰해야 할 코드량 자체가 늘어난 상황을 전제로 한다.

## 내 생각 · 적용점

### 핵심 전이 — "AI 생성물을 AI로 검증한다"는 패턴의 반복

이 글의 "에이전트 간 상호 검증으로 신뢰성 확보"는 [[2026-11-25-naver-ai-output-trust-mutation-testing]](네이버, 돌연변이 테스팅으로 AI 생성 테스트의 가짜 통과 잡기)와 [[2026-11-24-evals-underrated-ai-engineering-skill]](평가는 과소평가된 역량)이 같은 주 반복해서 강조한 "AI 결과물을 그대로 믿지 않고 별도 검증 루프를 둔다"는 원칙의 또 다른 사례다. 다만 이 글은 검증 주체 역시 AI(에이전트)라는 점이 다르다 — 사람이 아니라 에이전트가 에이전트를 검증하는 구조이므로, 그 검증 에이전트 자체의 신뢰도는 누가 보증하는지가 다음 질문으로 남는다.

### 적용점

코드 리뷰를 단일 프롬프트로 처리하지 않고 역할별 에이전트+상호검증으로 쪼갠다는 설계는, 다른 복잡한 AI 워크플로우(상담 응답 생성 등)에서도 "생성 에이전트"와 "검증 에이전트"를 분리하는 일반 원칙으로 가져올 수 있다.

## 호스피탈리티 / CRS 적용 포인트

**적용 가능성 있음(제한적).** CRS/PMS 환경에서 AI가 생성한 코드나 설정값(요금 규칙, 프로모션 로직 등)을 상호 검증 에이전트로 재검토하는 구조는 바로 참고할 만하다. 단, 토큰 비용 관리가 필요하다는 전제도 같이 가져와야 한다 — 검증 단계를 무한정 늘리면 비용이 신뢰성 이득을 넘어설 수 있다.
