# 한 줄 프롬프트에서 그래프 기반 Agent로 (AWS · ZEP)

> 출처: [한 줄 프롬프트에서 그래프 기반 Agent로: Amazon Bedrock AgentCore 기반 ZEP의 교육용 퀴즈 생성 아키텍처](https://aws.amazon.com/ko/blogs/tech/zep-quiz-generation-bedrock-agentcore/) (AWS 기술 블로그 · Slack #개발-뉴스-dev-news(TechArticles) 공유) · 정리일 2026-08-31

## 한 줄 요약

**ZEP은 교육용 퀴즈를 단일 프롬프트로 한 번에 생성하는 방식의 한계(오답 품질·난이도·성취기준 연계 같은 제약 조건을 동시에 만족시키기 어려움)를 극복하기 위해 LangGraph 기반 워크플로우로 생성 과정을 여러 단계로 쪼갰고, 이를 Amazon Bedrock AgentCore Runtime 위에서 실시간 서빙과 대량 배치 파이프라인 양쪽에 함께 운영하는 아키텍처를 소개하는 글이다.**

## 핵심 포인트

- ZEP은 퀴즈 생성에서 단일 프롬프트 호출의 한계를 넘기 위해 ***LangGraph 기반 워크플로우***를 도입해 문제 생성을 여러 단계로 세분화했다.
- 오답 품질, 난이도, 성취기준 연계 같은 복잡한 제약 조건을 각 단계에서 체계적으로 관리 — 실제로 ZEP QUIZ 서비스에는 "성취기준 기반 AI 문제 생성" 기능이 별도로 출시돼 있어(WebSearch로 확인), 이 아키텍처 변화가 실제 제품 기능과 맞닿아 있음을 교차확인할 수 있었다.
- Amazon Bedrock AgentCore Runtime을 인프라로 채택해, 사용자가 즉시 요청하는 ***실시간 서빙 경로***와 문항을 미리 대량 생성해두는 ***배치 파이프라인***을 함께 운영한다.
- AgentCore Runtime은 완전관리형 서버리스 런타임으로 세션 격리·자동 스케일링을 제공한다(WebSearch로 확인한 AgentCore 일반 특성) — ZEP이 이를 활용해 실시간·배치라는 서로 다른 트래픽 패턴을 하나의 그래프 구조 위에서 운영 복잡도를 낮췄을 것으로 보이나, 구체적으로 무엇을 얼마나 줄였는지는 원문 미확보로 확인하지 못했다.
- 교육 도메인은 "그럴듯하지만 틀린 오답"을 걸러내고 학년별 성취기준에 맞는 난이도를 보장해야 해서, 일반 텍스트 생성보다 검증 기준이 훨씬 까다롭다 — 그래프의 각 노드에 검증 책임을 나눠 맡기는 접근으로 이 까다로움에 대응한 것으로 읽힌다.

## 내 생각 · 적용점

### 핵심 전이 1 — "그래프 구조 자체는 새롭지 않다"는 경고가 이 사례에도 적용된다

[[2026-08-16-graph-vs-loop-engineering]]에서 Louis Bouchard가 짚었듯, 그래프형 에이전트 오케스트레이션은 DAG 스케줄러가 10년째 해온 것이고 달라진 건 노드가 스스로 판단하는 확률적 존재가 됐다는 점뿐이다. 특히 그 글의 가장 무거운 문장 — ***"에이전트가 에이전트를 검사하는 그래프는 극도로 잘 조직된 헛소리를 만들 수 있다"*** — 는 ZEP처럼 오답 품질·성취기준 연계를 "그래프 내부 노드"가 검증하는 구조에도 그대로 적용되는 위험이다. 원문에 실제 교사 채점이나 학생 오답률 같은 **시스템 외부 증거**로 검증했다는 언급이 있는지가 이 아키텍처의 신뢰도를 가르는 지점인데, 원문을 확보하지 못해 확인할 수 없었다 — 다음에 원문을 읽게 되면 가장 먼저 볼 부분이다.

### 핵심 전이 2 — "측정 가능한 완료 조건"과 "성취기준 연계"는 같은 원칙의 다른 도메인 적용

[[2026-08-16-practical-loop-engineering]]에서 Addy Osmani가 강조한 원칙 — 에이전트에게 최대 자율성을 주는 대신 **측정 가능한 완료 조건**을 명시하고 평가자가 그 하드 룰 충족 여부만 판정하게 하라 — 는 ZEP의 "성취기준 연계"와 구조적으로 같다. 성취기준이라는 외부에서 주어진 명시적 기준을 평가자 역할로 그래프에 박아 넣은 것이라면, 이건 루프 엔지니어링 원칙이 교육 콘텐츠 생성이라는 구체 도메인에서 실제로 작동한다는 걸 보여주는 사례로 읽을 수 있다.

## 호스피탈리티 / CRS 적용 포인트

퀴즈 생성처럼 "지켜야 할 제약 조건이 많은 콘텐츠 생성"은 CRS 쪽에도 있다 — 예를 들어 다국어 상품 설명이나 자동 응대 문구를 생성할 때 브랜드 톤, 법적 고지 문구, 현지화 규칙을 동시에 만족시켜야 하는 문제는 구조적으로 유사하다. 단일 프롬프트로 한 번에 처리하지 않고, 각 제약 조건(톤=난이도, 법적/브랜드 가이드라인=성취기준)을 그래프의 별도 노드에서 단계적으로 검증하는 접근은 참고할 만한 원칙이다. 다만 실시간 서빙과 대량 배치를 AgentCore Runtime 같은 전용 인프라 위에서 함께 운영하는 것까지 직접 도입하는 건 온다 규모에서는 멀다 — 아키텍처 패턴만 전이 가능한 수준으로 본다.
