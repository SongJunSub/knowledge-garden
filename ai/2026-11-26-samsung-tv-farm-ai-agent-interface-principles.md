# AI에게 API를 그대로 열어 주지 마세요 (삼성전자)

> 출처: [AI에게 API를 그대로 열어 주지 마세요 - 원격 TV 팜을 AI 에이전트용 인터페이스로 다시 설계하며 얻은 6가지 원칙](https://techblog.samsung.com/blog/article/111) (삼성전자 기술 블로그) · 정리일 2026-11-26

> **출처 한계**: `techblog.samsung.com`이 이 세션에서 egress 차단되어 원문을 열람하지 못했다. Slack 발췌 불릿 3개만 확보됐고, "6가지 원칙" 전체 목록과 구체 사례는 원문에만 있어 확인하지 못했다. WebSearch로도 이 글 자체를 특정하지 못했다 — 제목의 핵심 주장(사람용 API를 에이전트에 그대로 열면 안 된다)만 교차확인 가능했다.

## 한 줄 요약

**삼성전자가 원격 TV 테스트 팜(클라우드플레어·웹서버 간 통신 오류 디버깅용)을 사람이 쓰던 API 그대로가 아니라 AI 에이전트 전용 인터페이스로 재설계하면서, "API를 그대로 열어주면 안 된다"는 6가지 원칙을 얻었다는 글이다.**

## 핵심 포인트

- **520 에러 디버깅이 출발점** — 클라우드플레어와 원본 웹 서버 사이의 통신 오류로 발생하는 ***520 에러***의 원인 분석과 해결책을 안내하는 실무 맥락에서 이 재설계가 나왔다.
- **방문자 재접속 vs 서버 관리자의 로그 분석** — 문제 해결 과정에서 방문자는 재접속을 시도하고, 서버 관리자는 웹 서버의 에러 로그를 확인해 분석해야 한다는 역할 분리가 전제됨.
- **클라우드플레어 지원팀에 레이 ID 포함 로그 제출** — 문제 해결을 위해 레이 아이디를 포함한 로그를 클라우드플레어 지원팀에 제출해 조사를 요청할 수 있는 경로가 있다는 서술.
- **"6가지 원칙"의 구체 내용은 미확인** — 제목이 핵심으로 내세우는 "AI 에이전트용 인터페이스로 다시 설계하며 얻은 6가지 원칙" 자체의 목록은 Slack 발췌에 담기지 않았고, 이 레포는 그 구체 내용 없이 제목의 주장(사람용 API ≠ 에이전트용 인터페이스)만 다룬다는 걸 분명히 밝혀둔다.

## 내 생각 · 적용점

### 핵심 전이 — "사람용 설계를 에이전트에 그대로 쓰면 안 된다"는 반복되는 교훈

이 글의 제목 자체가 핵심이다 — ***사람이 쓰던 API를 그대로 노출하면 에이전트에게는 오히려 독***이라는 주장은, [[2026-11-25-llm-agents-serve-vendor-not-user]]가 다룬 "금지 대상과 대체 경로를 함께 정의하는 정책 설계"와 결이 비슷하다. 둘 다 "에이전트가 쓸 인터페이스는 사람이 쓰던 것과 다르게 설계해야 한다"는 원칙으로 묶인다. MCP 설계 맥락에서는 [[2026-11-26-naver-care-agent-mcp-agent-design-part2]](같은 배치, 네이버 D2)의 "MCP 응답 구조를 최적화해 입력 한도를 해결"도 같은 문제의식의 다른 해법이다.

### 적용점

사람용 API(세세한 저수준 호출, 복잡한 인증, 방대한 응답)를 에이전트에게 그대로 넘기면 토큰 낭비와 오작동의 원인이 된다는 교훈은, CRS/PMS API를 MCP로 노출할 때 "사람 개발자용 API 문서"가 아니라 "에이전트가 바로 쓸 수 있는 압축된 도구 정의"를 별도로 설계해야 한다는 원칙으로 일반화할 수 있다.

## 호스피탈리티 / CRS 적용 포인트

**적용 가능성 있음.** CRS/PMS 레거시 API를 AI 에이전트에게 그대로 노출하는 대신, 에이전트 전용 인터페이스(요청·응답 축소, 에러 처리 표준화, 권한 범위 제한)를 별도로 설계해야 한다는 원칙은 이 레포가 거듭 확인하는 핵심 설계 원칙 중 하나로 CRS 에이전트 게이트웨이 설계에 직접 참고할 만하다. 단 구체적인 "6가지 원칙"의 내용이 없어 체크리스트로 바로 쓰긴 어렵다.
