# 고처리량 AI-SQL 엔진 구축하기 (Quail, Modal)

> 출처: [Quail: a billion tokens per minute on one GPU](https://modal.com/blog/quail-billion-tpm) (Modal 블로그) · GeekNews(id=34860) 경유 · 정리일 2026-10-06

> **출처 한계**: `news.hada.io`와 `modal.com` 둘 다 이 세션에서 egress 차단으로 직접 열지 못했다(Google Translate 프록시·HN Algolia API 등 대체 경로도 같은 정책으로 차단됐다). 아래 내용은 **WebSearch가 반환한 모달 블로그의 복수 스니펫**(제목, 핵심 수치, 아키텍처 설명 문장)을 교차확인해 재구성한 것이며, 원문을 한 번에 통독하며 확인한 것이 아니라 **스니펫 조합이라 세부 맥락(실험 설정, 벤치마크 쿼리 종류, 한계로 언급된 사례)은 빠져 있을 수 있다.** hada 댓글 수, HN/Lobsters 큐레이션 여부도 전혀 확인하지 못했다. Modal Labs와 CMU 연구실의 공동 작업이라는 점은 WebSearch로 확인했으나, 구체적 저자명·소속은 특정하지 못했다.

## 한 줄 요약

**Quail(QUery-Aware Inference Layer)은 AI-SQL(테이블 데이터에 행마다 LLM 호출을 거는 분석 쿼리) 워크로드를 위해 Modal이 만든 오픈소스 추론 엔진으로, 쿼리 플래너가 "이 쿼리가 뭘 재사용할지"를 추론 엔진에 미리 알려주는 방식으로 vLLM 같은 범용 추론 엔진 대비 멀티조인 쿼리에서 10배 이상, 새 AI-SQL 벤치마크 전체 평균으로는 1.84배 빠른 처리량을 내 H100 한 장에서 분당 10억 토큰을 처리했다.**

## 핵심 포인트

- **AI-SQL의 구조적 문제 — 행(또는 조인 튜플)마다 LLM 호출 하나** — AI-SQL은 분석 SQL 레이어에서 LLM 변환을 실행하는 방식이다. 쿼리 옵티마이저를 거쳐도, 조인이 섞인 쿼리는 교차곱의 튜플마다 LLM 호출이 필요해 ***수십만~수백만 건의 LLM 호출***이 남는 경우가 흔하다.
- **범용 추론 엔진이 느린 이유 — KV 캐시가 "뭘 재사용할지" 모른다** — 이 워크로드는 입력이 대부분을 차지하고 출력은 짧은(prefill 위주) 패턴이라 이론상 추론 엔진에 유리해야 하지만, vLLM 같은 범용 엔진은 ***각 요청이 무엇을 공유하는지 미리 알지 못해*** KV 캐시를 효율적으로 재사용하지 못하고, 수많은 개별 요청을 처리하는 호스트 오버헤드도 커진다.
- **해법 — 쿼리 플래너 + 추론 엔진의 결합** — Quail은 ***쿼리 플래너가 먼저 어떤 프롬프트들이 접두사·구조를 공유하는지 분석***해, 그 정보를 추론 엔진에 넘겨 KV 캐시 재사용을 능동적으로 설계하게 만든다. "추론 엔진이 알아서 추측하게" 두는 대신 "쿼리 레이어가 알고 있는 걸 미리 알려준다"는 방향 전환이 핵심이다.
- **수치 — H100 한 장에서 분당 10억 토큰, vLLM 대비 10배 이상** — 멀티조인 쿼리에서 ***H100 1장당 분당 10억 토큰 이상***을 처리해 같은 하드웨어의 vLLM 베이스라인보다 10배 이상 빠르다. 새로 공개한 AI-SQL 벤치마크 전반(여러 태스크의 기하평균)으로는 vLLM보다 1.84배 빠르다.
- **오픈소스로 공개** — Modal의 팀과 CMU 연구실이 함께 만든 플래너+실행 엔진 구조를 오픈소스로 공개했다(정확한 라이선스·저자명은 이 세션에서 확인하지 못함).

## 내 생각 · 적용점

### 핵심 전이 1 — DeepSeek의 KV 캐시 압축과는 다른 축의 "KV 캐시 효율화"

[[2026-10-01-ai-race-got-awkward-deepseek-kv-cache]]는 모델 아키텍처 레벨에서 KV 캐시 자체의 ***크기***를 줄이는 접근(크로스레이어 재사용, FP4 양자화)을 다뤘다. Quail은 모델을 전혀 바꾸지 않고, 쿼리 레이어가 가진 사전 정보로 ***같은 크기의 KV 캐시를 더 영리하게 재사용***하는 접근이다. 두 노트를 겹쳐 보면 "추론 비용을 낮춘다"는 같은 목표에 "캐시를 작게 만든다"와 "캐시를 더 잘 재사용한다"는 서로 독립적이고 결합 가능한 두 축이 있다는 게 드러난다 — 실제로는 두 기법을 함께 쓰면 효과가 중첩될 가능성이 높다.

### 핵심 전이 2 — LY Corporation의 "LLM이 만든 SQL을 신뢰하기"와 Quail의 "LLM 호출을 SQL에 넣기"는 정반대 방향

[[2026-10-02-line-a2a-conversational-bi]]는 자연어를 SQL로 "번역"해서 실행하는 text-to-SQL 문제를 다뤘다. Quail이 다루는 AI-SQL은 그 반대축이다 — SQL ***안에*** LLM 호출을 끼워 넣어(행마다 분류·추출·요약 같은 LLM 변환을 적용) 분석을 수행하는 구조다. 같은 "LLM과 SQL의 결합"이라는 큰 범주 안에서, 하나는 "LLM이 SQL을 만든다", 다른 하나는 "SQL이 LLM을 호출한다"는 서로 다른 결합 방식을 보여준다는 점이 흥미로운 대조다.

### 핵심 전이 3 — Filament의 체크섬·체크포인트와 "쿼리가 아는 것을 미리 활용한다"는 설계 철학의 거울상

[[2026-09-23-filament-data-replication-engine]]은 배치 단위로 체크섬을 검증하고 성공한 지점까지만 체크포인트를 전진시키는 안전장치였다. Quail의 "쿼리 플래너가 재사용 패턴을 미리 알려준다"는 설계는 결이 다르지만, 둘 다 ***"실행 엔진에 맡기지 않고, 상위 레이어가 가진 구조적 정보를 미리 활용해 하위 레이어를 더 효율적으로 만든다"***는 같은 설계 철학을 공유한다 — 데이터 엔지니어링에서 반복적으로 등장하는 패턴으로 묶어볼 만하다.

## 호스피탈리티 / CRS 적용 포인트

**직접 적용 가능성이 있다.** CRS에서 LLM으로 대량의 예약·리뷰·문의 데이터를 행 단위로 분류·요약·태깅하는 배치 작업(예: 리뷰 감성 분류, 취소 사유 자동 태깅)은 구조적으로 AI-SQL과 동일한 "행마다 LLM 호출" 패턴이다. 지금 단순히 반복 API 호출로 처리하고 있다면, ***"입력 프롬프트의 공유 구조(공통 프리픽스·공통 스키마)를 쿼리 레이어에서 먼저 식별해 추론 엔진에 알려준다"***는 Quail의 설계 원칙만큼은 자체 배치 파이프라인에도 그대로 옮겨볼 만하다 — vLLM 같은 자체 호스팅 추론 엔진을 쓴다면 Quail 자체를 평가해볼 가치도 있다. 다만 온다 CRS의 배치 규모가 Quail이 겨냥하는 "수십만~수백만 LLM 호출" 규모에 맞는지는 먼저 측정해야 한다.
