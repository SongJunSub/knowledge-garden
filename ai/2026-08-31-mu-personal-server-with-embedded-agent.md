# mu — 에이전트가 들어 있는 개인 서버

> 출처: [micro/mu](https://github.com/micro/mu) (Asim Aslam / Micro, AGPL-3.0) · 정리일 2026-08-31

## 한 줄 요약
**mu는 메일·채팅·파일·노트·캘린더·연락처·뉴스와 AI 에이전트를 하나의 Go 바이너리로 직접 운영하는 개인 서버다.** 30여 개 서비스와 100여 개 도구를 웹/REST API/CLI/MCP 네 가지 인터페이스에서 동일하게 제공하며, 핵심은 "에이전트용 도구를 모아놓은 서비스"가 아니라 **사용자 자신의 도메인과 디스크에 데이터와 통신 수단을 직접 모으고, 에이전트가 그 안에서 일하게 하는 것**이다. SMTP/IMAP 메일 서버를 자체 구현해 기존 메일 클라이언트로 접속할 수 있다는 점이 벤더 API 위에 얹는 대부분의 "에이전트용 도구 모음"과 가장 다른 지점이다.

## 핵심 포인트
- **단일 Go 바이너리** — 메일·뉴스·날씨·시장(주식/암호화폐)·비디오·파일·항공편·연락처·문서·이벤트·지도·셸·SMS 등 **30여 개 실서비스**를 하나의 자체 호스팅 가능한 바이너리로 묶었다. 데이터가 전부 로컬에 저장돼 검색 가능하다.
- **네 가지 인터페이스, 같은 도구 집합** — 웹(`/home`, `/inbox`, `/agents` 등)·REST API(`/api/v1/<service>/<method>`)·CLI(`mu` 명령)·MCP(`/mcp` 엔드포인트로 Claude 등 MCP 클라이언트 연결) 네 경로 모두 동일한 **100여 개 도구**에 접근한다.
- **메일 서버를 직접 구현** — 외부 메일 API에 의존하지 않고 SMTP/IMAP을 자체 구현해, 표준 메일 클라이언트를 IMAP으로 그대로 연결할 수 있다(GitHub 저장소 확인). Slack 발췌는 여기에 연합(federation) 가능한 XMPP 채팅 서버 자체 구현도 함께 언급하는데, XMPP 관련 태그·언급은 검색으로 교차 확인했지만 "연합 가능" 여부의 구체적 구현 디테일까지는 이번 세션에서 GitHub 페이지 직접 열람으로 확인하지 못했다.
- **에이전트 정의 방식** — `/agents`에서 이름·상시 지침(standing instruction)·허용 서비스로 에이전트를 만든다. 허용 서비스를 비워두면 접근 가능한 모든 도구를 쓸 수 있는데, 이는 기본값이 아니라 **명시적 선택**으로 설계돼 있다.
- **핵심 주장: 도구 모음이 아니라 "자기 도메인에 데이터를 모으는 것"** — 뉴스·검색·날씨 등을 API로 호출하는 여느 에이전트 도구 서비스와 달리, mu는 사용자의 메일·파일·연락처 같은 **1차 데이터 자체**를 자신의 디스크에 두고 그 위에서 에이전트가 일하게 하는 것이 설계의 중심이라고 강조한다.
- **라이선스·모델** — AGPL-3.0으로 자체 호스팅·수정 가능. 검색 스니펫 기준으로 유료 호스팅형 모델도 병행하는 것으로 보이나, 이 부분은 micro.mu 공식 사이트 접근이 차단돼 직접 확인하지 못했다.

## 내 생각 · 적용점

### 핵심 전이 1 — "상시 실행되는 개인 에이전트"라는 점에서 장기 실행 에이전트 논의와 정면으로 만난다
[[2026-05-04-long-running-agents]]가 정리한 핵심 장벽 세 가지(유한 컨텍스트·비영속 상태·자기검증 부재) 중, mu는 최소한 "비영속 상태" 문제를 데이터를 전부 로컬 디스크(자신의 메일함·파일·연락처)에 두는 방식으로 정면 돌파하려 한다. Brain/Hands/Session의 "Session"에 해당하는 것이 mu에서는 사용자의 실제 메일함·캘린더 그 자체가 된다는 점이 흥미로운 변형이다.

### 핵심 전이 2 — "상시 사고하는 에이전트"라는 설계 목표를 공유하지만 인프라 층위가 다르다
[[2026-08-27-headlong-persistent-agent-microharness]]가 "지속형 에이전시"(외부 요청 없이도 스스로 관심사를 정해 계속 사고)를 하네스 층위에서 구현했다면, mu는 그 에이전트가 일할 **인프라**(메일·파일·연락처를 자기 도메인에 모으기) 층위를 만든다. 둘을 합치면 "24시간 스스로 생각하는 에이전트가, 남의 API가 아니라 내 메일함에서 직접 일한다"는 그림이 완성된다 — 다만 이는 이번 정리에서 확인한 두 개별 프로젝트를 조합한 추론이지, mu와 Headlong이 실제로 연결된다는 근거는 없다.

### 핵심 전이 3 — "로컬이 정본"이라는 원칙의 정면 실천 사례
[[2026-08-02-session-portability-inference-api-lockin]]이 경고한 "추론 API가 세션 상태를 서버에 가둔다"는 문제와, mu가 SMTP/IMAP을 자체 구현해 표준 클라이언트로 접속하게 만드는 설계는 정확히 반대 방향에서 같은 원칙을 향한다 — "검사 가능·내보내기 가능·삭제 가능"한 로컬 우선 데이터가 벤더 종속을 막는 가장 실질적인 방법이라는 그 글의 결론을, mu는 메일/채팅 인프라 수준에서 실제로 구현한 사례로 볼 수 있다.

## 호스피탈리티 / CRS 적용 포인트
직접 적용은 멀다. 온다는 B2B SaaS로 개인 서버형 자체 호스팅 모델을 CRS에 그대로 옮길 이유는 없고, mu가 겨냥하는 사용자층(개인 개발자의 자체 인프라)과 온다의 고객(호텔/체인 사업자)은 근본적으로 다르다. 다만 "에이전트가 일할 도구를 API로 흩어놓지 않고, 데이터가 실제로 존재하는 도메인 안에 모아서 그 안에서 일하게 한다"는 설계 원칙 자체는, 우리가 예약·재고·CS 데이터를 여러 벤더 API로 흩어놓은 채 에이전트를 붙이는 방식과 대비해 볼 가치가 있다 — 데이터가 실제로 사는 곳과 에이전트가 일하는 곳을 가깝게 두는 설계가 왜 유리한지에 대한 참고 사례 정도로 남긴다.
