# Claude와 Claude Code에서 Opus 5.5를 최대한 활용하는 방법 (Anthropic)

> 출처: [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5) (Claude Platform Docs, Anthropic 공식) · GeekNews(id=34734) 경유 · 정리일 2026-10-04

> **출처 한계**: `news.hada.io`는 egress 차단으로 직접 열지 못했지만, **`platform.claude.com`의 공식 프롬프팅 가이드는 WebFetch로 전문을 직접 확보**했다 — effort 기본값, 장기 실행 에이전트 처리, 멀티에이전트 시간 신호, 세이프가드 거부 등 핵심 내용은 1차 소스로 확정했다. 다만 Slack 힌트가 언급한 "CLAUDE.md의 중단 규칙"·"서브에이전트 결과의 근거 검증 요청"·"사용자 결정·승인 필요 항목부터 확인"은 이 공식 문서에 그대로 나오지 않는 내용이라, Claude Code 사용 커뮤니티 글(gritai.studio, claudefa.st 등 — 전부 이 세션에서 egress 차단으로 직접 열람 불가)을 WebSearch로 교차확인해 보강했다. 이 부분은 **공식 문서가 아니라 2차 해설의 종합**임을 밝혀둔다. GeekNews 토픽이 이 공식 문서 자체를 가리키는지, 혹은 이를 요약한 제3자 블로그를 가리키는지는 hada 접근 차단으로 확정하지 못했다. hada 댓글 수도 확인 불가.

## 한 줄 요약

**Opus 5.5는 Opus 5보다 긴 다단계 작업을 끝까지 이어가는 능력이 개선됐는데, 공식 가이드의 핵심은 "effort가 이제 지능·지연·비용을 조절하는 1차 변수이니 Opus 5 때 쓰던 effort 값을 그대로 옮기지 말고 다시 측정하라"는 것이다. 기본값이 `high`에서 `medium`으로 내려갔고, Anthropic 자체 테스트에서 `medium` Opus 5.5가 `high` Opus 5와 코딩·지식노동 평가에서 동등하거나 더 나았다. 장기 무인 실행에서는 모델이 텍스트로 진행 보고를 하며 턴을 끝내는 걸 "작업 완료"로 착각해 멈추는 문제가 있어, 체크리스트와 "완료 조건이 없으면 계속하라"는 명시적 지시가 필요하다.**

## 핵심 포인트

- **effort 기본값이 `high` → `medium`으로 바뀌었다** — ***"Opus 5.5는 항상 사고(thinking)가 켜져 있으므로, effort가 지능·지연·비용을 맞바꾸는 가장 중요한 조절 변수"***이고, 기본값은 `medium`이다(Opus 5는 `high`가 기본값이었다). Anthropic 공식 테스트에서 ***"Opus 5.5의 `medium`이 코딩·지식노동 평가에서 Opus 5의 `high`와 동등하거나 그걸 넘어섰고", 일부 코딩 평가에서는 `low`도 훨씬 낮은 비용으로 비슷한 수준에 근접***했다.
- **"신중하게 생각하라"는 지시는 빼도 된다** — Opus 5.5는 응답 전에 스스로 사고량을 결정하므로, 채팅 시스템 프롬프트에 남아있던 "think carefully" 류의 상투적 지시는 제거를 권한다. Anthropic 자체 테스트에서 ***이 문구를 빼자 응답이 더 빨리 시작됐고 품질 저하는 뚜렷하지 않았다.*** 다만 effort 값을 Opus 5 때 그대로 유지하면 **턴당 사고량이 더 늘어나** 응답이 길어지고 출력 토큰이 늘 수 있다는 부작용은 명시한다.
- **장기 무인 실행의 핵심 함정 — 텍스트로 끝나는 턴을 "완료"로 오인** — 긴 다단계 작업에서 Opus 5.5는 작업 중간에 진행 상황을 사용자에게 보고하는데, 이 보고가 도구 호출 없이 텍스트만으로 턴을 끝내는 경우(`stop_reason: "end_turn"`)가 있다. 무인 에이전트 루프가 이걸 "작업 완료"로 처리하면 거기서 멈춰버린다. 처방: **작업의 각 부분을 체크리스트(투두 도구나 파일)로 관리**하고, 턴이 끝났는데 미완료 항목이 남아 있고 막힌 이유가 없으면 "남은 항목을 계속하라"는 짧은 메시지를 보내되, ***같은 작업에 대해 자동 연속 실행을 2~3회로 제한***해 진짜로 막힌 실행은 멈추고 검토 대상이 되게 한다.
- **시스템 프롬프트에 "불필요하게 멈추지 말라"는 지시를 추가할 수 있다** — 완전 무인 실행용으로, 사용자가 답하지 않아도 될 때(요약만 하고 다음 단계를 발표만 하는 경우, 승인을 굳이 묻는 경우 등) 멈추지 말고 계속하라는 지침을 시스템 프롬프트 끝에 추가하는 구체적 문구 예시를 제공한다. 단, ***"위험하거나 되돌릴 수 없는 작업에 대한 확인 절차는 그대로 유지하라"***고 명시하며, 사람이 응답을 기다리는 human-in-the-loop 애플리케이션에는 이 지침을 넣지 말라고 경고한다.
- **멀티에이전트 하네스에는 시간 신호를 줘라** — 리드 에이전트가 서브에이전트에 위임하는 구조에서, 각 메시지 끝에 "경과 340초/예산 1200초" 같은 시간 정보를 붙이면 모델이 속도를 조절해 **병렬 작업을 더 빨리 끝낸다.** 시간 예산을 좁히는 것과 effort를 낮추는 것은 다른 효과를 낸다 — effort를 낮추면 작업 자체의 질이 떨어지고, 시간 예산은 주로 **더 많은 에이전트를 동시에 병렬로 돌리게** 만든다.
- **effort 전환이 이제 세션 중간에 캐시를 깨지 않는다(단, 메시지별 전환만)** — 요청 사이에 최상위 `effort` 값을 바꾸면 프롬프트 캐시가 무효화되지만, **메시지별 effort 변경(beta)**을 쓰면 캐시가 유지된다. 이는 [[2026-08-16-maximizing-claude-code-sessions]]가 지적했던 "effort 변경이 세션 전체를 정가로 재프리필시킨다"는 Opus 5 시절 문제를, 적어도 메시지 단위 전환에서는 완화한 변화다.
- **(2차 소스 종합, 공식 문서 미확인)** 커뮤니티 해설들은 Claude Code 활용에서 **CLAUDE.md에 "언제 스스로 계속 작업하고 언제 멈춰서 사용자에게 물어볼지"를 명시하는 규칙**을 두고, **서브에이전트로 큰 작업(저장소 전체 감사, 리팩터)을 나누되 각 서브에이전트 결과에 검증 단계를 끼워 넣으라**고 권한다고 전한다. 결과를 검토할 때는 **사용자의 결정이나 승인이 필요한 항목부터 먼저 확인**하라는 조언도 여러 2차 소스에서 공통적으로 확인되지만, 이 세션에서는 원문 공식 자료로 직접 대조하지 못했다.

## 인상 깊은 문장

> "Effort is the main control for how much Claude Opus 5.5 thinks, and because thinking is always on, it's the first setting to adjust when trading off intelligence, latency, and cost."
> (effort가 더 이상 "옵션"이 아니라 1차 변수가 됐다는 선언 — 모델이 항상 사고하므로, 사고량 자체를 끄고 켜는 선택지가 사라졌다.)

> "Claude Opus 5.5 at medium matches or exceeds Claude Opus 5 at high on coding and knowledge-work evaluations."
> (effort 레벨 이름이 모델 간에 같은 사고량을 의미하지 않는다는 걸 구체적으로 보여주는 문장 — 설정을 그대로 옮기면 비용만 더 쓰고 득이 없을 수 있다.)

> "Treat a text-only end of turn as a report rather than as proof the task is done."
> (장기 실행 에이전트가 스스로를 과신해 "다 했다"고 보고하고 멈추는 문제에 대한 가장 실무적인 한 문장.)

## 내 생각 · 적용점

### 핵심 전이 1 — "effort 설정을 그대로 옮기지 말라"는 경고가 Fable 5.1 가이드에서 이미 한 번 나왔던 패턴의 반복이다

[[2026-09-03-claude-fable-5-1-prompting-guide]]는 Fable 5.1로 넘어갈 때 ***"effort가 이제 지능·지연·비용을 조절하는 첫 번째 다이얼이라, 기존 5.0 설정을 그대로 옮기면 안 된다"***고 했다. 이번 Opus 5.5 가이드는 같은 경고를 Opus 계열에서 반복한다 — 다만 방향이 다르다. Fable 5.1 가이드는 "기본값 `high`에서 시작해 필요하면 올리거나 내리라"고 했는데, Opus 5.5는 **아예 기본값 자체가 `high`에서 `medium`으로 내려갔다.** 두 모델 계열 모두에서 "effort는 모델이 바뀔 때마다 재측정해야 하는 변수"라는 원칙이 공식 가이드 수준에서 두 번째로 명문화된 셈이다 — 이게 이제 Anthropic 전체 모델 라인업의 공식 모범 사례로 굳어지고 있다고 봐도 될 것 같다.

### 핵심 전이 2 — "텍스트로 턴이 끝나면 오해해서 멈춘다"는 문제는 장기 실행 에이전트 아키텍처 논의의 구체적 실패 모드다

[[2026-05-04-long-running-agents]]는 Brain/Hands/Session 3분리 아키텍처와 "완료 조건을 시작 전에 외부 파일로 명시하라"는 원칙을 다뤘다. 이번 가이드의 "체크리스트 + 미완료 항목이 남았는데 막힌 이유가 없으면 계속하라고 알려준다"는 처방은, 그 원칙을 **Claude Opus 5.5라는 구체적 모델의 구체적 실패 모드**(진행 보고를 완료 신호로 착각)에 맞춰 정확히 구현한 것이다. "완료 조건의 외부화"라는 추상적 설계 원칙이, 실제로는 "자동 연속 실행을 2~3회로 제한하라"는 매우 구체적인 숫자로 번역되는 과정을 보여준다는 게 흥미롭다 — 원칙은 일반적이어도 구현은 모델마다 다시 튜닝해야 한다는 뜻이다.

### 핵심 전이 3 — 캐시-effort 결합 문제가 "메시지별 전환"으로 부분적으로 풀렸다

[[2026-08-16-maximizing-claude-code-sessions]]가 짚었던 **"effort 수준도 캐시 키의 일부라 세션 중간에 바꾸면 대화 전체가 정가로 재프리필된다"**는 문제를, 이번 가이드는 최상위 `effort` 전환에는 여전히 그대로 적용된다고 인정하면서도 **메시지별 effort 변경(beta)**이라는 우회로를 공식 제공한다. 캐시 키 설계의 구조적 문제(모델·effort·Fast 모드가 캐시를 깬다는) 자체를 없애지는 않았지만, 적어도 "어려운 턴만 effort를 잠깐 올렸다 내리는" 흔한 사용 패턴에는 구멍을 뚫어준 셈이다 — 근본 해결이 아니라 자주 쓰는 경로 하나를 예외 처리한 방식이라는 점도 함께 적어둔다.

## 호스피탈리티 / CRS 적용 포인트

**이 가이드는 온다가 Claude Code나 Opus 5.5 API를 실무에 쓸 때 직접 적용할 수 있는 체크리스트를 제공한다.** ①**모델을 Opus 5에서 5.5로 전환할 계획이 있다면 effort 값을 그대로 복붙하지 말고, CRS 실제 작업(코드 리뷰, 데이터 마이그레이션, 리포트 생성)으로 `low`~`max`를 비교하는 미니 평가셋을 먼저 만들 것** — `medium`이 비용 절감 후보일 가능성이 높다. ②**야간 배치 작업(대량 마이그레이션, 코드 감사처럼 사람이 지켜보지 않는 장기 실행)에 Opus 5.5를 쓴다면, 체크리스트 기반 진행 관리와 "완료 조건 미달 시 자동 재개, 단 2~3회 제한" 규칙을 하네스에 반영**해야 한다 — 그렇지 않으면 진행 보고 한 줄에 작업이 조용히 멈출 수 있다. ③**여러 에이전트를 병렬로 돌리는 구조(예: 여러 호텔 파트너사 데이터를 동시 처리)라면 effort를 낮추는 대신 시간 예산 신호를 주는 쪽이, 품질을 유지하면서 속도를 올리는 더 나은 레버일 수 있다.**
