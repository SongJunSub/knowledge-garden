# LiteLLM PyPI 패키지에 인증 정보 탈취 악성코드와 백도어 삽입

> 출처: GeekNews 토픽(원문 매체 미확인) · GeekNews(id=35767) 경유 · 정리일 2026-10-22

> **출처 한계(중요)**: `news.hada.io`가 이 세션에서 egress 차단으로 열리지 않아 원문을 직접 확인하지 못했다. WebSearch로 Cloud Security Alliance·Averlon(GHSA-5mg7-485q-xm76)·the-decoder·ox.security 등 복수 보안 매체를 교차확인했는데, ***이번 조사로 확인한 실제 사건은 Slack 발췌의 "1.107.0"이 아니라 "1.82.7·1.82.8" 두 버전이었다*** — 2026년 3월 24일, 위협 행위자 그룹(TeamPCP로 보도됨)이 LiteLLM의 CI/CD 파이프라인에서 5일 전 침투한 백도어 Trivy 스캐너를 통해 PyPI 배포 토큰을 탈취하고, 이를 이용해 두 개의 악성 버전을 PyPI에 올렸다. 버전 번호가 Slack 발췌와 다르다는 점은 ①같은 사건을 매체마다 다르게 표기했거나 ②실제로는 별도의 두 번째 사건(1.107.0)이 있었는데 이번 조사에서 찾지 못했을 가능성 둘 다 열어둬야 한다 — ***이 노트는 WebSearch로 확인한 "1.82.7/1.82.8" 사건의 기술적 세부(공급망 경로·페이로드·영향 범위)를 중심으로 재구성했고, Slack 발췌의 "7개 설치 패키지" 서술은 원문 대조를 못해 그대로 남겨둔다.*** hada 댓글 수·HN/Lobsters 큐레이션 여부도 확인 불가.

## 한 줄 요약

**여러 LLM의 API를 연결하는 오픈소스 프록시 LiteLLM의 PyPI 배포본에서 인증 정보 탈취 악성코드와 백도어가 발견됐다 — 공격자는 LiteLLM을 직접 import하지 않아도 Python 시작 시 자동 실행되는 방식으로 SSH 키·클라우드 인증 정보·브라우저 비밀번호·AI 개발 도구 토큰·LiteLLM 프록시 데이터베이스에 저장된 LLM 제공업체 API 키까지 수집해 외부로 전송했으며, WebSearch로 확인한 실제 공격은 LiteLLM 자신의 CI/CD 파이프라인이 먼저 백도어 보안 스캐너에 당해 PyPI 배포 권한을 빼앗긴 결과였다.**

## 핵심 포인트

- **설치만 해도, import 없이도 실행된다** — 감염된 Python 환경에서는 LiteLLM을 직접 불러오지 않아도 ***Python 시작 시 악성코드가 실행***된다. WebSearch로 확인한 기술적 메커니즘으로는, 두 악성 버전 중 하나가 `.pth` 파일(Python이 시작할 때마다 자동으로 읽는 특수 파일)을 심어 ***해당 환경의 모든 Python 프로세스에 영향***을 미치게 만들었다 — 일반 애플리케이션뿐 아니라 pip, IDE 언어 서버, CI 작업도 실행 계기가 될 수 있다는 Slack 발췌의 서술과 정확히 일치한다.
- **탈취 대상 — SSH 키부터 LLM API 키까지** — SSH 키와 클라우드 인증 정보, 브라우저 비밀번호, AI 개발 도구 토큰을 수집해 외부로 전송했다. ***LiteLLM 프록시 데이터베이스에 저장된 LLM 제공업체 API 키***도 탈취 대상이었다는 점이 특히 무겁다 — LiteLLM 자체가 "여러 LLM API를 중계하는 게이트웨이"이기 때문에, 이 게이트웨이가 뚫리면 그 뒤에 물려 있는 모든 LLM 호출의 자격증명이 한 번에 노출되는 구조다.
- **(WebSearch로 확인한 공급망 경로) 공격의 시작점은 보안 스캐너 자체였다** — 2026년 3월 24일 사건의 경우, 공격자는 LiteLLM을 직접 뚫은 게 아니라 ***LiteLLM의 CI/CD 파이프라인이 사용하던 보안 취약점 스캐너(Trivy)를 5일 앞서 백도어화해, 그걸 통해 PyPI 배포 토큰을 탈취***했다고 보도된다. "보안을 점검하는 도구"가 공급망 공격의 진입점이 됐다는 역설이 핵심이다.
- **대응** — WebSearch로 확인한 권고로는, 마지막으로 확인된 깨끗한 버전(1.82.6 등)으로 되돌리고 LiteLLM 환경에서 접근 가능했던 모든 자격증명(LLM API 키 포함)을 즉시 전면 교체(rotate)하라는 것이었다 — "삭제"가 아니라 "이미 노출됐다고 가정하고 전부 교체"가 권고의 핵심이다.

## 인상 깊은 문장

> "the entirety of process.env at build time" 류의 사고(빌드 시점에 환경 전체가 산출물에 박히는 구조)는 아니지만, 같은 교훈으로 이어진다 — ***"보안 도구를 신뢰하고 CI에 넣었다는 사실 자체가 공급망 공격 표면이 된다."*** (WebSearch로 교차확인한 보도 재구성, 원문 인용 대조는 못함)

## 댓글

`news.hada.io` 전면 차단으로 hada 댓글 수·HN/Lobsters 큐레이션 여부를 확인하지 못했다. 정직하게 짚을 점: ①Slack 발췌의 버전 번호(1.107.0)와 WebSearch로 확인한 실제 사건의 버전 번호(1.82.7/1.82.8)가 일치하지 않아, 이 노트가 정확히 같은 사건을 다루고 있는지에 불확실성이 남는다. ②LiteLLM 공식 Docker 이미지 사용자는 의존성 버전이 고정(pin)돼 있어 영향을 받지 않았다는 보도도 있다 — "LiteLLM을 쓴다"와 "이 공격에 노출됐다"가 자동으로 같지 않다는 점도 밝혀둔다. ③공격 그룹(TeamPCP로 보도)의 신원·동기에 대한 1차 자료는 확인하지 못했다.

## 내 생각 · 적용점

**핵심 전이 1 — [[2026-10-21-abliterated-model-backdoor-supply-chain]]과 똑같이 "백도어"라는 단어를 쓰지만, 공급망 공격이 침투한 단계가 완전히 다르다.** 그 노트가 다룬 ProjectDiscovery 연구는 ***모델 파인튠 단계***(가중치 자체에 트리거 기반 악성 동작을 심음)에서 벌어진 공격이었다 — 모델을 받아오는 순간 이미 위협이 결정돼 있고, 런타임 입력 검증으로는 막을 수 없다는 게 그 노트의 결론이었다. 이번 LiteLLM 사건은 ***패키지 배포 단계***(PyPI에 올라가는 산출물 자체가 오염)의 공격이다 — "모델 가중치를 어떻게 검증할 것인가"가 아니라 "이 패키지의 CI/CD 파이프라인과 배포 권한을 누가 통제하는가"가 핵심 질문이 된다는 점에서, 같은 "AI 공급망을 겨눈 백도어"라는 제목 아래 사실은 서로 다른 방어선(모델 출처 검증 vs 패키지·배포 파이프라인 보안)이 필요하다는 게 두 사건을 나란히 놓았을 때 가장 또렷해지는 교훈이다.

**핵심 전이 2 — [[2026-06-08-aur-supply-chain-malware]]가 보여준 "설치 자체가 임의 코드 실행이 된다"는 패키지 매니저의 근본 구조가, 이번엔 `.pth` 파일이라는 Python 고유의 자동 실행 메커니즘으로 재현됐다.** AUR 사건은 PKGBUILD의 install/hook 스크립트가 설치 시점에 자동 실행되는 구조를 악용했다. 이번 LiteLLM 사건의 `.pth` 파일은 ***"설치만 하면 실행된다"를 한 단계 더 끌어올려, import조차 필요 없이 Python 인터프리터가 켜질 때마다 실행***되는 더 넓은 트리거다 — PKGBUILD는 그 패키지를 설치하는 사람에게만 영향을 미치지만, `.pth`는 그 환경에서 돌아가는 ***다른 모든 Python 프로세스***(IDE 언어 서버, CI 작업 등)까지 끌어들인다는 점에서 폭발 반경이 더 넓다.

**핵심 전이 3 — [[2026-07-25-hanwha-vision-github-token-firmware]]가 짚은 "CI/CD 파이프라인 자체가 공격 표면"이라는 교훈이, 이번엔 사고가 아니라 의도된 공격으로 재현된다.** 한화비전 사건은 빌드 도구(Vite)가 의도치 않게 CI 환경변수 전체를 산출물에 박아넣은 ***실수***였다. 이번 LiteLLM 사건은 공격자가 CI 파이프라인에 쓰이는 보안 스캐너를 ***의도적으로 백도어화***해 배포 토큰을 탈취한 ***공격***이다. 사고와 공격이라는 출발점은 다르지만, 결론은 같다 — ***"소스 코드가 깨끗한가"만 보고 "그 코드를 빌드·배포하는 파이프라인이 안전한가"를 보지 않으면, 공급망의 가장 약한 지점은 늘 파이프라인 쪽에 남는다.***

## 호스피탈리티 / CRS 적용 포인트

**직접 적용 가능성 있음.** 온다 개발자들이 LLM 기능(요금 문의 응대, 리뷰 요약 등)을 구현하며 LiteLLM 같은 LLM 게이트웨이/프록시 오픈소스를 도입하거나 자체 CI에 보안 스캐너를 넣을 때 이 사건이 직접 참고가 된다.

- **LLM 게이트웨이 자체가 "모든 LLM API 키가 모이는 단일 지점"이라는 걸 전제로, 그 게이트웨이의 의존성·CI/CD 권한을 별도로 취급한다.** 이 사건에서 가장 무거웠던 피해가 "프록시 데이터베이스에 저장된 LLM 제공업체 API 키" 탈취였다는 걸 생각하면, 게이트웨이를 쓸수록 자격증명이 한곳에 몰리는 구조적 위험이 커진다는 점을 설계 단계에서 감안해야 한다.
- **CI에 넣는 보안 스캐너·린터 같은 "신뢰하는 도구"도 공급망 신뢰 경계 안에 넣어 버전을 고정하고 변경을 감시한다.** "보안 도구이니 믿고 자동 업데이트"가 오히려 침투 경로가 된 사례다.
- **의존성 설치 시 `--ignore-scripts`·고정 버전(pin)·사설 미러를 기본값으로 둔다.** `.pth` 파일처럼 "설치=실행"을 넘어 "Python 시작=실행"까지 가는 트리거가 있다는 걸 이번 사건이 보여준 만큼, 자동 실행을 차단하는 설정을 CI·로컬 개발 환경 모두의 기본값으로 둘 필요가 있다.
