# LLM 시대의 확장 가능한 소프트웨어 (GeekNews)

> 출처: [LLM 시대의 확장 가능한 소프트웨어](https://news.hada.io/topic?id=36837) (GeekNews) · 정리일 2026-11-09

> **출처 한계**: `news.hada.io`가 이 세션에서 egress 차단되어 원문을 열람하지 못했다. WebSearch로 정확히 일치하는 1차 소스는 찾지 못했다 — 대신 멀티테넌트 AI 에이전트/LLM 게이트웨이의 테넌트 격리 설계를 다루는 벤더 자료(Gravitee 등)와, WASM 기반 확장 코드 실행이 서브밀리초 콜드스타트·강한 메모리 격리를 제공한다는 커뮤니티 발표 요약만 교차확인했다. 이 글 고유의 구체적 구현 사례나 수치는 확인하지 못했고, Slack 발췌 자체도 "안전한 확장은 광범위한 API 접근을 허…"에서 절단됐다.

## 한 줄 요약

**LLM의 확장 코드 작성 능력과 현대적인 샌드박스 기술을 결합하면, 제품 코어는 안정적으로 유지하면서 사용자별 롱테일 요구를 사용자가 직접 만들고 공유하는 확장 기능으로 채울 수 있다는 주장이며, 이를 안전하게 하려면 저렴한 실행 비용·빠른 콜드 스타트뿐 아니라 자원 제한·테넌트 격리·데이터 유출 방지가 필수 전제라는 게 핵심이다.**

## 핵심 포인트

- **핵심 기회**: LLM의 확장 코드 작성 능력과 현대적인 샌드박스를 결합하면, ***웹 앱의 안정적인 코어를 유지하면서 사용자별 요구를 확장 기능으로 채우는*** 새로운 기회가 생긴다는 주장(Slack 발췌).
- **UI 복잡성 트레이드오프**: 모든 기능을 제품에 넣으면 ***UI 복잡성이 커지지만***, 사용자가 필요한 확장을 만들고 공유하는 방식은 ***코어를 비대하게 만들지 않고 롱테일 수요를 수용***할 수 있다는 설계 원칙(Slack 발췌).
- **전제 조건 4가지**: 웹에서 사용자 코드를 실행하려면 ①저렴한 실행 비용 ②빠른 콜드 스타트뿐 아니라 ③자원 제한 ④테넌트 격리 ⑤데이터 유출 방지가 필요하다고 명시(Slack 발췌).
- **API 접근 범위(절단)**: "안전한 확장은 광범위한 API 접근을 허…"에서 끊겨, 구체적으로 어느 수준까지 API를 열어줘야 하는지에 대한 결론은 확인하지 못했다.
- **WebSearch로 보탠 배경**: 커뮤니티 발표 자료는 WASM 기반 워커가 서브밀리초 콜드스타트와 강한 메모리 격리를 제공해 "상태 없는 확장 코드"에 적합하며, 테넌트가 명시적으로 허용한 URL로만 egress를 제한하는 패턴을 든다 — 이 글이 말하는 "저렴한 실행+빠른 콜드스타트+격리"라는 요구조건과 방향이 일치하지만, 이 글이 실제로 WASM을 언급했는지는 확인 못함.

## 내 생각 · 적용점

### 핵심 전이 1 — 바로 같은 날 Replit이 보여준 "격리 비용을 먼저 해결해야 확장을 열 수 있다"는 사례

이 글의 네 가지 전제 조건 중 "테넌트 격리"는 추상적 원칙처럼 보이지만, 같은 배치에서 정리한 [[2026-11-09-replit-microvm-sandbox-rewrite]]가 바로 그 격리를 실제로 구현한 사례다 — Replit은 자사 플랫폼에서 돌아가는 사용자 코드(에이전트가 만든 코드 포함)를 위해 공유 커널에서 샌드박스별 microVM으로 격리 경계를 올렸다. 이 글이 "사용자가 확장을 만들고 공유한다"는 제품 비전을 제시했다면, Replit 사례는 그 비전이 실제로 요구하는 인프라 투자(microVM, eBPF 모니터링)의 구체적 크기를 보여준다 — 비전과 그 비전의 실제 인프라 비용이 같은 날 나란히 올라온 셈이다.

### 핵심 전이 2 — 샌드박스 격리 원칙과 확장 코드 자체의 신뢰 문제는 다른 축이다

[[2026-10-31-cursor-marketplace-claude-code-ssh-backdoor]]와 [[2026-11-04-postman-silent-agent-plugin-install]]은 "확장/플러그인을 로드하는 행위 자체가 위험할 수 있다"는, 이 글과는 다른 축의 경고다. 이 글이 말하는 "테넌트 격리·자원 제한"은 확장 코드가 **실행 중에** 할 수 있는 일을 제한하는 런타임 격리이고, 저 두 노트가 다루는 건 **설치/로드 시점**에 이미 변조된 확장이 신뢰를 얻는 공급망 문제다. 사용자 생성 확장 생태계를 설계한다면 이 두 축(런타임 격리 + 설치 시점 신뢰 검증) 모두를 갖춰야 한다는 걸 세 노트를 겹쳐보면 알 수 있다.

### 핵심 전이 3 — AWS의 에이전트 샌드박스 시리즈와 같은 문제의식의 제품 레이어 버전

[[2026-10-18-aws-agent-sandbox-eks-isolation-part1]]부터 이어진 AWS의 EKS 기반 에이전트 샌드박스 시리즈는 "AI 빌더(개발자)가 만든 에이전트를 어떻게 격리 실행할까"를 다뤘다. 이 글은 그 문제를 한 단계 더 일반 사용자 쪽으로 내려, "최종 사용자가 LLM으로 짠 확장 코드를 제품 안에서 어떻게 안전하게 돌릴까"로 치환한다 — 개발자용 에이전트 샌드박스와 최종 사용자용 확장 샌드박스가 같은 격리 기술 스택(VM/microVM, eBPF, 자원 제한)을 공유하는 하나의 연속선임을 보여준다.

## 호스피탈리티 / CRS 적용 포인트

**적용 가능성 있음(제한적).** 온다 CRS가 호텔사마다 다른 요금 규칙·리포트 커스터마이징 요구를 모두 코어 제품에 넣기보다, 호텔사(또는 파트너 개발자)가 LLM으로 짠 소규모 확장(맞춤 요금 계산 로직, 전용 리포트 필터 등)을 안전하게 실행하게 하는 모델은 장기적으로 검토할 만한 방향이다. 다만 이 글이 전제로 깔아둔 네 가지 조건(실행비용·콜드스타트·자원제한·테넌트격리) 중 CRS처럼 **다수 호텔사의 예약·결제 데이터가 공유 인프라에서 돌아가는 멀티테넌트 환경**에서는 테넌트 격리와 데이터 유출 방지가 특히 엄격해야 한다 — 한 호텔사의 확장 코드 버그가 다른 호텔사의 예약 데이터에 접근하는 사고는 CRS에서 치명적이다.
