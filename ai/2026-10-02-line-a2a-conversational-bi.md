# LLM이 만든 SQL을 믿고 실행하기까지: A2A 기반 대화형 BI 애플리케이션 개발기 (LY Corporation)

## 한 줄 요약

**LY Corporation은 자연어 질문을 SQL로 변환해 데이터를 시각화하는 대화형 BI 애플리케이션을 만들면서, LLM이 사내 데이터의 비즈니스 맥락(지표 정의·테이블 관계)을 모르는 탓에 틀린 답을 내놓는 문제를 겪었다 — 해결책으로 지표 정의와 데이터 관계를 체계화한 온톨로지 기반 RAG와, SQL 생성·데이터 검증·시각화 등 역할이 분리된 A2A(Agent-to-Agent) 멀티에이전트 구조를 도입해 단일 MCP 구조보다 정확성·일관성·운영 안정성을 확보했다고 밝힌다.**

## 핵심 포인트

- **문제: LLM은 "스키마"는 알아도 "비즈니스 맥락"은 모른다** — 자연어를 SQL로 바꾸는 작업 자체는 LLM이 잘하지만, ***"활성 사용자"나 "매출"처럼 사내에서 통용되는 지표의 정확한 정의, 테이블 간 관계(어떤 조인이 올바른지)***를 모르면 문법적으로는 맞지만 의미적으로 틀린 SQL을 만들어낸다는 게 출발점이다.
- **해결책 1: 온톨로지 기반 RAG** — 지표 정의와 데이터 관계를 체계적으로 정리한 온톨로지를 만들고, 질문이 들어오면 관련 온톨로지 조각을 검색(RAG)해 LLM에게 컨텍스트로 제공한다. 이렇게 하면 LLM이 ***"이 질문에서 '구매자'가 정확히 어떤 테이블의 어떤 조건을 뜻하는지"***를 매번 추측하는 대신 조회해서 쓸 수 있다.
- **해결책 2: A2A(Agent-to-Agent) 역할 분리** — 단일 에이전트(또는 단일 MCP 구조)가 질문 이해부터 SQL 생성, 검증, 시각화까지 전부 처리하는 대신, ***역할이 명확한 여러 전문 에이전트가 단계별로 협업***하는 구조로 바꿨다. WebSearch로 교차확인한 영문 글에 따르면 이 구조는 SQL 생성부터 데이터 검증, 시각화까지 **각 에이전트가 특정 역할에 특화**되고, 잘 정의된 프로토콜로 협업한다. 규칙이 에이전트별로 분산돼 있어 ***새 기능을 추가해도 기존 동작에 영향을 주지 않는다***는 게 핵심 장점으로 소개된다.
- **단일 MCP 구조와의 대조** — 영문 글은 이 A2A 구조가 "모놀리식 MCP 구조로는 달성하기 어려웠던 정확성·일관성·운영 안정성을 갖춘 분석 기반"을 세웠다고 주장한다. 다만 **이 비교의 구체적 근거(수치, 전후 비교 실험)는 확인하지 못했다.**
- **운영 환경의 안전장치** — Slack 발췌는 운영 환경에서 발생할 수 있는 ***데이터 권한 및 리소스 오남용 문제를 방지하기 위한 안전장치***를 설계했다고 언급한다. WebSearch로 확인한 관련 배경지식(일반론)에 따르면 OAuth·토큰 기반 인증은 리소스 레벨의 세밀한 권한 제어에 한계가 있어, 실제 인가 로직은 애플리케이션 레이어에서 직접 구현해야 하는 경우가 많다는 점이 이런 설계의 일반적 배경으로 꼽히지만, ***LY가 정확히 어떤 메커니즘을 썼는지는 원문 미확인이라 답할 수 없다.***
- **재사용 가능한 파이프라인** — 같은 데이터 구조와 파이프라인을 다른 서비스로 분석 범위를 확장할 때도 재사용할 수 있도록 설계했다고 밝힌다.

## 내 생각 · 적용점

### 핵심 전이 1 — "LLM에게 어디까지 맡길 것인가"를 같은 회사가 또 다른 각도에서 풀었다

[[2026-09-18-line-ai-agent-ad-report-automation]]은 같은 LY Corporation이 광고 분석 리포트 자동화에서 ***"계산과 해석을 한 프롬프트에 몰아넣었을 때 실패하고, 둘을 분리하고서야 안정적인 리포트가 나왔다"***는 결론에 도달한 사례였다. 이번 A2A 구조의 "역할 분리"는 정확히 같은 원칙을 SQL/BI 영역에 적용한 것으로 읽힌다 — **한 회사가 서로 다른 두 제품(광고 리포트, 대화형 BI)에서 독립적으로 "LLM의 역할을 분리하면 신뢰성이 올라간다"는 같은 결론에 도달했다는 점이 이 연결의 핵심 가치다.**

### 핵심 전이 2 — "코딩은 해결된 문제가 아니다"의 구체적 production 대응 사례

[[2026-09-29-coding-is-not-a-solved-problem]]은 "생성 비용은 0에 가까워져도 검증·신뢰 비용은 그대로 남는다"고 지적했다. 이번 글의 제목("LLM이 만든 SQL을 믿고 실행하기까지")은 그 지적을 **SQL 생성이라는 구체적 영역에서 실제로 겪은 프로덕션 문제**로 보여준다. 해결책(온톨로지 RAG + A2A 검증 단계)은 결국 "LLM의 지능 자체를 높이는 게 아니라, 검증 구조를 하네스 레벨에 쌓아서 신뢰를 확보한다"는 그 노트의 결론과 같은 방향이다.

### 핵심 전이 3 — 같은 회사의 "코드 기준 지식 SSOT"와 "온톨로지 RAG"는 같은 문제의 두 해법이다

[[2026-08-28-line-llm-wiki-code-driven-ssot]]에서 다룬 LLM Wiki(코드에서 뽑은 raw와 LLM이 정리한 knowledge를 분리)는, 이번 온톨로지 기반 RAG와 ***"LLM이 비즈니스 맥락을 모른다"는 같은 근본 문제에 대한 두 가지 다른 접근***이다. 하나는 코드를 근거로 지식을 구조화하고, 다른 하나는 지표·관계를 온톨로지로 구조화한다 — LY Corporation이 "LLM에게 조직의 암묵지를 어떻게 체계적으로 먹일 것인가"를 여러 프로젝트에서 반복해서 풀고 있다는 패턴이 보인다.

## 호스피탈리티 / CRS 적용 포인트

이번 배치 중 비교적 직접적인 CRS 접점이 있다: **"자연어로 예약·매출 데이터를 질의하는 대화형 BI"는 CRS/호텔 운영 대시보드에 그대로 옮겨볼 만한 아이디어다.** 다만 이 글이 겪은 것과 똑같은 함정이 기다린다 — "점유율", "ADR(평균객실단가)", "노쇼율" 같은 지표의 정의가 호텔·채널마다 미묘하게 다를 수 있어, ***지표 정의를 온톨로지로 먼저 고정하지 않으면 LLM이 숫자를 잘못 계산한 SQL을 "그럴듯하게" 내놓을 위험***이 크다. A2A식 역할 분리(SQL 생성 에이전트와 검증 에이전트를 분리)는 매출 리포트처럼 틀리면 안 되는 수치에 특히 적용할 가치가 있는 패턴이다.
