# Claude Cookbook — 레시피 100개보다 중요한 건 "운영" 카테고리가 생겼다는 사실

> 출처: [Claude Cookbook](https://platform.claude.com/cookbook/) (Anthropic 공식 · GeekNews GN⁺ 요약 + HN 큐레이션) · 정리일 2026-07-25

## 한 줄 요약

**Anthropic의 공식 레시피 저장소가 **100개 이상**으로 커졌고, 목차 자체가 지난 2년 동안 "LLM으로 무엇을 만드는가"가 어떻게 변했는지를 보여준다. 2024년 항목들은 *JSON 추출·계산기 도구·프롬프트 캐싱* 같은 **단일 호출 기법**이고, 2026년 항목들은 *비동기 멀티에이전트 오케스트레이션·세션 브라우저·에이전트 호스팅(Docker/Modal/Kubernetes)·프롬프트 버전 관리와 롤백·아웃컴 그레이더로 자기 검증·SRE 인시던트 대응 에이전트*다. **레시피북이 아니라 운영 매뉴얼로 이동 중**이라는 뜻이다. 카테고리는 크게 에이전트 패턴 / Agent SDK / Managed Agents / 도구 사용 / RAG·검색 / 멀티모달 / 응답·캐싱 / 확장 사고 / 평가 / 스킬 / 관측성·운영 / 코딩·프론트엔드 / 서드파티 통합. 장기 실행 에이전트를 위한 **메모리·컨텍스트 압축**과 **임베딩 기반 도구 검색**, **비용·관측성·안전장치**, **사람의 승인** 항목이 별도로 있는 게 이번 버전의 성격을 말해 준다. 다만 HN의 반론이 날카롭다 — 이런 기법의 상당수는 ***"모델 능력 향상과 함께 빠르게 무의미해진다"***. 2024년의 프롬프트 엔지니어링 기법 다수가 추론 모델과 하네스 업데이트로 불필요해졌듯이. 그래서 이 문서는 **레시피를 외우는 용도가 아니라, 내 문제에 해당하는 항목을 찾아 읽고 버리는 색인**으로 쓰는 게 맞다.**

## 핵심 포인트

- **규모** — **100개 이상의 레시피**, 최신 갱신 2026-06. 오픈 기여(`anthropics/claude-cookbooks`).
- **에이전트 패턴** — *비동기 멀티에이전트 오케스트레이션*(고정 N-에이전트 팀 vs 동적 생성 서브에이전트), *evaluator-optimizer*(생성/평가 피드백 루프), *orchestrator-workers*(중앙 LLM의 동적 위임), *basic workflows*(비용/지연 최적화 다중 LLM 패턴).
- **Agent SDK** — 리서치 에이전트 → chief of staff(서브에이전트·훅·플랜 모드) → observability(MCP로 GitHub/CI) → SRE 에이전트 → **OpenAI Agents SDK에서 마이그레이션** → **세션 브라우저**(디스크 기반 세션 관리·대화 히스토리) → **취약점 탐지 에이전트** → **호스팅**(Docker·Modal·Kubernetes, 3단계 운영 성숙도).
- **Managed Agents** — 에이전트/환경/세션 생성, 파일 마운트, **Vault 기반 MCP 자격증명**, **웹훅 패턴**, **서버 측 프롬프트 버전 관리와 롤백**, 전문가 팀 조율, **아웃컴 그레이더로 자기 검증**, **메모리 저장소로 사용자 선호 학습**.
- **도구 사용 (고급)** — **PTC(programmatic tool calling)**, **임베딩 기반 도구 검색**(수천 개 도구), **자동 컨텍스트 압축**, **컨텍스트 엔지니어링 전략 비교**(메모리 vs 압축 vs 도구 초기화), 병렬 도구 호출, 위협 인텔 강화 에이전트.
- **RAG·검색** — 기본 RAG, **contextual retrieval**(청크 임베딩 전 컨텍스트 부여 + 프롬프트 캐싱), **text-to-SQL**, **지식 그래프 구축**, 분류, 요약, 문서 전사. LlamaIndex/Pinecone/MongoDB 통합.
- **멀티모달** — 비전 기초·베스트 프랙티스, 차트·그래프·슬라이드 판독, **크롭 도구 제공**, Haiku를 서브에이전트로 쓰기.
- **평가(Evals)** — 평가 시스템 구축, **합성 테스트 데이터 생성**, **도구 평가**, **Claude의 벤치마크 점수 재현**(DeepSearchQA/BrowseComp).
- **관측성·운영** — **Usage & Cost Admin API**로 프로그래매틱 비용 분석, **Fable 5 분류기 차단 감지 및 폴백/과금 가이드**.
- **응답·캐싱** — 프롬프트 캐싱, **speculative prompt caching**(사용자 입력 전 캐시 사전 준비), 배치 처리(50% 절감), JSON 모드, 인용, 모더레이션 필터.

## 내 생각 · 적용점

### 핵심 전이 1 — 이 배치의 짝 글([[2026-07-25-context-engineering-rules-claude-5]])과 **정반대로 읽히는데, 결론이 같다**

한쪽은 *"프롬프트를 80% 지워라"*, 다른 쪽은 *"기법 100개를 봐라"* — 표면적으로 모순이다. 그런데 HN 댓글이 둘을 화해시킨다: ***"충실한 프롬프트 사용이 낡은 최적화를 피하는 방법"***. 즉 두 글이 실제로 말하는 건 같다.

> **기교(technique)는 감가상각되고, 구조(structure)는 남는다.**

Cookbook에서 감가상각되는 것: 프롬프트 트릭, prefill 우회, JSON 모드 강제 요령, 특정 모델용 포맷 지시.
Cookbook에서 남는 것: **평가 시스템, 비용·관측성, 배포·롤백, 사람의 승인 게이트, 메모리·컨텍스트 전략, 아웃컴 그레이더.**

**읽는 순서를 이렇게 바꾸면 이 문서의 가치가 완전히 달라진다** — 프롬프트 팁 섹션은 건너뛰고, **Evals / Observability & Operations / Managed Agents(버전 관리·롤백·웹훅) 부터** 읽는다. 그쪽은 모델이 바뀌어도 안 없어진다.

### 핵심 전이 2 — 목차의 시간축이 "LLM 앱"의 성숙 곡선을 그대로 보여준다

날짜를 따라 읽으면 이 문서는 산업의 연대기가 된다:

| 시기 | 대표 항목 | 관심사 |
|---|---|---|
| 2023~2024 초 | 위키피디아 검색, PDF 업로드, 메타프롬프트 | **호출 하나를 성공시키기** |
| 2024 중 | JSON 추출, 도구 선택, 프롬프트 캐싱, 배치 | **비용·형식 통제** |
| 2024 말 | evaluator-optimizer, orchestrator-workers | **워크플로 패턴** |
| 2025 | Agent SDK, PTC, 도구 검색, 메모리, 컨텍스트 압축 | **에이전트를 오래 돌리기** |
| 2026 | 호스팅, 프롬프트 버전 관리·롤백, 아웃컴 그레이더, SRE 에이전트, 벤치마크 재현 | **운영·검증·거버넌스** |

**2026년 항목이 전부 "운영" 쪽인 게 핵심 신호다.** 이건 [[2026-07-13-ai-agents-are-the-new-saas]]·[[2026-07-13-new-saas-playbook-ai-agent-era]]가 말한 흐름과 같고, 무엇보다 이번 배치의 [[2026-07-25-why-software-factories-fail]]·[[2026-07-25-nothing-works-and-everyone-is-euphoric]]가 말한 **"생성이 아니라 검증·운영이 병목"**을 벤더가 목차로 인정한 것이다. *레시피북이 운영 매뉴얼로 바뀌는 시점 = 기술이 실험에서 프로덕션으로 넘어가는 시점.*

### 핵심 전이 3 — "아웃컴 그레이더로 자기 검증"은 내 방법론의 DoD 게이트와 같은 물건이다

Managed Agents의 *"Outcomes: verify own work — 등급 및 개정 루프"*는 내 strict.md의 **DoD 게이트**(완료를 주장하기 직전, 선언한 DoD를 *실행 가능한 체크*로 외부화하고 통과할 때까지 재작업)와 **동일한 패턴**이다. 그리고 [[2026-07-25-context-engineering-rules-claude-5]]가 권한 *"평가 기준표(rubric)를 참조 자료로 주라"*와도 같다.

세 곳에서 독립적으로 같은 결론이 나왔다는 건, 이게 이번 세대 에이전트 운영의 **핵심 프리미티브**라는 뜻이다:

> **에이전트에게 "잘했는지"를 묻지 말고, 통과 여부가 결정적으로 판정되는 rubric을 주고 통과할 때까지 돌려라.**

이게 [[2026-07-25-why-software-factories-fail]]가 지적한 *"모델이 좋은 코드와 나쁜 코드를 구분할 수 있었다면 애초에 좋은 걸 썼을 것"*이라는 순환 논증을 **부분적으로** 깨는 방법이기도 하다 — 판정 기준이 모델 바깥(테스트·린트·종료 코드)에 있으면 순환이 아니다. **다만 rubric을 사람이 써야 한다**는 조건이 붙는다. 결국 사람 몫은 다시 상류로 간다.

### 핵심 전이 4 — 정직한 급소: **이 문서에서 가장 위험한 건 오래된 레시피가 삭제되지 않는다는 점**

2024년 3월 항목과 2026년 6월 항목이 **같은 목차에 나란히** 있다. `Sampling beyond max tokens`(prefill 기법)은 최신 모델에서 **400 에러**를 반환하고, `JSON mode` 요령은 structured outputs로 대체됐다. 그런데 목차만 보면 구분이 안 된다.

**공식 문서라는 권위 + 누적형 구조 = 낡은 조언이 계속 인용되는 조건.** 이건 이 가든이 반복해서 경계해 온 패턴이기도 하다([[2026-07-06-better-models-worse-tools]]: 모델이 좋아지는데 도구·지식은 뒤처진다). 실무 규칙:

> **Cookbook 레시피를 쓸 땐 날짜를 먼저 보고, 그 다음 현재 모델의 마이그레이션 문서와 대조한다.** 12개월 넘은 프롬프트 기법은 기본적으로 의심.

## 호스피탈리티 / CRS 적용 포인트

레퍼런스 문서라 "무엇을 골라 읽을 것인가"가 곧 적용점이다. 온다(B2B 호스피탈리티/CRS) 기준으로 **실제로 값이 나올 항목만** 추리면:

- **Text-to-SQL + 분류 + 요약** — 사업자 문의/예약 데이터에 대한 자연어 조회, 문의 티켓 자동 분류. 단 **읽기 전용 경로에서만**(내 운영 원칙: 조회는 SELECT/SHOW/DESCRIBE, 쓰기는 명시 승인).
- **Evals + 합성 테스트 데이터 생성** — 우리 도메인(요금·정책·객실 유형)에 대한 평가 세트를 만들어 두면 모델 교체 때마다 재검증이 가능해진다. **[[2026-07-25-context-engineering-rules-claude-5]]가 말한 "삭감 전에 rubric"의 실행 도구가 여기 있다.**
- **Usage & Cost Admin API** — 프로그래매틱 비용 분석. [[2026-07-25-claude-opus-5-release]]로 모델을 옮길 때 **실제 비용 델타를 재는 도구**.
- **사람의 승인(human approval) + 프롬프트 버전 관리·롤백** — 내 dry-run 게이트·최종 승인 원칙과 정확히 대응. 프롬프트를 코드처럼 버저닝·롤백하는 건 **아직 우리가 안 하고 있는 것** 중 회수가 빠른 축.
- **Contextual retrieval** — 사업자 매뉴얼·정책 문서 RAG를 한다면 기본 청킹보다 이쪽. 프롬프트 캐싱과 함께 쓰면 비용도 잡힌다.
- **건너뛸 것** — 프론트엔드 미학 프롬프팅(HN 평가가 나쁘고 우리 도메인과 무관), 2024년 프롬프트 트릭 전반(감가상각), LlamaIndex/Pinecone 통합(우리 스택 아님).
