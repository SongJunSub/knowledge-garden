# OpenCode 2.0 — Code Mode와 백그라운드 에이전트, 단일 서비스 구조 도입

> 출처: [sst/opencode (GitHub)](https://github.com/sst/opencode) · GeekNews(id=35371) 경유 · 정리일 2026-10-15

> **출처 한계**: `news.hada.io`는 이 세션에서 egress 전면 차단으로 열지 못했다. `opencode.ai`(공식 문서)도 `getaddrinfo ENOTFOUND`로 접근 불가했다. **1차 소스로 확인한 것은 `github.com/sst/opencode` 저장소뿐**이다 — WebFetch로 직접 확보한 README는 `build`(전체 권한 기본 에이전트)·`plan`(읽기 전용 에이전트)·`@general` 서브에이전트까지만 보여주고 Code Mode·백그라운드 실행·단일 서버 구조는 README 본문에 없었다. 다만 ①기본 브랜치 `dev`의 커밋 수 20,434개·`specs/v2/V2_HTTP_API_AUDIT.md` 같은 2.0 설계 문서 디렉터리가 실재하고, ②최신 안정 릴리스(v1.19.0)가 "`opencode upgrade --major`로 OpenCode 2로 업그레이드하라"고 명시하는 것으로 **2.0이 실제로 존재하고 메이저 업그레이드 경로가 열려 있다는 사실 자체는 1차로 확인**했다. Slack 발췌의 구체 기능(Code Mode, 백그라운드 서브에이전트, 80+ 플러그인, 핫 리로드)은 thenewstack.io·explainx.ai·byteiota.com·diariobitcoin.com·falcao.org(개인 블로그) 등 **복수 2차 매체가 서로 일치하게 보도하는 내용**으로만 교차확인했다. hada 댓글 수·HN/Lobsters 큐레이션 여부는 확인 불가. 베타 롤아웃이 길게 끌리면서 "2.0이 정식으로 안정화된 것인지"를 두고 개발자 커뮤니티에 혼선이 있었다는 보도도 있어, 이 노트가 정리하는 시점에도 기능 세부가 유동적일 수 있다.

## 한 줄 요약

**OpenCode 2.0은 TUI·웹·데스크톱(Electron) 인터페이스가 모두 하나의 로컬 백그라운드 서비스(단일 Hono/SQLite 서버로 보도됨)에 붙는 구조로 개편되면서, MCP 서버·OpenAPI 엔드포인트를 스크립트에서 호출 가능한 함수로 바꿔주는 "Code Mode"와, 주 에이전트가 다른 작업을 계속하는 동안 뒤에서 돌아가는 백그라운드 서브에이전트를 1급 기능으로 들여왔다 — 둘 다 "에이전트가 도구 호출을 위해 매번 왕복하거나, 사용자가 작업이 끝날 때까지 기다려야 한다"는 마찰을 줄이는 방향이다.**

## 핵심 포인트

- **단일 백그라운드 서비스 구조** — 2.0에서는 서버가 개발자 머신에서 ***하나의 백그라운드 프로세스로 자동 실행***되고, 터미널(TUI)·웹 UI·새 Electron 데스크톱 앱이 전부 같은 중앙 프로세스에 연결된다. byteiota는 이를 "터미널·데스크톱·웹을 동시에 뒷받침하는 단일 Hono/SQLite 서버"로 구체화해서 보도한다.
- **Code Mode — MCP·OpenAPI를 호출 가능한 함수로 번역** — ***MCP 서버와 OpenAPI 엔드포인트를 스크립트 안에서 직접 호출할 수 있는 함수로 변환***해, 여러 도구를 조합하는 작업을 한 번의 코드 실행(왕복 1회)으로 처리한다. 한 보도는 "v2.0에서는 기본적으로 모든 MCP 서버가 Code Mode로 활성화된다"고 전한다. 이 패턴 자체는 OpenCode가 처음 만든 게 아니다 — ***Cloudflare가 먼저 공개한 "Code Mode"***가 "OpenAPI 서비스를 검색용 도구 1개 + 실행용 도구 1개로만 노출하고, API 스펙 전체는 모델 컨텍스트 밖에 둔다"는 동일한 설계를 제안했고(WebSearch로 developers.cloudflare.com 문서 확인), OpenCode는 이 패턴을 로컬 코딩 에이전트의 표준 기능으로 가져온 사례로 읽힌다.
- **백그라운드 서브에이전트·넌 명령** — 서브에이전트와 셸 명령을 ***백그라운드에서 실행***할 수 있어, 주 에이전트가 다른 작업을 계속 처리하는 동안 사용자가 프롬프트를 계속 이어갈 수 있다. 위임은 자동 또는 수동으로 가능하고, 서브에이전트에 별도 모델을 지정할 수 있다.
- **80개 이상의 내부 플러그인·재구축된 API·SDK** — 거의 모든 기능을 80개 이상의 내부 플러그인으로 구현했고, API를 다시 짰으며 새로운 임베더블 SDK를 함께 내놓았다. v1 플러그인·서버 API에는 ***破괴적 변경(breaking changes)***이 있다.
- **안정성에 대한 이견** — 롤아웃이 길게 끌리면서 "2.0이 공식적으로 안정화된 것인지"를 둘러싼 개발자들의 혼란이 있었다는 보도(byteiota)와, 2.0 베타가 별도 npm 태그로 설치되며 문서가 이를 명시적으로 "베타"라 표시한다는 보도(falcao.org 개인 블로그)가 있다. 베타 출시일은 한 매체(byteiota)가 9월 22일로 보도했으나, 다른 매체(thenewstack)가 전하는 "정식 공개 요일" 정보는 1차 소스로 대조하지 못했다.

## 내 생각 · 적용점

### 핵심 전이 1 — Code Mode는 "도구 정의가 컨텍스트를 먹는다"는 문제에 대한 세 번째 해법의 재등장이다

[[2026-10-11-vercel-eve-agent-framework]]를 정리할 때 짚었던 구도를 그대로 가져올 수 있다 — "도구 정의가 컨텍스트를 과점한다"는 문제에는 프로토콜을 고치는 길(MCP의 progressive discovery)과 실행 환경을 코드 샌드박스로 바꾸는 길(Codemode) 두 갈래가 있었다. OpenCode의 Code Mode는 바로 그 ***두 번째 길의 독립적 재구현***이다 — Cloudflare가 "OpenAPI를 검색 1개+실행 1개 도구로 압축해 API 스펙을 컨텍스트 밖에 둔다"는 패턴을 먼저 제안했고, OpenCode는 그 패턴을 "로컬 코딩 에이전트가 MCP·OpenAPI를 기본적으로 Code Mode로 다룬다"는 형태로 표준화했다. 서로 다른 조직(Cloudflare, sst)이 같은 문제에 같은 해법으로 수렴한다는 점이 흥미롭다.

### 핵심 전이 2 — 백그라운드 서브에이전트는 [[2026-10-07-software-factory-pattern-linear-loop]]가 말한 "작업이 아니라 프로젝트를 돌리는" 방향의 인프라적 전제조건이다

Will Larson의 소프트웨어 팩토리 패턴 노트는 "에이전트가 개별 티켓이 아니라 프로젝트 전체의 목표·지표를 읽고 스스로 다음 작업을 찾는다"는 실험을 다뤘는데, 그 실험이 실용적으로 돌아가려면 ***에이전트가 사람의 다음 프롬프트를 기다리지 않고 계속 돌아갈 수 있어야 한다***는 전제가 필요하다. OpenCode 2.0의 "백그라운드 서브에이전트+사용자가 다른 프롬프트를 이어갈 수 있다"는 설계는 정확히 그 전제를 하부 인프라 차원에서 제공한다 — 프레임워크(소프트웨어 팩토리 패턴)와 런타임(OpenCode 2.0)이 같은 방향으로 수렴하는 사례다.

## 호스피탈리티 / CRS 적용 포인트

**직접 도입보다는 설계 원칙 차용에 가깝다.** ①Code Mode의 "여러 도구 호출을 스크립트 한 번으로 묶는다"는 원칙은, CRS 내부 자동화가 PMS·채널매니저·결제 게이트웨이 등 여러 외부 API를 순차 호출해야 할 때 왕복 횟수를 줄이는 설계로 참고할 만하다. ②다만 OpenCode 자체는 아직 베타 안정성 논란이 있는 로컬 개발자 도구이므로, CRS 프로덕션 파이프라인에 바로 들여오기보다는 "도구 호출을 스크립트로 묶어 왕복을 줄인다"는 아이디어만 가져와 자체 내부 에이전트 설계에 반영하는 쪽이 현실적이다.
