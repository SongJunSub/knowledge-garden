# Claude Code 팀의 코드 리뷰 방식

> 출처: [Bringing Code Review to Claude Code](https://claude.com/blog/code-review) (Anthropic, 추정) · 정리일 2026-10-17
>
> **출처 한계**: `news.hada.io`가 egress 차단으로 원문을 열지 못했다. WebSearch로 Anthropic의 실제 블로그 글 "Bringing Code Review to Claude Code"를 찾았지만, 거기 나온 수치(실질적 리뷰 코멘트 비율이 PR의 16%→54%로 상승, 평균 리뷰 20분, 별도 컨퍼런스 발언에서 "Claude Tag가 제품팀 PR의 65%를 병합")는 Slack 발췌의 "90% 자체 작성", "6~9월 병합 PR 2배", "되돌리기 40%대 감소"와 **정확히 일치하지 않는다** — 같은 사안을 다른 수치로 보도했거나, Slack 발췌가 다른 소스(컨퍼런스 발표 등)를 가리킬 가능성이 있다. 아래는 **Slack 발췌를 1차 근거**로 삼고, 교차확인된 사실은 각주처럼 덧붙인다.

## 한 줄 요약

**Claude가 자체 코드의 약 90%를 작성하는 Claude Code 팀은 "코드를 다 읽고 승인하는" 리뷰에서 "사람은 위험 판단과 결과 책임에만 집중하는" 리뷰로 전환했고, 그 결과 6~9월 사이 병합 PR 수는 2배 넘게 늘고 되돌리기 비율은 40% 넘게 줄었다고 보고한다.**

## 핵심 포인트

- **목표는 "읽기 자동화", 사람은 "위험 판단"** — 코드 읽기의 대부분을 자동화하고, 사람은 ***위험 판단과 결과 책임***에 집중하도록 리뷰 과정 자체를 재설계했다. 리뷰어가 diff 한 줄 한 줄을 읽는 게 아니라, AI가 먼저 거른 위험 신호에 반응하는 구조로 보인다.
- **"최대 1명 관여"가 목표치** — 대부분의 PR을 작성자를 포함해 ***사람 최대 1명***의 관여로 병합하는 게 목표. 되돌리기·사고를 늘리지 않는다는 전제가 붙는다 — 속도만 올리고 품질을 희생하는 트레이드오프가 아니라고 주장한다.
- **수치: PR 2배, 되돌리기 40%↓** — 6월부터 9월까지 병합 PR 수가 2배 이상 늘었고, 되돌려야 했던 비율은 40% 넘게 감소. (WebSearch로는 이 구간·수치를 독립적으로 재현하지 못했다.)
- **리뷰 = 승인이 아니라 지속적 검증** — 리뷰를 "마지막 승인 단계"가 아니라 ***지속적인 검증 과정***으로 운영. PR 생성 전 자체 검증 → AI 리뷰 → 보안 검사 → CI → 병합 대기열 → 점진적 배포 → 빠른 롤백까지 여러 방어 계층을 겹친다(Slack 발췌는 여기서 끊김).
- **교차확인된 실제 수치(다른 소스 가능성)** — Anthropic 공식 블로그는 "실질적 리뷰 코멘트가 달린 PR 비율이 16%에서 54%로 상승", "평균 리뷰 20분"을 보고하고, 별도 컨퍼런스 발언은 "Claude Tag가 제품팀 PR의 65%를 병합"이라고 말한다. 핵심 전략(사람 리뷰 부담을 줄이고 결과 책임에 집중)은 같은 방향이지만, 정량 지표는 이 노트의 Slack 발췌와 1:1로 맞지 않는다.

## 인상 깊은 문장

> "목표는 대부분의 PR을 작성자를 포함한 사람 최대 1명의 관여로 병합하되, 되돌리기와 사고를 늘리지 않는 것." (Slack 요약 인용)

## 내 생각 · 적용점

핵심 전이는 ***"리뷰의 목적을 코드 이해에서 위험 판단으로 좁힌다"***는 재정의다. [[2026-06-08-agentic-code-review]]가 다룬 "에이전트형 코드 리뷰"가 이미 비슷한 방향(사람이 전부 읽지 않고 AI가 먼저 거른다)을 가리켰는데, 이 글은 그 결과를 "PR 병합 수·되돌리기율"이라는 조직 단위 지표로 보여준다는 점에서 한 단계 더 나간다. [[2026-06-08-alibaba-open-code-review]]가 다룬 또 다른 대형 조직의 AI 리뷰 도입 사례와 겹쳐 보면, "AI가 1차 필터링 → 사람이 위험 신호에만 반응"이라는 패턴이 여러 조직에서 독립적으로 수렴하고 있다는 정황으로 읽힌다. 다만 "리뷰 품질 유지"를 벤더 자신이 보고한다는 점은 항상 할인해서 봐야 한다.

## 호스피탈리티 / CRS 적용 포인트

CRS 코드베이스에 그대로 적용은 멀지 않다 — 온다도 결국 PR 리뷰 부담을 겪는 B2B SaaS 개발팀이다. 다만 ***"사람이 전부 읽는다"가 아니라 "위험 신호에만 사람이 반응한다"***는 재정의를 그대로 가져오려면, 무엇이 "위험 신호"인지(요금·재고·결제 로직 변경, 외부 연동 스키마 변경 등)를 CRS 도메인 기준으로 먼저 정의해야 한다 — 이 전제가 없으면 "리뷰 완화"가 그냥 "리뷰 생략"이 될 위험이 있다.
