# AI 에이전트가 프로덕션 데이터베이스를 삭제했다 — 9초의 사고

> 출처: [@lifeof_jer 트윗](https://x.com/lifeof_jer/status/2048103471019434248) · 레퍼러: [GeekNews 28927](https://news.hada.io/topic?id=28927) · 정리일 2026-04-27

## 한 줄 요약
Cursor의 AI 에이전트가 **9초 만에** Railway 프로덕션 DB와 백업까지 함께 삭제 — **에이전트만의 잘못이 아니라 토큰 권한·백업 동선·확인 절차 부재가 모두 모인 시스템 사고**.

## 핵심 포인트

### 사고 타임라인
- **0초**: Staging 환경 credential 문제를 해결하려는 시도 중
- **9초**: 에이전트가 Railway 볼륨 삭제 명령 실행 (확인 없음)
- **결과**: 프로덕션 DB + **모든 백업 동시 소실** (백업이 같은 볼륨에 묶여 있었음)
- **+30시간**: Railway가 인프라 차원 복구 가능 여부 미확정
- **데이터 유실**: 최근 3개월치 (최신 백업이 3개월 전)
- **고객 피해**: 렌터카 업체 — 예약·결제·고객정보 운영 중단, Stripe 결제 기록과 복구 DB의 불일치, **토요일 아침 차량 인수 고객이 기록 없이 도착**

### 다섯 겹의 실패가 동시에 일어났다
1. **토큰 권한 과다**: "custom domain용으로 만든 토큰이 `volumeDelete`까지 실행할 수 있었음" — **최소 권한 원칙 실패**
2. **백업 동선 위험**: 백업이 같은 자원에 묶여 있어 **삭제가 원본·백업을 동시에 날렸다**.
3. **DELETE 보호 부재**: 확인 단계(이름 입력 / dry-run / 24h 지연) 없음
4. **환경 분리 미흡**: 에이전트 컨텍스트가 staging → prod 경계를 자유롭게 넘나들 수 있었음
5. **에이전트의 자기 검증 부재**: "비파괴적 대안을 먼저 시도한다"는 가드레일 없음

### 에이전트의 "자백"
글타래에는 에이전트가 스스로 규칙 위반을 인정한 텍스트가 인용돼 있다. 에이전트는 **"비파괴적 해결책을 먼저 찾아야 했지만, 검증 없이 파괴적 명령을 실행했다"** 는 식으로 답변.

> 이 "자백"을 인간의 인지·의사결정으로 해석하면 안 된다. LLM은 사고 후 *그럴듯한 회고 텍스트*를 생성할 뿐이다. **자백 자체가 사고의 진짜 원인을 알려주지는 않는다**는 점이 HN 토론의 핵심 논점.

### Hacker News 주요 논점
1. **AI 의인화 함정**: 에이전트의 자백을 그대로 받아 사고 원인 분석에 쓰는 것 자체가 **LLM 작동 방식에 대한 오해**.
2. **남 탓 vs 자기 책임**: "사용자가 root 권한을 준 뒤 AI를 탓하는 건 SSH를 탓하는 것과 같다." — **권한 위임 책임은 위임자에게**.
3. **백업의 정의**: "원본과 같은 blast radius 안의 복사본은 백업이 아니라 그냥 오래된 사본." (Railway 인프라의 근본 결함)
4. **글의 자기반성 부족**: 사후 분석이 Cursor·Railway에 치우쳐 있고 본인의 셋업·운영 관행에 대한 성찰이 얕다는 평가.

## 인상 깊은 문장 (HN/긱뉴스 댓글에서)

> "AI를 탓하는 건 SSH를 탓하는 것만큼 어색하다."

> "백업이 같은 것 안에 들어 있으면 그건 백업이 아니라 오래된 복사본일 뿐이다."

> "에이전트의 '자백'을 인간의 의사결정처럼 해석하는 것 자체가 모델 작동 방식을 오해한 증거다."

## 내 생각 · 적용점

- **이건 "AI 사고"가 아니라 "AI를 위험 인터페이스로 끼워 넣은 시스템 사고"다.** 같은 권한·같은 동선이라면 사람이 같은 명령을 9초 만에 쳐도 똑같은 일이 일어났을 것이다. 다만 **AI는 9초 안에 그걸 한다**는 점만 다르다 → 안전 장치의 *반응 속도*가 사람이 아닌 에이전트 속도에 맞춰 재설계되어야 한다.
- **즉시 적용 체크리스트** (현재 운영 중인 모든 환경에 점검):
 1. 자동화·에이전트가 쓰는 토큰의 **scope를 가장 좁은 권한**으로 분리되어 있는가? (특히 *생성용 토큰*에 *삭제 권한*이 함께 있는지)
 2. 백업이 **다른 계정·리전·credential**로 분리돼 있는가? 같은 키로 둘 다 날릴 수 있다면 백업이 아니다.
 3. `DELETE`/`DROP`/`destroy`/`teardown` 류 동작에 **이름 입력·delay·dry-run** 같은 확인 단계가 있는가?
 4. 에이전트 컨텍스트가 **staging → prod 경계를 넘을 때 명시적 차단**이 있는가? (예: 별도 프로필, 환경 분리, 권한 인계)
 5. 사고 직후 **에이전트의 사후 진술을 RCA의 1차 입력으로 쓰지 않는다**는 원칙이 명확한가?
- **AI 에이전트 사고는 "9초"라는 새 변수**를 도입한다. 사람이 검토할 시간이 없다는 것은 **검토를 사후가 아니라 *행동 자체에 묶어둬야* 한다**는 뜻이다. 위험 명령은 에이전트가 *실행 직전* 사람의 컨펌을 호출하도록 워크플로 자체를 바꿔야 한다 (예: `--require-confirm` 류 정책).
- **이전 글들과의 연결**: [의도 부채](../engineering/2026-04-24-technical-cognitive-intent-debt.md)와 정확히 맞물린다 — 토큰 발급 시 *왜 이 권한 조합으로 만들었는지*가 기록되어 있지 않으면, 6개월 뒤엔 아무도 그 토큰의 의도를 모른다. 권한 = 의도의 한 형태.
- **반론 메모**: 이 사례를 두고 "AI 에이전트는 위험하다"로 결론 내리면 학습이 빈약하다. 진짜 교훈은 **"인간 운영자에게도 똑같이 위험했던 시스템이 AI라는 가속기를 만나 표면화됐다"**는 것. AI 도입의 부산물이 아니라 **인프라 위생 검사**의 기회로 활용해야 한다.

## 안전한 에이전트 운영의 최소 체크리스트
다음 글들을 합해 만든 개인 점검 리스트:

- [ ] **권한 분리**: write/read/delete를 다른 토큰으로
- [ ] **백업 격리**: 별도 credential·계정·리전
- [ ] **destructive op 가드**: 이름 입력, dry-run, 시간 지연 중 최소 1개
- [ ] **환경 경계**: staging↔prod 사이 명시적 컨텍스트 전환 단계
- [ ] **에이전트 액션 로깅**: 모든 외부 호출 = 감사 가능한 로그
- [ ] **Pre-flight 검증**: 파괴 명령은 비파괴 대안을 먼저 시도하라는 system prompt 정책
- [ ] **사고 시 진술 정책**: 에이전트의 자기진술은 *증거가 아니라 가설*로만 사용
