# Jevlike - 문장 대신 선택지별 확률을 반환하는 오픈소스 모델 (vinnylarouge)

> 출처: [jevlike](https://github.com/vinnylarouge/jevlike) (vinnylarouge, GitHub) · GeekNews 경유 [id=33854](https://news.hada.io/topic?id=33854) · 정리일 2026-09-18
>

WebSearch로 실재하는 GitHub 저장소 `vinnylarouge/jevlike`를 찾아 README를 직접 WebFetch로 읽어 이 노트의 핵심 포인트를 작성했다. 다만 WebSearch 과정에서 같은 개념을 다른 메커니즘(prefill 1회+KV캐시 배치)으로 재구현한 `daseinlabs/open-jev`도 발견했는데, 이 저장소는 README에서 스스로 "jevlike에서 영감을 받은 독립적 재구현"이라 밝히고 있어 — 두 저장소가 서로 다른 프로젝트임을 확인했다. 이 노트의 핵심 포인트·인용문은 전부 `vinnylarouge/jevlike` 자체 README에서 나온 것이고, open-jev의 벤치마크 수치는 참고용으로만 별도 표시했다.

## 한 줄 요약

**TypeSafe AI의 상용 모델 Jev(문장 대신 선택지별 확률을 반환하는 "System One" 모델, 설계 비공개)와 같은 입출력 형태를 갖도록 독립적으로 재구현한 오픈소스 프로젝트 — 맥락과 매번 달라질 수 있는 선택지 목록을 받아, 답을 토큰 단위로 생성하지 않고 한 번의 처리로 각 선택지의 확률을 계산한다.**

## 핵심 포인트

- **동작 원리** — ***각 옵션이 쿼리 벡터가 되어 문맥 토큰에 주의(attention) 가중치를 할당***하고, 그 가중치로 문맥 벡터를 만든 뒤 공유 내적(dot product)으로 점수를 계산, 소프트맥스로 확률로 변환한다. 문장을 한 단어씩 생성하는 대신 선택지 전체를 동시에 평가하는 구조.
- **두 가지 학습 방식** — ① ***처음부터 바이트 임베딩 인코더를 학습***(기본값, 저렴함) ② ***Hugging Face 사전학습 인코더(예: Qwen)를 동결하고 점수 계산 헤드만 학습***(더 정확함). 처음부터 소형 모델을 훈련하거나 기존 프런티어 모델에 작은 판단 레이어만 얹는 두 경로를 다 열어둔 셈이다.
- **사용 사례 세 가지** — 고객 문의를 환불/영업/기술지원으로 분류하는 것 같은 텍스트 판단, ***Wikipedia에서 목표 페이지로 가기 위한 다음 링크 선택***(Wikispeedia 데이터셋 기반), Doom 게임의 컨트롤러 버튼 선택(체스 수 선택도 예시로 언급).
- **이미지 입력도 지원** — ***"옵션-주의 헤드는 이미지 패치에서 컨트롤러 버튼을 점수 매길 수 있다"*** — Doom 데모에서 화면 이미지를 보고 어떤 버튼을 누를지 확률로 직접 점수화하는 시각적 판단에도 같은 구조를 쓴다.
- **(참고, 별도 저장소) open-jev의 체감 성능** — 같은 개념의 다른 구현체 daseinlabs/open-jev는 prefill 1회 + KV 캐시를 옵션 배치 전체로 확장하는 방식을 써서, M5 Pro·202토큰 맥락·8개 옵션 기준 캐시된 배치 처리 0.17초 대 매번 재인코딩 0.68초로 ***약 4배*** 빠르다고 보고한다. jevlike 자체 벤치마크는 아니지만, "선택지를 토큰 생성 없이 한 번에 평가한다"는 접근이 실제로 지연시간을 줄이는 방향이라는 방증으로만 참고.

## 내 생각 · 적용점

### 핵심 전이 1 — 벤더 벤치마크를 외부에서 검증할 길을 여는 재구현

[[2026-09-16-typesafe-ai-jev-typed-judgments]]는 TypeSafe의 상용 Jev를 다루며 ***"벤더 자체 벤치마크라 실제 정확도·보정 품질은 외부 검증 전까지 유보적으로 봐야 한다"***는 한계를 명시적으로 지적했다. jevlike은 같은 입출력 형태(맥락+타입 지정 질문 → 확률+신뢰도)를 독립적으로 재구현해, 외부에서 직접 실험하고 검증할 길을 연다 — 다만 jevlike 자체도 정확도 수치를 공개하지 않아, "검증 가능성이 열렸다"와 "실제로 검증됐다"는 여전히 다른 단계라는 점은 짚어야 한다.

### 핵심 전이 2 — "작은 특화 모델이 프런티어를 이긴다"는 패턴의 다른 축

[[2026-08-02-500-dollar-finetune-beats-frontier-models]]는 카탈로그 검수라는 반복 판단을 9B 모델에 GRPO로 새겨 프런티어 모델 구성보다 13.5% 높은 점수를 340배 저렴하게 냈다. jevlike은 같은 축("변하지 않는 판단 기준만 작은 모델에 새기고 나머지는 범용 모델에 맡긴다")을 한 단계 더 밀어붙인다 — "판단"조차 문장으로 생성하지 말고 애초에 확률 벡터로 직접 뽑아내자는 제안이다. 두 사례 모두 반복되는 좁은 판단 작업에 범용 LLM을 쓰는 건 원래도 과잉스펙이었다는 같은 결론에, 서로 다른 경로(파인튜닝 vs 아키텍처 자체를 다르게)로 도달한다.

## 호스피탈리티 / CRS 적용 포인트

[[2026-09-16-typesafe-ai-jev-typed-judgments]]에서 이미 짚었듯 예약 요청 분류(정상/이상 패턴), 리뷰 감성 점수화, 채널 메시지 라우팅(고객문의 vs 스팸) 같은 CRS의 반복 판단 작업이 이 모델 클래스의 정확한 표적이다. 이번엔 ***오픈소스라 벤더 API 의존 없이 자체 호스팅·파인튜닝이 가능***하다는 실질적 진전이 붙는다 — 지연시간이 중요한 판단(예: 오버부킹 위험 신호 감지, 실시간 채널 메시지 분류)을 내부망 안에서 직접 실험해볼 후보다. 다만 정확도·보정 품질이 검증되지 않은 초기 오픈소스 프로젝트이므로, 지금 당장 프로덕션에 넣기보다는 아키텍처 아이디어 검증용 프로토타입 단계로 접근해야 한다.
