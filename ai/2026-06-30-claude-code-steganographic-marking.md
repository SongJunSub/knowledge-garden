# Claude Code의 스테가노그래피 마킹 논란 (thereallo.dev) — '날짜 문자열의 유니코드 아포스트로피가 리셀러·증류 탐지 신호를 인코딩한다'

> 출처: [Claude Code is Steganographically Marking Your Requests](https://thereallo.dev) (thereallo.dev) · 정리일 2026-06-30

## 한 줄 요약

**Claude Code 바이너리에서 시스템 프롬프트의 날짜 문자열("Today's date is 2026-06-30.")에 숨겨진 함수가 발견됐다. `ANTHROPIC_BASE_URL`이 공식 API가 아니고 특정 조건(중국 시간대·특정 도메인·AI 연구소 키워드)에 해당할 때, 아포스트로피를 서로 다른 유니코드 문자로 치환해 분류 신호를 인코딩한다. Anthropic은 모델 증류 공격·무단 재판매 탐지 목적이라 설명하나, 은밀한 방식 자체가 투명성 논란을 낳고 있다.**

## 핵심 포인트

- **발견된 메커니즘** — 기본 날짜 문자열 `"Today's date is 2026-06-30."`의 아포스트로피(`'`)를 다양한 유니코드 문자로 치환하고, 날짜 구분자를 `-`→`/`로 바꾸는 숨겨진 함수 확인.
- **활성화 조건** — 트리거는 `ANTHROPIC_BASE_URL` 환경 변수(공식 `api.anthropic.com`이 아닐 때만 작동). 추가 조건: 시스템 시간대가 `Asia/Shanghai`·`Asia/Urumqi`, API 호스트명이 특정 목록과 일치, 호스트명에 `deepseek`·`zhipu`·`moonshot` 등 키워드 포함.
- **인코딩 체계** — 아포스트로피 변형으로 분류 신호 표현: `'`(일반) / `’`(알려진 도메인) / `ʼ`(연구소 키워드) / `ʹ`(도메인+키워드 둘 다).
- **감지 대상 목록** — XOR(키 91)+Base64로 난독화된 도메인 목록에 중국 기업(baidu.com·bytedance.net·alibaba-inc.com 등)과 프록시/리셀러 서비스(proxyai.com·openclaude.me 등) 포함.
- **영향 범위** — 대부분 일반 사용자는 무관 (공식 API 사용 시 정상 날짜 형식 유지). 영향받는 경우: 내부 API 게이트웨이·로컬 프록시·모델 라우터 사용자.

## 인상 깊은 문장

> "은밀한 프롬프트 수정은 신뢰를 훼손한다 — 명시적 정책 공개가 더 투명하다."

## 댓글 — HN 다양한 관점 (GN⁺ 큐레이션)

- **투명성 비판**: 서비스 제공자가 도구 동작을 명시적으로 공개하지 않은 것이 "심각한 신뢰 문제"라는 지적. 정직한 공개와 사업상 보안 필요 사이의 긴장.
- **증류 방지 정당화**: 중국 AI 연구소의 모델 증류 시도 탐지 목적이라면 정당한 방어 메커니즘이라는 옹호. "초지능 경쟁에서 중국 모델 증류 위협 대응"이라는 관점.
- **구현 허술함 비판**: 스테가노그래피 구현 자체가 기술적으로 허술해서, 정상적인 내부 게이트웨이 사용자도 오탐(false positive) 피해를 입을 수 있다는 우려.
- **개인정보·신뢰 우려**: 클라이언트 소프트웨어가 사용자 모르게 요청을 마킹하는 것에 대한 근본적 불신.
- **오픈소스 대안 언급**: Codex CLI 같은 투명성이 더 높은 대안 도구 언급.

## 내 생각 · 적용점

### 핵심 전이 1 — "쓰기 방어"의 실전 사례이자 그 그림자

[[2026-06-29-decisions-and-dollars-ai-proof]]에서 다룬 "판단을 축적하고 쓰기를 방어하라"는 AI 시대 방어 전략이, Anthropic 입장에서는 정확히 이 형태로 실현된 것이다. **모델 자체(판단의 결정체)가 복제·재판매되는 것을 막는 것이 회사의 핵심 방어선이라면, 이런 탐지 메커니즘은 논리적으로 자연스럽다.** 다만 이 사례가 보여주는 것은 — **방어 전략이 투명하지 않을 때 사용자 신뢰가 어떻게 훼손되는가**라는 반례이기도 하다.

### 핵심 전이 2 — CRS·PickMe API 설계에서 "숨겨진 동작"의 위험성

이 논란의 핵심은 기능 자체가 아니라 **"명시되지 않은 숨겨진 동작"**이다. CRS·PickMe API에서도 특정 조건(IP·도메인·헤더)에 따라 응답이 미묘하게 달라지는 로직을 넣는다면, 나중에 디버깅하는 개발자(팀원이든 파트너든)가 원인을 찾지 못해 큰 시간을 낭비할 수 있다. **API 문서에 명시되지 않은 조건부 동작은 설령 선의라도 "숨겨진 버그"와 동일한 유지보수 리스크를 만든다.** [[2026-06-29-towards-understandable-software]]의 "이해 가능한 소프트웨어" 원칙과 정반대 방향.

### 핵심 전이 3 — 보안 조치의 "발견 가능성"이 신뢰의 핵심 변수

이 스테가노그래피는 리버스 엔지니어링으로 발견됐다. **숨긴 보안 조치는 결국 발견되며, 발견됐을 때의 반응(투명 공개 vs 침묵)이 신뢰를 좌우한다.** [[2026-06-29-reddit-antispam-internals]]에서 다룬 Reddit의 5년 후 공개 결정과 대조된다 — Reddit은 위험이 낮아진 후 스스로 공개했지만, 이 사례는 외부 리버스 엔지니어링으로 강제 공개됐다. **보안 조치를 설계할 때 "언젠가 발견될 것"을 전제로 설계하는 것이 장기적으로 신뢰를 지키는 방법.**
