# Flava MCP Hub가 걸어온 길: AI 시대를 위한 배관 공사 (LY Corporation)

> 출처: [Flava MCP Hub가 걸어온 길: AI 시대를 위한 배관 공사](https://techblog.lycorp.co.jp/ko/flava-mcp-hub-ai-infrastructure) (LY Corporation 기술 블로그) · Slack `#개발-뉴스-dev-news`(TechArticles 봇) 경유 · 정리일 2026-10-26

"4층 배관 모델"이라는 아키텍처 명칭은 확인했으나 4개 층이 각각 무엇을 하는지 세부는 확인하지 못했다.

## 한 줄 요약

**LINE Yahoo(LY Corporation)는 사내 여러 팀이 각자 인증·보안·연결 방식을 따로 구현하며 MCP 서버를 흩뿌려 놓았던 문제를, 카탈로그(발견)·런타임(생성·배포)·게이트웨이(권한·인증)로 역할을 나눈 플랫폼 "Flava MCP Hub"로 묶어, 현재 650개 이상의 서버와 200개 이상 팀, 누적 1,150만 건 이상의 도구 호출을 지탱하는 사내 AI 활용의 표준 기반이 됐다.**

## 핵심 포인트

- **흩어진 MCP 서버의 인증 중복 문제** — AI 에이전트 도입이 빨라지면서 사내 곳곳에 MCP 서버가 생겼지만, 팀마다 인증·보안·연결 방식을 ***제각각 구현***했다는 것이 출발점이다. 표준 프로토콜(MCP)만으로는 이 거버넌스 문제가 해결되지 않는다는 점을 짚는다.
- **카탈로그 · 런타임 · 게이트웨이 3계층** — 카탈로그는 사내에서 쓸 수 있는 MCP 서버를 한곳에서 찾게 하고, 런타임은 MCP 서버의 생성·배포·사용 과정을 단순화하고, 게이트웨이는 권한·접근 제어·인증 흐름을 처리하는 관문 역할을 한다. 즉 "발견 → 운영 → 보안"을 세 레이어로 명확히 분리했다.
- **"4층 배관 모델"** — 이 셋을 다시 요청 경로상의 4개 층으로 나눠 책임을 분리하는 아키텍처를 "배관(piping)"이라는 비유로 설명한다. 제목의 "배관 공사"가 바로 이 모델을 가리키는 것으로 보인다. (4개 층 각각의 구체 역할은 교차확인 못함.)
- **규모 — 650개+ 서버, 200개+ 팀, 1,150만+ 호출** — 플랫폼이 사내 표준으로 자리 잡았다는 근거로 제시되는 수치다. Slack 발췌의 "650개 이상의 서버를 운영하며 빠르게 자리 잡고 있다"는 서술과 일치한다.
- **속도 — 1분 연결, 5분 배포** — 카탈로그에서 서버를 골라 1분 안에 연결하고, 인증까지 갖춘 새 MCP 서버를 5분 안에 배포할 수 있다는 주장이다. 이게 바로 "팀별 중복 개발 비용 절감"의 구체적 수치화로 보인다.

## 인상 깊은 문장

> "사내 카탈로그에서 MCP 서버를 선택하면 1분 안에 연결할 수 있고, 새 MCP 서버도 인증을 갖춘 상태로 5분 안에 배포할 수 있습니다." (발표 슬라이드 검색 스니펫 재구성, LY Corporation Flava MCP Hub 팀)

이 수치가 인상적인 이유는, MCP의 약속(표준 프로토콜로 연동 비용을 줄인다)이 실제로는 **인증·권한 관리**라는 비표준 영역에서 비용이 재발생한다는 걸 역으로 증명하기 때문이다 — "1분 연결·5분 배포"는 표준 프로토콜이 아니라 그 위에 얹은 플랫폼 계층(카탈로그+게이트웨이)이 만든 속도다.

## 내 생각 · 적용점

**핵심 전이 1 — [[2026-10-12-uber-mcp-gateway-platform-design]]과의 연결.** Uber의 MCP Gateway가 Registry(컨트롤 플레인)+Proxy Gateway(데이터 플레인)+AutoCrawler(기존 API에서 도구 자동 발견)로 800개+ 서버·5,000개+ 도구를 운영하는 것과, Flava MCP Hub가 카탈로그+런타임+게이트웨이로 650개+ 서버·200개+ 팀을 운영하는 것은 **거의 같은 문제를 거의 같은 3분할 구조로 풀었다는 점에서 수렴**한다. 두 빅테크가 독립적으로 "표준 프로토콜만으론 거버넌스가 안 된다"는 같은 결론에 도달했다는 게 이 수렴의 의미다 — MCP를 많이 쓰는 조직이면 결국 등록·발견(카탈로그/레지스트리)과 인증·접근제어(게이트웨이)를 분리한 플랫폼 레이어가 필요해진다는 패턴으로 읽을 수 있다.

**핵심 전이 2 — [[2026-10-23-nvidia-openshell-ai-agent-sandbox-runtime]]과의 대조.** OpenShell은 "에이전트 프로세스 바깥에서 커널 수준으로" 파일·네트워크 접근을 중재하는 실행 격리에 집중한 반면, Flava MCP Hub는 "에이전트가 어떤 도구에 접근할 수 있는가"를 관문(게이트웨이)에서 통제하는 데 집중한다. 같은 "에이전트 접근 제어" 문제를 **런타임 격리**(OpenShell) vs **플랫폼 거버넌스**(Flava)라는 서로 다른 레이어에서 접근한다는 점에서, 실제 운영에서는 둘이 보완적으로 쓰일 가능성이 크다.

## 호스피탈리티 / CRS 적용 포인트

**부분~직접 적용 가능성이 있다.** 온다가 여러 팀에서 PMS·OTA·채널매니저 연동용 MCP 서버를 늘려가게 되면, 이 글이 지적한 "팀마다 인증·보안을 따로 구현하는" 문제를 그대로 겪을 가능성이 높다. Flava MCP Hub(카탈로그+런타임+게이트웨이)와 Uber MCP Gateway(Registry+Proxy+AutoCrawler)가 독립적으로 같은 3분할 구조에 도달했다는 사실 자체가, 이 구조를 **참조 아키텍처로 가져올 근거**가 된다 — 새 파트너 API 연동마다 인증 로직을 재구현하지 않도록, 처음부터 "발견(카탈로그)·생성(런타임)·접근제어(게이트웨이)"를 분리해 설계하는 것을 검토할 만하다.
