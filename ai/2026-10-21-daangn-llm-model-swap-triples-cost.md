# 모델만 바꿨는데 LLM 비용이 3배가 된 이유 (당근마켓)

> 출처: [모델만 바꿨는데 LLM 비용이 3배가 된 이유](https://medium.com/daangn/%EB%AA%A8%EB%8D%B8%EB%A7%8C-%EB%B0%94%EA%BF%A8%EB%8A%94%EB%8D%B0-llm-%EB%B9%84%EC%9A%A9%EC%9D%B4-3%EB%B0%B0%EA%B0%80-%EB%90%9C-%EC%9D%B4%EC%9C%A0-5ae60ab5108b) (당근 테크 블로그, Medium) · Slack #개발-뉴스-dev-news 채널(TechArticles 봇) 경유 · 정리일 2026-10-21
>
> **출처 한계(큼)**: `medium.com`은 이번 세션에서 egress 차단(`getaddrinfo ENOTFOUND`)으로 원문을 전혀 열지 못했다. WebSearch로도 이 정확한 글은 찾지 못했다 — 교체 전후 모델명, 실제 비용 수치(몇 배 증가라는 "3배"가 어느 기간·어느 워크로드 기준인지), 캐시 히트율이 구체적으로 몇 %에서 몇 %로 떨어졌는지는 전혀 확인하지 못했다. 이 노트는 Slack 발췌 3문장(마지막 문장 끊김)을 1차 근거로 삼는다.

## 한 줄 요약

**당근마켓이 쓰던 LLM 모델을 다른 모델로 바꾼 뒤 프롬프트 캐시 히트율이 급락하면서 요청당 비용이 3배 이상 뛰었고, 이 캐시 히트율 저하는 에러를 일으키지 않아 겉으로 드러나지 않기 때문에 지속적인 모니터링이 있어야만 알아챌 수 있었다는 사례.**

## 핵심 포인트

- **모델 교체가 캐시를 깨뜨린다** — ***"LLM 모델 교체 후 프롬프트 캐시 히트율이 급락하며 요청당 비용이 3배 이상 증가하는 현상이 발생함"***. 모델을 바꾸면 성능·품질 지표만 비교하기 쉽지만, 이 사례는 "같은 입력이 캐시에 걸리는가"라는 완전히 다른 축이 함께 깨질 수 있다는 걸 보여준다 — 새 모델의 토크나이저·캐시 키 구조·컨텍스트 윈도우 처리 방식이 이전 모델과 다르면 동일한 프롬프트라도 캐시가 재사용되지 않을 수 있다.
- **프롬프트 캐시가 왜 중요한가** — ***"프롬프트 캐시는 반복되는 입력의 연산 과정을 재사용해 비용과 시간을 절감하는 핵심 기술"***이다. 시스템 프롬프트나 긴 컨텍스트처럼 매 요청마다 반복되는 부분을 캐시가 재사용하지 못하면, 매번 전체를 다시 연산하는 비용을 그대로 지불하게 된다 — "3배"라는 수치는 캐시가 식었을 때의 비용 증폭이 작지 않다는 뜻이다.
- **조용히 무너지는 지표라는 게 핵심 위험** — ***"캐시 히트율 저하는 에러를 발생시키지 않아 인지가 어렵기에 지속적인 모니터링이 필수"***다. API 호출은 정상적으로 성공 응답을 반환하고 기능도 똑같이 동작하기 때문에, 비용 대시보드를 따로 들여다보지 않으면 "비용이 3배가 됐다"는 사실 자체를 놓칠 수 있다는 경고다.
- **(확인 불가)** 어떤 모델에서 어떤 모델로 바꿨는지, 어느 시점에 문제를 발견했는지, 해결책(캐시 키 재설계·구 모델 롤백·프롬프트 구조 변경 등)으로 무엇을 택했는지는 Slack 발췌가 끊겨 확인하지 못했다.

## 내 생각 · 적용점

**핵심 전이 — "가시성 없이는 비용 문제를 모른다"는 이 가든의 반복되는 LLM 비용 교훈에, 이번 글은 구체적인 침묵하는 실패 양상(캐시 히트율) 하나를 추가한다.** [[2026-10-20-llm-proxy-observability-without-running-your-own]]은 "벤더의 사용량 화면만으로는 어떤 호출이 무엇을 했는지 알 수 없다"고 주장했고, [[2026-10-20-aws-ai-agent-token-economics-bedrock]]은 "토큰량 자체가 비용의 좋은 대리 지표가 아니다"라는 역설적 사례를 들었다. 이번 당근 사례는 두 글의 주장을 한 단계 더 구체화한다 — ***"에러 없이 성공 응답을 반환하는 호출도, 캐시가 꺼진 순간부터는 숨은 비용을 쌓고 있을 수 있다"***는 것이다. 세 글을 이으면 "토큰량도, 성공 여부도 비용의 신호가 아니고, 결국 캐시 히트율 같은 내부 지표를 직접 계측해야 한다"는 결론이 더 또렷해진다. [[2026-09-15-samsung-llm-gateway-subscription-to-server]]가 보여준 "자체 게이트웨이로 호출을 직접 관측한다"는 선례도 같은 결의 해법으로 연결된다.

## 호스피탈리티 / CRS 적용 포인트

**직접 적용 가능성 있음.** 온다가 CRS 상품에 LLM 기능(요금 문의 응대, 리뷰 요약 등)을 넣고 모델을 교체·업그레이드할 때, ***"응답 품질이 떨어지지 않았는가"뿐 아니라 "캐시 히트율이 교체 전후로 유지되는가"를 비용 회귀 테스트 항목에 명시적으로 포함***해야 한다는 게 이 글의 직접적인 교훈이다. 특히 시스템 프롬프트에 호텔별 요금 규칙이나 정책 같은 긴 고정 컨텍스트를 반복 주입하는 구조라면, 모델 교체 시 그 고정 컨텍스트가 여전히 캐시에 걸리는지를 가장 먼저 확인해야 한다 — 기능은 정상 동작하는데 비용만 조용히 3배가 되는 상황을 그대로 재현할 수 있는 구조이기 때문이다.
