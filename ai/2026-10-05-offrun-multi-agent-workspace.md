# Offrun - 모든 코딩 에이전트를 하나의 작업 공간에서 관리

> 출처: [Offrun](https://offrun.dev/) (Mac 앱 공식 사이트) · GeekNews(id=34783) 경유 · 정리일 2026-10-05

> **출처 한계**: `news.hada.io`와 `offrun.dev` 둘 다 이 세션에서 egress 차단으로 직접 열지 못했다(HN Algolia API, web.archive.org 등 대체 경로도 전부 같은 정책으로 차단됐다). Slack 발췌는 말줄임표로 끊겨 전체 기능 목록을 주지 못했고, 아래 내용은 WebSearch가 반환한 공식 사이트 메타 요약과 Show HN 재인용 스니펫을 교차 확인해 재구성한 것이다. **Show HN 게시물이 74점·61댓글을 받았다는 수치는 2차 매체(Daily Hacker News 다이제스트)가 집계한 것으로, HN 원문 스레드를 직접 열어 대조하지는 못했다.** 가격("완전 무료, 신용카드 불필요")과 요구사항(Apple Silicon, macOS 14+)은 복수 소스가 일치해 신뢰도가 있지만, 실제 사용자 리뷰나 구체적 버그·불만 사항은 확인하지 못했다.

## 한 줄 요약

**Offrun은 기존 구독·계정을 그대로 쓰면서 Claude Code·Codex·Antigravity(AGY)·Grok Build를 Mac 한 작업 공간에서 병렬로 돌리는 무료 앱이다 — 에이전트마다 별도 git worktree를 줘서 같은 저장소의 리팩터링과 버그 수정을 동시에 진행하고, ***다른 에이전트가 커밋 전 diff를 먼저 읽어 검토***하게 할 수 있으며, 계정 사용량이 바닥나면 다른 로그인이나 다른 에이전트로 대화를 그대로 이어받게 해준다.**

## 핵심 포인트

- **worktree 격리 — 같은 저장소, 서로 다른 작업 공간** — 프로젝트의 에이전트마다 독립된 git worktree를 만들어, 두 에이전트가 같은 레포에서 작업해도 서로의 파일을 건드리지 않는다. 리팩터링 하나와 버그 수정 하나를 동시에 돌리고 각자의 일정에 맞춰 머지할 수 있다.
- **두 번째 에이전트의 사전 리뷰 — 커밋 전에, 미커밋 상태에서** — 다른 에이전트에게 변경 사항을 커밋 전에 검토하도록 맡길 수 있고, 발견한 문제를 수정하도록 요청할 수 있다. 중요한 건 ***아무것도 자동으로 머지되지 않는다는 점*** — 리뷰 결과는 채팅에 남고 최종 결정은 사람이 한다.
- **계정·사용량 한도 관리 — 로그인 단위로 라우팅** — 각 에이전트를 다른 로그인에 붙여놓고, 한도에 도달하면 Offrun이 대화를 여유 있는 로그인으로 옮긴다. 메시지를 다시 보내면 새 로그인이 전체 대화 맥락을 이어받고, 로그인이 다 떨어지면 다른 에이전트로 전환하는 선택지도 제공한다.
- **"내 머신에서, 내 계정으로" — 별도 구독·API 키 없음** — Offrun은 사용자의 Mac에서 CLI들을 그대로 실행하며, 새 계정이나 API 키를 요구하지 않고 비밀번호를 보지 않는다고 설명한다. 가격은 완전 무료(에이전트 수·프로젝트 수 무제한, 계정 연결 무제한)이며, GitHub·Slack 연동도 무료로 제공한다.
- **요구사항과 커뮤니티 반응** — Apple Silicon(M1 이상) + macOS 14 Sonoma 이상이 필요해 인텔 Mac은 배제된다. Show HN 게시물이 74점·61댓글(2차 집계)을 받아 적지 않은 화제성이 있었던 것으로 보이나, "100% 무료인 건 좋지만 DIY 조합(worktree + tmux + 직접 스크립팅)을 이기려면 커뮤니티 베스트 프랙티스 수준으로 압도적으로 좋아야 한다"는 회의적 반응도 있었다고 WebSearch 요약이 전한다.

## 댓글

**hada 댓글 수는 egress 차단으로 확인 불가.** HN Show HN 게시물의 74점·61댓글은 2차 다이제스트 집계일 뿐 원문 스레드의 구체적 논쟁 내용(회의적 댓글의 정확한 워딩, 버그 리포트 등)은 확인하지 못했다. Offrun이 **독립 개발자의 사이드 프로젝트인지 팀이 있는 스타트업인지도 이 세션에서는 특정하지 못했다** — 완전 무료 모델이 지속 가능한 비즈니스인지에 대한 판단 근거는 없다.

## 내 생각 · 적용점

### 핵심 전이 1 — Worktrunk가 CLI로 풀던 문제를, Offrun은 GUI와 "다른 벤더 간 조합"으로 더 넓게 푼다

[[2026-09-21-worktrunk-git-worktree-cli]]는 "에이전트마다 별도 git worktree가 필요하다"는 똑같은 문제를, 브랜치 이름 하나로 worktree 생성·이동·에이전트 실행을 묶는 Rust CLI로 풀었다. Offrun은 같은 문제를 ***Mac GUI 앱***으로 풀면서, 한 벤더의 CLI 하나가 아니라 ***Claude Code·Codex·Antigravity·Grok Build 네 개를 동시에*** 다룬다는 점에서 한 단계 더 나간다. CLI 성향 개발자에게는 Worktrunk가, 여러 벤더 계정을 동시에 굴리며 시각적으로 관리하고 싶은 쪽에게는 Offrun이 맞는 도구로 분화되는 모양새다.

### 핵심 전이 2 — Ordewell의 "의존성 그래프 기반 병렬 실행"과는 다른 축의 병렬화

[[2026-09-26-ordewell-multi-agent-orchestrator]]는 목표 하나를 의존성 그래프가 있는 작업 계획으로 쪼개 ***자동으로*** 병렬 분배하는 쪽이었다. Offrun은 그 반대축에 가깝다 — 작업 분배는 사람이 직접 하고(어느 에이전트에 뭘 맡길지), 도구는 "계정 관리 + worktree 격리 + 상호 리뷰"라는 운영 인프라만 깔아준다. 두 노트를 겹쳐 보면 "멀티 에이전트 병렬화"라는 같은 유행어 아래 "자동 오케스트레이션"과 "사람이 지휘하는 병렬 운영"이라는 서로 다른 설계 철학이 공존하고 있다는 게 드러난다.

**이 글은 "Claude를 더 잘 쓰는 데" 직접 도움이 되는 글이다.** Claude Code를 포함한 여러 에이전트 CLI를 동시에 쓰는 워크플로를 바로 조립해볼 수 있는 도구 소개이기 때문이다.

## 호스피탈리티 / CRS 적용 포인트

**직접 적용은 멀다 — 이건 개발자 로컬 작업 환경 도구고, CRS 제품 자체와는 층위가 다르다.** 다만 전이 가능한 원칙 하나는 있다 — ***"다른 에이전트가 변경을 머지 전에 검토하되, 최종 결정권은 사람에게 남긴다"***는 Offrun의 설계 원칙은, 온다 CRS에서 AI가 제안한 가격·재고 변경을 적용하기 전에 별도의 검증 로직(규칙 기반이든 또 다른 모델이든)이 한 번 더 훑고, 최종 승인은 운영자가 하는 이중 검증 구조로 옮겨볼 수 있다. "자동 머지 없음"이라는 Offrun의 명시적 약속은, 되돌리기 비용이 큰 B2B 운영 환경에서 왜 사람이 마지막 승인 단계를 쥐고 있어야 하는지에 대한 좋은 레퍼런스 문구이기도 하다.
