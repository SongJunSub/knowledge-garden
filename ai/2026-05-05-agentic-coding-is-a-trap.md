# Agentic Coding은 함정이다 — 비판적 관점

> 출처: [Lars Faye — Agentic Coding is a Trap](https://larsfaye.com/articles/agentic-coding-is-a-trap) · 레퍼러: [GeekNews 29155](https://news.hada.io/topic?id=29155) · 정리일 2026-05-05

## 🔖 한 줄 요약
**감독의 역설**: Claude를 *효과적으로* 쓰려면 감독해야 하는데, *Claude를 감독하는 능력*이 바로 *Claude 사용으로 위축되는 능력*이다 — 디버깅 능력 47% 감소가 수개월 단위로 진행된다.

## 🧩 비판적 주장 6가지

### 1. 감독의 역설 (Paradox of Supervision)
Anthropic 연구의 자기 모순:
> "Claude를 효과적으로 사용하려면 감독이 필요하고, Claude를 감독하려면 AI 과다 사용으로 위축될 수 있는 바로 그 코딩 기술이 필요하다."

이 역설은 *시간이 지날수록 깊어진다* — AI를 더 쓸수록 감독 능력이 줄고, 감독 능력이 줄수록 AI 출력 품질도 평가 불가.

### 2. 기술 위축 — 구체적 수치
- **디버깅 능력 47% 감소** (구체 숫자)
- 30년 경력 Simon Willison도: *"응용 프로그램의 명확한 정신 모델 부재"* 인정
- 수개월 내에 빠르게 진행되는 쇠퇴
- 주니어가 가장 위험: *직접 코딩 경험 부재 → 가파른 학습 곡선*

### 3. 벤더 종속성
- Claude 중단 사태로 일부 팀 *전면 마비*
- **토큰 비용 불확실성**: 월·연 단위 예측 불가
- 새 모델 출시마다 *토큰 사용량 2~3배* 증가 (성능 향상이 비용 증가를 가린다)

### 4. 잘못된 우선순위
- *깊은 이해와 간결성*이 아니라 *"일정 시간 안에 생성되는 코드량"* 을 최적화하는 방향으로 변질

### 5. 명확성 부족 = 토큰 낭비
> "LLM은 모호함을 가정으로 채우므로 더 많은 검토, 더 많은 수정, 더 많은 토큰 소모가 발생한다."

**핵심 철학적 반대**: *확률적 시스템(LLM)*으로 *결정론적 시스템(컴파일러)*을 대체하는 발상 자체에 대한 의문.

### 6. 책임 있는 위임 (대안)
| 방식 | 내용 |
|------|------|
| **LLM 역할 역전** | 계획·문서·연구는 AI / 구현은 자신 (20~100% 수동 코딩) |
| **의사코드 활용** | 모델과의 거리 축소 |
| **선택적 위임** | 임시 코드, 문서, 연구용으로만 |
| **리뷰 가능성 원칙** | 한 세션에서 검토 가능한 양만 생성 |
| **역량 범위 준수** | 직접 못 하는 작업은 거부 (교육 목적 제외) |

### 어떤 부분에 동의하는가
- **47% 디버깅 감소 같은 수치는 일단 받아들일 가치**: 정확한 출처는 추가 검증 필요하지만, 방향성은 *나도 체감*. AI에게 디버깅을 자주 맡기면 직접 트레이스를 *읽는 근육*이 약해진다.
- **감독의 역설은 진짜다**: Claude 출력의 *미묘한 오류*는 *그 영역에 익숙한 사람만* 잡는다. AI를 자주 쓰면 *그 영역에 안 익숙해진다* — 이중 함정.
- **벤더 종속 + 토큰 비용 불확실성**은 회사 차원의 진짜 위험: Claude Code 장애로 [9초 사고](2026-04-27-ai-agent-deleted-production-database.md) 같은 일이 일어나는 게 아니라, *팀 전체가 멈춘다*. 우리 팀의 *AI 의존도*가 지난 6개월간 얼마나 올랐는지 *측정해본 적이 없다*는 것 자체가 신호.

### 어떤 부분은 과하다고 보는가
- **"올인하면 구식화 보장"** (Jeremy Howard) 은 *시간 지평이 짧다*는 가정. 5년 후엔 *AI를 못 쓰는 사람*이 더 구식이 될 수도 있다.
- **확률적 시스템으로 결정론적 시스템 대체 불가**는 *철학적*으로는 맞지만 *실용적*으로는 이미 일부 가능 (테스트·린트가 결정론적 게이트를 제공). 둘 중 하나만 고를 필요 없음.
- *책임 있는 위임*의 5가지 룰 중 **"한 세션에서 검토 가능한 양만 생성"**은 [Long-running agents](2026-05-04-long-running-agents.md)의 시대 흐름과 정면 충돌. 둘은 *다른 시간 지평을 가정*한다 — 어느 쪽이 옳은지가 핵심 미해결 질문.

### 오늘 내 실무에서 느낀 점
오늘 작업한 [CRS-739 race condition + 조회 효율 개선](#) (PR #1831) 은 *AI에게 위임하기 어려운* 작업이었다 — *동시성 모델 + 도메인 의도 + 트랜잭션 경계*가 동시에 작용. 이런 작업을 *직접 디버깅하는 근육*은 AI에게 위임할 수 없다는 게 이 글의 정확한 주장. 한편, *Claude와 함께 가설을 좁혀나간 부분*은 가속이 됐다 — 즉, **하이브리드가 답이지 둘 중 하나가 답이 아니다**.

### MangoLove에 추가할 명시적 룰 후보
1. **"디버깅의 *재현·근본 원인 추적*은 사람이 먼저 시도"** — 자동 위임 기본값을 OFF로
2. **"AI 가속이 든 PR엔 *AI 사용 비율* 한 줄 메모"** — 측정 가능한 의존도 추적
3. **"한 달에 한 번 *AI 없이* 디버깅 세션"** — 근육 유지 운동 (Lars의 *책임 있는 위임* 원칙의 절충안)

### 호스피탈리티/CRS 컨텍스트
- 도메인이 깊고 *비즈니스 규칙이 회색지대*인 호스피탈리티는 **AI에게 *도메인 판단*을 위임하면 더 위험**하다. 검색·문서화·테스트 작성에 위임 + *비즈니스 결정은 사람*이라는 분리가 자연스럽다.
- 신입·주니어가 *Hotel Brain*을 너무 빨리 AI에 의존하면 [기술 위축 47%]가 *도메인 이해*에서도 일어난다. 온보딩 단계에선 *AI 사용 시간 제한* 같은 룰이 필요할 수도 있다.

## 🎯 즉시 시도할 액션 3가지
1. **MangoLove `/strict`에 *디버깅 1차 시도는 사람*** 룰 추가 (옵션이 아닌 default)
2. **이번 달 CRS PR 1개를 *AI 없이* 처리해보고 *체감 차이* 회고** — 근육 측정
3. **회사 단위 *AI 의존도 지표* 후보 도출** — Claude 호출량 / 토큰 비용 / 장애 시 팀 마비 시간 등
