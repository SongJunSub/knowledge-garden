# 기존 LangGraph 워크플로우를 AgentCore Runtime으로: 아이지에이웍스 클레어의 프로덕션 이관 2부 (AWS 기술 블로그)

## 한 줄 요약

**클레어는 기존 Amazon ECS 기반 LangGraph 워크플로우를 운영하며 동시 요청 증가에 따른 응답 지연과 에이전트별 확장성 부족 문제에 부딫혔고, 아이지에이웍스는 로직을 재작성하지 않은 채 AgentCore Runtime이 요구하는 `/invocations`·`/ping` 인터페이스에 맞춘 어댑터만 구현해 실행 환경을 이관했다 — 컨테이너 기동 시 의존성 초기화를 지연시키는 'Lazy 방식'으로 서비스 준비 시간을 최적화하고, 에이전트별 분리 배포·세션 단위 격리로 더 안정적인 프로덕션 환경을 구축했다는 운영 경험이다.**

## 핵심 포인트

- **ECS 운영에서 부딫힌 두 가지 한계** — 기존 Amazon ECS 기반 LangGraph 워크플로우 운영에서 ***동시 요청 증가에 따른 응답 지연***과 ***에이전트별 독립적 확장성 부족***이라는 두 가지 한계에 직면했다. 1부가 "유연성 부족"을 문제 삼았다면, 2부는 **운영 단계에서의 성능·확장성** 문제를 추가로 꺼낸다.
- **재작성 없이 어댑터로 이관** — 기존 로직을 재작성하지 않고도 실행 환경을 격리할 수 있는 'Amazon Bedrock AgentCore Runtime'으로의 이관을 결정했다. 이관의 핵심은 기존 LangGraph 워크플로우를 유지하면서, AgentCore Runtime이 요구하는 ***`/invocations`와 `/ping` 인터페이스***에 맞춘 ***어댑터***를 구현하는 것이었다 — 1부에서 말한 "로직 유지, 실행 환경만 전환" 전략의 구체적 구현 방법이 여기서 드러난다.
- **Lazy 방식 — 의존성 초기화 지연으로 서비스 준비 시간 최적화** — 컨테이너 기동 시 의존성 초기화를 지연시키는 ***'Lazy 방식'***을 도입해 서비스 준비 시간을 최적화했다. 컨테이너가 뜨자마자 모든 의존성을 로드하는 대신, 실제로 필요한 시점에 로드하는 식으로 콜드 스타트 체감 시간을 줄였을 것으로 추정된다(원문 미확인, 일반적인 lazy initialization 패턴의 적용으로 보임).
- **에이전트별 분리 배포 + 세션 단위 격리** — 결과적으로 ***에이전트별 분리 배포***와 ***세션 단위의 실행 환경 격리***를 확보했다. 1부가 PoC 단계에서 "입증했다"고 말한 것이, 2부에서는 "확보했다"는 완료형으로 바뀐다 — 설계 검증에서 실제 운영 구조로의 전환이다.
- **관측 데이터 기반 부하 테스트** — 관측 데이터를 기반으로 한 체계적인 부하 테스트와 최적화를 통해 더욱 안정적인 프로덕션 환경을 구축했다고 밝히지만, 구체적인 부하 테스트 수치(동시 요청 수, 응답 시간 개선율 등)는 Slack 발췌에 없다.

## 내 생각 · 적용점

**핵심 전이 1 — [[2026-10-27-igaworks-claire-agentcore-poc-part1]]과의 관계가 이 노트의 핵심이다.** 1부는 "결정론적 워크플로우의 유연성 부족"이라는 설계 문제와 그 PoC를, 2부는 "동시 요청 증가에 따른 응답 지연"이라는 운영 문제와 그 해법(어댑터 + Lazy 초기화 + 분리 배포)을 다룬다. 두 글을 합치면 클레어 팀이 거친 경로가 분명해진다 — **설계의 유연성 문제(1부)를 해결하려 선택한 아키텍처가, 운영 단계에서 또 다른 문제(확장성·지연)를 만들었고, 그 문제를 다시 어댑터 패턴으로 해결했다(2부)**는 두 단계의 연쇄다. 1부만 읽으면 "AgentCore로 바꿨더니 유연해졌다"는 단순한 성공담처럼 보이지만, 2부를 보면 그 전환 자체도 ECS 환경에서는 또 다른 운영 과제를 낳았다는 걸 알게 된다 — 전환에는 항상 다음 단계의 비용이 따라온다는 교훈이다.

**핵심 전이 2 — [[2026-09-04-samsung-agentcore-aiops-02]]의 "블랙보드 패턴"과 이 글의 "세션 단위 격리"는 같은 문제(동시성)에 대한 다른 해법이다.** 삼성 AIOps 2부는 사람과 에이전트가 공유 작업판(블랙보드) 위에서 단계별로 승인하며 협업하는 구조로 동시성과 안전성을 함께 풀었다. 이 글은 세션 단위로 실행 환경을 완전히 격리해 동시 요청이 서로 간섭하지 않게 만드는, **공유가 아니라 분리**로 동시성을 푸는 접근이다. 두 사례를 나란히 두면, AgentCore 기반 시스템에서 동시성 문제를 푸는 방법이 "공유 작업판 + 사람의 승인" 축과 "세션별 완전 격리" 축으로 갈라져 있다는 걸 보여준다 — 용도(운영 자동화 대 데이터 분석)의 차이가 이 선택을 가른 것으로 보인다.

## 호스피탈리티 / CRS 적용 포인트

**부분 적용 가능성이 있다.** CRS처럼 동시 요청(여러 호텔·채널에서 동시에 들어오는 예약·요금 질의)이 몰리는 도메인에서는, 이 글이 보여준 "재작성 없이 어댑터로 이관, 지연 초기화로 콜드 스타트 완화, 세션 단위 격리로 동시 요청 분리"라는 세 가지 조합이 구체적으로 참고할 만하다. 특히 **"기존 로직을 바꾸지 않고 경계면에 어댑터만 추가한다"**는 원칙은, CRS에서 레거시 워크플로우를 새 실행 환경으로 옮길 때 전면 재작성의 리스크를 피하는 저risk 전환 패턴으로 바로 쓸 수 있다. 다만 AgentCore 자체는 AWS 특정 서비스이므로, 온다의 클라우드 전략에 따라 "그대로 적용"이 아니라 "같은 패턴을 우리 스택에서 재현"하는 방향으로 받아들이는 게 맞다.
