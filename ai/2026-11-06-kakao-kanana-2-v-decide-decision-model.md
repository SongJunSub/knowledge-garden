# 카카오, 멀티모달 판단 전용 모델 'Kanana-2-v-decide' 오픈소스 공개(카카오, 원문 미확인)

> 출처: [AI 에이전트를 위한 멀티모달 의사결정 모델 'Kanana-2-v-decide' 오픈소스 공개](https://tech.kakao.com/posts/846) (카카오 테크 블로그, Slack TechArticles 발췌 전적 의존) · 정리일 2026-11-06

## 한 줄 요약

**카카오가 텍스트와 이미지를 동시에 이해해 확률·점수 형태의 판단 결과만 즉시 반환하는 3B 규모 멀티모달 모델 'Kanana-2-v-decide'를 오픈소스로 공개했다. 문장을 생성하지 않고 판단값만 계산해 GPT-6 Luna 대비 43배 빠른 약 0.04초 응답 속도를 구현했으며, 문의 분류·도구 선택 같은 반복적 서비스 로직에 바로 쓸 수 있는 Noul·Choice·Score 세 가지 판단 형식을 지원한다.**

## 핵심 포인트

- **생성 대신 판단** — 자연어 문장을 생성하는 일반 LLM과 달리, 판단에 필요한 값만 계산해 확률·선택·점수 등 수치 형태로 즉시 반환한다. 이 구조 전환이 응답 속도를 획기적으로 높인 핵심이다.
- **속도** — GPT-6 Luna 대비 **약 43배 빠른 약 0.04초**의 응답 시간을 기록했다고 발표됨(고객 문의 분류, 도구 선택 등 반복 판단 작업 기준).
- **세 가지 판단 형식** — 서비스 로직에 직접 활용 가능한 **Noul·Choice·Score** 세 형식을 지원한다(각 형식의 정확한 정의는 발췌에 없어 확인 못함).
- **규모와 배포** — 3B 파라미터 규모, 허깅페이스를 통해 오픈소스로 배포되어 국내외 연구자·기업이 자유롭게 활용·검증할 수 있도록 할 예정.
- **전략 연속성** — 카카오는 이번 공개를 통해 국내 연구자와 기업이 한국어 처리에 특화된 멀티모달 에이전트 서비스를 손쉽게 개발·검증하도록 지원하겠다고 밝혔다(Slack 발췌 기준, 원문 세부 확인은 못함).

## 내 생각 · 적용점

### 핵심 전이 1 — Kanana-2 패밀리가 "거대 범용 모델 하나" 대신 "작은 전용 모델 여러 개"로 조립되고 있다

2주 전 정리한 [[2026-10-21-kakao-kanana-2-vision-encoder]]에서 카카오는 범용 대형 모델 대신 한국어 문서·문화적 맥락에 맞춘 작은 비전 인코더를 직접 설계했다. 이번 Kanana-2-v-decide는 같은 패밀리의 "판단" 구성요소다. **카카오는 Kanana-2를 하나의 거대 모델이 아니라, 역할별로 분리된 작은 전용 모델의 집합으로 조립해가고 있다** — 비전 인코더 → 판단 모델 순서로 공개된 것이 그 증거다.

### 핵심 전이 2 — "생성과 판단의 분리"는 이 가든에 이미 하나의 장르다

[[2026-09-21-jev-field-guide-system-one-model]]이 정리한 "시스템원(판단 전용) 모델" 개념, [[2026-10-08-strands-decider-2b-decision-model]]의 "언어모델 헤드를 떼고 포인터 헤드를 붙여 순전파 한 번으로 판단한다"는 설계가 Kanana-2-v-decide와 정확히 같은 트레이드오프를 공유한다. 차이는 Kanana-2-v-decide가 **텍스트+이미지를 동시에 받는 멀티모달로 이 장르를 확장**했다는 점이다 — Jev·Strands Decider류가 텍스트 전용이었다면, 이번 모델은 "사진으로 들어온 입력도 즉시 판단"까지 영역을 넓힌 사례로 읽을 수 있다.

### 핵심 전이 3 — "반복 판단 작업"이라는 니치는 생성형 LLM의 약점을 정확히 찌른다

문의 분류, 도구 선택처럼 **선택지가 유한하고 반복적인 작업**에서는 대형 생성 LLM의 "문장을 만들고 파싱한다"는 과정 자체가 낭비다. Kanana-2-v-decide·Jev·Strands Decider 모두 이 낭비를 제거하는 같은 해법을 각자 다른 모달리티·설계로 구현한 것으로, **"판단 전용 소형 모델"이 2026년 하반기 AI 인프라의 독립된 한 축으로 자리잡았다**고 볼 수 있다.

## 호스피탈리티 / CRS 적용 포인트

이 글은 "온다가 Claude/AI를 어디에 쓸 수 있을지" 관점에서 특히 참고할 만하다. 온다의 CRS/PMS 운영에는 **선택지가 유한하고 반복되는 판단 작업**이 다수 존재한다 — 예: 들어온 예약 문의를 채널·유형별로 라우팅, 요금·재고 이상치(가격 오류, 중복 예약) 플래그, 고객이 보낸 사진(파손·청소 상태)을 몇 가지 카테고리로 분류. 지금까지는 이런 작업에도 대형 생성 LLM(Claude 등)을 호출해 자연어 응답을 받고 파싱하는 식으로 처리하기 쉬운데, **Kanana-2-v-decide·Jev·Strands Decider가 보여주는 설계 축("생성하지 말고 판단값만 반환")을 그대로 가져와 자체 데이터로 작은 판단 모델을 파인튠하면 지연시간·토큰 비용을 크게 줄일 수 있다**는 원칙을 얻을 수 있다. 다만 Kanana-2-v-decide 모델 가중치 자체(한국어·카카오 서비스 맥락에 최적화)를 그대로 가져다 쓰는 것은 멀고, 설계 패턴만 참고하는 선이 현실적이다.

**내가 Claude를 쓸 때 도움될 점**: 이 글이 보여주는 "판단과 생성의 분리"는 Claude Code 자동화 파이프라인에도 직접 적용 가능한 원칙이다. 예컨대 이 지식 가든 자동화에서 "이 노트를 커밋해도 되는가", "이 위키링크가 억지 연결인가"처럼 사실상 이진·소수 선택지 판단인 단계를, 매번 전체 문장 생성을 요청하는 대신 구조화된 판단 포맷(Choice/Score류)으로 명시적으로 요청하면 더 빠르고 일관된 결과를 받을 수 있다 — Claude에게 프롬프트를 설계할 때 "생성"이 필요한 단계와 "판단"만 필요한 단계를 구분하는 습관으로 옮길 만하다.
