## 한 줄 요약

**네이버 커머스API 플랫폼은 라우팅 규칙 자동 검수, API를 에이전트가 호출 가능한 도구로 바꾸는 MCP 게이트웨이, 흩어진 기술 지식의 자산화라는 세 가지 서로 다른 층위(운영·인터페이스·지식)에 AI를 순서대로 밀어넣고 있다.**

## 핵심 포인트

- **운영 층위 — 라우팅 규칙 자동 검수**: "AI를 활용해 라우팅 규칙을 자동 검수하고 운영 효율을 높인 사례." 사람이 수동으로 검토하던 API 라우팅 설정의 오류를 AI가 사전에 잡아내는 방향으로 보인다.
- **인터페이스 층위 — MCP 게이트웨이**: "API 명세를 AI 에이전트가 호출 가능한 도구로 변환하는 MCP 게이트웨이 설계 및 운영 경험." 기존 REST API 명세(OpenAPI 등)를 자동으로 MCP 툴 스펙으로 변환해, 외부·내부 AI 에이전트가 커머스 API를 직접 호출하게 만드는 설계로 추정된다.
- **지식 층위 — 기술 지식 자산화**: "흩어진 기술 지식을 자산화하여 AI가 문의 답변과 기술 지원 업무를 수행하도록 확장." 산발적인 FAQ·위키·문의 이력을 AI가 참조 가능한 자산으로 재구조화해 1차 CS 응답을 AI에 넘기는 흐름이다.
- **세 가지의 공통점**: 전부 "사람이 반복적으로 하던 검증·변환·응답 작업을 AI가 대신한다"는 점에서 같은 방향이지만, 적용 대상(설정 파일·API 명세·지식베이스)이 다른 세 개의 독립적인 프로젝트로 읽힌다.

## 내 생각 · 적용점

### 핵심 전이 — "API 명세 → 에이전트 호출 도구" 변환은 이 가든에 이미 반복 등장하는 LLM Gateway 계열의 다른 변종이다

[[2026-11-02-cj-olivenetworks-llm-gateway]] 같은 기존 "LLM Gateway" 노트는 전부 **LLM 호출을 중앙화**하는 쪽이었다. 이 네이버 글의 MCP 게이트웨이는 방향이 반대다 — **LLM(에이전트)이 거꾸로 우리 API를 호출하게** 만드는 게이트웨이다. 같은 "게이트웨이로 중앙 통제"라는 아키텍처 패턴이 "안으로 들어오는 LLM 트래픽"과 "밖으로 노출하는 API 트래픽" 양쪽 모두에 쓰이고 있다는 뜻이고, [[2026-08-10-doordash-ai-agent-gateway]]가 다룬 "에이전트 게이트웨이" 개념과 맥이 같다.

### Claude 사용자 관점의 적용점

API 명세를 MCP 툴로 자동 변환하는 설계는, 내가 Claude Code로 사내 API를 다룰 때 매번 수동으로 MCP 서버를 만들지 않고 **OpenAPI 스펙만 던져주면 자동으로 호출 가능한 도구가 되는 패턴**으로 참고할 만하다. 기술 지식 자산화(세 번째 포인트) 역시 Claude에 레포 CLAUDE.md·위키를 미리 구조화해서 넘겨주는 것과 같은 원리다 — 흩어진 지식일수록 AI가 참조하기 전에 "자산화" 단계가 필요하다는 교훈.

## 호스피탈리티 / CRS 적용 포인트

**적용 가능성 있음.** 온다 CRS의 예약·요금 API 명세를 MCP 게이트웨이로 노출하면, 파트너(호텔)나 내부 AI 에이전트가 자연어로 "이 날짜 가용 객실 보여줘" 같은 요청을 바로 API 호출로 연결할 수 있다. 다만 라우팅 규칙 자동 검수·지식 자산화는 원문 미확인 상태라 구체 설계까지는 참고하기 어렵고, "API를 에이전트용 도구로 바꾸는 게이트웨이가 필요하다"는 방향성만 가져올 수 있다.
