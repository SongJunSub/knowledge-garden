# 프롬프트를 쓰는 PM과 AI를 이해시키려는 개발자 (올리브영 테크블로그)

## 한 줄 요약

**올리브영이 카카오톡·챗GPT 플러그인에서 사용자 의도에 맞는 상품을 추천하는 MCP를 구축하면서 얻은 교훈은, ***LLM이 여러 툴 중 올바른 것을 고르게 하려면 툴의 기능·파라미터 설명에 충분한 맥락을 담아야 한다***는 것이고, 그 설명 문구는 한 번에 완성되지 않아 **QA 과정에서 PM과 개발자가 사용자 의도 추론 품질을 보며 반복적으로 다듬었다**는 것이다.** 코드보다 "설명을 어떻게 쓰느냐"가 시스템 품질을 좌우했다는, 프롬프트/툴 디자인이 곧 제품 품질이 되는 사례로 읽힌다 — 다만 이 요약 자체가 원문 3문장을 넘어서는 세부는 담지 못했다는 한계를 다시 강조해둔다.

## 핵심 포인트

(Slack 발췌 세 줄을 그대로, 확대 해석 없이 정리)

- **무엇을 만들었나** — 올리브영은 **카카오톡과 챗GPT 플러그인**을 통해 **사용자 의도에 맞는 상품을 추천하는 MCP**를 구축했다.
- **핵심 설계 원칙** — LLM이 여러 툴 중 **올바른 툴을 선택**하도록 돕기 위해, **툴의 기능과 파라미터에 충분한 맥락을 담는 것**이 핵심이었다.
- **QA에서 벌어진 일** — QA 과정에서 **PM과 개발자가 함께** 사용자 의도 추론을 최적화하기 위해 **설명 문구를 지속적으로 개선**했다. (구체적으로 무엇을 어떻게 고쳤는지 — 실패 사례·개선 전후 비교·반복 횟수 — 는 발췌에 없어 이 노트도 모른다.)

## 인상 깊은 문장

**해당 없음 — 원문을 못 읽어 직접 인용할 문장이 없다.** Slack 봇 발췌 자체도 원문 문장을 그대로 옮긴 인용이 아니라 3줄 요약이라, 따옴표를 붙여 인용하면 없는 원문 표현을 지어내는 셈이 된다. 대신 위 "핵심 포인트"에 발췌 내용을 그대로 남겨둔다.

## 내 생각 · 적용점

### 핵심 전이 1 — "툴 설명에 충분한 맥락"은 [[2026-06-08-anthropic-skills-building-guide]]의 "description이 트리거를 결정한다"와 정확히 같은 지점을 가리킨다

Anthropic Skills 가이드 노트가 뽑았던 핵심 처방은 ***"description 구조 = [무엇을 한다] + [언제 쓴다] + [핵심 능력]"*** 이고, 나쁜 예로 ***"Helps with projects"(너무 막연함)***를 들었다. 올리브영 사례의 "툴의 기능과 파라미터에 충분한 맥락을 담는 것이 핵심"이라는 교훈은, 도구(Skill이든 MCP tool이든)를 설계하는 주체가 다르고 회사도 다른데도 **결국 같은 실패 모드(설명이 막연하면 LLM이 잘못 고른다)와 같은 해법(설명에 트리거 조건·구체 맥락을 담는다)에 도달**했다는 점에서 흥미롭다. Anthropic 가이드가 이론적 원칙을 제시했다면, 올리브영 글은 **그 원칙을 QA에서 실제로 "문구를 반복 개선"하며 검증한 현장 사례**로 겹쳐 읽을 수 있다.

### 핵심 전이 2 — "PM·개발자가 QA에서 설명 문구를 계속 고쳤다"는 [[2026-08-23-mcp-new-roadmap-five-areas]]가 프로토콜 층위에서 풀려는 문제를 현장 층위에서 이미 겪고 있었다는 증거다

MCP 로드맵 노트가 인용했던 문장 — ***"tool selection tends to get worse as the list grows"*** — 은 MCP 메인테이너들이 **progressive discovery**라는 프로토콜 차원의 해법을 준비 중이라는 맥락이었다. 올리브영의 QA 에피소드는 그 문제를 **프로토콜이 고쳐주기 전, 지금 당장 현장에서 부딪히는 팀**의 모습을 보여준다 — 표준의 해법(카탈로그를 작게 쪼개 노출)이 없는 상태에서는, **결국 사람이 설명 문구를 직접 반복 튜닝하는 수작업으로 메울 수밖에 없다**는 것. 두 노트를 겹쳐보면 "tool 선택 품질"이라는 같은 문제를 ①프로토콜 표준(로드맵) ②개별 툴 설명 설계 원칙(Skills 가이드) ③현장 QA 반복(올리브영)이라는 세 층위에서 동시에 다루고 있다는 그림이 완성된다.

## 호스피탈리티 / CRS 적용 포인트

- **원칙 자체는 온다에도 그대로 옮겨온다.** 온다가 향후 B2B 호스피탈리티 제품(PMS·CRS)에 MCP 기반 AI 추천/조회 기능을 붙인다면 — 예를 들어 "이 날짜에 남는 객실 타입 찾아줘", "이 예약의 취소 규정 알려줘" 같은 자연어 질의를 여러 내부 API/툴로 라우팅해야 하는 상황 — 올리브영이 짚은 지점이 그대로 문제가 된다. 온다 도메인 용어(예: `rate plan`, `room type`, `channel mapping`, `allotment` 등 CRS 특유의 전문 용어)를 툴 설명·파라미터 설명에 얼마나 명시적으로 담느냐가 LLM의 툴 선택·파라미터 채움 정확도를 가른다는 원칙은 그대로 적용 가능하다.
- **QA 프로세스 시사점도 실무적으로 유용하다.** "설명 문구는 한 번에 완성되지 않고, PM·개발자가 함께 실제 질의로 반복 검증해야 한다"는 건 — 코드 리뷰처럼 **"툴 설명 리뷰"를 QA 프로세스에 정식으로 넣는다**는 구체적 실행 아이디어로 옮길 수 있다.
- **다만 직접 적용은 아직 가상 시나리오다.** 온다가 지금 시점에 MCP 기반 자연어 추천/조회 기능을 실제로 구축 중이라는 근거는 이 노트에 없다 — [[2026-08-23-mcp-new-roadmap-five-areas]] 정리 때도 짚었듯 "지켜볼 이유는 있지만 아직 로드맵/사례 학습 단계"라는 결론을 그대로 유지한다.
