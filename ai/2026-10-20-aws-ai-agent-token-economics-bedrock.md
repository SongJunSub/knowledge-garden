# AI 에이전트 시대의 기업 토큰 경제학 (AWS)

## 한 줄 요약

**에이전트가 스스로 도구를 호출하고 매 턴마다 컨텍스트를 재전송하면서 토큰 비용이 구조적으로 급증하자, AWS는 기업이 "관리형 에이전트"와 "개인용 에이전트"를 구분해 모델 선택과 예산을 차등 통제하고, 개인 사용자의 도구 사용은 강제 제한보다 기본값·넛지로 유도하라고 제안한다.**

## 핵심 포인트

- **비용 급증의 구조적 원인** — 에이전트가 ***스스로 도구를 호출하고 컨텍스트를 재전송***하는 루프 자체가 토큰 비용을 선형이 아니라 누적적으로 키운다는 게 출발점이다. (참고, 원문 미확인 교차확인) DoiT 블로그는 비슷한 맥락에서 "토큰량이 비용의 좋은 대리 지표가 아니다"라며 토큰이 가장 많이 든 에이전트 3개가 오히려 가장 저렴했던 역설적 사례를 들었다 — AWS 원문이 같은 논리를 썼는지는 확인 못했지만 방향은 일치한다.
- **관리형 vs 개인용 에이전트 구분** — 기업은 ***관리형 에이전트와 개인용 에이전트를 구분해 모델 선택과 예산을 차등적으로 통제***해야 한다. 같은 조직 안에서도 용도(고객 대응 자동화 같은 관리형 서비스 vs 개발자 개인 실험)에 따라 비용 거버넌스 수준이 달라야 한다는 뜻으로 읽힌다.
- **강제 제한보다 넛지** — 개별 사용자의 도구 사용을 ***강제로 제한하기보다 기본값 설정과 넛지***를 통해 비용 효율을 유도하는 전략을 제안한다. "비싼 모델을 못 쓰게 막는다"가 아니라 "기본값을 저렴한 모델/절제된 설정으로 깔아두고, 필요할 때만 사용자가 의도적으로 바꾸게 한다"는 설계다.
- Slack 발췌에 있는 "비용 방정식"의 실제 수식, Bedrock에서 구체적으로 어떤 기능(애플리케이션 추론 프로필 등)으로 이를 구현하는지는 확인하지 못했다.

## 내 생각 · 적용점

### 핵심 전이 1 — 같은 AWS 블로그의 Claude Code 토큰 비용 시리즈와의 연속

[[2026-09-02-aws-claude-code-token-economy-part1]]·[[2026-09-02-aws-claude-code-token-economy-part2]]는 **개인 개발자의 세션 습관**(프롬프트 캐싱, `/usage` 점검) 레벨에서 토큰 비용을 다뤘다. 이 글은 그보다 한 단계 위, **조직 거버넌스** 레벨("관리형 vs 개인용 에이전트를 구분해 예산을 다르게 설정하라")에서 같은 문제를 다룬다. 세 글을 나란히 두면 "개인 습관 → 조직 거버넌스"로 토큰 비용 관리의 스케일이 넓어지는 흐름이 보인다.

### 핵심 전이 2 — HarnessTax가 보여준 "하네스 선택 자체가 5배 비용을 가른다"는 사실과의 결합

[[2026-09-18-harnesstax-coding-agent-harness-cost-study]]는 같은 모델이라도 하네스(Claude Code vs Pi 등)만 바꿔도 비용이 최대 5배 벌어진다는 걸 실증했다. 이 AWS 글의 "관리형/개인용 구분"이라는 거버넌스 원칙에, HarnessTax의 "하네스 선택 자체가 비용 레버"라는 사실을 더하면 — 기업이 비용을 통제하려면 모델 선택뿐 아니라 ***"어떤 하네스를 기본값으로 깔아두는가"***도 같은 수준의 레버로 다뤄야 한다는 결론이 자연스럽게 이어진다.

## 호스피탈리티 / CRS 적용 포인트

이 글의 원칙은 온다 내부 AI 도구 운영에 **비교적 직접 적용 가능**하다. 온다도 개발자들이 Claude Code 같은 코딩 에이전트를 개인 세션으로 쓰는 동시에, CRS 운영(고객 문의 자동응답 등)에 관리형 에이전트를 도입할 가능성이 있다면 — 이 둘을 같은 예산·모델 정책으로 묶지 말고, ***관리형 서비스는 엄격한 비용/품질 SLA로, 개인 개발 세션은 기본값+넛지로*** 분리 통제하는 구조를 그대로 가져올 수 있다. 다만 실제 수치(비용 방정식)를 확인하지 못해 구체적인 임계값 설계까지는 이 노트만으로 못한다.
