# AI QA 에이전트 실무 후기 (Antigravity) — 결함을 '발견'하는 게 아니라 '왜 안 되는지 분석'하는 순간 도구가 동료가 된다, 그리고 막혔을 때의 협업 복원력이 완전 자동화보다 중요하다

> 출처: [CSP 차단까지 스스로 짚어낸 AI QA 에이전트: Antigravity 실무 후기](https://cannotbehidden.com/work/antigravity-ai-qa-agent-review/) (hoonyoung, cannotbehidden.com) · 정리일 2026-07-14

## 한 줄 요약

**좋은 기획서와 명확한 프롬프트만 있으면, 복잡한 자동화 테스트 코드를 짜지 않고도 AI 에이전트(Antigravity)로 "공유 가능한 수준"의 QA 리포트 초안을 뽑을 수 있었다는 실무 후기. 워크플로는 기획서를 Gemini에 넣어 QA 프롬프트를 다듬고 → Antigravity에 입력해 브라우저 QA를 실행 → 마크다운 리포트를 얻는 4단계다. 핵심 통찰 두 가지: 에이전트가 결함을 발견하는 데 그치지 않고 콘솔·네트워크 로그를 뒤져 "왜 안 되는지"(CSP 차단)까지 분석하고 해결책을 제안했다는 것, 그리고 자동화가 막혔을 때 사람이 화면을 넘겨주면 스크립트 수정 없이 재개하는 Human-in-the-Loop가 실무에서 통했다는 것. 다만 "최종 판단은 사람이 해야 한다"는 단서를 분명히 단다.**

> *Antigravity는 Google이 Gemini 3와 함께 공개한 에이전트 우선 개발 플랫폼(IDE + 다중 에이전트 오케스트레이션 + 브라우저 자율 검증)이다. 도구 스펙 자체는 이 정리의 관심 밖이고, 아래는 "AI 에이전트가 QA라는 지식 노동을 어디까지 하고 사람은 어디서 개입하는가"의 전이 원칙만 추린 것이다.*

## 핵심 포인트

- **워크플로 = Gemini(프롬프트 정련) + Antigravity(브라우저 QA 실행)** — 기획서를 Gemini에 주고 QA 프롬프트를 몇 차례 다듬은 뒤 그대로 에이전트에 입력한다.
- **"안 된다"가 아니라 "왜 안 되는지"** — 플레이어 요소가 렌더링되지 않자 제네릭 에러만 뱉지 않고 **콘솔 로그·네트워크 요청을 스스로 조사**해, CSP(Content Security Policy)로 외부 iframe 도메인이 차단됐음을 짚고 **"도메인 예외 처리"**를 해결책으로 제안했다.
- **Human-in-the-Loop** — React SPA의 동적 DOM 식별자 때문에 버튼 참조를 잃자, 사람이 문제 화면을 직접 띄우고 "앞 단계는 건너뛰고 지금 화면부터 이어서 검수해줘"라고 지시 → **스크립트 수정 없이 검수 재개**.
- **리포트 품질** — 항목별 PASS/FAIL/BLOCK 판정, 실패 사유 분류(문구 불일치·툴팁 누락 등), 개선 제안, 에러 스크린샷·검증 로그를 마크다운으로. "별도 가공이 거의 필요 없는 수준."
- **실무 도입의 관건** — "전부 자동이냐"가 아니라 **"막혔을 때 얼마나 유연하게 협업이 되느냐"**.
- **명확한 단서** — **"최종 판단은 사람이 해야 한다."** AI 리포트는 기획 의도·구현 맥락에 비춰 사람이 재검증해야 한다. 성공 전제는 좋은 기획서 + 명확한 프롬프트.

## 내 생각 · 적용점

### 핵심 전이 1 — AI의 가치는 '탐지'가 아니라 '분석'에서 나온다

결함을 지적하는 자동화는 흔하다. 그러나 콘솔·네트워크 로그를 스스로 파고들어 **근본 원인(CSP 차단)과 해결책(도메인 예외)까지** 제시하는 순간, 도구가 '검사기'에서 '동료'로 전환된다. 그렇다면 AI 도입 판단 기준을 **"탐지 커버리지"에서 "인과 설명 능력"으로** 옮겨야 한다. 이건 [[2026-05-27-react-doctor-ai-code-verification]]·[[2026-06-08-agentic-code-review]]의 "AI가 코드를 검증한다"는 논점을 QA로 확장한 것이고, [[2026-06-08-slack-agentic-testing]]의 에이전틱 테스트와 같은 계열이다.

### 핵심 전이 2 — 완전 자동화보다 '협업 복원력'이 실무 도입의 진짜 관건

React SPA 동적 DOM처럼 자동화가 반드시 막히는 지점이 존재한다. 중요한 건 100% 자동이 아니라, 막혔을 때 사람이 상태를 넘겨주고("여기서부터 이어서") 에이전트가 재개할 수 있는 유연함이다. **Human-in-the-Loop를 실패가 아니라 설계 원칙으로 받아들이는 것** — 이건 어제 정리한 [[2026-07-13-own-the-outer-loop]]의 "자율성은 최대화 대상이 아니라 설계 변수, 중단·조절·검증이 가능한 수준"과 정확히 같다. QA 에이전트의 이 후기가 그 원칙의 살아있는 사례다.

### 핵심 전이 3 — "최종 판단은 사람" = Answerability의 QA 판본, 그리고 프롬프트가 곧 명세

보고서가 아무리 매끈해도 사람의 재검증 없이 액면 수용하면 안 된다는 것은 [[2026-07-13-own-the-outer-loop]]의 Answerability(설명 책임), [[2026-07-13-i-love-llms-i-hate-hype]]의 "미래는 소시지다(도구가 대체하는 건 판단이 아니라 타이핑)"와 같은 축이다. 그리고 성과가 "좋은 기획서 + 명확한 프롬프트"에 전적으로 의존한다는 점은 **"garbage in, garbage out"의 프롬프트 버전** — 며칠 전 정리한 [[2026-07-13-ai-agents-are-the-new-saas]]의 "에이전트 명세 7요소", [[2026-07-12-write-code-like-a-human-will-maintain-it]]와 같이, AI 시대엔 명세를 정교하게 쓰는 능력이 산출물 품질을 결정한다.

### 핵심 전이 4 — AI가 낮추는 진짜 비용은 실행 속도가 아니라 커뮤니케이션 비용

"엑셀에 스크린샷 수동 삽입" 대신 공유 가능한 표준 리포트가 자동 생성되면서 팀 간 소통·재가공 비용이 줄었다는 게 실질 이득이다. **도구 ROI를 '실행 속도'가 아니라 '협업 마찰 감소'로 측정하는 관점** — 이건 앞서 정리한 여러 단위 경제 글([[2026-07-13-how-an-ai-token-travels-through-a-data-center]] 등)이 "무엇이 진짜 비용인가"를 물은 것과 같은 결이다.
