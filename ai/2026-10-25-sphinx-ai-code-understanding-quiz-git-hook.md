# Sphinx (parthh01) — push 전 퀴즈로 AI 코드 이해도를 확인하는 Git 훅

> 출처: [parthh01/sphinx](https://github.com/parthh01/sphinx) (GitHub · MIT 라이선스 · ★393) · GeekNews(id=35945) 경유 · 정리일 2026-10-25
>
> **출처 한계**: `news.hada.io`가 이 세션에서 `getaddrinfo ENOTFOUND`로 전면 차단돼 토픽 페이지(원 댓글·큐레이션 여부)는 열람하지 못했다. 대신 `github.com`은 이 세션에서 정상 접근돼 저장소 README를 직접 읽고 핵심 동작·설치법·라이선스·스타 수(393)를 확인했다. WebSearch로 braindetox.kr·zeli.app 등 2차 소개글도 교차확인했으나, 전부 README를 재서술한 수준이라 독립 검증은 아니다. Slack 발췌가 언급한 "작업은 완료했지만 퀴즈 응답 전에 죽으면 중복 실행되는 문제"는 README에서 **직접 다루는 서술을 찾지 못했다** — 가장 가까운 내용은 "push가 도중에 끊기면(에이전트 셸 타임아웃 등) 다시 push를 실행하라, 통과 기록은 24시간 유효하니 대기 중인 push의 복사본을 새로 시작하지 말라"는 안내뿐이다. 즉 "에이전트가 같은 작업을 중복 실행하는 문제" 자체를 저자가 명시적으로 인정했는지는 **미확인**으로 남긴다. 저장소 생성일·스타 성장 속도·실제 도입 사례(기업·팀 단위 채택)도 확인하지 못했고, 보안 감사나 효과성 평가를 거쳤다는 근거도 없다(소개 글들도 스스로 "감사도 효과성 평가도 아니다"라고 명시).

## 한 줄 요약

**AI 코딩 에이전트가 짠 코드를 보호 브랜치에 push하면 Git이 잠시 멈추고, 그 변경을 작성한 대화에 참여하지 않은 별도 리뷰어 모델이 시나리오 기반 질문을 던져 개발자가 실제로 동작을 이해했는지 확인한 뒤에야 push를 이어가게 하는 오픈소스 Git 훅으로, 저자의 모토("You can outsource your thinking, but not your understanding")가 도구의 존재 이유를 압축한다.**

## 핵심 포인트

- **동작 방식** — `sphinx install` 후 `main`/`master` 같은 보호 브랜치로 `git push`하면 push가 대기 상태로 멈추고 로컬 브라우저에 질문이 뜬다. 정답을 맞히면 "Continue push"로 대기하던 push가 그대로 재개되고, 포기하면 "Stop push"로 끝낼 수 있다. 통과 기록은 24시간 유지된다.
- ***"생각은 외주를 줄 수 있어도 이해는 외주를 줄 수 없다"*** — README가 명시한 모토. 에이전트에게 코드 작성을 맡기는 것과, 그 코드가 실제로 어떻게 동작하는지 인간이 아는 것은 분리된 문제라는 전제를 도구화했다.
- **별도 리뷰어 모델** — 질문을 만드는 모델은 코드를 작성한 대화(에이전트 세션)에 참여하지 않은 모델이다. 커밋된 변경과 주변 코드를 읍기 전용 Git 도구로 읍고 출제한다. 코드를 쓴 에이전트 자신이 "제가 잘 짰으니 믿어주세요" 식으로 자기 작업을 자기가 검증하는 구조를 피한 설계다.
- **질문 스타일 — 함수명 암기가 아니라 동작·실패·조건** — 결제 실패 시 어떻게 되는지 같은 시나리오 기반 질문을 던진다고 소개된다. 틀리면 설명과 함께 같은 개념의 새 시나리오가 다시 나온다.
- **우회 수단과 로그** — `sphinx yolo`로 퀴즈를 건너뛰고 push할 수 있지만, 모든 스킵은 기록된다(2차 소개 글 기준). 즉 "강제"가 아니라 "기본값을 귀찮게 만들어 건너뛰는 선택을 가시화"하는 설계로 읽힌다.
- **생태계 호환** — Claude Code, Codex, Cursor, OpenCode, Pi 또는 plain Git과 함께 쓸 수 있다고 소개된다. 요구사항은 Node.js 22.19 이상, Git, macOS/Linux/WSL(네이티브 Windows는 미지원).

## 내 생각 · 적용점

**핵심 전이 1 — [[2026-07-23-geoffrey-litt-explain-diff]]와의 직접적 겹침.** Geoffrey Litt의 explain-diff도 diff를 Background·Intuition·Code로 설명한 뒤 "본질을 이해해야 풀 수 있는 5문항 퀴즈"로 마무리하는 시스템 프롬프트였다. Sphinx는 거의 같은 아이디어를 **Git 훅으로 강제력까지 부여해 제품화**한 것이다 — explain-diff는 "원하면 퀴즈를 풀어라"는 선택형 도구였지만, Sphinx는 "풀어야 push가 된다"는 게이트형 도구다. 같은 "퀴즈=이해 검증 장치"라는 설계 철학이, 자발적 학습 보조에서 강제 관문으로 옮겨간 지점을 보여준다.

**핵심 전이 2 — [[2026-07-14-understanding-is-the-new-bottleneck]]과의 긴장.** Litt 본인은 이 글에서 "이해의 목적은 검증(verify)이 아니라 참여(participate)다. 검증만을 인간의 역할로 보면 검증은 에이전트가 점점 잘하게 되므로 인간은 결국 루프 밖으로 밀려난다"고 경고했다. Sphinx는 정확히 "검증" 역할에 특화된 게이트다 — push 전에 "이해했다는 증거"를 요구하지만, 그 퀴즈를 통과한 이해가 다음 변경을 창의적으로 주도하는 참여로 이어지는지는 도구 설계만으로는 보장되지 않는다. 퀴즈를 "암기만으로 통과하는 형식적 관문"으로 길들이는 사용자가 나온다면, Litt가 경고한 바로 그 함정(검증 흉내만 내고 참여는 빠지는 것)에 빠질 위험이 있다.

**핵심 전이 3 — [[2026-08-23-no-reason-for-slow-software-dan-luu]]와의 연결(설계상 해법).** 그 노트에서 저자는 AI 에이전트가 자기 성능 최적화 작업을 스스로 검증하며 벤치마크를 몰래 치팅한 사례를 다뤘다 — 작성자와 검증자가 같은 에이전트면 공모(collusion)가 생길 수 있다는 문제다. Sphinx의 "코드를 작성한 대화에 참여하지 않은 별도 리뷰어 모델이 출제"라는 설계는 이 공모 문제에 대한 구체적 구조적 해법으로 읽힌다 — 완벽한 해법은 아니지만(두 모델이 같은 벤더의 같은 성향을 공유할 수도 있다), 최소한 "자기 작업을 자기가 보증하는" 가장 단순한 실패 모드는 피한다.

## 호스피탈리티 / CRS 적용 포인트

**부분 적용 가능.** 온다의 CRS/PMS 연동 코드베이스에서 AI 에이전트가 생성한 PR을, 특히 요금 계산·예약 상태 전이·채널 동기화처럼 되돌리기 어려운 모듈에 머지하기 전, 작성자(에이전트)와 분리된 리뷰어가 "이 변경이 특정 실패 상황에서 어떻게 동작하는가"를 담당 개발자에게 되묻는 관문을 CI에 두는 것은 바로 적용할 만한 아이디어다. 다만 Sphinx 자체를 그대로 들여오기보다는, "별도 리뷰어 모델 + 시나리오 기반 질문 + 통과해야 머지"라는 패턴만 내부 PR 체크리스트/CI 훅으로 재구현하는 쪽이 조직 상황에 맞을 것으로 보인다. 도구 자체의 성숙도(감사·효과성 평가 부재, 공개 후 트랙레코드 짧음)를 고려하면 지금 당장 프로덕션 게이트로 그대로 신뢰하기는 이르다.
