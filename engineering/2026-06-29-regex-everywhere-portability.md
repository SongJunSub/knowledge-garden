# '어디서나' 동작하는 정규식 (johndcook.com) — '표현력과 이식성은 트레이드오프', 환경마다 다른 문법이 만드는 정규식 방언 문제와 최소 공통 분모 전략

> 출처: [Regex That Works Everywhere](https://www.johndcook.com/blog/2026/06/23/regex-everywhere/) (johndcook.com) · 정리일 2026-06-29

## 한 줄 요약

**정규식(regex)은 "어디서나 쓸 수 있다"고 알려졌지만, 실제로는 환경마다 지원 기능과 문법이 달라 같은 패턴이 다른 환경에서 실패한다. 표현력 풍부한 환경(Perl)에 익숙할수록 이식성 문제를 더 자주 만난다 — "어디서나 동작하는" 정규식의 범위는 예상보다 훨씬 좁다.**

## 핵심 포인트

- **정규식 "방언" 문제** — Perl·Python·GNU sed·awk·grep·Emacs 각각 지원 기능과 문법이 다름. 같은 `\s`가 어떤 환경에서는 공백, 다른 환경에서는 문자 클래스 구분자.
- **가장 좁은 "어디서나"** — 리터럴·`[…]`·`.`·`*`·`^`·`$`만 남음. 대부분의 "강력한" 기능은 이미 환경 종속.
- **GNU 4총사(sed·awk·grep·Emacs)의 공통 범위** (GNU `-E` 기준):
  - `.`·`^`·`$`·`[…]`·`[^…]`
  - `*`·`?`·`+`·`{n,m}`
  - `\w`·`\W`·`\s`·`\S`·`\b`·`\B`
  - `\1~\9` 역참조·`|` 대안·`(...)` 캡처
- **Emacs의 특이성** — `+ ? ( ) { } |`에 백슬래시 접두사 필요. `\s`·`\S` 의미가 다름.
- **숨은 복잡성** — 정규식 자체 외에도: 셸 이스케이프·Python raw 문자열·JSON 이스케이프 등 도구 경계를 건널 때마다 이스케이프 레이어 추가.

## 인상 깊은 문장

> "Perl 같은 기능이 풍부한 환경에 익숙하면, 다른 도구에서의 호환성 이슈를 더 자주 만난다."

> "'어디서나' 동작하는 가장 엄격한 정의는 — 리터럴·문자 클래스·. * ^ $만 남을 정도로 제한된다."

## 댓글 — HN 다양한 관점 (GN⁺ 큐레이션)

- **POSIX 기본 정규식**: 더 제한적이지만 진정한 의미의 이식성 표준이라는 의견.
- **RFC 9485**: 정규식 인터오퍼러빌리티를 위한 표준 제안 (JSON Schema 권장 부분집합 포함).
- **Go's regexp 패키지**: RE2 문법 기반으로 역참조·lookaround 제거 — 표현력을 줄인 대신 선형 시간 보장.
- **"정규식은 구조화된 언어였어야 한다"**: 이스케이프 중첩 문제가 애초에 언어 설계 결함이라는 비판.
- **Emacs 이스케이프 이슈**: Emacs Lisp 문자열 안에서 정규식 백슬래시가 중첩 이스케이프 필요.

## 내 생각 · 적용점

### 핵심 전이 1 — "표현력 vs 이식성" 트레이드오프는 모든 도구에 적용된다

정규식만의 문제가 아니다. **SQL 방언(MySQL·PostgreSQL·Oracle 문법 차이), OS API(POSIX vs Windows), 언어 기능(Java 21 vs Java 11) 모두 같은 구조다.** 강력한 기능에 의존할수록 환경 종속이 심해진다. 도구를 선택할 때 "이 기능이 얼마나 이식 가능한가"를 같이 질문하는 습관. CRS가 특정 DB 벤더 기능(MySQL JSON 함수 등)에 의존하면 나중에 마이그레이션 비용이 올라간다.

### 핵심 전이 2 — "최소 공통 분모" 전략의 가치

저자의 결론: 가장 표현력 있는 것 대신 "어디서나 동작하는 부분집합"을 의도적으로 선택. **이것은 소프트웨어 설계에서 "boring technology" 선택([[2026-05-29-choose-boring-technology-2015]])과 같은 논리다.** Go's regexp 패키지가 역참조·lookaround를 제거한 대신 선형 시간을 보장한 것처럼 — **표현력을 의도적으로 포기해서 예측 가능성을 얻는 트레이드오프**.

### 핵심 전이 3 — "이스케이프 레이어"는 시스템 경계의 복잡성

정규식을 셸 → Python → JSON → DB로 전달할 때마다 이스케이프 레이어가 쌓인다. **이것은 시스템 경계를 건널 때마다 직렬화·역직렬화가 필요한 것과 같다.** CRS에서 Opera PMS API → 우리 DB → OTA 채널로 데이터가 흐를 때 각 경계에서 인코딩·이스케이프 문제가 생기는 이유도 같다. **경계를 최소화하거나, 경계마다 명확한 계약(Contract)을 만드는 것이 복잡성을 줄이는 방법.**
