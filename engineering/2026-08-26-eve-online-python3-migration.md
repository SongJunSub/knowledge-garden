# EVE Online, 23년 된 240만 줄 Python 2 코드베이스를 Python 3로 옮기기 시작하다

> 출처: [The Move to Python 3 Begins!](https://www.eveonline.com/news/view/the-move-to-python-3-begins) (EVE Online 공식 개발 블로그, CCP Games) · 정리일 2026-08-26
> **출처 한계**: `eveonline.com`·`forums.eveonline.com`·`news.hada.io`·`massivelyop.com` 모두 이 세션에서 직접 접근이 막혔다. 아래 내용은 이 원문·EVE 공식 포럼·Massively Overpowered 보도의 내용을 인용·요약한 WebSearch 스니펫을 교차해 재구성한 것이며, 원문을 직접 눈으로 확인하지 못했다는 점을 감안해야 한다. 다만 Slack 발췌의 수치(240만 줄·95.9%·3,300줄·2만 줄)와 WebSearch로 재구성한 수치가 정확히 일치해, 핵심 사실관계 자체의 신뢰도는 높다고 판단한다.

## 한 줄 요약

**EVE Online이 23년간 쌓인 240만 줄·약 2만 개 파일의 Python 코드베이스를 Python 3로 옮기기 시작했다. 전략은 "한 번에 전환"이 아니라 ***먼저 Python 2.7과 3에서 모두 실행되게 만든 뒤, 두 버전에서 결과가 달라지는 코드만 사람이 한 줄씩 검토***하는 방식이다. 첫 검사에서 파일의 95.9%는 이미 양쪽에서 컴파일됐고, Python 3가 아예 거부하는 구문은 3,300줄에 그쳤다 — 그런데 ***양쪽에서 컴파일은 되지만 결과가 달라지는 코드가 약 2만 줄*** 있고, 그 전형적 사례가 정수 나눗셈이다(Python 2의 `1/2`는 `0`, Python 3에서는 `0.5`). 그 숫자가 데미지·ISK(게임 화폐)·좌표일 수 있는 게임에서는, 이 2만 줄 하나하나가 기계적으로 고칠 수 없는 ***사람의 판단***을 요구한다.**

## 핵심 포인트

- **규모** — **240만 줄, 약 2만 개 파일.** 23년 누적, 일부는 Python 2.7 이전 2.3~2.5 시대 표준으로 작성돼 Python 3 파서가 아예 파싱을 거부하는 구문도 있다.
- **가용성 제약** — Tranquility(라이브 서버)는 하루 **23.75시간 가동을 유지해야 하는** 상용 서비스라, 전체 재작성이나 빅뱅 전환이 불가능하다.
- **1단계: 양쪽 버전에서 실행되게 만들기** — Python 커뮤니티가 만든 도구(Python-Future/`futurize`, 2to3와 같은 코드 재작성 엔진 기반)로 오래된 패턴을 ***Python 2.7과 3 모두가 받아들이는 형태***로 자동 재작성.
- **1차 스캔 결과** — 파일의 ***95.9%가 이미 양쪽에서 컴파일***됐고, Python 3가 거부하는 구문은 ***약 3,300줄***뿐이었다 — "코드가 낡았다"는 우려에 비해 순수 구문 문제는 생각보다 작았다.
- **진짜 난제는 여기** — 양쪽에서 컴파일은 되지만 ***결과가 달라지는 코드가 약 2만 줄***. 대표 사례가 **정수 나눗셈**(Py2 `1/2 == 0` vs Py3 `1/2 == 0.5`) — 이 숫자가 **데미지·ISK·좌표**일 수 있어, 각 줄마다 기계적 자동 수정이 아니라 **사람의 결정**이 필요하다.
- **검증·배포 경로** — 7월 말 **Singularity**(테스트 서버)에서 플레이어와 함께 첫 변경분을 검증한 뒤, 그 변경을 **Tranquility**(라이브 서버)에 배포. 에이전트 미션 백엔드부터 시작했고 플레이어 입장에서는 체감 변화가 없도록 설계.
- **목적** — 더 빠른 인터프리터(함대전·마켓 허브 성능), 버그를 더 빨리 찾는 현대적 툴링, 신규 개발자가 생산적으로 기여할 수 있는 코드베이스.

## 내 생각 · 적용점

### 핵심 전이 1 — 같은 "대규모 언어 마이그레이션"이지만 정반대 축의 사례: 검증 가능성이 속도를 결정한다

[[2026-08-01-bun-zig-to-rust-rewrite-with-ai]]는 53만 줄을 **AI 64인스턴스로 11일** 만에 옮긴 사례였고, 그 성공 조건은 ***"이식(port)에는 정답지가 있다"***는 것 — 견고한 테스트 스위트가 있으면 배율이 풀린다는 결론이었다. EVE의 이 마이그레이션은 정확히 반대편에 있다: **23년 묵은 게임 서버 코드에는 그런 정답지(포괄적 테스트 스위트)가 없거나 불완전하고**, 무엇보다 ***"컴파일은 되지만 결과가 다른 2만 줄"*** 문제는 애초에 테스트로 잡아내기 어려운 종류다(의미는 바뀌지만 예외를 던지지 않으므로). 그래서 EVE는 AI 병렬 재작성이 아니라 **"두 버전에서 동시에 돌려보고 차이를 찾아 사람이 검토"**하는, 훨씬 느리지만 훨씬 보수적인 전략을 택했다. **Bun의 "재현 조건 셋"(주도 엔지니어·견고한 테스트·토큰 투자 각오) 중 "견고한 테스트 스위트"가 없을 때 대안이 무엇인지를 EVE가 실증한다** — 이중 컴파일 검증이라는, 테스트가 없어도 "차이를 발견"할 수 있는 별도의 안전망.

### 핵심 전이 2 — "무엇이 위험한가"의 정의가 구문 오류에서 조용한 의미 변화로 이동

Python 2→3 전환 논의는 흔히 "구문이 안 돌아간다"는 문제로 단순화되지만, EVE의 데이터(3,300줄 vs 2만 줄, 6배 차이)는 ***진짜 위험이 컴파일 실패가 아니라 "조용히 다른 값을 내는 코드"***에 있음을 보여준다. 이건 [[2026-08-25-waf-auto-block-agent-trust-boundary]]가 다룬 "판단 근거 자체가 조작 가능한 데이터에 오염될 수 있다"는 문제와 다른 결이지만, **"겉보기엔 정상 동작하는데 실제로는 다른 결과를 내는 코드가 가장 위험하다"**는 구조적 교훈은 공유한다 — 두 경우 다 "에러가 나면 오히려 안전하다"는 역설이 있다.

## 호스피탈리티 / CRS 적용 포인트

- **"컴파일되지만 결과가 다른" 클래스의 버그는 CRS 레거시 코드에서도 가장 위험한 유형이다.** 요금 계산·통화 환산·재고 차감 로직에 정수/부동소수점 나눗셈, 반올림 규칙 차이 같은 게 숨어 있으면, 언어·라이브러리 버전을 올릴 때 예외 없이 조용히 다른 금액이 나올 수 있다 — EVE의 "이중 실행 후 차이 진단" 전략은 이런 레거시 요금/정산 모듈을 업그레이드할 때 참고할 만한 구체적 기법이다.
- **가용성 제약이 있는 상용 서비스의 언어/런타임 마이그레이션은 "점진적 이중 호환 → 차이 검토 → 단계적 배포"가 정석**이라는 걸 실제 23년차 상용 게임 서버가 보여준다. CRS의 코어 예약·정산 엔진처럼 24/7에 가까운 가동을 요구하는 시스템의 기술 부채 청산 계획에 직접 참고 가능한 사례.
