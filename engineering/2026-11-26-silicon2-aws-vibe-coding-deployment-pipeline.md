# 실리콘투의 바이브코딩 에셋을 위한 AWS 기반 표준 배포 파이프라인 구축기 (AWS)

> 출처: [실리콘투의 바이브코딩 에셋을 위한 AWS 기반 표준 배포 파이프라인 구축기](https://aws.amazon.com/ko/blogs/tech/silicon2-vibe-coding-assets-aws-deployment-pipeline/) (AWS 기술 블로그) · 정리일 2026-11-26

> **출처 한계**: `aws.amazon.com`이 이 세션에서 egress 차단되어 원문을 열람하지 못했고, WebSearch로도 "실리콘투"(화장품 유통기업으로 추정) 고유 사례는 전혀 찾지 못했다. Slack 발췌 불릿 3개만을 근거로 작성했다. AWS가 MCP 서버 기반 배포 에이전트 SOP를 미리보기로 제공한다는 ***일반적인 배경 기술***은 WebSearch로 확인됐으나, 이 글의 구체 아키텍처와 직접 연결되는지는 불명확하다.

## 한 줄 요약

**실리콘투가 현업 구성원이 바이브코딩으로 만든 대시보드류 에셋을 안전하게 배포하기 위해, 에셋을 유형별로 분류하고 개발팀과 인프라팀의 역할을 나눠 GitHub Actions와 OIDC 인증으로 AWS 리소스 관리 부담을 줄이며 배포를 자동화하는 표준 파이프라인을 구축했다는 사례다.**

## 핵심 포인트

- **바이브코딩 에셋의 안전한 배포 체계 구축** — 현업 구성원이 바이브코딩으로 생성한 대시보드 에셋을 ***안전하게*** 배포하기 위한 표준 체계를 구축했다는 문제의식 — "누구나 만들 수 있지만 아무나 배포하면 위험하다"는 바이브코딩 시대의 전형적 긴장을 보여준다.
- **에셋 유형별 분류와 역할 분리** — 대시보드형 에셋을 유형별로 분류하고 ***개발팀과 인프라팀의 역할***을 명확히 나눠 운영 효율을 높였다는 서술.
- **GitHub Actions + OIDC로 리소스 관리 부담 경감** — GitHub Actions와 OIDC 인증을 활용해 AWS 리소스 관리 부담을 줄이고 배포 자동화를 구현했다는 핵심 기술 — 장기 수명 액세스 키 대신 ***OIDC 기반 단기 인증***을 쓰는 업계 모범 사례와 일치한다.

## 내 생각 · 적용점

### 핵심 전이 — "누구나 만들 수 있게 됐다"의 배포 측 숙제

바이브코딩으로 비개발자도 대시보드를 "만들 수" 있게 된 건 이 레포가 여러 번 다룬 변화지만, 이 글은 그 다음 단계 — ***"만든 걸 어떻게 안전하게 배포할 것인가"***라는, 생성 쪽이 아니라 배포 쪽의 숙제를 다룬다. [[2026-11-26-silicon2-aws-vibe-coding-deployment-pipeline]] 자체가 이 레포에서 "바이브코딩 배포 표준화"를 다루는 첫 사례다. 역할 분리(개발팀 vs 인프라팀)는 같은 배치의 [[2026-11-26-naver-care-agent-mcp-agent-design-part2]]가 보여준 "모델 vs 코드"의 역할 분리와는 다른 축(사람 조직 내 역할 분리)이지만, "누가 무엇을 책임질지 명확히 나눈다"는 원칙은 같다.

### 적용점

"생성이 쉬워질수록 배포 표준화가 병목이 된다"는 구조는, AI 코딩 도구 도입을 검토하는 모든 조직에 적용된다 — 코드/대시보드 생성 속도를 높이기 전에, 그 결과물을 안전하게 운영 환경에 올리는 파이프라인을 먼저 표준화해야 한다.

## 호스피탈리티 / CRS 적용 포인트

**적용 가능성 있음.** CRS 내부 운영팀이 바이브코딩으로 리포트·대시보드를 직접 만드는 문화가 생긴다면, "에셋 유형별 분류 + 역할 분리 + OIDC 기반 자동 배포"라는 이 사례의 3단 구조를 거의 그대로 가져올 수 있다 — 특히 OIDC로 장기 액세스 키를 없애는 부분은 보안 측면에서 바로 적용 가능한 모범 사례다.
