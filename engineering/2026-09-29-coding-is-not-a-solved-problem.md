# 코딩은 해결된 문제가 아니다 (Alex Ewerlöf)

> 출처: [Coding is NOT solved](https://blog.alexewerlof.com/p/coding-is-not-solved) (Alex Ewerlöf, Alex Ewerlöf Notes) · GeekNews(id=34435) 경유 · 정리일 2026-09-29
>
> **출처 한계**: `news.hada.io`가 이번 세션 egress 정책으로 전면 차단돼 원문·hada 댓글을 직접 열람하지 못했다. 아래는 Slack 발췌 3개 불릿과 WebSearch로 확인한 블로그 본문·HN 댓글 스니펫을 교차재구성한 것이다. 저자가 밝힌 "나는 AI 반대자가 아니다, LLM 코딩 도구 초기 채택자이고 직접 하네스도 만들었다"는 입장 표명은 WebSearch로 확인했지만, 본문 전체 논증 순서나 예시 코드까지는 확인하지 못했다.

## 한 줄 요약

**"코딩이 해결됐다"는 주장은 코드를 만드는 비용만 세고, 소프트웨어 비용의 큰 부분을 차지하는 유지보수·신뢰성·보안·확장성은 세지 않는다 — LLM은 하네스와 피드백 루프에 크게 의존하지만, 그럼에도 논리적 한계·긴 입력에서의 정확도 저하·비결정적 출력은 남고, 위험 허용도가 낮은 소프트웨어에서 이해와 책임까지 코드 생성에 넘길 수는 없다.**

## 핵심 포인트

- **"해결됐다"는 계산의 오류** — 코딩이 해결된 문제라고 말하는 사람들은 ***코드를 "만드는" 비용만 계산***한다. 그러나 실제 운영에서 소프트웨어 비용의 큰 부분은 유지보수·신뢰성·보안·확장성이며, 애초에 기능 요구사항을 충족했는지 검증하는 일도 여전히 필요하다. 생성 비용이 0에 가까워져도 이 뒷단 비용들은 그대로 남는다.
- **하네스 의존성** — LLM의 코딩 능력은 ***그 자체의 지능보다 하네스와 피드백 루프 설계에 크게 좌우***된다. 구문 오류·실행 오류를 모델에 되먹이고 테스트를 반복 실행하게 만드는 구조가 관찰되는 성능의 상당 부분을 설명한다.
- **되먹임으로도 못 없애는 한계 셋** — 하네스를 아무리 잘 짜도 ① 논리적 추론의 한계, ② 입력이 길어질수록 떨어지는 정확도, ③ 비결정적 출력(같은 프롬프트에도 다른 결과)은 남는다. 이 셋은 "더 나은 프롬프트"나 "더 많은 테스트"로 메울 수 있는 종류의 문제가 아니라는 게 논지다.
- **책임의 이전 불가능성** — 위험 허용도가 낮은 소프트웨어(예: 결제·의료·인프라)에서는 시스템에 대한 ***이해와 장애 발생 시의 책임을 코드 생성 자체에 위임할 수 없다***. AI가 "왜 이렇게 짰는지" 설명을 내놓을 수는 있어도, 그 설명이 실제로 맞는지 판단하고 장애의 결과를 지는 것은 여전히 엔지니어의 몫이다(Slack 발췌 이 지점에서 절단).
- **저자의 입장 표명** — 저자는 스스로를 "AI 반대자가 아니다"라고 못박는다. LLM 코딩 도구의 초기 채택자였고 직접 자신의 하네스까지 만든 실무자라는 걸 앞세운 뒤, 그럼에도 "해결됐다"는 프레이밍이 틀렸다고 말한다는 점에서 이 글은 러다이트적 반발이 아니라 ***실무자의 내부 비판***에 가깝다.

## 인상 깊은 문장

> "People who call coding solved count only the cost of creating code, while maintenance, reliability, security and scalability make up most of the cost of software in production."
> (WebSearch 스니펫으로 확인, 원문 직접 대조는 못 함)

## 댓글

**hada 댓글 수 확인 불가**(원문 차단). Hacker News에서는 큰 반향이 있었다 — WebSearch로 확인한 수치가 스니펫마다 469~476개 댓글·462~473점으로 소폭 엇갈리는데, 정확한 최종 수치는 확정하지 못했다. 다만 "이 정도 규모의 댓글에도 반응이 대체로 긍정적인 건 HN에서는 이례적"이라는 평가가 여러 소스에서 반복됐다. HN에 보이는 반론 하나: "소비자가 낮아진 품질에 적응해 게으르고 무능한 개발자의 존재를 정당화해줄지, 아니면 소비자가 반발할지는 시간이 말해줄 것"이라는 냉소적 댓글이 눈에 띈다 — 저자의 "책임은 여전히 사람 몫"이라는 주장과 결이 다른, "그래도 시장이 낮은 품질을 받아들이면 그만"이라는 반박이다. 저자 본인이 바이어스를 인정(자신도 하네스를 판다/만든다)했다는 점도 정직하게 남긴다.

## 내 생각 · 적용점

### 핵심 전이 1 — 같은 날 정리한 [[2026-09-29-problem-is-not-ai-code-nobody-knows-anything]]과 정확히 같은 GeekNews 배치, 다른 층위의 같은 경고

이 글이 "유지보수·신뢰성·보안 비용이 안 사라졌다"는 **시스템 운영 층위**의 경고라면, 같은 날 GeekNews에 오른 Simon Späti의 글은 "그 비용을 감당할 사람 자체가 이해를 잃고 있다"는 **조직 지식 층위**의 경고다. 두 글을 겹치면 하나의 완결된 그림이 나온다 — 생성 비용 하락이 감춘 두 개의 진짜 청구서(유지보수 비용 / 이해할 수 있는 사람의 소멸)가 같은 주에 각각 다른 저자에게서 나왔다는 것 자체가, 이게 한 사람의 우려가 아니라 실무 현장에서 동시다발로 감지되는 패턴이라는 신호다.

### 핵심 전이 2 — [[2026-09-08-build-vs-buy-ai-maintenance-cost]]의 "3~5년 뒤 청구서"와 같은 계산법

Kevin Goldsmith의 글은 "AI가 초기 개발비는 없앴지만 3~5년 뒤 유지보수·보안·장애 책임까지 없애주지는 않는다"고 했다. 이 글의 "코딩이 해결됐다는 계산은 생성 비용만 센다"는 명제는 정확히 같은 회계 오류를 지적한다 — 다만 Goldsmith는 build-vs-buy라는 조직의 의사결정 프레임에서, Ewerlöf는 "코딩은 해결됐다"는 업계 담론 자체를 반박하는 데서 출발한다는 점이 다르다. 같은 결론에 이르는 두 개의 서로 다른 입구다.

### 핵심 전이 3 — [[2026-09-28-nhn-harness-carving-old-man-no-silver-bullet]]과 부딪히는 "하네스 의존성" 대목

이 글은 "LLM 능력은 하네스·피드백 루프에 크게 좌우된다"고 했는데, NHN의 글은 정확히 그 하네스를 "정보 나열이 아니라 찾는 방법의 구조화"로 잘 설계하면 AI가 팀원처럼 일할 수 있다고 낙관했다. 두 글을 나란히 두면 흥미로운 긴장이 생긴다 — 하네스를 아무리 잘 설계해도 이 글이 말하는 "논리적 한계·긴 입력 정확도 저하·비결정성" 세 가지는 하네스 바깥의 문제라서, NHN의 낙관이 닿을 수 있는 지점과 이 글이 그어놓은 한계선이 서로 다른 자리에 있다는 걸 보여준다.

## 호스피탈리티 / CRS 적용 포인트

직접 적용 가능성이 높다. 온다의 CRS 코어는 정확히 저자가 말하는 "위험 허용도가 낮은 소프트웨어"에 해당한다 — 예약 이중 판매, 요금 오적용, 채널 연동 오류는 장애가 나면 파트너 호텔의 매출·신뢰에 직결된다. 이런 영역에서 AI 생성 코드를 도입할 때는 "생성이 빨라졌다"를 "검증·유지보수 비용도 줄었다"로 착각하지 않는 게 핵심이다. 구체적으로는, 코드 리뷰 기준에 "이 변경이 왜 필요했는지, 실패 시 무엇이 깨지는지를 사람이 설명할 수 있는가"를 게이트로 넣는 것이 저자의 "이해와 책임은 위임 불가"라는 주장을 실무에 옮기는 방법이다.
