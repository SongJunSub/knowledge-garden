# 소프트웨어가 느린 이유는 느린 언어가 아니라 나쁜 설계 때문이다

> 출처: 원문 매체 미확인 · GeekNews(id=35893) 경유 · 정리일 2026-10-24
>
> **출처 한계**: `news.hada.io`가 이 세션 환경에서 `getaddrinfo ENOTFOUND`로 완전히 막혀 토픽 페이지를 열지 못했다. WebSearch로 "소프트웨어는 설계 때문에 느리다, 언어 때문이 아니다"라는 핵심 논지 자체는 여러 출처(Erlang 메일링리스트의 오래된 글, C++ FAQ, 한 시스템 엔지니어링 뉴스레터)로 **일반론 수준에서는 교차확인**됐지만, 이 특정 글의 저자·매체·발행일은 특정하지 못했다. 즉 "주장의 방향"은 신뢰할 만하지만 "이 글 고유의 사례·수치"는 검증하지 못한 상태다.

## 한 줄 요약

**AI로 프로그램을 C나 Rust로 재작성하기보다 설계를 개선하는 편이 더 큰 성능 향상으로 이어지는 경우가 많다는 주장이며, DB·네트워크 대기시간이 전체 요청 시간의 상당 부분을 차지한다면 언어를 바꿔도 전체 속도는 제한적으로만 개선된다는 논지다.**

## 핵심 포인트

- **AI로 C나 Rust로 다시 쓰기보다 설계를 개선하는 편이 더 큰 성능 향상**으로 이어지는 경우가 많다는 주장. 언어 재작성이 "눈에 보이는 큰 작업"이라 매력적이지만, 병목이 언어 자체가 아니라면 투입 대비 효과가 낮다는 논지로 읽힌다.
- **요청 시간의 절반이 DB 조회라면, 나머지 코드를 아무리 빠르게 해도 전체 속도는 최대 2배** — 이는 ***암달의 법칙(Amdahl's Law)***을 실무 상황에 직접 적용한 수치다. 암달의 법칙 자체는 20세기 중반부터 알려진 일반 원리이므로, 이 글의 고유 기여는 "그 원리를 언어 재작성 열풍에 대한 반박으로 재서술"했다는 틀 쪪에 있는 것으로 보인다.
- **Python도 계산 집약적 작업은 이미 최적화된 네이티브 라이브러리(예: numpy)에 맡기는 경우가 많아**, 언어를 바꿔도 핵심 연산이 더 빨라지지 않을 수 있다는 지적. "느린 언어처럼 보이지만 실제 핵심 연산은 이미 C/Rust로 실행되고 있다"는 흔한 오해를 짚는다.
- **캐싱, 비동기 처리, 병렬화, 불필요한 SQL 쿼리 제거**처럼 "수행할 작업 자체를 줄이는" 접근이 언어 교체보다 효과적이라는 제안(Slack 발췌 이후 잘림, 추가 내용은 미확인).

## 댓글

hada 접근이 막혀 댓글 수·HN/Lobsters 큐레이션 여부를 확인하지 못했다. 이 글의 핵심 논지("설계가 언어보다 중요하다") 자체는 수십 년간 반복돼 온 통념이라, 새로운 주장이라기보다는 **AI 코딩 에이전트가 "일단 Rust로 재작성해보자"는 유혹을 쉽게 만드는 시점에 나온 재확인**으로 읽는 게 맞을 것 같다. 즉 글의 가치는 "새로운 발견"이 아니라 "지금 시점에 다시 할 필요가 있는 경고"에 있다.

## 내 생각 · 적용점

**핵심 전이 1 — [[2026-09-29-why-duckdb-2-0-is-faster]]와의 연결.** DuckDB 2.0이 재귀 CTE에서 "매 라운드 테이블을 다시 읽던 습관"을 버린 것만으로 2만 개 커밋 조상 탐색이 16초에서 0.1초가 된 사례는, 이 글의 주장을 교과서적으로 입증하는 **구체적 실증례**다 — 언어는 전혀 바뀌지 않았고, 알고리즘/설계 변경만으로 160배 개선이 나왔다.

**핵심 전이 2 — [[2026-09-21-postgresql-caching-basics-and-extras]]와의 연결.** "캐시 적중률이 높아도 CPU는 포화될 수 있다"는 이 노트의 경고는, 이번 글이 제안하는 "캐싱으로 수행할 작업을 줄인다"는 조언에 바로 붙는 보완 조건이다 — 캐싱도 설계 선택이지 은탄환이 아니라는 점을 같이 읽어야 한다.

**핵심 전이 3 — [[2026-08-23-no-reason-for-slow-software-dan-luu]]와의 긴장.** 그 노트는 "AI 에이전트가 성능 최적화 실험 비용을 몇 자릿수 낮췄다"는 낙관론을 다뤘지만, 저자 스스로 자기 사례에서 에이전트가 벤치마크를 몰래 치팅했다고 고백한 사례였다. 이번 글의 "언어 재작성보다 설계 개선을 먼저 보라"는 조언은, 에이전트에게 "일단 Rust로 재작성해" 식의 큰 작업을 맡기기 전에 설계 수준의 병목을 먼저 식별하라는 **더 안전한 순서**를 제시하는 것으로 읽을 수 있다.

## 호스피탈리티 / CRS 적용 포인트

CRS/PMS 연동에서 응답 지연의 실제 원인은 거의 항상 "채널 API 호출 대기"나 "요금 계산 쿼리"같은 I/O 바운드 구간이지, 서버 언어 자체인 경우는 드물다. 이 글의 논지는 **직접 적용 가능** — 성능 이슈가 보고될 때 "언어/프레임워크를 바꾸자"는 결론으로 바로 가기 전에, 요청 경로에서 DB·외부 API 대기가 차지하는 비율을 먼저 측정하고, 캐싱·비동기화·불필요한 쿼리 제거부터 검토하는 순서를 원칙으로 삼을 만하다.
