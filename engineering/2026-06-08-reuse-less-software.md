# 소프트웨어, '덜' 재사용하기 — 벤더링으로 의존성을 줄여 공급망 공격의 자동 확산을 끊자 (오픈소스 공급망 보안·도구 철학 라인)

> 출처: alopex.li wiki (GeekNews 경유) · 정리일 2026-06-08

## 한 줄 요약

**소프트웨어 배포 비용이 극도로 낮아진 시대에 *과도한 의존성 자동화*는 ***악성 변경을 CI 속도로 퍼뜨리는 통로***가 된다. 해법은 ***"덜 재사용하기"*** — 모든 의존성 소스를 프로젝트 저장소에 직접 포함(***벤더링***)하고, *자동 업데이트를 차단해 방화선*으로 삼아, 의존성 수를 *2~3개 수준*으로 제한하자. 트레이드오프는 *저장소 크기 증가*(디스크는 싸다)와 *의존성 사용 비용 상승* — 그런데 **그 "비용 상승"이 곧 *신중성*을 강제하는 기능**이다. 모든 SW에 맞진 않지만(거대 모노레포 제외), *압축·네트워크·UI 라이브러리처럼 비교적 독립적인 SW에 효과적*.**

## 핵심 포인트

- **문제 — 자동 갱신이 공격의 고속도로** — *"자동 의존성 갱신은 악성 변경이 CI 속도로 퍼지게 만든다."* 공급망 공격이 *월 단위로 발생*. **[[2026-06-08-aur-supply-chain-malware]] *AUR 408개 패키지 공격*의 정확한 방어 철학 쌍둥이** — 그 글이 *공격*이면 이 글은 *예방 설계*.
- **해법 — 벤더링 + 자동 업데이트 차단** — *의존성을 저장소에 포함*하면 *상위 저장소가 악성으로 바뀌어도 내 방화선 안*. *가시성이 늘어 불필요한 재사용이 줄어듦*.
- **"비용 상승 = 기능"** — *의존성 추가 비용이 오르면 신중해진다*. **무분별한 `npm install` 대신 "이 의존성이 정말 필요한가"를 묻게 만드는 마찰**. [[2026-06-08-static-types-and-the-shovel]] *"도구가 나쁘면 외면"*의 반대 응용 — *일부러 마찰을 둬서 남용을 막음*.
- **한계 — 만능 아님** — *거대 모노레포엔 부적합*, *libcurl 같은 적대적 입력 처리 C 라이브러리는 OS에 맡기는 게 안전*(직접 복사 금지). *적용선을 어디 긋느냐가 어려운 문제*.

## 인상 깊은 문장

> "Automatic dependency updates let a malicious change propagate at the speed of CI."
> (자동 의존성 갱신은 악성 변경이 CI 속도로 퍼지게 만든다.)

> "Raising the cost of using a dependency is a feature, not a bug — it forces deliberation."
> (의존성 사용 비용을 올리는 것은 버그가 아니라 기능이다 — 신중함을 강제한다.)

## Lobste.rs 토론 (댓글 전수 확인)

> GeekNews 댓글은 GN⁺가 Lobste.rs 토론을 큐레이션한 것. **6개 의견 클러스터를 답글까지 모두 확인:**

1. **콘텐츠 해시 고정(잠금) 절충안** — *모든 패키지를 콘텐츠 해시로 고정*하면 "상위 저장소가 악성으로 바뀜"은 막고(잠금 파일 효과), "상위가 사라짐"은 로컬 캐시 tarball로 해결. → *벤더링과 "단순·재사용 가능" 사이의 좋은 절충*. (예시로 Zig 패키지 매니저가 언급됐으나, 핵심은 *언어 무관한 콘텐츠 주소 지정·해시 고정 원리*.) **답글**: *모든 소스를 콘텐츠 주소 저장소에 두고 입력 해시로 빌드*; *공격하려면 잠금 파일 수정이나 해시 충돌 필요(둘 다 어려움)*, 단 *cargo는 전이 의존성이 조용히 따라 올라오는 게 불만*.
2. **"공급망 공격"이라는 이름 시비 + 벤더링 = 잠금 파일** — *서명된 계약 없으니 "공급망"은 아니다*. 해시 잠금 파일·Go의 *최소 버전 선택(MVS)* 도 의존성이 아래에서 안 바뀌게 보장하는 점에선 벤더링과 동일. *극단으로 가면 직접 구현·즉흥 생성 코드가 되니, **도메인 전문가가 작성·검증한 SW를 쓰는 편이 낫다***. Facebook의 서드파티 관리는 *비호환 버전 동시 최대 2개*만 허용 — *지속 가능하다고 보긴 어려움*. **답글**: *"지속 불가"는 정책보다 규모의 함수*; *Log4Shell 때 버전이 흩어진 회사가 더 고생*; *"그럼 의존성 공격이라 부르자 <3"*.
3. **"돼지도 추진력 있으면 난다"(RFC 1925)** — *Google/Facebook 관행은 그들이 충분한 추진력(전담 팀)을 댈 수 있어서만 작동*. *우리 대부분은 감당 못 함* — **대기업 베스트 프랙티스 맹신 경계**.
4. **패키지 매니저 역사 비판** — *벤더링은 의존성 비용을 올린다는 데 강하게 동의*. 단 *libcurl은 복붙 금지(OS가 더 안전)*. *apt(시스템 전체) 가 먼저 나오고 언어별 매니저가 뒤늦게 나온 게 문제의 뿌리* — rubygems가 "Ruby용 apt"를 만들려다 bundler로 수십 년 수습, *처음부터 프로젝트 격리를 인정했으면 불필요*. Python·Perl도 수습 중. **답글**: *역사적으로 패키지 매니저는 "시스템을 빌드"하는 도구였고, 웹앱·싼 디스크 시대엔 단일 프로그램 도구만 필요해짐 — 도구가 시대 변화를 못 따라감*.
5. **벤더링의 단점 — 스캐너 사각** — *복사해 온 의존성의 버그를 보안 스캐너가 감지 못함* → 알림받았을 문제가 조용히 남음. **답글**: *스캐너 오탐이 워낙 많아 오히려 장점일 수도 — 가짜 경보로 일정이 밀리는 게 더 골치*.
6. **"결국 한 바퀴 돌아 서드파티 포함 아닌가"** — 벤더링을 자동화하면 *결국 서드파티를 안 보고 포함하는 셈*. **답글**: *의미적 버전을 버리고 모든 버전을 고유·무관하게 다루면 같은 효과지만, 의존성 변조·소실 문제는 못 풀고 성급한 최적화. 시작점으로 삼지 말 것*.

→ **토론의 무게중심**: *벤더링/덜-재사용은 "은탄환"이 아니라 *트레이드오프 조정*. 핵심 합의는 ① **의존성 고정(해시 잠금)이 최소선**, ② **자동 갱신·무분별 재사용이 위험**, ③ **대기업 관행 맹신 금지**, ④ *적대적 C 라이브러리·규모 큰 경우엔 예외*.

## 내 생각 · 적용점

### 5번째 라인업 *오픈소스 공급망 보안·도구 철학 라인* (AI 축과 직교, 카운팅 무관)

AI 찬반이 아니라 *의존성 관리 철학*이다. 라인 자산(카운팅 무관). [[2026-06-08-aur-supply-chain-malware]]와 *공격·방어 짝*을 이룸 — 부채 0 유지 (46:35 ≈ 1.31:1).

### 핵심 전이 — "마찰을 일부러 두기" + "고정이 최소선"

가장 전이 가능한 두 원칙:

1. **"의존성 비용을 올리는 게 기능"** — *무분별한 재사용을 막는 의도적 마찰*. 사용자의 CRS·개인 프로젝트(PickMe·BugSip·stock-autotrader)에서 *"이 라이브러리 정말 필요한가"를 한 번 묻게 만드는 게* 공급망 표면을 줄인다.
2. **콘텐츠 해시 고정 = 최소선** — 벤더링까지 안 가도 *잠금 파일(해시 핀)·자동 업데이트 차단*만으로 [[2026-06-08-aur-supply-chain-malware]]의 *"악성이 CI 속도로 확산"*을 끊는다. **신뢰를 *이름·버전*이 아니라 *해시*로 거는 것** — 그 글의 결론과 동일.

### 에이전트 시대 — "즉흥 생성 의존성" 경고가 정확히 LLM 문제

댓글 2의 *"극단으로 가면 즉흥 생성 코드로 의존성을 만들게 되니, 도메인 전문가가 검증한 SW를 쓰는 편이 낫다"* 는 **AI 시대에 글자 그대로의 경고**다: *LLM이 그때그때 생성한 코드로 검증된 라이브러리를 대체하는 것*은 [[2026-06-01-domain-expertise-is-the-real-moat]] *도메인 전문성*·[[2026-06-08-human-attention-human-effort]] *검토 없는 AI 출력*과 정면으로 충돌. **재사용을 줄이되 "즉흥 생성"으로 줄이지 말 것** — *검증된 소수 의존성 > 무검증 자동 생성 다수*. 또 [[2026-05-09-agents-need-control-flow]]·[[2026-06-08-designing-loops-with-fable-5]] *에이전트가 자율로 `install` 실행*하는 파이프라인일수록 *벤더링·해시 고정·자동 갱신 차단*이 방화선.

### 대기업 베스트 프랙티스 맹신 경계 (RFC 1925)

*"돼지도 추진력 있으면 난다"* 는 가든의 반복 교훈과 정합 — [[2026-06-08-static-types-and-the-shovel]] *"단선적 진보 서사 경계"*처럼, **Google/FB 관행은 그들의 규모(전담 팀)에서만 작동**. 작은 팀은 *자기 규모에 맞는 단순함*이 답.
