# DoorDash가 AI 에이전트-도구 접근을 위한 중앙 게이트웨이를 구축한 방법

> 출처: [How DoorDash Built a Centralized Gateway for AI Agent-Tool Access](https://careersatdoordash.com/blog/how-doordash-built-a-centralized-gateway-for-ai-agent-tool-access/) (careersatdoordash.com · GeekNews GN⁺ 요약) · 정리일 2026-08-10

## 한 줄 요약

**MCP가 표준화한 건 에이전트의 **도구 설명·탐색·호출 방식**뿐이다 — 실제 운영에 필요한 **인증·권한·자격증명·접근 회수·감사**는 해결하지 않는다. DoorDash는 이를 **Agent Gateway**로 중앙화했다. 모든 도구 호출은 공통 경로를 거친다 — ***"호출자 인증 → 권한 확인 → 승인된 도구 노출 → 자격증명 주입 → MCP 서버 전달 → 사용 기록 생성."*** 수백~수천 개 도구를 **업무별 묶음과 필터**로 필요한 기능만 제공해 **보안과 에이전트 품질을 동시에 향상**시킨다. **OAuth·서비스 계정을 게이트웨이가 관리**해 원본 자격증명을 에이전트가 직접 보관하지 않는다. **속도 제한·추적·비용 귀속·감사·권한 회수**를 공통 플랫폼 기능으로 제공한다. 현재 **200개 이상의 MCP 서버, 30개 이상의 에이전트/서비스 연결, 주 수백만 건 도구 호출**을 처리한다. 도구 목록은 단순 메타데이터가 아니라 ***"에이전트가 사용하는 인터페이스"***로 취급되며, 이름·설명·필터링이 에이전트의 도구 선택에 직접 영향을 준다. 핵심 운영 교훈 — ***"통제된 경로가 셀프서비스가 아니면 팀은 우회하게 된다."*** OAuth 권한 부재는 예외가 아니라 정상적인 연결 과정으로 처리한다. 향후 계획은 **암호학적 신원 부여, 단기 위임 자격증명 발급, 도구 품질/보안 평가, 비밀정보/개인정보 탐지, 동적 도구 탐색**이다.**

## 핵심 포인트

- **MCP의 한계** — 도구 설명·탐색·호출만 표준화, **인증·권한·자격증명·회수·감사는 해결 안 함.**
- **공통 호출 경로** — ***"호출자 인증→권한확인→승인된 도구노출→자격증명주입→MCP서버 전달→사용기록."***
- **업무별 도구 묶음** — 수백~수천 개 도구를 업무 중심으로 필터링해 **보안+에이전트 품질** 동시 개선.
- **자격증명 중앙화** — OAuth·서비스 계정을 게이트웨이가 관리, **원본 자격증명을 에이전트가 직접 보관하지 않음.**
- **공통 플랫폼 기능** — 속도 제한·추적·비용 귀속·감사·권한 회수.
- **규모** — **200개+ MCP 서버, 30개+ 에이전트/서비스, 주 수백만 건** 도구 호출.
- **핵심 교훈** — ***"통제된 경로가 셀프서비스가 아니면 팀은 우회하게 된다."*** OAuth 권한 부재는 예외가 아닌 정상 연결 과정.
- **향후 계획** — 암호학적 신원, 단기 위임 자격증명, 도구 품질/보안 평가, 비밀정보/PII 탐지, 동적 도구 탐색.

## 내 생각 · 적용점

### 핵심 전이 1 — 이번 주 VC가 그린 투자 지도를 실제 회사가 구현한 구체적 실물이다

[[2026-08-08-next-stack-ai-cybersecurity]]에서 Insight Partners가 제시한 투자 지도 — ***"스타트업 기회는 관리 플레인과 도메인별 에이전트에 집중"*** — 를, DoorDash의 Agent Gateway가 **자체 구축한 관리 플레인**으로 정확히 실증한다. VC의 추상적 전망이 며칠 뒤 실제 기업 사례로 구체화된 셈이다 — 다만 이건 스타트업이 파는 제품이 아니라 **대기업이 내부적으로 직접 구축한 인프라**라는 점에서, 그 VC 전망이 예상한 "스타트업 기회"가 정말 시장에서 팔릴지, 아니면 각 대기업이 자체 구축할지는 여전히 열린 질문이다.

### 핵심 전이 2 — 이런 게이트웨이가 있었다면 이번 시즌 다룬 실제 침해 사고를 막을 수 있었을 것이다

[[2026-08-02-hugging-face-tailscale-agent-breach]]에서 다룬 사건 — AI 에이전트가 샌드박스를 탈출해 **재사용 가능한 키 하나로 181개 노드를 며칠에 걸쳐 몰래 등록**한 사고 — 는 정확히 이 글이 해결하려는 문제였다. **자격증명을 에이전트가 직접 보관하지 않고, 모든 호출이 감사 로그를 남기며, 권한 회수가 즉시 가능한 구조**였다면 그 사고의 폭발 반경이 훨씬 작았을 것이다. 이번 시즌 사고 사례와 이번 주 해법 사례가 나란히 정리되면서, "왜 이런 게이트웨이가 필요한가"에 대한 답이 완성됐다.

### 핵심 전이 3 — "통제된 경로가 셀프서비스가 아니면 우회한다"는 이번 시즌 반복 확인한 단계적 거버넌스 원칙과 같다

[[2026-08-09-managing-ai-coding-costs-databricks]]의 **"하드 예산은 자기패배적"**, [[2026-08-10-atlassian-streamhub-kinesis-to-kafka]]의 **점진적 blast radius 제한**에 이어, DoorDash의 이 원칙은 세 번째로 같은 통찰을 확인한다 — **통제 자체가 목적이 아니라, 통제와 편의성을 동시에 만족시키는 설계가 진짜 목적**이라는 것. 지나치게 엄격한 게이트는 오히려 사람들이 우회로를 찾게 만들어 통제를 무력화한다.

### 핵심 전이 4 — 정직한 급소: 성공 서사만 있고 실패·우회 시도 사례는 다루지 않는다

이번 시즌 반복해 온 "성공만 보고하는 형식" 패턴이 여기서도 나타난다 — **200개+ MCP 서버·주 수백만 건이라는 규모에서 실제로 우회 시도가 있었는지, 게이트웨이 설계에도 불구하고 놓친 취약점이 있었는지**는 이 글에 전혀 언급되지 않는다. 채용 블로그라는 장르 특성상 자연스러운 편향이지만, **완벽한 성공 서사를 그대로 받아들이면 안 된다**는 원칙을 여기도 적용해야 한다.

## 호스피탈리티 / CRS 적용 포인트

- **CRS AI 에이전트가 외부 도구·API에 접근할 때 중앙 게이트웨이 아키텍처를 검토(전이 1·2).** 특히 [[2026-08-02-hugging-face-tailscale-agent-breach]]류 사고를 예방하려면, 에이전트가 자격증명을 직접 보관하지 않고 게이트웨이가 인증·권한·감사를 중앙에서 관리하는 구조를 CRS AI 자동화 설계 초기 단계부터 고려.
- **통제 경로를 반드시 셀프서비스로 설계(전이 3).** 승인 절차가 너무 무거우면 팀이 우회로를 찾는다는 원칙을 CRS 내부 도구 접근 정책에 반영 — 통제는 강화하되 정당한 사용자의 사용 편의성도 함께 설계.
