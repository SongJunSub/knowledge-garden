# 일회용 VM으로 Linux에서 Windows 데스크톱 테스트 실행하기

> 출처: GeekNews 토픽 [id=35377](https://news.hada.io/topic?id=35377) (원문 외부 링크 이번 세션에서 미확인) · Slack `#개발-뉴스-dev-news` 경유 · 정리일 2026-10-15

> **출처 한계**: `news.hada.io` 원문은 egress 차단으로 열지 못했고, QA Wolf 공식 블로그(qawolf.com)에서 이 정확한 글(Windows 데스크톱 일회용 VM)도 찾지 못했다. WebSearch로 확인한 QA Wolf의 공개 기술 문서는 ***웹 테스트용 인프라***만 다룬다 — "사전에 부팅된(warm) 노드 풀을 Kubernetes가 관리하고, 수요가 몰리면 새 노드를 즉시 추가한다"는 설명과, Android 모바일 테스트는 "실행마다 새로 프로비저닝하고 끝나면 폐기하는 단기 에뮬레이터"를 쓴다는 설명이다. 이 둘은 Slack 발췌가 서술하는 "Windows VM을 테스트마다 폐기"·"Kubernetes 기기 스케줄러가 부팅·로그인 끝낸 VM 풀 관리"와 구조적으로 ***매우 유사***해, QA Wolf가 기존 웹·모바일 인프라의 같은 설계 철학을 Windows 데스크톱 테스트로 확장한 것이라는 추정은 합리적이지만, Windows 데스크톱 사례 자체를 1차 소스로 확인하지는 못했다. hada 댓글 수·HN/Lobsters 큐레이션 유무도 확인 불가.

## 한 줄 요약

**QA Wolf는 Windows 데스크톱 앱을 테스트할 때 Windows VM을 테스트 1회당 1번만 쓰고 폐기하는 구조를 쓴다 — 테스트 코드 자체는 Linux에서 실행되고, Windows 앱은 원격으로 제어된다. Kubernetes의 기기 스케줄러가 미리 부팅과 로그인을 끝낸 VM 풀을 관리해두기 때문에, 테스트는 Windows 특유의 2~3분 콜드스타트를 기다리지 않고 즉시 시작할 수 있다. 브라우저는 Playwright와 CDP로, 네이티브 앱은 WebdriverIO와 Appium으로 제어해, 하나의 테스트 흐름 안에서 브라우저 로그인부터 데스크톱 앱 검증까지 이어갈 수 있다.**

## 핵심 포인트

- **일회용 VM + 원격 제어라는 분리 구조** — Windows VM은 ***테스트마다 한 번만 쓰고 버려지며***, 테스트 코드 자체는 Windows가 아니라 ***Linux에서 실행***되고 Windows 앱은 원격으로 제어된다. 테스트 로직과 실행 환경(Windows)을 분리해, 테스트 작성·유지보수는 익숙한 Linux 기반 도구체인에서 할 수 있게 한 구조다.
- **콜드스타트를 테스트 실행 시점이 아니라 그 이전으로 밀어낸다** — Windows는 부팅·로그인에 ***2~3분***이 걸리는데, 이 시간을 테스트가 시작될 때마다 기다리는 게 아니라 ***Kubernetes의 기기 스케줄러가 미리 부팅·로그인까지 끝낸 VM 풀을 상시 관리***해둠으로써, 테스트는 그 풀에서 꺼내 쓰는 즉시 시작된다. WebSearch로 교차확인한 QA Wolf의 웹 테스트 인프라도 ***"warm, pre-booted nodes"***(사전에 부팅해둔 노드)라는 동일한 패턴을 쓴다고 설명해, 같은 설계 철학이 반복되고 있다는 걸 보여준다.
- **제어 도구의 이원화** — ***브라우저는 Playwright와 CDP(Chrome DevTools Protocol)***로, ***네이티브 Windows 앱은 WebdriverIO와 Appium***으로 제어한다. 두 도구체인이 공존하기 때문에, 하나의 테스트 시나리오 안에서 ***브라우저 로그인 → 데스크톱 앱으로 전환해 검증***하는 흐름을 이어갈 수 있다 — 예를 들어 웹에서 로그인한 뒤 그 계정으로 데스크톱 클라이언트의 동작을 확인하는 식의, 실제 사용자 여정에 가까운 테스트가 가능해진다.
- **대상 — 데스크톱 앱 테스트라는 틈새** — Slack 발췌는 QA Wolf가 이 구조로 ***데스크톱 앱 테스트***를 구현했다고 명시한다. 브라우저 테스트(Playwright)나 모바일 테스트(Appium 단독)는 이미 성숙한 도구가 많지만, Windows 네이티브 데스크톱 앱 테스트는 CI 환경에서 특히 다루기 까다로운 영역으로 꼽힌다는 점에서, 이 구조가 노리는 틈새가 분명하다.

## 인상 깊은 문장

## 댓글

**확인 불가.** hada 댓글 수·HN/Lobsters 큐레이션 유무 모두 원문 전면 차단으로 확인하지 못했다. 정직하게 감안할 점: (1) 이 노트의 원문 자체를 1차 소스로 확보하지 못해, "Windows 기본 이미지에 자동화 도..."로 끊긴 Slack 발췌의 마지막 줄이 어떤 내용인지(이미지에 미리 깔아두는 자동화 도구의 종류·설정 방식)는 확인할 수 없다. (2) QA Wolf는 ***테스트 자동화를 서비스로 판매하는 회사***이므로, 이 글이 블로그 포스팅이라면 자사 인프라의 우수성을 보여주는 홍보적 성격을 가질 수 있다 — "콜드스타트 문제를 해결했다"는 주장이 실제 운영 규모(동시 VM 풀 크기, 비용)에서도 경제적으로 성립하는지는 이 발췌만으로 판단할 수 없다. (3) VM 풀을 "미리 부팅해 대기시킨다"는 접근은 콜드스타트를 숨기는 대신 유휴 자원 비용을 치르는 트레이드오프이므로, 그 비용이 테스트 스위트 규모에 비해 합리적인지는 별도 검증이 필요한 영역으로 남겨둔다.

## 내 생각 · 적용점

### 핵심 전이 1 — [[2026-10-11-microsoft-mxc-sandbox-execution]]이 다룬 "격리 강도의 스펙트럼"과 QA Wolf의 선택은 정반대 축에 있다

MXC 노트는 "신뢰할 수 없는 코드를 격리 실행하려면 가벼운 프로세스 샌드박스부터 VM까지 격리 강도를 선택할 수 있어야 한다"는 걸 핵심 설계 원칙으로 짚었고, 그 선택의 동기는 ***보안***(에이전트가 만든 코드를 안전하게 가두는 것)이었다. QA Wolf의 Windows VM은 같은 "VM 단위 격리"라는 메커니즘을 쓰지만 동기가 다르다 — 여기서 VM을 매번 폐기하는 이유는 보안 격리가 아니라 ***테스트 간 상태 오염을 막는 재현성(reproducibility)***이다. 두 사례를 나란히 놓으면, "VM을 일회용으로 쓴다"는 같은 패턴이 ***신뢰할 수 없는 입력을 가두는 보안 문제***와 ***깨끗한 초기 상태를 보장하는 테스트 문제***라는 서로 다른 동기에서 독립적으로 수렴한다는 걸 보여준다 — 격리의 "강도"보다 "일회성"이 두 문제 모두에서 공통으로 요구되는 속성이라는 뜻이다.

### 핵심 전이 2 — [[2026-09-30-yogiyo-product-engineer-verification-bottleneck]]이 말한 "검증이 진짜 병목"이라는 진단의 구체적 인프라 사례

요기요 노트는 "AI가 코드를 짜는 시대에 진짜 병목은 코드 작성이 아니라 검증"이라며 단위/통합/E2E 테스트의 병렬화·시각 회귀 테스트 같은 CI 인프라 투자를 실증 사례로 들었다. QA Wolf의 "미리 부팅해둔 VM 풀 + Kubernetes 스케줄러"는 그 검증 병목을 ***데스크톱 앱이라는 더 다루기 어려운 영역***에서 어떻게 풀었는지 보여주는 구체적 사례다 — 요기요가 "병렬화로 검증 속도를 높인다"는 원칙을 웹 E2E 테스트에 적용했다면, QA Wolf는 같은 원칙(상시 준비된 자원 풀)을 Windows라는 콜드스타트가 특히 느린 플랫폼에 적용한 것으로, "검증 자동화에는 사람의 설계와 인프라 투자가 필요하다"는 같은 명제를 다른 플랫폼에서 재확인시킨다.

## 호스피탈리티 / CRS 적용 포인트

CRS가 Windows 데스크톱 앱(예: PMS 연동 클라이언트, 프런트데스크용 레거시 윈도우 프로그램)을 직접 만들거나 연동 테스트를 해야 하는 경우가 있다면, 이 구조는 구체적으로 참고할 만하다. **다만 직접 적용 가능성은 CRS가 실제로 Windows 네이티브 앱을 테스트 대상으로 갖고 있는지에 전적으로 달려 있고, 그 전제가 지금 확인되지는 않는다.**

- **전이 가능한 원칙** — ①***"콜드스타트를 테스트 실행 시점이 아니라 그 이전으로 밀어낸다"***는 설계는, CRS의 E2E 테스트나 스테이징 환경 초기화가 느리다면(예: 예약 시스템 전체 스택 기동) 그대로 적용할 수 있는 원칙이다 — 매 테스트 실행 전에 환경을 처음부터 올리는 대신, 미리 준비된 "웜" 환경 풀을 관리하는 쪽으로 전환하면 체감 테스트 속도가 크게 개선될 수 있다. ②***"테스트 코드는 익숙한 플랫폼에서, 실행 대상만 다른 플랫폼에 두고 원격 제어한다"***는 분리 구조는, CRS가 OTA·GDS 연동처럼 외부 레거시 환경을 다뤄야 할 때 테스트 작성 난이도를 낮추는 참고 패턴이 된다.
- **직접 적용은 신중해야 한다** — 온다 CRS가 Windows 데스크톱 앱을 테스트 대상으로 갖고 있다는 전제가 이 노트에서 확인되지 않았으므로, 이 구조 자체를 "도입 검토"할 근거는 아직 약하다. 원칙만 참고하고, 실제 적용은 CRS의 테스트 대상이 Windows 네이티브 환경을 포함하게 될 때로 미루는 게 정직하다.
