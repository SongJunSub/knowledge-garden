# 하네스가 프롬프트를 읽기도 전에 태우는 토큰 — Claude Code 33k vs OpenCode 7k, 그러나 진짜 교훈은 '벤더 숫자 말고 내 경계에서 직접 계측하라'

> 출처: [Claude Code Sends 4.7x More Tokens Than OpenCode Before Reading Your Prompt](https://systima.ai/blog/claude-code-vs-opencode-token-overhead) (Systima) · 정리일 2026-07-13

## 한 줄 요약

**동일 모델·머신·작업에서 API 경계를 프록시로 계측하니, 프롬프트가 도착하기도 전의 고정 오버헤드가 Claude Code 약 32,800토큰 / OpenCode 약 6,900토큰(4.7배)이었다. 격차의 주범은 시스템 프롬프트가 아니라 도구 스키마다(CC 27개 도구 = 24k 토큰). 다만 저자 스스로 헤드라인을 무력화한다 — 병렬 도구 배치를 하면 총합이 역전되고, 실제 사용자 설정에서는 MCP를 잔뜩 붙인 OpenCode가 오히려 더 많이 보냈다. 그래서 결론은 벤더 선택이 아니라 "지난 화요일에 우리가 모델에 정확히 무엇을 보냈는가"에 답할 수 있게 만들라는 운영 원칙이다.**

## 핵심 포인트

- **고정 오버헤드** — 22자짜리 프롬프트에도 CC ~32,800 / OC ~6,900 토큰. Fable 5에서는 CC가 모델별로 프롬프트를 줄여 격차가 3.3배로 축소.
- **주범은 도구 스키마** — CC 27개 도구 = 99,778자(약 24k 토큰), OC 10개 = 20,856자(4.8k). CC 도구에는 코딩과 무관한 오케스트레이션(Cron, Monitor, Task, 푸시 알림)까지 포함돼, 안 쓰는 세션에도 매번 전송된다.
- **하위 에이전트는 4.2배 곱셈기** — 직접 실행 121k → 서브에이전트 둘로 분산하니 513k. 각 서브에이전트가 자기 시스템 프롬프트 + 24개 도구를 다시 부트스트랩하고, 부모가 그 실행 기록을 다시 읽는다.
- **캐시 안정성이 진짜 차이** — OpenCode는 캡처한 모든 실행에서 접두부가 **바이트 단위로 동일**(재실행 캐시 쓰기 0). Claude Code는 43k 접두부를 **세션 중간에 통째로 재기록**해 캐시 쓰기가 5.9~54배. 같은 내용을 프리미엄 가격에 재구매하는 셈.
- **컨텍스트 창 점유는 캐시 할인을 받지 않는다** — 85k 부트스트랩이면 200k 창의 40%를 이미 먹고 시작한다.
- **조용한 실패** — Claude Code 2.1.207은 `AGENTS.md`를 **무시**했다(`CLAUDE.md`로 바꿔야 인식). print 모드는 `--mcp-config` 없이는 `.mcp.json`을 조용히 무시한다. 에러도 경고도 없다.
- **반전 ① 작업 형태에 따라 총합이 역전된다** — T3(작성·실행·테스트·수정)에서 CC는 병렬 배치로 3회 요청/121k, OC는 직렬 9회/132k.
- **반전 ② 내 설정이 벤더 기본값보다 큰 변수** — 실제 구성에서 MCP 11개 + 72KB 명령 파일을 붙인 **OpenCode가 90,817토큰**, Claude Code가 **약 75,000토큰**이었다. MCP 서버 하나당 요청마다 1,000~1,400토큰이 붙는다.
- **품질은 측정하지 않았다** — 두 하네스 모두 과제를 정확히 완료했고, "추가 비용만큼 품질이 오르는가"는 열린 질문으로 남겼다.

- **토큰 인플레이션** — "'Hey'나 'commit' 같은 프롬프트가 때때로 30회 넘는 도구 호출을 일으켰다."

## 내 생각 · 적용점

### 핵심 전이 1 — "블랙박스를 계측하라"가 이 글의 유일하게 오래 남을 교훈

33k vs 7k는 다음 버전이면 바뀌는 숫자다. 오래 남는 건 저자의 마지막 문장이다 — **"프로덕션에서 에이전트를 돌리는데 '지난 화요일에 모델에 정확히 무엇을 보냈는가'에 답할 수 없다면, 그게 가장 먼저 메워야 할 구멍이다."** 200줄짜리 Node 프록시 하나면 답할 수 있는 질문을 대부분의 조직이 답하지 못한다. 이건 AI 이전부터 있던 관측가능성 원칙의 재발견이고, 핵심은 **공급자가 제공하는 대시보드는 공급자가 보여주고 싶은 것만 보여준다**는 것이다. 어제 정리한 [[2026-07-13-own-the-outer-loop]]의 "역압 = 기존 신호를 에이전트 정지 장치로 재배치"와 같은 계열 — 계측 없이는 역압도 없다.

### 핵심 전이 2 — 서브에이전트의 곱셈 효과 = 오케스트레이션 세금의 재확인

121k → 513k(4.2배). 각 서브에이전트가 부트스트랩을 다시 내고, 부모가 결과를 다시 읽고, 그사이 캐시는 만료된다. 이건 [[2026-05-29-orchestration-tax]]가 말한 "오케스트레이션 세금"이 토큰 회계로 정확히 측정된 사례이며, 근본적으로는 **분산 시스템의 오래된 교훈**(통신 오버헤드가 병렬 이득을 잡아먹는 지점이 반드시 있다)의 반복이다. "일을 나누면 싸진다"가 아니라 **"나누는 비용이 나누는 이득을 넘는 지점이 있다."** 나도 이 세션에서 서브에이전트를 병렬로 쓰고 있으니, 남 얘기가 아니다 — 리서치처럼 **결과만 회수하면 되는 작업**엔 유효하지만, 맥락을 계속 공유해야 하는 작업에선 순차가 낫다.

### 핵심 전이 3 — "미니멀리즘 ≠ 효율성", 그리고 "내 설정이 벤더 기본값보다 큰 변수"

이 글의 가장 정직한 두 지점이자, 헤드라인만 보고 넘어가면 놓치는 부분이다. **나쁜 도구는 왕복 호출을 늘려 초기에 아낀 토큰을 전부 지운다** — 프롬프트 크기가 아니라 도구의 품질이 총비용을 정한다. 그리고 실제 설정에서는 **MCP 11개를 붙인 OpenCode(90,817)가 Claude Code(75,000)보다 더 많이 보냈다.** 즉 벤더를 탓하기 전에 **내 MCP 목록과 CLAUDE.md 크기부터 보라**는 뜻이다. [[2026-05-29-mcp-is-dead-cli-skills]]가 지적한 MCP 오버헤드가 숫자로 확인됐고(서버당 요청마다 1,000~1,400토큰), [[2026-07-12-good-tools-are-invisible]]의 "학습 곡선은 비용" · "무한 설정은 결정을 떠넘기는 변명"과도 이어진다.

### 핵심 전이 4 — 조용한 실패가 가장 비싸다 (그리고 캐시 안정성 = 마진)

`AGENTS.md`를 조용히 무시해서 그 파일에 쏟은 노력이 **0의 효용**을 냈다는 사례는 에러도 경고도 없이 일어난다. **설정 파일을 썼는데 실제로 읽히는지 확인하지 않는 것**은 AI 도구만의 문제가 아니라 모든 설정 기반 시스템의 보편적 함정이다. 그리고 "바이트가 동일한 43k 접두부를 세션 중간에 재기록"은 오늘 정리한 [[2026-07-13-how-an-ai-token-travels-through-a-data-center]]의 **"캐시 적중률이 곧 마진"**과 정확히 같은 이야기다 — 캐시 안정성은 성능 최적화가 아니라 **원가 구조**다. [[2026-07-13-how-to-kill-churn]]의 "높은 이탈 × 낮은 총마진 = 급락"까지 이으면, 하네스의 캐시 불안정은 AI 제품 원가표에 그대로 얹히는 항목이다.

### 핵심 전이 5 — 관측가능성이 컴플라이언스 의무가 되기 시작한다

저자가 감사 기록을 SHA-256 해시 체인으로 남기고 **"EU AI Act Article 12 로깅과 동일한 구조"**라고 명시한 건 부수적 디테일이 아니다. "모델에 무엇을 보냈는지 재구성할 수 있어야 한다"는 요구는 곧 비용 최적화가 아니라 **규제 의무**가 된다. 토큰 회계는 그 부산물로 따라온다. [[2026-07-13-own-the-outer-loop]]의 Answerability(설명 책임)가 규제 언어로 번역된 형태다.
