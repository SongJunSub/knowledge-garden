# 모든 코드를, 항상 다시 작성하라 (Adam Chlipala) — 명세가 코드보다 오래 산다

> 출처: [Rewrite All The Code, All The Time](https://stng.substack.com/p/rewrite-all-the-code-all-the-time) (stng.substack.com, Adam Chlipala · GeekNews GN⁺ 요약 + 직접 댓글) · 정리일 2026-08-10

## 한 줄 요약

**AI 코드 생성 비용이 계속 떨어지면, ***"프로덕션 코드를 희소한 자산으로 유지할 이유가 사라진다"***는 게 이 글의 출발점이다 — ***"주요 코드베이스를 지속적으로 재구현하는 비용이 오늘날 SaaS 구독 수준까지 떨어지는 지점에 도달할 것."*** 저자는 1960년대 고급 언어 도입 때도 같은 우려가 있었다는 역사적 선례를 든다 — 추상화 수준은 계속 상향돼 왔다는 것. 핵심 모델 — ***"우리가 확보할 수 있는 가장 높은 수준의 요구사항 기술을 저장하고, 나머지는 도구가 신뢰성 있게 자동화한다."*** 저장소엔 코드 대신 **요구사항의 최상위 기술**을 보관하고, 보안·성능 요구사항이 바뀌면 명세를 수정해 재생성하며, 더 나은 알고리즘이 발견되면 자동 재생성으로 전체 코드베이스에 적용한다. 정부 발주에 비유한다 — 명세 작성 계약자와 구현 계약자를 분리하되, ***"요구사항을 충분히 모호하지 않게 포착하면 그걸 충족하는 어떤 프로그램도 받아들일 수 있다."*** 그런데 현재의 EARS(Easy Approach to Requirements Syntax) 같은 형식 기법도 부분적이라고 비판한다 — 키워드(WHILE, WHEN, SHALL)로 구조화하지만 ***"나머지 모든 문구는 여전히 자유형식 자연어로 남아, 그 모든 모호성을 그대로 안고 있다."*** 저자는 ***"자연어 명세로부터 프로덕션 시스템을 완전 자동 생성하는 건 아마 영원히 불가능할 것"***이라 인정한다 — 딥러닝은 근본적으로 ***"강화된 검색 엔진"***일 뿐이고, 성능 병목이 있으며, 딥러닝 기반 시스템이 요구사항을 항상 충족한다는 걸 수학적으로 증명하는 게 불가능할 수도 있다는 것 — 완전 자동화에는 **형식 기법 기반의 논리적 패러다임**이 필수라는 결론이다.**

## 핵심 포인트

- **핵심 전제** — ***"재구현 비용이 SaaS 구독 수준까지 떨어질 것."*** 역사적 선례: 1960년대 고급 언어 도입 때도 같은 우려.
- **핵심 모델** — ***"가장 높은 수준의 요구사항 기술을 저장, 나머지는 도구가 자동화."*** 요구사항 변화 시 명세 수정→재생성. 새 알고리즘 발견 시 자동 재생성.
- **정부 발주 비유** — 명세 작성자와 구현자 분리, ***"명확한 명세면 어떤 구현도 수용 가능."***
- **형식 기법의 필요성** — 현재 EARS도 부분적 — ***"키워드 외 나머지는 여전히 자유형식 자연어, 모호성 그대로."*** 해법은 **명확한 형식 의미론을 가진 언어**로 전체 명세 작성.
- **완전 자동화의 한계 인정** — ***"자연어 명세로부터 완전 자동 생성은 아마 영원히 불가능."*** 딥러닝은 ***"강화된 검색 엔진"*** — 성능 병목·수학적 증명 불가능성. 완전 자동화엔 **형식 기법 기반 논리 패러다임** 필수.
- **핵심 결론** — ***"코드는 실제로 오래 사는 아티팩트의 일회성 자동 부산물이 될 것."*** ***"재생성 사이클 중 인간 감독 필요성을 절대적으로 최소화하도록 모든 걸 설계하는 게 핵심 — 형식 기법만이 그 도전에 걸맞아 보인다."***

## 내 생각 · 적용점

### 핵심 전이 1 — 이틀 전 정리한 "8줄 컨텍스트 파일"이 이 비전의 축소 실물이다

[[2026-08-09-eight-line-context-file]]에서 다룬 8줄 지침 — ***"에이전트가 알면서도 하지 않는 행동"***만 담은 압축된 규범 — 은 정확히 Chlipala가 말하는 ***"가장 높은 수준의 요구사항 기술"***의 실물 축소판이다. 코드베이스 자체는 얼마든지 재작성 가능하다는 전제 아래, **살아남아야 할 건 "이렇게 만들라"는 소수의 원칙뿐**이라는 것 — 8줄이라는 극단적 압축 사례가 이 글의 거대한 비전을 구체적으로 보여준다.

### 핵심 전이 2 — "코드=일회성 부산물"은 "소스=확장 시스템"이라는 다른 낙관과 정면으로 부딪힌다

[[2026-08-04-devtools-must-be-open-source]]에서 David Crawshaw가 그린 미래 — **소스 코드 자체가 확장 시스템**이 되어, 사용자가 직접 포크·수정하는 게 새로운 표준이 된다 — 는 **코드가 여전히 의미 있는 장기 자산**이라는 전제 위에 있다. Chlipala의 비전은 정반대다 — **코드는 언제든 버리고 다시 뽑아낼 수 있는 부산물**이고, 진짜 자산은 명세다. 같은 시즌에 정리한 두 개의 "AI가 소프트웨어 비용을 붕괴시킨다"는 낙관이, **정확히 무엇이 오래 살아남는 자산인가**(소스 코드 vs 명세)에서 서로 다른 결론에 도달한다.

### 핵심 전이 3 — bhryan의 도전은 결국 이번 주 안목 스레드의 "선택과 삭제" 문제로 되돌아간다

bhryan의 질문 — "명세가 곧 코드 아닌가" — 이 진지하다면, 형식화가 아무리 정교해져도 **"무엇을 명세할 것인가"라는 선택은 여전히 사람의 몫**으로 남는다. [[2026-08-08-taste-is-all-thats-left]]에서 다룬 ***"희소한 행위는 만들기가 아니라 고르기"***라는 원칙을 여기 적용하면, Chlipala의 비전이 완성되더라도 **"어떤 명세를 쓸 가치가 있는가"를 판단하는 안목**은 자동화되지 않는다 — 명세 작성이 코드 작성을 대체해도, 그 위에 또 다른 안목의 층위가 필요하다는 무한 회귀가 남는다.

### 핵심 전이 4 — 정직한 급소: 저자 스스로의 회의와 hanje3765의 "새롭지 않다"는 지적이 이 비전의 한계를 정확히 짚는다

저자 스스로 ***"자연어 명세로부터 완전 자동 생성은 아마 영원히 불가능"***하다고 인정한다는 게, 이 글에서 가장 정직한 대목이다. 그리고 hanje3765의 지적 — ***"tidy first와 큰 차이 없는 듯"*** — 은 이번 시즌 반복해 온 원칙을 정확히 적용한다: **새로운 어휘(재생성·형식 명세)로 포장됐지만, 핵심 실천(요구사항을 명확히 하고 코드를 갈아엎을 수 있게 유지)은 소프트웨어 공학이 오래전부터 알던 원칙일 수 있다.**

## 호스피탈리티 / CRS 적용 포인트

- **CRS 레거시 시스템 마이그레이션 계획에 "명세 우선" 접근을 시범 검토(전이 1).** 오래된 코드를 그대로 유지보수하기보다, 핵심 요구사항을 먼저 명확히 문서화한 뒤 필요시 전면 재생성하는 전략의 비용-편익을 비교.
- **"명세=코드"라는 bhryan의 질문을 팀 내부 논의로 가져가기(전이 3).** CRS 요구사항 문서를 얼마나 형식화할지 논의할 때, "이게 결국 코드를 다른 언어로 쓰는 것 아닌가"라는 질문을 명시적으로 검토.
