# 소프트웨어 팩토리가 실패하는 이유 (humanlayer / ACE) — 보상 함수에 '유지보수성'이 없다

> 출처: [Why Software Factories Fail](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md) (humanlayer, *Advanced Context Engineering for Coding Agents* 저장소 · GeekNews GN⁺ 요약 + HN 큐레이션) · 정리일 2026-07-25

## 한 줄 요약

**"컨텍스트 엔지니어링"과 하네스를 제대로 만들면 무인 소프트웨어 팩토리(lights-off factory)가 된다는 기대에 대한 정면 반박이다. 논지는 하네스의 문제가 아니라 모델 학습의 구조적 한계다 — 코딩 모델의 RL은 초~분 단위로 확인 가능한 신호(테스트 통과)만 최적화하고, 몇 달 뒤에 드러나는 설계 비용은 보상 함수에 아예 들어 있지 않다. *"유지보수성을 갉아먹은 데 대한 페널티가 없다."* SWE-bench도 같은 결함을 공유한다: ~15분짜리 작업 단위를 FAIL_TO_PASS/PASS_TO_PASS 이진으로만 채점하니, 과도한 try/catch·무분별한 타입 캐스트로 테스트만 통과시키는 변경이 만점을 받는다. *"테스트는 수초 안에 피드백을 주지만, 나쁜 아키텍처의 비용 함수는 몇 주 단위로 측정된다."* 그리고 결정적 순환 논증: *"모델이 좋은 코드와 나쁜 코드를 확실히 구분할 수 있었다면, 애초에 좋은 쪽을 썼을 것이다."* — 그러니 "AI 리뷰어를 붙이면 되지"는 답이 아니다. 실측(Faros AI)은 이미 그 부채를 보여준다: 리뷰 코멘트 +25%, 코멘트 길이 +22.7%, **검토 없이 병합된 PR +31.3%**, 그리고 프로덕션에서 **PR당 인시던트 +242.7%**, 월간 인시던트 +57.9%, 개발자당 버그 +54%. 코드베이스 건강성은 보통 에이전트 도입 **3~6개월 뒤** 무너진다. 저자의 결론은 체념이 아니라 재배치다 — 모델의 제약을 인정하면 10~100배가 아니라 **2~3배**가 정직한 기대치이고, 남는 지렛대는 코드 생성이 아니라 상류의 계획이다: Product Review → System Architecture → Program Design → Vertical Slices 4단계. *"30분의 계획이 몇 시간의 리뷰를 아낀다."* 그리고 지금으로선 **코드를 읽어야 한다**는 불편한 사실을 수용하라고 한다.**

## 핵심 포인트

- **문제는 하네스가 아니라 보상 함수다** — 코딩 모델의 RL은 *"수백만 번의 루프, 수주~수개월"* 규모로 돌면서 **빠르게 검증 가능한 신호**(테스트 통과)를 최적화한다. 3개월 뒤 드러나는 설계 비용은 그 루프 안에 들어올 방법이 없다. ***"유지보수성을 갉아먹은 데 대한 페널티가 없다."***
- **시간 척도의 불일치가 핵심** — ***"테스트는 수초 안에 피드백을 주지만, 나쁜 아키텍처의 비용 함수는 몇 주 단위로 측정된다."*** 어떤 하네스도 이 간극을 학습 신호로 바꿔줄 수 없다.
- **SWE-bench는 이 결함을 재생산한다** — ~15분 작업 단위, FAIL_TO_PASS/PASS_TO_PASS **이진 평가**. 코드 품질을 악화시키는 변경(과도한 try/catch, 타입 캐스트로 컴파일 통과)도 만점이 나온다. *벤치마크가 측정하지 않는 것은 모델이 배우지 않는다.*
- **"AI 리뷰어를 붙이자"는 순환 논증** — ***"모델이 좋은 코드와 나쁜 코드를 확실히 구분할 수 있었다면, 애초에 좋은 버전을 썼을 것이다."*** 판별기와 생성기가 같은 모델이면 판별기는 새 정보를 못 준다.
- **실측 부채 (Faros AI)** — 리뷰 코멘트 **+25%**, 코멘트 길이 **+22.7%**, ***검토 없이 병합된 PR +31.3%***. 프로덕션: ***PR당 인시던트 +242.7%***, 월간 인시던트 **+57.9%**, 개발자당 버그 **+54%**. 즉 **생성은 빨라지고 검증은 오히려 밀리고 있다.**
- **붕괴는 늦게 온다** — 코드베이스 건강성 악화는 대체로 **3~6개월 뒤** 표면화. 초기 처리량 지표는 좋아 보인다.
- **정직한 기대치는 2~3배** — *"모델은 어떤 건 잘하고 어떤 건 못한다. 그 제약을 감안해 프로세스를 어떻게 최적화할 것인가?"* 10~100배 서사를 버리면 남는 건 **안전한 2~3배**.
- **대안 = 상류 4단계 계획**
  1. **Product Review** — 사용자 문제 정의, 성공 지표, 목업으로 시각화
  2. **System Architecture** — 서비스·엔드포인트·스키마 관계, 시퀀스 다이어그램·API 계약
  3. **Program Design** — 타입·메서드 시그니처·콜 스택, 콜 트리/파일 구조 다이어그램
  4. **Vertical Slices** — 스택 레이어 순서가 아니라 **기능 단위**로 잘라, 각 조각마다 테스트·리뷰 가능하게
  → ***"30분의 계획이 몇 시간의 리뷰를 아낀다."***
- **수용해야 할 불편한 진실** — *지금으로서는 코드를 읽어야 한다.* 인간의 코드 리뷰와 제품·아키텍처 검토는 제거 대상이 아니라 **재작업을 줄이는 장치**다.

## 내 생각 · 적용점

### 핵심 전이 1 — 어제의 [[2026-07-24-software-factories-light-and-dark]]와 같은 결론, 다른 증명

Addy Osmani가 **비유**(다크 팩토리·이해 부채·생성은 넓은 입구/검증은 좁은 목)로 도달한 곳에, 이 글은 **메커니즘**으로 도달한다. Osmani가 "왜 다크 팩토리는 늦게 무너지나"를 *이해 부채*로 설명했다면, 여기서는 그 부채가 왜 **모델 쪽에서 구조적으로 갚아지지 않는지**를 RL 보상 함수의 시간 척도로 설명한다. 두 글을 겹치면 이렇게 된다:

> 생성은 초 단위로 보상되고, 검증은 주 단위로 비용이 발생한다. 학습 루프에 들어올 수 있는 건 앞엣것뿐이다. 그래서 **뒤엣것은 영원히 사람 몫으로 남는다** — 적어도 보상 설계가 바뀌기 전까지는.

이건 [[2026-07-14-understanding-is-the-new-bottleneck]]·[[2026-07-13-own-the-outer-loop]]가 말한 *"인간에게 남는 건 품질·판정·설명 책임"*의 **근거 제시**다. 그동안 "왜 남는가"는 다소 규범적 주장("사람이 봐야 한다")이었는데, 이 글은 그걸 *"보상 함수에 없으니까"*라는 기술적 이유로 바꾼다. 훨씬 반박하기 어렵고, 훨씬 쓸모 있다.

### 핵심 전이 2 — "벤치마크가 측정하지 않는 것은 학습되지 않는다"는 KPI의 법칙 그 자체

SWE-bench 비판(*이진 통과/실패, 15분 단위*)은 소프트웨어 조직의 KPI 병리와 **정확히 같은 구조**다. 이번 배치의 [[2026-07-25-nothing-works-and-everyone-is-euphoric]]가 말하는 *"안정성 향상은 KPI나 발표 자료에서 돋보이기 어려워 기업은 새 기능을 우선한다"*는, 이 글의 *"유지보수성엔 페널티가 없다"*와 **동일한 문장의 조직판**이다. 모델도 조직도 **측정되는 것만 최적화한다.**

여기서 실무 결론이 하나 나온다 — **에이전트 도입 성과를 PR 수/머지 속도로 재면, 정확히 Faros가 측정한 그 곡선을 재현하게 된다**(생성 +, 검토 없이 병합 +31.3%, 인시던트 +242.7%). 재야 할 지표는 *변경 리드타임*이 아니라 **변경 실패율·롤백률·3개월 뒤 결함 밀도**다. [[2026-07-14-on-data-quality-basics]]가 데이터에 대해 말한 것과 같다: 측정 정의가 결과를 만든다.

### 핵심 전이 3 — 4단계 계획은 이미 내 방법론(strict.md)이 하고 있는 것 = 사후 검증

Product Review → System Architecture → Program Design → Vertical Slices는 내가 쓰는 mangolove 워크플로우와 놀랍도록 겹친다: **Spec → Spec 적대적 리뷰 → Product 리뷰 → Engineering 리뷰 → 승인 → 작은 편집 루프**. 특히 두 지점이 그대로 대응한다.

- **Vertical Slices ↔ "작은 편집 루프 — 한 번에 하나"**: 스택 레이어 순서(DTO 전부 → Repository 전부 → …)가 아니라 **기능 하나가 끝까지 관통**하도록 자르고, 조각마다 검증. 이건 내 규칙의 "새 API 추가: DTO → Repository → Service → Controller → 테스트(각 사이클)"보다 오히려 더 강한 주장이다 — 레이어 순서로 자르면 **끝까지 가기 전엔 아무것도 검증할 수 없다**. 이 부분은 내 분할 기준을 수정할 가치가 있다: *레이어 사이클이 아니라 수직 슬라이스 사이클로.*
- **"30분 계획 = 몇 시간 리뷰 절감" ↔ Medium/Large 트랙의 Spec 단계**: 그동안 "무겁다"고 느낀 Spec 단계에 **정량적 정당화**가 생겼다. 반대로 Trivial/Small 트랙에서 Spec을 건너뛰는 것도 이 글이 지지한다 — 15분짜리 작업엔 15분짜리 계획이 과하다.

### 핵심 전이 4 — 정직한 급소: "2~3배"는 겸손이 아니라 **판매 가능한 숫자**다

이 글의 가장 실용적인 문장은 벤치마크 비판이 아니라 **"2~3배"**다. [[2026-07-06-zuckerberg-agentic-slower-than-expected]]·[[2026-07-06-ai-margin-collapse-glm-5-2]]류의 기대 조정 흐름과 같은 방향인데, 여기선 *왜* 2~3배인지가 붙어 있다(생성만 빨라지고 검증은 그대로니까 — 암달의 법칙의 소프트웨어 프로세스판). 조직에 AI 도입을 제안할 때 **10배를 약속하면 6개월 뒤 인시던트 그래프로 반박당한다**. 2~3배 + "검토는 그대로 든다"를 약속하면 지킬 수 있고, 지키면 다음 예산이 나온다.

단, 이 글이 **스스로 인정하지 않는 한계**도 있다: 저자가 제안하는 4단계 계획 자체가 *"인간이 상류를 지킨다"*는 전제에 의존한다. 만약 계획 단계마저 에이전트에게 넘긴다면(그리고 많은 팀이 그러고 있다) 같은 보상 함수 문제가 한 층 위로 이동할 뿐이다. [[2026-07-19-human-in-the-loop-is-tired]]가 지적한 대로, *"사람을 루프에 넣는다"*는 말은 **사람이 실제로 무엇을 판단하는지**를 명시하지 않으면 알리바이가 된다.

## 호스피탈리티 / CRS 적용 포인트

온다(B2B 호스피탈리티/CRS)는 이 글의 경고가 **가장 아프게 적용되는 유형의 시스템**이다 — 예약·요금·재고·정산은 결함이 3개월 뒤가 아니라 *다음 체크인에* 드러나고, 비용이 코드가 아니라 **사업자 신뢰**로 청구된다.

- **에이전트 성과 지표를 바꾼다.** PR 수·머지 속도가 아니라 **변경 실패율 / 롤백률 / 배포 후 24h 인시던트 / 3개월 후 결함 밀도**. Faros 곡선(검토 없이 병합 +31.3% → 인시던트 +242.7%)이 그대로 재현되는지가 우리 조직의 조기 경보다.
- **"검토 없이 병합"의 실제 비율을 먼저 재본다.** 이 글이 준 가장 값싼 액션이다 — 최근 3개월 PR 중 리뷰 코멘트 0개로 머지된 비율을 뽑아보면, 우리가 다크 팩토리 쪽으로 얼마나 갔는지 한 숫자로 나온다.
- **Vertical Slice를 CRS 도메인에 맞춰 정의.** "요금 정책 1개가 조회→계산→예약→정산까지 관통"을 한 슬라이스로. 레이어별로 쌓으면 **정산까지 도달하기 전엔 아무것도 검증할 수 없고**, 그게 이 도메인에서 가장 비싼 실수다.
- **LLM 위임 경계와 정확히 겹친다.** 결제 금액·재고/객실 할당·권한 판정은 *"테스트만 통과시키는 변경"*이 가장 위험한 지점이다 — 여기는 결정적 코드 + dry-run이고, 에이전트에게 넘길 곳은 상류의 탐색·초안·리팩토링 후보 추출이다([[2026-07-15-wrapping-the-unpredictable-genius]]의 "예측 불가능한 천재를 결정적 껍데기로 감싸라"와 같은 결론).
- **상류 4단계를 우리 트랙 정의에 반영.** Medium/Large의 Spec에 *"수직 슬라이스 분할과 각 슬라이스의 완료 기준"*을 명시 항목으로 추가할 값어치가 있다.
