# Linus Torvalds, Claude Code로 Linux 커널의 대폭 개선 작업 진행 중

> 출처: [GeekNews GN⁺ 요약](https://news.hada.io/topic?id=35265) (저자·원문 매체 미특정) · 정리일 2026-10-13
>
> **출처 한계 — 원문 미확인, 그러나 부분 교차확인.** `news.hada.io` 이번 세션 전면 차단으로 원문을 열람하지 못했다. 대신 WebSearch로 "folio refcount scalability" 계열을 검색해, **기술적 설명(여러 스레드가 한 파일을 조금씩 읽을 때 folio 참조 카운팅 경합이 병목이 된다)과 거의 정확히 일치하는 실제 LKML 패치 시리즈**를 찾았다 — Ilya Gladyshev의 `[PATCH] mm: improve folio refcount scalability`(RFC는 2026-01, v6은 2026-09-12 게시, CAS 루프를 낙관적 증가로 대체). 다만 **이 패치 시리즈의 주저자는 Gladyshev이고, Torvalds는 2026년 초 직접 cmpxchg 변형을 실험하며 "lock bit" 방식이 최선이라 판단하고 `Acked-by`를 남긴 역할**로 확인된다 — 즉 WebSearch로 찾은 실제 스레드에서는 ***Torvalds가 패치를 직접 작성·주도한 게 아니라 검토·어크(ack) 역할***이었고, **Claude Code 사용 여부는 이 스레드 어디에서도 독립적으로 확인하지 못했다.** 따라서 Slack 발췌의 "토발즈가 Claude Code를 활용해 직접 지휘"라는 프레이밍이 이 실제 스레드를 가리키는 것인지, 그 이후(9월 이후) 별도로 Torvalds가 자신의 실험 코드에 Claude Code를 쓴 다른 작업을 가리키는 것인지는 **단정할 수 없다.** 아래 요약은 이 불확실성을 전제로 Slack 발췌를 기반으로 작성했다.

## 한 줄 요약

**Linus Torvalds가 Claude Code를 활용해, 여러 스레드가 한 파일을 조금씩 동시에 읽을 때 Linux 커널 페이지 캐시에서 발생하는 folio 참조 카운팅 경합 병목을 개선하는 작업을 진행했다는 소식 — 코드·테스트 프로그램 작성, 검토, 패치 소개문 초안 작성에 LLM 코딩 보조 도구를 썼고, 직접 지휘하며 자신의 머신에서 성능을 측정했다는 것. 다중 스레드 읽기 상황에서 상당한 성능 개선이 있었다고 한다.**

## 핵심 포인트

- **병목의 성격 — folio 참조 카운트 경합** — 여러 스레드가 ***같은 파일을 조금씩 동시에 읽을 때*** 페이지 캐시의 folio 참조 카운팅에서 ***경합(contention)***이 발생해 병목이 된다는 진단. WebSearch로 확인한 실제 패치 시리즈 설명과 일치한다 — `folio_try_get`의 CAS(compare-and-swap) 루프가 다중 코어 환경에서 캐시라인 경합을 일으킨다는 것.
- **해법 방향 — 참조 없이 읽기** — 패치 시리즈는 ***folio 참조를 매번 획득하지 않고도 페이지 캐시를 읽도록*** 메모리관리 코드를 수정하는 방향(WebSearch로 확인한 실제 시리즈는 "CAS 루프를 낙관적 증가로 대체 + 참조 카운트를 카운터와 별도 dead/frozen 비트로 분리"하는 접근을 취한다).
- **LLM 코딩 보조의 쓰임 — 작성보다 보조** — Slack 발췌에 따르면 ***코드·테스트 프로그램 작성, 검토 작업, 패치 소개문(커밋 메시지) 초안 작성***에 LLM을 썼다는 것이 핵심이고, ***Torvalds가 직접 지휘하며 자신의 머신에서 성능을 측정***했다는 점이 강조된다 — 즉 "AI가 패치를 만들었다"가 아니라 "사람이 방향을 정하고 AI를 보조로 썼다"는 프레이밍.
- **성과 — 다중 스레드 읽기 상황에서 상당한 개선** — 구체 수치는 Slack 발췌에 없어 미확인이다. WebSearch로 찾은 실제 패치 시리즈의 v4 벤치마크(저자 자체 측정)는 "크로스 소켓 NUMA에서 24스레드 기준 약 +94.7%"라는 수치를 보였으나, **이 수치가 이번 GeekNews 글이 가리키는 것과 같은 버전·같은 측정인지는 확인할 수 없다.**

## 내 생각 · 적용점

### 핵심 전이 1 — "메인테이너가 직접 지휘하며 도구로 쓴다"는, [[2026-07-17-linus-torvalds-llm-in-kernel-development]]에서 Torvalds 본인이 선언한 입장을 실제로 수행한 사례(단, 주저자는 아니다)

7월 노트에서 정리한 Torvalds의 커널 LLM 정책 — ***"AI는 우리가 쓰는 다른 도구들과 같은 하나의 도구이며, 분명히 유용하다"***, ***"결정은 두려움이 아니라 기술적 이점에 근거한다"*** — 가 이번 사례와 정확히 맞물린다. 이 소식이 사실이라면 **"내가 직접 지휘하며 쓴다"는 선언을 실제로 실천한 모습**이고, "LLM이 코드를 대신 쓰는 게 아니라 작성·검토·문서화를 보조하고 사람이 방향과 검증을 쥔다"는 구도는 7월 노트가 Linus 입장의 가장 방어 가능한 버전으로 짚었던 그대로다. 단, **실제 LKML 스레드에서 Torvalds의 역할이 Ack(검토)에 가깝고 주저자는 Gladyshev라는 점**은, "Torvalds가 직접 지휘"라는 이번 기사 프레이밍이 메인테이너 중심으로 단순화됐을 가능성을 다시 보여준다 — 7월 노트가 지적한 "GN⁺ 렌더링이 한쪽에 기울어진다"는 구조적 패턴의 재현이다.

### 핵심 전이 2 — 이 사례가 "도구냐 자동화냐" 논쟁([[2026-10-13-rich-hickey-ai-is-automation-not-a-tool]] · [[2026-10-13-ai-is-a-tool-that-requires-skill]])에서 어느 쪽에 유리한 증거인지는 신중해야 한다

표면적으로는 이 사례가 [[2026-10-13-ai-is-a-tool-that-requires-skill]] 쪽("사람이 지시하고 피드백을 해석하고 오류를 수정하면 LLM도 도구로 쓸 수 있다")에 힘을 보태는 실증 사례처럼 보인다 — 코드베이스를 극도로 깊이 아는 사람(커널 메인테이너)이 방향을 정하고, 자기 머신에서 직접 성능을 측정해 검증했다는 구도이기 때문이다. 하지만 **과장해선 안 된다.** 이 사례는 "LLM이 자동화든 도구든, 검증을 사람이 직접 쥐고 있으면 결과가 좋다"는 것만 보여줄 뿐, Hickey가 제기한 "예측가능성·결정성 결여" 자체를 반박하진 않는다 — Torvalds가 "자신의 머신에서 직접 성능을 측정"해야 했다는 사실 자체가, **결과를 사람이 매번 직접 검증해야 하는(=예측불가능한) 도구라는 Hickey의 전제를 오히려 긍정**하는 쪽으로도 읽힌다. 즉 이 사례는 두 입장 중 하나의 승리가 아니라, **"숙련된 전문가가 직접 검증 루프를 쥐면 유용한 보조가 된다"는 두 글 모두가 동의하는 공통분모**를 보여주는 사례로 읽는 게 더 정확하다.

### 핵심 전이 3 — "브레인은 좋아졌는데 바디는 그대로"([[2026-10-11-why-coding-agents-are-so-dumb]])라는 비판과는 다른 결의 성공 사례

mtlynch의 비판은 코딩 에이전트의 하네스(위임·보안)가 모델 발전을 못 따라간다는 것이었다. 이번 사례는 그 비판이 지적한 문제(위임을 흉내만 낸다, 보안이 프롬프트 수준이다)가 애초에 발생하지 않는 사용 방식을 보여준다 — **위임이 아니라 보조**(코드·테스트·문서 초안을 돕고 사람이 전부 검토), **권한 위임이 아니라 자신의 로컬 머신에서 직접 측정**. 즉 mtlynch가 지적한 "제대로 안 된 위임"의 문제를 이 사례는 **애초에 위임을 거의 안 함으로써** 회피한 것에 가깝다 — 이건 하네스가 좋아져서 해결된 문제가 아니라, 사용자가 신중하게 범위를 좁혀서 피해간 문제라는 차이를 분명히 해둘 필요가 있다.

## 호스피탈리티 / CRS 적용 포인트

직접 적용은 멀다 — 커널 메모리관리 코드 수준의 저수준 성능 작업은 CRS 도메인과 거리가 있다. 다만 전이 가능한 원칙은 분명하다: **"코드베이스를 극도로 깊이 아는 사람이 방향을 정하고, LLM은 작성·검토·문서화를 보조하며, 결과는 반드시 직접 측정해 검증한다"는 패턴**은 CRS의 성능 최적화·리팩토링 작업에도 그대로 옮길 수 있는 역할 분담이다 — 특히 "자신의 머신에서 직접 성능을 측정"했다는 디테일은, LLM이 제시한 개선안을 벤치마크 없이 받아들이지 않는다는 원칙으로 일반화할 수 있다.
