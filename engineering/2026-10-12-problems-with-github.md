# GitHub의 문제점 (GNU Project)

> 출처: [Problems with GitHub](https://www.gnu.org/software/repo-criteria-evaluation.html) (GNU Project) · GeekNews(id=35206) 경유 · Slack `#개발-뉴스-dev-news` · 정리일 2026-10-12
> **출처 한계**: `news.hada.io`가 egress 전면 차단되어 원문을 직접 열지 못했다. WebSearch로 GNU Project의 저장소 윤리 평가 페이지(`gnu.org/software/repo-criteria-evaluation.html`)가 GitHub에 F 등급을 매긴다는 사실, 그리고 그 평가가 "비자유 JavaScript 없이는 핵심 기능(포크·PR·이슈 트래커)이 작동하지 않는다"는 근거를 든다는 사실을 교차확인했다. 다만 **이 평가 페이지가 상시 갱신되는 문서**라는 점에서, Slack 발췌가 인용한 정확한 문구와 WebSearch가 반환한 2016년 Phoronix 보도 시점의 평가 내용이 완전히 같은 버전인지는 확인하지 못했다. GNU의 자체 저장소 Savannah가 유일한 A등급이라는 점도 2차 소스(Phoronix) 기준이며 현재도 유지되는지는 직접 확인 못했다.

## 한 줄 요약

**GNU Project는 GitHub 저장소 호스팅을 피하라고 권고한다. 근거는 세 가지다 — ①GPL 라이선스 적용 안내가 불충분해 적용 버전과 이용자의 권리·의무가 불명확해질 수 있고, ②웹사이트 핵심 기능(포크·PR·이슈 트래커 등)이 비자유(nonfree) JavaScript 없이는 거의 작동하지 않으며, ③사용자가 통제할 수 없는 원격 서비스에 Git이라는 분산 도구가 중앙집중화되고 있다는 것이다. 자유 소프트웨어 운동의 원칙(라이선스 명확성·소프트웨어 자유)과 실용적 개발 편의(네트워크 효과·발견 가능성) 사이의 오래된 긴장이, GitHub가 점점 더 많은 개발 활동의 사실상 표준 인프라가 되면서 더 날카로워지는 사례다.**

## 핵심 포인트

- **GPL 적용 안내가 불충분하다** — GitHub는 라이선스 전문을 저장소에 넣는 것만으로 충분하다고 안내하고, 파일별 고지(copyright header)를 선택 사항으로 취급한다. GNU Project 입장에서 이는 ***적용 버전(GPLv2 vs v3, "or later" 여부)과 이용자의 정확한 권리·의무를 불명확하게 만드는 관행***이다.
- **비자유 JavaScript를 거부하면 웹사이트 이용이 크게 제한된다** — GNU 평가가 F등급을 매기는 핵심 근거다. 포크, PR 생성, 이슈 트래커 사용 등 ***주요 협업 기능이 obfuscated·proprietary JavaScript 실행 없이는 동작하지 않는다***. Git 명령줄과 REST API로 일부 작업은 대체할 수 있지만, GNU Project는 공식 명령줄 도구(`gh` CLI)의 원격 측정(telemetry) 기능도 별도로 문제 삼는다.
- **Git의 분산성과 개발 과정의 중앙집중화는 별개다** — Git 자체는 분산 버전관리 시스템이라 어느 서버에도 종속되지 않지만, ***이슈·PR·Actions·발견 경로(스타·팔로우) 같은 "개발 과정"은 GitHub라는 단일 플랫폼에 사실상 중앙집중화***되어 있다. 코드는 미러링해도 그 주변 워크플로·커뮤니티는 쉽게 옮겨지지 않는다는 지적이다.
- **GNU Project의 결론 — 자체 호스팅 권고** — 평가 페이지는 GitHub·SourceForge 등 주요 상용 포지(forge)에 낮은 등급을 매기고, GNU 자체 서비스인 Savannah를 ***유일한 A등급***으로 제시한다(WebSearch로 교차확인한 2016년 시점 Phoronix 보도 기준).

## 인상 깊은 문장

> (WebSearch로 확인된 GNU 평가 페이지 취지의 재구성) "github.com은 중요한 사이트 기능이 비자유 JavaScript 실행 없이는 작동하지 않는다."

> (WebSearch로 확인된 Mike Gerwitz 블로그 글의 재구성) GitHub를 방문하면 200kB가 넘는 난독화된 코드를 내려받게 되고, 그 상당수가 proprietary다. JavaScript를 끄면 포크·PR 생성·이슈 트래커 사용이 전부 작동을 멈춘다.

## 댓글

**hada 댓글 수 확인 불가**(원문 전면 차단). HN·Lobsters 큐레이션 여부도 확인하지 못했다. **정직하게 감안할 점**: ①**이 글은 GNU Project 자체 평가 페이지라는 1차 자료**이지만, GNU는 자유 소프트웨어 운동이라는 명확한 입장을 가진 조직이고, 이 평가 기준 자체가 "실용적 편의"보다 "자유 소프트웨어 원칙"을 압도적으로 우선하도록 설계돼 있다 — 즉 "GitHub가 나쁘다"는 결론은 평가 기준 안에서는 당연히 도출되지만, 그 기준 자체를 모든 개발자가 공유하지는 않는다. ②**실용적 반론이 체계적으로 빠져 있다** — 네트워크 효과, CI/CD 무료 러너(Actions)의 실질적 가치, 발견 가능성(스타·팔로우) 같은 GitHub의 비기술적 자산에 대한 반론은 이 평가 틀에 반영되지 않는다. ③**최신성 불확실** — 이 평가가 2026년 현재도 동일한 근거로 유지되는지, GitHub의 최근 변화(Copilot 통합 등)를 반영해 갱신됐는지 확인하지 못했다.

## 내 생각 · 적용점

### 핵심 전이 1 — [[2026-08-19-github-is-not-just-git]]이 "Git은 분산, 개발 과정은 중앙집중"을 이미 구체 장애 사례로 실증했다

8월에 정리한 GeekNews 아티클은 정확히 이 글의 세 번째 근거를 숫자로 뒷받침했다 — 8월 17일 장애가 웹·API 트래픽의 20%, 아카이브 다운로드의 50%에 영향을 줬고, ***"자체 호스팅 러너도 작업을 받지 못한다, 제어면(control plane)이 GitHub에 남아 있기 때문"***이라는 문장은 GNU Project의 "중앙집중화" 비판을 가장 아픈 지점에서 확인해준다. 두 글을 겹치면 GNU의 비판이 이념적 트집이 아니라 ***실제 가용성 리스크***로도 작동한다는 걸 알 수 있다 — 라이선스·자유 소프트웨어 원칙에 동의하지 않는 개발자도, "장애 시 대체 경로가 없다"는 실용적 이유로 같은 결론(대안을 고려해야 한다)에 도달할 수 있다.

### 핵심 전이 2 — [[2026-08-04-github-has-alternatives-no-replacement]]가 "그래서 왜 아무도 안 떠나는가"에 답한다

Lalit Maganti의 글은 GitLab·SourceHut·Forgejo·Radicle·Tangled 등 기술적 대안이 이미 여럿 있는데도 아무도 GitHub를 완전히 대체하지 못하는 이유를 ***"공유된 정체성·협업 관습·발견 경로"***라는 사회적 자산으로 설명했다. GNU Project의 이 글이 순수하게 "원칙과 기술"의 문제로 GitHub를 비판한다면, Maganti의 글은 "그 비판이 맞아도 왜 실천되지 않는가"를 사회적 콜드스타트 문제로 설명하는 셈이다 — ***윤리적으로 F등급을 받은 플랫폼이 여전히 업계 표준으로 남는 이유는 기술이 아니라 네트워크 효과***라는 걸 두 글을 겹쳐 읽으면 알 수 있다.

### 핵심 전이 3 — [[2026-09-09-mit-to-eupl-license-switch]]와 [[2026-08-27-bambu-lab-agpl-violation]]이 "라이선스 명확성" 근거의 실제 무게를 보여준다

GNU Project가 "GPL 적용 안내 불충분"을 비판하는 것은, Henri Bergius가 EUPL로 전환하며 들었던 것과 같은 계열의 문제의식 — ***"관대한 조건·불명확한 조건이 결국 누구에게 유리하게 작동하는가"*** — 와 통한다. 그리고 Bambu Lab AGPL 위반 사례는 라이선스가 명확해도(AGPLv3는 GPL류보다 훨씬 명시적이다) ***집행(enforcement)이 안 되면 명확성 자체가 무력화된다***는 균형추를 제공한다. 세 글을 겹치면 "GitHub의 라이선스 안내가 불명확하다"는 GNU의 비판에 "안내가 명확해져도 집행 자원이 없으면 소용없다"는 현실적 단서가 따라붙는다 — 플랫폼의 UX 문제와 법적 집행력 문제는 별개의 축이라는 뜻이다.

### 핵심 전이 4 — [[2026-09-21-nobody-pays-for-open-source]]가 던지는 "누가 진짜 돈을 버는가"라는 질문과 만난다

Laurie Voss(Seldo)의 글은 npm 생태계에서 "진짜 돈은 유지보수자가 아니라 JFrog·Docker 같은 레지스트리 인접 업체로 흘러간다"고 지적했다. GitHub도 구조적으로 비슷한 위치에 있다 — 오픈소스 프로젝트의 ***협업 인프라***를 거의 독점하면서도, 그 인프라 위에서 활동하는 유지보수자에게 직접적 수익을 분배하지 않는다(Sponsors 프로그램은 부분적 예외). GNU의 "통제할 수 없는 원격 서비스"라는 비판과 Voss의 "돈이 중개 계층에만 쌓인다"는 관찰을 겹치면, GitHub 같은 플랫폼이 오픈소스 생태계에서 ***통제와 수익 양쪽에서 비대칭적으로 유리한 위치***를 점한다는 더 큰 그림이 드러난다.

### 핵심 전이 5 — [[2026-05-04-if-i-could-make-my-own-github]] · [[2026-08-04-devtools-must-be-open-source]]가 이미 같은 질문을 선제적으로 던졌다

가든에는 이미 "내가 직접 GitHub를 만든다면"이라는 사고실험과 "개발자 도구는 오픈소스여야 한다"는 원칙론이 쌓여 있다. 이번 GNU Project의 글은 그 두 선행 논의에 ***자유 소프트웨어 재단(FSF)이라는 가장 엄격한 기준의 평가***를 더하는 셈이다 — "더 나은 GitHub를 만들 수 있을까"라는 실용적 질문과 "GitHub를 쓰는 것 자체가 원칙에 반하는가"라는 규범적 질문이 가든 안에서 서로 다른 각도로 축적되고 있다.

## 호스피탈리티 / CRS 적용 포인트

- **"제어면이 외부 플랫폼에 있다"는 리스크를 내부 개발 인프라 의존도 점검에 적용할 것.** [[2026-08-19-github-is-not-just-git]]이 짚은 "자체 러너도 GitHub 제어면에 종속된다"는 구조는, 온다가 CI/CD나 사내 개발 워크플로를 특정 SaaS에 깊게 의존시킬 때 똑같이 발생할 수 있는 리스크다 — 장애 시 대체 경로가 실제로 존재하는지(완전히 독립적인지, 아니면 같은 제어면에 묶여 있는지)를 점검할 가치가 있다.
- **라이선스 고지 관행을 사내 오픈소스 사용·공개 양쪽에 명확히 할 것.** GNU가 비판하는 "불충분한 라이선스 안내"는 GitHub만의 문제가 아니라, 사내에서 외부 오픈소스를 가져다 쓸 때도 재현될 수 있는 패턴이다 — 라이선스 전문만 복사하고 적용 범위·버전을 명시하지 않는 관행은 추후 분쟁 시 같은 불명확성을 낳는다.
- 직접 적용은 제한적이다 — 이 글의 핵심 논지(자유 소프트웨어 원칙에 따른 플랫폼 보이콧)는 B2B 호스피탈리티/CRS 사업 운영에 직접 걸리는 사안은 아니다. 다만 "플랫폼 종속의 비용을 가용성·라이선스 양쪽에서 미리 계산하라"는 원칙만은 전이 가능하다.
