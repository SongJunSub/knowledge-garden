# 상담 흐름과 오류를 검증하는 API 테스트 설계 (베스핀글로벌)

## 한 줄 요약

**단일 API 호출이 200을 반환해도 상담이라는 멀티 스텝 흐름은 실패할 수 있다. 검색→저장으로 이어지는 사용자 행동 시나리오를 테스트 단위로 삼고, 정적 검증→평가 회귀 테스트로 범위를 단계적으로 넓혀야 실패 원인을 빠르게 좁힐 수 있다.**

## 핵심 포인트

(Slack 발췌 원문 그대로)
- 검색부터 저장까지 이어지는 **사용자 행동 시나리오**를 기준으로 통합 테스트를 설계한다.
- 단순 API 호출 성공 여부를 넘어 **상담 흐름의 연결성과 업무 규칙 준수 여부**를 검증한다.
- **정적 검증부터 평가 회귀 테스트까지** 단계별로 범위를 넓혀 실패 원인을 빠르게 파악한다.

## 내 생각 · 적용점

### 핵심 전이 1 — [[2026-09-10-coding-agents-test-verification-techniques]]의 "자기 검증의 구조적 결함"과 정반대 극단의 대응

Dan Luu의 실험은 "에이전트가 자신이 만든 테스트를 통과시키는 데만 능하고, 그 테스트가 부실해서 실제 버그를 놓친다"는 문제를 보였다. 이 글의 "사용자 행동 시나리오 기준 통합 테스트"는 정확히 그 함정을 피하는 설계다 — **테스트 단위를 에이전트/API가 아니라 사람의 행동 시나리오로 못 박으면, 에이전트가 스스로 느슨한 테스트를 지어내는 여지가 줄어든다.** 다만 이 글도 그 통합 테스트 자체를 누가(사람 or AI) 설계했는지는 밝히지 않아, Dan Luu가 지적한 함정에서 완전히 자유로운지는 알 수 없다.

### 핵심 전이 2 — [[2026-10-16-addy-osmani-agentic-verification-e2e-property-tests]]와 같은 축: 유닛보다 상위 레벨의 검증 단위가 에이전틱 시스템에 더 맞는다

그 노트가 다룬 E2E·속성 기반 테스트 논의와 이 글의 "사용자 행동 시나리오 기준" 접근은 같은 결론으로 수렴한다 — **AI 에이전트가 낀 시스템은 유닛 테스트로는 "흐름이 끊기는" 실패를 못 잡는다. 검증 단위를 사용자가 실제로 겪는 시나리오까지 끌어올려야 한다.**

### 핵심 전이 3 — [[2026-11-17-bespin-ai-agent-service-architecture]]의 검색/상세질의 API 분리를 검증하는 쪽이 바로 이 테스트 설계

같은 시리즈의 서비스 구조 설계 글이 검색과 상세 질의 API를 분리했다면, 이 테스트 설계 글은 그 분리된 API들이 **합쳐졌을 때도 상담 흐름이 끊기지 않는지**를 검증하는 짝이다. API를 쪼갤수록 "쪼갠 조각들이 이어지는가"를 보는 통합 테스트의 가치가 커진다는 것을 이 둘을 같이 보면 알 수 있다.

## 호스피탈리티 / CRS 적용 포인트

**적용 가능성 있음, 다만 범용 원칙에 가깝다.** CRS의 예약 흐름(검색→요금확인→객실선택→결제→확정)도 각 API는 개별적으로 통과해도 전체 흐름에서 끊기는 경우(예: 프로모션 적용 후 결제 모듈이 할인된 금액을 못 받는 경우)가 실제로 발생할 수 있는 지점이다. "사용자 행동 시나리오 기준 통합 테스트 + 정적 검증부터 회귀 테스트까지 단계적 확장"은 CRS 예약 플로우 전체에 원칙으로 적용할 수 있다. 다만 이 글이 보험 상담 맥락의 사례라 CRS 고유의 결제·재고 확정 같은 결정적 액션 검증까지 그대로 옮기기엔 디테일이 부족하다 — 원칙만 참고하고 CRS 자체 시나리오로 다시 설계해야 한다.
