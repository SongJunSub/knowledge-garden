# 격리 안 된 테스트의 초록불은, 에이전트가 믿을 수 없습니다

## 한 줄 요약
**AI 에이전트에게 테스트 실행과 수정을 맡기는 워크플로우에서, 테스트가 격리되어 있지 않으면 "초록불(성공)"이라는 신호 자체를 신뢰할 수 없다는 경고. 에이전트가 실패 원인을 정확히 진단하지 못한 채 코드를 고치면, 실제로는 멀쩡한 코드를 오히려 망가뜨릴 위험이 크다는 글이다.**

## 핵심 포인트
- **전체 실행 vs 단독 실행 대조가 필수** — 에이전트가 테스트를 자동 수행할 때는 ***전체 스위트를 돌린 결과와 그 테스트 하나만 단독으로 돌린 결과를 대조***해 오염 여부를 판별해야 한다.
- **코드 외적 요인이 신뢰도를 깎는다** — 테스트 간 ***데이터 오염***이나 외부 인프라 편차 같은, 짜여진 코드 로직과 무관한 요인이 테스트 결과의 신뢰도를 떨어뜨릴 수 있다.
- **잘못된 진단 → 잘못된 수정** — 실패 원인을 정확히 짚지 못한 채 에이전트에게 수정을 맡기면 ***멀쩡한 코드를 훼손할 위험***이 크다. 에이전트는 "실패했다"는 신호만 보고 원인을 코드에서 찾으려 들기 때문이다.
- **자동화 환경엔 실행 일관성이 전제조건** — 에이전트가 올바른 수정안을 도출하려면 ***실행 환경의 일관성 확보***가 먼저다. 격리되지 않은 테스트 환경 위에 에이전트를 얹는 것은 순서가 거꾸로다.

## 내 생각 · 적용점
1. 이 글의 핵심은 "에이전트가 똑똑해서 문제"가 아니라 ***"에이전트는 사람과 달리 '이 실패, 어쩐지 낯익은데 아마 그 오염된 테스트 데이터겠지' 같은 암묵지 없이 눈앞의 초록/빨강 신호를 곧이곧대로 믿는다"***는 점이다. 사람 개발자는 flaky한 테스트를 몇 번 겪으면 "아 이건 원래 가끔 이래" 하고 무시하는 감각이 생기지만, 에이전트에게는 그런 히스토리가 기본적으로 없다.
2. [[2026-09-06-ai-sre-skill-atrophy]]와 거울상 관계다 — 그 글은 "AI가 반복 작업을 대신하면서 사람이 시스템 감각을 잃는다"는 문제였다면, 이 글은 반대로 ***"사람이 당연히 가진 시스템 감각(이 테스트는 원래 가끔 실패해)을 에이전트가 처음부터 갖고 있지 않다"***는, 같은 "암묵지 부재" 문제를 다른 방향에서 드러낸다.
3. [[2026-09-05-surviving-code-reviews-ai-era]]와도 연결된다 — 그 글이 "AI가 생성한 큰 diff를 사람이 어떻게 검증할 것인가"를 다뤘다면, 이 글은 그보다 한 단계 앞선 문제다. ***애초에 에이전트가 스스로 검증(테스트)한 결과조차 격리가 안 되어 있으면 못 믿는다*** — 사람 리뷰 이전에, 에이전트의 자기 검증 루프부터 신뢰 기반이 깨질 수 있다는 것.

## 호스피탈리티 / CRS 적용 포인트
CRS/PMS 연동 테스트는 태생적으로 "격리가 어려운" 영역이다 — 채널 재고 동기화, 요금 캐시, 예약 상태 전이(pending→confirmed→checked-in) 같은 테스트는 공유 DB 상태나 외부 채널 API mock 상태에 종종 암묵적으로 의존한다. 온다에서 AI 에이전트(코드 리뷰, 자동 수정, 테스트 생성)를 CI 파이프라인에 도입한다면, 이 글의 원칙을 그대로 가져와 ***"에이전트가 손댈 대상 테스트가 단독 실행과 전체 스위트 실행에서 동일한 결과를 내는지"를 먼저 감사하는 단계***를 넣는 게 우선순위가 높다. 특히 요금/재고처럼 순서 의존적인 테스트가 많은 도메인일수록, 에이전트의 "초록불 → 수정 없음" 판단과 "빨강불 → 코드 수정" 판단 둘 다 격리 안 된 상태에서는 오판 확률이 커진다.
