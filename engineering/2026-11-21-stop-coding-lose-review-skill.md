# 코드 작성을 멈추면 코드 리뷰 실력도 떨어진다 (원문 1:1 매칭 미확정) — 코드 리뷰는 'use it or lose it' 스킬이고, 소프트웨어 엔지니어링은 코드 작성보다 넓지만 둘을 대체할 수는 없다

> 출처: [Code review was the safeguard. AI is wearing it down.](https://itnext.io/code-review-was-the-safeguard-ai-is-wearing-it-down-c04c7b225813) (ITNEXT, 추정) · 정리일 2026-11-21

## 한 줄 요약

**코드를 직접 쓰며 문제를 해결하는 경험은 코드 리뷰의 판단 기반이 되는데, 구현을 전부 AI에게 맡기고 지시·검토만 반복하면 결과물이 좋아져도 리뷰어 자신의 개발 역량은 유지되거나 향상되지 않는다 — 소프트웨어 엔지니어링이 코드 작성보다 넓은 건 맞지만, 좋은 코드와 변경하기 쉬운 구조를 알아보는 능력도 필요하며, AI가 만든 코드를 읽고 피드백하는 것만으로 직접 구현하며 배우는 과정을 대체하기는 어렵다.**

## 핵심 포인트

- **코드를 직접 쓰며 문제 해결한 경험이 코드 리뷰의 판단 기반**이 된다. 구현을 모두 맡기고 지시와 검토만 반복하면 결과물이 좋아져도 자신의 개발 역량까지 유지·향상되는 것은 아니다.
- 쟁점은 AI가 만든 코드의 단기적인 품질이 아니라, 직접 작업하는 개발자와 그렇지 않은 개발자의 **숙련도 변화**에 있다.
- 소프트웨어 엔지니어링은 코드 작성보다 넓지만, **좋은 코드와 변경하기 쉬운 구조를 알아보는 능력**도 필요하다. AI가 만든 코드를 읽고 피드백하는 것만으로 직접 구현하며 배우는 과정을 대체하기는 어렵다.
- 외부 교차검증으로 확인되는 같은 주제의 반복: 리뷰는 **"use it or lose it" 스킬**이라는 주장이 다수 블로그에서 반복됨. 수년간 직접 코딩을 떠난 시니어 엔지니어가 "숨은 복잡도를 감지하는 감각이 둔화되어 리뷰가 얕아지고 질문이 고수준에만 머문다"고 1인칭으로 서술한 글도 있음(Jono Herrington, "The Atrophy Problem").
- Addy Osmani 계열 글은 "**평가는 작성보다 더 강한 스킬을 요구한다**"는 논지로, 자동조종 중인 파일럿·집도를 멈춘 외과의사에 비유함.
- **반론도 존재**: 스킬이 사라지는 게 아니라 "무엇이 잘못됐는지 감지하는 능력"으로 이동한다는 주장. "이기는 개발자는 문법을 외운 사람이 아니라 뭔가 잘못됐다는 냄새를 아는 사람"이라는 반박 댓글도 확인됨.

## 내 생각 · 적용점

### 핵심 전이 1 — [[2026-11-19-harvard-ai-coding-agents-review-bottleneck]]과 짝을 이루는 "리뷰 역량" 관점의 보강

Harvard 연구는 "코드량 증가가 완료량 증가로 안 이어지고 리뷰 단계로 병목이 이동한다"는 **처리량(throughput)** 관점이었는데, 이 글은 같은 현상을 **역량(skill)** 관점에서 본다 — 병목이 리뷰로 옮겨간다는 사실 자체보다, **그 병목을 처리하는 사람의 판단력이 시간이 지나며 둔화될 수 있다**는 게 추가된 위험이다. 처리량 문제는 프로세스로 완화할 수 있어도, 역량 저하는 더 느리고 눈에 안 보이게 진행된다.

### 핵심 전이 2 — [[2026-10-19-anthropic-junior-hiring-decline]]의 "주의력이 새 병목"과 같은 축, 한 단계 더 나간 경고

Anthropic의 주니어 채용 비중 감소 노트는 "AI 산출물을 검증할 판단력"을 신입 채용 기준으로 삼으라고 했는데, 이 글은 그 판단력 자체가 **코드를 직접 쓰지 않으면 시간이 지나며 둔화된다**는 반론을 던진다. 두 글을 합치면 "AI 검증 역량을 요구하되, 그 역량을 유지하려면 일정량의 직접 작성도 필요하다"는 더 정교한 조직 설계 과제가 보인다.

### 핵심 전이 3 — "반론"이 가리키는 더 나은 질문: 스킬이 사라지는가, 이동하는가

"무엇이 잘못됐는지 감지하는 능력으로 이동한다"는 반론은 완전히 기각할 게 아니다. [[2026-08-20-code-outruns-review]]의 기존 문제의식과 겹치되, **"어떤 스킬이 남고 어떤 스킬이 사라지는지"를 구분하는 게 다음 질문**이다 — 문법·구현 세부에 대한 감각은 둔화돼도, 아키텍처 수준의 "냄새 감지" 능력은 유지되거나 오히려 강화될 수 있다는 가능성은 아직 검증된 연구가 없다.

## 호스피탈리티 / CRS 적용 포인트

**적용 가능성 있음.** 개발팀이 AI 코딩 에이전트에 구현을 많이 맡길수록, 리뷰어의 판단력을 유지하기 위한 의도적 장치(정기적으로 직접 코드 작성, 리뷰 전 스스로 먼저 구현해보는 루틴)가 필요하다는 원칙은 온다의 개발 조직 운영에도 그대로 적용 가능하다 — 특히 예약·결제처럼 리스크가 큰 코드 경로의 리뷰어는 해당 영역 코드를 주기적으로 직접 작성해 감각을 유지하는 로테이션을 고려할 만하다.
