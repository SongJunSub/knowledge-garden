# GCC 운영위원회, AI 정책 발표 (LWN.net) — 15줄이라는 오래된 자로 새 문제를 잰다

> 출처: [GCC steering committee announces AI policy](https://lwn.net/Articles/1086041/) (lwn.net · GeekNews GN⁺ 요약 + HN 큐레이션) · 정리일 2026-08-02

## 한 줄 요약

**GCC(GNU Compiler Collection) 운영위원회가 AI 정책 워킹그룹의 권고를 채택해 **LLM 활용 기여의 범위**를 명시적으로 정했다. 핵심 문구: ***"프로젝트는 LLM이 생성한 콘텐츠를 포함하거나 그로부터 파생된 '법적으로 중요한 기여'를 받지 않는다."*** "법적으로 중요한"의 기준은 새로 만들지 않고 **GNU 프로젝트 유지관리자 가이드라인의 기존 정의를 그대로 가져왔다** — ***"저작권 목적상 중요하다고 인정되는 임계값은 약 15줄의 코드 및/또는 텍스트."*** 즉 15줄 미만의 변경은 애초에 저작권상 "중요한 창작"으로 안 보므로 LLM 출처 여부를 따질 필요가 없고, 15줄을 넘으면 LLM 생성·파생 콘텐츠는 거부된다. 그런데 정책은 도구 사용 자체를 막지 않는다 — ***"이 정책은 연구, 분석, 버그 발견 및 보고, 패치 검토 등에 LLM을 사용하는 것을 금지하지 않는다, 단 그 출력물이 기여에 포함되지 않는 한."*** 그리고 예외 하나가 흥미롭다 — ***"GCC 유지관리자는 LLM이 생성한 법적으로 중요한 테스트 케이스를 재량으로 수용할 수 있다."*** 테스트 코드는 제품 코드와 다른 저작권·신뢰 기준으로 다뤄진다는 뜻이다. 이 정책의 배경에는 **Guix 등 다른 GNU 프로젝트의 선례**가 있고, 정책은 **정기적으로 재검토**될 예정이다.**

## 핵심 포인트

- **핵심 규정** — ***"프로젝트는 LLM이 생성한 콘텐츠를 포함하거나 그로부터 파생된, 법적으로 중요한 기여를 거부한다."***
- **"법적으로 중요한"의 기준 = 기존 GNU 지침 재사용** — ***"저작권 목적상 '중요함'의 임계값은 약 15줄의 코드 및/또는 텍스트."*** 새 기준을 만드는 대신, **저작권법 문제로 오래전부터 써온 잣대를 AI 문제에 그대로 적용**한 것.
- **유지관리자 재량 예외** — ***"GCC 유지관리자는 LLM이 생성한 법적으로 중요한 테스트 케이스를 재량으로 수용할 수 있다."*** 제품 코드보다 테스트 코드에 더 관대한 기준.
- **도구 사용은 허용** — ***"이 정책은 연구, 분석, 버그 발견 및 보고, 패치 검토 등에 LLM을 사용하는 것을 금지하지 않는다, 단 그 출력물이 기여에 포함되지 않는 한."*** 즉 **"AI로 조사하고 사람이 직접 쓴다"는 워크플로는 완전히 허용**된다 — 금지되는 건 AI의 출력물을 그대로(또는 파생된 형태로) 기여물에 넣는 것.
- **배경** — 댓글에서 GNUtoo가 **Guix의 접근 방식**을 언급하며, GNU 자체도 LLM 정책 수립 과정에서 이를 참고했다고 지적. **다른 오픈소스 프로젝트의 선례가 이 정책 형성에 영향**을 미쳤다.
- **재검토 예정** — 정책은 **정기적으로 재검토**될 계획.

## 인상 깊은 문장

> "the project will decline any 'legally significant contributions which include LLM-generated content or are derived from LLM-generated content'"

> "the definition of 'legally significant' from the GNU Project maintainer guidelines, which holds that the threshold is 'around 15 lines of code and/or text' to qualify as significant for copyright purposes"
> (이 정책의 실질적 핵심 — 새 기준이 아니라 낡은 저작권 잣대의 재사용)

> "GCC maintainers may, however, choose to accept legally significant test cases that are generated by an LLM"

> "The policy does not forbid use of LLMs for research, analysis, bug discovery and reporting, patch review, etc. as long as the output is not included in contributions"

## 내 생각 · 적용점

### 핵심 전이 1 — "15줄"은 [[2026-08-02-openai-codex-security-oss]]가 보여준 diff 기반 검증과 정반대 방향에서 같은 문제(경계 설정)를 푼다

Codex Security 노트에서 나는 *"검증 범위를 diff로 좁히는 게 검증을 자주 돌릴 수 있게 만든다"*고 정리했다. GCC의 15줄 기준은 **반대 방향의 경계 설정**이다 — **"이 정도 이하는 저작권상 의미가 없다"는 하한선**을 그어서, 그 이하는 아예 심사할 필요가 없게 만든다. 두 사례를 겹치면 흥미로운 원칙이 보인다: **불확실한 새 문제(AI 생성 코드의 저작권, 보안 취약점)를 다룰 때, 완전히 새로운 판정 기준을 만드는 것보다 이미 검증된 오래된 기준을 재활용하는 게 더 안전한 시작점일 수 있다.** GCC는 "AI 코드 탐지 도구"를 새로 만들지 않고, 이미 수십 년간 저작권 분쟁에서 써온 "15줄" 기준을 그대로 가져왔다 — **새 기술 문제에 낡은 법적 도구를 재사용하는 실용주의.**

### 핵심 전이 2 — "도구 사용은 허용, 출력물 포함은 금지"는 내 LLM 위임 경계와 구조적으로 같다

GCC의 구분 — **AI로 조사·분석·버그 발견은 자유, 그 출력물을 기여물에 직접 넣는 건 금지** — 은 내 CLAUDE.md의 LLM 위임 경계와 정확히 같은 문법이다. 내 3층 구조 원칙(*"결정적 스캐폴딩 → LLM 판단(좁은 범위) → 결정적 도구"*)을 GCC의 정책에 대입하면: **연구·분석은 LLM 판단 영역(비결정적이어도 안전)이고, 실제 코드베이스에 들어가는 기여물은 결정적 검증(사람이 직접 작성·책임)이 필요한 영역**이다. GCC는 이 경계를 "저작권"이라는 다른 이유로 그었지만, **결과적으로 도달한 경계선은 내가 코드 작업에 적용하는 것과 동일**하다.

### 핵심 전이 3 — 테스트 케이스에 대한 관대한 예외는 [[2026-08-01-bun-zig-to-rust-rewrite-with-ai]]가 보여준 "정답지가 있는 작업"의 실제 정책 사례다

GCC가 **LLM 생성 테스트 케이스는 재량으로 수용 가능**하다고 예외를 둔 이유를, 지난주 정리한 Bun 재작성 노트의 원칙으로 설명할 수 있다 — **테스트는 "이 코드가 맞는지"를 판정하는 도구이지, 판정 대상이 아니다.** 제품 코드는 저작권·품질 판정이 필요한 대상이지만, 테스트 케이스는 **"이 테스트가 통과하면 코드가 옳다"는 정답지 역할**만 하면 충분하다. LLM이 생성한 테스트가 저작권상 문제가 있어도, **테스트 자체의 정확성은 실행 결과로 검증 가능**하므로 위험이 낮다. 이건 [[2026-08-02-openai-codex-security-oss]]에서 다룬 검증 자동화의 원리가 오픈소스 거버넌스에서도 같은 방식으로 작동한다는 증거다.

### 핵심 전이 4 — 정직한 급소: "파생된(derived from)"의 판정 불가능성이 이 정책의 실행 가능성을 위협한다

GCC 정책의 가장 약한 지점은 **집행 메커니즘의 부재**다. 15줄 기준은 명확하지만, **"이 코드가 LLM에서 파생됐는가"를 어떻게 검증할 것인가**는 정책에 없다. 개발자가 자진 신고하지 않는 한 유지관리자가 파생 여부를 판정할 방법이 마땅치 않다. 이건 지난주 [[2026-08-02-anthropic-position-open-weight-models]]에서 다룬 *"의무 안전성 테스트를 누가 어떻게 운영하는가"*와 같은 종류의 문제다 — **좋은 원칙을 세우는 것과 그 원칙을 실제로 집행하는 것은 다른 난이도의 문제**다.

## 호스피탈리티 / CRS 적용 포인트

- **우리 코드 기여 정책에도 "15줄" 같은 명시적 경계를 고려한다.** 사내에서 AI 생성 코드에 대한 명확한 규칙이 없다면, GCC처럼 **"조사·분석은 자유, 프로덕션 코드에 그대로 넣는 건 검토 필요"**라는 경계를 문서화하는 것이 실용적 출발점이다.
- **테스트 코드에 대한 별도 기준을 고려한다(전이 3).** 프로덕션 코드보다 테스트 코드에는 AI 생성물을 더 관대하게 허용하는 게 GCC의 실용적 선택이고, 우리 코드 리뷰 기준에도 참고할 만하다.
- **"파생 여부 판정 불가능"이라는 급소를 우리 정책에서도 명시(전이 4).** 규칙을 만들 때 집행 메커니즘이 없다는 걸 숨기지 말고, **"이 규칙은 자진 준수에 의존한다"는 한계를 명시**하는 게 GCC보다 한 걸음 더 정직한 정책이다.
