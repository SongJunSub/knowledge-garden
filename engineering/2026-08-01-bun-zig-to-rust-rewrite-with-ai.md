# Bun의 Zig→Rust 재작성, 11일 (Gergely Orosz) — 배율이 풀리는 조건은 "정답지가 있는가"다

> 출처: [The Pulse: What can we learn from Bun's rapid Rust rewrite with AI?](https://blog.pragmaticengineer.com/the-pulse-what-can-we-learn-from-buns-rapid-rust-rewrite-with-ai/) (Gergely Orosz, The Pragmatic Engineer · GeekNews GN⁺ 요약) · 정리일 2026-08-01

## 한 줄 요약

**Bun이 **535,496줄(주석 제외) / 1,448개 `.zig` 파일**을 Rust로 이식했다. **Claude 인스턴스 64개**, **11일**, **커밋 6,500개**, 도중에 발생한 **컴파일 에러 약 16,000개**. 비용은 API 기준 **$165,000**이고, 토큰 내역이 이 사건의 성격을 말해 준다 — 입력 59억(비캐시) / 출력 6.9억 / **캐시 읽기 720억**. 동기는 성능이 아니라 안전이었다: Zig은 메모리 안전 언어가 아니라 크래시가 계속 났고, Jarred Sumner의 말로는 ***"버그 수정 목록이 기분 나빴고, 크래시를 걱정하며 잠드는 데 지쳤다."*** 성공의 토대는 에이전트 수가 아니라 **600줄짜리 `PORTING.md`** — Zig→Rust 변환 패턴을 못 박고, 무엇보다 **금지 목록**이 강하다(*"No tokio, rayon, hyper, async-trait, futures. No std::fs, std::net, std::process"* — Bun 자체 이벤트 루프와 syscall을 쓰라는 것). 파이프라인은 10단계: **패턴 합의+PORTING.md 작성 3시간 → 파일 3개 시범 변환 + 적대적 검토 2회 → 1,448파일을 64에이전트로 병렬 → git 충돌을 worktree 4개로 분산(~1일) → 에이전트 실행(~2일) → 크레이트별 병렬 컴파일 에러 수정(~12시간) → 로컬 테스트(~2일) → CI 통과(~3일) → 병합.** Orosz의 결론은 열광이 아니라 조건부다: ***"AI 마이그레이션은 분명히 빨라지고 있다 — 단 Bun처럼 잘 엔지니어링된 프로젝트에서만."*** 재현 조건 셋 — **①코드베이스를 깊이 아는 강한 동기의 주도 엔지니어 ②통과하면 동작을 보장하는 견고한 테스트 스위트 ③성공 보장 없이 토큰을 쏟을 각오.** Mitchell Hashimoto의 평: ***"그 연봉의 엔지니어가 이걸 해낼 방법은 절대 없다."*** 그리고 남는 질문 하나 — **1년짜리 작업이 1주일이 된다면, 당신은 그동안 미뤄둔 그 마이그레이션을 하겠는가?**

## 핵심 포인트

- **규모와 결과** — **535,496줄**(주석 제외), **1,448개 `.zig` 파일** → Rust. **11일**, **6,500 커밋**, 도중 **컴파일 에러 ~16,000개**.
- **자원** — **Claude 인스턴스 64개**, 비용 **$165,000**(API 정가 기준). 토큰: 입력 **59억**(비캐시), 출력 **6.9억**, ***캐시 읽기 720억***.
- **동기는 성능이 아니라 메모리 안전** — Zig은 메모리 안전 언어가 아니어서 크래시가 반복됐다. ***"Our bugfix list felt bad and I was tired of going to sleep worrying about crashes."*** Rust의 **컴파일러 강제 안전성**이 해법으로 선택됐다.
- **`PORTING.md` 600줄이 진짜 인프라** — Zig→Rust 변환 패턴의 단일 기준. 핵심은 허용이 아니라 **금지**다: ***"No tokio, rayon, hyper, async-trait, futures. No std::fs, std::net, std::process"*** — 표준 async/sync 패턴을 거부하고 **Bun 자체 이벤트 루프와 syscall**을 쓰게 강제했다. (이걸 안 박아뒀다면 64개 에이전트가 64가지 방식으로 이식했을 것이다.)
- **10단계 파이프라인**

  | # | 단계 | 시간 |
  |---|---|---|
  | 1 | Claude와 패턴 매핑 논의 → `PORTING.md` 작성 | **3시간** |
  | 2 | 파일 3개 시범 변환 + **적대적 검토 2회** | — |
  | 3 | 1,448파일을 **64에이전트로 병렬** 처리 | — |
  | 4 | git 충돌 해결 — **worktree 4개로 분산** | ~1일 |
  | 5 | 에이전트 실행·대기 | ~2일 |
  | 7 | **크레이트별 병렬** 컴파일 에러 수정 | ~12시간 |
  | 8 | 테스트 스위트 로컬 실행 | ~2일 |
  | 9 | **CI 테스트 통과** | ~3일 |
  | 10 | 최종 병합 | — |

  → **주목: 변환(생성)보다 검증(7~9단계)이 더 오래 걸렸다.** 대략 생성 2~3일 vs 검증 5일 이상.
- **적대적 검토를 세션 밖에서** — Claude가 리뷰어 역할을 하되 **같은 세션 바깥에서** 수행. (자기가 쓴 걸 자기가 검토하지 않게 한 것.)
- **재현 조건 3가지** — ①**코드베이스 이해도가 높은, 매우 동기부여된 주도 엔지니어** ②**통과하면 동작을 보장하는 견고한 테스트 스위트** ③**성공 보장 없이 토큰을 투자할 의지**.
- **비용 정당화** — 수작업이었다면 **경험 많은 엔지니어 3명 × 약 1년**. Hashimoto: ***"There's absolutely no way an engineer with that salary would've been able to achieve."***
- **Orosz의 단서** — ***"Migrations with AI are surely speeding up, but only when projects are well-engineered like Bun's."***

## 내 생각 · 적용점

### 핵심 전이 1 — 지난주 [[2026-07-25-why-software-factories-fail]]와 정면충돌하는데, **모순이 아니라 조건의 발견**이다

일주일 전 나는 *"10~100배는 환상이고 2~3배가 정직한 기대치"*라고 정리했다. 그리고 지금 **1년 → 11일(대략 30배 이상)** 사례가 왔다. 둘 다 맞다. 갈라지는 지점은 하나다:

> **wsff의 논지: 모델의 보상 함수에 "유지보수성"이 없어서, 좋고 나쁨의 판정을 사람이 해야 한다.**
> **Bun의 조건: 이식(port)에는 "좋고 나쁨"의 판정자가 이미 있다 — 원본 동작과 테스트 스위트.**

즉 wsff가 말한 *좁은 목(검증)*이 여기서는 **자동화돼 있었다.** 컴파일러가 16,000개 에러로 타입 계약을 강제하고, 테스트 스위트가 동작 동등성을 판정한다. 사람이 판단할 게 없는 게 아니라 **판단 기준이 코드 바깥에 이미 존재**한다. 그래서 이렇게 정리하는 게 맞다:

> **AI의 배율은 작업의 난이도가 아니라 검증의 자동화 가능성에 비례한다.**
> - **정답지가 있는 작업**(이식, 언어 업그레이드, API 마이그레이션, 대량 리팩토링, 테스트가 두꺼운 리라이트) → **10배 이상 가능**
> - **정답지를 사람이 만들어야 하는 작업**(신규 기능, 제품 설계, 아키텍처 결정) → **2~3배** (wsff)

그리고 파이프라인 시간 배분이 이걸 그대로 증명한다 — **생성 2~3일 vs 검증 5일 이상.** 검증이 자동화된 상태에서도 **여전히 검증이 더 오래 걸렸다.** [[2026-07-24-software-factories-light-and-dark]]의 *"생성은 넓은 입구, 검증은 좁은 목"*은 여기서도 깨지지 않았다 — 목이 넓어진 게 아니라 **기계가 목을 지킨 것**이다.

### 핵심 전이 2 — `PORTING.md` 600줄은 지난주 컨텍스트 엔지니어링 글과 **모순이 아니라 정확히 그 처방**이다

[[2026-07-25-context-engineering-rules-claude-5]]는 *"시스템 프롬프트를 80% 줄여라"*였는데, 여기서는 600줄 문서가 성공의 토대다. 표면적 모순인데 실제로는 같은 말이다. 그 글이 권한 것 중 두 항목이 정확히 `PORTING.md`다:

- ***"풍부한 참조 자료를 활용하라"*** — `PORTING.md`는 **시스템 프롬프트가 아니라 참조 자료**다. 항상 로드되는 규칙 더미가 아니라, **이식이라는 특정 작업에서만 필요한 도메인 계약**이다. 이건 **점진적 공개의 정석**이다.
- ***"고정 규칙보다 맥락 기반 판단"*** 의 예외 — 그런데 `PORTING.md`의 핵심은 **금지 목록**(`No tokio, rayon, hyper... No std::fs`)이다. 왜 여기선 하드 규칙이 옳은가? **64개 에이전트가 독립적으로 판단하면 일관성이 깨지기 때문**이다. 즉 규칙은 *모델이 못 판단해서*가 아니라 ***여러 판단자 사이의 일관성을 위해*** 필요하다.

**여기서 실무 규칙이 하나 나온다:**

> 프롬프트에서 지울 것 = 모델을 통제하려는 규칙.
> 남길 것 = **여러 에이전트·여러 세션 사이의 계약**(명명, 금지 의존성, 에러 처리 관례, 경계 정의).

내 CLAUDE.md/strict.md를 이 기준으로 다시 보면, 지울 후보(모델 통제형 강제 표현)와 남길 후보(팀·세션 간 계약)가 훨씬 선명하게 갈린다. **3시간 투자로 600줄**을 만든 게 11일 전체를 가능하게 했다는 건, [[2026-07-25-why-software-factories-fail]]의 *"30분 계획이 몇 시간 리뷰를 아낀다"*의 **스케일 업 버전**이다.

### 핵심 전이 3 — 파이프라인이 내 methodology와 소름 돋게 겹친다 (한 곳만 빼고)

| Bun이 한 것 | 내 strict.md / 스킬 |
|---|---|
| 패턴 합의 → `PORTING.md` 3시간 | **Spec 단계** (Medium/Large 트랙) |
| 파일 3개 시범 변환 + **적대적 검토 2회** | **Spec 적대적 리뷰** + 3인 탈상관 find→verify |
| Claude 리뷰어를 **같은 세션 밖에서** | **서브에이전트 탈상관 리뷰** (자기가 쓴 걸 자기가 검토하지 않기) |
| git 충돌을 **worktree 4개**로 분산 | `mangolove-subagent-worktree` **격리 서브에이전트** |
| 크레이트별 병렬 에러 수정 | 병렬 서브에이전트 + 메인 세션 재검증 |
| 테스트 → CI → 병합 | **DoD 게이트** (실행 가능한 체크로 외부화) |

**한 곳만 정면으로 어긋난다.** 내 strict.md는 이렇게 못 박고 있다:

> *"'한 PR로 다 갈아엎기'는 **금지** — Medium/Large의 큰 변경은 Compatibility Layer / Module-by-Module Port / Branch by Abstraction 중 하나를 선택해야 한다."*

**Bun은 셋 중 아무것도 안 했다.** 빅뱅 재작성이었다. 그런데 내 규칙이 존재하는 이유를 되짚어보면 — 빅뱅이 금지된 건 *본질적으로 나빠서*가 아니라, **오래 걸리는 동안 원본이 계속 움직이고 롤백 지점이 없어서**다. 그 전제가 **11일이면 상당 부분 무너진다.** 브랜치가 1년 떠 있으면 재앙이지만 11일이면 관리 가능하고, 테스트 스위트가 정답지 역할을 하면 각 단계가 곧 롤백 가능 지점이 된다.

**그래서 규칙을 폐기하는 게 아니라 조건을 붙이는 게 맞다:**

> 빅뱅 재작성 금지 — **단, 아래 셋을 모두 만족하면 예외**:
> ①동작 동등성을 판정하는 테스트 스위트가 존재하고 ②변환 계약(`PORTING.md` 같은)이 사전에 합의됐으며 ③전체 소요가 원본 변경 속도보다 짧을 것.
> 셋 중 하나라도 없으면 기존 3전략 중 하나를 택한다.

이게 이번 글에서 내가 얻은 **가장 실질적인 변경 사항**이다.

### 핵심 전이 4 — 캐시 720억 토큰: 이 배율은 **프롬프트 캐싱 경제학 위에 서 있다**

토큰 내역을 다시 보자 — 비캐시 입력 **59억** vs **캐시 읽기 720억**. 즉 **입력의 약 92%가 캐시에서 읽혔다.** 캐시 읽기가 정가의 ~10% 수준이라는 걸 감안하면, 캐싱이 없었을 때 이 작업의 비용은 **$165,000이 아니라 몇 배**였을 것이다.

이건 [[2026-07-13-harness-token-overhead-instrument-your-own-boundary]]가 말한 *"내 경계의 토큰을 직접 계측하라"*의 **가장 극적인 사례**다. 그리고 [[2026-07-25-claude-opus-5-release]]에서 내가 실측 항목으로 적어둔 것(**캐시 최소 길이 1024→512**, `cache_read_input_tokens`)이 정확히 이 축이다 — **대규모 에이전트 작업의 경제성은 모델 가격표가 아니라 캐시 적중률이 결정한다.** 64개 에이전트가 같은 `PORTING.md`와 같은 코드 컨텍스트를 공유했기 때문에 캐시가 그렇게 먹혔다는 점도 중요하다: **공통 접두사를 설계한 것 자체가 비용 설계**였다.

### 핵심 전이 5 — 정직한 급소: **"11일"은 이식 완료까지지, 안정화까지가 아니다**

[[2026-07-25-why-software-factories-fail]]가 말한 *"코드베이스 건강성 악화는 3~6개월 뒤 표면화"*와 [[2026-07-24-software-factories-light-and-dark]]의 *"이해 부채는 조용히 늦게 터진다"*를 여기에 그대로 적용하면, **이 사례의 진짜 채점은 아직 안 끝났다.**

물어야 할 질문들:
- 6,500 커밋으로 들어온 53만 줄의 Rust를 **팀이 실제로 이해하고 있는가?**
- CI는 통과했지만 **테스트가 커버하지 않는 동작**(성능 특성, 메모리 사용 패턴, 엣지 케이스)은?
- 다음 기능 개발 속도가 **이식 전보다 빨라졌는가, 느려졌는가?**

이건 회의가 아니라 **회고 항목**이다. 그리고 [[2026-07-25-nothing-works-and-everyone-is-euphoric]]의 렌즈로 보면 진짜 성공 지표는 "11일"이 아니라 **"크래시 걱정하며 잠드는 일이 실제로 없어졌는가"**다 — Jarred가 밝힌 동기가 바로 그거였으니까. 메모리 안전 언어로 옮겼으니 그 목표는 구조적으로 달성될 가능성이 높다. **그게 이 사례에서 가장 확실한 부분이다.**

## 호스피탈리티 / CRS 적용 포인트

온다(B2B 호스피탈리티/CRS)에 이 사례를 그대로 옮길 수는 없지만, **"정답지가 있는 작업"의 목록은 우리에게도 실재한다.**

- **먼저 물어야 할 질문: 우리에게 미뤄둔 마이그레이션이 있는가?** 이 글의 마지막 질문이 그대로 우리 질문이다. Java/Spring 버전 업, 레거시 배치의 재작성, 오래된 API의 표준화, 테스트가 두꺼운 모듈의 구조 개선 — **"1년짜리라 못 한다"고 접어둔 것들**의 재평가가 이 글의 실질 액션이다.
- **다만 조건 세 개를 먼저 채점한다.** ①**테스트 스위트가 동작 동등성을 판정할 수 있는가** — 이게 없으면 나머지는 무의미하다. 예약·요금·정산 같은 도메인은 오히려 유리하다(**입출력 계약이 명확하고 회귀 테스트를 만들 수 있다**). ②**코드베이스를 깊이 아는 주도자가 있는가.** ③**토큰 예산을 실패 가능성과 함께 승인받을 수 있는가.**
- **`PORTING.md`에 해당하는 것을 먼저 쓴다(전이 2).** 우리 도메인에서는 *변환 계약*이 곧 컨벤션 문서다 — 금지 의존성, 에러 처리 관례, 트랜잭션 경계, 네이밍. **여러 에이전트/여러 사람이 같은 방향으로 움직이게 하는 계약**만 남기고 나머지는 지운다.
- **`dry-run` 게이트는 그대로 유효하다.** Bun의 이식은 되돌리기 어려운 작업이 아니었다(브랜치에서 했고 테스트가 판정했다). 우리 도메인에서 **DB 스키마·정산·외부 write**가 얽히면 배율은 훨씬 낮아지고, 그때는 속도가 아니라 **롤백 가능성**이 설계 기준이다.
- **비용 계측을 먼저 붙인다(전이 4).** 대규모 에이전트 작업을 시도한다면 캐시 적중률(`cache_read_input_tokens`)부터 계기판에 올린다. **공통 접두사(계약 문서 + 코드 컨텍스트)를 공유하도록 설계하는 것이 곧 비용 절감 설계**다.
- **worktree 격리는 이미 우리 도구에 있다.** git 충돌을 worktree 4개로 분산한 건 `mangolove-subagent-worktree`가 하는 일과 같다 — **병렬 에이전트의 첫 번째 병목은 지능이 아니라 머지 충돌**이라는 게 이 사례의 실무 교훈이다.
