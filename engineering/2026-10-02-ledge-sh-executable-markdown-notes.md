# Ledge.sh - 실행 가능한 Markdown 노트

> 출처: [Ledge: Runnable Markdown notes](https://ledge.sh/) (ledge.sh) · GeekNews(id=34601) 경유 · 정리일 2026-10-02

> **출처 한계**: `ledge.sh`·`news.hada.io`·`news.ycombinator.com` 모두 이 세션에서 egress 차단돼 원문·Show HN 스레드를 직접 열람하지 못했다. WebSearch로 공식 소개 문구와 Show HN 토론(item id=49902382) 스니펫을 복수 쿼리로 교차확인해 재구성했다. 기능 설명(노트별 독립 쉘, SSH 원격 호스팅, 크로스플랫폼 지원)은 여러 검색 결과에서 일치해 신뢰도가 있다고 보지만, **정확한 라이선스 조항·가격 정책의 세부(완전 무료인지, 유료 플랜이 있는지)는 원문 대조 없이는 확정하지 못했다.**

## 한 줄 요약

**Ledge는 Markdown 노트 안에 적은 쉘 명령·코드·SQL 블록을 그 자리에서 실행하고 결과를 블록 바로 아래에 스트리밍하는 노트 앱이다. 각 노트가 독립된 쉘을 유지해 `cd`·환경 변수·활성화한 가상환경이 다음 실행에도 그대로 이어지고, `ledge-server`로 SSH 원격 머신에 연결하면 노트북을 닫아도 서버 쪽 작업이 계속된다 — "명령어를 복사해 터미널에 붙여넣는" 습관을 노트 자체의 실행 기능으로 대체하려는 도구다.**

## 핵심 포인트

- **코드 블록이 곧 실행 버튼** — 노트에 쉘·코드·SQL·AI 프롬프트 블록을 쓰고 ***⌘↩(또는 해당 단축키)를 누르면 결과가 블록 바로 아래에 실시간으로 표시***된다. 설명과 실행 절차가 한 문서 안에 공존한다.
- **노트별 독립 쉘 — 상태가 실행 간에 유지된다** — 각 노트는 ***자신만의 영속적인 쉘***을 가지며, 그 쉘에서의 `cd`, `export`한 환경 변수, 활성화한 가상환경(virtualenv)이 ***다음 코드 블록 실행에도 그대로 이어진다*** — 매번 새 터미널을 여는 게 아니라 하나의 작업 컨텍스트가 노트 안에 유지된다.
- **SSH로 원격 머신에 노트를 둘 수 있다** — `ledge-server`를 원격 머신에서 띄우면, 서버가 파일과 쉘을 보유하고 로컬 앱은 그 창 역할만 한다. ***SSH로 서버에 연결해 작업하면 노트북을 닫아도 작업이 계속되며***, 휴대전화 앱으로도 같은 서버의 노트를 열어 읽고 편집할 수 있다.
- **"복붙 터미널"을 없애는 용도** — 명령어를 설명과 분리해 터미널에 복사하는 대신, 프로젝트 실행·장애 대응·데이터 분석·호스팅 관리 절차를 설명+실행이 한 몸인 노트로 관리하는 용도로 제시된다.
- **크로스플랫폼, Bun 기반** — Mac(Apple Silicon)·Windows(WSL 필요)·Linux·iOS·Android를 지원하며, Bun과 Electrobun으로 만들어졌다. GitHub(`ledgesh/ledge`)에 코드가 공개돼 있다.
- **HN 반응 — 니치를 메운다는 호평과 CLI 한계 지적** — Show HN 토론에서는 ***"Observable Framework 같은 데이터 분석 도구와 터미널 앱 사이의 틈을 메운다"***는 호평, Emacs 사용자의 ***"org-babel 같은데 일반인도 쓸 수 있는 UI"***라는 평가, Markdown 기반이라 ***Ledge 없이도 일반 텍스트 에디터로 노트를 열 수 있다는 점***에 대한 긍정적 반응이 나왔다. 동시에 "CLI에서 코드 블록을 바로 실행할 수 없다"는 현재 CLI의 한계도 지적됐다.

**HN Show HN 스레드(item id=49902382)가 존재함은 WebSearch로 확인했으나, `news.ycombinator.com` 자체가 이 세션에서 차단돼 정확한 포인트·댓글 수는 확인하지 못했다.** 위 "CLI에서 코드 블록을 바로 실행할 수 없다"는 지적과 "org-babel과 비슷하다"는 평가는 검색 스니펫에서 반복 확인됐지만, 반대 의견이나 보안 우려(원격 쉘 접근 권한 모델 등)가 논의됐는지는 **원문 없이는 확인할 수 없다.** 신생 프로젝트(2026-09 공개)라 실사용 안정성에 대한 독립적 평가도 아직 축적되지 않은 것으로 보인다.

## 내 생각 · 적용점

### 핵심 전이 1 — "일반 텍스트 위기" 노트에 대한 반증 사례

**[[2026-09-24-plain-text-files-in-crisis]]**는 스마트폰이 일반 사용자를, 이제는 AI 에이전트가 개발자마저 일반 텍스트 편집에서 떼어놓고 있다고 경고했다. Ledge.sh는 그 반대 방향의 증거로 읽힌다 — ***일반 Markdown 파일에 "실행"이라는 레이어를 얹어서, 평문의 효용을 줄이는 게 아니라 늘렸다.*** HN 댓글이 짚은 "Ledge 없이도 평문 에디터로 열린다"는 지점이 정확히 그 노트의 우려("텍스트 편집기 생태계가 방치될 것")에 대한 반례다 — 텍스트 파일이 죽는 게 아니라, 텍스트 파일 위에 쌓이는 레이어가 다양해지는 쪽으로 진화하고 있다는 해석이 가능하다.

### 핵심 전이 2 — "클라이언트를 닫아도 작업은 계속된다"는 같은 패턴의 다른 레이어

**[[2026-10-01-nsl-nspawn-subsystem-for-linux]]**는 OS/컨테이너 레이어에서 "호스트는 깨끗하게, 개발 작업은 영속적인 원격 VM에"라는 패턴을 구현했다. Ledge.sh는 같은 패턴을 노트/쉘 레이어에서 구현한다 — SSH로 원격 머신에 붙어 작업하고, 로컬 클라이언트를 닫아도 서버 쪽 쉘과 상태는 그대로 유지된다. 플랫폼은 다르지만 ***"로컬 기기는 창일 뿐, 진짜 작업과 상태는 원격에 영속한다"***는 설계 원칙이 독립적으로 반복해서 등장한다.

## 호스피탈리티 / CRS 적용 포인트

온콜 런북·배포 체크리스트를 "복붙할 명령어 목록"이 아니라 "실행과 결과가 같이 남는 노트"로 관리한다면, 장애 대응 이력이 그대로 재현 가능한 문서가 된다는 원칙은 전이 가능하다 — 다음 번 같은 장애가 났을 때 "이 노트를 그대로 다시 실행해본다"가 가능해진다. 다만 온다가 이 구체적인 도구를 도입했다는 근거는 없고(직접 적용 사례 없음), Confluence/Notion 기반 런북 문화를 바꾸는 데는 조직적 전환 비용이 따른다는 점은 정직하게 밝힌다. 원격 쉘 접근 권한 모델이 운영 환경에 안전한지도 이번 조사로는 검증하지 못했다.
