# 토큰 압축의 착시: RTK에 회의적인 이유 — '절감 그래프만 있고 정확도 평가가 없다' (측정 함정·검증 라인)

> 출처: mroczek.dev (GeekNews 경유) · 정리일 2026-06-08

## 한 줄 요약

**AI 코딩 에이전트용 *터미널 출력 압축 도구 RTK*에 대한 비판. RTK는 *"60~90% 토큰 절감"*을 광고하지만, 저자는 이 수치가 ***실제 API 비용 절감을 의미하지 않으며 정확성·안정성에 위험***하다고 주장. ① *과장된 절감 — "60~90%"는 Bash 출력 일부만 줄인 것이고, 파일 읽기·저장소 컨텍스트·시스템 프롬프트 같은 더 큰 비용은 남음*. ② *정확성 — "조용한 실패(silent failure)"로 중요한 스택 트레이스·컴파일러 정보가 누락되어 에이전트가 불완전한 정보로 작동*. ③ ***부재한 검증 — 토큰 절감 그래프만 있고 실제 작업 성공률·SWE-bench식 정확도 평가가 없다***. ④ *운영 리스크 — Git·Cargo·npm 출력 형식 변화에 취약(정규식 파싱)*.**

## 핵심 포인트

- **"토큰 절감 ≠ 비용 절감 ≠ 정확도"** — *작은 부분만 압축, 더 큰 비용은 남음·추론 토큰 증가로 총 비용↑ 가능*. **[[2026-06-08-dont-trust-large-context-windows]] *"마케팅 숫자 vs 실효"*와 정합**.
- **"조용한 실패"의 위험** — *스택 트레이스·컴파일러 정보 누락을 에이전트가 모름*. **[[2026-06-08-agentic-code-review]] *"검증 무결성"*·[[2026-06-08-not-everyone-uses-ai-for-everything]] *"결정론적 출력을 LLM이 망침"*의 사례**.
- **"절감 그래프만, 정확도 평가 없음"** — *SWE-bench식 성공률 검증 부재*. **[[2026-06-08-lines-of-code-got-a-publicist]] *"허영 지표(채택률·절감) vs 검증된 성과"*의 도구 버전**.

## 인상 깊은 문장

> "Saved tokens aren't saved costs, and there's no accuracy benchmark — just a savings graph."
> (절약된 토큰은 절약된 비용이 아니고, 정확도 벤치마크도 없다 — 절감 그래프만 있을 뿐.)

## HN 토론 (댓글 전수 확인)

> GN⁺가 Hacker News를 큐레이션. **확인 — RTK 저자·옹호·비판 격론:**
- ***"LLM 마법 상자 산업 — 개발자가 엔지니어가 아니라 주문 외우는 마법사, 각자 자기 주문이 궁극의 토큰 절약법이라 확신"*** → ***"평가 하네스 안에 없는 아이디어는 대체로 별로"***.
- *RTK 옹호: "도구 출력이 큰 비중·390만 중 370만 절약이면 받음·필터 실패 시 원본으로 폴백·자주 쓰는 명령 소스 직접 봤고 신뢰"*.
- *비판: "절약된 토큰이 절약이 아닐 때도(플래그 제거→나중에 더 씀·도구 호출 1→3회)"·"정확성 보존만으론 부족, RTK가 성능 유지를 입증해야"·이슈 링크(silent failure)*.
- ***"핵심은 AI를 더 좋게 만든다는 도구는 많은데 실제로 더 잘 작동하는지 측정할 방법이 없다는 것·전부 감"***·*블라인드 A/B 테스트의 어려움·"정답당 비용으로 벤치마크해야"*.
- *글쓴이 등장: "rtk가 이상해 보여 썼다·정확도 언급 부재·경영진이 비용 최적화로 밀어붙이는 방식이 걸림"*. → 비판: *"왜 실제 사용 수치를 하나도 제시 안 했나"*.
- *"이 글도 데이터 거의 없고 LLM 생성 같음"*·*"2천 명 조직은 ~250만$, 우리는 절충을 알고 포크·벤치마크해 씀(맹목 아님)"*.

→ **무게중심**: *(1) **"측정 없이 토큰 절감만 광고하는 도구"에 대한 회의가 핵심**(평가 하네스가 기준). (2) 단 **옹호도 강함**(필터 실패 시 폴백·도구 출력 비중·조직 비용은 진짜). (3) **"정답당 비용으로 벤치마크해야"**가 건설적 합의. (4) 글 자체도 "데이터 없다"는 역비판.*

## 내 생각 · 적용점

### 5번째 라인업 *측정 함정·검증 라인* (친/axelk 축과 직교, 카운팅 무관)

*AI 능력 찬반*이 아니라 *AI 도구의 측정·검증*. 라인 자산(카운팅 무관). 부채 *−1 유지* (53:42 ≈ 1.27:1).

### 핵심 전이 1 — "토큰 절감은 허영 지표일 수 있다"

가장 전이력 높은 경고: ***"X% 토큰 절감" 광고는 [[2026-06-08-lines-of-code-got-a-publicist]] "코드 줄 수"·[[2026-06-08-anthropic-founders-playbook]] "오후 하나면 검증"처럼 허영 지표***일 수 있다 — *측정하기 쉬운 대리지표(토큰)를 목표로 삼되 실제 가치(정확도·성공률·총 비용)는 안 봄*. **AI 도구를 도입할 때 "토큰 절감" 그래프가 아니라 "작업 성공률·정답당 비용"을 물어야**. 세션 내내 반복된 *"산출이 아니라 가치를 측정"*의 도구 버전.

### 핵심 전이 2 — "조용한 실패 = 검증 무결성 훼손"

*압축이 스택 트레이스를 조용히 누락*시키는 건 [[2026-06-08-not-everyone-uses-ai-for-everything]] *"결정론적 출력을 LLM이 망침"*·[[2026-06-08-agentic-code-review]] *"테스트 고침(검증 무결성)"*과 같은 위험 — **검증 경로(컴파일러·테스트 출력)에 손실 압축을 두면 에이전트가 불완전 정보로 작동**. *"필터 실패 시 원본 폴백"*이 최소 안전장치이되, *검증에 영향을 주는 정보는 압축하지 말 것*([[2026-06-08-reuse-less-software]] *"중요 경로에 외부 의존성 두지 말라"*와 정합).

### 핵심 전이 3 — "평가 하네스가 기준" (블라인드 A/B)

HN의 건설적 합의: *"평가 하네스 안에 없는 아이디어는 대체로 별로·정답당 비용으로 벤치마크"*. 이는 [[2026-06-08-designing-loops-with-fable-5]] *"명확한 평가 기준"*·이 가든의 *링크 검증·전수 확인*과 같은 규율 — **AI 도구·프롬프트의 가치는 "느낌"이 아니라 "블라인드 A/B·평가 하네스"로**. 단 *"측정이 부실하면 테스트 자체가 무의미"*라는 메타 경계도.
