## 한 줄 요약

**TurboPython(원문 미확인)은 Python 문법으로 작성한 코드를 C++로 변환한 뒤 컴파일해, CPython 런타임·가비지 컬렉션·자동 참조 카운팅 없이 동작하는 독립 실행 파일·네이티브 라이브러리를 만들겠다는 정적 타입 언어·컴파일러다. 핵심은 Rust류의 소유권·빌림 모델을 Python 문법에 얹어 객체 수명을 컴파일 타임에 검사한다는 점이다.**

## 핵심 포인트

- **Python 문법 + 정적 타입** — 타입을 지정한 Python 코드를 C++로 변환한 뒤 컴파일해 네이티브 실행 파일·라이브러리를 생성한다고 설명된다.
- ***런타임 제거*** — 생성된 프로그램은 CPython 인터프리터·가비지 컬렉션(GC)·자동 참조 카운팅(ARC) 없이 실행된다고 주장한다.
- **소유권·빌림 모델** — 객체 수명을 소유권·빌림(ownership/borrow) 개념으로 관리하며, ***소유자보다 오래 살아남는 참조는 컴파일 단계에서 검사해 걸러낸다***는 설명이 있다.
- **`Own[T]` 소유권 이전** — `Own[T]`라는 타입으로 값의 소유권을 호출자나 컨테이너에 명시적으로 전달할 수 있다고 한다.
- **리스트 의미 변화** — Python의 리스트는 (참조로 동작하는) 같은 객체를 여러 번 담을 수 있지만, TurboPython의 리스트는 참조가 아니라 ***객체 자체를 보관***한다는, 기존 Python 사용자에겐 의미론적 전환이 필요한 차이가 있다고 설명된다.

## 내 생각 · 적용점

### 핵심 전이 1 — "타입을 지우지 않고 기계어까지 굳힌다"는 AOT 네이티브 컴파일 계열의 반복

[[2026-10-11-bun-aot-typescript-native-compiler]]가 다룬 Bun의 TypeScript AOT 실험도 핵심 전제가 "타입을 지우는 게 아니라 끝까지 들고 가서 JIT 없이 기계어로 굳힌다"였다. TurboPython이 Python에 하려는 일도 구조가 같다 — **동적 언어의 생산성과 네이티브 컴파일의 성능을 동시에 가지려는 시도가 TypeScript·Python 양쪽에서 거의 같은 시기에 반복되고 있다.** 다만 TurboPython은 한 걸음 더 나가 소유권·빌림까지 요구해, GC 제거의 대가로 Rust급 학습 곡선을 Python 사용자에게 지운다는 점이 다르다.

### 핵심 전이 2 — "참조 리스트"에서 "값 리스트"로의 전환은 공짜가 아니다

Python 리스트가 같은 객체의 참조를 여러 번 담을 수 있는 반면 TurboPython 리스트는 객체 자체를 보관한다는 차이는, 표면적으로는 "Python 문법"이라고 광고해도 실제로는 **의미론이 다른 별개의 언어를 배우는 것**이라는 신호다. 이런 "익숙한 문법 + 다른 의미론" 조합은 마이그레이션 비용을 과소평가하게 만들기 쉽다는 점에서, 새 언어·프레임워크 도입 전 "문법이 아니라 의미론이 얼마나 다른가"를 먼저 따져야 한다는 일반적 경계로 남는다.

## 호스피탈리티 / CRS 적용 포인트

직접 적용은 멀다. 온다의 CRS 스택이 Python으로 성능이 급한 네이티브 바이너리를 찍어낼 일은 당장 없다. 다만 전이 가능한 원칙 하나는 있다 — **GC·런타임 오버헤드가 실제 병목인지 먼저 측정하지 않고 "네이티브 컴파일"류의 해법에 뛰어드는 것은 순서가 틀렸다**는 원칙은, CRS의 실시간 재고 동기화·대량 요금 계산 경로에서 성능 이슈가 생길 때도 동일하게 적용된다.
