# Jane Street ASIC 리버스 엔지니어링 챌린지 (jestoph 외) — 기존 칩 설계 도구를 안 쓰고 SQLite 시뮬레이터·자체 HDL·파서를 처음부터 만든 이유

## 한 줄 요약

**Jane Street이 라벨 없는 GDS(칩 배치도) 파일 하나만 주고 "이 ASIC이 무슨 일을 하는지 알아내라"는 챌린지를 냈다. 참가자 jestoph는 gdstk 라이브러리와 SKY130 오픈소스 PDK 문서로 배치도의 도형·레이어·핀을 식별하고, 서로 맞닿은 배선을 그래프로 병합해 실행 가능한 Verilog 회로로 복원했다. 여기서 그치지 않고 기존 칩 설계 툴체인(상용 시뮬레이터 등)을 쓰는 대신 SQLite를 구동 엔진으로 삼은 회로 시뮬레이터, 회로 기술용 커스텀 언어와 그 파서, 검증 도구까지 전부 직접 만들었다 — 약 1만 개 부품·81종 셀로 이뤄진 회로에서, 모든 120비트 입력을 전수 조사하는 대신 출력 조건(성공 신호)을 역산해 정답 `(* TWO STARS *)`을 찾아냈다.**

## 핵심 포인트

- **입력은 물리 배치도뿐** — 회로도·넷리스트·기능 설명 전혀 없이 GDS 파일(칩 제조용 도형 데이터) 하나만 주어짐. Jane Street은 별도로 "두 개 시프트 레지스터+가산기+비교기, A+B=496이면 성공"이라는 워밍업용 소형 예제(회로도·넷리스트·GDS 셋 다 공개)를 함께 제공해 참가자가 자기 도구를 검증할 기준선을 마련해줬다.
- **1단계: 도형 → 소자 식별** — `gdstk`(GDS 파싱 Python 라이브러리)로 도형·레이어를 읽고, SKY130(오픈소스 130nm 공정 PDK) 문서를 대조해 각 도형이 어떤 표준 셀(`sky130_fd_sc_hd__` 접두 게이트류)인지, 핀이 어디인지 식별한다.
- **2단계: 배선 → 그래프 병합** — 물리적으로 맞닿은 배선(폴리곤)들을 하나의 net으로 묶어, 소자-net 관계를 그래프로 구성 — 이게 사실상 넷리스트 역추출이다.
- **3단계: 그래프 → 실행 가능한 회로** — 이 그래프를 Verilog로 변환해 시뮬레이션 가능한 형태로 만든다.
- **기존 툴체인을 안 쓴 이유(추정)** — 상용 EDA 툴은 무겁고 라이선스·설정 장벽이 있으며, 챌린지 규모(부품 ~1만·셀 81종)에서는 목적에 맞춘 경량 자체 시뮬레이터가 더 빠르게 반복 검증하기 유리했을 것으로 보인다. jestoph는 SQLite를 시뮬레이션 엔진 삼아 회로 상태를 테이블/쿼리로 다루는 파서·HDL·검증기 세트를 직접 구현했다(**"기존 도구 대신 목적에 맞는 최소 도구를 새로 짠다"**는 접근 자체가 이 글의 공학적 핵심).
- **전수 탐색이 아니라 역산** — 120비트 입력 공간을 전부 시도하는 건 비현실적이라, 출력(성공 신호)이 참이 되는 조건을 회로 구조에서 역으로 추적해 정답 입력을 좁혀나간다. "브루트포스 대신 구조를 읽고 필요조건을 좁힌다"는 전형적 리버스엔지니어링 전략.
- **상당한 우회·시행착오** — Slack 발췌가 명시하듯 이 과정에서 반복된 시행착오가 있었다는 점을 정직하게 서술하고 있어, 결과물이 매끄러운 일필휘지가 아니라 도구 자체를 여러 번 고쳐가며 얻은 결과임을 알 수 있다.

## 내 생각 · 적용점

### 핵심 전이 1 — "표준 도구가 없으면 최소 도구를 직접 만든다"는 태도의 반복

기존 EDA 툴체인 대신 SQLite 기반 자체 시뮬레이터·HDL·파서를 만든 선택은, [[2026-08-25-reverse-engineering-my-peripherals-ownership]]에서 Claude Opus 5로 주변기기 펌웨어를 직접 역공학해 "서명 검증이 실제로 언제 걸리는지"를 능동적으로 확인했던 태도와 같은 계열이다. 두 경우 모두 **"벤더/표준 도구가 보여주는 것"에 의존하지 않고, 필요한 최소 도구를 스스로 만들어 시스템의 실제 동작을 확인**한다. 리버스엔지니어링의 본질은 도구를 빌리는 게 아니라 검증 가능한 최소 도구를 스스로 갖추는 것이라는 원칙이 다시 확인된다.

### 핵심 전이 2 — LLM 정적 분석 리버싱과의 대비 — "정적 구조 읽기"라는 공통 전략

[[2026-08-24-qwen-27b-reverse-engineering-license-bypass]]에서는 로컬 LLM이 앱을 실행하지 않고 arm64 디스어셈블리를 정적 분석해 라이선스 키를 복원했다. 이번 챌린지도 회로를 "실제로 동작시켜보며" 찾는 게 아니라 **배치도(정적 구조)를 읽어 넷리스트를 역추출**한 뒤에야 시뮬레이션 단계로 넘어간다. 두 사례 모두 "실행 관찰"보다 "구조 분석"이 우선되는 리버스엔지니어링 전략의 반복이며, 전자는 사람이 도구를 만들었고 후자는 LLM이 그 분석 자체를 수행했다는 차이가 다음 단계(구조 분석 자동화에 LLM을 붙이는 것)를 자연스럽게 상상하게 만든다.

### 핵심 전이 3 — 전수 탐색 대신 역산하는 습관

120비트를 브루트포스하지 않고 출력 조건에서 역산해 입력을 좁히는 전략은, 디버깅·최적화 전반에서 "모든 경우를 실행해보지 말고 구조에서 필요조건을 도출하라"는 일반 원칙의 하드웨어 버전이다.

## 호스피탈리티 / CRS 적용 포인트

직접 적용은 멀다 — 온다는 ASIC이나 하드웨어 리버스엔지니어링을 다루지 않는다. 다만 원칙 수준 전이: **레거시 PMS/채널 연동처럼 문서화되지 않은 외부 시스템의 동작을 파악해야 할 때, 범용 통합 도구에 기대기보다 "그 시스템의 응답 패턴만 정확히 재현하는 최소 시뮬레이터/모킹 도구"를 직접 만드는 편이 더 정확하고 빠른 검증 루프를 준다**는 점은 이 사례에서 배울 만하다.
