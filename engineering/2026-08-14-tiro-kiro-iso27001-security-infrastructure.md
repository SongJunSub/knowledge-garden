# Tiro가 Kiro와 함께 보안 인프라를 만들고 ISO 27001을 받은 과정 (더플레이토 · AWS Korea)

> 출처: [Tiro가 Kiro로 보안 인프라를 구축하고 ISO 27001 인증을 획득한 여정](https://aws.amazon.com/ko/blogs/tech/tiro-security-infrastructure-with-kiro-iso27001-certification/) (AWS Korea Tech Blog · 신정섭, 김민해 · 2026-08-14) · 정리일 2026-08-14
> **이해관계 고지**: **AWS 가 발행한 고객 사례**이고 **Kiro 는 AWS 제품**이다. "Kiro 덕분에 됐다"는 서사는 발행자의 사업 이익과 정렬돼 있다(→ 읽을 때 감안 ①).
> **GeekNews 경유가 아니라 원문 직접**이고, **댓글이 없다.** 외부의 반박이나 검증을 볼 수 없다.

## 한 줄 요약

**AI 회의록 서비스 Tiro 를 만드는 더플레이토가, 일본 엔터프라이즈 시장 진출을 앞두고 ISO 27001 을 준비하면서 AWS 의 코딩 에이전트 Kiro 로 보안 인프라를 구축한 기록이다. 문제 제기가 이 글의 값이다. 엔지니어 한 명이 하루 50~100 커밋을 쓰는 게 낯설지 않게 된 시대에 생기는 건 속도지 안전이 아니다. 그래서 답을 "AI 를 더 믿는다"가 아니라 "AI 가 안전하게 움직일 수 있는 경계를 먼저 그린다"로 잡았다. 네 개의 가드레일이 그 경계다. ①모든 작업은 읽기 전용 진단으로 시작한다 ②변경은 requirements.md / design.md / tasks.md 로 쪼개 스펙을 먼저 만든다 ③실제 apply 는 사람이 검토하고 승인한 뒤에만 한다 ④변경 전후 상태를 evidence/ 폴더에 before.json / after.json 으로 남기고 통제 항목과 연결한다. AWS 계정을 Management·Security·Ops·Production·Development 로 쪼개 모든 계정의 API 활동을 Security 계정에 모으고, 204개 ISO 27001 통제 항목을 플랫폼으로 실시간 추적했다. 결과는 약 18주, Stage 2 심사 Major 부적합 0건, 정책 문서 23개, 인프라 통제 30여 건 개선, 그리고 이 인프라 작업의 대부분을 엔지니어 한 명이 Kiro 와 함께 했다.**

## 핵심 포인트

- **회사·제품**: **더플레이토**의 AI 회의록 서비스 **Tiro**. 일본 엔터프라이즈 시장 진출을 앞두고 인증이 필요했다.
- **문제 제기**: ***"한 명의 엔지니어가 하루에 50~100개의 커밋을 작성하는 일도 더 이상 낯설지 않게 되었습니다."*** 그리고 그렇게 해서 생기는 건 **속도지 안전이 아니다.**
- **전제**: ***"AI 에이전트는 통제 밖의 실행자가 아니라 통제 안의 작업 파트너여야 합니다."***
- **Kiro 에게 준 것**: 워크스페이스(Terraform 코드·스크립트), 셸 명령(AWS CLI, `terraform plan`, git), **MCP 로 AWS 문서**, **Agent Hooks**(파일 저장·스펙 실행·도구 호출 시 이벤트 자동화), **Steering 파일**(`.kiro/steering/` 에 상시 적용되는 운영 규칙·기술 스택 제약·금지 조건).
- **가드레일 ①읽기 전용 우선**: ***"어떤 리소스도 생성, 수정, 삭제하지 마세요."*** 모든 작업이 진단부터 시작한다.
- **가드레일 ②스펙 주도**: **requirements.md**(컴플라이언스 요구사항과 수용 기준), **design.md**(아키텍처·롤백 전략·통합 방식), **tasks.md**(읽기 전용 진단 → 승인 게이트 → 검증까지의 단계). **결정 기록이 추적 가능해진다.**
- **가드레일 ③감독 모드**: ***"apply 는 사람이 검토하고 승인한 뒤에만 진행했습니다."*** 자동화가 단독으로 변경을 실행하지 않는다.
- **가드레일 ④증거 보존**: ***"변경 전후 상태를 evidence/ 폴더에 before.json 과 after.json 으로 저장해."*** 통제 항목과 연결한다.
- **증거의 연결 고리**: ***"변경 전 상태, 변경 계획, 사람의 승인, 변경 후 검증 결과가 연결되어야"*** 한다.
- **멀티 계정 구조**: **Management**(조직·빌링), **Security**(중앙 로깅·컴플라이언스·감사), **Ops**(공용 운영), **Production**(고객 대면), **Development**(실험·AI 보조 코딩). **모든 계정의 API 활동이 Security 계정으로 집계**된다.
- **쓰인 AWS 서비스**: CloudTrail, AWS Config, GuardDuty, IAM Access Analyzer, Security Hub, Organizations, 그리고 EBS·EFS·S3 암호화와 VPC·EKS 네트워크·컨테이너 통제.
- **결과 수치**: **약 18주**(최악 추정보다 4개월 빠름), **Stage 2 심사 Major 부적합 0건**, **정책 문서 23개**, **인프라 통제 30여 건 개선**, **204개 ISO 27001 통제 항목** 실시간 추적, **인프라 작업 대부분을 엔지니어 1명이 Kiro 와 함께**.
- **추가 확보**: SOC 2 Type 1(Type 2 관찰 기간 진행 중), CIS Controls v8.1 매핑, NIST AI RMF 정렬, NIST CSF 매핑.
- **운영 원칙**: **직무 분리가 AI 워크플로에도 적용된다.** 통제는 ***"코드 리뷰, 인프라 변경, 계정 접근, 로그 보관, 침해 탐지 같은 일상 운영 흐름 속에서 실제로 작동해야"*** 한다.
- **닫는 문장**: ***"보안은 속도를 늦추는 장치가 아니라, 더 오래 더 빠르게 달리기 위한 운영 기반입니다."***

## 댓글

**댓글 없음.** AWS 공식 블로그이고 GeekNews 경유가 아니라 **외부 반박이나 독립 검증을 볼 수 없다.** 이 노트에서 비판적 검토는 전부 내가 붙인 것이다.

**읽을 때 감안**
- ①**AWS 가 발행한 고객 사례이고 Kiro 는 AWS 제품이다.** "Kiro 로 이걸 해냈다"는 서사는 **발행자의 사업 이익과 정렬**돼 있다. 검사 도구 기준으로 입증 책임이 올라간다. **다만 정렬과 무관하게 남는 정보가 크다**(→ 전이 1). 네 개의 가드레일과 멀티 계정 구조는 **Kiro 를 안 써도 그대로 쓸 수 있는 설계**다.
- ②**반사실이 없다.** "Kiro 없이 했으면 몇 주 걸렸을까"에 대한 비교 대상이 없다. **18주가 4개월 빠르다는 건 자체 추정치와의 비교**이고, 그 추정치의 근거는 나오지 않는다.
- ③**"Kiro 덕분"과 "규율 덕분"이 분리되지 않는다.** 스펙 주도·읽기 전용 우선·승인 게이트·증거 보존은 **도구가 아니라 방법론**이다. 성과의 어느 정도가 도구이고 어느 정도가 규율인지 이 글로는 알 수 없다. **개인적으로는 규율 쪽 기여가 더 크다고 본다**(→ 전이 2).
- ④**인증 통과는 통제의 존재를 증명하지 실제 보안을 증명하지 않는다.** ISO 27001 Stage 2 Major 부적합 0건은 **문서화된 통제가 심사 시점에 작동했다**는 뜻이다. 이 글도 그걸 알고 ***"일상 운영 흐름 속에서 실제로 작동해야"***라고 쓰지만, **그 작동을 보여주는 사후 데이터는 아직 없다.**
- ⑤**스타트업 규모의 사례**다. 엔지니어 1명이 인프라 대부분을 했다는 건 인상적인 동시에, **조정 비용이 거의 없는 조건**이었다는 뜻이기도 하다. 팀이 커지면 같은 방식이 그대로 작동하는지는 다른 문제다.
- ⑥**AI 가 만든 산출물의 품질에 대한 독립 검증이 없다.** Terraform 코드와 정책 문서 23개의 질을 판정한 건 결국 **같은 팀과 심사원**이다.

## 내 생각 · 적용점

### 핵심 전이 1: 발행자 정렬과 무관하게 남는 게 크다. 네 가드레일이 그대로 재사용 가능한 설계다

**검사 도구를 먼저 적용한다.** AWS 가 발행했고 Kiro 는 AWS 제품이다. 정렬은 자명하다. **그래서 물어야 할 건 "믿을 만한가"가 아니라 "정렬과 무관하게 남는 정보가 무엇인가"다.**

**남는 게 크다.** 네 개의 가드레일은 **Kiro 에 대한 이야기가 아니라 에이전트 일반에 대한 이야기**다.

| 가드레일 | 일반화한 형태 |
|---|---|
| 읽기 전용 우선 | **첫 접촉은 관측만.** 권한이 아니라 **작업 순서**로 안전을 만든다 |
| 스펙 주도 분리 | **요구사항·설계·작업목록을 실행 전에 파일로 고정.** 결정 기록이 추적 가능해진다 |
| 감독 모드 | **되돌리기 어려운 작업의 실행 게이트를 사람이 쥔다** |
| 증거 보존 | **변경 전후 상태를 산출물로 남기고 통제 항목과 연결한다** |

**이건 그대로 우리 방법론의 문장이다.** dry-run 게이트, 최종 승인, Spec 선행, 산출물 경로와 함께 보고. **같은 결론에 다른 조직이 독립적으로 도달했다는 게 이 글의 값**이고, 그 값은 Kiro 를 쓰든 안 쓰든 남는다.

**특히 ①번이 제일 값싸고 강하다.** ***"어떤 리소스도 생성, 수정, 삭제하지 마세요"***는 IAM 정책도 아니고 샌드박스도 아니다. **작업의 첫 단계를 관측으로 못박은 것뿐**인데, **에이전트 사고의 상당수가 "이해하기 전에 바꾸는" 데서 나온다**는 걸 생각하면 비용 대비 효과가 가장 크다.

### 핵심 전이 2: 어제 정리한 두 설계가 정확히 반대편이고, 이번 주에 나란히 왔다

**어제 [[2026-08-13-grok-bot-agent-teammate]]를 정리하면서 이렇게 썼다.** 사흘간 세 번 확인한 원칙(원본 자격증명 미보관 · vault egress 치환 · 본 적 없는 비밀은 트레이스에도 안 남는다)의 **정확한 반대 설계**라고. HN 이 독립적으로 같은 우려에 도달했다고.

**오늘 그 반대편의 반대편이 왔다.** 같은 문장을 두 회사가 정반대로 쓴다.

| | Grok Bot | Tiro + Kiro |
|---|---|---|
| **에이전트의 위치** | ***"동료에게 지시하듯"*** 맡기고 자율 수행 | ***"통제 밖의 실행자가 아니라 통제 안의 작업 파트너"*** |
| **자격증명** | 앱·웹사이트에 **사용자처럼 로그인** | 워크스페이스·셸·MCP 로 **범위를 명시해 부여** |
| **실행 권한** | 승인이 필요할 때 돌아옴(**범위 비공개**) | **apply 는 사람 승인 뒤에만**(범위 명시) |
| **첫 접촉** | 즉시 조작 | **읽기 전용 진단부터** |
| **기록** | 예약 루틴으로 저장 | **before.json / after.json 을 통제 항목과 연결** |

**두 설계가 커버리지와 격리 사이에서 반대편을 골랐다.** 어제 나는 Grok Bot 을 "무지가 아니라 트레이드오프이고 커버리지를 골랐다"고 적었다. **오늘 사례는 격리를 골랐을 때 무엇을 얻는지 보여준다: ISO 27001 Major 부적합 0건과 SOC 2 Type 1.** 즉 **격리 쪽 선택의 대가가 속도 손실이 아니라 인증이라는 자산**이었다는 것.

**그리고 [[2026-08-10-doordash-ai-agent-gateway]]와 계열이 같다.** DoorDash 는 200개 이상의 MCP 서버를 게이트웨이로 중앙화해 자격증명을 대신 주입했고, 여기는 계정 경계와 승인 게이트로 같은 일을 한다. **DoorDash 노트의 교훈이 그대로 걸린다: 통제된 경로가 셀프서비스가 아니면 팀은 우회한다.** 이 글에는 그 관점이 없다. **엔지니어 1명 규모라 우회 유인이 안 생겼을 뿐일 수 있고, 팀이 커질 때 첫 시험대가 거기일 것이다.**

### 핵심 전이 3: 하루 50~100 커밋이라는 문제 정의가 이번 주 데이터와 정확히 맞물린다

**이 글의 출발점이 어제 정리한 두 논문·두 에세이와 같은 현상이다.**

- [[2026-08-13-ai-removing-middle-class-of-software-engineering]]: 리뷰 화면의 **`+24506 -3938`**, 하루 끝에 **남은 PR 13개**. AI 가 **나쁜 결정의 속도 제한기를 없앤다**.
- [[2026-08-13-from-human-centric-to-agentic-code-review]]: **급속 도입군은 리뷰 시간이 KLOC 당 4.5일 줄었는데 품질 지표는 안 따라왔다.**
- [[2026-08-13-human-ai-synergy-agentic-code-review]]: **채택된 AI 제안이 복잡도와 크기를 더 크게 늘렸다.**

**셋 다 "속도가 늘고 안전이 안 는다"를 각각 다른 방식으로 말한다.** 그리고 이 글의 첫 문장이 **정확히 그 진단**이다. ***"속도는 생기지만 안전은 아니다."***

**차이는 다음 문장이다.** 앞의 셋은 **진단에서 멈추거나(논문) 도구를 끊는 선택으로 갔다**([[2026-08-13-im-done-using-ai]]). **여기는 통제 구조를 설계했다.** 그리고 [[2026-08-14-the-human-is-the-loop]]의 처방("사람이 루프이고 에이전트를 의도적으로 불러들인다")을 **조직 수준으로 옮긴 게 정확히 이 네 가드레일**이다.

**이번 주 축이 여기서 닫힌다.**
- 진단(논문 두 편) → 개인의 이탈(Brett Codes) → 개인의 처방(Fitzgerald) → **조직의 처방(이 글)**.

### 핵심 전이 4: 감사 증거를 문서가 아니라 링크로 정의한 게 이 사례의 진짜 이전 가능한 부분이다

***"변경 전 상태, 변경 계획, 사람의 승인, 변경 후 검증 결과가 연결되어야"*** 한다는 문장이 이 글에서 가장 재사용 가능한 문장이라고 본다.

**통상적인 컴플라이언스 대응은 심사 직전에 증거를 만든다.** 스크린샷을 찍고 문서를 쓰고 표를 채운다. **여기는 그걸 뒤집었다.** 변경을 할 때마다 **before.json / after.json 이 자동으로 남고 통제 항목에 연결**되니, **증거 수집이 시점 작업이 아니라 상시 부산물**이 된다. Terraform 이 관리하는 인프라의 **불변 변경 이력이 그 자체로 감사 증거**가 된다는 것도 같은 구조다.

**그리고 이건 우리 방법론의 "PASS 만 보고 금지, 산출물 경로와 함께 보고"와 같은 원리다.** 검증을 **주장이 아니라 링크 가능한 산출물**로 만드는 것. **차이는 이 사례가 그걸 도구 체인에 박아 넣어서 사람이 기억하지 않아도 남게 만들었다는 점**이다. [[2026-08-08-eval-driven-development-airbnb]]가 평가를 개발 루프에 박아 넣은 것과 같은 형태다.

**신뢰성 게이트 관점으로 보면 정확히 옳은 방향이다.** "증거를 남기자"를 프롬프트나 규칙 문서에 적어두면 잊히고, **Agent Hooks 로 파일 저장·스펙 실행 시점에 자동 실행하면 잊힐 수 없다.** 강제 표현을 코드로 옮긴 사례다.

### 핵심 전이 5: 남는 질문은 "이게 도구인가 규율인가"이고, 이 글은 답하지 않는다

**정직하게 남겨야 할 부분이다.** 네 가드레일 중 **Kiro 여야만 되는 건 사실상 없다.**

- 읽기 전용 우선: 프롬프트와 작업 순서의 문제.
- 스펙 주도: `requirements.md` / `design.md` / `tasks.md` 는 Kiro 의 기능이지만, **같은 파일 세 개를 손으로 만들어도 된다.**
- 감독 모드: `terraform plan` → 사람 승인 → `apply` 는 **에이전트 없이도 표준 관행**이다.
- 증거 보존: Hooks 로 자동화했지만 **CI 단계로도 가능**하다.

**Kiro 가 실제로 기여한 건 이 넷을 한 도구 안에서 강제 가능하게 묶었다는 점**이고, 그건 작지 않다. **하지만 "Kiro 를 도입하면 18주에 ISO 27001"이라고 읽으면 인과를 잘못 읽는 것**이다. **선행 조건은 이 팀이 가드레일을 먼저 설계했다는 것**이고, 그 설계는 도구가 만들어주지 않는다.

**이건 이번 시즌 반복 확인한 형태이기도 하다.** [[2026-08-13-from-human-centric-to-agentic-code-review]]에서 **도구 선택보다 도입 곡선이 결과를 갈랐다**고 정리했다. 여기서도 같다. **도구가 아니라 도입 방식이 결과를 만들었다고 읽는 게 데이터에 더 맞는다.**

## 호스피탈리티 / CRS 적용 포인트

**온다는 B2B 호스피탈리티/CRS 이고 파트너사의 예약·정산·고객 데이터를 다룬다. 이 사례는 직접 적용도가 이번 주 노트 중 가장 높다.**

- **네 가드레일을 그대로 쓴다.** 도구와 무관하게 성립한다.
  - **읽기 전용 우선**: 에이전트가 운영 리소스를 처음 만날 때는 **조회만**. 이건 이미 우리 DB 규칙(조회는 SELECT/SHOW/DESCRIBE 만)과 같은 원리인데, **인프라와 외부 API 까지 확장**할 여지가 있다.
  - **스펙 주도**: 되돌리기 어려운 작업은 **요구사항·설계·작업목록을 실행 전에 파일로 고정**하고, 그 파일이 곧 리뷰 대상이 된다.
  - **감독 모드**: `apply`, 대량 UPDATE, 외부 채널 API write 는 **사람 승인 뒤에만**. 이미 규칙이지만 **에이전트 도구 체인에 박혀 있는지**는 별개 문제다.
  - **증거 보존**: 변경 전후 상태를 JSON 으로 남기는 건 **컴플라이언스가 아니라 장애 대응에도 쓰인다.** 요금 정책이나 재고 설정을 바꾼 뒤 문제가 생겼을 때 `before.json` 이 있으면 복구가 즉시 가능하다.
- **증거 수집을 시점 작업에서 상시 부산물로 바꾼다.** 파트너사 보안 실사나 인증 요구가 들어올 때마다 증거를 만드는 구조라면, **변경 시점에 자동으로 남게 하는 쪽이 총비용이 낮다.**
- **계정 경계를 운영 흐름과 맞춘다.** Security 계정으로 로그를 집계하는 구조는 규모와 무관하게 유효하다. **AI 보조 코딩을 Development 계정에 격리한 게 특히 참고할 만하다.**
- **인증 취득 자체가 영업 자산이라는 점.** 일본 엔터프라이즈 진출이 동기였다는 게 명시돼 있다. **B2B 호스피탈리티에서도 파트너사 실사 통과 시간이 곧 계약 리드타임**이고, **상시 증거 구조가 그 시간을 줄인다.**
- **다만 우회 유인을 미리 본다.** [[2026-08-10-doordash-ai-agent-gateway]]의 교훈대로, **통제 경로가 불편하면 팀은 우회한다.** 승인 게이트를 도입할 때 **"급할 때 어떻게 하는가"의 정식 경로**를 같이 만들어두지 않으면 그 경로가 비공식으로 생긴다.
- **인증 통과와 실제 보안을 구분해서 말한다.** 대외적으로는 인증이 신호지만, 내부적으로는 ***"일상 운영 흐름 속에서 실제로 작동"***하는지가 별개 질문이다.
