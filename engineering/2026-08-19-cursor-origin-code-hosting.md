# Cursor, Origin 코드 호스팅 시작 (cursor.com)

> 출처: [Origin code hosting](https://cursor.com/changelog/origin-code-hosting) (cursor.com changelog · GeekNews 경유, 제출자 princox) · 정리일 2026-08-19
> **얼리 베타**이고 ***"에이전트 네이티브 기능은 곧 나온다"***고 명시한다. 지금은 기반만.
> **hada 댓글 2개**(dhy0613 + GN⁺ HN 큐레이션). **큐레이션에 무거운 항목이 있다.**

## 한 줄 요약

**Cursor 가 코드 호스팅을 시작했는데 대체를 시도하지 않는다. 푸시는 계속 GitHub 로 가고, 거기서 시작된 것에 대해서는 GitHub 이 진실 공급원으로 남는다. Cursor 에서 만든 변경이 GitHub 에 올라가고 반대도 수 초 안에 되는 양방향 동기화다. 새 Codebase 탭이 허브가 되고, CLI 로 로컬 프로젝트를 Origin 에 푸시하거나 클론한다. 에이전트는 브라우징 중인 코드에 대해 질문에 답하고, 변경하고, PR 을 갱신하고, 브랜치를 푸시한다. 통합은 셋이 살아 있다. Vercel 이 PR 마다 프리뷰 배포를 만들고, Depot 과 Buildkite 가 기존 GitHub Actions 워크플로를 실행한다. 관리자가 opt-out 한 엔터프라이즈를 빼면 전 유료 플랜에 오늘부터 배포된다. 그러면 질문이 하나 남는다. GitHub 이 진실 공급원인데 왜 사본이 필요한가. 답은 에이전트가 붙을 표면이 자기 인프라에 있어야 하기 때문이고, 어제 정리한 대로 에이전트 작업에서 읽기가 비용의 지배항이다.**

## 핵심 포인트

- **성격**: **얼리 베타**, **전 유료 플랜**(관리자가 opt-out 한 엔터프라이즈 제외). ***"에이전트 네이티브 기능은 곧 나온다."***
- **GitHub 과의 관계가 핵심**: ***"푸시는 계속 GitHub 로 가고, 거기서 시작된 것에 대해서는 GitHub 이 진실 공급원으로 남는다."*** **대체가 아니라 병행이다.**
- **양방향 동기화**: Cursor 에서 만든 변경이 GitHub 에 올라가고 반대도 **수 초 안에.**
- **Codebase 탭**: Origin 저장소의 허브. 인터페이스에서 저장소를 만들고 **CLI 로 클론·푸시.** **저장소 URL 의 일부가 되는 codebase 이름**이 필요하다.
- **에이전트가 하는 일**: ***"브라우징 중인 코드에 대해 Cursor 에게 물어보라. 답할 수도, 변경할 수도, PR 을 갱신할 수도, 브랜치를 푸시할 수도 있다."***
- **통합 셋**: **Vercel**(PR 마다 프리뷰 배포), **Depot**·**Buildkite**(기존 GitHub Actions 워크플로 실행).

## 내 생각 · 적용점

### 핵심 전이 1: dhy0613 의 질문에 어제 노트가 답을 준다

***"여러 플랫폼이 최근 코드 저장소를 내놓는 동기가 무엇인가."***

**어제 [[2026-08-18-flex-modules-agents-read-less]]에서 확인한 게 답의 한 조각이라고 본다.** 에이전트 작업에서 **읽기가 비용의 지배항**이고, 같은 작업이 13,891 대 34,695 토큰으로 갈렸다.

**그러면 코드가 어디 있느냐가 비용 구조를 바꾼다.**
- 코드가 **남의 인프라**에 있으면: API 로 가져오고, 레이트리밋에 걸리고, 인덱싱을 매번 다시 하거나 별도로 유지해야 한다.
- 코드가 **자기 인프라**에 있으면: **인덱스를 상시 유지하고, 검색을 자기 방식으로 하고, 캐시를 자기가 관리한다.**

**그리고 [[2026-08-16-maximizing-claude-code-sessions]]의 가격 구조로 보면 그게 곧 돈이다.** 캐시 읽기가 입력의 0.1배인데, **캐시를 유지하려면 컨텍스트가 자기 통제 아래 있어야** 한다.

**그러면 이 발표가 "GitHub 과 싸우겠다"가 아니라 "에이전트를 싸게 돌리겠다"로 읽힌다.** 진실 공급원을 양보한 게 그 증거다. **필요한 건 권위가 아니라 사본이다.** (내 추론이고 changelog 에 이런 설명이 없다.)

### 핵심 전이 2: [[2026-08-04-github-has-alternatives-no-replacement]]가 예측한 형태다

**8월 4일 노트의 요지가 "대안은 있지만 대체는 없다"였다.** GitHub 을 떠날 수 없는 이유가 기능이 아니라 **생태계와 통합**이라는 것.

**Cursor 가 그 결론을 그대로 받아들인 설계를 냈다.** 대체를 시도하지 않고 **옆에 붙는다.** 그리고 통합 셋(Vercel, Depot, Buildkite)이 전부 **기존 GitHub Actions 워크플로를 실행**한다는 게 그 태도를 보여준다. **GitHub 의 CI 정의를 자기 것으로 바꾸지 않는다.**

**HN 의 두 의견이 정확히 그 긴장을 말한다.** 한쪽은 ***"또 하나의 중앙집중형 대안"***이 필요 없다고 하고, 다른 쪽은 **GitHub 생태계가 실질적 표준화 필요를 만든다**고 한다. **둘 다 맞고, Cursor 의 답이 "그러면 표준은 두고 사본만 갖는다"이다.**

**일반화: 네트워크 효과가 강한 자리에서는 대체보다 병행이 싸다.** 그리고 병행의 대가는 **동기화 복잡성**인데, 이 발표가 그걸 ***"수 초 안에"***로만 처리한다. **양방향 동기화의 충돌 처리가 어떻게 되는지가 없다.**

**앞의 셋은 무언가가 지나가는 이야기였고, 이건 머무르는 이야기다.** 프롬프트는 통과하고 사라지지만 **저장소는 남는다.**

**그리고 [[2026-07-13-grok-cli-wire-analysis-consent-and-trust-boundaries]]가 그 위험의 선례다.** 거기서 **동의 없이 전체 코드베이스가 업로드된 사건**을 다뤘고, HN 이 이 발표 아래에서 그걸 다시 꺼낸다.

**코드 호스팅이 그 위험을 구조화한다는 게 양면이다.**
- **좋은 쪽**: 업로드가 **명시적 행위**가 된다. 몰래 올라가는 게 아니라 내가 저장소를 만든다.
- **나쁜 쪽**: 동의 범위가 **파일 단위가 아니라 저장소 전체**가 되고, **한 번 동의하면 계속 유효**하다.

**실무 규칙: 무엇이 지나가는가와 무엇이 머무르는가를 나눠서 본다.** 머무르는 것에는 **보존 기간과 삭제 절차**를 계약에 넣어야 하고, **이 changelog 에 그게 없다.**

### 핵심 전이 4: 이름 충돌 지적이 사소해 보이는데 사소하지 않다

**HN 의 ***"Origin 이라는 이름이 git 의 `origin` 과 겹쳐 LLM 해석에 모호성을 만든다"***가 재밌는 지적이다.**

**git 에서 `origin` 은 기본 원격 저장소 이름**이고, 모든 문서와 명령에 등장한다. 그러면 **"Origin 에 푸시해"라는 지시가 두 가지로 읽힌다.** 사람은 맥락으로 구분하는데, **에이전트에게는 그 맥락이 프롬프트에 없으면 없다.**

**그리고 이게 이번 시즌 반복 확인한 형태의 작은 판본이다.** [[2026-08-18-gpt-5-6-sol-best-vision-model]]에서 **좌표 형식 하나가 15 mAP 를 좌우**했고, [[2026-08-16-working-with-ai-feels-like-leadership]] 댓글이 ***"I/O 스키마를 명확히"***라고 했다. **에이전트 시대에는 이름이 인터페이스다.**

**일반화: 에이전트가 읽을 문서에 쓰이는 고유명은 기존 예약어와 겹치지 않는 게 낫다.** 사람 대상 브랜딩과 **기계 대상 식별자**의 요구가 갈리기 시작했다. **(내 관찰이고 HN 지적을 확장한 것이다.)**

## 호스피탈리티 / CRS 적용 포인트

**직접 도입 대상은 아니다. 얼리 베타이고 보안 설명이 없다. 판단 재료로만.**

- **코드를 벤더 인프라에 두는 결정은 "지나가는 것"과 다르게 취급한다.** 프롬프트가 통과하는 것과 저장소가 머무르는 것은 위험의 종류가 다르다. **보존 기간, 삭제 절차, 학습 사용 여부**를 계약에 명시하지 않으면 도입하지 않는다.
- **엔터프라이즈 opt-out 이 기본값이 아니라는 걸 확인한다.** 관리자가 명시적으로 빼야 안 켜진다는 서술이라, **조직 정책이 없으면 개인이 켠다.**
- **동기화 충돌 처리를 묻는다.** 양방향 동기화에서 **같은 브랜치가 양쪽에서 바뀌면 무엇이 이기는지**가 이 문서에 없다. 정산·요금 관련 코드에서는 조용한 덮어쓰기가 사고다.
- **이름 충돌을 우리 쪽에서도 본다.** 에이전트에게 주는 문서와 명령에서 **기존 예약어와 겹치는 고유명**을 피한다. 우리 도메인에도 `order`, `booking`, `channel` 처럼 겹치기 쉬운 말이 많다.
- **"대체가 아니라 병행"이라는 전략은 참고할 만하다.** 파트너 연동에서도 **파트너의 진실 공급원을 빼앗지 않고 사본으로 붙는 쪽**이 도입 저항이 낮다.
