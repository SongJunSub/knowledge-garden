# 미첼 하시모토 인터뷰: Ghostty, Zig, 오픈소스 유지보수 (Alex Alejandre) — '오픈소스 유지보수자는 사용자에게 의무가 0', AI가 대규모 API 변경의 90%를 자동 처리했다

> 출처: [Interview with Mitchell Hashimoto](https://alexalejandre.com/programming/interview-with-mitchell-hashimoto/) (alexalejandre.com) · 정리일 2026-07-10

## 한 줄 요약

**Vagrant·Terraform·Vault를 만든 Mitchell Hashimoto가 터미널 에뮬레이터 Ghostty 개발과 오픈소스 철학을 이야기한다. GPU 프로그래밍·Zig 학습이라는 개인 목표로 시작한 프로젝트가 기능 풍부한 크로스플랫폼 터미널로 발전한 과정, "오픈소스 유지보수자는 사용자에게 의무가 0"이라는 단호한 입장, 그리고 Zig 0.15의 대규모 API 변경에서 "AI가 diff의 90%를 자동 처리했다"는 실전 경험을 다룬다.**

## 핵심 포인트

- **Ghostty 시작 배경** — 15년간 CLI를 만들었지만 터미널 에뮬레이터 작동 원리를 제대로 이해 못 했다는 문제의식. Hashicorp 퇴사 후 GPU 프로그래밍·데스크톱 최적화·Zig 학습이라는 3가지 개인 목표로 시작 → "빠르고 기능 풍부한 크로스플랫폼 터미널의 부재"를 발견하며 공식 프로젝트로 확대. **"비공개 베타"로 오래 운영해 과도한 관심을 의도적으로 제한.**
- **터미널 범위 제한 철학** — 터미널을 극단으로 밀어붙이는 것에 반대. **"CLI 도구는 구성성이 우월하고, 터미널 애플리케이션은 자동화·스크립트성 있는 세상이 더 나은 세상."** 근본 문제는 PTY의 비구조적 바이트 스트림·이스케이프 시퀀스. 개선안: **N-화면 API**(무제한 배경 화면·오버레이), **버튼 프로토콜**(스크롤백에서도 클릭 이벤트 작동).
- **오픈소스 유지보수 철학** — **"오픈소스 라이선스의 첫 줄은 '있는 그대로, 보증 없음'"** — 유지보수자는 사용자에게 의무가 없다는 단호한 입장. 그러나 "좋은 소프트웨어를 만들려는 노력"은 개인적 선택으로 감당할 가치. **모든 PR을 수락하면 비전 없는 코드 산더미가 된다** — 개별 요청 대신 "3~4개 요청을 하나의 일관된 기능으로" 해결. 포크 생태계 확산을 지지: "더 많은 사람이 포크하면 빌더에 대한 공감이 늘어난다."
- **Zig와 API 설계** — Zig의 비안정성을 미리 이해하고 선택. 설계 원칙: 다양한 생태계 라이브러리를 폭넓게 사용(Java 빌더 패턴·Ruby·Haskell/Prolog/Clojure), **"명사가 중요하다"**(Vagrant는 개발 중심 명사로 설계, Docker와 대조), 직접 사용자가 되어보기.
- **AI와 언어 마이그레이션** — Zig 0.15의 writer 인터페이스 변경에서 **다양한 맥락의 변경 예시를 보여주고 나머지를 AI에 맡김 → "90%의 변경이 자동화되는 동안 주방에 있을 수 있었다."** Zig의 엄격한 반AI 정책에도 불구하고 AI가 하위 사용자의 고통을 완화하는 역설. **"이후 역호환성이 덜 중요할 수 있다"**는 미래 전망.
- **프로그래밍 커뮤니티 견해** — "언어마다 특정 기능 부재는 창의성과 문화를 낳는다." **"나는 Rust 문화를 좋아하지 않는다. 하지만 그것이 나쁜 뜻은 아니다"** — 기술과 커뮤니티를 분리해 평가. Zig를 "사과하지 않는 이상한 언어"로 평가하며 정체성 유지를 존경.
- **핵심 조언** — 제품의 실제 사용자가 될 것(고객에서 멀어지면 "명세 완료" 수준의 사고로 전락), C/저수준 학습은 언어 자체가 아닌 컴퓨터 작동 원리 학습이 목표.

## 내 생각 · 적용점

### 핵심 전이 1 — "AI가 diff의 90%를 자동 처리"가 [[2026-07-09-typescript-7-0-announcement]]의 마이그레이션 논점과 정확히 겹친다

지난번 정리한 TypeScript 7.0의 "안정 API 부재로 6.0과 병행 필요"라는 제약과, 이 인터뷰의 "AI가 Zig 언어 변경의 90%를 처리했다"는 실전 사례가 직접 연결된다. **CRS가 TypeScript 7.0이나 다른 대규모 언어/프레임워크 업그레이드를 할 때, "예시 몇 개를 보여주고 AI에게 나머지 diff를 맡기는" 이 패턴이 구체적인 마이그레이션 전략이 될 수 있다.**

### 핵심 전이 2 — "오픈소스 유지보수자는 의무가 0"이라는 단호함이 [[2026-06-30-yagni-hidden-costs]]·[[2026-07-06-less-is-more-ai-era]]의 "거절할 용기"와 연결

"모든 PR을 수락하면 비전 없는 코드 산더미가 된다"는 지적은, 지난번 정리한 YAGNI의 선택권 비용과 "덜한 것이 더 낫다"의 삭제 문화를 오픈소스 유지보수 맥락에서 재확인한다. **CRS 팀에서도 "모든 기능 요청을 개별적으로 수락"하지 않고 "여러 요청을 하나의 일관된 설계로 해결"하는 태도가 장기적 코드베이스 건강성을 지킨다.**

### 핵심 전이 3 — "제품의 실제 사용자가 되기"가 CRS 개발 문화에 주는 직접적 시사점

"도구 제작자의 딜레마를 극복하기 위해 직접 TUI를 개발했다"는 실천은, CRS 개발자가 실제로 호텔 예약·체크인 프로세스를 직접 경험해봐야 한다는 원칙으로 이어진다. **[[2026-06-30-last-people-who-know-how-it-works]]의 "저항이 곧 지식"과 결합하면, CRS 개발팀이 정기적으로 Opera PMS나 예약 플로우를 직접 사용해보는 것이 "명세 완료 수준의 사고"에 빠지지 않는 방법이다.**
