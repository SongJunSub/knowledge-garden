# GitHub Stacked PR 공개 프리뷰 시작 — 나눈 diff도 결국 선형으로 읽어야 한다

> 출처: [Stacked pull requests are now in public preview](https://github.blog/changelog/2026-07-30-stacked-pull-requests-are-now-in-public-preview/) (github.blog · GeekNews GN⁺ 요약 + HN·Lobsters 큐레이션) · 정리일 2026-08-02

## 한 줄 요약

**큰 변경을 작고 검토 가능한 계층으로 나누는 **Stacked pull requests**가 모든 저장소에 **공개 미리보기**로 순차 제공된다. 각 PR은 **바로 아래 계층을 대상**으로 삼아, 팀원들이 **좁은 범위의 diff를 병렬로 독립 검토**할 수 있다. **최신 PR을 병합하면 아래의 미병합 계층까지 한 번에 반영**되고, 일부만 병합하면 **위쪽 PR은 자동 리베이스 및 대상 변경**된다. 기존 **PR 검토, 필수 검사, 브랜치 보호, 병합 요건**이 그대로 적용되고 **GitHub.com·CLI·모바일 앱·GitHub Copilot**에서 스택을 다룰 수 있다. **Merge queue 지원**은 이후 몇 주 동안 점진적으로 제공될 예정이다. HN·Lobsters 반응은 실용적인 지적이 많다 — ***"스택 기능이 큰 변경을 여러 작은 변경으로 나누는 데는 찬성하지만, 결국 작은 변경들을 선형으로 리뷰해야 한다"***는 우려, **스쿼시 병합+필수 리뷰를 함께 쓰면 각 PR마다 재승인이 필요**한 문제, **병합 큐가 완전히 준비되지 않은 상태에서 공개 미리보기로 승격**한 점 지적. Lobsters에서는 **`gh extension install github/gh-stack`**이라는 CLI 설치 명령이 공유되고, **jujutsu(git 대안 VCS) 사용자들의 긍정적 경험**과 **git-spice 같은 대안 도구** 추천도 나왔다.**

## 핵심 포인트

- **핵심 메커니즘** — 각 PR이 **바로 아래 계층을 대상**으로 삼아 **좁은 범위의 diff를 병렬로 독립 검토** 가능.
- **병합 동작** — **최신 PR 병합 시 아래 미병합 계층까지 한 번에 반영.** 일부만 병합하면 **위쪽 PR은 자동 리베이스·대상 변경.**
- **기존 기능과의 호환성** — **PR 검토, 필수 검사, 브랜치 보호, 병합 요건**이 그대로 적용. **GitHub.com·CLI·모바일 앱·Copilot**에서 스택 조작 가능.
- **배포 일정** — 공개 미리보기는 **며칠에 걸쳐 전체 저장소로 확대**, **Merge queue 지원은 이후 몇 주 동안 점진적 제공.**
- **CLI** — `gh extension install github/gh-stack`.

## 내 생각 · 적용점

### 핵심 전이 1 — "결국 선형으로 리뷰해야 한다"는 지적은 이번 배치의 [[2026-08-02-refactoring-economic-benefit]]가 보여준 "컨텍스트 분할이 항상 병목을 없애지 않는다"는 교훈이다

Fowler의 리팩터링 노트에서 **파일을 19개로 쪼개면 에이전트의 토큰 비용이 83% 줄었다**는 결과를 다뤘는데, 그 성공은 **각 조각을 독립적으로 처리할 수 있었기 때문**이다. Stacked PR의 경우는 다르다 — **각 계층이 이전 계층에 의존**하는 구조라, 아무리 diff를 잘게 나눠도 **병합 순서라는 병목은 그대로 남는다.** 이건 [[2026-08-01-bun-zig-to-rust-rewrite-with-ai]]에서 다룬 병렬화 원칙과의 대비도 보여준다 — Bun의 64개 에이전트는 **서로 독립적인 파일**을 병렬 변환했기에 진짜 병렬성을 얻었지만, Stacked PR은 **계층 간 의존성이 명시적으로 존재**해서 검토는 병렬이어도 **머지는 본질적으로 순차적**이다. **"나눈다"는 것과 "병렬화한다"는 것은 다른 문제**라는 걸 이 두 사례가 대비해서 보여준다.

### 핵심 전이 2 — 이건 내 방법론의 "작은 편집 루프 — 한 번에 하나"의 정확한 도구화지만, 병합 정책이 그 정신을 지켜야 값이 난다

내 CLAUDE.md의 규칙 — *"큰 변경 1개보다 작은 편집 N개를 선호한다"* — 을 GitHub이 정확히 기능으로 구현한 게 Stacked PR이다. 다만 HN의 지적이 정확히 겨냥하는 지점이 있다 — **작은 단위로 쪼개는 것 자체는 도구가 강제할 수 있지만, "각 단위를 진짜로 리뷰어가 30분 안에 읽을 수 있게" 만드는 건 여전히 사람의 판단**이다. 도구가 기계적으로 스택 구조를 관리해줘도, **개발자가 여전히 하나의 거대한 변경을 인위적으로 계층 5개로 쪼갠 것에 불과**하다면 이 기능의 가치는 반감된다. 도구는 필요조건이지 충분조건이 아니다.

### 핵심 전이 3 — "스쿼시 병합 + 필수 리뷰"의 재승인 문제는 [[2026-08-02-gcc-ai-policy]]가 보여준 "새 도구가 낡은 정책과 충돌한다"는 패턴이다

GCC 노트에서 나는 **"새 기술 문제에 낡은 법적 도구(15줄 기준)를 재사용"**했다고 정리했는데, 이번엔 반대 방향이다 — **새 워크플로 기능(스택)이 낡은 정책(스쿼시 병합 시 재승인 필수)과 충돌**한다. 이건 새 도구를 도입할 때 흔히 겪는 마찰이다 — **기존 프로세스가 새 워크플로의 전제(각 계층이 독립적으로 빠르게 병합됨)를 고려하지 않고 설계돼 있으면, 새 도구의 이점이 기존 정책에 흡수돼 사라진다.**

### 핵심 전이 4 — 정직한 급소: "병합 큐가 미완성인 채로 공개 미리보기 승격"은 이번 배치의 [[2026-08-02-gemini-robotics-2]]가 보여준 "부분 검증만으로 발표"의 GitHub 버전이다

HN이 지적한 이 부분이 흥미로운 이유는, **대형 벤더(GitHub)조차 이번 시즌 반복해 온 패턴(핵심 기능이 미완성인 채로 "프리뷰"라는 이름으로 조기 공개)**을 따른다는 것이다. "공개 프리뷰"라는 이름 자체가 이 불완전함을 정당화하는 장치이지만, **실무에서 이걸 도입하는 팀은 "Merge queue 지원 전"이라는 제약을 반드시 인지**해야 한다.

## 호스피탈리티 / CRS 적용 포인트

- **Stacked PR 도입 전 병합 정책을 먼저 정비한다(전이 3).** 스쿼시 병합+필수 리뷰 조합을 쓴다면, 스택 도입 전에 **각 계층 병합 시 재승인이 얼마나 마찰을 일으킬지** 파일럿으로 확인.
- **"쪼개기"와 "병렬화"를 구분해서 기대치를 설정한다(전이 1).** Stacked PR을 도입해도 **머지 자체는 순차적**이라는 걸 팀에 명확히 하고, 진짜 병렬 처리가 필요한 작업(독립적인 모듈 변경)에는 별도 브랜치를 유지.
- **Merge queue 지원 완성 전까지는 신중하게 파일럿.** 핵심 CI 파이프라인에 이 기능을 전면 도입하기 전에, 부수적인 저장소에서 먼저 검증.
