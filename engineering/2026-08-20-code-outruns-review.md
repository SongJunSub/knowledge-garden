# 코드는 다 읽을 수 없고, 코드 리뷰가 맡아온 책임은 사라지지 않는다 (GeekNews)

> 출처: [코드는 다 읽을 수 없고, 코드 리뷰가 맡아온 책임은 사라지지 않는다](https://news.hada.io/article/code-outruns-review) (GeekNews 자체 편집 아티클 · `1P by GeekNews`) · 정리일 2026-08-20
> **저자 표기가 없다.** 외부 링크 요약이 아니라 **GeekNews 가 직접 쓴 종합 아티클**이고, **자사에 올라온 글 20편을 엮은 메타 큐레이션**이다.
> **게시 직후라 댓글이 없다.** 하단에 "댓글과 토론" 링크만 있고 본문 안에 **긱뉴스 댓글 2개가 인용**돼 있다.
> **이번 시즌 내가 이 계열로 쓴 노트가 8편**인데, 이 글이 그 8편의 **상위 프레임**을 준다(→ 전이 1).

## 한 줄 요약

**AI 가 만든 가장 근본적인 변화는 코드를 더 잘 쓰게 된 게 아니라 사람이 읽고 검토할 수 있는 속도를 코드 생성 속도가 앞질렀다는 것이고, 그 격차가 가장 먼저 터지는 곳이 코드 리뷰다. Faros AI 텔레메트리에서 AI 도입도가 낮은 팀에서 높은 팀으로 갈수록 중앙값 리뷰 소요 시간이 441.5% 늘고 리뷰 없이 머지된 PR 이 31.3% 늘었다. 그런데 이 글의 결론은 AI 리뷰어를 붙이자도 아니고 그래도 다 읽자도 아니다. 코드 리뷰가 원래 한 자리에서 처리하던 다섯 가지 역할, 검증·유지보수성 확인·지식 공유·게이트키핑·책임 분산을 시간축을 따라 나누자는 것이다. 코드 생성 전에는 의도와 경계를 사람이 정하고, 생성 중에는 반복 가능한 검사를 자동화하고, PR 시점에는 AI 를 판결자가 아니라 센서로 쓰고, 머지 전에는 틀렸을 때의 비용으로 리뷰 강도를 정하고, 배포 후에는 관측과 복구로 받아낸다. 그리고 사람이 끝까지 소유해야 하는 건 모든 코드 줄이 아니라 의도·맥락·증거·책임 넷이다. 코드를 전부 읽을 수 없게 됐다고 해서 책임까지 자동화된 것은 아니다.**

## 핵심 포인트

**문제 규정**
- ***"사람이 코드를 읽고 검토할 수 있는 속도보다, 코드가 만들어지는 속도가 빨라진 것이 더 근본적인 변화."***
- 질문을 **사람 대 AI 의 리뷰 실력 대결이 아니라** ***"하나의 PR 에 뒤섞여 있던 검증/이해/지식 전달/승인/책임을 누구에게 어떻게 나눌 것인가"*** 로 재정의한다.

**코드 리뷰의 다섯 역할**(Google 사내 연구 + 이후 논의 종합)
- **검증**(변경의 결함 찾기) · **유지보수성 확인**(다른 사람이 이해할 수 있는가) · **지식 공유**(관례와 과거 결정 전달) · **게이트키핑**(무엇을 받아들일지) · **책임 분산**(판단을 한 사람에게만 맡기지 않기).
- ***"이 역할들을 모두 사람이 diff 를 읽으며 처리해 온 것이 기존 코드 리뷰였음."***

**수치**
- **Faros AI**: 4,000개 팀 22,000명 **2년치 텔레메트리**. AI 도입도 낮은 팀 → 높은 팀으로 갈수록 **중앙값 리뷰 소요 시간 +441.5%**, **리뷰 없이 머지된 PR +31.3%.**
- **GitClear**: AI 일일 사용자의 **원시 산출량이 비사용자 대비 약 4배**, 그런데 **1년 전 자신 대비 생산성 향상은 약 12%.**
- **오픈소스 300개 프로젝트**: PR **54,330개**, 인라인 리뷰 대화 **278,790개**. **전체 리뷰의 55.7% 를 AI 에이전트가 시작.** AI 코멘트의 **95% 이상이 코드 개선·결함 탐지**에 집중. **AI 수정안 채택률 16.6% vs 인간 56.5%**. **AI 가 시작한 리뷰의 85% 이상이 첫 코멘트 뒤 추가 응답 없이 종료.** 인간이 **에이전트 계정 코드**를 리뷰하면 대화가 **평균 11.8% 길어짐.**
- **207개 프로젝트 102만 개 PR**: LLM 참여 프로젝트의 **같은 리뷰어 조합 반복 비율 평균 60%**, 사람만 참여는 **약 16%.**
- **Anthropic 내부 측정**: 실질적인 리뷰를 받는 PR 비율 **16% → 54%.** **GitHub**: 플랫폼 리뷰 **5건 중 1건 이상에 에이전트 관여.**

**AI 와 사람이 보는 것이 다르다**
- ***"AI 는 코드 안에서 답을 찾으려 했고, 인간은 코드 밖의 맥락을 가져왔음."***
- 인간 리뷰어가 잡고 LLM 이 놓친 실제 사례 셋: `~/.gitconfig` **동시 수정 잠금 충돌**(과거 성능 문제 기억 필요), CI 의 **오래된 AWS CLI 버전 호환성**, tarball 과 checksum 을 따로 갱신할 때의 **비원자적 상태**. 전부 ***"현재 diff 바깥의 기억"***이 필요했다. **셋 중 둘은 그 코드를 잘 알던 개발자의 PR**이었고 익숙한 작성자가 놓친 것을 남이 찾았다.
- 채택된 **AI 수정안이 인간 수정안보다 코드 크기와 분기 복잡도를 더 많이 늘리는 경향.**
- 실무 해석: ***"AI 리뷰는 판결보다 결함 후보를 넓게 탐지하는 센서에 가까움."***

**빠른 리뷰가 좋은 리뷰는 아니다**
- **점진 도입** 또는 에이전트 등장 후 빠르게 확대한 프로젝트는 리뷰 결정이 빨라졌다.
- **초기 LLM 리뷰어를 대부분의 PR 에 일괄 적용**한 프로젝트는 **속도 개선이 없었고 리뷰 안티패턴은 오히려 늘었다.**
- 빨라진 프로젝트에서도 **리뷰 품질 대리 지표는 함께 좋아지지 않았다.**
- ***"모든 PR 에 같은 모델을 붙이면 리뷰어 수는 늘어난 것처럼 보여도 관점은 하나로 고정될 수 있음."***

**사라진 의도**
- 사람이 쓰면 **검토하고 버린 대안이 작성자 머릿속에 남아** 리뷰가 그 판단을 점검하는 일이었다.
- ***"에이전트가 만든 diff 에는 무엇을 시도했고 왜 버렸는지가 남지 않는 경우가 많아, 리뷰어가 기록되지 않은 의도를 다시 구성해야 함."***
- 현장의 모습: 리뷰어가 라이브러리 선택 이유를 물으면 **개발자가 AI 에게 다시 물어 답을 전달**하고, ***"사람은 작성자가 아니라 중개인이 됨."***
- 해법은 **모델 내부 사고 과정 보관이 아니다.** ***"에이전트가 수행한 도구 호출, 검토한 대안, 테스트 결과와 최종 판단 근거를 외부에서 검증 가능한 결정 로그로 남기는 것."***
- 판정 기준: ***"리뷰어가 '왜 이렇게 했나'라고 물어야 한다면 의사결정 로그에 빈 부분이 있다는 신호."***

**그래도 읽기는 남는다**
- ***"리뷰어가 코드만 보고 모든 버그를 찾을 수는 없지만, 리뷰어가 이해하지 못한 코드는 미래의 유지보수자도 이해하기 어려울 가능성이 큼."***
- ***"읽기는 무결성을 증명하는 행위가 아니라 다른 사람이 이 변경을 이해하고 이어받을 수 있는지 확인하는 행위."***
- 좋은 리뷰어를 **기르는 것도 리뷰 시스템의 일부**: **소크라테스식 리뷰**(답 대신 가정과 판단 근거를 먼저 묻기), **near-miss 공유**(막힌 버그를 작성자가 설명해 팀 경험으로), **분리된 모델링**(코드를 안 본 사람이 시스템 모델을 만들고 구현자와 테스트 사례를 맞춰보기).

**다섯 단계로 나누기**

| 시점 | 무엇을 |
|---|---|
| **코드 생성 전** | **의도와 경계.** 스펙·설계·데이터 모델·성능 목표·보안 경계·수용 기준을 사람이 먼저 |
| **생성 중** | **반복 가능한 검증 자동화.** 타입·린트·테스트·정적 분석·보안 스캔. ***"AI 의 설명보다 실제 명령과 결과를 증거로"***, 테스트 자체가 틀렸을 가능성도 확인 |
| **PR 생성 시** | **AI 를 센서로.** 결함 후보·중복·누락 테스트·의심 변경을 **선별**하되 판결하지 않음 |
| **머지 전** | **위험 기반 인간 검토.** ***"틀렸을 때의 비용으로 리뷰 강도를 결정"***. 일회성 스크립트는 테스트·AI 중심, 핵심 로직은 설계·유지보수성까지, **인증/결제/권한/데이터 삭제/인프라는 시스템 소유자 직접**. ***"작성자가 사람인지 AI 인지보다 잘못됐을 때 어떤 일이 생기는지가 리뷰 수준을 결정"***. **테스트가 많이 수정된 diff 는 assertion 까지 바꿨는지 테스트 변경부터 확인** |
| **배포 후** | **관측과 복구.** 기능 플래그·점진 배포·관측 가능성·빠른 롤백. ***"배포 전 리뷰를 대신하는 장치가 아니라 리뷰가 놓친 문제를 받아내는 마지막 안전망"*** |

**사람이 최종 소유할 넷**: **의도**(올바른 문제를 풀고 있는가) · **맥락**(코드 밖 제약과 과거 결정을 반영했는가) · **증거**(실제로 작동하고 실패에 대비했는가) · **책임**(문제가 생겼을 때 설명하고 되돌릴 수 있는가).

## 댓글

**하단 댓글 없음**(게시 직후, "댓글과 토론" 링크만). **본문 안에 긱뉴스 댓글 2개가 인용**돼 있고 둘 다 위에 옮겼다.

**읽을 때 감안**
- ①**GeekNews 자체 편집 아티클이고 저자 표기가 없다.** `1P by GeekNews` 뿐이다. 관점의 주인이 누구인지 알 수 없다.
- ②**메타 큐레이션이다.** 인용 20편이 **전부 GeekNews 에 올라온 글**이고, 상당수가 **원문이 아니라 GeekNews 요약을 경유한 2차 인용**이다. 그래서 **선택 자체가 이 매체의 관심사에 의해 걸러져 있다.** 반대 진영의 글이 GeekNews 에 안 올라왔다면 이 종합에도 없다.
- ③**저자가 한계를 반복해서 명시한다.** 이건 높이 살 만하다. Faros 는 ***"AI 도입이 변화를 직접 일으켰다고 입증한 실험이 아니라 개발 생산성 분석 업체가 수집한 관찰 데이터"***, GitClear 는 ***"원래 생산성이 높은 개발자가 AI 사용 집단에 더 많이 포함됐을 가능성"***, 두 대규모 연구는 ***"모두 관찰 연구이며 실제 장애나 결함 발생률 대신 리뷰 과정의 대리 지표를 사용"***. **네 군데에서 스스로 브레이크를 건다.**
- ④**Faros AI 와 GitClear 는 개발 생산성 분석을 파는 회사**다. "AI 도입하면 리뷰가 막힌다"는 결론이 **그들의 제품 수요와 맞는다.** 수치를 버릴 이유는 아니지만 이해관계는 있다.
- ⑤**441.5% 의 정체가 애매하다.** ***"AI 도입도가 낮은 팀에서 높은 팀으로 갈수록"***이라는 **팀 간 비교**이지 **같은 팀의 시계열 변화가 아니다.** AI 도입도가 높은 팀이 원래 더 큰 조직이거나 더 복잡한 코드베이스일 수 있다. **인과로 읽으면 안 된다.**
- ⑥**"AI 작성 코드"의 정의가 좁다.** 저자도 밝힌다. **에이전트 계정이 만든 PR** 만 세므로 **사람이 AI 도구로 쓴 코드는 안 잡힌다.** 지금 대부분의 AI 코드가 후자다.
- ⑦**5단계 제안은 규범이지 실증이 아니다.** 이 구조를 적용한 팀의 결과 데이터가 **이 글에 없다.** 앞부분의 수치는 문제 진단이고, 뒷부분의 처방은 논증이다. **둘의 근거 강도가 다르다는 걸 구분해서 읽어야 한다.**
- ⑧**Anthropic 16% → 54% 는 자사 측정**이다. 그리고 ***"실질적인 리뷰"***의 정의가 없다.

### 핵심 전이 1: 이번 시즌 흩어져 있던 노트 8편의 상위 프레임이 생겼다

**이 글이 인용한 20편 중 8편이 이미 이 가든에 있다.** 그동안 각각 따로 정리해왔는데, **이 글이 그것들을 하나의 축 위에 세운다.**

| 이 글이 인용한 것 | 내 노트 | 이 프레임에서의 자리 |
|---|---|---|
| 에이전틱 코드 리뷰 | [[2026-06-08-agentic-code-review]] | **문제 진단**: 생성량이 프로세스보다 빨리 는다 |
| 인간-AI 시너지 | [[2026-08-13-human-ai-synergy-agentic-code-review]] | **AI 와 사람이 보는 것이 다르다** |
| 인간 중심에서 에이전틱으로 | [[2026-08-13-from-human-centric-to-agentic-code-review]] | **빠른 리뷰가 좋은 리뷰는 아니다** |
| 코드 리뷰도 배워야 하는 기술 | [[2026-08-12-reviewing-code-is-a-skill]] | **코드 밖을 보는 능력은 배울 수 있다** |
| 코드 작성은 병목이 아니었다 | [[2026-05-07-bottleneck-was-never-the-code]] | **원래 병목이 드러났을 뿐** |

| Alibaba open-code-review | [[2026-06-08-alibaba-open-code-review]] | **AI 1차 리뷰 도구** |

**그리고 안 다룬 12편이 그대로 내 빈칸이다.** Critique(구글 만족도 97%), 코드 리뷰 안티패턴들, AI 시대의 코드 리뷰(입증 책임), **코드 리뷰를 없애는 방법**(체크포인트를 생성 이후에서 이전으로), **코드 리뷰에는 읽기가 필요하다**, 풀 리퀘스트는 죽었다, 작성자가 리뷰어가 되어도 될까 등.

**이 중 우선순위가 높은 둘은 "코드 리뷰를 없애는 방법"과 "코드 리뷰에는 읽기가 필요하다"다.** 이 글에서 **정확히 반대 입장으로 맞붙는 두 축**이고, 내 노트엔 양쪽 다 없다.

**그리고 이 프레임 자체가 값어치다.** 나는 그동안 이 계열을 **"AI 리뷰가 사람만큼 하나"**로 읽어왔는데, 그 질문이 틀렸다. **한 PR 에 다섯 역할이 뭉쳐 있었고, AI 는 그중 검증 하나만 부분적으로 대신할 수 있다.** 나머지 넷(유지보수성·지식 공유·게이트키핑·책임 분산)은 **누가 대신하느냐가 아니라 어디로 옮기느냐**의 문제다.

### 핵심 전이 2: Faros 수치가 어제 [[2026-08-20-linear-ai-usage-patterns]]의 빈칸을 정확히 채운다

**어제 그 노트에서 이렇게 적었다.** *PR 수가 생성을 세고 읽기를 안 센다. 생성 지표와 소비 지표를 같이 봐야 한다.* 그리고 **소비 쪽 숫자가 없다**는 게 그 보고서의 한계였다.

**이 글의 Faros 수치가 그 소비 쪽이다.**

| | 생성 쪽 | 소비 쪽 |
|---|---|---|
| Linear | **PR +111%**, AI 생성 이슈 약 49% | 없음 |
| **이 글** | GitClear **원시 산출량 4배** | **리뷰 소요 시간 +441.5%**, **리뷰 없이 머지 +31.3%** |

**두 자료를 붙이면 그림이 닫힌다.** 산출은 몇 배로 늘고, 검토 시간은 그보다 더 크게 늘고, 그래도 못 따라가서 **읽히지 않은 코드가 머지된다.** 그리고 GitClear 의 **4배 산출 대 12% 생산성**이 그 격차의 크기를 준다.

**단서를 두 개 달아야 한다.** ①**둘 다 관찰 데이터고 인과가 아니다.** Linear 는 자사 텔레메트리, Faros 는 생산성 분석 업체 데이터. ②**441.5% 는 팀 간 비교**라 같은 팀의 변화가 아니다.

**그럼에도 어제 세운 규칙이 강화된다: 생성 지표를 볼 때 소비 지표를 짝으로 붙인다.** 여기에 하나 더 붙일 게 생겼다. **"리뷰 없이 머지된 비율"** 이 그 짝 중에서도 가장 직접적인 신호다. 리뷰 시간은 팀 사정에 따라 흔들리지만, **리뷰를 아예 안 거친 비율은 방어선이 뚫렸다는 뜻**이다.

### 핵심 전이 3: 사라진 의도와 의사결정 로그가 이 글의 진짜 새 기여다

**이 글에서 다른 어디서도 정리된 걸 못 본 대목이다.**

***"사람이 코드를 쓰면 검토하고 버린 대안이 작성자 머릿속에 남아 있어 리뷰는 그 판단을 점검하는 일이었다."***

**이게 맞다.** 리뷰어가 "왜 이렇게 했어?"라고 물으면 작성자가 답할 수 있었던 건 **버린 대안이 머릿속에 있었기 때문**이다. 그리고 **에이전트 diff 에는 그게 없다.** 그래서 ***"사람은 작성자가 아니라 중개인이 됨"*** 이라는 장면이 나온다. 리뷰어가 묻고, 개발자가 AI 에게 다시 묻고, 답을 전달한다.

**해법이 정확하다.** ***"모델의 내부 사고 과정을 보관하는 것이 아님. 에이전트가 수행한 도구 호출, 검토한 대안, 테스트 결과와 최종 판단 근거를 외부에서 검증 가능한 결정 로그로 남기는 것."***

**즉 사고 과정(비검증 가능)이 아니라 행적(검증 가능)을 남긴다.** 이 구분이 중요하다. LLM 의 chain-of-thought 를 저장해봐야 **그게 실제 판단 근거였는지 검증할 방법이 없다.** 반면 **실행한 명령과 그 출력**은 재현 가능하다.

**그리고 이건 mangolove 방법론이 이미 요구하는 것과 같은 구조다.**
- `.progress.md` 의 **결정 사항** 절(날짜와 이유).
- 완료 보고의 **산출물 경로 원칙**("PASS"만 보고 금지, 빌드·테스트 결과를 경로와 함께).
- 어제 [[2026-08-20-aws-scte35-ai-ad-insertion]]에서 적은 **증거 4종**(입력 스냅샷·판정값·신뢰도·임계값 버전).

**셋 다 "판단이 아니라 판단의 재료를 남긴다"는 같은 원리다.** 그리고 그 반대 사례가 [[2026-07-15-codex-encrypting-subagent-prompts-audit-gap]]이었다. **서브에이전트 프롬프트가 암호화되면 감사 격차가 생긴다.**

**바로 쓸 수 있는 테스트가 이 글에 있다.** ***"리뷰어가 '왜 이렇게 했나'라고 물어야 한다면 의사결정 로그에 빈 부분이 있다는 신호."***

**이걸 규칙으로 쓴다: 그 질문이 나올 때마다 PR 을 고치지 말고 PR 템플릿을 고친다.** 같은 질문이 반복되면 그건 개별 PR 의 문제가 아니라 **로그 설계의 빈칸**이다.

### 핵심 전이 4: 60% 대 16% 는 사흘 전 내가 적은 명제의 실측 대응물이다

**어제 [[2026-08-20-miricanvas-trendbot-three-agents]]에서 이렇게 적었다.** *탈상관은 개수가 아니라 역할·근거의 분리에서 온다.* 그건 **미리디 저자의 주장**이었고 근거는 없었다.

**이 글이 그 명제의 실측을 준다.** 102만 PR 에서 **LLM 참여 프로젝트의 같은 리뷰어 조합 반복 비율 60%**, 사람만 참여는 **약 16%.**

***"모든 PR 에 같은 모델을 붙이면 리뷰어 수는 늘어난 것처럼 보여도 관점은 하나로 고정될 수 있음."***

**즉 리뷰어가 늘어난 게 아니라 한 명이 여러 번 온 것이다.** 그리고 대가가 같이 나온다. **초기 LLM 리뷰어를 대부분의 PR 에 일괄 적용한 프로젝트는 속도 개선이 없었고 안티패턴이 늘었다.**

**이 시즌에 같은 원리가 세 형태로 나왔고 이제 근거 강도가 층을 이룬다.**

| 자료 | 형태 | 근거 |
|---|---|---|
| [[2026-08-20-miricanvas-trendbot-three-agents]] | **설계 원칙 주장** | 없음(채용 글) |
| mangolove 3인 탈상관 리뷰 | **방법론 규범** | 없음(내 규칙) |
| **이 글의 102만 PR** | **관찰 실측** | **60% 대 16%** |

**셋이 같은 방향인데 처음으로 숫자가 붙었다.** 여전히 관찰 연구이고 대리 지표지만, **"AI 리뷰어를 늘리면 관점이 늘어난다"는 직관이 틀렸다**는 증거로는 충분하다.

**실무 규칙 둘.** ①**같은 프롬프트·같은 설정의 AI 리뷰를 모든 PR 에 일괄로 걸지 않는다.** 변경 유형별로 **관점을 갈라준다**(보안 / 성능 / 하위 호환 / 데이터 정합성). mangolove 의 스마트 리뷰 라우팅이 이미 그 방향인데, **이 데이터를 보면 그게 선택이 아니라 필수에 가깝다.** ②**리뷰어 조합 반복률을 측정 가능하면 재본다.** 우리 PR 에서 **같은 사람 같은 조합이 계속 붙는지**를 보면 사람 쪽 탈상관도 같이 점검된다.

### 핵심 전이 5: "틀렸을 때의 비용으로 리뷰 강도를 결정"이 내가 이미 쓰는 트랙 분류의 리뷰 판본이다

***"모든 줄에 같은 검토 비용을 쓰지 않고 틀렸을 때의 비용으로 리뷰 강도를 결정."***
***"작성자가 사람인지 AI 인지보다 잘못됐을 때 어떤 일이 생기는지가 리뷰 수준을 결정."***

**두 번째 문장이 특히 좋다.** AI 코드에 대한 흔한 반응이 **"AI 가 썼으니 더 꼼꼼히 봐야 한다"**인데, 이 글은 **작성자 속성이 아니라 실패 비용**으로 기준을 옮긴다. **AI 가 쓴 로그 포맷 변경보다 사람이 쓴 권한 체크 한 줄이 더 위험하다.**

**mangolove 의 Change Impact Score 가 정확히 이 구조다.** 파일 수·로직 변경·API·DB·인증으로 점수를 매기고 트랙을 정한다. 그리고 **인증/인가 변경은 점수와 무관하게 최소 Large 로 승격**한다. 이 글의 ***"인증/결제/권한/데이터 삭제/인프라는 시스템 소유자가 직접 확인"***과 같은 규칙이다.

**그런데 이 글이 내 규칙에 없는 걸 하나 준다.**

***"테스트가 많이 수정된 diff 에서는 새 동작에 맞춰 assertion 까지 바꿨는지 테스트 변경부터 확인."***

**이건 구체적이고 바로 쓸 수 있다.** 그리고 **AI 코드에서 가장 흔한 조용한 실패 모드**를 짚는다. 구현이 테스트를 통과하는 게 아니라 **테스트가 구현에 맞춰 조정된 것.** mangolove 의 **근본 원인 우선 원칙**이 금지하는 것("assertion 완화 금지")인데, **리뷰에서 그걸 찾는 순서**는 없었다.

**규칙 추가: diff 를 열면 구현보다 테스트 변경을 먼저 본다.** 테스트 수정량이 구현 수정량에 비해 크면 그 자체가 신호다.

### 핵심 전이 6: 읽기의 목적이 무결성 증명에서 이해 가능성 확인으로 바뀐다

***"리뷰어가 이해하지 못한 코드는 미래의 유지보수자도 이해하기 어려울 가능성이 큼."***
***"읽기는 무결성을 증명하는 행위가 아니라 다른 사람이 이 변경을 이해하고 이어받을 수 있는지 확인하는 행위."***

**이게 이 글에서 가장 조용하지만 오래 갈 재정의라고 본다.**

**왜냐하면 첫 번째 목적(무결성 증명)은 AI 가 점점 잘하고, 두 번째 목적(이해 가능성)은 AI 가 원리상 못 하기 때문이다.** AI 는 ***"이 코드에 버그가 있는가"***는 답할 수 있어도 ***"우리 팀이 6개월 뒤 이걸 이어받을 수 있는가"***는 답할 수 없다. **팀이 무엇을 아는지 모르기 때문이다.**

**그리고 이게 [[2026-08-18-flex-modules-agents-read-less]]와 붙으면 불편한 계산이 나온다.** 거기서 확인한 건 **읽기가 비용의 지배항**이라는 것이었다. 이 글이 말하는 건 **그 읽기 중 자동화 가능한 부분과 불가능한 부분이 갈린다**는 것이다.

**그러면 남는 읽기가 더 비싸진다.** 자동화되는 건 **기계적으로 확인 가능한 읽기**(패턴, 타입, 흔한 결함)이고, 남는 건 **판단이 필요한 읽기**(이 설계가 우리 것과 맞는가, 6개월 뒤 이해될까)다. **후자는 시니어만 할 수 있다.**

**그래서 이 글이 리뷰어를 기르는 방법을 같이 넣은 게 맞다.** 소크라테스식 리뷰, near-miss 공유, 분리된 모델링. ***"사람에게 어려운 판단만 남긴다면 그 판단을 할 사람을 기르는 일도 리뷰 시스템의 일부가 되어야 함."***

**이건 [[2026-08-13-ai-removing-middle-class-of-software-engineering]]의 정확한 반대편 처방이다.** 중간층이 사라지면 시니어가 어디서 나오나. **리뷰가 그 훈련 자리였는데 리뷰를 AI 에 넘기면 훈련 자리도 같이 사라진다.**

### 핵심 전이 7: 책임은 자동화되지 않는다는 게 결론이고, 이건 규범이 아니라 사실 진술이다

***"모델은 온콜 담당자가 되어 장애 호출을 받고 대응할 수도, 사용자에게 결정을 설명하거나 그 결과를 책임질 수도 없음."***

**이게 도덕적 주장이 아니라 구조적 사실이라는 게 중요하다.** 책임은 **결과를 감수할 수 있는 주체**에게만 귀속되고, 모델은 그런 주체가 아니다.

**그리고 긱뉴스 댓글이 그 공백이 어떻게 느껴지는지 준다.** ***"내가 뭘 만들었는지도 모르겠고 어쨌든 결과물은 있으니 니가 평가해서 문제점을 찾아라."***

**이건 리뷰 부하 문제가 아니라 책임 이전 문제다.** 작성자가 설명 책임을 포기하면 **그 부담이 리뷰어에게 통째로 넘어간다.** 그리고 리뷰어는 **원래 검증만 하던 사람**이지 작성자의 의도까지 재구성하는 사람이 아니었다.

**그래서 이 글의 넷(의도·맥락·증거·책임) 중 실무에서 가장 먼저 깨지는 게 책임이다.** 나머지 셋은 도구로 보조할 수 있는데 **책임은 사람이 안 지면 아무도 안 진다.**

**규칙: PR 작성자가 자기 변경을 설명할 수 없으면 그 PR 은 리뷰 대상이 아니라 반려 대상이다.** 이건 AI 사용을 막는 규칙이 아니라 **설명 가능한 상태로 만들어서 오라는 규칙**이고, 전이 3 의 의사결정 로그가 그걸 가능하게 만드는 장치다.

## 호스피탈리티 / CRS 적용 포인트

- **5단계 분산을 우리 PR 흐름에 그대로 매핑할 수 있다.** 지금 우리 리뷰는 **머지 전 한 지점에 다 몰려 있다.** 스펙·설계 검토(생성 전)와 배포 후 관측(플래그·롤백)으로 **앞뒤로 덜어내면** 머지 전 부하가 준다.
- **위험 등급을 명문화한다.** 우리 도메인의 **시스템 소유자 직접 확인 대상**은 명확하다: **정산 금액 계산, 요금·재고 반영, 예약 상태 전이, 파트너 권한, 채널 연동 인증.** 이건 mangolove 가 **LLM 위임을 금지한 영역**과 정확히 겹친다. **위임 금지 = 사람 직접 리뷰 필수**로 같이 묶어둔다.
- **PR 템플릿에 의사결정 로그 3칸을 넣는다.** ①**검토한 대안과 버린 이유** ②**실행한 검증 명령과 실제 출력**(경로 포함) ③**이 변경이 틀렸을 때 무슨 일이 생기는가.** 세 번째 칸이 곧 리뷰 강도를 결정한다.
- **"왜 이렇게 했나"가 반복되면 PR 을 고치지 말고 템플릿을 고친다.** 같은 질문이 세 번 나오면 그건 로그 설계의 빈칸이다.
- **테스트 변경부터 본다.** 특히 **정산·요금 계산 테스트**에서 assertion 이 구현에 맞춰 조정됐는지. 우리 도메인에서 이건 금액 오류가 조용히 정답이 되는 경로다.
- **AI 리뷰를 모든 PR 에 같은 설정으로 걸지 않는다.** 60% 대 16% 가 그 대가를 보여준다. **변경 유형별로 관점을 갈라준다**(정산 정합성 / 파트너 하위 호환 / 채널 연동 계약 / 성능).
- **리뷰 없이 머지된 비율을 재본다.** 리뷰 소요 시간보다 이 지표가 방어선이 뚫렸는지를 더 직접적으로 말해준다.
- **리뷰를 훈련 자리로 유지한다.** near-miss 공유(막힌 버그를 작성자가 설명)와 소크라테스식 질문은 **도구 없이 오늘 시작할 수 있다.** 그리고 이걸 안 하면 **어려운 판단을 할 사람이 다음 세대에 없다.**
- **경계면 교차검증을 4단계에 붙인다.** 우리 구조(BFF·멀티레포·공용 DTO 카피본)에서는 **AI 리뷰가 한쪽 파일만 보고 통과시키기 쉽다.** 머지 전 인간 검토에서 **생산자와 소비자를 같이 여는 것**을 체크리스트로 둔다.
