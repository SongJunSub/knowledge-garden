# 코드가 나빠지는 데는 한계가 없다

> 출처: [There's No Limit to How Bad Code Can Get](https://zachkehs.com/blog/theres_no_limit_to_how_bad_code_can_get/) (Zach Kehs) · GeekNews(id=33300) 경유 · 정리일 2026-09-07

> **출처 한계**: `zachkehs.com`·`news.hada.io` 모두 이번 세션 egress 차단으로 직접 열람하지 못했다. Simon Willison의 인용 정리(simonwillison.net/2026/Sep/6/zach-kehs/)와 소프트웨어 엔트로피 관련 배경 글들을 WebSearch로 교차 확인했다.

## 한 줄 요약

**소프트웨어에는 건물처럼 "계속 층을 올리면 무너진다"는 물리적 붕괴 한계가 없다 — 새로운 간접 계층을 계속 추가하거나 성능이 계속 떨어져도 시스템은 어떻게든 돌아가기 때문에, 복잡성과 성능 저하가 끝없이 누적될 수 있다. Amazon 주문 처리 조직에서는 지식 손실과 미완료 재설계가 반복되며, 기존 구조에 새 계층과 인력이 계속 남는 악순환이 이어졌다.**

## 핵심 포인트

- **건물과 소프트웨어의 근본적 차이** — 건물에 층과 방을 영원히 계속 추가하면 결국 붕괴한다는 물리 법칙이 자연스러운 제동장치 역할을 한다. 소프트웨어에는 그런 물리적 붕괴 한계가 없어 ***"작동은 하지만 나쁜" 상태가 이론상 무한히 나빠질 수 있다***는 게 핵심 명제다.
- **작동 여부가 코드 품질을 보장하지 않는다** — 시스템이 계속 작동한다는 사실 자체가 남기는 변경들이 있지만, ***"작동 여부"가 코드 품질을 보장하지는 않는다.*** 겉으로 멀쩡히 돌아가는 것과 내부가 건강한 것은 별개라는 지적이다.
- **기술 부채에는 파산 같은 초기화가 없다** — 재정적 부채는 파산이라는 "리셋" 메커니즘이 있지만, 기술 부채에는 그런 초기화가 없다 — 전면 재작성은 선택하기 어렵고, 별도 시스템을 새로 만드는 것도 쉽지 않다.
- **Amazon 주문 처리 조직 사례** — 지식 손실과 미완료 재설계가 반복되면서, 기존 구조에 새로운 계층과 인력이 계속 남는 방식의 악순환이 이어졌다는 사례가 인용된다. 변화를 완전히 멈추는 결정은 빠르게 되돌릴 수 있어도, 그 전까지 품질을 악화시킨 수천 건의 변경은 남기 때문에 ***"작동 여부가 코드 품질을 보장하지 않는다"***는 명제가 다시 확인된다.

## 내 생각 · 적용점

### 핵심 전이 1 — "기술 부채는 은유부터 틀렸다"는 관점과 정확히 만나는 지점

[[2026-08-16-not-tech-debt-just-mess]]에서 정리한 Nat Bennett의 논지 — ***"금융 부채는 계약 시점에 비용이 알려져 있지만, '기술 부채'라 불리는 것 대부분은 결정 시점에 이해되지 않았던 것이라 은유의 전제부터 어긋난다"*** — 를 이 글이 다른 각도에서 보완한다. Bennett이 "왜 부채라는 이름이 잘못됐는가"(은유의 정합성)를 다뤘다면, 이 글은 "왜 그 문제가 금융 부채와 달리 저절로 브레이크가 걸리지 않는가"(물리적 붕괴 한계의 부재)를 다룬다. 두 글을 합치면, ***기술 부채라는 은유가 잘못된 이유(예측 불가능성)와, 그 문제가 무한히 악화될 수 있는 구조적 이유(붕괴 메커니즘의 부재)가 함께 설명***된다.

### 핵심 전이 2 — Amazon 사례가 브라운필드 코끼리의 조직적 원인과 겹친다

같은 배치에서 정리한 [[2026-09-07-brownfield-elephant-ai-individuals-orgs]]도 Amazon 주문 처리 조직의 "지식 손실과 미완료 재설계 반복" 사례를 인용했다 — 같은 조직의 같은 패턴이 두 글에서 서로 다른 프레임(역할·권한의 정체성 문제 vs 물리적 붕괴 한계의 부재)으로 설명되는 셈이다. 조직 구조의 경직성(코끼리)과 코드베이스의 무한 악화 가능성(한계 없음)이 서로를 강화하는 악순환일 가능성이 있다.

## 호스피탈리티 / CRS 적용 포인트

**원칙 차원에서 직접 적용 가능하다.** CRS처럼 오래 운영되며 계속 기능이 누적되는 시스템은 정확히 이 글이 경고하는 위험에 노출돼 있다 — ***"작동하고 있다"는 사실이 "건강하다"를 보장하지 않는다***는 원칙을, 정기적인 아키텍처 건강도 점검(단순히 장애가 없는지가 아니라 새 기능 추가 속도가 얼마나 느려지고 있는지, 간접 계층이 얼마나 쌓였는지)으로 구체화할 수 있다. 특히 AI 코딩 에이전트가 빠르게 코드를 추가하는 시대에는, "빌드가 되고 테스트가 통과한다"는 사실만으로 안심하지 말고 ***"이 변경이 시스템을 얼마나 더 복잡하게 만들었는가"***를 리뷰 기준에 명시적으로 포함시키는 게 이 글의 경고를 실무에 반영하는 방법이다.
