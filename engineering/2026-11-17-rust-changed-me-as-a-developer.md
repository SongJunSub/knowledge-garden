# Rust가 개발자로서의 나를 바꾼 방식

> 출처: [Rust가 개발자로서의 나를 바꾼 방식](https://news.hada.io/topic?id=37313) (GeekNews 경유, 1차 소스 미확인) · 정리일 2026-11-17

## 한 줄 요약

**Rust를 6년 쓰고 4년 이상 실무에 적용한 경험을 통해, 타입·추상화·소유권·성능을 "따로" 생각하던 방식에서 "서로 얽힌 하나의 설계 결정"으로 생각하는 방식으로 바뀌었다는 회고. 타입 주도 개발은 실행 전 오류 검사 도구가 아니라 설계와 API를 다듬는 도구이고, 컴파일 시점 매크로(Serde, Clap)는 보일러플레이트 제거를 통해 추상화와 성능 사이의 비용을 더 명확히 드러낸다.**

## 핵심 포인트

- **타입과 추상화, 소유권과 성능을 생각하는 방식 자체가 달라짐** — 더 이상 분리된 네 가지 고려사항이 아니라, 서로 얽힌 설계 결정들.
- **합 타입(sum type)과 정적 디스패치** — 인터페이스나 런타임 분기에만 의존하지 않고 도메인을 직접 모델링할 수 있게 해 추상화 비용을 더 명확하게 드러냄.
- **타입 주도 개발의 재정의** — 실행 전 오류 검사에 그치지 않고, 설계와 API 자체를 다듬어가는 도구로 재해석.
- **컴파일 시점 매크로로 반복 코드 제거** — Serde는 타입에 속성(attribute)을 붙이는 것만으로 직렬화 코드를 생성하고, Clap은 타입과 문서 주석을 기반으로 CLI 파서를 만듦.

## 내 생각 · 적용점

### 핵심 전이 1 — "따로 생각하던 것들이 하나의 결정으로 합쳐진다"는 성숙의 패턴

이건 Rust에 한정된 이야기가 아니라, **도구에 깊이 익숙해질 때 공통적으로 나타나는 성숙 패턴**이다 — 처음에는 타입 체크, 메모리 관리, 성능 최적화를 별개 작업으로 여기다가, 숙련되면 이것들이 사실 같은 설계 결정의 다른 측면이었음을 깨닫는다. [[2026-09-11-rust-microsoft-tier-1-language]]에서 본 "타입 주도 설계가 API 레벨까지 규정한다"는 Google 스타일가이드의 태도와 같은 결이다.

### 핵심 전이 2 — 매크로가 "추상화-성능 트레이드오프"를 숨기지 않고 드러낸다는 역설

보일러플레이트를 없애는 도구(Serde, Clap)가 오히려 **추상화의 비용을 더 명확하게 보여준다**는 관찰이 흥미롭다 — 보통 코드 생성 도구는 비용을 "숨기는" 방향으로 작동하는데, 여기선 반대로 "무엇이 생성됐는지 타입 수준에서 명시적으로 드러나서" 비용이 더 잘 보인다는 뜻이다. 이는 [[2026-10-22-rust-compiler-2026-exciting-year]]에서 다룬 "오래 막힌 제약이 동시에 풀린다"는 Rust 생태계 성숙 흐름과 자연스럽게 이어진다.

## 호스피탈리티 / CRS 적용 포인트

직접 적용은 멀다(Onda 스택과 Rust의 직접 연관 없음). 다만 **"타입/스키마를 도구가 강제하게 만들어서 설계 실수를 코드가 아니라 구조로 막는다"**는 원칙은, PMS·CRS 연동 스키마를 엄격한 타입(혹은 강한 스키마 검증)으로 설계할 때 참고할 만한 원칙만 전이 가능하다.
