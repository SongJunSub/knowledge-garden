# 코드 리뷰의 주된 목적은 유지보수하기 어려운 코드를 찾는 것 (Mark Dominus) — '버그를 찾아라'보다 '이해해보고 막히는 부분을 표시하라'가 더 실행 가능하다

> 출처: [I think many people misunderstand the purpose of code review](https://mathstodon.xyz/@mjd/115096720350507897) (Mark Dominus, Mathstodon) · 정리일 2026-06-30

## 한 줄 요약

**코드 리뷰의 전통적 목표는 "버그 발견"이지만, 코드 검사만으로 버그를 안정적으로 찾겠다는 기대는 비현실적이다. 실제로 더 실행 가능하고 효과적인 리뷰 과제는 "이해하기 어려운 코드"를 찾는 것이다 — 리뷰어가 이해하지 못한다면 미래의 유지보수자도 같은 어려움을 겪을 것이기 때문이다.**

## 핵심 포인트

- **리뷰의 진정한 목적 재정의** — "버그를 찾아라"는 목표는 실패하기 쉽다. 대신 "이해해보고, 막히는 부분을 표시하라"가 리뷰어에게 실제로 수행 가능한 과제.
- **핵심 논리** — 리뷰어(대개 코드 작성자만큼 맥락을 모르는 사람)가 코드를 이해하지 못한다면, **미래의 유지보수자도 같은 어려움을 겪을 가능성이 높다.** 이해 실패 자체가 결함의 신호.
- **버그 발견의 한계** — 버그는 리뷰 중 발견될 수 있지만, 이는 **부수 효과**에 가깝다 — 주된 메커니즘이 아니다.
- **실무적 기준** — "이해할 수 없는 코드"는 그 자체로 수정 대상. **원 작성자가 맥락을 아직 기억하고 있을 때(리뷰 시점) 개선하는 것이 가장 효율적** — 나중에는 그 맥락 자체가 사라진다.

## 인상 깊은 문장

> "리뷰어가 코드를 이해하지 못한다면, 미래의 유지보수자도 같은 어려움을 겪을 가능성이 높다."

## 댓글 — HN 다양한 관점 (GN⁺ 큐레이션)

- **다목적성 강조**: 코드 리뷰는 유지보수성 외에도 안전장치·지식 공유·공동 책임·멘토링 등 단일 목적이 아니라는 반박.
- **자동화 테스트의 중요성**: 코드 리뷰만으로는 부족, 테스트와 함께 작동해야 함.
- **비판적 관점**: "게으른 리뷰어의 자기합리화"라는 냉소적 지적도 제기됨.
- **프로세스 맥락**: 동기식 대면 리뷰와 비동기 PR 리뷰의 효과성이 다를 수 있다는 지적.
- **팀 규모·조직 구조에 따른 차이**: 리뷰 방식이 상황에 따라 달라져야 함.
- **AI 시대 리뷰의 중요성 증대**: AI 생성 코드가 늘수록 "이해 가능성" 검증이 더 중요해진다는 관측.
- **리뷰 코멘트 접두어 관행**: `thought`·`change`·`nit` 등 접두어로 코멘트의 강도·의도를 명확히 하는 실무 팁 공유.

## 내 생각 · 적용점

### 핵심 전이 1 — AI 생성 코드 리뷰에서 이 원칙이 더욱 중요해진다

[[2026-06-30-artificial-adventures-ai-tools-reality]]에서 다룬 저자의 경험 — "Opus가 fuzzer도 놓친 버그를 찾았다" — 는 정확히 이 원칙의 실증이다. **AI가 리뷰할 때도 "버그가 있는가"보다 "이 코드가 이해 가능한가"를 먼저 묻는 것이 더 강력한 필터다.** [[2026-06-30-towards-understandable-software]]의 "추상화는 예측 가능하고 일관되어야 한다"는 주장과 정확히 같은 원리 — 이해 불가능한 코드는 추상화 실패의 증거다.

### 핵심 전이 2 — "맥락이 살아있을 때 고쳐라"는 CRS 코드 리뷰 문화의 구체적 실천 지침

CRS·PickMe PR 리뷰에서 "이거 왜 이렇게 했어요?"라는 질문에 작성자가 즉답하지 못하면, 그 코드는 즉시 리팩토링 대상이 되어야 한다. **[[2026-06-30-arguments-are-about-ego-not-ideas]]와 결합하면** — 이 질문을 "당신이 틀렸다"가 아니라 "이 부분이 저에게 이해가 안 됩니다"로 프레이밍하는 것이 관계도 지키고 코드 품질도 지키는 방법이다.

### 핵심 전이 3 — 리뷰 코멘트 접두어 관행을 CRS 팀에 도입 검토

`thought`(제안, 선택)·`change`(반드시 수정)·`nit`(사소함) 같은 접두어는 리뷰 코멘트의 강도를 명확히 해서 불필요한 방어적 반응을 줄인다. **이것이 [[2026-06-30-arguments-are-about-ego-not-ideas]]의 "논쟁이 자아 방어로 흐르는 것"을 구조적으로 예방하는 실무 장치다.** CRS PR 템플릿에 이 관행을 명시적으로 도입하면 리뷰 문화 개선에 즉시 적용 가능하다.
