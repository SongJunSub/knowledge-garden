# Git 3.0의 SHA-256 기본값 전환은 값비싼 실수다 (Scott Chacon)

> 출처: [Git 3.0's upcoming SHA-256 default will be a costly mistake](https://blog.gitbutler.com/git-3-sha-256) (GitButler 블로그, Scott Chacon) · GeekNews(id=34627) 경유 · 정리일 2026-10-02

> **출처 한계**: `blog.gitbutler.com`·`news.hada.io`·`news.ycombinator.com` 모두 이 세션에서 egress 차단돼 원문·HN 토론을 직접 열람하지 못했다. WebSearch로 복수 쿼리를 교차확인해 재구성했고, 핵심 논거(해시 무결성과 출처 신뢰의 구분, 전환 비용의 구체 항목, 대안 제안)는 여러 검색 결과에서 일관되게 재현돼 신뢰도가 있다고 판단한다. **HN 댓글 수는 소스마다 273점/277점, 256~273댓글로 갈려 정확한 숫자를 확정하지 못했고, 인용문의 정확한 워딩도 원문 대조는 못했다.**

## 한 줄 요약

**Git 3.0은 새 저장소의 기본 해시를 SHA-1에서 SHA-256으로 바꿀 계획인데, GitHub 공동창업자 Scott Chacon은 "보안상 이익은 미미한 데 반해 생태계 전환 비용은 막대하다"며 반대한다. 핵심 논거는 해시가 콘텐츠의 무결성을 확인하는 것과 그 코드의 출처를 신뢰하는 것은 다른 문제라는 것 — 저장소 쓰기 권한이 탈취되면 더 강한 해시로도 악성 코드 유입을 막을 수 없기 때문에, SHA-256 전환이 실제로 지키는 보안은 생각보다 작다는 것이다.**

## 핵심 포인트

- **해시 무결성과 출처 신뢰는 다른 문제** — 해시는 콘텐츠가 ***바뀌지 않았음을 확인***하는 것이고, 그 코드를 누가 썼고 믈을 수 있는지를 신뢰하는 것은 별개 문제다. 저장소 ***쓰기 권한이 탈취***되면 공격자는 그냥 유효한 SHA-256 해시를 가진 악성 커밋을 만들 수 있어, ***더 강한 해시가 이 공격을 막지 못한다.*** Git의 실제 신뢰 모델은 처음부터 해시 강도가 아니라 ***"어디서 코드를 가져오는가"(GitHub 로그인·조직 권한 등)***에 의존해왔다.
- **SHA-1 약점의 실제 범위는 좁다** — SHA-1에 알려진 공격(SHAttered 등)은 ***이론적 충돌 공격***이고, 특정 해시를 역산해 악성 콘텐츠를 만드는 ***실용적 역상(preimage) 공격은 아니다.*** 즉 당장 실무에서 악용 가능한 위협은 아니라는 게 Chacon의 판단이다.
- **전환 비용의 구체 항목** — SHA-1/SHA-256 저장소가 나뉘면 ***서브모듈 호환성이 깨지고, 커밋·태그 서명이 깨지고, 커밋을 가리키는 URL이 깨지고***, 해시가 40자(SHA-1 길이)라고 가정한 수많은 스크립트·CI·DB 스키마·내부 도구가 함께 깨진다.
- **대안 제안 — 오브젝트 포맷은 건드리지 않는다** — 전체 오브젝트 포맷을 SHA-256으로 바꾸는 대신, ***독립적으로 계산한 SHA-256(또는 BLAKE3) 해시를 커밋/태그에 서명된 헤더로 추가***하는 방식(Colin Walters의 `git-evtag`와 유사)을 제안한다 — 콘텐츠 검증은 얻으면서 오브젝트 포맷 전환이라는 막대한 비용은 피하자는 것.
- **저자의 입지** — Chacon은 GitHub 공동창업자이자 『Pro Git』 저자로, Git 생태계 호환성 문제를 수십 년 겪어본 당사자다. 이 글은 외부 비평이 아니라 ***내부자의 비용 경고***에 가깝다.

## 댓글

HN에서 약 ***270점 전후, 250~270여 댓글***(소스 간 273/277점, 256~273댓글로 집계가 갈림)을 받았다. 확인된 주요 논점: ①SHA-256 전환의 하위 비호환성을 ***IPv6 전환***에 비유 — "효용은 불분명한데 모든 도구가 따라잡아야 한다"는 우려. ②해시가 40자라고 가정한 스크립트·CI·DB 스키마가 실무에서 깨질 거라는 지적. ③Git 측 전환 계획에는 SHA-1/SHA-256 상호운용성이 포함돼 있어 기존 저장소가 하루아침에 깨지지는 않는다는 반론도 소개된 것으로 WebSearch가 합성했다. **원문·HN 모두 직접 대조하지 못해, 이 논점들의 비중·순서는 확정하지 못한다.**

## 내 생각 · 적용점

### 핵심 전이 1 — 9월엔 "논의 중", 10월엔 "구체적 반대" — 아직도 확정이 아니다

**[[2026-09-23-git-2-56-and-3-0]]**가 9월에 "아직 논의 중"이라 유보적으로 다뤘던 그 SHA-256 전환 계획에, 이번 글이 구체적 반대 논거를 들고 등장한 후속편이다. 그 노트가 남긴 회고 항목 — ***"실제 릴리스 시점과 세부 사항은 원문에서 직접 확인이 필요하다"*** — 이 한 달이 지나도 그대로라는 것도 같이 확인된다. Git 3.0의 SHA-256 기본값은 9월에도, 10월에도 "확정된 로드맵"이 아니라 ***"GitHub 공동창업자급 인사도 반대하는, 여전히 논쟁 중인 제안"***인 채로 남아 있다.

### 핵심 전이 2 — 같은 "암호 알고리즘 교체"인데, 정당화 기준이 정반대다

**[[2026-08-24-pqc-ml-kem-developer-guide]]**가 다룬 PQC(ML-KEM) 전환은 "지금은 못 풀어도 미래 양자컴퓨터가 지금 도청한 암호문을 나중에 푼다"는 ***harvest-now-decrypt-later***라는 구체적이고 시간차가 있는 위협에 대응하는 선제적 전환이었다. 이 Git SHA-256 전환은 반대로 — Chacon의 논거를 따르면 — ***실용적 역상공격이 아닌 이론적 충돌 공격***이라는, 당장도 미래도 급박하지 않은 위협에 생태계 전체의 막대한 호환성 비용을 치르는 전환이다. 같은 "암호 해시 알고리즘 교체" 결정이라도, ***위협의 구체성과 시간차가 비용 정당화를 가르는 기준***이 된다는 대비가 두 노트를 나란히 놓으면 선명해진다.

## 호스피탈리티 / CRS 적용 포인트

직접 적용은 멀다 — 온다가 Git 해시 알고리즘 선택에 관여할 일은 없다. 다만 전이 가능한 의사결정 원칙 하나는 남긴다: ***"보안·기술적으로 더 나은 선택"이라는 이유만으로 생태계 전체(서명, URL, 외부 연동, 레거시 스키마)가 깨지는 마이그레이션을 밀어붙이기 전에, 그 위협이 이론적인지 실제로 악용 가능한지, 그리고 전환 비용을 상쇄할 만큼 급박한지를 먼저 구분해야 한다*** — PMS·채널 연동처럼 외부 파트너가 많이 얽힌 CRS 아키텍처 변경 결정에 그대로 적용 가능한 체크리스트다.
