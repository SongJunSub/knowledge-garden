# small-change로 코드 리뷰 속도 높이기, 조건을 충족한 PR의 승인 자동화(GeekNews)

> 출처: [small-change로 코드 리뷰 속도 높이기 - 조건을 충족한 PR의 승인 자동화](https://news.hada.io/topic?id=36270) (GeekNews) · 정리일 2026-10-31

> **출처 한계**: news.hada.io는 egress 차단으로 원문 열람 불가. WebSearch로 가장 근접한 사례는 Ona(옛 Gitpod)의 "Auto-approving low-risk PRs" 블로그로, "승인은 하되 병합은 하지 않는다", "승인 대기 시간이 중앙값 2시간49분에서 5분 미만으로 줄었다"는 내용이 Slack 발췌의 결과 지향적 서사와 결이 같다. 다만 ona.com은 이 세션에서 egress 차단돼 **직접 원문을 확인하지 못했고**, "1,000줄 미만·p1/p2 지적 없음·작성자의 해당 서비스 PR 병합 경험 10건 이상" 같은 구체 조건이 이 블로그의 것인지도 검증하지 못했다. "small-change"라는 정확한 이름을 WebSearch 결과에서 직접 확인하지도 못했다 — **이 노트는 Slack 발췌를 1차 자료로, Ona 사례는 참고 맥락으로만 인용한다.**

## 한 줄 요약

**엔지니어링 PR 병합이 2년간 4배로 늘고 리뷰 시간이 두 배 넘게 길어지자, 제한된 조건(크기·자동 리뷰 결과·작성자 경험)을 CI/CD로 검사해 통과한 PR만 빠르게 승인하는 `small-change` 방식을 도입했다.**

## 핵심 포인트

- **PR 병합 4배 증가, 리뷰 시간 중앙값 33분→77분** — AI가 코드 작성 속도를 높이면서 리뷰 쪽이 명백한 병목이 됐다는 수치다.
- **CI/CD가 거르는 조건: 1,000줄 미만, 자동 리뷰의 p1·p2 지적 없음, 작성자의 해당 서비스 PR 병합 경험 10건 이상** — ***공유 라이브러리와 민감한 경로는 이 자동 승인 대상에서 제외한다.*** 크기만이 아니라 "이미 신뢰를 쌓은 작성자가 위험하지 않은 영역을 건드렸는지"까지 함께 본다.
- **승인하거나 건너뛸 뿐, 댓글은 남기지 않는다** — ***모든 검사를 통과한 PR을 승인하거나 건너뛰며, 사람이 AI 리뷰 댓글을 중계하고 다시 AI로 답변하는 과정에서 생기는 부담을 피하려는 설계다.*** AI가 댓글을 달면 사람이 그걸 읽고 AI에게 다시 물어보는 왕복이 생기는데, 이 방식은 그 왕복 자체를 없앴다.
- **(WebSearch 참고) Ona 사례에서는 승인 대기 시간이 2시간49분→5분 미만으로 줄었다고 보도됨** — 자동 승인의 효과가 "리뷰를 없애는 것"이 아니라 "승인까지 기다리는 시간을 없애는 것"에 있다는 해석과 맞아떨어진다.

## 내 생각 · 적용점

**핵심 전이 1 — "자동 승인"의 핵심은 범위를 좁히는 설계에 있다.** 크기 제한 하나만으로는 안전하지 않다(작은 변경이 민감한 경로를 건드릴 수 있다). 이 방식은 크기 + 자동 리뷰 결과 + 작성자 신뢰도 + 경로 제외라는 **네 가지 조건을 겹쳐서** 안전망을 만들었다. [[2026-10-31-cursor-marketplace-claude-code-ssh-backdoor]]에서 다룰 "신뢰 경계를 어디에 두느냐"의 문제와 같은 축이다 — 자동화의 범위는 "무엇을 자동화하는가"보다 "무엇을 자동화 대상에서 제외하는가"로 설계해야 더 안전하다.

**핵심 전이 2 — AI 리뷰 댓글의 왕복 비용을 명시적으로 없앤 설계가 인상적이다.** AI가 댓글을 달고 사람이 중계하고 다시 AI가 답하는 구조는 속도를 전혀 올리지 못하면서 피로만 늘릴 수 있다. "댓글 없이 승인만 하거나 건너뛴다"는 선택은 단순하지만, 병목의 정체(승인 대기 시간)를 정확히 짚었기 때문에 효과가 난다.

## 호스피탈리티 / CRS 적용 포인트

**부분 적용 가능성이 있다, 신중하게.** 온다의 CRS 코드베이스에도 변경 빈도가 높고 리스크가 낮은 영역(문서, 내부 도구, 테스트 전용 코드 등)이 있다면, 크기·자동 검사 결과·작성자 경험을 조건으로 건 자동 승인을 제한적으로 시도해볼 수 있다. 다만 ***예약·요금·재고 로직처럼 오류가 매출로 직결되는 경로는 이 방식의 제외 대상으로 명확히 선을 그어야 한다.*** 직접 전면 적용은 리스크가 크다.
