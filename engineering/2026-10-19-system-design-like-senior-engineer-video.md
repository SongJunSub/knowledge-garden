# 시니어 엔지니어처럼 소프트웨어 시스템 설계하기 - 풀코스 [동영상]

> 출처: 원문 미확인(`news.hada.io` 차단) · GeekNews(id=35613) 경유 · WebSearch로 freeCodeCamp의 "Learn how to design software systems like a senior engineer" 영어 강좌와 제목이 유사함을 확인(동일 강좌의 한국어 소개인지, 다른 영상인지는 미확정) · 정리일 2026-10-19
>
> **출처 한계**: `news.hada.io`는 이번 세션 내내 열리지 않았다. WebSearch 결과 영어 제목이 거의 동일한 freeCodeCamp 강좌("learn how to design software systems like a senior engineer")를 찾았으나, Slack 발췌가 언급한 "Spotify, Booking.com, WhatsApp과 유사한 시스템을 설계" 같은 세부 커리큘럼이 그 강좌와 정확히 일치하는지는 확인하지 못했다 — 동일 영상일 가능성이 높지만 단정하지 않는다. Booking.com 관련 WebSearch 결과(실제 면접 후기)는 "객실 검색·가용성 시스템 설계"가 실제 Booking.com 면접 소재로 쓰인다는 정황만 뒷받침한다.

## 한 줄 요약

**시스템 설계 면접은 완성된 아키텍처를 맞히는 시험이 아니라, 모호한 요구사항을 구체화하고 선택의 이유를 설명하는 과정 자체를 평가한다.**

## 핵심 포인트

- 약 3시간 분량의 시스템 설계 면접 대비 강의, ***5단계 접근법***을 배우고 Spotify, Booking.com, WhatsApp과 유사한 시스템을 설계하는 과정에 적용.
- 시스템 설계 면접은 완성된 아키텍처뿐 아니라 ***소통과 협업, 구조화된 사고, 기술적 판단, 실무 깊이, 시간 관리***를 평가하며, 모호한 요구사항을 구체화하는 과정이 중요.
- 진행 순서: ***요구사항 확인 → 데이터/API와 상위 아키텍처 설계 → 확장성과 장애 검토 → 절충점 정리***.
- ***정답을 외우기보다 가정을 확인하고 선택 이유를 설명하는 능력***에 초점.
- (발췌가 "음악 스…"에서 끊겨 Spotify 관련 구체 설계 내용은 확인하지 못함.)

## 내 생각 · 적용점

"정답 암기가 아니라 가정 확인과 선택 설명"이라는 평가 기준은 시스템 설계 면접을 넘어 실무 코드 리뷰·아키텍처 결정 회의에도 그대로 적용되는 원칙이다. [[2026-10-19-person-behind-the-software-linear]](같은 날 다룬 다른 글)이 말하는 "제품의 직관은 고객과의 대화·실수에서 쌓인 판단력"이라는 결론과 구조적으로 닮았다 — 둘 다 "정해진 정답"보다 "맥락에 맞는 판단과 그 판단을 설명하는 능력"을 더 높게 친다.

## 호스피탈리티 / CRS 적용 포인트

CRS 아키텍처 설계 회의에서도 "완성된 다이어그램"보다 "왜 이 트레이드오프를 골랐는지 설명할 수 있는가"를 평가 기준으로 삼을 수 있다. 특히 Booking.com류의 "날짜 범위별 객실 가용성 검색, 고트래픽 처리"는 CRS 자체의 핵심 도메인 문제이므로, 이 강좌의 설계 접근법(요구사항 확인 → 데이터/API → 확장성/장애 → 절충점)을 신입 엔지니어 온보딩용 아키텍처 리뷰 체크리스트로 바로 가져올 수 있다.
