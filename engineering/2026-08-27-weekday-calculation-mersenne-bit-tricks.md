# 요일 계산을 더 빠르게 만드는 방법 (Ben Joffe)

> 출처: [A faster way to calculate the day-of-the-week](https://www.benjoffe.com/fast-day-of-week) (benjoffe.com, Ben Joffe) · 정리일 2026-08-27
> **출처 한계**: `news.hada.io`·`benjoffe.com`(원문 포함)·`web.archive.org` 전부 이 세션에서 접근이 막혔다. 아래 내용은 WebSearch가 반환한 검색엔진 요약·스니펫을 여러 차례 교차 조회해 재구성한 것이며, 구체적인 코드 스니펫·상수값 전부·정확한 문단 순서는 원문을 직접 대조하지 못했다. Slack 발췌의 수치(`(u32(rd) * M + Z) >> 29`, `>> 29` 시프트)는 WebSearch로 재구성한 "제한 범위에서 곱셈+덧셈+시프트 3연산" 설명과 부합해 핵심 아이디어의 신뢰도는 높다고 판단한다. hada 댓글·HN·Lobsters의 정확한 댓글 수는 확인하지 못했다.

## 한 줄 요약

**7이 메르센 수(Mersenne number, `2ⁿ - 1` 형태 중 `2³ - 1`)라는 성질 하나로, `rd % 7`(rata die 날짜 카운트에서 요일 추출)을 나눗셈 없이 곱셈·덧셈·비트 시프트만으로 계산하는 방법을 제시한다. 핵심 항등식은 `N % 7 = floor(N * 8/7) % 8`** — 7로 나누는 대신 8/7을 곱해 값을 "가짜 8일짜리 주"로 밀어넣은 뒤, 하위 3비트만 읽으면 진짜 요일이 나온다. **제한된 날짜 범위에서는 이 원리가 `weekday = (u32(rd) * M + Z) >> 29` 같은 단 3개 연산으로 압축**되고, 32비트 전체 범위를 감당해야 하는 경우엔 보정 시프트·두 번의 곱셈·곱셈 결과의 상하위 비트를 나눠 쓰는 여러 변형으로 확장한다. 저자는 지연시간(latency) 최적화 버전과 처리량(throughput) 최적화 버전을 구분해 제시하고, 이 트릭이 7뿐 아니라 3·15·31 같은 다른 메르센 수 나눗셈에도 일반화된다고 설명한다.**

## 핵심 포인트

- **핵심 항등식** — `N % 7 = floor(N * 8/7) % 8`. 8/7(≈1.142857)을 정수 고정소수점 곱셈으로 근사해 곱하면, 결과가 "8일 주기"에 맞춰지고 **하위 3비트를 읽는 것만으로 실제 7일 요일이 나온다.** 나눗셈(느린 연산)을 곱셈+비트 마스크(빠른 연산)로 치환하는 것이 트릭의 전부다.
- **제한 범위 공식** — `weekday = (u32(rd) * M + Z) >> 29` 형태 — **곱셈 1회 + 덧셈 1회 + 시프트 1회, 단 3연산.** `rd`는 rata die(1970-01-01을 기준점 삼는 부호 있는 32비트 날짜 카운트, 이 기준으로 목요일=4).
- **32비트 전체 범위로 확장** — 단일 곱셈으로는 부호·오버플로 문제가 생기는 전체 범위를 감당하려면, 보정 시프트를 추가하거나 **두 번의 곱셈을 쓰거나, 한 곱셈 결과의 상위/하위 비트를 각각 다른 용도로 재사용**하는 변형들이 필요하다 — 저자는 이걸 여러 개의 이름 붙은 변형(예: `32unix_medium`)으로 벤치마크 페이지에 정리해둔 것으로 보인다.
- **지연시간 vs 처리량 트레이드오프** — 일부 변형은 `(rd >> 1) + (rd >> 4)` 항을 손으로 짠 나눗셈으로 대체해 **처리량(throughput)에 최적화**하고, 다른 변형은 항을 하나 줄여 **지연시간(latency)**을 낮추는 대신 범위를 좁힌다(약 ±146만 년 범위로 축소되는 버전 언급) — "빠르다"가 단일 축이 아니라는 걸 명시한다.
- **왜 특히 x86/ARM에서 빠른가** — x86의 `LEA` 명령어는 값을 2·4·8배 곱하면서 동시에 다른 변수를 더하는 걸 **한 사이클**에 처리할 수 있어 이 공식과 궁합이 좋다. ARM에서도 일부 라인이 앞선 코드와 부분적으로 한 명령으로 합쳐져(fuse) 최종 비트마스크 연산이 사실상 단일 사이클이 된다.
- **일반화** — 이 기법은 7뿐 아니라 **3·15·31처럼 `2ⁿ - 1` 형태의 다른 메르센 수를 나누는 모듈로 연산 전반**에 적용 가능하다. 단 제약이 있다 — 나누는 수가 `2^(비트폭/2-1)`보다 작아야 한다는 조건.
- **기존 연구 위에 세워진 벤치마크** — 저자의 보조 저장소(`fast-date-benchmarks`)가 **Neri-Schneider EAF**(기존에 학술적으로 발표된 요일 계산 알고리즘)를 포크해 만들어졌다는 정황이 있다 — 완전히 새로운 발견이라기보다 기존 최적 알고리즘군과의 비교·개선 작업으로 읽는 게 정확하다(이 부분은 WebSearch 스니펫으로만 확인, 원문에서 직접 대조 못함).

## 내 생각 · 적용점

### 핵심 전이 — SIMD 글과 같은 "저수준 크래프트" 축이지만, 정반대로 정직한 저자의 태도

[[2026-07-24-everyone-should-know-simd]]에서 정리한 Mitchell Hashimoto의 결론은 ***"SIMD는 극단적 트릭이 아니라 알아볼 수 있으면 되는 일상 최적화"***였고, HN 반론은 ***"측정·자료구조가 먼저"***였다. 이 요일 계산 글도 정확히 같은 구조의 트릭이다 — CPU가 이미 잘 지원하는 기본 연산(곱셈·시프트)으로 느린 연산(나눗셈)을 대체하는, **"기회를 알아보면 적용할 수 있는" 종류의 저수준 최적화**다. 다만 이 글이 SIMD 글보다 한 걸음 더 정직한 지점이 있다 — 저자 스스로 **지연시간 최적화판과 처리량 최적화판을 나누고, 각 변형이 커버하는 날짜 범위를 명시**해, "더 빠르다"는 주장이 맥락 의존적이라는 걸 숨기지 않는다. `% 7` 하나가 프로그램의 병목일 일은 거의 없다는 점에서, **이 글의 진짜 가치는 실무 적용보다 "느린 연산을 빠른 연산의 조합으로 재구성하는 사고 패턴" 자체를 보여주는 데 있다** — 컴파일러의 상수 나눗셈 최적화(strength reduction)가 내부적으로 하는 일을 사람이 손으로 유도해본 사례로 읽는 게 정확하다.

## 호스피탈리티 / CRS 적용 포인트

**직접 적용은 멀다.** 온다 CRS는 I/O·DB 바운드 시스템이고, `% 7` 같은 마이크로초 단위 CPU 연산이 실측 병목이 될 가능성은 거의 없다 — 요일 계산이 필요한 곳(예약 캘린더·주기 반복 규칙)은 이미 언어 표준 라이브러리(`java.time.DayOfWeek` 등)가 충분히 빠르고 검증돼 있어, 이런 손수 비트 트릭을 끌어올 이유가 없다. 전이 가능한 원칙만 남긴다: **"나눗셈이 느리면, 그 나누는 수의 수학적 성질(메르센 수·2의 거듭제곱 등)을 먼저 살펴보라"**는 사고방식은 드물게 실제 핫 루프(대량 배치 정산·시간대 변환 반복문)에서 컴파일러가 못 잡는 상수 나눗셈이 병목으로 잡힐 때 참고할 수 있는 최후의 수단 정도로만 기억해둔다.
