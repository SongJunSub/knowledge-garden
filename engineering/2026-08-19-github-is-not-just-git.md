## 한 줄 요약

**8월 17일 장애가 웹과 API 트래픽의 20%, 아카이브 다운로드의 50%에 영향을 줬고 PR 과 Issues 와 Actions 가 함께 막혔다. 그런데 아티클이 짚는 건 빈도가 아니라 범위다. 최근에는 장애가 더 자주 보일 뿐 아니라 서로 다른 작업을 연달아 막는다는 것. 그리고 복구된 뒤에도 PR 에 접근할 수 없는데 공식 상태 페이지는 모두 정상으로 표시되는 상황이 나온다. 논지는 제목 그대로다. Git 은 분산돼 있지만 개발 과정은 분산돼 있지 않다. 그래서 의존을 네 층으로 나눈다. 코드와 Git 히스토리는 미러만 있으면 옮기기 쉽고, Issues 와 PR 은 GitHub 의 데이터 모델과 URL 에 묶여 중간이고, Actions 와 릴리스 파이프라인은 어렵고, 정체성과 발견 가능성이 가장 어렵다. 셋째 층에 대한 문장이 이 아티클에서 가장 아프다. 자체 호스팅 러너도 작업을 받지 못한다. 제어면이 GitHub 에 남아 있기 때문이다. 결론은 이전이 아니라 분리다. GitHub 를 떠나는 것보다 먼저 해야 할 일은 필요할 때 떠날 수 있는 구조를 만드는 것.**

## 핵심 포인트

- **8월 17일 장애**: **웹·API 트래픽의 20%**, **아카이브 다운로드의 50%** 영향. **PR·Issues·Actions** 가 함께 막혔다.
- **관측의 문제**: ***"복구된 뒤에도 Pull Request 에 접근할 수 없는데 공식 상태 페이지는 모두 정상으로 표시되는 상황."***
- **변한 것은 빈도가 아니라 범위**: ***"최근에는 장애가 더 자주 보일 뿐 아니라 서로 다른 작업을 연달아 막음."***
- **규모 수치**(GitHub COO 공개): **GitHub Actions 실행 시간이 2023년 주당 5억 분 → 2025년 주당 10억 분**, **2026년 4월 초에는 그 주 누적 21억 분.**
- **섹션 제목이 논지를 담는다**: ***"GitHub 장애는 오래됐지만 멈추는 범위가 달라짐"***, ***"Git 은 분산돼 있지만 개발 과정은 분산돼 있지 않음"***, ***"GitHub 는 저장소를 잘 호스팅해서만 승리한 것이 아님."***
- **왜 GitHub 인가**: GitHub 이전의 오픈소스는 **저장소·이슈·토론·발견이 여러 서비스에 흩어져** 있었다. ***"GitHub 의 중앙화는 이런 기록을 한곳에 보존하고 발견할 수 있게 만들었음."***
- **의존의 네 층**:

| 층 | 이전 난이도 | 문제 |
|---|---|---|
| **코드·Git 히스토리** | 쉬움 | 미러가 있으면 위험이 작다 |
| **Issues·PR** | 중간 | **GitHub 의 데이터 모델과 URL 에 묶임** |
| **Actions·릴리스 파이프라인** | 어려움 | ***"자체 호스팅 러너도 작업을 받지 못함. 제어면은 GitHub 에 남아 있기 때문"*** |
| **정체성·발견 가능성** | 가장 어려움 | 계정 이력·Stars·기여 기록이 안 따라간다 |

- **Ghostty 사례**: Mitchell Hashimoto 가 **거의 매일** GitHub 관련 작업 중단을 기록했다. ***"Issues, Pull Requests, Actions 같은 주변 인프라가 실제 작업을 막고 있음."*** 대응은 **전면 이전이 아니라 점진적 의존 축소**이고, **GitHub URL 은 읽기 전용 미러로 유지**한다.
- **대안 네 갈래**: **관리형 Forge**(GitLab, Codeberg, 이전은 쉽지만 중앙화를 재현), **자체 호스팅 Forge**(Forgejo, Gitea, 운영 부담과 기여자 계정 장벽), **경량 Git 호스팅**(SourceHut, cgit, 빠르지만 협업 모델을 포기), **연합·P2P**(Forgejo Federation, Radicle, 이론상 견고하지만 미성숙).
- **자주 간과되는 락인 요인**: **여러 OS 플랫폼의 무료 CI 실행기.**
- **결론의 권고 넷**: ①**코드는 다른 곳에도 존재해야 함**(실제 복구 테스트까지) ②**프로젝트의 기억을 코드 밖에만 두지 않기** ③**릴리스 경로는 별도로 복구 가능해야 함** ④**오픈소스의 입구와 작업 공간을 분리할 수 있음.**
- **핵심 문장**: ***"GitHub 를 떠나는 것보다 먼저 해야 할 일은, 필요할 때 떠날 수 있는 구조를 만드는 것."***

## 내 생각 · 적용점

### 핵심 전이 1: 아티클이 엮는 흐름을 가든이 이미 갖고 있었다

**[[2026-08-17-weekly-371]]에서 편집자의 새 형식 도입 이유를 정리했다.** ***"뉴스는 각각 독립되어 보이지만 시간이 지나면 서로 연결되어 흐름을 만든다."***

**이 아티클이 그 흐름의 실물인데, 그 조각들이 이미 가든에 있다.**

| 아티클이 엮는 것 | 가든의 노트 |
|---|---|
| Ghostty 의 이탈 결정과 GitHub 대안 논의 | [[2026-08-04-github-has-alternatives-no-replacement]] |
| Mitchell Hashimoto 와 Ghostty | [[2026-07-10-mitchell-hashimoto-interview-ghostty-zig]] |
| Forge 에 대한 요구 | [[2026-05-04-if-i-could-make-my-own-github]] |
| 코드 호스팅의 새 시도 | [[2026-08-19-cursor-origin-code-hosting]] |

**8월 4일 노트에 이미 이렇게 적혀 있었다.** ***"Ghostty 가 GitHub Actions 장애로 이탈을 결정한 그날, 저자도 2시간 동안 PR 리뷰를 못 했다. Git 이 아니라, 우리가 의존하는 그 주변 인프라의 문제."***

**이 아티클의 논지가 그 문장의 확장이다.** 편집자가 만든 흐름과 가든이 만든 흐름이 **독립적으로 같은 자리에 도착했다.** 그게 위클리 노트에서 적은 것의 재확인이고, **아티클 형식이 유용한 이유이기도 하다.** 단발 뉴스만 보면 매번 "또 장애"인데, 엮으면 **의존의 구조**가 보인다.

### 핵심 전이 2: "제어면은 GitHub 에 남아 있다"가 가장 실무적인 발견이다

**self-hosted runner 를 쓰면 의존이 줄었다고 믿기 쉽다.** 실행이 우리 머신에서 도니까. **그런데 작업 배정이 GitHub 에서 온다.** GitHub 이 멈추면 **우리 러너는 놀고 있다.**

**즉 self-hosted 는 실행 위치를 옮긴 것이지 의존을 옮긴 게 아니다.** 그리고 이건 CI 만의 이야기가 아니다. **대부분의 "self-hosted" 옵션이 데이터 평면만 주고 제어 평면을 안 준다.**

**그리고 이게 이번 주에 반대편에서 확인한 것과 같은 원리다.** [[2026-08-17-airbnb-flexible-authentication]]에서 ***"클라이언트는 어떤 챌린지를 보여줄지 절대 결정하지 않는다"***가 서버 주도 UI 의 진짜 이유였고, 거기서 **결정 지점을 정보 지점으로 옮기는 게 리팩토링의 한 유형**이라고 정리했다.

**여기서는 그 원리가 불리하게 작동한다.** 결정 지점이 벤더에 있으면, **실행을 아무리 우리 쪽으로 가져와도 벤더가 멈추면 우리도 멈춘다.**

**실무 규칙: 벤더 의존을 점검할 때 데이터가 어디 있는지가 아니라 결정이 어디서 내려지는지를 본다.** 그리고 **"self-hosted"라는 말이 그 질문에 답하지 않는다.**

### 핵심 전이 3: 네 층 구분이 어제 Cursor 노트를 정확히 평가하게 해준다

**어제 [[2026-08-19-cursor-origin-code-hosting]]를 정리하면서 이렇게 적었다.** GitHub 이 진실 공급원으로 남으니 **필요한 건 권위가 아니라 사본**이고, 대체가 아니라 병행이라고.

**이 아티클의 네 층으로 보면 그 평가가 더 정확해진다.** **Cursor Origin 이 복제하는 건 1층(코드)뿐**이다. 2층(Issues·PR)은 GitHub 데이터 모델에, 3층(Actions 제어면)은 GitHub 에, 4층(정체성·발견)은 GitHub 에 그대로 있다.

**그러면 어제 노트의 두 결론이 동시에 참이 된다.**
- **에이전트를 싸게 돌리려면 사본이 필요하다**(1층이면 충분하다).
- **그 사본이 의존을 줄이지는 않는다**(2~4층이 안 움직인다).

**그리고 어제 통합 셋(Vercel·Depot·Buildkite)이 전부 기존 GitHub Actions 워크플로를 실행한다는 게 이제 다르게 읽힌다.** **제어면을 GitHub 에 남긴 채로 실행만 가져온 것**이라, 이 아티클이 지적한 self-hosted 러너와 **정확히 같은 구조**다.

### 핵심 전이 4: 벤더의 상태 페이지는 우리 관측 도구가 아니다

***"복구된 뒤에도 PR 에 접근할 수 없는데 공식 상태 페이지는 모두 정상으로 표시되는 상황."***

**이건 벤더가 거짓말했다는 이야기가 아니라 측정 대상이 다르다는 이야기다.** 벤더는 **자기 서비스 지표**를 재고, 우리는 **우리 워크플로가 되는지**를 알아야 한다. 둘이 자주 어긋난다.

**그리고 이번 주에 같은 형태를 세 번 봤다.**
- [[2026-08-19-claude-code-weekly-limit-extension]]: **같은 신호가 두 해석**을 낳고 외부에서 구분할 수 없다.
- [[2026-08-18-gruber-watermark-perversion-of-writing]]: **구현이 공개되지 않아** 논쟁이 해결되지 않는다.
- **여기**: **벤더 지표가 우리 상태를 대신하지 못한다.**

**공통 규칙: 우리에게 중요한 것은 우리가 재야 한다.** [[2026-07-13-harness-token-overhead-instrument-your-own-boundary]]에서 세운 ***"내 경계에서 직접 계측하라"***가 여기서도 그대로다.

**실무 형태는 단순하다.** GitHub 상태 페이지를 보는 대신 **"우리 PR 이 열리는가, 우리 파이프라인이 도는가"를 주기적으로 확인하는 합성 점검**을 둔다.

### 핵심 전이 5: 무료 CI 가 락인 요인이고, 그 원가가 오르고 있다

**아티클이 자주 간과된다고 지목한 게 여러 OS 플랫폼의 무료 CI 실행기다.** 맞는 지적이다. **macOS·Windows·Linux 러너를 무료로 주는 곳이 거의 없다.**

**그리고 규모가 나온다: 2023년 주당 5억 분, 2025년 10억 분, 2026년 4월 주 21억 분.** 3년에 약 4배다.

**그런데 어제 정리한 [[2026-08-19-memory-prices-climb-500-percent]]와 겹쳐 보면 질문이 생긴다.** 하드웨어 원가가 오르는 국면에서 **무료 실행 시간이 4배로 늘면 그 비용은 어디서 나오나.** 그리고 **그게 계속 무료일 수 있나.**

**두 결과 중 하나로 갈 것 같다.** 한도가 조여지거나, 유료 전환이 늘거나. **그리고 어느 쪽이든 락인 비용이 뒤늦게 청구된다.** 이번 주에 [[2026-08-19-claude-code-weekly-limit-extension]]에서 **한도에도 만료일이 붙는다**를 규칙으로 세웠는데, **무료 CI 한도가 같은 구조**다. **(내 추론이고 아티클이 이렇게 말하지 않는다.)**

### 핵심 전이 6: "떠날 수 있는 구조"가 우리 방법론의 추상화 분기다

***"GitHub 를 떠나는 것보다 먼저 해야 할 일은, 필요할 때 떠날 수 있는 구조를 만드는 것."***

**이게 우리 방법론의 마이그레이션 전략 셋 중 추상화 분기(Branch by Abstraction)와 정확히 같다.** 기존 구현을 살려둔 채 대안을 붙이고 점진 전환하는 것. **그리고 Ghostty 의 실제 선택이 그 형태다.** 전면 이전이 아니라 **점진적 축소**, GitHub URL 은 **읽기 전용 미러로 유지.**

**그리고 각 층마다 전략이 달라야 한다는 게 이 아티클의 층 구분에서 따라 나온다.**
- **1층(코드)**: 미러. **다만 복구 테스트까지** 해야 한다(아티클이 명시한다).
- **2층(Issues·PR)**: 기억을 **코드 밖에만 두지 않기.** 결정 근거를 PR 코멘트에만 남기면 그게 벤더 데이터가 된다.
- **3층(릴리스)**: **별도 복구 경로.** 배포가 Actions 에만 걸려 있으면 GitHub 장애가 곧 배포 불가다.
- **4층(정체성)**: **입구와 작업 공간을 분리.** 발견은 GitHub 에 두고 실제 작업은 다른 데서.

**2층이 이번 시즌 반복 주제와 겹친다.** [[2026-05-14-naur-programming-as-theory-building]]과 [[2026-08-16-not-tech-debt-just-mess]]에서 **결정의 이론이 코드에 안 남는 문제**를 다뤘는데, **여기서는 그게 벤더 락인 문제이기도 하다.** 이론을 PR 코멘트에 남기면 **이해가 안 쌓이는 동시에 옮길 수도 없다.**

## 호스피탈리티 / CRS 적용 포인트

- **네 층으로 나눠 우리 GitHub 의존을 점검한다.** 코드는 미러가 있는지, Issues·PR 의 결정 기록이 밖에도 있는지, 릴리스가 Actions 외 경로가 있는지, 그리고 4층은 사내 저장소면 해당 없다.
- **"self-hosted 러너를 쓰니까 괜찮다"를 검증한다.** **제어면이 어디 있는지**가 실제 질문이다. GitHub 이 멈추면 우리 러너에 작업이 안 온다.
- **릴리스 경로를 이중화한다.** 우리 배포가 GitHub Actions 에만 걸려 있으면 **GitHub 장애 = 긴급 배포 불가**다. 장애 대응 중에 배포가 필요한 상황이 가장 흔하다.
- **결정 근거를 PR 코멘트 밖에 남긴다.** 이번 시즌 세 번째 확인이다. **이해가 안 쌓이는 문제이면서 동시에 옮길 수 없는 문제**다.
- **벤더 상태 페이지를 우리 관측으로 쓰지 않는다.** ***"우리 PR 이 열리는가, 우리 파이프라인이 도는가"***를 재는 합성 점검을 둔다.
- **무료 CI 한도에 만료일이 있다고 가정한다.** 이번 주에 세운 가격 규칙 다섯 중 셋째(**각 한도에 만료일**)가 여기 적용된다.
- **떠나기 전에 떠날 수 있는 구조부터.** 우리 방법론의 **추상화 분기**를 그대로 쓰면 되고, **층마다 다른 전략**이 필요하다.
