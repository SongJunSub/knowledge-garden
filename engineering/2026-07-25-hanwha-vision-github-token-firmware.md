# 한화비전 카메라 웹 UI에 GitHub 관리자 토큰이 출하됐다 — 빌드 설정 한 줄이 조직 전체를 열었다

> 출처: [Hanwha Vision shipped a GitHub admin token in their camera login page](https://hhh.hn/hanwha-github-token/) (hhh.hn · GeekNews GN⁺ 요약 + HN 큐레이션) · 정리일 2026-07-25

## 한 줄 요약

**한화비전 보안 카메라 펌웨어의 **웹 관리 UI 로그인 페이지**에서 GitHub 토큰이 발견됐다. 그 토큰은 **조직 내 수백 개 저장소에 대한 관리자 권한**을 가지고 있었고, **약 30개 파일**에 박힌 채 출하됐다. 저자는 약 600개 펌웨어 중 **500개를 받아 62%를 추출**했는데, **발견된 토큰이 전부 동일**했다 — 즉 한 번의 실수가 제품군 전체에 복제된 것이다. 원인은 침해가 아니라 **빌드 파이프라인**이다: Vite 빌드가 **빌드 시점의 `process.env` 전체**를 번들에 기록하면서 CI 환경 전체(`GITHUB_NPM_TOKEN` + 내부 설정)가 클라이언트 자산으로 나갔다. 여기에 두 번째 층의 실패가 겹친다 — 펌웨어 암호화의 AES 키가 *"바이너리 안의 작은 정적 테이블과 XOR되어 런타임에 재조립"*되는 방식이라 **난독화일 뿐 보안이 아니었고**, 키와 IV는 같은 모델에서 공통이었다. 그리고 이 조사에서 가장 시대를 보여주는 문장은 기술적 발견이 아니라 방법론이다: ***"2023년이었다면 나도 붙잡고 파고들었겠지만, 나는 Claude Code를 겨눠 놓고 근사한 저녁을 만들러 갔다."*** — **리버싱 난이도가 진입 장벽이던 시대의 종료 선언**이다. 부수적으로 CI 환경변수에서 **미 국방부에 할당된 IP 대역**(`55.101.212.23`, `55.101.212.21:5601`, `55.101.211.213`)이 함께 노출됐는데, HN 다수는 **토큰보다 이쪽이 더 심각**하다고 봤다. 한화의 대응은 빨랐다 — **신고 후 12시간 내 토큰 폐기**.**

## 핵심 포인트

- **무엇이 새어 나갔나** — 웹 관리 UI 파일 **약 30개**에 동일한 GitHub 토큰. 권한은 **조직 내 수백 개 저장소에 대한 관리자 권한**. (토큰 자체는 `GITHUB_NPM_TOKEN`, 즉 사내 npm 패키지 설치용으로 발급된 것으로 보이는데 **권한 범위가 과대했다**.)
- **근본 원인 = 빌드 시점 환경 직렬화** — Vite 빌드 변수가 ***"빌드 시점의 process.env 전체"***를 기록하면서 **CI 환경 전체가 클라이언트 번들에 들어갔다**. 개발자가 시크릿을 "하드코딩"한 게 아니라, **빌드 도구가 대신 하드코딩해 줬다**. 이 구분이 중요하다 — 코드 리뷰로는 안 잡힌다.
- **규모와 균질성** — 약 **600개 중 500개** 펌웨어 다운로드, **추출 성공률 62%**, 발견된 GitHub 토큰 **3개(모두 동일)**. *한 번의 파이프라인 실수 → 제품군 전체*.
- **펌웨어 암호화는 난독화였다** — Binwalk로 암호화된 `fwimage.tgz`를 발견, 1단계는 선행 연구(Matt Brown)의 `"HTW" + 모델번호` 방식으로 복호화. 중첩된 2단계는 ***"AES 키가 바이너리 안의 작은 정적 테이블과 XOR되어 런타임에 재조립"***되는 구조 — 저자는 `fwupgrader` 바이너리를 **Claude Code로 역분석**해 XOR 난독화를 벗겨냈다. **키·IV는 같은 모델에서 공통.**
- **국방부 IP 노출** — CI 환경변수에 세 개 주소: `SWARM_MASTER_NFS_ADDRESS: 55.101.212.23`, `OTEL_ELASTIC_URL: http://55.101.212.21:5601`, `CIMIP: 55.101.211.213`. **55.0.0.0/8은 미 국방부 할당 대역**이다. HN의 다수 의견은 *"토큰보다 이게 더 심각한 문제"*.
- **대응** — 신고 후 ***12시간 내 토큰 폐기***. (문제의 규모에 비해 **대응은 모범적**이었다는 점은 공정하게 기록해 둘 만하다.)
- **방법론이 곧 뉴스다** — ***"2023년이었다면 붙잡고 파고들었겠지만, Claude Code를 겨눠 놓고 저녁을 만들러 갔다."*** 바이너리 역분석·난독화 해제의 **인건비가 0에 수렴**했다.

## 내 생각 · 적용점

### 핵심 전이 1 — 이건 "시크릿을 하드코딩하지 마라"가 아니라 **"빌드 도구가 대신 하드코딩한다"**는 이야기다

내 규칙(CLAUDE.md의 프롬프트 위생 조항)에도 *"코드에 하드코딩 금지"*가 있고, 대부분의 조직 규칙도 거기서 멈춘다. 이 사고는 그 규칙을 **완벽히 지켰어도 발생한다.** 아무도 토큰을 소스에 적지 않았다 — `process.env.GITHUB_NPM_TOKEN`을 참조했을 뿐이고, **Vite가 빌드 시점에 그것을 값으로 치환해 번들에 굳혔다.**

그래서 실무 규칙을 한 단계 올려야 한다:

> **시크릿 위생의 단위는 "소스 코드"가 아니라 "빌드 산출물"이다.**
> 리뷰 대상은 diff가 아니라 **번들·이미지·펌웨어**여야 한다.

즉시 실행 가능한 형태로:
- **번들에 대해 시크릿 스캐너를 돌린다** (gitleaks/trufflehog를 소스가 아니라 `dist/`·컨테이너 이미지·아티팩트에).
- **`define`/`envPrefix` 화이트리스트를 강제한다** — Vite의 `import.meta.env`는 `VITE_` 접두사만 노출하지만, `define: { 'process.env': process.env }` 같은 한 줄이 그 방어를 통째로 무력화한다. **그 패턴을 CI에서 금지 grep 한다.**
- **빌드 CI에서 시크릿을 아예 다른 채널로 준다** — npm 레지스트리 인증은 `.npmrc`/OIDC로, **환경변수로 주지 않는다.**

이건 내 방법론의 *"강제 표현 → 코드/hook 인코딩"* 위계 그 자체다. *"번들에 시크릿 넣지 마세요"*는 프롬프트고, **`dist/`에 대한 gitleaks 스텝**은 게이트다.

### 핵심 전이 2 — 최소 권한이 있었다면 이 사고는 **뉴스가 아니었다**

토큰이 새어 나간 건 사고지만, 그 토큰이 *"조직 내 수백 개 저장소 관리자 권한"*을 가진 건 **설계**다. 이름이 `GITHUB_NPM_TOKEN`인 걸 보면 용도는 **사내 패키지 읽기 하나**였을 것이다. 읽기 전용 토큰이었다면 이 글은 *"카메라 펌웨어에서 만료된 읽기 토큰 발견"*이라는 각주로 끝났다.

이건 내 dry-run 게이트의 **최소 권한 토큰** 조항과 정확히 같은 이야기다: *"작업별 단일 용도 토큰 발급, 과대 권한이면 거부 또는 축소 요청."* 여기에 이 사건이 하나를 더한다 — **회전 일자 추적.** 토큰이 언제 발급됐고 언제 회전되는지 아무도 모르면, 유출 시점부터 폐기까지의 창은 *제품 수명 전체*가 된다(이 사건에선 펌웨어가 출하된 순간부터 신고 시점까지였다).

**행동 항목**: 우리 CI의 토큰 목록을 뽑고, 각각에 대해 ①실제로 필요한 최소 스코프 ②마지막 회전 일자 ③유출 시 폭발 반경을 적어보기. 세 칸을 못 채우는 토큰이 이 사건의 후보다.

### 핵심 전이 3 — [[2026-07-24-fake-interview-git-hook-malware]]의 **거울상**: 같은 AI, 반대 방향

어제 정리한 그 글에서는 AI가 **공격 쪽**에 서 있었다(과제형 면접 ZIP에 심긴 pre-commit 훅, 그리고 방어자가 Claude에게 분석을 요청했다가 거부당하고 Gemini로 넘어간 장면). 여기서는 정반대다 — **연구자가 Claude Code를 겨눠 놓고 저녁을 만드는 동안 AES 난독화가 벗겨졌다.**

두 장면을 겹치면 이번 주 보안 축의 결론이 나온다:

> **LLM은 공격/방어 어느 쪽에도 인건비를 0으로 만든다. 그러면 "발견되기까지 걸리는 시간"을 전제로 한 모든 보안 모델이 무너진다.**

난독화, 펌웨어 암호화, "설마 누가 500개 펌웨어를 다 까보겠어" — 전부 **시간 비용에 기댄 방어**였고, 그 비용이 사라졌다. 남는 건 시간에 기대지 않는 방어뿐이다: **최소 권한, 시크릿을 애초에 산출물에 넣지 않기, 짧은 수명과 회전.** [[2026-05-09-ai-breaking-vulnerability-cultures]]가 예고한 *"취약점 문화의 붕괴"*가 이번엔 **펌웨어에서** 일어났다.

동시에 이건 [[2026-07-25-claude-opus-5-release]]의 사이버 정책과 맞물린다 — *"소스코드 취약점 탐지 허용 / 익스플로잇 생성 차단"*, *"분류기 오탐 85% 감소"*. 이 사건의 저자가 한 일(펌웨어 복호화 + 시크릿 탐지 + 책임 있는 공개)은 **정확히 허용되어야 하는 쪽**이다. 어제 Claude가 거부했던 그 종류의 요청이 정당한 방어 연구였다는 걸 생각하면, 오탐 감소는 **정책 문서가 아니라 이런 사례에서 검증된다.**

### 핵심 전이 4 — 정직한 급소: 노출된 시크릿은 **지운다고 회수되지 않는다**

12시간 폐기는 훌륭하지만, 그건 *앞으로의 사용*을 막을 뿐이다. **이미 출하된 펌웨어 500개 안의 토큰 문자열은 영원히 거기 있고**, 폐기 전에 누가 복사했는지는 알 수 없다. 그래서 사후 질문은 *"토큰을 폐기했는가"*가 아니라 **"그 토큰으로 무엇이 일어났는지 감사했는가"**다 — 저장소 접근 로그, 이상 클론, 커밋 이력.

이건 내 규칙의 *"위반 발견 시 즉시 회전 안내 — 이미 노출된 시크릿은 코드에서 지우는 것만으로는 회수되지 않는다"*와 같은데, **한 항목이 빠져 있었다**: 회전과 함께 **노출 기간의 사용 감사**. 이번 사건을 계기로 그 조항을 보강할 만하다.

## 호스피탈리티 / CRS 적용 포인트

온다는 카메라 펌웨어를 만들지 않지만, **클라이언트 번들과 CI 환경변수는 똑같이 쓴다.** 오히려 사업자용 프론트엔드(예약·정산 화면)와 파트너 연동이 있어 **번들이 곧 공개 자산**인 구조다.

- **`dist/`에 시크릿 스캐너를 붙인다.** 소스가 아니라 **빌드 산출물**에 gitleaks/trufflehog. 이번 사건은 소스 스캔으로는 절대 안 잡혔다.
- **Vite/Next 빌드 설정 감사.** `define`으로 `process.env`를 통째 주입하는 패턴, `NEXT_PUBLIC_`/`VITE_` 접두사 오남용(민감값에 붙여 놓기)을 grep으로 금지. **CI required check으로 인코딩.**
- **CI 환경변수 목록 자체를 자산으로 취급.** 이번 사건에서 유출된 건 토큰만이 아니라 **내부 인프라 지도**(NFS 마스터, OTEL/Elastic 엔드포인트, 내부 IP)였다. 우리 CI에도 온프레미스 k8s 주소·RDS 리더 엔드포인트 같은 값이 있다 — **번들에 절대 닿지 않는 경로**로 분리.
- **토큰 인벤토리 + 최소 권한 + 회전 일자.** dry-run 게이트의 "최소 권한 토큰" 조항을 **실제 표로** 만든다(토큰 / 스코프 / 최종 회전일 / 폭발 반경).
- **파트너·사업자에게 나가는 산출물은 "공개된 것"으로 간주.** 펌웨어든 JS 번들이든 SDK든, **고객 손에 들어가는 순간 리버싱 비용은 0**이다(전이 3).
