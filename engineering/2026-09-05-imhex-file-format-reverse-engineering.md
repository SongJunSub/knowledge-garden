# ImHex로 미지의 파일 형식 리버스 엔지니어링하기 (WerWolv)

> 출처: [Reverse Engineering Unknown File Formats with ImHex](https://werwolv.net/posts/file_format_reverse_engineering/) (WerWolv, werwolv.net) · 정리일 2026-09-05
> **출처 한계**: `werwolv.net`·`news.hada.io`·`news.ycombinator.com` 모두 이 세션의 네트워크 egress 정책상 차단돼 원문·hada/HN 댓글을 한 글자도 직접 읽지 못했다. 아래 내용은 Slack `#개발-뉴스-dev-news` 발췌(말줄임표로 잘려 있어 불완전할 수 있음)와, WebSearch로 이 원문 URL·저자(ImHex 제작자 WerWolv)·소재(게임 FEZ의 세이브 파일, `EasyStorage.dll`의 `PCSaveDevice` 클래스와 `Save` 함수 서술)를 교차 확인해 재구성한 것이다. 인용부호를 쓰지 않고 문단으로만 서술한 이유가 이것 — 원문 문장을 그대로 옮겼다고 확신할 수 없다.

## 한 줄 요약
**ImHex 제작자 WerWolv가 게임 FEZ의 독자적인 바이너리 세이브 파일을 예제로, 매직 바이트도 공개 명세도 없는 파일 형식을 리버스 엔지니어링하는 전 과정을 보여준다. 핵심은 "바이트만 노려봐서는 답이 안 나온다"는 것 — 대신 그 파일을 실제로 읽고 쓰는 코드(이 경우 C# 어셈블리 디컴파일)를 먼저 찾아 직렬화 순서·자료형을 역추적하고, 그렇게 복원한 구조를 ImHex Pattern Language로 한 줄씩 옮겨 실제 바이트와 맞춰보는 반복 검증이 방법론의 전부다.**

## 핵심 포인트
- ***"매직 바이트도 형식 명세도 없는 파일은 바이트만 들여다봐서는 의미를 알 수 없다"*** — 표준 포맷(PNG, ZIP 등)은 헤더 시그니처나 공개 스펙이 있어 역추적이 쉽지만, FEZ 세이브 파일처럼 게임이 자체 직렬화 로직으로 찍어낸 파일은 그런 단서가 전혀 없다.
- **출발점은 바이트가 아니라 코드** — 해당 파일을 읽고 쓰는 게임의 C# 어셈블리(`EasyStorage.dll` 계열)를 디컴파일해 `PCSaveDevice` 클래스와 `Save` 함수, 그 안의 `BinaryWriter` 호출 순서를 추적함으로써 "어떤 값이 몇 바이트로, 어떤 순서로 직렬화되는지"를 먼저 코드 레벨에서 확정한다.
- **구조를 ImHex Pattern Language로 하나씩 옮기고 실제 바이트와 대조** — 코드에서 확인한 필드를 패턴 언어(C 유사 구문의 구조체·배열·enum 정의)로 선언하면 ImHex가 그 구조를 raw 바이트 위에 오버레이해서 보여준다. 이 대조 작업을 반복하며 가설을 검증·수정한다.
- **다양한 자료형·구조 패턴을 실전에서 확인** — 시간·버전 값, 불리언, 문자열(길이 접두 문자열 포함), 목록과 중첩 객체, 그리고 값을 정수 그대로 두지 않고 **enum으로 선언해 이름을 남기는** 방식까지, 실제 세이브 파일에 나타나는 다양한 인코딩 패턴을 하나씩 보여준다.
- **선택적(optional) 객체·고정 크기 필드 같은 까다로운 패턴도 다룸** — 항상 존재하지 않는 객체, 고정 길이 블록처럼 단순 순차 파싱만으로는 안 풀리는 경우를 패턴 언어의 조건부·배열 문법으로 표현하는 예시가 포함된다.

## 내 생각 · 적용점

### 핵심 전이 1 — [[2026-08-25-reverse-engineering-my-peripherals-ownership]]와 순서가 정반대다: "코드를 먼저 읽어라"가 이 글의 핵심인데, schlarp.com 사례는 "코드가 아예 없거나(펌웨어 블랍) 접근 불가능"한 상황이었다

schlarp.com 노트에서 확인한 건 벤더 펌웨어·업데이트 도구를 LLM(Claude Opus 5)에 맡겨 소스 없이 바이너리만으로 프로토콜을 복원하는 접근이었다. 이 글은 반대로 **소스(디컴파일 가능한 C# 어셈블리)가 존재하는 유리한 상황**을 전제로, "바이트를 추측하지 말고 그 바이트를 만든 코드부터 봐라"는 훨씬 근본적인 원칙을 제시한다. 두 글을 겹치면 리버스 엔지니어링 난이도의 스펙트럼이 보인다 — ①코드에 접근 가능(이 글, 가장 쉬움) → ②코드는 없지만 벤더 도구·펌웨어 바이너리는 있음(schl라프 사례, LLM 에이전트가 그 공백을 메움) → ③아무 단서 없이 순수 바이트만 있음(가장 어려움). 실무에서 "레거시 바이너리 포맷을 분석해야 한다"는 요청이 오면 이 스펙트럼에서 지금 위치가 어디인지부터 판단하는 게 방법론 선택의 첫 단계다.

### 핵심 전이 2 — enum으로 정수를 선언해 이름을 남기는 습관은 코드 리뷰에서도 같은 원칙이다

패턴 언어에서 정수 필드를 그냥 `u8`로 두지 않고 enum으로 선언해 "이 값이 무슨 의미인지"를 구조 정의 자체에 남기는 방식은, 매직 넘버를 상수·enum으로 승격시켜 이름을 붙이라는 일반적인 코드 리뷰 원칙과 정확히 같은 동기다 — 여기서는 "내가 나중에 다시 볼 나 자신"이 독자이고, 그 독자를 위해 파싱 결과에 의미를 새겨 넣는 것.

## 호스피탈리티 / CRS 적용 포인트
직접 적용은 멀다 — 온다는 게임 세이브 파일이나 미지의 바이너리 포맷을 다루지 않는다. 다만 원칙 수준에서는 옮길 게 있다: **레거시 PMS·채널 연동 벤더 중 문서가 부실하거나 비공개 바이너리/전문 포맷(EDI, 구형 XML 변종, 벤더 자체 배치 파일 등)을 쓰는 곳을 분석할 때, "포맷 자체를 추측"하기보다 "그 포맷을 생성/파싱하는 벤더 쪽 코드나 SDK가 있는지부터 확인"하는 순서가 이 글의 핵심 교훈과 같은 축이다.** [[2026-08-25-reverse-engineering-my-peripherals-ownership]]의 CRS 적용점이 짚은 "레거시 벤더 프로토콜을 이해하는 데 원칙 수준에서 참고 가능, 단 벤더 인증 우회 목적이 아닌 정당한 통합 문서화 용도로 한정"이라는 경계도 그대로 유효하다.
