# git-bug, 이슈를 Git 저장소 안에 그대로 저장하는 분산형 오프라인 우선 버그 추적기

> 출처: [git-bug](https://github.com/git-bug/git-bug) (GitHub) · GeekNews 경유(https://news.hada.io/topic?id=34272) · 정리일 2026-09-26
>
> **출처 한계**: `news.hada.io`가 egress 차단돼 GeekNews 한글 발췌·hada 댓글은 확인하지 못했다. `github.com`은 접속 가능해 README·릴리스 페이지를 1차 자료로 직접 읽었다. 이 프로젝트는 2018년경부터 존재해 온 잘 알려진 오픈소스 도구이고, 최신 태그 릴리스(v0.11.0)는 **2023년 9월 22일**로 확인된다 — 즉 이번 GeekNews·(추정)HN 노출은 새 버전 출시에 따른 것이 아니라, **오래된 프로젝트가 특별한 계기 없이 다시 화제가 된 경우**로 보인다. 정확한 재부상 계기(Show HN 재제출인지, 다른 콘텐츠에서 인용됐는지)는 확정하지 못했다.

## 한 줄 요약

**git-bug는 이슈·댓글·레이블을 별도 서버가 아니라 git 저장소 자체(git 오브젝트)에 저장해, 기존에 쓰던 git 원격 저장소만으로 푸시·풀·오프라인 작업이 가능한 분산형 버그 추적기다 — CLI·터미널 UI·웹 UI·GraphQL API를 제공하고 GitHub·GitLab·Jira와 양방향 브릿지를 지원하지만, 태그된 최신 릴리스는 2023년 것으로 활발한 신규 개발의 증거는 이번 조사에서 확인하지 못했다.**

## 핵심 포인트

- **핵심 설계 — 완전히 git에 통합됨** — 이슈·댓글을 별도 파일이 아니라 ***git의 내부 저장 방식을 그대로 사용***해, 프로젝트에 추가 파일이 생기지 않는다. `git bug push`/`git bug pull`로 기존 git 원격을 그대로 버그 트래커의 동기화 채널로 쓴다.
- **오프라인 우선 — 서버 종속을 없앤다** — 원래 목적 자체가 ***"버그를 다루기 위해 어딘가의 웹 서비스에 의존하지 않는 것"*** — 인터넷 없이도 이슈를 읽고 쓸 수 있고, 평소 쓰던 서비스가 다운되더라도 이미 완전한 백업을 로컬에 갖고 있는 구조다.
- **여러 인터페이스 — CLI·TUI·웹 UI·GraphQL** — `git bug termui`로 터미널에서 이슈를 탐색·편집할 수 있고, 리스트/열람이 밀리초 단위로 빠르다고 소개된다. v0.11.0에서는 코드 브라우저(파일 트리·구문 강조·마크다운 렌더링·커밋 히스토리)와 폴링 없는 GraphQL 구독이 추가됐다.
- **브릿지 — GitHub·GitLab·Jira·Launchpad 연동** — 기존 이슈 트래커와 `git bug bridge pull`/`push`로 동기화해, 개인 로컬 리모트처럼 병행 사용할 수 있다.
- **활발해 보이지만 정체된 릴리스 — 2,700+ 커밋, 그러나 태그 릴리스는 2023년** — GitHub 저장소는 trunk 브랜치 기준 2,700개 이상의 커밋, 130개의 미결 이슈, 23개의 PR이 열려 있어 표면적으로는 활발해 보이지만, ***공식 태그 릴리스(v0.11.0)는 2023-09-22가 마지막***으로 확인된다 — "화제성"과 "최신 배포 상태" 사이에 간극이 있다.

## 인상 깊은 문장

> "Someone should not have to rely on a web service somewhere just to deal with bugs." (프로젝트가 내세우는 설계 동기의 취지)

## 댓글

**GeekNews(hada) 댓글 수 확인 불가** — egress 차단. 프랑스어 미러(`fr.news.hada.io/topic?id=34272`) 검색 스니펫에서 "SSH 인증 관련 어려움과 우회법을 공유하는 댓글이 있다"는 언급을 확인했으나, 정확한 댓글 수·전체 논조는 원문 미확인. **HN**: 이 프로젝트를 다룬 과거 HN 스레드는 여러 건 존재(2018년 Show HN `item?id=17782121`, 2022년 `item?id=33730417` 등)하지만, **이번 2026-09 재부상에 대응하는 정확한 HN 스레드 ID·점수는 특정하지 못했다** — WebSearch 결과가 서로 다른 수치(96점·22댓글 / 324점·107댓글)를 함께 반환해 신뢰도 있는 단일 값으로 확정할 수 없었다는 걸 정직하게 남긴다. **정직성 노트**: git-bug는 잘 알려진 오래된 프로젝트라 "신선한 뉴스"로 다루기보다 "왜 지금 재조명됐는지" 자체가 불확실하다는 점, 그리고 태그 릴리스가 3년 가까이 없다는 점에서 유지보수 활력에 대한 판단은 유보한다.

## 내 생각 · 적용점

### 핵심 전이 1 — "GitHub의 진짜 자산은 소셜 계층"이라는 진단 앞에서 git-bug는 정반대 극의 해법이다

[[2026-08-04-github-has-alternatives-no-replacement]]는 GitHub의 진짜 해자가 저장소 호스팅이 아니라 ***"공유된 정체성·습관·발견 경로의 풀"***이라고 진단했고, Radicle 같은 P2P 대안을 두고 ***"버그를 신고하려고 포지 소프트웨어를 설치해야 하는 건 안 된다"***고 비판했다. git-bug는 정확히 그 비판이 겨냥하는 지점에 서 있다 — 기술적으로는 완전히 분산돼 있고 벤더 종속을 없앴지만, **협업자가 이슈를 보거나 댓글을 달려면 git-bug CLI/UI를 설치해야 한다**는 점에서 "콜드스타트 문제"를 그대로 안고 있다. 기술적 탈중앙화가 사회적 진입장벽 문제를 자동으로 풀어주지 않는다는 걸 보여주는 실물 사례다.

### 핵심 전이 2 — "서버 권위형" 오프라인 우선과 "완전 분산형" 오프라인 우선의 대조

[[2026-08-29-syncular-offline-first-sqlite-sync-engine]]가 다룬 syncular는 "서버가 진실의 원천이지만 클라이언트는 진짜 DB를 갖는다"는 **서버 권위형(server-authoritative)** 오프라인 우선 구조였다. git-bug는 그 반대 극단이다 — **중앙 서버 자체가 없고**, git이라는 분산 버전 관리 시스템의 push/pull 모델에 완전히 올라탄다. 같은 "오프라인 우선"이라는 목표 아래, 신뢰의 중심을 서버에 둘지(syncular) 아예 없앨지(git-bug)가 정반대 아키텍처 선택으로 갈리는 좋은 대조 사례다 — 각각 "충돌 해결을 누가 책임지는가"라는 질문에 다른 답을 내놓는다(syncular는 서버가 검증, git-bug는 git의 merge/rebase 관례에 위임).

## 호스피탈리티 / CRS 적용 포인트

**직접 적용은 멀다.** 온다의 이슈 트래킹은 이미 Linear 등 중앙화된 SaaS에 의존하고 있고, 팀 규모·협업 방식상 git-bug 같은 완전 분산형 트래커로 전환할 유인이 크지 않다. 다만 원칙 하나는 참고할 만하다 — ***"핵심 데이터를 외부 서비스에만 의존하면, 그 서비스가 멈추는 순간 완전히 발이 묶인다"***는 vendor lock-in 위험 인식은 CRS/PMS 연동 데이터(예약·재고 상태)를 설계할 때도 마찬가지로 적용된다. 다만 "완전 분산화"가 아니라 "핵심 데이터의 로컬 백업·오프라인 조회 경로를 확보한다"는 훨씬 약한 형태로만 전이 가능하다.
