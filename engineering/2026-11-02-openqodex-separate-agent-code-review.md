# OpenQodex, 코딩 에이전트의 변경을 별도 에이전트가 검증하는 코드 리뷰 도구(GeekNews)

> 출처: [OpenQodex - 코딩 에이전트의 변경을 별도 에이전트가 검증하는 코드 리뷰 도구](https://news.hada.io/topic?id=36426) (GeekNews) · 정리일 2026-11-02
>
> **출처 한계**: news.hada.io 접근 차단으로 원문·hada 댓글을 직접 열람하지 못했다. WebSearch로 프로젝트 소개 페이지(everydev.ai, glama.ai 등)와 교차확인했으나, GitHub README 원문은 직접 열람하지 못했고 독립적인 품질 평가·벤치마크도 찾지 못했다.

## 한 줄 요약

**OpenQodex는 Claude Code·Codex의 기존 로그인 계정을 그대로 활용해, 코드를 쓴 에이전트와 다른 별도의 리뷰어 프로세스를 띄워 푸시 전 변경을 검증하는 오픈소스 도구로, "AI가 쓴 코드를 같은 AI가 검토한다"는 구조적 약점을 프로세스 분리로 해결하려 한다.**

## 핵심 포인트

- **쓴 주체와 검토 주체를 분리** — ***"기존 로그인 계정을 활용해 코딩 에이전트의 변경을 별도의 Claude Code 또는 Codex 프로세스로 리뷰"***한다. WebSearch로 확인한 바, OpenQodex는 사용자의 기존 Claude Code/Codex 플랜을 그대로 쓰면서 ***"기본적으로 코드를 쓴 에이전트가 그 코드를 검토하지 않도록"*** 별도 리뷰어 프로세스를 시작한다.
- **검사 범위가 유연하다** — ***"미푸시 커밋과 미커밋 변경 전체를 기본 검사하며, 특정 브랜치나 PR, 저장소 전체 리뷰도 지원"***한다. 일상적인 푸시 전 점검뿐 아니라 전체 저장소 감사까지 같은 도구로 처리할 수 있다.
- **22개 내장 스캐너 + 확장성** — ***"22개 내장 스캐너로 비밀키, 보안 취약점, 의존성, 린트, CI와 인프라 설정, SQL 등을 검사하며 외부 스캐너 추가도 가능"***하다. 먼저 빠른 정적 스캐너를 변경 라인에 돌린 뒤, 그 결과를 별도 AI 리뷰어가 다시 검토하는 2단계 구조로 보인다.
- **발견과 검증을 분리** — ***"문제 발견과 검증 세션을 분리해 변경 코드와 관련 호출부를 살피고, 정적 분석 결과까지 확인하거나 반박한다"***. 즉 정적 분석기가 낸 결과를 AI 리뷰어가 맹신하지 않고 실제 코드 맥락(호출부 등)을 살펴 반박할 수 있는 구조다. ***"인용한 코드의 실재 여부와 변경 구간의 리뷰 전달 여부를…"***에서 발췌가 끊긴다.
- **출력과 게이트** — WebSearch로 확인한 바, 결과는 터미널·`report.md`·`report.json`·`report.sarif` 형식으로 출력되고, 리뷰가 없으면 `git push`를 막는 훅(push gate)을 설정할 수 있다. Apache 2.0 라이선스이며 리뷰 비용은 사용자 본인의 Claude Code/Codex 플랜을 소모한다. Qodex라는 회사가 이 오픈소스 도구와 별도로 호스팅형 유료 제품도 운영한다.

## 인상 깊은 문장

> "By default, the agent that wrote the code does not review it." — OpenQodex 소개 페이지(WebSearch 교차확인, everydev.ai)

## 댓글

hada 댓글 수·HN/Lobsters 큐레이션 여부는 접근 차단으로 확인하지 못했다. WebSearch 결과 이 프로젝트는 ***"새 프로젝트로 1.0을 향해 가는 중"***이라고 스스로 밝히고 있어, 아직 성숙 단계는 아니다. 독립적인 탐지 품질 리뷰나 벤치마크는 찾지 못했다 — 소개 페이지와 프로젝트 자체 서술에 의존한 정보라는 한계가 있다.

## 내 생각 · 적용점

**핵심 전이 — "같은 에이전트가 자기 코드를 리뷰하지 않는다"는 구조는 [[2026-08-13-human-ai-synergy-agentic-code-review]]가 밝힌 실증 데이터의 직접적 응답이다.** 그 연구는 "AI 제안 중 채택되지 않은 것의 절반 이상이 틀렸다"는 걸 보였는데, 그중에서도 가장 위험한 경우는 코드를 쓴 바로 그 에이전트가 자기 작업을 스스로 검토하는 상황이다. OpenQodex는 프로세스를 분리해 이 문제를 구조적으로 막으려 한다는 점에서, [[2026-09-20-px0-lightweight-browser-code-review]]가 "저작과 검토를 분리"한 것과 같은 철학을 코드 리뷰 자동화 쪽으로 가져온 것으로 읽힌다. 다만 저작과 검토 모두 AI(Claude Code/Codex)라는 점에서, [[2026-09-23-samsung-code-review-war]]가 "승인은 하되 댓글은 남기지 않는다"는 식으로 저위험 영역에만 자동 승인을 제한한 것과 비교하면, OpenQodex의 적용 범위(전체 리뷰까지)가 더 야심 찬 쪽이다.

## 호스피탈리티 / CRS 적용 포인트

**직접 적용 가능성 있음.** 온다 개발팀이 Claude Code를 코딩에 적극 활용한다면, 같은 에이전트가 자기 작업을 리뷰하지 않도록 OpenQodex 같은 별도 리뷰어 프로세스를 push gate로 걸어두는 것은 실무적으로 바로 시험해볼 만하다. 다만 프로젝트가 아직 1.0 이전 단계라는 점을 감안해, 비밀키·보안 취약점 등 고위험 스캐너 결과는 그대로 신뢰하지 말고 도입 초기엔 사람이 교차 검증하는 과도기를 두는 것이 안전하다.
