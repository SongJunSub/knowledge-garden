# GitHub의 대안은 있지만 대체재는 없다 — 저장소를 잘 호스팅하는 것과 사회를 만드는 것은 다른 문제다

> 출처: [GitHub has alternatives, but no replacement](https://lalitm.com/post/github-alternatives/) (lalitm.com, Lalit Maganti · GeekNews GN⁺ 요약 + HN 큐레이션) · 정리일 2026-08-04

## 한 줄 요약

**GitHub가 진짜로 제공하는 건 저장소 호스팅이 아니라 ***"공유된 정체성·습관·발견 경로의 풀"***이라는 게 이 글의 핵심 진단이다 — ***"GitHub gives projects a shared pool of identities, habits and paths to discovery."*** **공유 정체성**(대부분 개발자가 이미 계정을 가짐), **협업 관습**(이슈·PR이라는 표준 워크플로우), **발견 경로**(팔로우·스타로 우연히 새 프로젝트를 만남) — 이 세 요소를 비슷한 규모로 재현한 대안이 거의 없다. **GitLab**은 기능은 갖췄지만 ***"GitHub보다도 더 기업 냄새가 난다."*** **SourceHut**은 투명하고 가치 지향적이지만 이메일 중심 워크플로우가 낯설다. **Forgejo**는 연합 기능이 흥미롭지만 여전히 실험 단계다. **Radicle**은 P2P로 기술적으로 흥미롭지만, ***"버그를 발견한 사람이 그걸 신고하려고 포지 소프트웨어를 설치해야 하는 건 아니다"***라는 문제가 있다. **Tangled**는 발견 기능이 인상적이지만 알파 단계다. **Codeberg**는 최근 **생성형 AI 코드 대부분으로 이뤄진 프로젝트를 금지**하기로 결정해 논쟁이 일었는데, 저자는 이를 비판하지 않는다 — ***"Codeberg는 처음부터 중립 인프라가 아니라 미션 중심 대안으로 자리매김해왔다"***는 것. 이 논쟁 자체가 **"GitHub 대체재 부재"라는 더 큰 공백**을 드러낸다. 극적인 사례는 **Ghostty**다 — 저자가 이 글을 쓰던 바로 그날, ***"GitHub Actions 장애로 약 2시간 동안 PR 리뷰를 전혀 못 했다"*** — 이탈을 결정했지만, 정작 ***"Git이 아니라 우리가 의존하는 그 주변 인프라(이슈·PR·Actions)의 문제"***이고, 명확한 기본 대안이 없어 여러 곳과 협상하며 "쇼핑" 중이다. 저자가 제안하는 방향은 **"의도적으로 평범한 회사"**(bunny.net 스타일) — 벤처 야심 없이 소셜 계층 자체를 핵심 제품으로 설계하고, 수익이 지탱하는 속도로만 성장하는 모델. 결론: ***"GitHub를 대체할 무엇이든 여전히 공유된 소셜 계층이 필요하다."***

## 핵심 포인트

- **GitHub의 진짜 자산 3가지** — ***"공유된 정체성·습관·발견 경로의 풀."*** 저장소 호스팅 자체가 아니라 이 사회적 인프라가 핵심.
- **GitLab** — 기술적으로 유능하나 ***"GitHub보다도 더 기업 냄새."*** 발견 기능이 약함.
- **SourceHut** — 투명·가치지향, Linux 커널급 프로젝트에서 검증된 이메일 워크플로우지만 GitHub 사용자에겐 진입장벽.
- **Forgejo** — 자체 호스팅 인스턴스 연합 가능성 제시하나 오래 실험 단계.
- **Radicle** — P2P 저장소 복제·로컬 이슈/패치 저장은 흥미롭지만, ***"버그 신고하려고 포지 소프트웨어를 설치해야 하는 건 안 된다."***
- **Tangled** — 코드 중심 소셜 경험·자동 프로젝트 추천(구 GitHub 느낌)이 강점이나 알파 단계.
- **Codeberg의 AI 코드 금지 정책 논쟁** — 많은 개발자가 "보편적 GitHub 대체재"로 기대했으나 특정 기준 적용에 실망. 저자: ***"처음부터 중립 인프라가 아니라 미션 중심 대안으로 자리매김해왔다."*** 논쟁 자체가 공백을 드러냄.
- **Ghostty의 GitHub 이탈** — ***"이 글을 쓰던 그날, GitHub Actions 장애로 약 2시간 PR 리뷰 불가."*** ***"Git이 아니라, 우리가 의존하는 그 주변 인프라의 문제."*** 목적지 미정, 여러 곳과 협상 중.
- **콜드스타트 문제** — ***"더 나은 저장소 호스팅만으로는 이 문제를 풀 수 없다."*** Bitbucket 반례 — 상용 포지였지만 GitHub급 오픈소스 커뮤니티 형성 실패.
- **GitHub 자체 문제** — ***"GitHub의 기본 경험이 꾸준히 나빠지고 있다."*** ***"에이전트가 코드를 더 많이 써도, 그걸 리뷰할 인터페이스가 이미 허덕이면 도움이 안 된다"*** — Copilot에 집중하며 핵심 기능 방치.
- **해법 제안 — "의도적으로 평범한 회사"** — bunny.net 스타일. 벤처 야심 없이, 개발자·소규모 조직에 직접 요금 부과, 수익이 지탱하는 속도로 성장, 소셜 계층을 핵심 제품으로.
- **결론** — ***"GitHub를 대체할 무엇이든 여전히 공유된 소셜 계층이 필요하다."***

## 댓글

**hada 댓글 1개(GN⁺의 HN 의견 정리), 6개 논점.**
- **네트워크 효과** — "소셜 코딩의 네트워크 효과"가 GitHub 이탈의 최대 장벽이라는 데 공감, 연합형 구조 필요성 제기.
- **협업 도구 vs 소셜 플랫폼의 이원성** — GitHub는 사실 "팀용 코드 저장소"와 "오픈소스 협업"이라는 **서로 다른 두 제품**이 하나로 묶인 것이고, **팀 도구로서는 형편없다**는 냉정한 평가.
- **SourceHut의 장점 재평가** — 이메일 기반 PR 방식을 실제로 선호하는 사용자층이 있으며, 오히려 **"영리 기업이 강제하는 계약 관계"가 문제**라는 지적.
- **CI/CD 의존성의 과소평가** — **무료 Windows·Mac 실행기(러너)**의 가치가 저평가됐다는 지적, Microsoft의 **연간 약 1억 달러 투자**가 실제로 이탈을 막는 핵심 요인이라는 관찰.
- **Radicle의 연합 모델 긍정 평가** — 이슈·PR을 저장소 자체에 포함시키는 Git 네이티브 방식에 대한 호평.
- **대안들의 공통 미성숙** — LFS 미지원, 성능 문제 등 각 플랫폼이 저마다 다른 제약을 갖고 있다는 총평.

**읽을 때 감안**
- ①**저자는 개인 기술 블로거**이고, 특정 대안 플랫폼에 이해관계가 있다는 신호는 없다 — 이번 시즌 반복해 온 VC 콘텐츠들과 달리 비교적 중립적인 관찰로 읽을 수 있다.
- ②**"의도적으로 평범한 회사"라는 해법 자체를 저자도 확신하지 못한다** — 원문에서 이게 "실질적 사업이 될 수 있을지 불명확"하다고 인정한다. 처방보다 진단이 훨씬 강한 글이라는 점을 감안해야 한다.
- ③**CI/CD 무료 러너의 가치를 저평가했다는 댓글 지적이 원문 분석에 빠진 중요한 축**이다 — GitHub 이탈 장벽이 "사회적 네트워크 효과"만이 아니라 **"무료 인프라 보조금"**이라는 경제적 요인도 크다는 걸 원문이 충분히 다루지 않았을 가능성.

## 내 생각 · 적용점

### 핵심 전이 1 — "또 다른 파편"이라는 지적이 터미널 도구 생태계에 이어 Git 포지 생태계에서도 반복된다

[[2026-08-02-superlogical-multiplexer]]에서 다룬 HN의 암묵적 지적 — Superlogical이 pi-web·herdr·firstmate·ouijit·Orca 같은 기존 유사 도구에 **"또 하나의 파편을 더하는 것"**일 수 있다는 우려 — 가 이 글에서는 GitLab·SourceHut·Forgejo·Radicle·Tangled로 그대로 반복된다. **저장소 호스팅이라는 통제 지점을 노리는 시도가 이미 다섯 개나 있지만, 아직 명확한 승자가 없는 초기 경쟁 단계**라는 점도 똑같다. 이 글이 짚은 **콜드스타트 문제**("더 나은 저장소 호스팅만으로는 풀 수 없다")가 바로 왜 이런 파편화가 오래 지속되는지에 대한 가장 정확한 설명이다 — 사회적 인프라는 기능 경쟁으로는 뒤집히지 않는다.

### 핵심 전이 2 — "에이전트가 코드를 더 써도 리뷰 인터페이스가 허덕이면 소용없다"는 Stacked PR 노트의 병목 원칙과 정확히 같다

[[2026-08-02-github-stacked-pull-requests]]에서 정리한 핵심 — HN이 지적한 ***"결국 작은 변경들을 선형으로 리뷰해야 한다"***, 즉 **나누기(diff 분할)가 병목(리뷰·병합)을 자동으로 없애지 않는다** — 를 이 글의 문장 ***"An agent writing more code doesn't help when the interface for reviewing it is already struggling"***가 정확히 재확인한다. **GitHub이 Stacked PR·Copilot 같은 생산 측 기능은 늘리면서, 정작 그 생산물을 검토·신뢰하는 인프라(Actions 안정성)는 방치**하고 있다는 이 글의 비판은, 같은 회사가 스스로 만든 병목 회피 도구(Stacked PR)의 한계를 실증하는 셈이다.

### 핵심 전이 3 — Codeberg의 AI 코드 금지 정책은 GCC AI 정책과 같은 종류의 경계 설정이지만, 기준이 다르다

[[2026-08-02-gcc-ai-policy]]에서 다룬 GCC의 접근 — ***"LLM 생성·파생된 법적으로 중요한 기여는 거부, 기준은 GNU 지침의 약 15줄"*** — 은 **저작권이라는 객관적 기준**으로 경계를 그었다. Codeberg의 정책은 그와 달리 **"미션 중심 정체성"**(중립 인프라가 아니라는 자기규정)에 근거한 경계다 — 저작권 문제가 아니라 **커뮤니티가 지향하는 가치(인간이 쓴 코드)**를 지키려는 결정이다. 같은 "AI 생성 코드를 어떻게 다룰 것인가"라는 질문에 **하나는 법적 기준으로, 하나는 정체성 기준으로 답한다**는 대비가 흥미롭다 — 어느 쪽이 지속가능한 정책인지는 두고 볼 문제다.

### 핵심 전이 4 — 정직한 급소: "여전히 소셜 계층이 필요하다"는 결론은 진단이지 처방이 아니다

이 글의 결론 문장 — ***"Whatever replaces GitHub still needs a shared social layer"*** — 은 사실 **이 글이 처음부터 말하려던 것을 다시 말한 것**뿐이다. "사회적 계층이 필요하다"는 진단은 쉽지만, **그걸 어떻게 만드는가는 콜드스타트 문제 때문에 정확히 어렵다**는 게 이 글 자신의 논지다. 저자 스스로도 자신의 해법("의도적으로 평범한 회사")이 **"실질적 사업이 될 수 있을지 불명확"**하다고 인정한다. 이건 이 글이 나쁘다는 뜻이 아니다 — 오히려 **진단이 정확하고 처방이 겸손한 좋은 글의 전형**이다. 다만 "결론"이라는 문단 형식이 마치 답을 준 것처럼 읽히기 쉬우니, **이 글의 진짜 기여는 해법이 아니라 문제의 정확한 명명(사회적 인프라 vs 기술 인프라 구분)에 있다**는 걸 분명히 해야 한다.

## 호스피탈리티 / CRS 적용 포인트

- **내부 개발자 도구·플랫폼 선택 시 "사회적 인프라"와 "기술 기능"을 분리해서 평가(전이 1·4).** 새 도구를 도입할 때 기능 비교표만 볼 게 아니라, 팀 전체가 이미 공유하고 있는 습관·발견 경로를 얼마나 유지·재현할 수 있는지 함께 평가.
- **CI/CD 무료 인프라 같은 "숨은 보조금" 요소를 마이그레이션 비용 계산에 포함(댓글 4).** GitHub Actions 같은 무료 러너의 실제 대체 비용을 도구 전환 검토 시 명시적으로 산정.
- **새 생산성 기능(코드 생성 자동화 등) 도입 전 그 산출물을 검토할 인프라가 이미 감당 가능한지 먼저 확인(전이 2).** 생산 측을 가속하기 전에 검토·신뢰 인프라의 여유를 먼저 점검.
