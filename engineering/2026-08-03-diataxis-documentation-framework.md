# Diátaxis — 기술 문서를 위한 체계적 접근법

> 출처: [Diátaxis](https://diataxis.fr/) (diataxis.fr · GeekNews GN⁺ 요약 + HN 큐레이션) · 정리일 2026-08-03

## 한 줄 요약

**Diátaxis는 문서 **사용자의 요구**를 기준으로 기술 문서의 내용·형식·구조를 설계하는 체계적 접근법이다. 핵심은 사용자 요구를 **튜토리얼·하우투 가이드·기술 참조·설명** 네 가지로 구분하고, 각 유형의 역할과 관계에 따라 전체 문서 체계를 구성하는 것 — **"무엇을 쓸지"(콘텐츠)·"어떻게 쓸지"(문체)·"어디에 배치할지"(정보 구조)**를 한 틀 안에서 다룬다. **Divio 문서화 시스템**에서 기원했고, 가볍고 특정 구현 방식에 제약을 두지 않아 기존 문서에 **점진적으로 적용** 가능하다. **Vonage·Gatsby·Cloudflare**가 도입해 문서 품질·탐색성·정보 구조의 명확성이 개선됐다고 평가했다. HN 댓글은 실전 경험담(고객 인수인계 문서화, R/Python 언어별 적용)부터 날카로운 비판까지 폭넓다 — 가장 정직한 비판 하나: ***"이걸 읽고 나면 모든 문서가 결함투성이의 혼란스러운 구조로 보이기 시작하니 차라리 읽지 않는 편이 행복할 수도 있다."*** 그리고 실용적 약점도 짚힌다 — ***"튜토리얼과 참조 자료는 버전이 지정된 코드에서 자동 생성하지 않으면 시간이 지나며 실제 동작과 어긋난다."***

## 핵심 포인트

- **4분류 체계** — **튜토리얼**(학습 지향)·**하우투 가이드**(작업 지향)·**기술 참조**(정보 지향)·**설명**(이해 지향). 각 유형은 목적이 다르므로 **한 문서가 여러 유형을 겸하면 어느 쪽 독자에게도 잘 안 맞는다**는 게 핵심 진단.
- **다루는 세 층위** — **콘텐츠**(무엇을 쓸지)·**문체**(어떻게 쓸지)·**정보 구조**(어디에 배치할지)를 하나의 틀로 통합.
- **기원과 특성** — **Divio 문서화 시스템**에서 파생. 가볍고 특정 구현에 종속되지 않아 **기존 문서에 점진적 적용** 가능.
- **채택 사례** — **Vonage·Gatsby·Cloudflare**가 도입, 문서 품질·탐색성·정보 구조 개선을 보고. 수백 개 프로젝트가 도입.
- **가장 날카로운 비판** — ***"이걸 읽고 나면 모든 문서가 결함투성이의 혼란스러운 구조로 보이기 시작하니 차라리 읽지 않는 편이 행복할 수도 있음."*** / ***"문서 담당자가 자기 일자리를 정당화하는 도구처럼 느껴질 수 있다."***
- **유지보수의 실용적 한계** — ***"튜토리얼과 참조 자료는 버전이 지정된 코드에서 자동 생성하지 않으면 시간이 지나며 실제 동작과 어긋날 수 있다."*** 일정 기간 후 소유자가 최신 여부를 확인하게 하는 기능이 유용하다는 제안.
- **언어별 적용 사례** — **R**은 Diátaxis 세 범주가 패키지 구조와 잘 대응(튜토리얼=vignettes, 하우투=roxygen, 참조=TeX/Markdown). **Python**은 언어 기능 추가 시 PEP에 "How to Teach This" 절을 요구하는 관행이 이미 Diátaxis 정신과 맞닿아 있음.
- **LLM 활용** — ***"바이브 코딩 중 LLM에 'do diataxis'라고 지시해 제법 괜찮은 초안 문서를 얻기에 편리하다."*** 튜토리얼 작성 시 에이전트에 스크린샷·절차를 제공해 안내서로 정리하게 하는 방식도 효과적이라는 경험담.
- **자기 자신에 대한 태도** — ***"Diátaxis에는 인증, 교육 과정, 선언문, 'Diátaxis Master' 채용 공고가 없다는 점이 마음에 든다"*** — 다만 인기를 얻으면 이런 요소가 생길 가능성도 함께 제기됨.

## 내 생각 · 적용점

### 핵심 전이 1 — "규칙 대신 인터페이스"라는 이번 시즌의 원칙이 문서 설계에도 정확히 같은 형태로 나타난다

[[2026-07-25-context-engineering-rules-claude-5]]가 정리한 컨텍스트 엔지니어링 원칙 — ***"점진적 공개"***(필요한 순간에 필요한 정보만), ***"규칙 대신 인터페이스"***(예시를 늘리기보다 표현력 있는 인터페이스를 설계) — 는 Diátaxis의 4분류와 본질적으로 같은 문제의식이다. **한 문서가 튜토리얼·레퍼런스·설명을 모두 겸하려 하면**, CLAUDE.md 하나에 모든 규칙을 욱여넣는 것과 똑같이 **누구에게도 딱 맞지 않는 결과물**이 된다. 프롬프트 엔지니어링이 "언제 필요한 정보만 로드할까"를 고민하듯, 문서 설계도 "이 독자는 지금 배우러 왔나, 문제를 풀러 왔나, 사양을 찾으러 왔나"를 먼저 구분해야 한다는 것 — **AI 컨텍스트 설계와 인간 문서 설계가 같은 정보 구조 원칙을 공유**한다.

### 핵심 전이 2 — "do diataxis"라는 LLM 프롬프트는 어제 정리한 "표현력 있는 인터페이스"가 실제로 작동하는 사례다

[[2026-08-03-boris-cherny-unhobbling-claude-code]]에서 다룬 핵심 조언 — ***"과잉 지시하지 말고, 명확한 결과·제약·검증 수단을 줘라"*** — 를 "do diataxis"라는 한 단어가 정확히 실천한다. 이 프롬프트가 작동하는 이유는 Diátaxis라는 **이름 자체가 4분류·각 분류의 목적·상호 관계라는 압축된 구조**를 담고 있어서다 — 사용자가 "튜토리얼은 이렇게, 레퍼런스는 저렇게 써줘"라고 단계별로 지시할 필요 없이, **명명된 프레임워크 하나가 그 모든 지시를 대신한다.** 좋은 이름·좋은 프레임워크는 그 자체로 압축된 프롬프트라는 걸 보여주는 좋은 사례다.

### 핵심 전이 3 — "버전 코드에서 자동 생성 안 되면 문서가 부패한다"는 이 시즌의 "검증 자동화" 원칙이 갖는 구조적 한계를 보여준다

[[2026-08-01-bun-zig-to-rust-rewrite-with-ai]]가 보여준 원칙 — **"정답지(테스트 스위트)가 있는 작업만 AI 배율이 크게 풀린다"** — 를 문서에 적용하면 역설이 드러난다: **문서에는 보통 실행 가능한 "정답지"가 없다.** 코드는 컴파일·테스트로 검증되지만, 문서가 "정확한지"는 사람이 읽고 실제 동작과 비교해야만 알 수 있다. 댓글이 지적한 "버전 코드에서 자동 생성하지 않으면 어긋난다"는 건 정확히 이 구조적 한계에 대한 유일한 해법 — **문서를 코드에서 파생시켜 정답지를 코드 자체로 삼는 것**만이 부패를 막는다는 뜻이다. Diátaxis가 아무리 좋은 구조를 줘도, **자동 검증 파이프라인이 없으면 결국 침식한다.**

### 핵심 전이 4 — 정직한 급소: 체계 자체의 권위가 실제 유용성을 앞지를 위험

"문서 담당자가 자기 일자리를 정당화하는 도구처럼 느껴진다"는 HN 비판은, [[2026-08-02-superlogical-multiplexer]]에서 다룬 **"유명 창시자의 후광 효과를 경계하라"**는 교훈과 같은 형태다 — 다만 여기서는 인물이 아니라 **프레임워크 자체가 후광**이 되는 경우다. "우리는 Diátaxis를 도입했다"는 선언이 실제 문서 품질 개선보다 **조직 내부의 정당화 서사**로 소비될 위험이 있다는 것. 이 노트가 인용한 채택 사례(Vonage·Gatsby·Cloudflare)의 효과가 diataxis.fr 자체 소개에 근거한다는 점(위 읽을 때 감안 ①)과 겹쳐 보면, **프레임워크의 성공 서사를 프레임워크 공식 채널로만 확인하는 것의 위험**을 다시 한번 짚어야 한다.

## 호스피탈리티 / CRS 적용 포인트

- **CRS API 문서에 4분류를 시범 적용(전이 1).** 온다 CRS API 문서가 튜토리얼(온보딩)·하우투(특정 작업)·레퍼런스(엔드포인트 명세)·설명(설계 배경)을 뒤섞어 놓은 경우가 흔하다면, 신규 문서부터 4분류를 명시적으로 나눠 작성.
- **버전 코드 기반 자동 문서 생성을 레퍼런스 문서부터 우선 적용(전이 3).** API 레퍼런스처럼 정답지(코드 스펙)가 명확한 문서 유형부터 자동 생성 파이프라인을 도입하고, 튜토리얼·설명처럼 정답지가 없는 유형은 정기 검토 주기를 명문화.
- **"do diataxis" 같은 압축 프롬프트를 팀 내 문서 작성 관행에 시범 도입(전이 2).** LLM에게 문서 초안을 맡길 때, 단계별 지시 대신 명명된 프레임워크를 참조시키는 방식의 효율을 검증.
