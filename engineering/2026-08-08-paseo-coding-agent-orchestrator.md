# Paseo — 여러 코딩 에이전트를 데스크톱/모바일에서 관리하는 오케스트레이터

> 출처: [Paseo](https://github.com/getpaseo/paseo) (GitHub, getpaseo · GeekNews GN⁺ 요약 + 직접 댓글) · 정리일 2026-08-08

## 한 줄 요약

**Paseo는 여러 코딩 모델(**Claude Code·Codex·Copilot** 등)을 **단일 인터페이스**에서 관리하는 셀프호스팅 오케스트레이터다. **로컬 daemon**이 에이전트를 관리하고 **여러 클라이언트**(iOS·Android·데스크톱·웹·CLI)가 거기 접속하는 구조 — **음성 제어**와 **크로스 플랫폼**을 지원하며, **프라이버시 중심 설계**(텔레메트리·강제 로그인 없음)가 핵심 차별점이다. **CLI로 모든 기능**을 실행할 수 있고, **Skills 기능**으로 에이전트 간 오케스트레이션을 학습시킬 수 있다. **Docker 지원, AGPL-3.0 라이선스.** 바로 앞서 정리한 [[2026-08-08-orca-parallel-coding-agents-ade]]와 같은 날 나란히 GeekNews에 올라왔고, 제출자 xguru의 말처럼 ***"Orca와 비교되며 같이 뜨는 도구"*** — ***"2월에 첫 릴리즈 했으니 Orca보다 약간 빠르긴 하다."***

## 핵심 포인트

- **단일 인터페이스 관리** — Claude Code·Codex·Copilot 등 **여러 코딩 모델**을 하나의 인터페이스에서 다룸.
- **셀프호스팅 아키텍처** — **로컬 daemon**이 에이전트를 관리, **여러 클라이언트**(iOS·Android·데스크톱·웹·CLI)가 접속.
- **프라이버시 중심** — **텔레메트리 없음·강제 로그인 없음.**
- **음성 제어·크로스 플랫폼** 지원.
- **Skills 기능** — 에이전트 간 오케스트레이션 학습.
- **Docker 지원, AGPL-3.0 라이선스** — Orca(MIT)와 다른 카피레프트 조건.
- **출시 시점** — 2026년 2월 첫 릴리즈, Orca보다 조금 앞섬.

## 내 생각 · 적용점

### 핵심 전이 1 — 같은 날 정리한 Orca와의 직접 비교가 이 노트의 핵심 가치다

[[2026-08-08-orca-parallel-coding-agents-ade]]와 Paseo는 **같은 니치(다중 코딩 에이전트 오케스트레이션)를 다른 설계 철학**으로 푼다 — Orca는 **병렬 실행+비교·병합**(git worktree 격리)에 초점을, Paseo는 **크로스 플랫폼 접근성+프라이버시**(로컬 daemon+여러 클라이언트)에 초점을 맞춘다. 두 도구가 거의 동시에(2월 vs 이후) 등장해 경쟁하는 걸 보면, **"여러 에이전트를 어떻게 조율할 것인가"라는 문제 자체가 이 시점 개발자 커뮤니티의 뚜렷한 공통 니즈**였다는 걸 보여준다.

### 핵심 전이 2 — Skills 기능은 그제그제 정리한 "소스가 확장 시스템" 비전과 같은 방향이다

[[2026-08-04-devtools-must-be-open-source]]에서 David Crawshaw가 그린 미래 — AI가 도구를 직접 커스터마이징하는 비용을 붕괴시킨다 — 를 Paseo의 **"Skills 기능으로 에이전트 간 오케스트레이션 학습"**이 실천한다. 사용자가 미리 정의된 오케스트레이션 패턴에만 갇히지 않고, **에이전트가 스스로 오케스트레이션 방법을 익히도록** 설계된 구조라는 점에서, 이번 시즌 반복해 온 "확장성을 제품 자체에 내장"하는 철학의 연장선이다.

### 핵심 전이 3 — "텔레메트리·강제 로그인 없음"은 "로컬이 정본" 원칙의 또 다른 실천이다

[[2026-08-02-session-portability-inference-api-lockin]]에서 요구한 7원칙 중 하나 — ***"로컬 이벤트 로그가 정본이고 서버 저장은 선택사항이어야 한다"*** — 를 Paseo의 **로컬 daemon 아키텍처**가 그대로 실천한다. AI 코딩 에이전트 오케스트레이션이라는, 민감한 코드베이스를 다루는 영역에서 **프라이버시를 제품의 핵심 설계 원칙으로 삼은 것**은, 이번 시즌 반복해 온 "벤더 종속을 피하려는 로컬 우선 설계"의 개발자 도구 버전이다.

### 핵심 전이 4 — 정직한 급소: AGPL-3.0은 Orca의 MIT와 다른 종류의 채택 장벽을 만든다

[[2026-08-04-github-has-alternatives-no-replacement]]에서 다룬 **콜드스타트 문제**와는 다른 축의 장벽이다 — Paseo가 실제로 널리 채택되려면, **기업이 AGPL의 카피레프트 의무를 감수할 만큼의 가치**를 제공해야 한다. MIT 라이선스인 Orca가 상업적 활용에서 더 유리한 조건을 갖는다는 점에서, 두 도구의 경쟁 구도에는 기능 비교만이 아니라 **라이선스 전략의 차이**도 중요한 변수로 작용할 것이다.

## 호스피탈리티 / CRS 적용 포인트

- **라이선스 조건을 먼저 확인 후 내부 도구 스택에 채택(급소).** AGPL-3.0 기반 도구를 CRS 내부 인프라에 통합할 때, 파생 소프트웨어의 소스 공개 의무가 발생하는지 법무 검토를 먼저 거친다.
- **프라이버시 요구사항이 있는 CRS 내부 도구엔 셀프호스팅 오케스트레이터를 우선 고려(전이 3).** 민감한 사업자·고객 데이터를 다루는 코드베이스에 AI 코딩 에이전트를 붙일 때, 텔레메트리 없는 로컬 우선 아키텍처를 선택 기준에 포함.
