# 오픈소스는 누구를 위한 것인가? (Glyph Lefkowitz) — 일방적 선물이 아니라 유지관리자와 사용자가 서로 신뢰를 지불하는 관계다

## 한 줄 요약

**Rich Hickey의 유명한 "Open Source Is Not About You"(2018)를 정면 반박하며, 오픈소스는 유지관리자가 사용자에게 베푸는 일방적 선물이 아니라 양쪽이 평판·영향력·신뢰를 주고받는 지속적인 사회적 관계라고 주장한다 — 그리고 이 관계 프레임은 최근 불거진 "LLM 생성 코드 PR을 받아야 하는가" 논쟁의 배경이기도 하다.**

## 핵심 포인트

- **Hickey 반박, 그러나 전면 부정은 아니다** — Hickey의 원 프레임("내가 소프트웨어를 준비했으니 즐기고 불평하지 말라")이 당시 크게 공감을 얻은 이유(무리한 요구를 하는 사용자들에 대한 반감)는 인정하되, ***과도한 단순화***라고 짚는다.
- **유지관리자가 얻는 것** — 평판, 영향력, 역량 향상, 유지보수 부담의 분담. 컨설팅업을 겸하는 경우 오픈소스는 곧 ***평판 자본이자 서비스 광고 효과***로 전환되며, 사용자는 관심·존경, 나아가 고객·고용으로 이를 되갚는다.
- **사용자 신뢰는 유지관리자의 의무** — 라이브러리를 설치하고 업데이트를 받는 것은 자신의 시스템(과 자격증명)을 유지관리자에게 위탁하는 행위다. 유지관리자에게는 ***"거기 사용자 자격증명을 빼돌리는 백도어가 있어서는 안 된다"*** 같은 암묵적 규칙이 거래가 아니라 남용해선 안 될 의무로 존재한다.
- **기능 변경이 사용자에게 미치는 영향** — 가상의 "OpenPaint" 사례로, 유지관리자가 기능을 제거하거나 지원을 중단하면 거기 의존하던 사용자들이 고립될 수 있음을 보여준다. 유지관리자의 선택은 진공 속 결정이 아니라 관계 속 결정이다.
- **LLM 생성 코드 PR 갈등으로 연결** — 이 에세이는 실제로 어느 유명 오픈소스 커뮤니티에서 "AI가 생성한 코드를 그만 받으라"고 사용자들이 항의한 사건에서 촉발됐다. 오픈소스가 상호 신뢰 관계라면, 유지관리자가 어떤 기여(LLM 생성 포함)를 받아들일지 결정하는 것도 사용자 신뢰(코드 품질·보안·유지보수성)를 저버리지 않는 범위에서 이뤄져야 한다는 긴장으로 이어진다.

## 인상 깊은 문장

> "I have prepared some software for you, please enjoy it, you have no right to complain" — Hickey 원 프레임의 요지(재구성 인용)

> "there is a trust relationship between the user and the maintainer" — 신뢰 관계의 핵심 명제(재구성 인용, 원문 검증 필요)

## 댓글

**논의 현황 미확인.** hada 댓글 수는 원천 차단으로 확인 못 했다. 저자가 Twisted 프레임워크 창시자로 지명도가 있어 HN·Lobsters 논의가 있었을 가능성은 있으나, 구체적인 스레드를 특정하지 못했다 — "논의 유무 불명"으로 정직하게 남긴다. 원문 본문도 검색 스니펫 재구성이라 저자의 논증 순서나 다른 사례가 더 있었을 가능성을 놓쳤을 수 있다.

## 내 생각 · 적용점

### 핵심 전이 1 — 평판이라는 비금전적 보상과 "아무도 오픈소스에 돈을 내지 않는다"의 다른 얼굴

[[2026-09-21-nobody-pays-for-open-source]](Laurie Voss)가 짚은 "오픈소스 경제적 보상 구조의 부재"와 이 글의 "유지관리자가 얻는 것(평판·영향력)"은 같은 문제의 다른 측면이다 — 금전적 보상은 없지만 비금전적 보상(평판 자본)은 실재한다는 것. 두 글을 나란히 읽으면 오픈소스 유지관리 동기의 전체 그림이 완성된다.

### 핵심 전이 2 — LLM 생성 코드 수용 정책들과의 직접 연결

[[2026-08-30-debian-generative-ai-policy-contributor-responsibility]]는 "AI 사용 금지 대신 기존 품질 기준 그대로, 책임은 기여자에게"로 결론 내렸고, [[2026-08-02-gcc-ai-policy]]도 비슷하게 "LLM 생성 기여는 받지 않되 도구 사용 자체는 허용"이라는 정책을 세웠다. 이 두 사례는 정확히 이 글이 말하는 ***"유지관리자가 어떤 기여를 받아들일지 결정하는 신뢰 관계"***를 제도화한 실제 정책이다. [[2026-08-28-sourcehut-bans-llm-generated-content]]는 더 급진적으로(디스킬링·노동/환경 피해라는 윤리적 판단으로) 원천 금지하는 대조군이다 — 신뢰 문제보다 더 근본적인 입장 차이를 보여준다.

### 핵심 전이 3 — "권한이 어디서 오는가"라는 질문과의 계열

[[2026-09-11-who-owns-wordpress-automattic-governance]]가 다룬 "오픈소스 프로젝트 리더십과 통제점이 회사 지배구조와 분리된다"는 사례는, 이 글의 "유지관리자 권한은 코드 소유가 아니라 관계에서 나온다"는 논지와 같은 계열이다.

## 호스피탈리티 / CRS 적용 포인트

온다의 CRS는 오픈소스 프로젝트가 아니므로 "유지관리자-사용자" 관계를 그대로 이식하는 건 다소 억지다. 다만 원칙 수준에서 두 가지는 전이 가능하다. 첫째, **사내 플랫폼팀-현업팀 관계** — 사내 API/SDK를 제공하는 플랫폼팀 구조는 이 관계와 구조적으로 유사하다. "우리가 만들었으니 알아서 쓰라"는 태도로 가면 현업팀 요구를 무시하기 쉽고, 반대로 현업팀도 피드백·버그 리포트·채택을 통해 플랫폼팀에 평판과 우선순위 정보를 되돌려준다는 상호성 프레임을 명시하면 내부 API 변경·폐기 시 커뮤니케이션 부담(OpenPaint 사례처럼 의존 팀이 고립되지 않도록)을 규범화하는 데 참고할 만하다. 둘째, **CRS 연동 파트너(호텔·OTA) 관계** — API 변경이 파트너 운영에 미치는 영향을 사전 고지하고, 업데이트가 파트너의 신뢰(가용성·보안)를 훼손하지 않도록 하는 책임은 이 글의 "악성 업데이트로부터 사용자를 보호할 의무" 프레임과 원칙적으로 통한다. 다만 오픈소스 특유의 무보수·자발적 관계의 함의(평판 경제, 번아웃 등)까지 그대로 옮길 수 있는 건 아니므로, 직접 적용은 멀고 원칙만 전이 가능하다고 밝혀둔다.
