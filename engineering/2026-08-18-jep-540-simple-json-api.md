# Jackson Gson 비켜, Simple JSON API가 온다 (SpringRunner)

> 출처: [Jackson Gson 비켜, Simple JSON API가 온다](https://www.linkedin.com/pulse/jackson-gson-%EB%B9%84%EC%BC%9C-simple-json-api%EA%B0%80-%EC%98%A8%EB%8B%A4-springrunner-0oqqc/) (SpringRunner · 2026-08-16 · LinkedIn Pulse) · 정리일 2026-08-18
> **저자**: **Broadcom 의 Spring 교육팀**. 교육 콘텐츠라 정리는 정확한 편이지만 **일차 출처가 아니다.**
> **출처 한계**: **openjdk.org 의 JEP 540 원문이 403 으로 막혀 직접 확인하지 못했다.** 아래 시그니처와 상태 표기는 **이 글 경유**이고, 실제 API 와 다를 수 있다.
> **제목이 낚시다.** 본문은 정반대로 ***"Jackson 도 Gson 도 비킬 필요는 없습니다"***라고 쓴다.

## 한 줄 요약

**JEP 540 이 JDK 28 을 겨냥해 JSON API 를 표준 라이브러리에 넣으려 한다. 질문은 단순하다. 간단한 JSON 처리만 필요한 자바 프로그램이 반드시 외부 라이브러리를 선택해야 하는가. 그런데 이 API 의 성격은 작은 Jackson 이 아니라 java.nio.file.Files.readString 에 가깝다. 외부 의존 없이 가벼운 일을 할 수 있게 해주는 편의이지 대체가 아니라는 것. 그리고 설계가 유연성이 아니라 엄격함을 고른다. 객체의 중복 키를 만나면 값을 하나 고르는 대신 JsonParseException 을 던지고, 주석과 후행 쉼표와 느슨한 숫자 형식을 허용하는 옵션이 없고, 진입점이 Json.parse(String) 과 Json.parse(char[]) 둘뿐이다. 저자가 뽑은 문장이 이 글의 값이다. 선택지를 늘리는 대신 보증을 늘립니다. 그리고 2014년의 JEP 198 은 범위를 넓게 잡았다가 실패했다는 대비가 붙는다. 상태는 아직 Proposed to Target 이고 jdk.incubator.json 이라는 인큐베이터 모듈로 들어가므로, 공개 API 에 노출할 거라면 어댑터 뒤에 숨기라는 것이 저자의 권고다.**

## 핵심 포인트

- **JEP 540**, **JDK 28 겨냥**, 상태는 **Proposed to Target**(확정이 아니다). **2026-08-10 부터 CSR 검토 중**이라고 이 글은 적는다.
- **동기**: ***"간단한 JSON 처리만 필요한 자바 프로그램이 반드시 외부 라이브러리를 선택해야 하는가?"***
- **성격 규정이 중요하다**: 작은 Jackson 이 아니다. ***"JSON 은 java.nio.file.Files 에 가깝습니다."*** NIO 채널을 대체하지 않으면서 가벼운 편의를 주는 자리.
- **엄격함 셋**:
  - **중복 키 거부**: 값을 고르지 않고 **`JsonParseException`** 을 던진다.
  - **확장 문법 없음**: 주석, 후행 쉼표, 느슨한 숫자 형식이 **옵션으로도 없다.**
  - **진입점 제한**: **`Json.parse(String)`** 과 **`Json.parse(char[])`** 뿐. **데이터가 메모리에 들어간다는 전제.**
- **명시적 비목표**: 기존 라이브러리 대체, **데이터 바인딩**, **스트리밍 파싱**, 비표준 문법 수용, 다중 파서 설정.
- **누락과 명시적 null 의 분리**: **`tryGet(name)`** 은 필드 존재를, **`tryValue()`** 는 명시적 JSON null 을 확인한다.
  ```java
  String nickname = user
      .tryGet("nickname")
      .flatMap(JsonValue::tryValue)
      .map(JsonValue::asString)
      .orElse("(none)");
  ```
- **PATCH 시맨틱**: ***"필드가 없으면 기존 값을 두고, 명시적 null 이면 삭제, 실제 값이면 바꾼다."***
- **핵심 설계 문장**: ***"선택지를 늘리는 대신 보증을 늘립니다."***
- **역사적 대비**: **2014년 JEP 198** 은 **범위를 넓게 잡으려다 실패**했다.
- **인큐베이터 주의**: **`jdk.incubator.json`** 으로 들어가므로 **API 가 바뀌거나 제거될 수 있다.** 공개 API 라면 **어댑터 뒤에 숨긴다.**
  ```java
  public interface SimpleJsonReader {
      Optional<String> findString(String json, String path);
  }
  ```
- **저자가 강조하는 구분 둘**: **"JDK 28 잠정"과 "JDK 28 확정"**, 그리고 **"JDK 에 포함됨"과 "안정된 표준 API"**.

## 내 생각 · 적용점

### 핵심 전이 1: "선택지를 늘리는 대신 보증을 늘린다"가 이번 시즌 축과 정확히 같다

**이 문장이 JSON 이야기가 아니다. API 설계 원칙이고, 가든이 8월 내내 다른 영역에서 같은 자리에 도착했다.**

| 영역 | 같은 형태의 문장 |
|---|---|
| 에이전트 루프 | [[2026-08-16-practical-loop-engineering]]: **완료 조건을 정의하면 모델이 "충분히 좋은지" 판정할 필요가 없다** |
| 오케스트레이션 | [[2026-08-16-graph-vs-loop-engineering]]: 노드가 확률적이 되면 **상태·거부권·예산을 명시**해야 한다 |
| 조직 통제 | [[2026-08-14-tiro-kiro-iso27001-security-infrastructure]]: ***"어떤 리소스도 생성, 수정, 삭제하지 마세요"*** |
| 인증 | [[2026-08-17-airbnb-flexible-authentication]]: **클라이언트는 결정하지 않는다** |

**공통 형태: 무엇을 안 할지 정하는 것이 무엇을 할 수 있는지 늘리는 것보다 강한 보증을 만든다.**

**그리고 넷 다 결과가 같다: 코드가 줄어든다.** Airbnb 는 클라이언트 코드 60% 감소를 냈고, JEP 540 은 파서 설정 API 를 아예 안 만든다. **제약이 구현을 줄인다.**

**우리 방법론의 최소 구현 우선 원칙이 같은 자리인데, 이 글이 하나를 더한다.** 최소 구현은 **지금 안 만든다**는 것이고, 이건 **앞으로도 안 만든다고 계약한다**는 것이다. **후자가 훨씬 강한 약속이고 그래서 훨씬 강한 보증을 준다.**

### 핵심 전이 2: JEP 198의 실패와 540의 성공 시도가 12년 간격이다

**2014년에 범위를 넓게 잡았다가 실패했고, 2026년에 좁혀서 다시 왔다.**

**표준화에서 이건 흔한 패턴인데, 이번 주에 정확히 반대 사례를 봤다.** [[2026-08-16-activitypub-won-by-being-boring]]에서 ActivityPub 이 ***"지루한 것은 구현 가능하다"***로 채택을 얻었지만, **만료된 인터넷 초안(`draft-cavage-http-signatures-12`)을 표준처럼 배포**해서 기술 부채를 안았다.

**두 사례를 나란히 놓으면 축이 하나 나온다.**
- **ActivityPub**: **빨리 배포**했고 **나중에 비호환 정식판**이 왔다.
- **JEP 540**: **12년 기다렸고** 좁혀서 왔다.

**그리고 JEP 540 도 아직 인큐베이터다.** 즉 **여전히 초안 단계**이고, ActivityPub 이 겪은 문제를 **똑같이 겪을 수 있는 자리**에 있다. 저자의 어댑터 권고가 정확히 그 위험 관리다.

**[[2026-08-16-activitypub-won-by-being-boring]]에서 세운 규칙이 그대로 적용된다: 지루한 기술을 고를 때 친숙한가와 확정됐는가를 따로 묻는다.** JEP 540 은 **친숙하지만(JSON) 확정되지 않았다(incubator).**

**그리고 같은 JDK 28 에 [[2026-06-08-project-valhalla-jdk28]]이 있다.** 10년 작업이 들어가는 릴리스다. **두 전략이 대비된다: Valhalla 는 범위를 유지하며 오래 갈았고, JSON API 는 범위를 좁혀서 돌아왔다.** 둘 다 결국 같은 릴리스에 도착했다는 게 흥미롭다.

### 핵심 전이 3: 중복 키 거부가 경계면 문제의 정석 해법이다

**JSON 스펙은 중복 키의 처리를 정의하지 않는다.** 그래서 파서마다 다르게 처리한다. 마지막 값을 쓰거나, 첫 값을 쓰거나, 배열로 만들거나.

**그러면 같은 바이트가 파서마다 다른 값이 된다.** 그리고 이게 **경계면 교차검증**이 잡으려는 문제의 정확한 형태다. 생산자와 소비자가 **다른 파서를 쓰면 같은 페이로드가 다른 의미**가 된다.

**보안 쪽으로도 고전적인 벡터다.** **검증하는 파서와 실행하는 파서가 중복 키를 다르게 읽으면** 검증을 통과한 페이로드가 다른 값으로 실행된다. **던지는 게 맞다.** (이 글이 보안을 언급하지 않으므로 **내 추론**이다.)

**실무 함의가 하나 있다: 우리가 지금 쓰는 파서가 중복 키를 어떻게 처리하는지 아는가.** 대부분 모른다. 그리고 **파트너사가 보내는 페이로드에 중복 키가 있으면 조용히 하나가 선택된다.**

### 핵심 전이 4: tryGet 과 tryValue 분리가 PATCH 를 살린다

**이 API 설계에서 가장 실무적인 부분이다.** ***"필드가 없으면 기존 값을 두고, 명시적 null 이면 삭제, 실제 값이면 바꾼다."***

**세 상태가 필요한데 대부분의 데이터 바인딩이 앞의 둘을 뭉갠다.** Jackson 으로 DTO 에 바인딩하면 **필드 부재와 명시적 null 이 똑같이 `null` 필드**가 된다. 그러면 **PATCH 에서 "안 보낸 필드"와 "지우라고 보낸 필드"를 구분할 수 없다.**

**그리고 이건 조용히 데이터를 잃는 종류의 버그다.** 부분 수정 API 에서 클라이언트가 두 필드만 보냈는데 나머지가 null 로 덮이면, **테스트가 통과하고 배포되고 운영에서 발견된다.**

**실무 규칙: PATCH API 를 만들 때 세 상태를 타입에서 구분할 수 있는지 먼저 확인한다.** Jackson 에서는 `JsonNullable` 같은 래퍼나 원시 `JsonNode` 접근이 필요하고, **그걸 안 하면 PATCH 가 아니라 부분 PUT 이다.**

## 호스피탈리티 / CRS 적용 포인트

**온다는 Java/Spring 스택이라 직접 관련이 있다.**

- **지금 당장 확인할 것 하나: 우리 PATCH API 가 세 상태를 구분하는가.** 예약 부분 수정, 요금 정책 갱신, 파트너 설정 변경에서 **"안 보냄"과 "null 로 보냄"이 다른 의미**여야 하는데, Jackson DTO 바인딩이면 둘 다 `null` 이다. **조용히 데이터를 지우는 버그가 여기서 난다.**
- **우리 파서의 중복 키 처리를 확인한다.** 파트너사나 채널이 보내는 페이로드에 중복 키가 있을 때 지금 어떻게 되는지 아무도 모를 가능성이 높다. **검증 단계와 처리 단계가 다른 경로를 쓴다면 특히 위험하다.**
- **JEP 540 자체는 아직 도입 대상이 아니다.** JDK 28 은 멀고 **인큐베이터**다. 다만 **작은 도구·배치 스크립트에서 의존성 하나를 줄이는 선택지**로 기억해둘 만하다. 서비스 코드는 **데이터 바인딩이 필요해서 Jackson 이 계속 간다.**
- **인큐베이터 타입을 공개 API 에 노출하지 않는다.** 저자의 어댑터 권고는 JEP 540 뿐 아니라 **초안 단계 스펙 전반의 규칙**이다. ActivityPub 이 그걸 안 해서 만료된 초안에 묶였다.
- **"선택지를 늘리는 대신 보증을 늘린다"를 우리 내부 API 에 적용한다.** 파트너 연동 인터페이스에서 **설정 옵션을 늘리는 대신 허용하지 않는 것을 명시**하는 쪽이, 나중에 파서 차이나 해석 차이로 생기는 사고를 줄인다.
