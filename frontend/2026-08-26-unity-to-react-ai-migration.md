# Unity를 몰라도 AI로 Unity 서비스를 React로 옮길 수 있었던 이유 (한컴테크)

> 출처: [tech.hancom.com/migrated-unity-to-react-with-ai](https://tech.hancom.com/migrated-unity-to-react-with-ai/) (한컴테크) · 정리일 2026-08-26

## 한 줄 요약

**C#과 Unity 경험이 없는 개발자가 AI를 활용해 기존 Unity 서비스를 React·Next.js로 마이그레이션한 사례. 핵심은 "AI가 코드를 대신 짜준다"가 아니라, ***코드 검증의 기준점을 소스 코드 자체에서 AI가 번역한 자연어 명세로 옮겨*** 협업 효율을 끌어올렸다는 것 — 그리고 그 과정에서 AI를 코드 생성기가 아니라 ***맥락을 주입하고 안전장치를 설계하는 하네스***로 다뤘다는 것이다.**

## 핵심 포인트

- **경험 없는 언어/프레임워크의 마이그레이션** — 저자는 ***C#·Unity 경험이 없는*** 개발자. AI를 매개로 삼아 기존 Unity 서비스를 **React·Next.js**로 옮겼다.
- **검증 기준의 이동** — ***"코드 검증의 기준을 소스 코드 자체가 아닌 AI가 번역한 자연어 명세로 옮겨 협업의 효율성을 극대화했다"*** — 원문(Unity/C#)을 직접 읽고 대조하는 대신, AI가 원문의 동작을 자연어로 명세화한 문서를 검증·리뷰의 기준으로 삼았다는 뜻으로 읽힌다.
- **하네스 엔지니어링의 명시적 적용** — ***"AI를 단순히 코드 생성 도구로 쓰지 않고 맥락 주입과 안전장치를 설계하는 하네스 엔지니어링을 적용했다"*** — AI를 둘러싼 실행 환경(맥락 주입 방식, 안전장치)을 의도적으로 설계했다는 것이 저자의 자기 서술이다.
- **개발자 주도의 검증 흐름** — ***"정확성이 중요한 작업에서 AI가 제시하는 답변을 개발자가 주도적으로 판단하고 검증하는 흐름을 구축했다"*** — 이 문장에서 발췌가 끊겨 구체적으로 어떤 절차인지는 확인하지 못했다.

## 내 생각 · 적용점

### 핵심 전이 1 — "루프 바깥의 평가자"라는 Weng의 원칙이, 언어를 모르는 개발자의 실무 제약에서 같은 형태로 재발견된다

[[2026-08-06-harness-engineering-for-self-improvement]]에서 Lilian Weng이 정리한 핵심 결론은 ***"평가기와 권한 제어는 루프 바깥에 있어야 한다"***, ***"인간은 루프에서 빠지는 게 아니라 스택을 올라가야 한다"***였다. 이 한컴테크 글의 "검증 기준을 소스 코드에서 자연어 명세로 옮긴다"는 동작이 정확히 이 원칙의 실무적 구현으로 읽힌다 — **개발자가 Unity/C# 코드 한 줄 한 줄을 읽고 검증할 수 없으니(그 스킬이 없으니), 검증 가능한 층을 코드보다 한 단계 위(자연어 명세)로 옮겨서 그 층에서 "루프 바깥의 평가자" 역할을 계속 수행한다.** 원문을 못 읽는 인간이 그럼에도 판단 권한을 유지하는 방법이 "명세 층에서 검증"이라는 것 — 이건 Weng의 추상적 원칙이 낯선 코드베이스를 넘겨받은 실무자에게 어떻게 구체화되는지 보여주는 사례다.

### 핵심 전이 2 — React Doctor가 도구로 자동화한 문제를, 이 사례는 워크플로로 풀었다

[[2026-05-27-react-doctor-ai-code-verification]]가 다룬 React Doctor는 ***"AI가 쓴 React 코드가 정말 올바른지 누가 검토하는가"***라는 질문에 정적 분석 도구로 답한 사례였다. 이 한컴테크 글은 같은 질문에 ***도구가 아니라 워크플로 설계***로 답한다 — 검증 기준 자체를 옮기는 것. **한쪽은 "AI가 쓴 코드를 사후에 자동 채점"하고, 다른 쪽은 "애초에 검증 가능한 형태(자연어 명세)로 작업 단위를 재정의"한다** — 같은 문제(AI 생성 코드를 어떻게 신뢰할 것인가)에 대한 두 개의 서로 다른, 그러나 상호 보완 가능한 답이다.

## 호스피탈리티 / CRS 적용 포인트

- **레거시 프론트엔드(구형 프레임워크·낯선 언어)를 다루는 신규/이직 개발자가 CRS 내부에도 있을 수 있다.** 이 사례의 "검증 기준을 자연어 명세로 옮긴다"는 원칙은, 온다의 레거시 모듈(오래된 Java/PHP 등)을 새 팀원이 AI 도움으로 이관·리팩터링할 때 **"원문 코드를 다 이해하지 못해도, AI가 뽑아낸 동작 명세를 팀이 함께 검증하는 절차"**로 원용할 수 있다.
- 다만 이 노트 자체가 원문 미확인 상태라 — **구체적인 "하네스 엔지니어링" 설계(어떤 안전장치, 어떤 맥락 주입인지)를 CRS에 그대로 적용하기엔 근거가 너무 얇다.** 원문을 나중에 확보하면 이 CRS 적용 포인트를 구체화할 필요가 있다.
