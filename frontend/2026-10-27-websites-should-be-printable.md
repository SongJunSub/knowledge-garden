# 웹사이트는 인쇄할 수 있어야 한다 (GeekNews)

> 출처: GeekNews 토픽 [id=36049](https://news.hada.io/topic?id=36049) (원문 매체·저자 미특정) · 정리일 2026-10-27

> **출처 한계**: `news.hada.io`는 이 세션에서 egress 차단(`ENOTFOUND`)으로 원문을 전혀 열람하지 못했다. WebSearch로 "websites should be printable" 류를 검색했으나 이 GeekNews 토픽의 원문 자체는 특정하지 못했다 — 대신 CSS 인쇄 스타일시트에 대한 일반적인 가이드(Peter Molnar의 `petermolnar.net` 등)만 배경지식으로 교차확인했다. Slack 발췌에도 "코드 블록 페이지 나뉨" 항목이 "…(이하 생략)"으로 끊겨 있어, 저자가 그 문제를 결국 어떻게 처리했는지(포기했는지, 다른 대안을 찾았는지)는 확인하지 못했다. hada 댓글 수, HN/Lobsters 큐레이션 여부도 확인 불가하다.

## 한 줄 요약

**웹페이지를 인쇄할 수 있다는 것과 읽기 좋은 인쇄물을 얻는 것은 다르다 — 저자가 자기 사이트를 직접 인쇄해보니 글자가 너무 크고 헤더·흑백 링크의 가독성이 나빴고, `@media print`로 화면용과 인쇄용 스타일을 분리해 본문 12pt·제목은 더 크게·링크는 검은색으로 바꿔 해결했지만, 코드 블록이 페이지 경계에서 매끄럽게 나뉘지 않는 문제만큼은 해결하지 못했다는 실전 기록이다.**

## 핵심 포인트

- **"인쇄 가능"과 "읽기 좋은 인쇄물"은 다른 목표다** — 저자가 직접 운영하는 사이트를 인쇄해보니 ***글자가 너무 크고, 헤더와 흑백 링크의 가독성도 좋지 않았다.*** 브라우저가 "인쇄 버튼이 작동한다"는 것과 "뽑아낸 종이가 읽을 만하다"는 것 사이에는 꽤 큰 간극이 있다는 걸 직접 테스트로 확인한 셈이다.
- **`@media print`로 화면과 인쇄를 분리** — CSS의 `@media print`로 ***인쇄 전용 스타일을 적용***하고, 화면과 인쇄물에 각각 다른 요소를 표시하도록 지정할 수 있다. 네비게이션·사이드바처럼 화면에서만 의미 있는 요소를 인쇄에서는 숨기는 식의 분기가 가능하다.
- **구체적 조정값 — 12pt 본문, 검은 링크** — 인쇄용으로 ***본문은 12pt, 제목은 그보다 크게, 링크는 검은색***으로 바꿨다. 화면에서 흔한 색상 링크가 흑백 인쇄에서는 밑줄 없이 흐릿한 회색으로만 보여 가독성이 떨어지는 문제를 색상 재정의로 해결한 것으로 보인다.
- **코드 블록의 페이지 나뉨은 미해결 과제로 남았다** — 스타일을 손봐도 코드 블록이 ***한 덩어리로 유지되며 페이지 경계에서 매끄럽게 나뉘지 않는*** 문제는 해결하지 못했다(Slack 발췌가 이 지점에서 끊긴다). `page-break-inside: avoid`를 코드 블록에 적용하면 오히려 블록 전체가 다음 페이지로 통째로 밀려 빈 공간이 생기는, 인쇄 CSS의 흔한 딜레마로 보인다.

## 인상 깊은 문장

> "직접 운영하는 사이트를 인쇄해 보니 글자가 너무 크고, 헤더와 흑백 링크의 가독성도 좋지 않았다." (Slack GN⁺ 발췌)

"인쇄가 되는지"를 코드 리뷰나 체크리스트가 아니라 ***실제로 종이를 뽑아보는 행위***로 검증했다는 점이 이 글의 태도를 압축한다 — `@media print` 규칙을 작성해두고 "작동하겠지"라고 넘어가는 대신, 직접 프린터에 넣어본 뒤에야 글자 크기·링크 색의 문제를 발견했다는 것.

## 내 생각 · 적용점

**핵심 전이 — [[2026-08-31-justified-text-super-metroid-walkthrough]]와 결이 통하는, "원래 의도되지 않은 출력 환경에 맞춰 텍스트를 다시 손본다"는 같은 종류의 수작업.** 그 노트는 가변폭 글꼴을 위해 설계된 양쪽 정렬 관행을 고정폭 ASCII 텍스트 위에서 재현하려고, 자동 도구 없이 ***문장 자체를 다시 써서*** 오른쪽 끝을 맞춘 사례였다. 이 글도 화면용으로 설계된 웹페이지를 인쇄라는 다른 출력 매체에 맞추려고 글자 크기·색을 수작업으로 재조정한다 — 두 글 모두 "자동으로 다 잘 될 것"이라는 가정이 틀렸다는 걸 직접 테스트(인쇄, 또는 화면에 띄워보기)로 확인한 뒤에야 수작업 교정에 들어갔다는 공통점이 있다. 다만 이 연결은 "매체 전환 시 가독성은 자동으로 보장되지 않는다"는 원칙 수준의 가벼운 연결이고, 기술적으로는 전혀 다른 영역(인쇄 CSS vs 고정폭 타이포그래피)이라는 점은 분명히 해둔다.

## 호스피탈리티 / CRS 적용 포인트

**직접 적용은 멀다.** 온다 CRS는 B2B 운영자용 대시보드·API 중심이라, 고객이 웹페이지를 종이로 인쇄해 보는 상황 자체가 핵심 사용 경로가 아니다. 다만 ***예약 확인서, 정산 내역, 운영 리포트처럼 "결국 인쇄되거나 PDF로 저장될 가능성이 있는 화면"***이 CRS에도 존재한다면, 이 글이 확인한 "화면에서 괜찮아 보여도 인쇄하면 글자 크기·링크 가독성이 깨진다"는 교훈과 `@media print`로 화면/인쇄를 분리하는 접근은 그대로 참고할 만하다 — 다만 이는 원칙 차원의 참고이고, 당장 CRS 화면 중 어떤 것이 인쇄 대상인지조차 확인되지 않은 상태라 "적용 없음"에 가깝다는 걸 정직하게 밝힌다.
