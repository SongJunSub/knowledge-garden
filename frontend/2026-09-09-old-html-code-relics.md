## 한 줄 요약
**오래된 웹사이트에 화석처럼 남아 있는 HTML 메타 태그·조건부 주석들은, 브라우저마다 제각각이던 렌더링 방식을 하나로 맞추려던 흔적인 동시에 — Microsoft의 Smart Tags, Skype 툴바처럼 — 외부 소프트웨어가 사이트 소유자 동의 없이 페이지를 마음대로 바꿔치기하던 시절에 개발자들이 쳐야 했던 방어선이었다는 것을 아카이브 형식으로 되짚는 글.**

## 핵심 포인트
- **`X-UA-Compatible` / `IE=edge`** — Internet Explorer에게 "지원하는 가장 최신 문서 모드로 렌더링하라"고 지시하는 메타 태그다. `IE=5`부터 `IE=11`, `EmulateIE7`~`EmulateIE11` 같은 특정 버전 고정값도 가능했지만, 유효한 DOCTYPE이 있어야만 동작하고 없으면 쿼크 모드로 떨어졌다 — 브라우저마다, 심지어 같은 IE의 버전마다 렌더링이 달라지던 시절의 흔적이다.
- **`chrome=1`** — 구글이 IE 6~9용으로 배포했던 플러그인 **Google Chrome Frame**을 활성화하는 값이다. 이 메타 태그가 있으면 IE 안에서도 페이지를 IE의 Trident 엔진 대신 Chrome의 WebKit 기반 엔진으로 렌더링했다 — ***"IE 안에서 Chrome을 실행"***하는 우회로였던 셈. Chrome Frame은 오래전에 단종됐다.
- **조건부 주석(conditional comments)** — `<!--[if IE]>...<![endif]-->` 형태로, IE 5~9만 이 안의 마크업을 읽고 실행하고 다른 모든 브라우저는 그냥 평범한 주석으로 무시했다. 특정 브라우저에만 CSS·스크립트를 태우던 표준적 방법이었으나 IE10부터 지원이 빠졌고 다른 브라우저는 애초에 지원한 적이 없다.
- **Microsoft Smart Tags 차단 태그** — Windows XP 시절 IE 6이 도입한 Smart Tags는 ***Microsoft가 웹페이지 본문에 자동으로 하이퍼링크를 끼워 넣는*** 기능이었다(예: 회사명을 인식해 주가 정보 링크로 자동 태깅). 사이트 소유자 동의 없이 남의 페이지 콘텐츠를 바꾼다는 반발이 거세게 일었고, 결국 이를 막기 위한 `MSSmartTagsPreventParsing` 메타 태그를 추가해야 했다 — 여론의 반발로 기능 자체는 시장에서 밀려났지만 이 방어용 태그만 유물로 남았다.
- **Skype 툴바 차단 태그** — Skype 설치 시 함께 깔리던 브라우저 확장이 페이지에서 전화번호처럼 보이는 텍스트를 인식해 옆에 클릭 가능한 아이콘을 붙였는데, 이 삽입이 종종 레이아웃을 깨뜨렸다. 개발자들은 `<meta name="SKYPE_TOOLBAR" content="SKYPE_TOOLBAR_PARSER_COMPATIBLE" />` 태그로 이 기능을 꺼야 했다 — 이 확장은 Firefox에서 특히 불안정해서 2011년 Mozilla가 아예 강제 차단하기도 했다.
- **ICBM / `geo.position` 메타 태그** — Usenet 시절 자기 사이트의 위경도를 등록하던 관행에서 유래한 해커 은어 "ICBM 주소"(대륙간탄도미사일이 목표를 찾듯 좌표로 위치를 특정한다는 농담 섞인 이름)가 그대로 메타 태그명으로 남았고, 이후 `geo.position`이라는 유사 표준과 GeoURL 같은 서비스가 이 좌표들로 사이트를 지도에 표시해줬다. 냉전기 미사일 좌표에서 나온 이름이 21세기 초 웹사이트 위치 태그로 재활용된 셈이다.
- 이 밖에 구글이 한때 AJAX 콘텐츠 색인을 위해 권장했다가(2009) 이후 폐기한(2015) **`_escaped_fragment_`** 규약, `rel="image_src"` 같은 미디어 지정 링크 태그, iOS 홈 화면 추가 시 브라우저 크롬을 없애는 **Apple 전용 메타 태그**들도 같은 계열의 유물로 다뤄진다.

## 내 생각 · 적용점
1. 이 항목들이 공통으로 증언하는 건 **"플랫폼(브라우저·확장 프로그램)이 콘텐츠 소유자의 동의 없이 페이지를 바꿀 수 있던 시대에, 개발자가 할 수 있는 유일한 방어가 메타 태그 하나 심는 것뿐이었다"**는 힘의 불균형이다. Smart Tags(Microsoft가 본문에 링크 삽입)와 Skype 툴바(전화번호 옆 아이콘 삽입) 둘 다 "플랫폼이 콘텐츠를 마음대로 재해석해 얹는다"는 동일한 패턴이고, `MSSmartTagsPreventParsing`·`SKYPE_TOOLBAR` 두 태그는 그 재해석을 거부하는 옵트아웃 신호였다.
2. 같은 배치로 정리한 [[2026-09-08-beusable-geo-strategy-brand]]와 시대를 건너뛴 대칭을 이룬다 — 그 글은 "AI가 내 콘텐츠를 재해석해 답변에 인용/누락하는 시대에 어떻게 대응할까"(GEO)를 다루는데, 이 글의 Smart Tags·Skype 사례는 "플랫폼이 내 콘텐츠를 재해석해 삽입/변형하는 시대에 어떻게 막을까"를 다룬다 — 방향은 정반대(하나는 노출을 원하고, 하나는 변형을 막으려 한다)지만 **"내 콘텐츠의 최종 형태를 내가 통제하지 못한다"는 동일한 문제의식**을 20여 년의 시차를 두고 반복하고 있다. 다만 이 연결은 이 노트 하나만으로는 억지스러울 수 있어, GEO 노트 쪽에서 이미 세운 "발견 가능성을 플랫폼이 통제한다"는 프레임에 곁가지로만 붙여둔다.
3. 조건부 주석·`chrome=1` 같은 항목은 [[2026-09-09-extreme-server-side-rendering-2025]]와 나란히 놓으면 "브라우저의 실제 동작 방식을 얼마나 진지하게 파고드느냐"는 태도가 겹친다 — 하나는 브라우저 파편화의 역사를 아카이브하고, 하나는 브라우저의 렌더링 성질을 실험으로 극한까지 밀어붙인다.

## 호스피탈리티 / CRS 적용 포인트
직접 적용은 멀다 — 이 태그들 자체는 지금 쓸 일이 없는 폐기된 유물이다. 다만 전이 가능한 원칙 하나는 남는다: 온다의 CRS/채널 매니저처럼 **여러 OTA·PMS 파트너의 위젯·스크립트가 한 페이지(호텔 예약 페이지, 파트너 포털)에 얹히는 구조**에서는, 과거 Smart Tags·Skype 툴바가 그랬듯 특정 파트너 스크립트가 레이아웃이나 데이터 표시를 예기치 않게 변형할 위험이 여전히 존재한다 — "외부 스크립트가 내 페이지를 마음대로 바꾸지 못하게 하는 옵트아웃 지점을 명시적으로 마련해둔다"는 원칙은, CSP(Content-Security-Policy)나 iframe sandbox 속성처럼 지금 시대의 도구로 형태만 바뀌어 여전히 유효하다.
