# 서버 개발자가 헥사코드를 몰라도 되게 만들기 (카카오스타일 · 지그재그)

> **출처 한계**: `devblog.kakaostyle.com`이 이번 세션에서 네트워크 게이트웨이 정책으로 접속 차단됐다. 발행일이 오늘(2026-08-31)이라 WebSearch에도 아직 색인되지 않아 원문 본문을 확인하지 못했다. 이 노트는 **Slack이 전달한 4줄 발췌 요약**을 뼈대로 하고, 같은 devblog의 선행 글 두 편 — [Server Driven UI 설계를 통한 UI 유연화(2021-12-16)]·[프론트엔드팀의 디자인 시스템 재구축기(2024-12-13, CSS 변수 기반 디자인 토큰·테마 관리로 재구축)] — 을 WebSearch로 확인해 정황만 보강했다. 원문의 구체적 아키텍처 다이어그램·코드 예시·수치는 담지 못했다.

## 한 줄 요약

**지그재그는 SDUI(Server Driven UI) 도입 이후 서버 코드에 색상 헥사코드가 하드코딩되고 그걸 처리하는 분기가 쌓이는 문제를 겪었고, 색상 상수를 서버가 직접 들고 배포하는 구조에서 벗어나 디자인 시스템과 연동된 참조 구조로 바꿔 코드 수정 없이 화면을 바꿀 수 있는 환경을 만들었다는 글이다.**

## 핵심 포인트

- 지그재그는 SDUI 도입 이후 서버가 화면 구성뿐 아니라 색상 같은 스타일 값까지 직접 결정하게 되면서, 서버 코드 안에 ***하드코딩과 복잡한 분기 처리***가 쌓이는 문제를 겪었다.
- 컬러 상수를 서버 코드가 직접 관리하는 방식이 비효율적이었고, 색을 하나 바꾸려 해도 서버 배포가 필요해 ***개발 생산성의 병목***이 됐다.
- 해법은 서버가 스타일 값을 직접 소유하는 대신 ***디자인 시스템과 연동된 유연한 구조***로 바꾸는 것 — 서버는 "무엇을 보여줄지"만 결정하고 "어떻게 보일지"는 디자인 시스템 쪽 토큰 참조로 넘긴 것으로 읽힌다.
- 결과적으로 ***코드 수정 없이도 화면을 바꿀 수 있는 환경***을 만들어 배포 부담을 크게 줄였다는 것이 제목("헥사코드를 몰라도 되게")의 요지다.
- (정황 보강, 원문 미확보) 지그재그는 2021년부터 SDUI를 도입해왔고 2024년 말 프론트엔드 디자인 시스템을 CSS 변수 기반 디자인 토큰·테마 체계로 재구축한 이력이 있다 — 이번 글은 그 토큰 인프라를 서버 쪽 색상 관리까지 연결한 후속 작업으로 추정되나, 이건 추정이지 원문에서 직접 확인한 사실이 아니다.

## 내 생각 · 적용점

### 핵심 전이 1 — "기계가 읽을 수 있게, 기계가 통치하게는 말고"의 서버사이드 실증

[[2026-08-05-future-of-design-systems-context]]에서 TJ Pitre가 세운 원칙 — 디자인 시스템을 **기계가 읽을 수 있게** 만들되 **기계가 통치하게는 말라** — 는 클라이언트·AI 에이전트 쪽 논의였는데, 이 글은 그 원칙이 **서버 쪽에도 그대로 적용**된다는 걸 보여준다. 서버가 헥사코드를 직접 들고 있던 상태는 "판단(어떤 색을 쓸지)"과 "실행(그 값을 배포)"이 서버 코드 안에 뒤섞여 있던 것이고, 디자인 시스템 토큰 참조로 옮긴 건 판단은 디자인 시스템(사람이 정의)에 남기고 서버는 그걸 읽어 실행만 하도록 역할을 분리한 것 — 원칙은 같고 층위만 다르다.

### 핵심 전이 2 — Astryx와 같은 방향의 "하드코딩 탈피" 계열

[[2026-07-06-astryx-meta-open-source-design-system]]도 결국 대규모 서비스가 스타일 값을 코드에 흩어놓지 않고 토큰·컴포넌트로 참조하게 만든 사례다. Meta는 프런트엔드 컴포넌트 레벨에서, 지그재그는 서버가 내려주는 SDUI 응답 레벨에서 같은 문제(하드코딩된 스타일 값 → 배포 없이는 못 바꿈)를 같은 해법(토큰 참조)으로 풀었다는 점에서 같은 계열의 사례로 묶인다.

## 호스피탈리티 / CRS 적용 포인트

CRS Admin이나 예약 위젯도 상태 배지 색상(예약확정=초록, 대기=노랑, 취소=빨강)이나 브랜드별 테마 색상이 코드에 하드코딩돼 있으면, 파트너사 화이트라벨이나 브랜드 리스킨을 할 때마다 배포가 필요해지는 **똑같은 병목**이 생긴다. 이 글의 핵심 원칙 — 값을 코드에 직접 넣지 말고 디자인 시스템 토큰을 참조하게 만들어 코드 수정 없이 값만 바꾸는 구조 — 는 CRS의 멀티 브랜드/화이트라벨 요구사항에 직접 전이 가능한 원칙이다. 다만 SDUI 자체를 도입할지 여부는 별개 판단이라, "SDUI를 쓰라"가 아니라 "스타일 값은 토큰으로 참조하고 코드에 박지 마라"는 원칙만 가져온다.
