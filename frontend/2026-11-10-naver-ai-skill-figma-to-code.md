## 한 줄 요약

**네이버가 Figma 디자인을 네이티브 UI 코드로 자동 변환하는 플러그인을 만들고, 거기에 AI를 더해 디자인 검수까지 자동화해 생산성을 끌어올렸다고 주장하는 실전 경험기다.**

## 핵심 포인트

- **변환 자동화** — Figma 디자인을 ***네이티브 UI 코드로 자동 변환***하는 플러그인을 자체 개발. "Figma→Code"라는 제목 그대로, 디자인 핸드오프 단계를 플러그인으로 대체하려는 시도.
- **검수까지 AI가 개입** — 단순 변환을 넘어 ***AI를 활용해 디자인 검수와 개발 과정을 자동화***한다고 명시 — 변환된 코드가 원본 디자인과 일치하는지 확인하는 단계까지 AI가 맡는다는 뜻으로 읽힌다. 구체적으로 어떤 기준(픽셀 단위 비교, 컴포넌트 구조 비교 등)으로 검수하는지는 발췌에서 끊겨 확인 불가.
- **제목의 "10계명"** — 열 가지 구체적 원칙이 본문에 있을 것으로 추정되나 Slack 발췌에는 등장하지 않아 전부 미확인.

### 핵심 전이 1 — "디자이너와 개발자 사이 간극을 AI/자동화로 좁힌다"는 동시대 사례 축적

같은 날 수집된 [[2026-11-10-miridih-axpd-squad-designer-dev-bridge]](미리디 AXPD스쿼드)도 "프로덕트 디자이너와 개발자를 AI로 연결한다"는 동일한 문제를 다룬다. 이 글은 ***기술적 해법(Figma→Code 변환 플러그인)***에 집중하고, 미리디 글은 ***조직적 해법(전담 스쿼드 구성)***에 집중한다는 점이 대조적이다 — 같은 문제("디자인-개발 간극")에 "도구로 푼다"와 "조직으로 푼다"는 두 가지 답이 같은 날 동시에 올라온 드문 경우.

### 핵심 전이 2 — 디자이너가 AI로 직접 결과물을 만드는 흐름의 연장선

[[2026-06-08-claude-code-designer-builds-with-ai]]는 디자이너가 Claude Code로 직접 프로덕트를 만드는 사례였다. 이 글은 방향이 다르다 — ***디자이너가 직접 코드를 짜는 게 아니라, 디자이너가 만든 Figma 산출물을 플러그인+AI가 코드로 변환***한다. "디자이너의 AI 활용"이 "직접 코딩"과 "자동 변환 도구 제작" 두 갈래로 분화하고 있다는 신호.

## 호스피탈리티 / CRS 적용 포인트

**적용 가능성 있음.** 온다 CRS/B2B 호스피탈리티 제품도 디자이너가 Figma로 설계한 화면을 개발팀이 수작업으로 재구현하는 핸드오프 비용이 분명 존재한다. 이런 Figma→Code 자동 변환 플러그인이 성숙하면, 신규 백오피스 화면이나 고객사별 커스터마이징 UI 제작 시간을 줄이는 데 참고할 만하다 — 단, 이 노트 자체가 변환 정확도·수작업 보정 비율을 밝히지 않아 실제 도입 전 자체 파일럿이 필요하다.
