## 한 줄 요약

**미리캔버스(미리디)가 별도 이미지 처리 라이브러리 없이 CSS·SVG 필터 속성만으로 브라우저 내에서 실시간 이미지 보정(밝기·대비·채도 등)을 구현한 사례를 다룬 글이다.**

## 핵심 포인트

- **라이브러리 없이 브라우저 네이티브 기능으로 해결** — ***이미지 처리 라이브러리 없이도 CSS와 SVG 필터 속성만으로*** 이미지 편집 기능을 구현했다는 점이 핵심 — 서버 왕복이나 무거운 클라이언트 라이브러리(canvas 픽셀 연산 등) 없이 브라우저 렌더링 엔진에 보정을 맡긴 접근이다.
- **실시간 색상·효과 보정** — SVG 필터를 활용해 이미지의 색상과 효과를 ***실시간으로*** 보정하는 기술을 다룬다. 디자인 툴(미리캔버스) 특성상 사용자가 슬라이더를 움직이는 즉시 결과가 반영돼야 하는 UX 요구와 맞아떨어지는 선택으로 보인다.
- **필터 조합으로 다양한 시각 효과** — 필터를 조합해 ***밝기, 대비, 채도*** 등 다양한 시각적 효과를 브라우저 내에서 즉시 적용하는 방법을 설명한다.

## 내 생각 · 적용점

### 핵심 전이 1 — 같은 회사(미리디)의 다른 노트와 잠재적으로 이어지는 "이미지 편집 기술" 사례

[[2026-09-01-miridih-hackathon-30-outputs-in-two-days]]는 미리디 엔지니어팀이 이틀 해커톤에서 만든 30여 개 결과물 중 ***"이미지 편집 기술 등 혁신적인 결과물"***을 언급했다. 이 SVG 필터 글이 그 해커톤 산출물과 같은 계열인지는 확인하지 못했지만(시기·형식이 다를 수 있음), 적어도 **같은 회사가 이미지 편집을 프론트엔드 과제로 반복해서 다루고 있다는 정황**은 겹친다 — 억지로 같은 프로젝트라고 단정하지는 않는다.

### 핵심 전이 2 — "무거운 처리를 서버·라이브러리 대신 브라우저 표준 기능에 맡긴다"는 원칙

[[2026-09-04-browser-main-thread-is-expensive]]가 브라우저 메인 스레드 비용의 무거움을 짚었던 것과 대비해서 보면 흥미롭다 — 이 글은 오히려 ***"이미지 처리를 서버나 무거운 JS 라이브러리로 보내지 않고 브라우저의 렌더링 엔진(SVG 필터, GPU 가속 가능)에 위임"***함으로써 메인 스레드 부담을 줄이는 방향의 사례로 읽을 수 있다. 다만 SVG 필터도 대형 이미지·복잡한 필터 체인에서는 렌더링 비용이 들 수 있어, 두 글을 "항상 브라우저 네이티브가 가볍다"는 결론으로 단순화하진 않는다.

## 호스피탈리티 / CRS 적용 포인트

**직접 적용은 멀다.** CRS/PMS는 이미지 보정이 핵심 업무가 아니라, 온다 제품 중 객실 사진·프로모션 배너 편집 기능이 있다면 참고할 만한 정도다. 전이 가능한 일반 원칙만 남기면: ***"클라이언트 사이드 실시간 편집 기능이 필요할 때, 서버 왕복이나 무거운 이미지 처리 라이브러리보다 먼저 브라우저 표준 API(CSS/SVG 필터)로 해결 가능한지 검토한다"*** 정도다.
