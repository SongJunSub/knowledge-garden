# 왜 더 많은 개발자가 "플랫폼을 활용"하지 않을까 (Nolan Lawson)

> 출처: [Why don't more developers "use the platform"?](https://nolanlawson.com/2026/10/03/why-dont-more-developers-use-the-platform/) (Read the Tea Leaves, Nolan Lawson) · GeekNews(id=34753) 경유 · 정리일 2026-10-05

> **출처 한계**: `news.hada.io`와 `nolanlawson.com` 모두 이번 세션 egress 차단으로 직접 열지 못했다(`web.archive.org` 미러 시도도 이 환경에서는 지원되지 않았다). 이 노트는 Slack 발췌 5줄과, WebSearch가 반환한 복수의 독립 스니펫(daily.dev 재배포 제목·날짜, Lobsters 제출 페이지 메타데이터, 저자 블로그 태그 페이지 존재 확인)을 교차확인해 재구성했다. 저자가 Nolan Lawson(전 Microsoft Edge·PouchDB 관련 작업으로 알려진 웹 플랫폼 엔지니어)이라는 것, 게시일이 2026-10-03이라는 것은 검색 결과 메타데이터로 확인했지만, 원문의 정확한 문장·예시 코드·전체 논증 순서는 대조하지 못했다. hada 댓글 수는 확인 불가이며, Lobsters에 별도 제출 스레드가 존재한다는 것만 확인했을 뿐 그 댓글 논조는 확보하지 못했다.

## 한 줄 요약

**브라우저의 기본 기능을 쓰면 직접 만든 JavaScript보다 성능·사용성이 나을 가능성이 높은데도, 개발자들이 "플랫폼을 활용"하지 않는 데는 역사적 지원 격차·익숙한 도구·직접 만드는 즐거움(IKEA 효과)이 함께 작용한다는 게 이 글의 진단이다. 라이브러리 생태계는 브라우저가 못 하던 기능의 빈틈뿐 아니라, 사용 편의성과 문서의 빈틈까지 메워왔다 — MDN이 자리잡기 전까지 네이티브 웹 API 문서는 블로그·StackOverflow·CSS-Tricks에 흩어져 있었던 반면, npm 패키지는 친절한 README와 예제·스크린샷을 갖추고 있었다.**

## 핵심 포인트

- **역사적 이유가 가장 근본적이다** — 가장 명백한 이유는 역사적인 것이다. ***오랫동안 브라우저는 그 위에 쌓인 생태계를 뒤따라가기만 했고***, 그래서 직접 만드는 게 합리적인 선택이었다. jQuery 같은 라이브러리가 브라우저가 아직 구현하지 못한 기능의 빈틈을 메웠던 시절의 습관이 그대로 남아있다는 것.
- **익숙함의 관성** — npm에서 React 컴포넌트를 찾는 데 익숙해지면, 문제의 성격과 무관하게 ***그게 먼저 손이 가는 도구***가 된다. 이건 능력 부족이 아니라 순수한 습관의 문제다.
- **문서 격차가 라이브러리 쪽으로 저울을 기울였다** — 많은 npm 패키지는 애정을 들인 README나 예제·튜토리얼·스크린샷을 갖춘 웹사이트를 갖고 있다. 반면 ***MDN이 "가야 할 곳"으로 자리잡기 전까지 웹 플랫폼 문서는 블로그·StackOverflow·CSS-Tricks 같은 사이트에 흩어져 있었다*** — 같은 기능이라도 라이브러리 쪽이 "찾기 쉬운 답"을 먼저 내줬다.
- **IKEA 효과 — 직접 만드는 게 재밌고, 내 코드에 애착이 생긴다** — 어떤 유형의 개발자에게는 직접 만드는 과정 자체가 더 재밌고, 그 결과물이 오히려 추론하기 쉬울 수 있다. 한 번 뭔가를 직접 만들고 나면, ***자기가 만든 코드를 유지·수정하고 싶어하는*** 심리적 애착(IKEA 효과)이 생긴다.
- **직접 구현이 플랫폼을 깊이 배우는 계기가 되기도 한다** — 완전하지 않은 결과물을 낳더라도, 직접 구현해보는 과정 자체가 플랫폼을 더 깊이 이해하게 만드는 학습 경험이 된다는 양면성도 짚는다.
- **CSS의 과거 표현력 부족, React 생태계의 분업** — 과거 CSS가 표현할 수 없던 것들의 공백도 한몫했고, 많은 React 개발자들은 JSX·React 관용구를 선호해 로우레벨 DOM API가 "낯설다"고 느끼면서도, 그 API를 감싸 더 익숙한 형태로 패키징해주는 하위 레벨 라이브러리는 기꺼이 쓴다 — ***플랫폼 API를 더 능숙한 사람이 감싸서, 덜 능숙한 사람에게 익숙한 형태로 전달하는 자연스러운 분업***이 생긴다는 관찰이다.

## 인상 깊은 문장

> "Once you've built something yourself, there's a kind of IKEA effect where you want to maintain and tinker with your own homemade code."
> (WebSearch 스니펫 재구성 — 여러 소개 글이 동일 표현으로 인용해 원문 취지에 가깝다고 판단했으나, 원문 페이지를 직접 대조하지는 못했다.)

> "Until MDN became cemented as the go-to place for web documentation, documentation for the web platform was scattered across blogs, StackOverflow, and sites like CSS Tricks."
> (WebSearch 스니펫 재구성.)

## 댓글

**hada 댓글 수는 확인하지 못했다**(`news.hada.io` 차단). Lobsters에 별도 제출 스레드(`lobste.rs/s/srduzv/...`)가 존재한다는 것은 검색으로 확인했지만, `lobste.rs` 역시 이 세션에서 egress 차단이라 ***실제 댓글 논조·투표 수는 확보하지 못했다.*** 정직하게 감안할 점 — (1) 이 글은 저자 자신이 웹 플랫폼 엔지니어로서 가진 입장(플랫폼 활용 옹호)이 녹아있을 수 있는 에세이 성격의 글이다. "플랫폼이 이제 충분히 좋아졌다"는 전제 자체가 모든 기능·모든 브라우저에 똑같이 적용되는지는 원문을 직접 대조하지 않고는 검증할 수 없다. (2) React 생태계 부분의 "자연스러운 분업" 서술은 긍정적 균형점처럼 읽히는데, 이게 저자의 결론인지 비판적 지적인지는 스니펫만으로는 어조를 판별하기 어려웠다.

## 내 생각 · 적용점

### 핵심 전이 1 — [[2026-05-21-susam-dont-roll-your-own-web-ui]]가 세운 "원칙"에, 이 글은 "왜 원칙대로 안 되는가"라는 현실을 짝지운다

Susam의 글은 crypto의 "don't roll your own" 원칙을 웹 UI로 확장해, 브라우저 기본 스크롤·`<a href>` 탐색·표준 비밀번호 필드·네이티브 날짜 선택기를 직접 구현하지 말라는 처방을 내렸다. 그 글은 "무엇을 하지 말아야 하는가"를 다뤘다면, 이 글은 "그런데 왜 다들 그렇게 하고 있는가"라는 뒷이야기를 메운다 — 역사적 습관·문서 격차·IKEA 효과라는 ***심리적·생태계적 설명***이다. 두 글을 합치면 "원칙은 명확한데 실천이 안 되는 이유"에 대한 꽤 완전한 그림이 그려진다. 다만 Susam의 글이 댓글로 짚었던 "맥락 의존"(Safari 날짜 선택기가 고객 지원 문제의 1/3을 차지한다는 실측 데이터)은 이 글의 "역사적 지원 격차"라는 설명과 정확히 들어맞는다 — 플랫폼 기능이 실제로 불완전했던 시절의 흔적이 지금도 고객 지원 비용으로 남아있다는 것.

### 핵심 전이 2 — [[2026-08-24-small-native-web-tricks-worth-remembering]]은 이 글이 말하는 "문서 격차"가 메워지고 있다는 구체적 증거다

HTMLcat 노트가 다룬 사이트는 "기능 + 예제 + 캐비어트"라는 3칸 구조로 네이티브 웹 기능(`dialog`, Popover API, `inert`, `:has()` 등)을 라이브러리 README처럼 친절하게 설명한다. 이건 이 글이 지적한 "라이브러리는 친절한 문서를 갖췄지만 플랫폼 문서는 흩어져 있었다"는 격차를 ***플랫폼 쪽에서 직접 메우려는 시도***로 읽을 수 있다. HTMLcat 같은 사이트가 늘어날수록, 이 글이 진단한 "문서 격차로 인한 라이브러리 선호"라는 이유 하나는 점점 약해질 가능성이 있다 — 다만 역사적 습관과 IKEA 효과라는 나머지 두 이유는 문서 개선만으로는 해결되지 않는다는 한계도 같이 보인다.

### 핵심 전이 3 — [[2026-07-06-if-youre-a-button-one-job]]과는 "직접 구현이 꼭 나쁜 결과를 낳지는 않는다"는 지점에서 가볍게 연결된다

버튼 하나의 반복 입력 처리(iPhone은 버퍼링, Nothing Phone은 무시)를 다룬 그 노트는, 네이티브 플랫폼끼리도 같은 문제에 서로 다른 답을 낸다는 걸 보여줬다. 이 글이 말한 "직접 구현이 불완전한 결과를 낳기도 하지만 플랫폼을 깊이 배우는 계기가 된다"는 양면성과 가볍게 공명한다 — 플랫폼 기본값 자체도 완벽한 정답이 아니라 여러 구현 중 하나일 뿐이라는 걸 상기시키는 정도의 연결이라, 억지로 깊게 묶지는 않는다.

## 호스피탈리티 / CRS 적용 포인트

**이 글의 소재(브라우저 네이티브 API vs JS 라이브러리)는 B2B CRS 백엔드·어드민 UI에 간접적으로만 닿는다 — 직접 적용은 다소 멀다.** 다만 전이 가능한 원칙 하나는 분명하다. ①CRS Admin·PickMe 같은 내부·파트너용 웹 UI를 만들 때, "이 기능을 라이브러리로 가져올까, 네이티브로 직접 쓸까"를 결정하는 순간마다 이 글의 세 가지 이유(지원 격차가 실제로 있는가 / 익숙함 때문에 선택하는가 / 직접 만드는 재미 때문에 선택하는가)를 자문해보면, "습관이라서 라이브러리를 쓴다"는 결정과 "실제로 플랫폼이 못 해줘서 라이브러리를 쓴다"는 결정을 구분하는 데 도움이 된다 — 전자라면 번들 크기·의존성 비용을 줄일 기회가 있다는 뜻이다. ②날짜 선택기·모달(`dialog`)·팝오버처럼 [[2026-08-24-small-native-web-tricks-worth-remembering]]이 다룬 기능들은 호텔사 어드민 화면에서도 흔히 쓰이는 UI 패턴이라, 신규 기능 개발 시 네이티브 우선 검토 체크리스트에 그대로 올릴 만하다.

**Claude 활용과의 직접적 접점은 약하다.** 이 글은 AI 코딩이나 에이전트 사용법을 다루지 않는, 순수한 웹 플랫폼 에세이다 — 다만 "라이브러리를 반사적으로 추가하기 전에 플랫폼 기본 기능으로 되는지 먼저 확인하라"는 습관은, Claude Code에게 새 UI 기능을 요청할 때 "불필요한 의존성 추가하지 말고 네이티브 API로 먼저 시도해달라"고 프롬프트에 명시하는 식으로 가볍게 옮겨볼 수는 있다.
