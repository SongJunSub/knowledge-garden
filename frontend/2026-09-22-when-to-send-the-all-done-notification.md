# '다 됐습니다' 알림, 대체 언제 보내야 맞나

> 출처: [flex 기술 블로그](https://flex.team/blog/2026/09/22/backend43) · Slack TechArticles 경유 · 정리일 2026-09-22
>
> **출처 한계**: `flex.team` egress 차단으로 원문 접근 불가. Slack GN⁺ 발췌(4개 불릿, 마지막이 "공유 자원을 기준으로 삼으면 데이터가 갱신될 때 완료 판정이 왜곡될 수 있어 기준 설정에 주의가 필요함"으로 온전히 끝남)로 재구성했다. flex의 다른 기술 블로그 글들(가든에 이미 여러 개 정리됨)과 마찬가지로 실제 프로덕션 트러블슈팅 경험담으로 보이나, 세부 수치·아키텍처는 원문 확인이 필요하다.

## 한 줄 요약

**배치 작업 완료 알림이 실제 결과 반영 시점보다 빠르게 발송되는 문제는 "처리 완료"와 "사용자가 결과를 확인할 수 있는 시점" 사이의 간극을 놓쳐서 생기며, 이를 해결하려면 단순히 처리 건수를 세는 대신 사용자가 실제로 조회할 경로를 직접 확인하는 프로브 방식을 도입해야 한다 — 이때 공유 자원을 완료 판정 기준으로 삼으면 그 자원이 다른 이유로 갱신될 때 완료 판정 자체가 왜곡될 수 있다.**

## 핵심 포인트

- **완료 알림이 실제 반영보다 먼저 나가는 문제** — 배치 작업 완료 알림이 ***실제 결과 반영 시점보다 빠르게 발송되는 문제***로 인해 사용자 경험이 저해된다 — "다 됐다"는 알림을 보고 확인하러 갔는데 아직 반영되지 않은 상태를 마주치는 전형적인 비동기 시스템의 함정이다.
- **"처리 완료"와 "확인 가능 시점" 사이의 간극을 측정해야 한다** — 처리 완료 시점과 사용자가 결과를 확인하는 시점 사이의 ***간극을 이해하고 이를 정확히 측정***하는 것이 중요하다.
- **건수 세기의 한계 → 실제 조회 경로를 확인하는 프로브 방식** — 단순히 처리 건수를 세는 방식은 비동기 구조에서 한계가 있어, ***실제 조회 경로를 확인하는 프로브(probe) 방식***을 도입했다 — 즉 "N건을 처리했다"는 내부 카운터가 아니라 "사용자가 보게 될 화면·API가 실제로 최신 데이터를 반환하는가"를 직접 찔러보고 확인하는 방식이다.
- **공유 자원을 완료 기준으로 삼을 때의 함정** — 공유 자원을 기준으로 삼으면 ***데이터가 갱신될 때 완료 판정이 왜곡***될 수 있어 기준 설정에 주의가 필요하다 — 여러 작업이 같은 자원을 공유하면, 다른 작업의 갱신이 마치 내 작업이 끝난 것처럼 오판되는 경쟁 조건이 생길 수 있다는 뜻으로 읽힌다.

## 인상 깊은 문장

> "단순히 처리 건수를 세는 방식은 비동기 구조에서 한계가 있어 실제 조회 경로를 확인하는 프로브 방식을 도입함."

## 내 생각 · 적용점

### 핵심 전이 — 가든의 flex 기술 블로그 계열에 "완료를 어떻게 정의할 것인가"라는 실무적 문제를 추가

가든에는 이미 [[2026-09-15-flex-transactional-event-listener-silent-ignore]](트랜잭션 이벤트 리스너가 조용히 무시되는 문제), [[2026-09-08-flex-non-isolated-test-agent-trust]], [[2026-08-25-flex-scheduled-trigger-outside-app-lifecycle]], [[2026-08-18-flex-modules-agents-read-less]] 등 flex의 비동기·이벤트 기반 아키텍처 트러블슈팅 사례가 여러 개 쌓여 있다. 이 글이 더하는 것은 ***"내부적으로는 완료됐지만 사용자 관점에서는 아직 완료가 아니다"***라는 최종 일관성(eventual consistency) 문제를 사용자 경험(알림 타이밍) 관점에서 다룬다는 점이다 — 이는 [[2026-09-15-flex-transactional-event-listener-silent-ignore]]가 다룬 "트랜잭션 커밋과 이벤트 발행 사이의 타이밍 문제"와 근본적으로 같은 종류의 함정(내부 상태와 외부에서 관찰 가능한 상태 사이의 시차)이 다른 층위(알림 UX)에서 반복된 것으로 볼 수 있다.

## 호스피탈리티 / CRS 적용 포인트

CRS·PMS의 배치 작업(대량 예약 임포트, 야간 정산, 요금 일괄 변경) 완료 알림에 정확히 적용되는 사례다 — "N건 처리 완료"라는 내부 카운터 기반 알림 대신, 실제로 프런트 데스크 직원이 조회할 화면(예약 목록, 정산 리포트)이 최신 데이터를 반환하는지 프로브로 확인한 뒤 알림을 보내는 방식으로 바꾸면, "알림은 왔는데 아직 반영 안 됨" 문의를 줄일 수 있다. 특히 여러 지점이 공유하는 재고·요금 테이블을 완료 기준으로 삼을 때는, 다른 지점의 갱신이 완료 판정을 왜곡하지 않는지 반드시 점검해야 한다.
