# 당신이 안 보는 사이 프론트엔드에 무슨 일이 있었나 (David Poblador) — 모든 도구는 흉터 조직, 44미터를 파내려가 도착한 곳은 20년 전 현관

> 출처: [What Happened to the Frontend](https://davidpoblador.com/deep-dives/what-happened-to-the-frontend/) (David Poblador · GeekNews GN⁺ 요약) · 정리일 2026-07-20

## 한 줄 요약

**2008년경 프론트엔드를 떠난 사람에게 20년 변화를 설명하는 글. 중심 은유는 "모든 도구는 진짜 문제 위에 생긴 흉터 조직(scar tissue) — 누군가 진짜 문제를 만났고, 해결책을 만들었고, 그 해결책이 다음 문제를 만들었다"이다. jQuery→프레임워크→빌드→툴링 군비경쟁→서버렌더링 귀환→엔지니어링 도구→배포→AI의 8단계(44미터 "내림")를 파내려가면, 2026년 최전선은 '서버에서 HTML 렌더·최소 JS·웹 플랫폼 활용'으로 돌아와 있다 — 2008년 PHP 파일과 닮았지만 최적화된 형태다. 교훈은 셋: ①복잡성은 임의적이지 않다(각 도구는 정당한 상처 위의 흉터), ②구조를 지탱하는 20%만 이해하면 나머지 80%는 골라 쓰는 뷔페다, ③AI가 코드를 써도 그 코드가 8개 레이어를 암묵적으로 가정하므로 무엇이 나왔는지 이해해야 한다.**

## 핵심 포인트

- **중심 은유: 흉터 조직** — *"모든 도구는 실제 문제 위에 생긴 흉터 조직이다. 누군가 진짜 문제를 맞닥뜨렸고, 해결책을 만들었으며, 그 해결책이 다음 문제를 만들고, 그것도 해결책을 얻었다."* 도구를 "자의적"이라 비판하는 입장을 거부하고 **인과의 사슬**로 본다.
- **① jQuery/AJAX (2006–2010)** — 문제: 리로드 없이 부분만 바꾸고 싶다(XHR 호환성 악몽). 새 문제: 데이터가 JS 변수 *와* 화면에 동시 존재 → 수동 동기화(*"하나라도 빠지면 UI가 거짓말을 한다"*).
- **② 프레임워크/선언적 UI (2010–2015)** — 문제: 수동 DOM 동기화를 멈춰줘. 해결: **선언적 UI**("어떻게 보여야 할지 기술하면 프레임워크가 단계를 생각"). React(JSX+가상DOM)·Vue·Angular·Svelte·Solid. 새 문제: 버튼 22바이트에 **React 런타임 45KB**, 컴포넌트가 런타임 없이는 존재 불가 → **빌드 단계 필요**.
- **③ 빌드 스텝 (2012–2018)** — 문제: 왜 이제 파일을 그냥 못 열어(JSX·ES6+를 옛 브라우저가 모름). 해결: Babel(트랜스파일)+Webpack(번들·minify·tree-shake). 새 문제: **`node_modules`("우주에서 가장 무거운 물체"), 기본 프로젝트가 25만 파일**.
- **④ 툴링 군비경쟁 (2018–2024)** — 문제: 빌드 90초, webpack 설정은 암호문. 해결: Go·Rust 재작성 — **esbuild(10~100배)·SWC·Vite(HMR)**. (복잡성은 늘되 *성능*은 해결.)
- **⑤ 서버 렌더링 귀환 (2014–2026)** — 문제: 빈 흰 화면·Google이 못 봄(역설: 2008년으로 회귀). 해결: SSR·SSG·ISR·메타프레임워크(Next·Astro·Nuxt). 새 문제: **하이드레이션 — *"한 끼를 두 번 산다: 서버에서 한 번, 브라우저에서 한 번."*
- **⑥ 엔지니어링 도구 (2015–2026)** — 문제: 리팩터 못 함·같은 드롭다운 반복. 해결: **TypeScript**(버그 예방)·**Tailwind**("조용히 가장 생산적")·**shadcn/ui**(설치 아닌 복사)·TanStack Query·Zustand·Zod·Vitest·Playwright. 2026년 버튼은 *47개 레이어 뒤*에서 90바이트지만 접근성·타입·디자인 토큰 내장.
- **⑦ 배포 (2015–2026)** — 문제: 인터넷에 어떻게 올려(FTP 악몽). 해결: **git push = 자동 배포**(Vercel·Netlify·Cloudflare), PR별 프리뷰 URL, 서버리스·엣지. **저자 평: 이 부분만 "명백히 2008년보다 낫다."**
- **⑧ AI 코드 생성 (2023–2026)** — 문제: 기계가 React를 대신 써줄 수 없나. 해결: v0·Lovable·Bolt·Cursor·Claude Code. **"Vibe Coding"**(Karpathy). 새 문제: **생성된 코드는 위 8개 레이어를 암묵적으로 가정 → "로봇이 쓴 것과 당신이 이해한 것 사이의 간격."**
- **귀환** — 44미터를 파고 도착한 곳은 *"자기 자신의 현관"*: **서버 HTML(Astro·Islands·RSC) + 최소 JS + 웹 플랫폼(:has()·컨테이너 쿼리)**. 2008년 PHP와 닮았으나 최적화됨(빌드 0·의존성 0 → 최소 JS·CDN). *"산업은 거대한 원을 그렸고… 본능은 만료되지 않았다."*
- **교훈** — ①복잡성은 임의적이지 않다, ②**구조 지탱하는 20%만 이해하면 나머지 80%는 뷔페**, ③AI가 써도 무엇이 나왔는지 이해해야. *"당신이 늦은 게 아니라 일찍 온 거다."* *"이건 처방이 아니라 뷔페다."*

## 내 생각 · 적용점

### 핵심 전이 1 — "각 해결책이 다음 문제를 만든다"는 프론트엔드로 물질화된 Problem Promotion이다

이 글의 은유(*흉터 조직 — 해결이 다음 문제를 낳음*)는 오늘 정리한 [[2026-07-19-three-responses-to-problems]]의 **새 문제 승격(Problem Promotion)**(Weinberg: *"1순위를 없애면 2순위가 승격된다"*)이 **프론트엔드 스택으로 육화된 것**이다. jQuery가 리로드 문제를 풀자 동기화 문제가, 프레임워크가 그걸 풀자 빌드 문제가, 빌드가 그걸 풀자 node_modules가 승격됐다. 그리고 weekly [[2026-07-13-weekly-366]]의 *"부채는 사라지지 않고 이동한다"*와 정확히 같은 물리학이다 — **복잡성은 제거되지 않고 다음 레이어로 밀린다.** 20년 뒤 서버 HTML로 돌아온 건 그 사슬이 한 바퀴를 돈 것이지 문제가 사라진 게 아니다.

### 핵심 전이 2 — "AI가 써도 8개 레이어를 이해해야 한다"는 이번 주 '이해가 병목'의 프론트엔드 판본

⑧레이어의 결론(*"생성된 코드는 8개 레이어를 암묵적으로 가정 → 로봇이 쓴 것과 이해 사이의 간격"*)은 이번 몇 주 최대 축과 **정확히 같은 말**이다 — [[2026-07-14-understanding-is-the-new-bottleneck]]의 *"이해가 병목"*, [[2026-07-14-why-write-code-in-2026]]의 *"AI는 좋은/나쁜 결정을 다 증폭"*, [[2026-07-19-human-in-the-loop-is-tired]]의 *"감독 피로"*가 프론트엔드에서 구체화된다. **바이브 코딩은 44미터 흉터 조직 위에서 이뤄지므로, 리뷰하려면 그 스택을 알아야 한다.** AI가 프론트엔드 진입장벽을 낮춘 게 아니라, **이해의 부담을 생성에서 검증으로 옮겼을 뿐**이다.

### 핵심 전이 3 — "구조 20% + 뷔페 80%"는 부분 이해 논제의 실전 지침

저자의 *"대성당 전체가 아니라 구조를 지탱하는 20%만 이해하라, 나머지는 뷔페"*는 [[2026-07-13-in-defense-of-not-understanding-your-codebase]]의 **부분 이해도 기술**을 프론트엔드 학습에 적용한 것이다. 이건 [[2026-07-16-teddynote-ml-study-repo]]의 *"14폴더는 지도지 길이 아니다, 한 트랙만 완주하라"*와 같은 처방 — **폭에 압도되지 말고 구조적 20%(왜 SSR인가·왜 하이드레이션인가·왜 빌드 단계인가)를 잡고, 도구 80%는 필요할 때 고른다.** 흉터의 *이유*를 알면 도구 선택은 뷔페가 된다.

### 핵심 전이 4 — 복잡성으로의 회귀가 아니라 "왜"의 회귀: 배포만 명백한 진보였다는 정직함

저자가 *"배포(⑦)만 명백히 2008년보다 낫다"*고 못 박은 건 이 글의 정직함이다 — **20년의 복잡성 대부분은 순수한 진보가 아니라 왕복이었고, 확실한 순증분은 배포·엣지뿐**이라는 것. 이건 [[2026-06-30-yagni-hidden-costs]]의 *"복잡성의 숨은 비용"*·[[2026-07-12-good-tools-are-invisible]]의 *"좋은 도구는 보이지 않는다"*(git push=배포가 투명해진 것이 진짜 진보)와 통한다. **회귀(서버 HTML)는 패배가 아니라 "본능이 만료되지 않았다"는 확인**이고, 흉터의 역사를 알아야 그 회귀가 왜 정당한지 안다.

## 호스피탈리티 / CRS 적용 포인트

온다도 프론트엔드(React/Next 계열 CRS 화면)를 다루므로 직접적이다.

- **콘텐츠성 화면 vs 앱성 화면을 나눠 스택 선택.** 저자의 필드킷대로 — **정보 위주(랜딩·문서·공개 페이지)는 서버 HTML(Astro/RSC)+최소 JS**로 가볍게, **로그인 앱(대시보드·예약 관리)은 React+Next+TS+shadcn**. CRS의 무거운 SPA가 늘 정답은 아니다.
- **AI 생성 프론트엔드는 스택 이해가 리뷰 조건(전이 2).** 바이브 코딩으로 화면을 빨리 뽑아도, 리뷰어가 하이드레이션·번들·접근성 레이어를 이해 못 하면 "UI가 거짓말"하는 버그를 못 잡는다 — 온다의 프론트 리뷰 규율에 이 스택 이해가 전제.
- **구조 20%를 팀 공유 지식으로.** 신규 프론트 팀원에게 "왜 이 도구들이 있는가(흉터의 이유)"를 먼저 가르치면, 도구 80%는 스스로 뷔페처럼 고른다(전이 3).
