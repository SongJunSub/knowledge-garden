## 한 줄 요약

**웹사이트 제작은 프롬프트 하나로 가능해졌지만 성능 비용은 사라지지 않는다 — 캐시 정책·리소스 도착 순서·메인 스레드 작업이 서버 거리보다 체감 속도를 더 좌우하며, 자동재생 영상·커스텀 폰트·캐러셀 같은 장식 요소는 결국 방문자의 시간과 데이터를 쓰는 디자인 결정이다.**

## 핵심 포인트

- 웹사이트 제작은 프롬프트 하나로 가능해졌지만, ***성능 비용은 사라지지 않으며*** 느린 페이지의 대기 시간은 방문자가 부담한다.
- 페이지 로딩 속도는 서버와의 거리, HTML 생성 방식뿐 아니라 ***캐시 정책, 리소스 도착 순서, 메인 스레드 작업***에 좌우된다.
- 자동 재생 영상, 커스텀 폰트, 캐러셀과 애니메이션은 방문자의 ***시간과 데이터를 사용하는 디자인 결정***이므로, 디자인도 성능 비용을 판단하는 데 참여해야 한다.
- 첫 화면의 주요 이미지를 작게 만들고 지연 없이 불러오며, ***네트워크와 CPU를 제한한 모바일 테스트***로 실제 체감을 확인해야 한다.

## 내 생각 · 적용점

### 핵심 전이 — "속도=설계 선택"이라는 같은 축이 반복된다

이 글의 핵심 주장("속도는 기술 문제가 아니라 디자인 결정")은 [[2026-06-08-how-is-linear-so-fast]](Linear는 어떻게 이렇게 빠른가 — 로컬 우선·필드 단위 반응성·키보드 affordance)가 보여준 "속도는 아키텍처 선택의 결과"라는 원칙과 같은 축이다. Linear 노트는 성공 사례(빠르게 만든 선택들)를 다뤘고, 이 글은 실패 사례(장식 요소가 속도를 깎아먹는 선택들)를 다룬다는 점에서 서로 보완적이다.

### 적용점

"네트워크와 CPU를 제한한 모바일 테스트로 체감을 확인한다"는 원칙은, 어떤 프로젝트든 배포 전 체크리스트에 저사양 환경 시뮬레이션 테스트를 넣는 식으로 바로 적용할 수 있다.

## 호스피탈리티 / CRS 적용 포인트

**적용 가능성 있음.** 예약엔진·채널매니저 UI에서 캐러셀·배경영상 등 장식 요소가 모바일 예약 전환율에 미치는 체감속도 비용을 판단하는 원칙으로 쓸 만하다. 특히 해외 투숙객이 느린 네트워크 환경(해외 로밍, 호텔 와이파이)에서 예약 페이지를 여는 경우가 많다는 점에서, 저사양·저속 환경 테스트는 CRS 프런트엔드에 직접 적용할 가치가 있다.
