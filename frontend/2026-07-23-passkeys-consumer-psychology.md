# Passkey는 소비자 심리를 이해 못 한 엔지니어들이 만들었다 (Nikita Bier) — 잘 만든 것과 옳은 문제를 푼 것은 다르다

> 출처: [Nikita Bier (X)](https://twitter.com/nikitabier/status/2079787406300266743) (X 프로덕트 헤드 · GeekNews GN⁺ 요약 + HN 큐레이션. 원문은 트윗이라 GN 요약 기준) · 정리일 2026-07-23

## 한 줄 요약

**Nikita Bier(X 프로덕트 헤드)가 패스키를 "마법의 가루"라 비판했다 — 사용자는 이 열쇠가 휴대폰·브라우저·OS·자기 신체 중 어디에 있는지조차 모르고, 그래서 장점을 평가하지도 반박하지도 못한다. 근본 원인은 "소비자 심리를 이해 못 한 보안 엔지니어들이 만들었기 때문". 옹호 측은 "입력하는 단어(비밀번호)가 아니라 소유한 열쇠라 훔치기 어렵고 피싱에 강하다"고 맞고, 그 말은 기술적으로 옳다. 그러나 반대 측 핵심은 UX다 — 26년차 기술자조차 "여러 기기·브라우저에서 어떻게 써야 로그인에 지장이 없는지 모르겠다", 유일 기기를 잃으면 계정에서 잠기고, 복구 경험이 미흡하며, 동기화 패스키는 대형 플랫폼 종속을 낳는다. 즉 패스키는 '비밀번호가 근본적으로 망가졌다'는 진짜 문제를 기술적으로 잘 풀었지만, 사용자가 정신 모델을 세울 수 없고 복구를 신뢰할 수 없어 채택에 실패했다 — 잘 만든 것(craft)과 옳은 문제를 사용자에게 맞게 푼 것(strategy)은 다르다.**

## 핵심 포인트

- **"마법의 가루" 비판** — *"앱이 로그인을 위해 어디에 있는지 모르는 인증 수단을 요구한다."* 패스키가 *"휴대폰/브라우저/OS/사용자의 신체 중 어디에 있는지 불명확"*하고, 사용자가 정체를 몰라 *"장점을 평가하거나 반박하기도 어려웠다."* 원인 = *"소비자 심리를 이해 못 하는 보안 엔지니어들."*
- **옹호(기술적으로 옳음)** — *"입력하는 단어가 아니라 소유한 열쇠 — 단어는 훔치기 쉽지만 열쇠는 어렵다."* **피싱 저항성**: *"가짜 로그인 페이지는 TOTP 코드를 중계할 수 있지만 패스키 질의·응답은 중계 못 한다."*
- **반대(UX·복구)** — *"유일하게 작동하는 패스키 기기를 잃으면 계정 접근도 잃는다"*(비밀번호는 기억·별도 보관, 2FA 앱은 여러 기기 가능). *"UX가 나쁘고 계정에서 잠겨 나올 가능성이 크다."*
- **정신 모델 붕괴(HN)** — *"26년차 기술자, 공개키/개인키도 이해하지만 여러 기기·브라우저에서 어떻게 써야 로그인에 지장이 없는지 모르겠다."* *"휴대폰 Safari에서 우연히 패스키를 만들면 다른 기기에서도 되는지, 동기화·기기별 추가·사이트별 개수 제한이 불분명."* **교육 부재**: *"어느 날 갑자기 버튼이 생겨 누르면 로그인될 뿐, 사용자 교육은 전혀 없었다 — 기존 비밀번호가 지워지는지, 새 기기에서 만들면 첫 기기가 잠기는지 알 수 없다."*
- **생태계 종속** — Tim Sweeney: *"패스키는 사용자를 대형 플랫폼에 묶어두는 계획."* 동기화 패스키(iCloud/1Password)는 *"모든 자격증명을 독점 클라우드에 맡기는"* 종속. 도입 동기로 비용 절감·종속 의심.
- **반론(정당함)** — *"비밀번호는 근본적으로 망가진 모델이고 사용자도 제대로 쓴 적 없다. 새 방식이 어렵다고 쉬운 문제에만 머무는 건 나쁘다 — 비판만 말고 더 나은 모델을 제시하라."*
- **실무 해결책(hada)** — **xguru: 이메일 매직링크로 가입 후 패스키 등록** → 서버에 비밀번호 0, 기기를 잃어도 **이메일로 재로그인해 새 패스키 등록**(BeeBS 방식). **null468**: 편하려면 *"모든 플랫폼 관통하는 단 하나의 패스워드 관리앱"*이 사실상 필요 = 관리자 종속 강화.

## 내 생각 · 적용점

### 핵심 전이 1 — 어제 "잘못된 싸움(craft vs strategy)"의 교과서적 사례다

이 논쟁은 어제 정리한 [[2026-07-23-sharpening-knives-for-the-wrong-fight]]의 **완벽한 실물**이다. 패스키는 *craft*(기술적 완성도 — 피싱 저항·공개키 암호)로는 탁월한데, *strategy*(사용자에게 옳은 문제를 옳게 푸는가)에서 실패했다. Maccarone의 *"만들 수 있다고 만들어야 하는 건 아니다"*·*"무엇이 존재할 가치가 있는지, 누구를 위해, 왜 지금"*을 패스키에 대면 — **엔지니어는 "비밀번호는 안전하지 않다"(자기 문제)를 풀었지만, 사용자의 job("나를 확실히 들여보내되 잠기지 않게 해줘")은 안 풀었다.** 이건 [[2026-07-22-taste-cannot-be-delegated]]의 *"선호 vs 판단"*·[[2026-07-13-how-to-kill-churn]]의 **Jobs-to-be-Done**과 같은 렌즈다 — 로그인이 사용자를 위해 하는 "일"은 보안이 아니라 *신뢰할 수 있는 접근*이고, 패스키는 후자를 흔들었다.

### 핵심 전이 2 — 좋은 인증은 보이지 않아야 한다: 패스키는 메커니즘을 가시화했다

*"열쇠가 어디 있는지 모르겠다"*는 비판의 핵심은 **패스키가 인증 메커니즘을 사용자에게 보이게 만들었다**는 것이다. 이건 [[2026-07-12-good-tools-are-invisible]]의 *"좋은 도구는 보이지 않는다"*의 정반대 — 사용자는 "어디 저장되나·동기화되나·기기 잃으면?"을 *생각하게* 됐다. 반면 비밀번호+관리자는 (근본은 취약해도) 정신 모델이 단순하다("기억하거나 관리자가 채워준다"). **인증의 UX 목표는 안전함이 아니라 안전하면서 안 보이는 것**이고, 패스키의 실패는 "정신 모델을 요구하는 순간 진 것"이라는 교훈이다 — 이 지점에서 [[2026-07-22-who-will-thrive-in-the-age-of-ai]]와 뒤집힌 방향으로 만난다(그 글은 *사용자가 판단을 유지해야* 한다지만, 인증은 *판단을 요구하지 않아야* 한다 — 도구의 위생 위치가 다르다).

### 핵심 전이 3 — 실무 정답은 "거부"가 아니라 "전체 흐름 설계": 이메일 매직링크 + 패스키

이 논쟁의 진짜 소득은 xguru의 처방이다 — **이메일 매직링크로 가입/복구 + 패스키로 일상 로그인.** 이러면 (a) 서버에 비밀번호 0(유출 위험 제거), (b) 피싱 저항(패스키), (c) **기기 분실 시 이메일로 복구**(락아웃 해소)를 동시에 얻는다. 즉 패스키의 기술적 이득을 취하되 **복구라는 job을 이메일이 메운다.** 이건 [[2026-07-23-sharpening-knives-for-the-wrong-fight]]의 *"완성도가 아니라 사용자의 job에서 출발"*의 실행이고, "패스키 vs 비밀번호"라는 이분법이 애초에 잘못된 싸움임을 보여준다 — 옳은 질문은 *"사용자의 로그인 job(들어가기·안 잠기기·안 털리기)을 각각 무엇이 가장 잘 메우나"*의 조합 설계다.

### 핵심 전이 4 — 동기화 패스키의 락인은 인증판 주권 문제

Tim Sweeney의 *"대형 플랫폼에 묶는 계획"*·동기화 패스키의 클라우드 종속은 이번 주 오픈웨이트/주권 스레드([[2026-07-21-american-ai-locked-down-losing]])의 **인증 버전**이다 — 편의(동기화)를 위해 자격증명을 독점 플랫폼(Apple/Google/1Password)에 맡기면 이식성·통제를 잃는다. 모델을 자가호스팅하는 것과 같은 논리로, **인증도 "누가 열쇠를 통제하나"가 락인 축**이다. 표준(WebAuthn)이 개방적이어도 *구현·동기화가 플랫폼에 갇히면* 개방성은 반쪽이다([[2026-07-15-usb-c-maximalist-standardization]]의 "겉은 표준인데 구현이 제각각"과 같은 형태).

## 호스피탈리티 / CRS 적용 포인트

온다는 숙박사업자·게스트 로그인을 다루므로 인증 UX가 직접 걸린다.

- **패스키를 '유일 수단'으로 내지 말 것.** CRS/게스트 로그인에 패스키를 도입하더라도 **이메일 매직링크(또는 다른 복구 경로)를 반드시 병행**(전이 3) — 기기 잃은 사업자가 정산·예약에서 잠기면 사업 손실이다. "패스키만"은 락아웃 사고 설계다.
- **로그인의 job부터 정의(전이 1).** 온다 사용자의 로그인 job은 "빠르고 확실히 들어가기 + 안 잠기기"다. 보안(피싱 저항)은 우리 관심사이지 사용자 관심사가 아님 — 사용자에게는 *보이지 않는 안전*으로 제공(전이 2).
- **정신 모델을 요구하지 않는 흐름.** "패스키가 어디 저장되나"를 사용자가 고민하게 하지 말 것 — 온보딩에서 선택지·복구를 명확히 안내하거나, 아예 매직링크 기본 + 패스키 옵트인.
- **락인 인지(전이 4).** 동기화 패스키를 쓰면 사용자가 특정 플랫폼에 묶임 — B2B 사업자엔 이식성이 중요하니 복구 경로를 플랫폼 독립(이메일/우리 서버)으로.
