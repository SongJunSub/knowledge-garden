## 한 줄 요약

**당근 "동네갖기" 서비스에서 온보딩·이벤트·안내 등 여러 오버레이가 동시에 뜨려고 경합하는 문제를, 오버레이를 띄우는 컴포넌트끼리 서로 직접 참조하는 대신 Promise 패턴으로 노출 순서를 체인처럼 관리해 해결했다고 밝히는 사례다 — 웹뷰와 네이티브 환경이 섞인 하이브리드 앱 특유의 팝업 제어 복잡도를 추상화와 비동기 스케줄링으로 다뤘다고 한다.**

## 핵심 포인트

- **문제 — 여러 오버레이가 동시에 노출을 경쟁한다** — 당근 "동네갖기" 서비스에서 ***다수의 오버레이(팝업·바텀시트 등으로 추정)가 동시에 노출***되려는 문제가 있었다고 밝힌다. 여러 기능팀이 각자의 판단으로 오버레이를 띄우면, 한 화면 위에 여러 개가 겹치거나 중요도가 낮은 것이 먼저 떠 더 중요한 안내를 가리는 전형적인 프런트엔드 UX 문제로 읽힌다.
- **해법 — 컴포넌트 간 직접 연결 대신 Promise 패턴** — ***컴포넌트 간 직접 연결 대신 Promise 패턴을 활용***해 오버레이 노출 순서를 관리했다고 한다. "A가 끝나면 B를 띄운다"는 순서를 컴포넌트끼리 서로의 존재를 알고 명시적으로 호출하는 방식이 아니라, 각 오버레이 요청을 Promise로 감싸 체인·큐 형태로 줄 세우는 방식으로 짐작된다 — 다만 정확한 API 설계(전역 큐 매니저인지, 각 화면 단위 스케줄러인지)는 확인하지 못했다.
- **웹뷰+네이티브 혼합 환경의 팝업 제어** — ***웹뷰와 네이티브 환경의 복잡한 팝업 제어 문제***를 추상화와 비동기 스케줄링으로 풀었다는 문장에서 발췌가 끝난다. 당근이 하이브리드 앱(네이티브 셸 + 웹뷰 화면 혼합) 구조라는 건 다른 당근 기술 블로그 글들에서도 반복적으로 확인되는 배경이라, 이 오버레이 문제도 "웹뷰 안에서 뜨는 오버레이와 네이티브가 띄우는 오버레이가 서로의 존재를 모른다"는 하이브리드 앱 특유의 어려움에서 비롯됐을 가능성이 있다 — 이는 추정이며 원문으로 검증되지 않았다.

## 인상 깊은 문장

> "컴포넌트 간 직접 연결 대신 Promise 패턴을 활용해 오버레이 노출 순서를 우아하게 관리함. 웹뷰와 네이티브 환경의 복잡한 팝업 제어 문제를 추상화와 비동기 스케줄링으로 해결함." (Slack 발췌 원문)

## 댓글

**GeekNews 경유 아님.** hada 댓글이나 HN/Lobsters 큐레이션 자체가 대상이 아니다. **자사 기술 블로그**이므로 "우아하게 해결했다"는 평가는 자사 서술이다. 이 노트는 세 줄짜리 봇 발췌 이상의 근거가 없다는 점이 다른 노트들보다 특히 두드러진다 — Promise 패턴의 구체 코드나 API, 도입 전후 정량적 개선(오버레이 충돌 빈도, 개발자 리뷰 시간 등)은 전혀 확인되지 않았다. "우아하게"라는 표현 자체가 자사 마케팅적 수사일 가능성을 열어둔다.

## 내 생각 · 적용점

### 핵심 전이 1 — [[2026-09-22-when-to-send-the-all-done-notification]]과 같은 축, "내부 상태와 사용자가 보는 화면 사이의 시차"를 다루는 또 다른 사례

flex의 "다 됐습니다 알림" 노트는 ***"처리 완료"와 "사용자가 실제로 확인할 수 있는 시점"*** 사이의 간극을 다뤘다. 이 글이 다루는 오버레이 경합 문제는 그 간극의 거울상이다 — flex 사례가 "알림을 언제 보낼 것인가"라는 **타이밍 결정**의 문제였다면, 당근 사례는 "여러 비동기 이벤트가 동시에 화면에 개입하려 할 때 그 순서를 누가 조정하는가"라는 **경합 조정**의 문제다. 둘 다 근본적으로는 여러 비동기 소스가 각자의 시점에 사용자 화면에 개입하려 할 때, 그 개입을 어떻게 줄 세울 것인가라는 같은 종류의 설계 질문에 대한 서로 다른 답으로 읽을 수 있다.

### 핵심 전이 2 — [[2026-08-20-daangn-auth-evolution]]과 같은 회사, "표준 위에 기능을 얹어두면 나중에 확장이 싸다"는 원칙이 이 글에도 걸릴 가능성

당근 인증 진화 노트가 남긴 교훈은 ***"OAuth 표준 위에 SSO를 만들어뒀더니 MCP의 OAuth 2.1 요구가 왔을 때 확장으로 끝났다"***는 것이었다. 이 오버레이 제어 글에서 "컴포넌트 간 직접 연결 대신 Promise 패턴"을 택한 것도 비슷한 방향성으로 읽을 수 있다 — 오버레이를 띄우는 쪽과 그걸 조율하는 쪽이 서로 직접 참조(강한 결합)하는 대신, Promise라는 표준적인 비동기 어휘 위에 느슨하게 결합해두면 새로운 오버레이 종류가 추가될 때마다 조율 로직을 다시 짤 필요가 없다는 이점이 있을 것으로 짐작된다 — 다만 이 연결은 두 글 모두 원문을 완전히 확인하지 못한 상태에서 짐작으로 세운 것이라, 억지로 당기지 않고 느슨한 유비로만 남겨둔다.

## 호스피탈리티 / CRS 적용 포인트

온다의 CRS 관리자 콘솔이나 파트너 대시보드도 "동시 예약 알림", "요금 변경 경고", "온보딩 가이드" 같은 여러 오버레이/모달이 한 화면에서 경합할 수 있는 구조라면, ***"오버레이를 띄우려는 각 기능이 서로를 직접 알 필요 없이, 중앙의 큐/스케줄러가 순서를 정한다"***는 이 글의 원칙 방향은 참고할 만하다. 다만 이 노트는 구체 구현을 전혀 확인하지 못한 상태이므로, "Promise 패턴으로 오버레이 큐를 관리한다"는 방향성 이상의 것(구체 API 설계 등)을 이 노트 하나로 CRS에 그대로 옮기는 건 이르다 — 직접 적용을 검토하려면 원문 확인이 먼저 필요하다.
