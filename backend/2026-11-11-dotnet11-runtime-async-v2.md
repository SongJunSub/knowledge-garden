# .NET 11 런타임의 새로운 기능

> 출처: GeekNews [id=36957](https://news.hada.io/topic?id=36957) 경유, 원문 미확인 · 정리일 2026-11-11
>
> **출처 한계(일부 완화)**: `news.hada.io`가 egress 차단돼 원문, hada 댓글은 못 봤다. 다만 WebSearch로 .NET 11 Runtime Async V2를 다룬 Microsoft Learn 공식 문서 등을 찾아 핵심 사실을 교차확인했다. Runtime Async V2는 Preview 2(2026년 3월 10일 출시)에서 도입됐고, 프로젝트 파일에 기능 플래그를 추가해 옵트인하며, .NET 11 GA는 2026년 11월 예정이다. 다만 "50% 빨라짐" 같은 구체적 성능 수치 주장은 Microsoft 1차 자료가 아니라 2차 블로그에서만 나와, 이번 검색으로도 확인하지 못했다. 이 부분은 Slack 발췌와 마찬가지로 미검증으로 남긴다.

## 한 줄 요약

**.NET 11이 Runtime Async V2를 미리보기로 도입해 컴파일러가 생성하던 비동기 상태 머신을 런타임이 직접 관리하게 바꿨다. 스택 추적, 디버깅이 개선되고 JIT, SIMD 최적화 여지가 커지지만, 그 대가로 x86-64-v2, ARM64 LSE 같은 더 높은 최소 CPU 요구사항을 치른다.**

## 핵심 포인트

- **컴파일러에서 런타임으로 이동(교차확인됨)**: 기존에는 컴파일러가 async/await를 상태 머신 클래스로 변환해 생성했는데, Runtime Async는 그 작업을 런타임이 직접 중단, 재개 관리로 처리한다. 목적은 스택 추적을 깨끗하게 하고 비동기 처리 오버헤드를 줄이는 것.
- **최소 CPU 요구사항 상향(Slack 발췌)**: x86/x64는 x86-64-v2, Windows Arm64는 LSE가 필요해지며, 이 기준을 못 채우는 구형 하드웨어에서는 아예 실행되지 않는다고 한다. 런타임 전체가 이 설정으로 컴파일된다는 점과 맞물려, 이번 상향은 일부 기능이 아니라 플랫폼 전체의 전제 조건 변화로 보인다.
- **JIT, SIMD 최적화(Slack 발췌)**: 불필요한 경계 검사, 가상 호출을 줄이고, 지원 CPU에서 Half 연산에 하드웨어 FP16 명령을 활용한다고 설명.
- **일정(교차확인됨)**: Preview 2가 2026년 3월, GA는 2026년 11월 예정으로 이번 Slack 공유 시점과 거의 맞물린다. GA 임박 시점의 새 기능 소개 글로 추정.

## 내 생각 · 적용점

### 핵심 전이 1 — "문법은 그대로, 런타임만 조용히 바뀐다"는 같은 패턴이 Java 27에서도 있었다

[[2026-09-16-java-27-ga-release]]는 언어 문법 변화 없이 G1을 전 환경 기본 GC로, 객체 헤더를 압축하는 식으로 런타임 레벨에서 조용히 개선되는 릴리스였다. .NET 11의 Runtime Async도 똑같다. async/await 문법은 그대로인데 그 밑에서 작동하는 메커니즘이 컴파일러에서 런타임으로 옮겨간다. 두 생태계 모두 언어 설계를 더 추가하기보다 이미 있는 문법의 런타임 구현을 재설계하기로 수렴하고 있다는 신호로 볼 수 있다.

### 핵심 전이 2 — 런타임을 강화하는 방향과 런타임을 없애는 방향이 정반대로 공존한다

[[2026-10-13-turbopython-native-compiler]]는 Python 문법에 소유권 검사를 더해 CPython 런타임, GC 없이 네이티브 컴파일로 가는 사례였다. 런타임을 아예 제거하는 방향. .NET 11은 정반대다. 컴파일러가 하던 일을 런타임에 더 많이 맡긴다. 같은 시기 두 생태계가 런타임을 없앨 것인가, 런타임을 더 똑똑하게 만들 것인가라는 정반대 전략을 각자 고르고 있다는 게 흥미롭다.

## 호스피탈리티 / CRS 적용 포인트

**직접 적용은 멀다.** 온다 스택이 .NET 기반이 아니면 이 변화는 직접 영향이 없다. 다만 전이 가능한 원칙 하나: 런타임 메이저 업그레이드가 최소 하드웨어 요구사항을 올릴 수 있다는 걸 미리 점검하는 습관. 어떤 스택이든 컴파일러, 런타임이 조용히 바뀌는 메이저 버전을 올릴 때는 타겟 환경이 새 최소 요구사항을 충족하는지 먼저 확인해야 한다는 교훈은 일반화된다.
