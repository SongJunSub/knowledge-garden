# 일부 봇을 차단하는 방법 (nochan.net) — 진짜 경고는 "차단하는 법"이 아니라 "무엇을 함께 잃는가"

> 출처: [How To Block Some Of The Bots](https://nochan.net/b/Internet-Crap/20260606-How-To-Block-Some-Of-The-Bots/) (nochan.net · GeekNews GN⁺ 요약 + HN 큐레이션) · 정리일 2026-08-02

## 한 줄 요약

**CDN 없이 **HTTP 프로토콜·IP 대역·클라이언트 신호·TCP 특성·TLS 지문·콘텐츠 압축**을 조합해 구현이나 설정이 부실한 봇 대부분을 차단하는 실무 가이드다. 그런데 저자가 이 글에서 가장 강조하는 건 기법이 아니라 **부작용에 대한 반복적 경고**다 — ***"모든 방법은 선택적으로 조정해야 하며, 1~3년치 접근 로그를 먼저 분석하지 않으면 VPN 사용자·검색엔진·CDN·학교·도서관·특정 언어 사용자를 함께 차단할 수 있다."*** **HTTP/1.1 클라이언트와 데이터센터 AS/CIDR 대역을 차단**하면 많은 봇이 제거되지만, ***"GoogleBot을 비롯한 검색엔진과 정상적인 데이터센터 이용자도 제외될 수 있다."*** **Nginx 헤더 검사·nftables의 TCP 윈도 크기/MSS/TTL 필터**는 단순 크롤러를 줄이지만, ***"LTE/VPN/Windows 같은 정상 환경에서 오탐이 발생할 수 있다."*** 장기적으로는 **JA4 TLS 지문 탐지**와 Brotli 전용 응답을 대안으로 제시하지만, **완전한 차단은 보장하지 않으며 수익을 내는 서비스에는 사용하지 말라**고 명시적으로 경고한다.**

## 핵심 포인트

- **핵심 기법 조합** — **HTTP 프로토콜 버전, IP 대역(AS/CIDR), 클라이언트 신호, TCP 특성, TLS 지문(JA4), 콘텐츠 압축(Brotli 전용 응답)**을 조합.
- **가장 중요한 경고** — ***"1~3년치 접근 로그를 먼저 분석하지 않으면 VPN 사용자, 검색엔진, CDN, 학교, 도서관, 특정 언어 사용자를 함께 차단할 수 있다."***
- **HTTP/1.1·데이터센터 대역 차단의 트레이드오프** — 많은 봇을 제거하지만 ***"GoogleBot을 비롯한 검색엔진과 정상적인 데이터센터 이용자도 제외될 수 있다."***
- **TCP/헤더 필터의 트레이드오프** — Nginx 헤더 검사, nftables TCP 윈도/MSS/TTL 필터는 단순 크롤러·스캐너를 줄이지만 ***"LTE/VPN/Windows 같은 정상 환경에서 오탐 발생 가능."***
- **장기 대안과 명시적 한계** — **JA4 TLS 지문 탐지 + Brotli 전용 응답**을 제시하되, **완전한 차단은 보장하지 않으며 수익 서비스에는 사용하지 말라**고 저자 스스로 경고.

## 내 생각 · 적용점

### 핵심 전이 1 — 이 글의 진짜 메시지는 기법이 아니라 [[2026-08-02-hugging-face-tailscale-agent-breach]]에서 다룬 "폭발 반경을 먼저 계산하라"는 원칙의 방화벽 버전이다

Hugging Face 사건 노트에서 나는 *"자격증명이 새면 폭발 반경이 얼마나 큰가를 먼저 재라"*고 정리했다. 이 글도 같은 구조다 — **봇 차단 규칙 하나하나가 "정당한 트래픽까지 함께 차단할 폭발 반경"**을 갖는다. HTTP/1.1 차단은 GoogleBot을, TCP 지문 필터는 VPN 사용자를 함께 걸러낸다. **"1~3년치 로그 분석"이라는 요구사항은 정확히 "이 규칙을 켜기 전에 폭발 반경을 재라"는 명령**이다. 이건 내 dry-run 게이트 원칙 — *"되돌리기 어려운 작업은 실제 실행 전에 dry-run 산출물을 생성한다"*와 같은 구조다: **봇 차단 규칙을 실제로 적용(block)하기 전에 로그로 시뮬레이션(dry-run)해서 무엇이 걸리는지 먼저 확인해야 한다.**

### 핵심 전이 2 — "AI 봇 크롤링으로 CPU 과도 사용"은 이번 배치의 [[2026-08-02-tv-streaming-stick-fraud-botnet]]와 같은 계보의 리소스 남용 문제다

댓글에서 나온 실제 피해 사례(공유 호스팅에서 AI 봇이 CPU를 과도 사용)는, 이번 배치의 TV 스트리밍 스틱 노트에서 다룬 **"소유자가 관찰하지 않는 자원을 몰래 소비한다"**는 패턴과 같은 종류다. 다른 점은 TV 스틱 사건은 명백히 악의적 설계였고, AI 크롤러의 CPU 과사용은 대개 **악의보다는 무분별함(rate limiting 부재, 재시도 로직 미흡)**에서 온다는 것 — 하지만 **피해받는 쪽 입장에서는 원인이 악의든 무분별함이든 결과(자원 소진)는 같다.**

### 핵심 전이 3 — "80개 정규식으로 모든 트래픽 차단"은 이번 배치의 [[2026-08-02-refactoring-economic-benefit]]가 보여준 "복잡성이 결국 관리 비용으로 돌아온다"는 원칙의 반례처럼 보이지만 실은 같은 교훈이다

댓글의 "80개 정규식"이라는 실전 규모는 인상적이지만, **80개의 규칙을 유지보수하는 비용**은 만만치 않을 것이다 — 새 봇이 나타날 때마다 규칙을 추가해야 하고, 오탐이 생기면 어떤 규칙이 원인인지 디버깅해야 한다. Fowler의 리팩터링 노트가 보여준 원칙(**응집도 높은 작은 단위로 정리하면 유지보수 비용이 줄어든다**)을 봇 차단 규칙에도 적용할 수 있다 — **80개의 임시방편 정규식보다, 소수의 잘 설계된 계층적 규칙(TLS 지문 → IP 평판 → 행동 패턴)이 장기적으로 관리하기 쉽다.**

### 핵심 전이 4 — 정직한 급소: "완전한 차단은 보장 안 됨"이라는 저자의 정직함이 이 글의 가장 큰 가치다

이 글에서 가장 신뢰할 만한 부분은 화려한 기법이 아니라 **저자가 스스로 이 방법의 한계를 명확히 인정한 것**이다 — [[2026-08-02-gemini-robotics-2]]·[[2026-08-02-openai-ten-advances-in-mathematics]]에서 다룬 벤더 발표들이 대개 성공만 강조하는 것과 대조적으로, 이 글은 **"이건 완벽한 해법이 아니고, 특히 돈이 걸린 서비스엔 위험할 수 있다"**고 먼저 밝힌다. 이런 정직함이 오히려 이 글을 이번 배치에서 **가장 신뢰할 만한 실무 가이드 중 하나**로 만든다.

## 호스피탈리티 / CRS 적용 포인트

- **봇 차단 규칙 적용 전 반드시 로그 시뮬레이션(dry-run)을 거친다(전이 1).** 온다의 CRS API·웹 서비스에 봇 차단을 도입한다면, 실제 차단 전에 **"이 규칙이 과거 트래픽에서 무엇을 걸렀을지"**를 먼저 시뮬레이션한다 — 사업자·파트너의 정당한 API 호출이 데이터센터 IP에서 오는 경우가 흔하므로 특히 중요하다.
- **AI 크롤러 대응을 rate limiting으로 우선 접근(전이 2).** 악의적 차단보다 먼저, **속도 제한과 자원 사용 상한**으로 무분별한 크롤링의 피해를 줄이는 게 정당한 트래픽을 덜 해친다.
- **규칙 복잡도를 관리 가능한 수준으로 유지(전이 3).** 임시방편 규칙이 누적되지 않도록, 봇 차단 시스템도 정기적으로 리팩터링·정리하는 루틴을 둔다.
