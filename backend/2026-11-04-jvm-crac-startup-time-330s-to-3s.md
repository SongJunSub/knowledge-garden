## 한 줄 요약

**CRaC(Coordinated Restore at Checkpoint)로 워밍업을 마친 JVM의 프로세스 상태를 저장해두고 새 파드에서 복원하면, 약 330초였던 파드 준비 시간을 2~3초로 줄일 수 있다는 사례다.**

## 핵심 포인트

- **기존 문제: 파드마다 부팅+JIT 워밍업 반복** — 기존에는 ***파드마다 부팅과 JIT 워밍업을 반복***해 CPU 여유 용량을 상시 확보해야 했고, 장애 복구와 ***오토스케일링***도 5분 넘는 준비 시간에 제약받았다.
- **CRaC 적용 효과: 330초 → 2~3초** — CRaC 적용 후 ***파드 준비 시간이 약 330초에서 2~3초로*** 줄었다.
- **배포 시간과 CPU 사용량도 동반 개선** — 적용 후 전체 배포 시간은 약 ***20분에서 4분***으로, 정상 상태 파드 CPU는 기존 기준의 약 ***20%***로 줄었으며 오토스케일링이 가능해졌다.
- **실제 운영에서 CPU 명령어 기능 불일치 문제 발생** — 실제 운영에서는 ***CPU 명령어 기능 불일치***로 여러 파드의 JVM이 시작하지 못했으며, CRaC 적용 전 정상 이미지…(이하 Slack 발췌 절단으로 상세 불명).

## 내 생각 · 적용점

**핵심 전이 — 콜드 스타트를 줄이는 방법이 "워밍업을 빠르게 하는 것"에서 "워밍업 자체를 건너뛰는 것"으로 이동한다.** [[2026-09-10-aws-eks-gemma4-vllm-part1-cold-start]]는 vLLM 서빙 콜드 스타트를 4단계로 쪼개 47% 단축하는 **최적화** 접근이었다면, 이 글의 CRaC는 워밍업을 마친 프로세스 상태 자체를 ***통째로 복제***해 부팅·JIT 과정을 생략하는 **우회** 접근이다. 같은 콜드 스타트 문제를 "더 빠르게 데우기"와 "데운 상태를 저장해 재사용하기"라는 서로 다른 축으로 공격하고 있다.

## 호스피탈리티 / CRS 적용 포인트

**적용 멀다.** CRS가 JVM 기반 백엔드를 쓰고 오토스케일링 시 콜드 스타트가 체크인 성수기 트래픽 급증 대응에 병목이라면 참고할 기술이지만, CPU 명령어 불일치 같은 운영 리스크가 실제 사례로 보고된 만큼 가벼운 적용은 아니다. 트래픽 급증이 예측 가능한 성수기 대비용으로는 "미리 워밍업된 인스턴스를 풀로 유지"하는 더 단순한 대안도 함께 검토할 가치가 있다.
