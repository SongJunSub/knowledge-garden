# 백업은 단순하지 않다 (Filipovski)

> 출처: [Backups aren't simple](https://filipovski.net/2026/09/16/backups-arent-simple.html) (filipovski.net) · GeekNews 경유 [id=33827](https://news.hada.io/topic?id=33827) · 정리일 2026-09-18
>
> **출처 한계**: `news.hada.io`·`filipovski.net` 모두 이번 세션 egress 차단으로 직접 열람하지 못했다. 아래 내용은 WebSearch로 확인한 원문 스니펫과 GitHub `daily-hackernews`·`hackernews-daily` 미러 아카이브를 교차 확인해 재구성했다. **HN 반응 지표가 출처마다 불일치한다**(아래 댓글 항목 참고) — 어느 쪽도 확정된 사실로 다루지 않는다.

## 한 줄 요약

**파일을 다른 곳에 복사하는 것으로 시작한 백업은, 실수와 랜섬웨어에 대비해 ***"과거 상태를 보존하는 일"***까지 필요해진다 — RAID 1처럼 현재 상태를 복제하는 것만으로는 충분하지 않다는 게 이 글의 출발점이다. 과거 상태를 계속 남기면 저장 공간이 늘어나므로 백업 주기·보존 정책·증분 백업·중복 제거(deduplication)를 순서대로 고민하게 되고, 홈랩에 실제로 적용하면 Docker 컨테이너의 root 소유 파일 접근 권한과 데이터베이스의 "실제 복원 가능성" 문제에 부딪힌다. 화재·하드웨어 고장까지 대비하려면 매체와 장소도 분산해야 한다는 3-2-1 원칙급 결론으로 이어진다.**

## 핵심 포인트

- **출발점 — RAID는 백업이 아니다** — RAID 1(미러링)은 디스크 하나가 죽어도 데이터가 남지만, 실수로 파일을 지우거나 랜섬웨어에 암호화당하면 그 변경사항이 그대로 양쪽에 복제될 뿐이다. "현재 상태의 복제"와 "과거 상태의 보존"은 다른 문제라는 게 글 전체를 관통하는 첫 전제다.
- **증분·중복 제거로의 자연스러운 이행** — 과거 상태를 계속 쌓으면 저장 공간이 선형으로 늘어나므로, 매번 전체를 새로 복사하는 대신 ***변경분만 저장하는 증분 백업***과, ***동일한 데이터 블록을 한 번만 저장하는 중복 제거***가 필요해진다. 하드링크로 기존 파일을 참조하는 rsnapshot류 도구가 이 방식의 예시로 언급된다.
- **GFS(Grandfather-Father-Son) 로테이션** — 매일·매주·매월 스냅샷을 다른 보존 기간으로 순환 삭제하는 전통적 백업 보존 정책까지 이어진다. 저장 공간과 "얼마나 과거로 돌아갈 수 있어야 하는가"를 맞바꾸는 정책적 선택이 필요해지는 지점이다.
- **홈랩 현실의 벽 — Docker 파일 권한** — 실제로 10개가 넘는 Docker 컨테이너를 백업해보면, 많은 컨테이너가 **root 소유 파일**을 만들어놔서 일반 사용자 권한의 백업 스크립트가 그 파일들을 제대로 읽거나 복사하지 못하는 문제에 부딪힌다.
- **데이터베이스는 파일 복사로 끝나지 않는다** — 웹 앱이 흔히 쓰는 데이터베이스는 데이터를 메모리에 올려두고 성능을 위해 배치로 디스크에 플러시하기 때문에, 단순히 데이터 파일을 복사하는 방식으로는 ***"그 시점에 실제로 일관된 상태로 복원 가능한지"***를 보장할 수 없다 — 덤프·트랜잭션 로그 기반의 별도 백업 절차가 필요하다는 함의다.
- **매체·장소 분산 — 화재·고장 대비** — 클라우드에 사본을 둬도 파일 권한 보존, 작은 파일이 많을 때의 업로드 오버헤드 같은 별도 문제가 남는다는 점까지 짚으며, 궁극적으로는 서로 다른 매체·서로 다른 물리적 장소에 사본을 두는 전통적인 3-2-1 원칙급 구조로 수렴한다.

## 인상 깊은 문장

**확인 불가.** 원문(`filipovski.net`)이 이번 세션 내내 egress 차단이라 직접 인용할 수 있는 문장을 확보하지 못했다. WebSearch 스니펫은 문단 요지만 전달할 뿐 따옴표로 묶인 원문 그대로의 문장은 반환하지 않아, 억지로 재구성한 인용을 싣는 대신 이 섹션을 비워둔다.

## 댓글

**hada 댓글 수는 확인 불가.** `news.hada.io`가 세션 전체 차단이라 직접 볼 수 없었다. Hacker News 크로스포스트(`news.ycombinator.com/item?id=49732513`)는 존재가 확인되지만, **두 개의 GitHub 미러 아카이브가 서로 다른 수치를 보고한다** — 하나는 141포인트·73댓글, 다른 하나는 282포인트·177댓글. 두 수치 모두 같은 글을 가리키는 건 맞지만 스냅샷 시점이 다르거나(같은 날 서로 다른 시각) 집계 방식이 다를 가능성이 있어, ***이 노트에서는 어느 쪽도 확정된 사실로 취급하지 않는다.*** Lobsters 등 다른 큐레이션 여부는 확인 불가.

**읽을 때 감안**
- ① **홈랩 규모의 사례라는 한계** — 저자가 실제로 겪은 문제(Docker 컨테이너 10여 개)는 개인 홈랩 규모다. 기업 규모의 백업 인프라(테라바이트~페타바이트급, 다중 리전)에서는 이 글이 짚지 않은 별도의 문제(네트워크 대역폭, RPO/RTO SLA, 컴플라이언스 보존 요건)가 추가로 따라붙는다.
- ② **원문 미확인으로 세부 논증 순서를 놓쳤을 가능성** — 이 노트는 검색엔진 스니펫 재구성이라, 저자가 각 문제(Docker 권한 → DB 복원 → 매체 분산)를 실제로 어떤 순서·어떤 해결책과 함께 제시했는지는 확인하지 못했다.

## 내 생각 · 적용점

### 핵심 전이 1 — 같은 날 GeekNews에 함께 올라온 "파일시스템 선택" 노트와 정확히 맞물린다

[[2026-09-07-nas-backup-filesystem-choice]]는 "여러 디스크를 파일시스템 내장 RAID로 관리할지, 별도 도구로 관리할지"를 묻는 Lobsters 질문에 ZFS(스냅샷·증분 복제)·btrfs(유연한 확장)·ext4/XFS(단순함) 세 갈래 답을 정리했다. 이 글의 "RAID는 백업이 아니다"라는 전제와 겹쳐 읽으면, ZFS·btrfs가 제공하는 "스냅샷"이 바로 이 글이 요구하는 "과거 상태 보존"의 구현 수단이라는 게 명확해진다 — 파일시스템 선택이 곧 백업 전략의 하부 구조 선택이라는 연결이다.

### 핵심 전이 2 — "복원 검증"을 설계로 강제한 두 사례가 이 글의 경고를 실제로 해결한다

이 글이 짚은 "데이터베이스는 복사만으로 복원 가능성을 보장 못한다"는 문제에, [[2026-09-07-databasus-backup-restore-verification]]과 [[2026-08-10-planetscale-parallel-backups]]는 이미 각자 다른 규모에서 구체적인 답을 내놓았다. Databasus는 매 백업마다 일회용 컨테이너에 실제로 복원해 원본과 테이블별 행 수를 대조하고, PlanetScale은 "이전 백업을 복원해 WAL을 재생한 뒤 그걸 다시 백업으로 저장"하는 구조 자체로 매 주기마다 복구 가능성을 검증한다. 세 글을 겹쳐 읽으면 "백업이 단순하지 않은" 이유(이 글)와 그 해법의 스펙트럼(개인 규모 도구 vs 기업 인프라)이 한 축으로 정리된다.

## 호스피탈리티 / CRS 적용 포인트

- **직접 적용 가능성이 크다** — CRS는 예약·요금·재고 데이터를 다루는 B2B 시스템이라, "RAID는 백업이 아니다"·"데이터베이스는 파일 복사로 끝나지 않는다"는 이 글의 핵심 경고가 그대로 우리 인프라에도 적용된다. 특히 DB 백업이 실제로 복원 가능한지를 정기적으로 검증하는 루틴(위 Databasus·PlanetScale 사례가 보여주는 "복원 검증 내장" 패턴)이 있는지 점검할 가치가 있다.
- Docker 파일 권한 문제는 온다 인프라가 컨테이너 기반이라면 그대로 재현될 수 있는 구체적 함정이다 — 백업 스크립트가 실제로 모든 컨테이너의 볼륨을 권한 문제없이 읽어내는지 별도로 확인해볼 만하다.
