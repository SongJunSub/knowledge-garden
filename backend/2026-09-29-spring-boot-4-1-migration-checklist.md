# Spring Boot 4.1까지 나온 지금, 무엇이 바뀌었고 무엇을 먼저 준비해야 할까 (flex 팀 블로그)

> 출처: [Spring Boot 4.1까지 나온 지금, 무엇이 바뀌었고 무엇을 먼저 준비해야 할까](https://flex.team/blog/2026/09/29/backend44) (flex 기술 블로그) · Slack `#개발-뉴스-dev-news`(TechArticles 봇) 경유(GeekNews 아님) · 정리일 2026-09-29

> **출처 한계(큼)**: `flex.team`이 이번 세션 내내 egress 프록시로 차단돼(`EGRESS_BLOCKED`) 원문을 열람하지 못했다. WebSearch로도 이 특정 글은 찾지 못했다(자사 기술 블로그라 발행 당일 색인이 안 된 것으로 보인다). 대신 URL 경로(`backend44`)로 미루어 flex의 backend 시리즈(WebSearch로 확인한 범위: `backend15`가 2026-05-20, `backend43`이 2026-09-22)의 **다음 편**임을 확인했고, **Spring Boot 4.0/4.1의 실제 변경사항은 Spring 공식 마이그레이션 가이드·GitHub 릴리스 노트 위키·Spring.io 블로그**로 직접 교차검증했다. 즉 이 노트의 "핵심 포인트"는 두 층위로 나뉜다 — **Slack 발췌(이 글 고유 정보, 얕음)**와 **Spring 공식 문서로 검증한 일반 사실(깊지만 이 글이 정확히 이 순서·강조로 다뤘는지는 미확인)**.

## 한 줄 요약

**Spring Boot 3.5가 2026년 6월 30일 OSS 지원 종료(마지막 OSS 패치 3.5.16은 6월 25일 출시, 이후 CVE는 유료 상용 지원에서만 패치)되면서 4.x로의 이전이 더 이상 선택이 아니게 된 시점에, flex 팀이 "3.5 EOL → 4.x 마이그레이션"을 backend 시리즈 44편으로 다룬 글로 추정된다. Slack 발췌가 짚은 세 축 — 자동 설정 모듈화, Jackson 3, JSpecify — 은 모두 4.0(2025년 11월 GA)에서 도입됐고, 이 글이 강조하는 "4.0에서 deprecated된 게 4.1(2026년 6월 GA)에서 제거된다"는 패턴은 실제로 Derby 지원·layertools 같은 항목에서 공식 확인된다.**

## 핵심 포인트

**(공식 문서로 검증한 배경 사실 — 이 글 자체의 내용은 아니지만 이 글이 다뤘을 소재)**
- **3.5 EOL 압박이 실재한다**: Spring Boot 3.5는 ***2026-06-30 OSS 지원 종료***, 마지막 OSS 릴리스는 3.5.16(2026-06-25). 이후 CVE는 상용 지원(2032-06-30까지)에서만 패치된다. 4.0도 ***OSS 지원이 2026-12-31까지***라 4.1(OSS 지원 2027-07-31까지)로 더 가는 편이 안전하다.
- **자동 설정 모듈화**: Spring Boot 4.0에서 자동 설정 코드베이스가 ***70개 이상의 세분화된 모듈***로 쪼개졌다. 목적은 시작 시간·네이티브 이미지 크기·빌드 성능 개선. 커스텀 자동 설정을 만들거나 특정 모듈만 골라 쓰던 프로젝트는 의존성 그래프를 다시 짜야 할 수 있다.
- **Jackson 3 요구**: Spring Boot 4.0부터 ***Jackson 3가 필수***다. 아직 Jackson 2에 의존하는 코드를 위해 `spring-boot-jackson2`라는 **deprecated 임시 모듈**을 제공하지만, 이름 그대로 **잠깐 쓰고 떠나야 하는 다리**다.
- **JSpecify 도입**: `org.jspecify.annotations.Nullable` 같은 null 안전성 애노테이션이 엔드포인트 옵셔널 파라미터 등에 적용됐고, 이 nullability 메타데이터가 ***Kotlin의 타입 시스템까지 흘러간다*** — Kotlin에서 Spring API를 쓸 때 정적 분석 도구가 null 문제를 더 정확히 잡아낼 수 있다.
- **4.0 deprecated → 4.1 제거, 실제 사례로 확인됨**: GitHub 공식 릴리스 노트 위키 기준, 4.1에서 ***Apache Derby 지원과 layertools가 실제로 제거***됐다(Derby 프로젝트 자체가 종료돼 H2/HSQL 이전 권장). 이 패턴 — "4.0에서 경고, 4.1에서 삭제" — 이 Slack 발췌가 강조한 "단계적 코드 수정과 기술 부채 해결이 필요하다"는 문장과 정확히 일치한다.
- **4.1의 다른 변화들(부가 확인)**: Netty 기반 Spring gRPC 지원, SSRF 방지를 위한 `InetAddressFilter`, jOOQ 3.20+/Java 21 요구, Reactor HTTP 클라이언트 기본값이 `proxyWithSystemProperties()` 포함으로 변경, Log4j 4가지 회전 전략(크기/시간/크기-시간/cron) 지원.

**(flex의 인프라 맥락 — WebSearch로 확인한 flex 자체 정보, 이 글의 배경일 가능성이 높음)**
- flex 백엔드는 ***50개 이상 레포, 3,500개 이상 모듈*** 규모의 생태계이고, `flex-gradle-plugins`가 전 레포의 빌드 규칙을, `flex-v2-backend-commons`가 Spring Boot 기반 **자체 자동 설정**을 관리한다. 이 규모라면 Spring Boot의 "자동 설정 모듈화"가 남 일이 아니라 **자체 커스텀 자동 설정과의 충돌 여부를 전 레포에 걸쳐 검증해야 하는 실무 문제**가 된다 — Slack 발췌가 "자동 설정 모듈화"를 첫머리에 둔 이유로 추정된다.

## 인상 깊은 문장

> "자동 설정 모듈화, Jackson 3 도입, JSpecify 적용 등 주요 변경 사항에 대한 사전 대비가 필수적이다"
> (Slack TechArticles 봇 발췌, 원문 대조 불가) — **세 항목 모두 "당장 컴파일이 깨지는 것"이 아니라 "지금 안 고치면 다음 마이너에서 깨지는 것"**이라는 공통점이 있다. deprecated 경고를 무시하기 쉬운 이유이자, 정확히 이 글이 경고하는 지점이다.

Slack 봇의 발췌가 마지막 문장에서 끊겨 있어 4.1 이후 로드맵 언급 여부도 불명.

## 내 생각 · 적용점

### 핵심 전이 1 — "deprecated 경고"는 계약 만료 예고이고, 이 시리즈가 반복해서 짚는 "숨은 계약" 문제의 가장 노골적인 버전이다

**[[2026-09-15-flex-transactional-event-listener-silent-ignore]]**에서 flex 팀은 `@TransactionalEventListener`가 "이름이 암시하는 계약"과 "실제 계약"이 다르다는 걸 짚었다. 이번 글의 구조는 그와 정반대로 **친절하다** — Spring 팀은 4.0에서 "이건 곧 사라진다"고 명시적으로 경고(deprecated)하고, 실제로 4.1에서 제거한다. **암묵적으로 깨지는 계약(트랜잭션 리스너)과 명시적으로 예고되고 깨지는 계약(deprecated API) 사이의 스펙트럼**에서, 이번 글은 가장 다루기 쉬운 극단을 보여준다 — 그런데도 "사전 대비가 필수적"이라고 강조해야 한다는 건, **경고가 있어도 실제로 읽고 대응하는 팀은 드물다**는 뜻이다.

### 핵심 전이 2 — 대규모 모듈 생태계에서 프레임워크 업그레이드는 "우리 자동 설정과의 충돌 검증" 문제로 바뀐다

flex 자체가 3,500개 이상 모듈, `flex-v2-backend-commons`라는 자체 Spring Boot 자동 설정 레이어를 갖고 있다는 사실은, **자동 설정 모듈화 70개**라는 Spring 쪽 변화가 flex에게는 "레퍼런스 문서 읽기"가 아니라 "우리가 이미 오버라이드해둔 자동 설정 빈들이 새 모듈 경계에서 여전히 먹히는지 전수 검증"이라는 훨씬 무거운 작업으로 번역된다는 뜻이다. **[[2026-06-08-java-to-kotlin-woowahan]]**이 대규모 마이그레이션(45,000줄, 0장애)에서 세운 원칙 — ***"테스트부터, 작은 단위로, 점진 전환"*** — 이 여기서도 그대로 적용될 후보다. 한 번에 3.5→4.1로 건너뛰는 대신, 4.0에서 deprecated 경고를 전부 해소한 뒤 4.1로 넘어가는 **단계적 경로**가 같은 원칙의 프레임워크 버전 버전.

### 핵심 전이 3 — Jackson 2→3 전환은 이 가든의 "JSON 처리 방식이 바뀌는 시점" 계열에 합류한다

**[[2026-08-18-duckdb-2-0-cyanoptera-preview]]**에서 정리한 DuckDB의 VARIANT 타입, 그리고 그 노트가 연결한 JEP 540(Java의 JSON API)까지 — 이 가든에는 "JSON을 어떻게 다룰 것인가"가 바뀌는 시점을 다룬 노트가 몇 있다. Jackson 3 강제는 같은 계열의 백엔드판이다. 다만 이번엔 **저장 형식이나 파싱 전략의 혁신이 아니라, 메이저 버전 자체가 브레이킹 체인지라는 훨씬 평범한(그러나 실무에는 더 즉각적인) 형태**다. `spring-boot-jackson2`라는 이름 그대로의 "임시 다리" 모듈이 존재한다는 것 자체가, **Spring 팀도 이 전환이 하루아침에 안 끝난다는 걸 알고 있다**는 신호로 읽힌다.

## 호스피탈리티 / CRS 적용 포인트

- **직접 적용 가능성이 높다.** 온다가 Java/Kotlin + Spring 생태계로 백엔드를 운영한다면(일반적인 국내 B2B SaaS 스택 기준 개연성 높음), 3.5 EOL(2026-06-30)은 **이미 지난 마감**이라는 뜻이다. 4.0/4.1 마이그레이션 여부를 점검할 실무적 근거가 된다.
- **Jackson 3 전환이 CRS API 계층에 특히 민감하다.** 온다처럼 파트너(OTA·PMS)와 JSON 기반 연동이 많은 시스템은, 커스텀 `ObjectMapper` 설정·날짜 직렬화 포맷·null 처리 방식이 Jackson 2→3에서 미묘하게 달라질 경우 **파트너 쪽 파서가 우리 응답을 못 읽는** 형태로 장애가 번질 수 있다. 계약 테스트로 응답 스키마를 고정해두는 편이 안전하다.
- **자동 설정 모듈화는 멀티 모듈 CRS 백엔드에 실이익이 있다** — 서비스별로 필요한 자동 설정만 가져가면 시작 시간·이미지 크기가 줄어든다는 건, 예약·재고·정산처럼 여러 서비스로 쪼개진 구조에서 직접 체감 가능한 이득이다.
- **단계적 전환 원칙을 그대로 채택할 만하다**: 3.5→4.1 직행 대신, 4.0에서 deprecated 경고를 모두 해소(spring-boot-jackson2 같은 임시 모듈 활용)한 뒤 4.1로 넘어가는 경로.
