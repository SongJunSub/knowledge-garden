# 연 15만 달러 Looker를 HTML 파일 뭉치로 대체할 수 있을까

> 출처: [Can we replace a $150k Looker with a bucket of HTML files?](https://david.lequin.dev/blog/bi-software-is-dead/) (David Lequin 개인 블로그) · GeekNews(id=35975) 경유 · 정리일 2026-10-26
>
> **출처 한계**: `news.hada.io`와 저자 개인 블로그(`david.lequin.dev`) 모두 egress 차단으로 직접 열람하지 못했다(WebFetch는 이 환경에서 `github.com`만 열렸다). WebSearch로 Hacker News 게시(item id=50212320, 포인트·댓글 수는 확인 못함), daily.dev·ecosistemastartup.com 등의 요약, 그리고 같은 시기 출시된 Anthropic 공식 Claude Dashboards 베타(2026-10-08) 관련 보도를 교차확인했다. 회사명·업종·500명이라는 정확한 인원 수는 원문 직접 열람 없이는 확정하지 못했고(Slack 발췌의 "약 500명"을 그대로 썼다), "자동 갱신"·"재무/운영/마케팅까지 확산"이라는 세부도 Slack 발췌 기반이며 독립적으로 재현하지 못했다. 반면 "8개월", "주간 사용자 Looker 수준 도달", "Looker 사용량 약 1/3 감소", "연 비용 15만→약 2만 달러", "대시보드당 토큰 비용 약 0.5달러(Opus 5.5 전환 후)", "Snowflake가 조회자 본인 권한으로 쿼리를 실행한다"는 핵심 수치·구조는 복수의 2차 요약이 일치시켜 신뢰도가 높다.

## 한 줄 요약

**약 500명 규모 회사의 소규모 데이터 플랫폼팀이 Claude로 생성한 HTML 대시보드를 자체 호스팅해, 8개월 만에 연 15만 달러짜리 Looker와 맞먹는 주간 사용자를 확보하고 Looker 사용량을 3분의 1 가까이 줄였다 — 핵심은 Claude가 화면을 잘 만든다는 게 아니라, 데이터 접근 권한을 Snowflake 역할에 그대로 맡겨 AI 생성 레이어가 권한 체계를 새로 만들 필요가 없었다는 구조적 선택이다.**

## 핵심 포인트

- **"Claude가 만들고, dbt가 모델을 주고, Snowflake가 권한을 지킨다"는 3단 분리** — 이 구조의 핵심은 역할이 완전히 분리돼 있다는 점이다. Claude는 화면(HTML/JS)을 생성하고, dbt는 "무엇이 매출이고 무엇이 재고인가"라는 데이터 모델을 이미 정의해두고, ***Snowflake는 대시보드를 보는 사람 본인의 권한(Snowflake OAuth)으로 쿼리를 실행***한다. 새로운 권한 시스템이나 시맨틱 레이어를 따로 만들지 않았다.
- **이 분리가 안전한 이유는 "생성 레이어가 조회자보다 더 많은 권한을 가진 적이 없다"는 것** — 흔한 실수는 앱이 하나의 공유 서비스 계정으로 모든 쿼리를 실행하고, "올바른 필터링"을 AI가 생성한 코드의 정확성에 떠넘기는 구조다. 이 사례는 반대로 설계됐다 — ***AI가 생성한 코드가 버그가 있거나 프롬프트 인젝션에 당해도, 실행 자체가 조회자 본인의 Snowflake 역할로 제한돼 있어 그 사람이 원래 볼 수 없는 데이터에는 애초에 닿을 수 없다.*** 권한 문제를 코드 정확성이 아니라 인프라 계층에서 구조적으로 막아둔 것이다.
- **고정 레이아웃 대신 프롬프트로 원하는 화면을 즉석에서** — 기존 BI 도구의 고정된 차트·배치 대신, 원하는 디자인·버튼·자동 갱신을 프롬프트로 즉석에서 구현할 수 있게 되면서 재무·운영·마케팅 등 비개발 직군까지 사용이 확산됐다. ***"내가 원하는 화면을 내가 직접 설명해서 만든다"는 경험이 Looker의 "이미 정의된 대시보드를 찾아서 쓴다"는 경험을 대체***했다는 뜻이다.
- **생성 자유도와 보안을 동시에 지키는 3중 장치** — 초기 HTML 호스팅 단계에 ***대시보드별 실행 격리, 자격 증명 분리, 게시 후 검사***를 추가했다. 즉 자유롭게 만들게 해주는 대신, 각 대시보드가 서로의 실행 환경을 침범하지 못하게 하고, 쓰는 자격 증명을 앱 전체가 공유하지 않게 하고, 배포 전에 한 번 더 검사를 거치는 구조로 "자유로운 생성"과 "안전한 운영"을 동시에 만족시켰다.
- **비용 구조가 이 모델을 현실적으로 만든다** — 연 운영비가 Looker 대비 7분의 1 수준(약 2만 달러 vs 15만 달러)이고, 모델을 Opus 5.5로 전환한 뒤로는 대시보드 하나 생성 비용이 약 0.5달러까지 떨어졌다. ***생성 비용이 사람이 수동으로 대시보드를 만드는 인건비보다 압도적으로 낮아지는 지점을 지났다는 뜻***이다.

## 인상 깊은 문장

> "Snowflake runs the queries with the viewer's permissions."
>
> 이 문장 하나가 이 사례 전체의 보안 설계를 요약한다. "AI가 안전하게 생성하도록 만든다"가 아니라 "AI가 뭘 생성하든 조회자의 기존 권한 밖으로는 못 나가게 한다"는, 신뢰의 소재를 생성 레이어에서 인프라 레이어로 옮긴 선택이다.

## 내 생각 · 적용점

**핵심 전이 1 — [[2026-09-16-dbt-charts-dashboard-as-code]]와의 대조: 같은 "거버넌스를 어디서 지킬 것인가" 문제의 다른 해법.** dbt Charts는 대시보드를 YAML 텍스트 파일로 만들어 ***버전관리·diff·PR 리뷰***로 거버넌스를 지키는 접근이었다. 이 사례는 그 대신 ***실행 격리·자격 증명 분리·게시 후 검사***로 거버넌스를 지킨다. 전자는 "만들어지는 과정"을 감사 가능하게 만들고, 후자는 "실행되는 순간"을 안전하게 만든다 — 어느 쪽도 AI 생성 자체를 안전하게 만들려 하지 않고, 둘 다 생성 바깥의 다른 레이어에 신뢰를 위임한다는 공통 전략이 드러난다.

**핵심 전이 2 — [[2026-10-02-line-a2a-conversational-bi]]와의 대조: SQL을 직접 신뢰할지, SQL을 안 믿어도 되게 만들지.** LY Corporation의 사례는 "LLM이 만든 SQL을 믿고 실행하기까지" 온톨로지 RAG와 5개 전문 에이전트로 신뢰를 쌓는 방식이었다 — ***생성된 쿼리 자체의 정확성을 끌어올려 신뢰 문제를 정면으로 푸는 접근***이다. 이 사례는 정반대다 — 쿼리가 틀려도, 조회자의 Snowflake 권한이 이미 바운더리이기 때문에 ***쿼리 자체를 완벽하게 신뢰할 필요가 없다***. 같은 "AI가 만든 쿼리를 어떻게 믿는가"라는 문제에 "더 똑똑하게 만든다" vs "덜 믿어도 되게 설계한다"라는 서로 다른 답을 내놓은 사례다.

**핵심 전이 3 — [[2026-09-14-why-vibe-coded-dashboards-look-bad]]와의 긴장.** Kucharski의 비판은 "AI는 차트와 필터는 만들어주지만 무엇부터 봐야 하는지는 정리해주지 않는다"는 것이었다. 이 사례는 사용량 증가라는 결과만 보여줄 뿐, 개별 대시보드의 설계 품질을 논하지 않는다 — ***이미 dbt로 정의된 지표와 Snowflake 거버넌스가 있었기 때문에 "무엇을 봐야 하는가"라는 질문이 이미 어느 정도 답이 나와 있는 상태에서 AI가 화면만 조립했다***고 보는 게 더 정확하다. 거버넌스가 없는 조직이 똑같이 시도하면 Kucharski의 비판이 그대로 적용될 수 있다는 경고로 읽어야 한다.

## 호스피탈리티 / CRS 적용 포인트

이 글은 온다에 가장 직접적으로 적용 가능한 사례다. CRS/호스피탈리티 BI에서 자주 나오는 수요는 "요금·재고 대시보드를 숙박업체 담당자나 레비뉴 매니저가 자연어로 직접 만든다"는 시나리오다. 이 사례의 구조를 그대로 옮기면:

- **데이터 접근권(누가 무엇을 볼 수 있는가)은 웨어하우스 역할에 고정한다.** 특정 호텔의 레비뉴 매니저가 자기 숙박업체의 요금·재고만 보도록 하는 권한은 Snowflake/웨어하우스의 role·RLS(row-level security)로 이미 한 번 정의해두고, dbt 모델로 "요금"·"재고"·"점유율" 같은 지표를 표준화해둔다. 이 계층이 이미 올바르면, 그 위에 어떤 화면이 생성되든 ***그 담당자가 다른 숙박업체 데이터를 볼 수 있는 경로 자체가 존재하지 않는다.***
- **생성(Claude)은 조회자 본인의 권한으로만 실행되게 한다.** 자연어 대시보드 빌더가 하나의 공유된 "서비스 계정"으로 모든 쿼리를 실행하면, 생성된 코드 하나의 버그나 프롬프트 인젝션이 곧바로 다른 숙박업체 데이터 유출로 이어진다. 반대로 조회자 본인의 이미 스코프된 자격 증명으로 쿼리가 실행되면, ***AI가 틀린 쿼리를 만들어도 피해 범위가 "그 사람이 원래 볼 수 있는 데이터" 안으로 제한***된다 — 이게 이 사례가 보여준 핵심 안전장치다.
- **대시보드별 실행 격리·게시 후 검사는 멀티테넌트 환경에서 특히 중요하다.** 온다처럼 여러 숙박업체·체인을 동시에 다루는 멀티테넌트 구조에서는, 한 테넌트를 위해 생성된 대시보드 코드가 다른 테넌트의 세션이나 캐시를 침범하지 않도록 하는 실행 격리가, 단일 조직 내부 도구보다 더 엄격하게 필요하다.

요약하면, 이 사례의 교훈은 "AI에게 데이터를 안전하게 다루라고 가르치는" 게 아니라 ***"AI가 무엇을 하든 원래 정의된 권한 밖으로 나갈 수 없도록 인프라를 짜는"*** 것이다. 이미 요금·재고 데이터에 대한 역할 기반 접근 제어가 웨어하우스 레벨에 있다면, 그 위에 자연어 대시보드 빌더를 얹는 것은 추가적인 보안 리스크가 아니라 UI 리스크(화면이 이상하게 나올 수 있다는 정도)로 축소된다. Claude 사용에도 바로 도움이 된다 — 온다가 Claude를 CRS 대시보드 생성에 쓴다면, "Claude에게 얼마나 많은 접근 권한을 줄 것인가"를 걱정하는 대신 "Claude가 호출하는 쿼리 실행 계층이 이미 올바른 권한으로 스코프돼 있는가"를 먼저 점검하는 게 이 사례가 주는 실질적 체크리스트다.
