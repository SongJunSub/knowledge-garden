# Google DevSite에서 찾은 인증 없는 원격 코드 실행

> 출처: [GeekNews GN⁺ 요약](https://news.hada.io/topic?id=35260) (1차 보안 연구 블로그 저자·게시처 미특정) · 정리일 2026-10-13
>

## 한 줄 요약

**Google 개발자문서 플랫폼(DevSite)의 Flask 세션 쿠키 안에 쿠키 자체를 서명하는 데 쓰는 `SECRET_KEY`가 — OAuth `client_secret`과 같은 값으로 재사용되어 — 노출돼 있었고, 이를 추출해 서명을 재계산하면 로그인 없이 유효한 세션을 위조할 수 있었다. 더 나아가 OAuth 콜백이 세션에 저장된 객체를 `pickle.loads`로 역직렬화하면서, 이 세션 위조가 인증 없는 원격 코드 실행(RCE)으로 이어졌다.**

## 핵심 포인트

- **비밀이어야 할 값이 비밀을 지키는 그릇 안에 들어 있었다** — Flask의 세션 쿠키는 `SECRET_KEY`로 서명돼 위조를 막는 장치인데, ***그 서명키 자체가 쿠키 내용물(OAuth `client_secret`)과 같은 값으로 재사용***돼 쿠키를 들여다보면 서명키가 같이 나오는 구조였다. 자물쇠와 열쇠를 같은 상자에 넣어둔 셈이다.
- **서명 재계산 → 세션 위조 → 서버가 받아들임** — 추출한 `SECRET_KEY`로 임의 세션 쿠키의 서명을 직접 계산해 만들면, 서버가 이를 ***정상 로그인 세션으로 받아들이는 것까지 검증***됐다.
- **세션 위조가 RCE로 전이된 지점은 `pickle.loads`** — OAuth 콜백 처리 과정에서 세션에 저장된 객체를 `pickle`로 역직렬화하는데, 세션 내용을 완전히 통제할 수 있게 된 공격자는 ***pickle의 임의 코드 실행 특성을 그대로 이용***할 수 있게 된다. Flask 생태계에서 `SECRET_KEY` 유출이 "쿠키 위조"에서 끝나지 않고 "RCE"까지 가는 전형적인 체인이다.
- **윤리적 PoC** — 실제 운영 서버에서는 임의 시스템 명령을 실행하는 대신 ***`time.sleep(N)`을 호출시켜 응답 지연으로 실행 여부를 검증***하는, 피해를 주지 않는 방식으로 취약점을 증명했다.
- **포상금 규모** — 약 1.2억 원(Google 취약점 보상 프로그램, 정확한 달러 환산·등급은 미확인).

## 내 생각 · 적용점

### 핵심 전이 1 — "비밀값 재사용"은 처음 보는 실수가 아니라 반복되는 기본 실수 계열이다

[[2026-06-08-hacking-google-with-ai-bug-bounty]]가 정리한 brutecat의 결론 — ***"Google의 버그는 정교한 익스플로잇이 아니라 인내가 핵심", "같은 깨진 패턴이 도처에 반복된다"*** — 가 이번 사례에도 그대로 적용된다. 그 글은 권한 검사 누락·인증 없는 API·스테이징의 실데이터 노출을 반복 패턴으로 꼽았는데, 이번 건은 그 목록에 하나를 더한다: **서명용 비밀값과 평문 전달용 비밀값을 같은 변수로 재사용하는 것.** 거대 조직도 "암호학적으로 분리돼야 할 역할의 값을 하나로 합치는" 기본적 실수에서 자유롭지 않다는 걸 재확인한다.

### 핵심 전이 2 — pickle 역직렬화는 WordPress 사례와 "조건부 RCE"라는 같은 구조를 공유한다

[[2026-09-24-wordpress-unauthenticated-rce-vulnerability]]는 경로 검증 누락(LFI)이 특정 테마·서버 설정 조건이 겹칠 때만 RCE로 전이되는 "조건부 RCE"였다. 이번 건도 구조가 같다 — **1차 결함(세션 위조)만으로는 "그냥 로그인 우회"에 머물렀을 것**이고, 그 위에 **2차 결함(`pickle.loads` 역직렬화)이 겹쳐야만 RCE까지 간다.** 두 사례 모두 "하나의 큰 구멍"이 아니라 **독립된 두 개의 작은 결함이 체인으로 연결될 때** 심각도가 비약적으로 올라간다는 점을 보여준다 — 보안 검토에서 결함을 개별로만 평가하면 이 전이를 놓친다.

## 호스피탈리티 / CRS 적용 포인트

- **세션/쿠키 서명키와 OAuth client_secret 등 다른 용도의 비밀값이 같은 변수·환경변수로 재사용되고 있지 않은지 점검한다.** 역할이 다른 비밀값은 원천부터 분리 발급해야, 하나가 노출돼도 다른 하나까지 같이 뚫리지 않는다.
- **세션 저장소에 `pickle`(또는 언어 동일 계열의 범용 역직렬화)을 쓰고 있다면, 서명 검증을 통과한 데이터라도 신뢰하지 말아야 한다는 원칙을 재확인한다.** 서명이 깨지지 않는다는 전제 자체가 틀릴 수 있으므로(이번 사례처럼), 역직렬화 포맷을 JSON류의 코드 실행 불가능한 포맷으로 제한하는 것이 더 근본적인 방어선이다.
- CRS/예약 시스템에서 세션 관리 라이브러리의 기본 설정(서명키 생성 방식, 역직렬화 포맷)을 "프레임워크 기본값이니 안전하다"고 가정하지 않고 한 번은 직접 확인해볼 근거가 되는 사례다.
