# 데이터 분석의 출발점, 조직의 지표 기준 통일하기 (Com2uS Hive)

> 출처: [데이터 분석의 출발점, 조직의 지표 기준 통일하기](https://on.com2us.com/tech/common-metric-standard/) (김동완 · Com2uS ON Tech) · 정리일 2026-08-20
> **자사 제품(Hive 애널리틱스) 기능 소개 글**이다. 짧고 **수치·거버넌스 실무가 없다**(→ 댓글 절).
> **게시일 미표기**. 출처 한계로 밝힌다.
> **[[2026-08-20-hive-internal-user-exclusion]]과 한 쌍**이다. 저기가 모집단, 여기가 집계 방식.

## 한 줄 요약

**같은 이름의 지표라도 이벤트 선택·필터·계산 필드가 다르면 같은 기간을 조회해도 다른 숫자가 나온다. AU, 매출, 구매전환율처럼 매일 쓰는 지표가 전부 그렇다. 그리고 차트마다 개별 설정하면 차이를 알아차릴 방법이 없어서, 회의나 보고에서 숫자가 안 맞은 뒤에야 계산 기준부터 되짚게 된다. Hive 애널리틱스의 메트릭은 자주 쓰는 지표 설정을 저장하고 재사용하는 기능이다. 수정 불가한 플랫폼 메트릭과 조직 맞춤형 커스텀 메트릭이 있고, SQL 없이 UI 에서 이벤트·속성값·집계 방식(COUNT, COUNT DISTINCT, SUM, AVG)을 조합한다. 구성은 단일 이벤트, 다중 이벤트와 수식, 이벤트 필터 세 가지다. 그리고 이 글이 말하는 결론은 도구 이야기가 아니다. 공통 지표는 조직이 데이터를 기반으로 소통하기 위한 기준이다.**

## 핵심 포인트

- **문제**: 같은 이름의 지표도 ***"계산 기준이 다르면 같은 기간을 조회해도 서로 다른 수치가 나온다."*** **활성사용자(AU)·매출·구매전환율**이 전부 **이벤트 선택·필터 적용·계산 필드**에 따라 달라진다.
- **왜 안 잡히나**: **차트마다 개별 설정하면 차이를 알아차리기 어렵다.** 발견 시점이 **회의·보고 중**이고, 그때부터 **계산 기준을 역추적**하게 된다.
- **정책 변경 시**: 관련 차트를 하나씩 고치면 **일부 화면 누락 위험.**
- **왜 필요한가**: 운영·기획·마케팅·사업 담당자가 **같은 기준의 수치**로 봐야 한다. ***"조직이 중요하게 보는 이용자 행동과 성과를 메트릭으로 관리하면, 여러 담당자가 같은 관점으로 데이터를 해석하고 논의할 수 있다."***
- **메트릭 기능**:
  - ***"차트에서 자주 사용하는 지표 설정을 저장하고 재사용하는 기능."***
  - **플랫폼 메트릭**(수정 불가) / **커스텀 메트릭**(조직 맞춤형).
  - **SQL 없이 UI 에서** 이벤트·속성값·집계 방식 조합. **COUNT, COUNT DISTINCT, SUM, AVG** 지원.
  - ***"메트릭의 계산 기준을 변경하면 해당 메트릭을 사용하는 모든 차트와 대시보드에 변경 내용이 반영된다."***
- **구성 3가지**:
  - **단일 이벤트**: 로그인 이벤트의 **deviceId 를 고유 개수(COUNT DISTINCT)** 로 세어 **AU** 정의.
  - **다중 이벤트 + 수식**: 구매 이용자 수 / 로그인 이용자 수로 **구매 전환율.**
  - **이벤트 필터**: 로그인 이벤트에 **country=KR 또는 country=US** 조건.
- **경고**: ***"같은 이름의 지표가 여러 개 생성되거나 설명이 충분하지 않으면 어떤 수치를 기준으로 삼아야 하는지 판단하기 어려워진다."***

## 인상 깊은 문장

> ***"공통 지표는 조직이 데이터를 기반으로 소통하기 위한 기준이다."***
> 이 글의 결론. **도구 기능이 아니라 커뮤니케이션 프로토콜**이라는 규정(→ 전이 2).

> ***"메트릭의 계산 기준을 변경하면 해당 메트릭을 사용하는 모든 차트와 대시보드에 변경 내용이 반영된다."***
> **가장 편리한 기능이자 가장 위험한 기능**(→ 전이 3).

> ***"같은 이름의 지표가 여러 개 생성되거나 설명이 충분하지 않으면 어떤 수치를 기준으로 삼아야 하는지 판단하기 어려워진다."***
> **도구가 중복 생성을 막지 못한다는 자백**이기도 하다(→ 전이 4).

## 댓글

**댓글 없음.** 자사 기술 블로그 직접 링크.

**읽을 때 감안**
- ①**제품 기능 소개다.** 결론은 Hive 애널리틱스의 메트릭 기능을 쓰라는 것이고, **자체 구축이나 타 도구와의 비교는 없다.**
- ②**수치가 없다.** ***"수치 불일치 발견 시 계산 기준부터 재확인"***이 문제라는데 **그 비용이 얼마인지, 도입 후 얼마나 줄었는지가 없다.** 지표 표준화의 ROI 는 원래 재기 어렵지만, 최소한 **불일치 사고 건수**는 셀 수 있다.
- ③**게시일 미표기.** 목록에도 날짜가 없다.
- ④**가장 어려운 부분을 안 다룬다: 거버넌스.** 커스텀 메트릭을 **누가 만들 수 있고 누가 승인하는지**, **중복 이름을 어떻게 막는지**가 없다. 글 스스로 ***"같은 이름의 지표가 여러 개 생성되거나"***를 걱정하면서 **막는 장치는 제시하지 않는다.**
- ⑤**소급 변경의 위험이 없다.** 자동 반영을 장점으로만 쓴다(→ 전이 3).
- ⑥**SQL 없이 UI 조합**은 진입 장벽을 낮추지만 **표현력의 상한**이 있다. 코호트·윈도우 함수·세션화가 필요한 지표는 이 조합으로 안 된다. 그 경계가 안 나온다.
- ⑦**플랫폼 메트릭이 수정 불가**라는 건 좋은데, **그 정의가 우리 조직 정의와 다르면** 어떻게 되는지가 없다. 커스텀으로 다시 만들면 **같은 이름 두 개**가 되는데 그게 정확히 ④의 문제다.

## 내 생각 · 적용점

### 핵심 전이 1: 게임 분석 도구가 semantic layer 와 같은 결론에 도달했다

**이 글이 설명하는 게 정확히 semantic layer 다.** 지표 정의를 **차트(소비 지점)에서 떼어내 중앙(정의 지점)에 두는 것.**

**같은 결론에 서로 다른 계보가 도착해 있다.**

| 계보 | 이름 | 정의 위치 |
|---|---|---|
| BI | LookML | 모델 파일 |
| 데이터 엔지니어링 | dbt metrics / semantic models | 리포지토리 |
| 헤드리스 BI | Cube | 스키마 |
| **게임 분석 SaaS** | **Hive 메트릭** | **프로젝트 설정** |

**계보가 다르고 사용자도 다른데(SQL 쓰는 사람 vs 안 쓰는 사람) 구조가 같다.** 이건 **문제가 도구 문제가 아니라 조직 문제**라는 신호다. 사람이 여럿이면 정의가 갈라지고, 정의가 갈라지면 숫자가 안 맞는다.

**그리고 우열이 있다.** SQL 기반은 **버전 관리·코드 리뷰·CI 검증**이 되고, UI 기반은 **접근성**이 좋다. **Hive 쪽은 접근성을 택하고 버전 관리를 포기했다.** 그 대가가 전이 3의 문제로 돌아온다.

### 핵심 전이 2: 지표 표준화의 ROI 는 정확도가 아니라 회의 시간이다

***"회의나 보고 과정에서 수치 불일치 발견 시 계산 기준부터 재확인해야 함."***

**이게 실제 비용이 발생하는 지점이고, 자주 과소평가된다.**

**불일치가 한 번 발견되면 이런 순서로 간다.**
1. 회의가 **원래 안건에서 이탈**한다.
2. 두 숫자의 계산 기준을 **각자 확인**한다(며칠).
3. 확인 결과가 나올 때까지 **의사결정이 멈춘다.**
4. 그리고 **다음 회의에서 같은 일이 다른 지표로 반복**된다.

**진짜 손실은 3번보다 4번이다.** 한 번 숫자가 안 맞은 조직은 **모든 숫자를 의심하기 시작**하고, 그러면 **데이터 기반 의사결정 자체의 신뢰가 깎인다.** 그 다음은 **감으로 결정하고 데이터는 사후 정당화에 쓰는 상태**다.

**[[2026-07-20-why-data-teams-fail]]이 지목한 실패 경로가 이거다.** 데이터 팀이 기술적으로 잘해도 **조직이 숫자를 안 믿으면** 아무 소용이 없다.

**그래서 이 글의 결론이 맞다.** ***"공통 지표는 조직이 데이터를 기반으로 소통하기 위한 기준이다."*** **정확도 도구가 아니라 신뢰 인프라다.**

### 핵심 전이 3: 자동 반영은 양날이다. 과거 보고서의 숫자가 소급으로 바뀐다

***"메트릭의 계산 기준을 변경하면 해당 메트릭을 사용하는 모든 차트와 대시보드에 변경 내용이 반영된다."***

**글은 이걸 장점으로만 쓴다.** 실제로 장점이다. **누락 없이 일괄 적용**된다.

**그런데 같은 성질이 이렇게도 작동한다.**
- 3월에 낸 보고서의 **AU 가 지금 열면 다른 숫자**다.
- 지난 분기 KPI 달성 여부가 **정의 변경으로 뒤집힐 수 있다.**
- 그리고 **언제 왜 바뀌었는지 기록이 없으면** 아무도 재현할 수 없다.

**즉 "모든 차트에 자동 반영"은 "모든 과거 숫자가 가변"과 같은 말이다.**

**필요한 것 셋인데 이 글에 없다.**
- **변경 이력**: 누가 언제 무엇을 왜 바꿨는가.
- **버전 고정**: 확정 보고서는 **그 시점 정의로 고정**되어야 한다.
- **변경 알림**: 이 메트릭을 쓰는 대시보드 소유자에게 통지.

**[[2026-08-02-data-landscape-guide-for-developers]] 축에서 보면 이건 스키마 진화 문제와 같은 종류다.** 정의가 바뀌면 **과거 데이터의 해석이 바뀐다.** 그래서 성숙한 시스템은 **정의에 버전을 붙인다.**

**실무 규칙: 지표 정의를 바꿀 때 ①변경 이력을 남기고 ②이미 배포된 보고서는 옛 정의를 명시하고 ③영향 대시보드 목록을 먼저 뽑는다.** 셋 다 도구가 안 해주면 사람이 해야 한다.

### 핵심 전이 4: 중복 생성을 막는 건 도구가 아니라 거버넌스다

**글이 스스로 걱정한다.** ***"같은 이름의 지표가 여러 개 생성되거나 설명이 충분하지 않으면."***

**그런데 커스텀 메트릭은 누구나 만들 수 있는 구조다.** 그러면 **"AU", "AU(신규 제외)", "AU_final", "AU_최종_v2"** 가 생긴다. 이건 도구의 결함이 아니라 **접근성을 높인 대가**다.

**필요한 최소 규칙 넷.**
- **이름 규칙**: 지표 이름에 **집계 단위와 모집단**을 넣는다(`AU_daily_device`).
- **설명 필수**: 설명 없는 메트릭은 만들지 못하게 한다. 못 막으면 **주기적으로 설명 없는 메트릭을 청소**한다.
- **소유자**: 메트릭마다 담당자. 없으면 아무도 못 고치고 아무도 안 지운다.
- **승인 경로**: 조직 공통으로 쓸 지표는 **한 사람이 승인**한다. 개인 실험용은 **개인 네임스페이스**에 둔다.

**공통과 개인을 네임스페이스로 가르는 게 가장 실효가 크다고 본다.** 누구나 만들되 **공용 이름은 승인이 필요**하면, 접근성과 일관성을 둘 다 얻는다.

### 핵심 전이 5: 지표는 "집계 방식 + 모집단"이고 둘 다 통일해야 한다

**[[2026-08-20-hive-internal-user-exclusion]]과 이 글은 같은 등식의 두 항이다.**

```
지표 = 집계 방식 (이 글)  +  모집단 (제외 유저 글)
```

**하나만 통일하면 숫자는 여전히 안 맞는다.**
- 집계 방식만 통일: 두 팀이 같은 COUNT DISTINCT 를 쓰는데 **한쪽은 내부 계정을 빼고 한쪽은 안 뺀다.**
- 모집단만 통일: 같은 사용자 집합인데 **한쪽은 deviceId, 한쪽은 userId 로 센다.**

**그래서 Hive 가 둘을 같은 "메트릭 설정" 하위에 둔 게 구조적으로 맞다.**

**우리 점검 방식: 지표 하나를 골라 두 질문을 같이 던진다.** ①**어떻게 세나**(이벤트·집계 함수·기간·중복 처리) ②**누구를 세나**(내부·테스트·봇·취소·환불 포함 여부). **둘 중 하나라도 팀마다 다르면 그 지표는 아직 공통 지표가 아니다.**

## 호스피탈리티 / CRS 적용 포인트

- **직접 대응이 크다.** 온다의 **"예약 건수"** 가 팀마다 다를 수 있다. **취소 포함? 노쇼? 무료·제휴 예약? 테스트 예약? 확정 시점 기준인가 체크인 기준인가?** 다섯 개 답이 갈리면 **같은 이름 다섯 지표**다.
- **호스피탈리티 표준 지표부터 고정한다.** **ADR, RevPAR, 점유율, 취소율, 리드타임**은 업계 정의가 있는데도 **회사마다 계산이 다르다.** 특히 **분모**(판매 가능 객실 수에 정비 중 객실을 넣는가)에서 갈린다. **분모 정의를 먼저 못 박는다.**
- **정의에 집계 단위와 모집단을 이름에 넣는다.** `예약건수` 가 아니라 `확정예약건수_체크인기준_테스트제외` 처럼. 길어도 **회의에서 되묻는 시간보다 싸다.**
- **파트너에게 나가는 숫자는 정의를 고정하고 버전을 붙인다.** 파트너 리포트의 지표가 **소급으로 바뀌면 신뢰 사고**가 된다. 대시보드 자동 반영과 **대외 리포트는 경로를 분리**한다.
- **변경 이력·소유자·승인 경로를 지금 만든다.** 지표가 20개 넘어가면 **뒤에 정리하는 비용이 만드는 비용보다 커진다.**
- **공용 네임스페이스와 개인 네임스페이스를 가른다.** 분석 담당자가 자유롭게 실험하되, **공용 이름은 승인**을 거친다.
- **[[2026-08-20-hive-internal-user-exclusion]]과 같이 처리한다.** 집계 방식만 통일하고 테스트 예약·데모 숙소를 안 빼면 숫자는 여전히 안 맞는다.
