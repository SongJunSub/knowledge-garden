# 일회성 샌드박스를 위한 버전 관리 파일시스템

> 출처: GeekNews 토픽 [id=35606](https://news.hada.io/topic?id=35606) (원문 매체 미특정, Tines 기술 블로그로 추정) · 정리일 2026-10-19
>
> **출처 한계**: `news.hada.io`는 egress 차단으로 열지 못했고, Slack 발췌는 "여러 실행이 동시에 작업해도 서로 다른 파일의..."에서 끊겼다. WebSearch로 "Tines 3B"라는 제품명을 특정하지 못했다 — Tines는 보안 자동화(SOAR) 업체로 알려져 있지만, 이 정확한 제품·기능명은 독립 확인하지 못했다. 다만 ***같은 아키텍처 패턴(실행마다 폐기되는 샌드박스에 버전 관리된 영속 파일시스템을 마운트)을 쓰는 독립 사례***를 두 건 찾았다 — 학술 논문 Chronos(에이전트 샌드박스용 브랜칭 파일시스템, 지연 복사·블록 단위 버전 저장)와 Tensorlake 공식 문서(샌드박스에 마운트되는 버전 관리 파일시스템, 샌드박스 자체는 휘발성이지만 마운트된 파일시스템은 내구성을 가지며 여러 샌드박스가 공유 가능). 이 노트는 Slack 발췌를 1차 근거로 삼고, 두 독립 사례는 "같은 설계가 업계에 실재한다"는 정황 증거로만 사용한다.

## 한 줄 요약

**Tines의 3B(추정)는 실행 후 폐기되는 일회성 Linux 샌드박스에, Git 저장소·SQLite·DuckDB 같은 상태를 다음 실행으로 이어받는 영속 파일시스템을 연결한다 — 성공한 실행의 변경만 반영하고 실패하면 폐기하며, 수 GB 데이터도 복사 없이 분기해 운영 데이터에 영향을 주지 않고 실험할 수 있게 한다.**

## 핵심 포인트

- **실행마다 고정 스냅샷, 실패하면 폐기** — 각 실행은 ***고정된 스냅샷을 읽고***, 성공한 실행의 변경만 다음 실행에 일괄 반영한다. 실패하면 파일 변경 자체를 폐기해, 다른 실행이나 UI에 ***반쯤 작성된 파일이 노출되지 않도록*** 한다.
- **복사 없는 분기(copy-on-write 유사)** — 수 GB 데이터도 ***복사 없이 분기***해 운영 데이터에 영향을 주지 않고 실험할 수 있다. 같은 스냅샷을 가리키는 포인터만 추가하고, 이후 변경된 부분만 따로 저장하는 구조로 보인다.
- **동시 실행 격리** — 여러 실행이 동시에 작업해도 ***서로 다른 파일의*** (발췌 끊김) — 문맥상 서로 다른 실행 간 파일 변경이 섞이지 않도록 격리하는 설계로 추정된다.
- **(WebSearch 교차확인) Chronos 논문의 유사 설계** — 에이전트 샌드박스용 브랜칭 파일시스템을 다룬 arXiv 논문은 ***호스트 디렉터리를 지연 복사(lazy copy)로 분기***하고, ***수정된 블록만 버전으로 저장***하며, 원본 디렉터리는 읽기 전용으로 유지해야 한다고 설명한다 — Slack 발췌의 "복사 없이 분기"·"변경된 부분만 따로 저장"과 구조적으로 거의 일치한다.
- **(WebSearch 교차확인) Tensorlake의 마운트형 영속 파일시스템** — Tensorlake 공식 문서는 샌드박스에 마운트되는 버전 관리 파일시스템을 설명한다 — ***샌드박스의 루트 디스크는 휘발성이지만, 마운트된 파일시스템은 내구성을 가지고 샌드박스가 끝나도 살아남으며 여러 샌드박스가 동시에 공유할 수 있다.*** 이 글이 설명하는 "실행 후 폐기되지만 상태는 이어받는다"는 구조와 같은 축이다.

## 내 생각 · 적용점

**핵심 전이 — [[2026-10-11-microsoft-mxc-sandbox-execution]]·[[2026-10-15-qa-wolf-disposable-vm-windows-testing]]과 "일회성 실행 환경" 계열로 묶이지만, 이 글은 그중에서도 ***"폐기되는 실행 환경에 무엇을 영속시킬 것인가"***라는 다른 질문에 답한다.** MXC는 "어느 강도로 격리할 것인가"(프로세스 샌드박스 ~ VM)를 정책 선택의 문제로 바꿨고, QA Wolf는 "콜드스타트를 테스트 실행 시점 이전으로 미리 끝내둔다"는 시간 축의 문제를 풀었다. 이 글은 ***"매번 새로 시작하되, Git 저장소·DB 같은 누적 상태는 버려지지 않게 한다"***는, 일회성과 영속성을 동시에 만족시키는 세 번째 축을 다룬다 — 세 노트를 합치면 "일회성 실행 환경"이라는 패턴이 격리 강도·콜드스타트·상태 영속이라는 세 가지 독립적인 설계 축으로 분해된다는 그림이 완성된다.

## 호스피탈리티 / CRS 적용 포인트

**직접 적용 가능성 있음.** CRS 테스트·실험 환경에서 ***"프로덕션 데이터를 복사하지 않고도 수 GB 규모 예약 데이터로 실험"***할 수 있다는 점은 매력적이다 — 예를 들어 새 요금 로직이나 오버부킹 규칙을 실제 데이터 스냅샷 위에서 실험하되, 실패하면 흔적 없이 폐기하고 성공한 실행만 반영하는 구조는 지금의 "스테이징 DB를 매번 수동으로 동기화"하는 방식보다 안전하고 빠를 수 있다. 다만 ***여러 실행의 동시 격리 디테일이 발췌로 확인되지 않아, 실제 도입 전에는 동시성 보장 범위를 원문으로 직접 확인해야 한다.***
