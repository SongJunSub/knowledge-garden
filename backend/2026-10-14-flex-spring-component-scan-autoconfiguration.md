# 코딩 에이전트가 Spring을 못 짠다면, component scan부터 걷어내 보세요 (flex)

> 출처: [코딩 에이전트가 Spring을 못 짠다면, component scan부터 걷어내 보세요](https://flex.team/blog/2026/10/13/backend46) (flex 기술 블로그 백엔드 시리즈 #46 · 2026-10-13) · Slack `#개발-뉴스-dev-news` TechArticles 경유(GeekNews 아님) · 정리일 2026-10-14

> **출처 한계**: `flex.team`이 이 세션에서 `ENOTFOUND`로 전면 차단돼 원문을 열람하지 못했다. 이 노트는 Slack 발췌(그마저 결론부에서 끊겼다)에 전적으로 의존한다. WebSearch로 "AutoConfiguration.imports"나 "컴포넌트 스캔 빈 충돌"을 직접 다루는 이 글 자체는 찾지 못했다(자사 기술 블로그라 발행 직후 색인이 안 된 것으로 보인다 — [[2026-09-29-spring-boot-4-1-migration-checklist]]에서도 같은 패턴을 겪었다). 대신 인프런 Q&A 게시판 등에서 "빈 이름 중복은 자동/수동 등록 여부와 무관하게 같은 이름이면 충돌한다"는 **일반적인 Spring 지식**은 확인했지만, 이는 이 글의 구체적 주장을 검증한 게 아니라 배경 지식 수준이다. `AutoConfiguration.imports`(Spring Boot 2.7+에서 `spring.factories`를 대체한, 자동 설정 클래스를 한 줄에 하나씩 명시하는 텍스트 파일 메커니즘) 자체는 Spring 공식 문서에 기반한 일반 지식으로 보충했으나, flex가 정확히 이 글에서 어떤 코드 예시·마이그레이션 절차를 제시했는지는 확인하지 못했다. Slack 스레드의 댓글 1개도 열람하지 않았다.

## 한 줄 요약

**flex 팀은 코딩 에이전트가 Spring Boot 프로젝트에서 빈 충돌을 일으키는 근본 원인을 "컴포넌트 스캔의 불투명성"으로 짚는다. `@ComponentScan`은 어떤 빈이 등록되는지를 코드 어디에도 명시적으로 적어두지 않고 런타임에 클래스패스를 훑어 알아내는 방식이라, 에이전트가 의존성의 범위를 코드만 보고 파악할 수 없다. 대안으로 제시된 것이 `AutoConfiguration.imports` — 자동 설정으로 등록될 클래스의 전체 이름을 텍스트 파일에 한 줄씩 명시하는 방식 — 이며, 이렇게 하면 "무엇이 빈으로 등록되는가"가 grep 한 번으로 보이는 정보가 된다.**

## 핵심 포인트

- **문제의 핵심 — 빈 등록 목록이 코드에 없다** — Slack 발췌가 짚는 근본 원인은 ***컴포넌트 스캔은 빈 등록 목록이 코드에 명시되지 않아 에이전트가 의존성 범위를 파악하기 어렵게 만든다***는 것. `@ComponentScan`·`@Component` 조합은 "이 패키지 아래 있는 걸 전부 훑어서 등록해줘"라는 지시일 뿐, 실제로 몇 개의 빈이, 어떤 이름으로 등록되는지는 **애플리케이션을 실제로 구동해봐야 알 수 있는 런타임 정보**다.
- **에이전트에게 특히 치명적인 이유(내 추론 보충)** — 사람 개발자는 IDE의 "빈 찾기" 기능이나 실행 로그로 이 정보를 보완할 수 있지만, 코드 스냅샷만 보고 추론하는 에이전트에게는 "패키지 아래 뭐가 있는지 전부 스캔해보지 않으면 빈 충돌 여부를 알 수 없다"는 게 훨씬 큰 장벽이 된다 — 특히 같은 이름의 빈이 서로 다른 패키지에서 각각 `@Component`로 등록되는 경우, 에이전트는 코드를 아무리 읽어도 그 충돌을 "선험적으로" 예측할 수 없다.
- **대안 — `AutoConfiguration.imports`** — Slack 발췌는 ***빈 등록을 명시적으로 관리하기 위해 컴포넌트 스캔 대신 AutoConfiguration.imports 설정을 권장한다***고 전한다. 이는 Spring Boot가 자동 설정 클래스를 로드하는 공식 메커니즘(Boot 2.7부터 `spring.factories`의 자동 설정 항목을 대체)으로, `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 파일에 전체 클래스 이름을 한 줄씩 적어두는 방식이다(이 메커니즘 자체는 Spring 공식 문서 기반 일반 지식이며, flex가 이 글에서 정확히 어떤 활용법을 제시했는지는 확인하지 못했다).
- **"명시 vs 암묵"이라는 구조적 전환** — 컴포넌트 스캔에서 `AutoConfiguration.imports`로 옮긴다는 건, "코드를 실행해야 알 수 있는 정보"를 "텍스트 파일을 열면 바로 보이는 정보"로 바꾸는 것이다. 빈 등록 여부를 둘러싼 불확실성이 "탐색해서 알아내야 하는 것"에서 "읽으면 끝나는 것"으로 바뀐다.

## 내 생각 · 적용점

### 핵심 전이 1 — 같은 flex 팀이 반복해서 증명하는 "명시적으로 만들면 에이전트가 더 잘 다룬다" 원칙의 세 번째 사례

[[2026-08-18-flex-modules-agents-read-less]]는 "모듈 경계가 교차 참조를 선언하게 만들어 컴파일로 강제한다"는 명시화 사례였고, [[2026-09-15-flex-transactional-event-listener-silent-ignore]]는 반대로 "`@TransactionalEventListener`가 이름이 암시하는 계약과 실제 계약이 달라 암묵적으로 깨진다"는 경고 사례였다. 이번 글은 그 스펙트럼에서 **"암묵적인 것을 명시적인 것으로 적극적으로 바꾸자"**는 처방까지 나아간다 — 컴포넌트 스캔(런타임에 알아내야 함) → `AutoConfiguration.imports`(파일을 열면 보임). 세 글을 합치면 flex 팀이 일관되게 "에이전트(그리고 사람)가 코드를 신뢰하려면, 신뢰해야 할 정보가 코드/설정에 **보이는 형태로 존재**해야 한다"는 하나의 원칙을 각기 다른 Spring 메커니즘에 적용해온 셈이다.

### 핵심 전이 2 — Spring Boot 4.x 마이그레이션([[2026-09-29-spring-boot-4-1-migration-checklist]])과 겹치는 시기, 겹치는 팀, 다른 각도

[[2026-09-29-spring-boot-4-1-migration-checklist]]에서 flex는 "자동 설정 코드베이스가 70개 이상의 세분화된 모듈로 쪼개졌다"는 Spring Boot 4.0의 변화를 다뤘다. 이번 글의 `AutoConfiguration.imports`도 정확히 그 "자동 설정" 메커니즘의 일부다. 두 글을 나란히 보면, flex 팀이 Spring 자동 설정 메커니즘을 **프레임워크 업그레이드 대응(9월)**과 **AI 에이전트 친화적 구조 설계(10월)**라는 두 다른 목적으로 연달아 다루고 있다는 걸 알 수 있다 — 같은 기술 요소가 "버전 호환성 문제"로도 "에이전트 가독성 문제"로도 번역될 수 있다는 점이 흥미롭다.

### 핵심 전이 3 — "컴파일 타임에 보이는 것 vs 런타임에만 알 수 있는 것"이라는 일반 원칙

이 글의 구조를 한 단계 추상화하면, **"정적으로 읽어서 알 수 있는 정보"와 "실행해봐야 알 수 있는 정보"를 구분하고, 가능하면 전자로 옮기라**는 조언이다. 이는 Spring의 컴포넌트 스캔에 국한되지 않는다 — 리플렉션 기반 설정, 런타임 동적 바인딩, 관례(convention) 기반 프레임워크 전반이 같은 문제를 갖는다. AI 코딩 에이전트의 등장이 "암묵적 관례(convention over configuration)"라는 오랜 프레임워크 설계 철학에 역풍이 되고 있다는 신호로 읽을 수 있다 — 사람에게는 편리했던 "관례"가, 코드만 읽고 추론해야 하는 에이전트에게는 오히려 장벽이 된다.

## 호스피탈리티 / CRS 적용 포인트

**직접 적용 가능성이 높다.** 온다가 Java/Kotlin + Spring 생태계로 백엔드를 운영한다면([[2026-09-29-spring-boot-4-1-migration-checklist]]에서 이미 짚었듯 개연성이 높다), 다음을 점검할 실무적 근거가 된다 — ① 코딩 에이전트(Claude Code 등)로 Spring 모듈을 작업시킬 때 빈 충돌·중복 등록 오류가 자주 발생했다면, 그 원인이 컴포넌트 스캔의 암묵성 때문인지 실제로 점검해볼 것 ② 사내 공용 라이브러리(자동 설정 레이어가 있다면)는 `AutoConfiguration.imports` 방식으로 명시적 관리가 가능한지 검토할 것 ③ 일반 애플리케이션 코드(`@Service`, `@Repository` 등)까지 전부 컴포넌트 스캔을 걷어내는 건 과도할 수 있으므로, **"에이전트가 자주 건드리는 모듈"부터 선택적으로 명시화하는 점진적 접근**이 현실적이다 — 이 세 번째 항목은 flex 원문에 없는, 내 추론에 따른 적용 제안이다.
