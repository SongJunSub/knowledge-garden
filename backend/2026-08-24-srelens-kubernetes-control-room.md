# srelens — 엔지니어와 AI 에이전트 모두를 위한 쿠버네티스 컨트롤룸

> 출처: [srelens/srelens](https://github.com/srelens/srelens) (srelens 팀, GitHub · GeekNews 경유) · 정리일 2026-08-24
> **출처 한계**: 아래 "댓글" 절에 상세.

## 한 줄 요약

**쿠버네티스 트러블슈팅에서 터미널·대시보드·로그 뷰어·YAML 편집기를 오가며 컨텍스트를 잃는 문제를, 로컬 kubeconfig로 API 서버에 직접 붙는 단일 데스크톱 워크스페이스로 묶었다. 이 프로젝트의 진짜 포지셔닝은 UI가 아니라 백엔드 공유다 — 사람이 쓰는 데스크톱 앱과 AI 에이전트가 붙는 MCP 서버가 같은 Rust 기능 레지스트리를 공유해서, "에이전트가 본 것"과 "내가 본 것"이 같은 소스에서 나온다.**

## 핵심 포인트

- **문제 정의**: 인시던트 대응 중 *"터미널, 대시보드, 로그 뷰어, YAML 편집기 사이를 오가며 컨텍스트를 잃는다"* — 조사(리소스 탐색·이벤트·로그)와 실행(exec·포트포워드·롤백)이 별도 도구에 흩어져 있는 게 근본 문제.
- **아키텍처**: React 19 프런트엔드 + Tauri v2 셸 + 순수 Rust 백엔드(`kube-rs`, `tokio`). **로컬 kubeconfig 자격증명으로 쿠버네티스 API 서버에 직접 연결** — 중간에 별도 SaaS·클라우드 프록시를 거치지 않는다. 멀티클러스터 워크스페이스 지원.
- **기능 범위**: 워크로드·네트워킹·스토리지·RBAC·admission·오토스케일링·CRD를 실시간 watch로 브라우징, 다중 컨테이너 로그 추적(**크래시 후 이전 인스턴스 로그 스트리밍** 포함), pod exec·디버그 컨테이너·**노드 셸** 터미널, 클러스터 간 포트포워드 관리, Helm 설치/업그레이드/롤백, `metrics-server` 기반 CPU/메모리 뷰.
- **AI 에이전트 통합이 핵심 차별점**: 데스크톱 앱과 MCP 서버가 **같은 백엔드 기능 레지스트리**를 쓴다. `stdio` 또는 loopback HTTP로 MCP 노출, 설정 → MCP에서 활성화. *"MCP access uses your locally authenticated cluster contexts"* — 에이전트가 별도 자격증명을 새로 발급받지 않고 내가 로그인한 컨텍스트를 그대로 쓴다.
- **파괴적 작업의 게이트 = 실행 플래그**: 파괴적 작업은 호출 시 `"_confirm": true` + 프로세스 실행 시 `--mcp-allow-destructive` 플래그가 필요하고, 민감한 읽기는 `--mcp-allow-sensitive-reads`로 별도 분리. 즉 **게이트가 "매 호출마다 사람이 승인"이 아니라 "이 세션에서 파괴적 작업을 허용할지"를 프로세스 시작 시 한 번 켜고 끄는 방식**이다.
- **실물 지표(2026-08-24 GitHub 직접 확인)**: **MIT 라이선스, star 144개, dev 브랜치 커밋 352개**, 최신 릴리스 **v0.5.0**. macOS(Developer ID 서명)·Linux(.AppImage/.deb/.rpm)·Windows(.exe/.msi) 바이너리 제공, 다운로드 크기가 경쟁 제품 대비 macOS 약 11배·Linux 약 7배 작다고 자체 주장(README 근거, 제3자 벤치마크는 확인 못함).

## 내 생각 · 적용점

### 핵심 전이 1 — [[2026-08-10-doordash-ai-agent-gateway]]와 정반대 방향에서 같은 문제("AI 에이전트가 도구에 접근할 때 인증·권한을 어디서 통제하나")에 답한다

DoorDash 노트에서 확인한 원칙은 *"MCP는 도구 설명·탐색·호출만 표준화했지, 인증·권한·자격증명·회수·감사는 해결하지 않는다"*였고, 그 답으로 **조직 전체의 MCP 트래픽을 중앙 게이트웨이 하나로 모아 인증·감사·권한회수를 집중**시켰다. srelens는 정확히 반대 방향으로 이 공백을 메운다 — **게이트웨이를 세우는 대신, 애초에 통제 지점을 "내 로컬 프로세스" 하나로 좁힌다.** 에이전트는 내가 이미 인증된 kubeconfig 컨텍스트 밖으로 나갈 수 없고, 별도 자격증명 발급·회수 인프라 자체가 필요 없다. **개인/소규모 팀 스케일에서는 이게 압도적으로 저렴한 해법이지만, DoorDash 사례가 보여준 "누가 언제 무엇을 했는지 중앙에서 감사"하는 능력은 구조적으로 포기한다** — 로컬 프로세스 안에서 벌어진 일은 그 사람의 로그에만 남는다. 두 사례를 나란히 놓으면 "AI 에이전트 도구 접근 통제"가 조직 규모에 따라 완전히 다른 아키텍처로 갈라진다는 게 보인다.

### 핵심 전이 2 — [[2026-08-14-tiro-kiro-iso27001-security-infrastructure]]와 같은 원칙("파괴적 작업엔 사람이 게이트를 쥔다")을 훨씬 거친 정밀도로 구현한다

Tiro/Kiro 사례의 가드레일은 *"어떤 리소스도 생성, 수정, 삭제하지 마세요"*를 기본값으로 두고, **실제 apply는 사람이 매번 검토·승인한 뒤에만** 진행하는 구조였다 — requirements/design/tasks로 변경을 스펙화하고 before/after를 증거로 남기는 절차까지 갖췄다. srelens의 `--mcp-allow-destructive` 플래그는 **같은 문제의식(파괴적 작업은 기본으로 막는다)에서 출발하지만, 게이트의 단위가 "작업 하나"가 아니라 "세션 전체"다.** 플래그를 켜는 순간 그 세션에서는 에이전트가 어떤 파괴적 작업이든 별도 승인 없이 수행할 수 있다 — Tiro/Kiro의 "apply마다 사람이 본다"는 정밀도에는 못 미친다. **개발자 데스크톱 도구가 이 정도 거친 게이트로 충분한 건, 애초에 사용자가 그 세션 동안 화면을 보고 있다는 전제가 깔려 있기 때문**이다 — 무인 자동화(크론으로 밤새 도는 에이전트)에 이 모델을 그대로 옮기면 Tiro/Kiro가 짚은 위험이 그대로 재현될 것이다.

### 핵심 전이 3 — [[2026-06-01-ai-in-sre-google-reliable-operations]]의 "L0~L4 점진적 자율성" 축에서 보면, srelens의 게이트는 사실상 이진(binary)이다

Google SRE 노트가 제시한 안전 모델은 *"통계적으로 검증된 성공률에 따라 권한을 점진적으로 확대"*하는 L0~L4 단계였다. srelens의 `_confirm`/`--mcp-allow-destructive`/`--mcp-allow-sensitive-reads` 세 플래그는 **읽기 / 민감한 읽기 / 파괴적 쓰기 세 단계로 분리는 돼 있지만, 각 단계 안에서는 켜짐-꺼짐 둘 뿐이고 "이 에이전트가 지금까지 얼마나 정확했는가"에 따라 권한이 넓어지는 메커니즘은 없다.** 오픈소스 데스크톱 도구가 통계적 신뢰도 기반 자율성 등급까지 갖추길 기대하는 건 과한 요구지만, **격자가 성기다는 사실 자체는 이 도구를 인시던트 대응에 도입할 때 감안해야 할 실무 지점**이다 — "에이전트가 지금까지 안전했으니 권한을 넓혀도 된다"는 판단은 srelens가 대신 해주지 않고, 사람이 세션 단위로 계속 다시 내려야 한다.

## 호스피탈리티 / CRS 적용 포인트

- **CRS 백엔드 운영팀이 쿠버네티스 인시던트 대응에 AI 에이전트를 함께 투입한다면, srelens류 "사람과 에이전트가 같은 백엔드를 보는" 설계 자체는 핸드오프 정확도를 직접 올린다.** 사람이 조사하다 에이전트에게 넘기거나 반대 순서로 넘길 때, 둘이 서로 다른 도구(사람은 `kubectl`+Grafana, 에이전트는 별도 API 클라이언트)로 각자 상태를 봤다면 "그때 본 게 지금도 맞나"를 재확인하는 시간이 든다. 같은 기능 레지스트리를 공유하면 이 재확인 비용이 구조적으로 사라진다.
- **다만 온다처럼 여러 사람·여러 팀이 같은 클러스터를 운영하는 조직 규모에서는, [[2026-08-10-doordash-ai-agent-gateway]]가 짚은 "로컬 프로세스 단위 통제는 조직 감사를 포기한다"는 트레이드오프를 그대로 안는다.** 개별 엔지니어 데스크톱에 srelens를 설치하고 각자 `--mcp-allow-destructive`를 켜는 방식은, "누가 언제 어느 클러스터에서 무엇을 지웠는지" 중앙에서 감사하는 능력을 안 준다. 프로덕션 클러스터 운영에 이런 로컬 우선 컨트롤룸을 들일 거면, **쿠버네티스 audit log를 별도로 중앙 수집하는 걸 전제 조건으로 깔아야** DoorDash가 포기하지 않은 감사 가능성을 유지할 수 있다.
- **파괴적 작업 플래그를 세션 단위로 켜는 모델은, 사람이 화면 앞에 있는 "인시던트 대응 중 보조" 용도로는 적당하지만 무인 자동 복구(야간 자동 롤백 등)에는 그대로 옮기면 안 된다** — 핵심 전이 2에서 짚었듯 그건 Tiro/Kiro가 요구한 "apply마다 사람 승인"이 빠진 상태다. CRS 인프라에서 야간 자동 대응까지 확장하려면 srelens의 게이트를 그대로 쓰지 말고 별도의 승인 큐를 앞에 둬야 한다.
- **로컬 kubeconfig 기반 인증 자체는 CRS팀 규모(수 명~수십 명)에서는 매력적인 시작점이다.** 별도 자격증명 발급·회수 인프라를 새로 짓지 않고도 "이미 클러스터 접근 권한이 있는 사람만 에이전트도 그 권한으로 쓸 수 있다"는 최소 보안선을 공짜로 얻는다 — 다만 이건 "출발점"이지 조직이 커지면 DoorDash류 중앙 게이트웨이로 옮겨갈 걸 전제한 임시 해법으로 봐야 한다.
