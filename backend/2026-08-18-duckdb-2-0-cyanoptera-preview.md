# DuckDB v2.0 'Cyanoptera' 미리보기 (duckdb.org)

> 출처: [DuckDB v2.0 Preview: Highlights](https://duckdb.org/2026/08/17/duckdb-20-highlights) (duckdb.org · GeekNews 경유, 제출자 GN⁺) · 정리일 2026-08-18
> **미리보기이지 릴리스가 아니다.** v2.0 은 **2026년 가을** 출시 예정.
> **hada 댓글 1개**(GN⁺ HN 큐레이션, 항목 11개). **실사용자 후기가 많아 값이 있다.**
> **가든에 DuckDB 노트가 처음**이다. 인접 계열로 ClickHouse 노트가 셋 있다.

## 한 줄 요약

**v1.5(2026년 3월) 이후 1만 커밋이 넘게 들어갔고, 그 변화의 방향이 하나로 모인다. 프로세스 안에서 도는 분석 엔진이 네트워크 서버이자 장기 실행 서비스로 나온다는 것. Quack 프로토콜이 그 중심이다. 어떤 DuckDB 프로세스든 자기 데이터베이스를 네트워크에 서빙할 수 있고 다른 어떤 DuckDB 든 거기 붙을 수 있다. 옵티마이저는 PostgreSQL 과 MySQL 에도 SQL 을 직접 밀어 보내서 테이블 전체를 네트워크로 끌어오지 않는다. VARIANT 타입은 JSON 처럼 행마다 다른 모양을 담되 텍스트 형식이 아니고, v2.0 이후에는 일반 JSON 타입이 VARIANT 로 뒷받침된다. 비동기 I/O 로 I/O 계층이 쿼리 처리와 독립적으로 확장되고, 저자들 말로 큰 이득이 나오는 곳은 네트워크 스토리지다. 그리고 눈에 띄는 숫자 하나. 엣지 100만 개 위의 단일 출발점 도달 가능성 질의를 재귀 CTE 로 풀 때 v1.5.4 가 4.90초였는데 v2.0 프리뷰가 0.12초다. 약 40배. 그 밖에 트리거 전면 구현, PEG 기반 새 파서, ICU 의존성 제거, 확장을 한 번 빌드해 여러 버전에서 쓰는 안정 C API 가 들어간다.**

## 핵심 포인트

- **규모**: **v1.5(2026-03) 이후 1만 커밋 이상.** 방향은 **네트워크 서버와 장기 실행 서비스**.
- **Quack 프로토콜**: ***"어떤 DuckDB 프로세스든 자기 데이터베이스를 네트워크에 서빙할 수 있고, 다른 어떤 DuckDB 든 거기 붙을 수 있다."*** `quack_serve()` 로 인증 토큰과 함께 서버를 띄우고, 클라이언트는 `ATTACH 'quack:server.example.com'` 과 `CONNECT` 로 붙는다. 결과는 **스트리밍**으로 돌아온다.
- **원격 푸시다운**: 옵티마이저가 **PostgreSQL·MySQL 에 SQL 을 직접 보낸다.** 테이블 전체를 네트워크로 끌어오지 않는다.
- **VARIANT 타입**: ***"JSON 처럼 VARIANT 컬럼은 행마다 다른 모양의 데이터를 담을 수 있다. JSON 과 달리 텍스트 형식이 아니다."*** 스토리지에서 **shredded 실행**, 스캔으로 **추출 푸시다운**, **Parquet 읽기·쓰기 지원**, 함수 `variant_type()`·`variant_keys()`·`variant_contains()`. **v2.0 이후 일반 JSON 타입이 VARIANT 로 뒷받침된다.**
- **트리거 전면 구현**: BEFORE/AFTER, FOR EACH ROW/STATEMENT, `REFERENCING OLD/NEW TABLE` 전이 테이블, 이벤트당 다중 트리거. 용례로 **감사 테이블**을 든다.
- **SQL 방언 추가**: **NEAREST 조인**(벡터 유사도 검색을 조인 절로), **CTE 안의 DML**(INSERT/UPDATE/DELETE/COPY 를 파이프라인 단계로), **중첩 스키마**(`CREATE SCHEMA finance.reports`), **`$variable_name`** 문법, **JSON 부분 변경**(`json_set()`·`json_insert()`·`json_replace()`·`json_remove()`), **`USING KEY` 재귀 CTE**.
- **비동기 I/O**: I/O 계층이 쿼리 처리와 **독립적으로 확장**된다. Parquet 읽기·쓰기, CSV 읽기, 네이티브 포맷, 새 **MMAP·DIRECT_IO 모드**. ***"큰 이득이 보이는 곳은 네트워크 스토리지다."***
- **재귀 CTE 벤치마크**: 엣지 **100만 개** 위 단일 출발점 도달 가능성. **v1.5.4 4.90초 → v2.0 프리뷰 0.12초**, **약 40배**. 기여 요인은 **재귀 CTE 엔진 재작성**, **조인 아래로 내린 부분 집계**, **메모리 초과 시 디스크 스필**.
- **파티션 인식 계획**: DuckLake·Iceberg·S3 의 Hive 파티션 Parquet 에서 **기존 파티셔닝을 계획에 활용**해 불필요한 스캔을 건너뛴다. **row-group 프루닝 확대**(struct·list·decimal·UUID·IN 필터·함수 술어까지 min-max 와 Parquet Bloom 필터 적용).
- **스토리지 포맷 v2.0**: **버퍼 관리되는 ART 인덱스**(메모리에 고정되지 않고 필요할 때 페이징), **넓은 테이블의 지연 컬럼 메타데이터 로딩**, **DICT_FSST 문자열 압축 기본 활성화**, 압축된 삭제 저장, **읽기 시 손상 검증 강화**. 효과는 **큰 인덱스 테이블이 즉시 열리고 메모리 부담이 작다**는 것.
- **PEG 기반 새 파서**: PostgreSQL 유래 파서를 대체. **런타임 확장 가능한 문법**(확장이 SQL 문법에 훅), **정확한 위치를 짚는 오류 메시지**, **방언 호환 모드**(`SET dialect_compatibility_mode = 'spark'`).
- **ICU 의존성 제거**: 타임존·달력·콜레이션을 네이티브 구현. **압축 IANA 데이터 약 45kB**. 벤치마크로 **타임존 변환(2,500만 행) 2.2배**, **독일어 콜레이션 필터(500만 행) 2.6배**.
- **안정 C API**: **YAML 로 선언된 버전 관리 API 명세**, 통합 심볼 버저닝, 커스텀 할당 핸들러, 정적 링크 지원. ***"이걸 컴파일한 바이너리가 DuckDB 버전을 넘어 계속 작동한다."*** 조직이 **신뢰 저장소를 등록해 서명된 확장을 호스팅**할 수 있다.
- **동시성**: ***"DuckDB 는 첫날부터 완전한 MVCC 와 트랜잭션 격리를 갖춘 트랜잭셔널 다중 연결 데이터베이스로 만들어졌다."*** 장기 실행 서버 배포를 위한 **메트릭·로그·관측 가능성 계층** 개선.
- **거버넌스**: 2026년 가을부터 **DuckDB Foundation 자문 위원회**가 DuckDB·DuckLake·Quack 로드맵에 의견을 준다.

## 내 생각 · 적용점

### 핵심 전이 1: 제품의 정체가 바뀌는 릴리스이고, 그게 채택 판단을 바꾼다

**DuckDB 를 선택하는 이유는 대개 "서버가 없어서"였다.** 프로세스 안에서 돌고, 배포할 게 없고, 파일 하나면 끝난다. **v2.0 은 그 전제를 뒤집지 않으면서 반대 선택지를 추가한다.**

**HN 의 관찰이 정확하다.** ***"프로세스 내 실행 엔진에서 클라우드 데이터 웨어하우스 엔진으로."***

**그런데 이건 양날이다.** 서버 모드가 생기면 **운영 부담과 보안 표면이 따라온다.** 그리고 이 글이 그 비용을 거의 말하지 않는다. `quack_serve()` 한 줄로 시작되는 것이 **인증·인가·네트워크 격리·감사**를 요구하는데, 릴리스 노트는 **인증 토큰**만 언급한다.

**[[2026-08-16-activitypub-won-by-being-boring]]에서 세운 구분이 여기 걸린다.** 지루한 기술의 이점은 **놀랄 일이 없다**는 것인데, **새 실행 모드는 그 이점을 소모한다.** DuckDB 를 파일로 쓰는 조직과 서버로 쓰는 조직은 **같은 도구를 쓰는 게 아니다.**

**실무 규칙: Quack 을 켜는 것은 새 서비스를 배포하는 것으로 취급한다.** 라이브러리 설정 변경이 아니다.

### 핵심 전이 2: 안정 C API 가 오늘 정리한 JEP 540 의 정확한 반대편이다

**오늘 [[2026-08-18-jep-540-simple-json-api]]를 정리하면서 인큐베이터 문제를 적었다.** `jdk.incubator.json` 타입이 공개 API 에 노출되면 **다운스트림이 JDK 변경에 묶인다**는 것. 그리고 [[2026-08-16-activitypub-won-by-being-boring]]에서 **만료된 초안을 표준처럼 배포한** 결과를 봤다.

**DuckDB 의 안정 C API 가 그 문제를 정면으로 푼다.** ***"이걸 컴파일한 바이너리가 DuckDB 버전을 넘어 계속 작동한다."*** 그리고 방법이 흥미롭다. **YAML 로 선언된 버전 관리 API 명세.** 즉 **API 계약을 코드가 아니라 데이터로 만들고 버전을 붙였다.**

**그리고 이게 어제 세운 원칙과 같은 형태다.** ***"선택지를 늘리는 대신 보증을 늘린다."*** 확장 개발자에게 더 많은 훅을 주는 대신 **"이 표면은 안 바꾼다"고 계약**한 것.

**확장 생태계에 이게 왜 중요하냐면, 재빌드 요구가 생태계의 실질 진입 장벽이기 때문이다.** 버전마다 다시 빌드해야 하면 **유지되는 확장만 남고 나머지는 죽는다.** HN 에서 확장 개발자가 정확히 그걸 요청했다.

### 핵심 전이 3: VARIANT 가 오늘의 JSON 논의와 겹치는 자리

***"JSON 과 달리 텍스트 형식이 아니다."*** 그리고 **v2.0 이후 일반 JSON 타입이 VARIANT 로 뒷받침된다.**

**오늘 정리한 [[2026-08-18-jep-540-simple-json-api]]와 층위가 다르지만 같은 문제를 다룬다.** 반구조 데이터를 어떻게 다루느냐.
- **JEP 540**: **엄격하게 파싱**하고 옵션을 안 준다.
- **DuckDB VARIANT**: **파싱하지 않고 구조를 감지해 압축**한다. 스키마 선언 없이.

**둘 다 "JSON 을 텍스트로 다루는 비용"을 문제로 본다.** 앞은 파싱 계약을 좁혀서, 뒤는 저장 형식을 바꿔서.

**그리고 [[2026-08-10-postgresql-mvcc-tradeoffs]]의 "비용은 사라지지 않고 자리만 옮긴다"가 여기서도 성립할 것이다.** shredded 저장은 **읽기를 빠르게 하는 대신 쓰기와 스키마 변화에 비용**을 낼 가능성이 높은데, **이 글이 그 비용을 말하지 않는다.** 가을 릴리스 후에 확인할 항목이다.

### 핵심 전이 4: ClickHouse 와의 비교 축이 이 릴리스로 좁혀졌다

**가든에 ClickHouse 노트가 셋 있다.** [[2026-07-03-clickhouse-winning-observability-wars]]에서 **10~14배 압축률로 Datadog 대비 1/30 비용**을 정리했고, 규모가 커질수록 구조 차이가 벌어진다고 적었다.

**DuckDB v2.0 이 그 격차를 좁히는 방향이다.** 네트워크 서빙, 비동기 I/O, 파티션 인식, 장기 실행 서버용 관측 가능성. **HN 에서 나온 "ClickHouse 같은 정렬된 테이블 시맨틱" 요청도 같은 방향의 신호다.**

**다만 겹치는 게 아니라 만나는 중이라고 본다.** ClickHouse 는 **분산 클러스터에서 시작해 단일 노드로 내려왔고**, DuckDB 는 **단일 프로세스에서 시작해 네트워크로 올라온다.** **선택 기준은 여전히 시작점**이다. 로컬 분석이 주면 DuckDB, 대규모 수집이 주면 ClickHouse.

**실무 규칙: 두 도구의 최신 기능 목록을 비교하지 말고 우리 워크로드의 시작점을 본다.** 기능은 수렴하는데 **운영 모델은 안 수렴한다.**

## 호스피탈리티 / CRS 적용 포인트

- **분석·리포팅 용도로 검토할 만하다.** 예약 데이터 분석, 파트너별 정산 대사 검증, 채널 성과 집계 같은 **읽기 중심 배치 작업**에 맞는다. 운영 DB 를 건드리지 않고 **Parquet 로 내려받아 로컬에서 도는** 형태가 특히.
- **파티션 인식 계획이 실제 이득이다.** 우리 데이터는 **날짜와 파트너로 자연스럽게 파티션**되므로, Hive 파티션 Parquet 를 S3 에 두면 스캔이 크게 줄어든다.
- **Quack 을 켜는 것은 새 서비스 배포로 취급한다.** 인증 토큰만으로 예약·정산 데이터를 네트워크에 서빙하면 안 된다. **네트워크 격리와 감사가 먼저.**
- **VARIANT 는 채널 페이로드 보관에 후보다.** 파트너·채널마다 필드가 다른 원본 응답을 **스키마 선언 없이 담고 나중에 질의**할 수 있다. 다만 **쓰기 비용이 이 글에 없어** 검증이 필요하다.
- **아직 미리보기다.** 가을 릴리스와 실사용 보고를 보고 판단한다. **40배는 재귀 CTE 한 형태의 자체 벤치마크**이지 우리 워크로드의 배수가 아니다.
- **선택 기준은 시작점.** ClickHouse 와 기능표를 비교하지 말고 **로컬 분석이 주인지 대규모 수집이 주인지**로 가른다.
