# Oxynote - 실시간 지표와 API 문서를 함께 관리하는 기술 위키

> 출처: [Oxynote: Self-Hosted Wiki with Live Metrics](https://noted.lol/oxynote-self-hosted-wiki-docker/) (noted.lol 게스트 가이드), [alternativeto.net 제품 소개](https://alternativeto.net/software/oxynote/about/) · GeekNews(id=35787) 경유 · 정리일 2026-10-22
>
> **출처 한계**: `news.hada.io`·`noted.lol`·`alternativeto.net`이 모두 이 세션에서 egress 차단으로 직접 열람하지 못했다. WebSearch 스니펫으로 교차 확인한 결과, Oxynote는 ***실제로 존재하는 자가 호스팅(Self-Hosted) 오픈소스 프로젝트***로 확인된다 — Apache-2.0 라이선스, Docker 이미지로 배포(Postgres 내장, amd64/arm64 지원), Prometheus·PostgreSQL/MySQL 쿼리 기반 라이브 차트, Stripe 스타일 API 문서, 초안·diff·승인 리뷰 흐름, 실시간 공동편집, 그리고 ***Claude 같은 어시스턴트가 문서를 검색·수정할 수 있는 MCP 서버***까지 확인됐다. alternativeto.net 기준 ***GitHub 스타 약 61개·포크 8개·열린 이슈 71개***로, 초기 단계의 작은 프로젝트로 보인다. 정확한 가격 정책, Slack 발췌의 "연결된…"에서 끊긴 마지막 문장(아마 외부 서비스 연동 범위)은 확인하지 못했다. hada 댓글 수·HN/Lobsters 큐레이션 여부도 확인 불가.

## 한 줄 요약

**Oxynote는 시스템 운영팀을 위한 자가 호스팅 기술 위키로, 운영 절차·API 설명 같은 정적 문서 옆에 Prometheus·PostgreSQL/MySQL/MariaDB 쿼리로 그린 실시간 지표(시계열·막대·게이지)를 직접 박아 넣고, 문서와 차트 변경 모두를 초안·diff·승인 과정으로 리뷰해 병합하는 구조다 — 문서의 정확성 검증을, "버전 코드에서 자동 생성"이 아니라 "지금 이 순간의 실제 데이터를 문서 안에서 바로 보여주는" 방식으로 다른 경로로 풀었다.**

## 핵심 포인트

- **운영 문서 옆에 살아있는 숫자를 직접 박는다** — Prometheus와 PostgreSQL/MySQL/MariaDB 쿼리로 ***시계열·막대 차트·게이지를 문서 페이지 안에 표시***한다(교차 확인됨: alternativeto.net은 이를 "Prometheus-backed chart blocks"로 소개). 운영 절차 문서를 읽는 사람이 "지금 이 서비스 상태가 어떤가"를 별도 대시보드로 옮겨가지 않고 같은 페이지에서 바로 확인할 수 있다는 게 핵심 설계다.
- **Stripe 스타일 API 문서** — API 설명과 요청 예시, 응답 구조를 ***좌우 분할 레이아웃***으로 배치한다. 설명(좌측)과 코드 예시·응답(우측)을 나란히 두는 구성은 Stripe 공식 문서가 대중화한 패턴이다.
- **초안 → diff → 승인의 리뷰 흐름(교차 확인됨)** — alternativeto.net에 따르면 ***보호된 페이지는 승인된 초안만 반영***되며, 이는 "문서를 위한 풀 리퀘스트"처럼 동작한다. 문서뿐 아니라 ***차트 변경도 같은 리뷰 과정***을 거친다는 게 Slack 발췌의 서술이다 — 코드 리뷰 관행을 문서·차트에 그대로 옮긴 구조.
- **실시간 공동편집 + 어시스턴트 연동(교차 확인됨)** — 여러 사람이 동시에 문서를 편집하고, 문장·다이어그램 소스·차트에 댓글을 달아 논의할 수 있다. alternativeto.net은 ***Claude 같은 어시스턴트가 MCP 서버를 통해 문서를 검색·편집할 수 있다***는 점도 명시한다 — 사람의 리뷰 흐름(초안·diff·승인)과 AI의 문서 접근이 같은 플랫폼에 공존하는 구조다.
- **작은 오픈소스 프로젝트 — 성숙도는 아직 이르다** — GitHub 스타 약 61개·포크 8개·열린 이슈 71개라는 수치(alternativeto.net 기준)는, 이 도구가 ***아직 널리 검증되지 않은 초기 단계***라는 걸 보여준다. 열린 이슈가 포크 수보다 훨씬 많다는 점도 아직 다듬어지는 중인 기능이 많다는 신호로 읽을 수 있다.

## 내 생각 · 적용점

**핵심 전이 1 — [[2026-08-03-diataxis-documentation-framework]]가 짚은 "버전 코드에서 자동 생성하지 않으면 문서가 실제 동작과 어긋난다"는 경고에, Oxynote는 전혀 다른 해법을 들고 나온다.** 그 노트는 "자동 생성"(코드 스펙에서 문서를 뽑아내는 것)만이 문서 부패를 막는 유일한 해법처럼 보이게 했다. Oxynote는 ***"자동 생성"이 아니라 "실시간 조회"***로 같은 문제를 푼다 — 운영 절차 문서 자체는 사람이 쓰지만, 그 옆의 숫자(지표)는 쓰는 순간이 아니라 ***보는 순간의 실제 값***을 매번 다시 가져온다. "이 문서가 최신인가"라는 질문이 지표 블록에는 애초에 성립하지 않는다 — 항상 지금 값이기 때문이다. 다만 이건 ***지표처럼 외부 시스템에 실시간으로 조회 가능한 값에만 적용되는 해법***이라는 한계도 분명하다 — 절차 설명 자체(어떤 순서로 무엇을 하는지)는 여전히 사람이 갱신해야 코드와 어긋나지 않는다.

**핵심 전이 2 — [[2026-08-28-line-llm-wiki-code-driven-ssot]]의 "코드가 바뀌면 PR로 지식을 자동 갱신"이라는 처방과 비교하면, Oxynote는 "지식을 갱신"하는 게 아니라 "매번 다시 조회"하는 쪽을 택했다는 게 더 분명해진다.** LLM Wiki 노트에서 다뤘던 "SAGE(실시간 MCP 조회) vs LLM Wiki(코드 트리거 재생성)"라는 두 패턴의 대립을, Oxynote의 라이브 차트는 ***지표 영역에서는 명백히 SAGE 쪽***에 선다 — 미리 정리해두지 않고 매번 쿼리한다. 반면 Oxynote의 초안·diff·승인 흐름은 ***LLM Wiki 쪽의 "변경을 리뷰 루프로 끌어들인다"***는 발상과 같다. 한 도구 안에 두 패턴이 영역별로 나뉘어 공존한다는 게 이번 사례의 흥미로운 지점이다 — "숫자"는 실시간 조회로, "설명·절차"는 리뷰 승인으로.

**핵심 전이 3 — [[2026-09-16-dbt-charts-dashboard-as-code]]가 세운 "대시보드가 텍스트 파일이라 diff·PR 리뷰가 가능해진다"는 원칙이, Oxynote에서는 대시보드뿐 아니라 문서 전체로 확장된다.** dbt Charts는 YAML로 선언한 차트를 Git으로 버전관리해 diff 리뷰를 가능하게 하는 게 핵심이었다. Oxynote는 ***차트와 문서를 같은 승인 파이프라인(초안→diff→승인)으로 묶어***, "대시보드도 코드처럼 리뷰한다"는 원칙을 "문서도 코드처럼 리뷰한다"는 더 넓은 범위로 확장한 사례로 읽을 수 있다 — 둘 다 "운영 산출물(대시보드·문서)을 GUI에 가둬 리뷰 불가능하게 만들지 않는다"는 같은 방향이다.

## 호스피탈리티 / CRS 적용 포인트

**직접 적용 가능성 있음 — 운영 절차와 지표가 분리돼 있는 CRS 운영팀의 흔한 문제와 정확히 맞닿는다.**

- **CRS 운영 런북(장애 대응 절차, 배치 작업 가이드)에 관련 지표(에러율, 큐 적재량, API 응답시간 등)를 같은 페이지에 실시간으로 띄우는 구조는, 온다 SRE/운영팀이 "절차를 읽으면서 지금 상황을 따로 대시보드에서 또 확인"하는 이중 작업을 줄여줄 수 있다.** 다만 Oxynote 자체는 아직 스타·포크 수가 작은 초기 프로젝트이므로, 당장 프로덕션 운영 문서 전체를 이걸로 이전하기보다는 ***신규 작은 런북 하나에 시범 적용***해보는 수준이 맞다.
- **초안→diff→승인이라는 문서 변경 리뷰 흐름은, CRS 운영 절차 문서가 "누군가 조용히 고쳐서 아무도 모르게 바뀌는" 문제를 막는 데 참고할 만하다** — 특히 파트너사(채널·PMS)별 예외 처리 절차처럼 바뀌면 운영 사고로 직결되는 문서는 코드 리뷰와 같은 수준의 승인 절차를 요구하는 게 맞다는 걸, 이 도구의 설계가 재확인해준다.
- **MCP 서버를 통한 AI 어시스턴트 연동은, 온다가 이미 Claude Code 등으로 운영 문서를 다루는 흐름과 맞닿는다.** 다만 이 노트 자체가 교차 확인한 수준이 얕으므로, 실제 도입 전에 보안·권한 모델(어시스턴트가 어떤 페이지까지 수정할 수 있는지)을 직접 검증해야 한다.
