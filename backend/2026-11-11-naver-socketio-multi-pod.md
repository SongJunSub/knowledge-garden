> **출처 한계**: `d2.naver.com` egress 차단으로 원문 미확인. 네이버의 구체적 사례는 WebSearch로도 못 찾았지만, Socket.IO 공식 문서로 일반적인 멀티 노드 패턴은 잘 교차확인된다. Socket.IO 세션의 HTTP 요청은 대부분 같은 서버로 가야 하므로 스티키 세션(클라이언트 IP 기반 Ingress 해싱 등)이 필요하고, 한 노드에서 발생한 이벤트를 다른 노드의 소켓에 전달하려면 Redis 어댑터가 필요하다는 점이 확인된다. Slack 발췌가 말하는 "인증, 부하 분산, 오토스케일링" 과정의 네이버 고유 디테일은 미확인.

## 한 줄 요약

**네이버가 쿠버네티스에서 Socket.IO 서버를 다중 Pod로 운영하기 위한 이벤트 전달, 연결 유지 설계를 공유했다. 일반적으로 이런 구성에는 스티키 세션과 Redis 어댑터가 핵심 축인데, 네이버가 정확히 어떤 조합을 택했는지는 원문 차단으로 확인 못 했다.**

## 핵심 포인트

- **이벤트 전달 설계(Slack 발췌)**: 쿠버네티스 환경에서 다중 Pod 간 이벤트 전달과 연결 유지를 설계했다고 명시. Socket.IO 표준 해법은 Redis 어댑터로 이벤트를 모든 노드에 전파하는 것(일반 자료로 확인).
- **운영 제약 세 가지(Slack 발췌)**: 인증, 부하 분산, 오토스케일링 과정에서 발생하는 기술적 제약을 다룬다고 하는데, 구체적으로 어떤 문제였는지는 미확인.
- **스티키 세션이 보통의 핵심 난제(일반 자료로 보강)**: Kubernetes Ingress에서 클라이언트 IP 해시로 같은 Pod에 라우팅하는 방식이 표준 해법으로 제시되는데, 이는 오토스케일링과 근본적으로 충돌하는 긴장이다. Pod가 스케일 인/아웃될 때마다 어느 클라이언트가 어느 Pod에 묶여 있었는지가 흔들리기 때문. 네이버 글이 이 긴장을 어떻게 풀었는지가 핵심일 가능성이 높지만 미확인.

## 내 생각 · 적용점

### 핵심 전이 1 — "동시 접속을 어떻게 저렴하게, 안정적으로 버티는가"라는 같은 질문의 다른 답

[[2026-08-31-mmorpg-1000-concurrent-users-6-dollar-vps]]는 6달러 VPS 한 대로 동시접속 1,000명을 버티는 극한 비용 최적화 답이었다. 이 네이버 글은 정반대 극단이다. 다중 Pod, 오토스케일링이 가능한 대규모 표준 아키텍처로 같은 동시 접속 유지 문제에 답한다. 같은 질문에 대한 답의 스펙트럼이 VPS 한 대로 버티기부터 쿠버네티스로 수평 확장하기까지 걸쳐 있다는 걸 보여주는 짝 사례.

### 핵심 전이 2 — 상태를 공유 저장소로 분리한 사례와 같은 "상태를 어디에 둘 것인가" 질문

[[2026-09-08-sega-sonic-rumble-dynamodb-elasticache]]는 세가가 ElastiCache Serverless로 상태를 중앙화해 샤드 관리 없이 트래픽에 대응한 사례였다. Socket.IO의 Redis 어댑터도 똑같은 구조다. 개별 Pod는 상태가 없고, 연결 상태와 이벤트 전파는 공유 저장소에 위임한다. 실시간 연결을 수평 확장하려면 상태를 애플리케이션 서버 바깥으로 빼야 한다는 원칙이 게임 서버와 웹소켓 서버에서 똑같이 반복된다.

## 호스피탈리티 / CRS 적용 포인트

**적용 가능성 있음.** 온다 CRS가 실시간 알림(예약 상태 변경, 재고 동기화 알림)을 웹소켓으로 운영한다면 똑같은 문제를 만난다. Pod를 늘릴수록 어느 클라이언트가 어느 Pod에 연결돼 있는지를 추적해야 하고, 오토스케일링 시 연결이 끊기지 않게 하려면 Redis 어댑터 같은 공유 상태 계층이 필요하다. 특히 다수 파트너사가 동시에 재고 변경 알림을 구독하는 구조라면, 이 설계 원칙을 미리 검토해둘 가치가 있다.
