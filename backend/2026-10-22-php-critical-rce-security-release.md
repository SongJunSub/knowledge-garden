# PHP, 원격 코드 실행 가능한 치명적 취약점 2건 긴급 패치 (PHP 개발팀)

WebSearch로 "PHP 8.5.12 8.4.27 8.3.36 8.2.35" 등 여러 조합을 검색했지만 ***이 정확한 버전 조합·CVE 번호는 이번 조사로 확정하지 못했다*** — 다만 PHP가 2026년에 반복해온 보안 릴리스 주기(8월 8.5.9/8.4.24/8.3.33/8.2.33, 9월 22일 8.5.11/8.4.26/8.3.35/8.2.34)와 비교하면, Slack 발췌의 "8.5.12·8.4.27·8.3.36·8.2.35"는 ***그 다음 순번으로 자연스럽게 이어지는 숫자***라 패턴상 신뢰할 만하다고 판단했다. CVE 번호, 정확한 결함의 기술적 성격(메모리 손상 종류, 공격 벡터)은 Slack 발췌 자체가 "완전한 해결책은 업데…"에서 끊겨 확인하지 못했다. hada 댓글 수·HN/Lobsters 큐레이션 여부도 확인 불가.

## 한 줄 요약

**PHP가 인증 없이 원격 코드 실행이 가능한 치명적 취약점 2건을 수정한 보안 릴리스(8.5.12·8.4.27·8.3.36·8.2.35)를 내고 모든 사용자에게 즉시 업데이트를 강력히 권고했다 — PHP-FPM, Apache mod_php, php-cgi, FrankenPHP, LiteSpeed 등 웹 요청을 처리하는 모든 PHP 설치 환경이 대상이며, 특히 mod_php에서는 애플리케이션 코드가 실행되기도 전에 공격이 성립하는 사례가 확인됐다.**

## 핵심 포인트

- **"애플리케이션 코드와 무관하다"는 게 이 릴리스의 핵심 위험** — PHP-FPM, Apache의 mod_php, php-cgi, FrankenPHP, LiteSpeed 등 ***웹 요청을 처리하는 모든 PHP 설치 환경***이 영향을 받는다고 밝혔다. 특히 mod_php 사례는 ***애플리케이션 코드가 실행되기 전 단계에서 이미 공격이 성립***한다고 명시했다 — 즉 "내 코드는 안전하다"는 확인이 방어가 되지 못하는 결함이라는 뜻이다. 이 성질은 바로 아래 Wiz의 [[2026-10-22-wiz-php2shell-ai-exploit-chain]]이 실증한 "애플리케이션이 아니라 PHP 엔진 자체의 문제"라는 구조와 정확히 같은 결이다.
- **수정 버전 — 4개 지원 라인 동시 패치** — PHP 8.5.12, 8.4.27, 8.3.36, 8.2.35. PHP가 여러 버전 라인을 동시에 지원·패치하는 체계 자체가, 한 번의 패치로 전체 생태계를 덮기 어렵다는 걸 보여준다 — 네 버전 각각이 실제 운영 환경에 깔려 있다는 전제가 깔려 있다.
- **배포 전 사전 전달 — 공급망의 중간 단계도 움직였다** — Linux 배포판과 LTS 공급업체에 패치가 사전 전달돼, 각 배포업체가 자체 업데이트 패키지를 준비할 시간을 확보했다고 밝혔다. 이는 [[2026-10-22-php-foundation-patch-delay-postmortem]]가 다룬 "조율된 공개 일정"의 실제 집행 사례로 읽힌다 — 다만 그 노트가 설명하듯 이번에도 조율이 완벽하진 않았을 가능성(CVE 정보 유출로 릴리스가 하루 앞당겨졌다는 서술)이 있다.
- **(확인 불가)** 완전한 해결책이 "업데이트"라는 문장에서 Slack 발췌가 끊겨, 업데이트 외에 WAF 룰·설정 변경 같은 임시 완화책이 제시됐는지는 확인하지 못했다.

## 내 생각 · 적용점

**핵심 전이 1 — [[2026-10-22-wiz-php2shell-ai-exploit-chain]]과 "같은 날 세 각도에서 본 PHP 보안 생태계"의 한 축.** 이 글은 PHP 개발팀이 "치명적 RCE 2건을 고쳤다"는 공식 패치 공지이고, Wiz의 PHP2Shell은 "그런 류의 오래된 결함을 AI로 실제 공격 체인으로 구현했다"는 공격 실증이다. 두 글이 정확히 같은 CVE를 가리키는지는 양쪽 다 CVE 번호를 원문에서 확인하지 못해 단정할 수 없지만 — ***이 패치가 나온 바로 그 시점에 PHP 엔진 자체의 구조적 결함을 보여주는 공격 연구가 함께 공개됐다는 사실 자체가, "패치가 나왔다"와 "위협이 끝났다"는 별개라는 걸 보여준다.***

**핵심 전이 2 — [[2026-10-22-php-foundation-patch-delay-postmortem]]이 설명하는 "왜 이렇게 오래 걸렸는가"의 결과물이 바로 이 릴리스다.** 그 노트는 PHP 재단이 2024년부터 알고 있던 메모리 처리 문제의 수정이 호환성·합의·인력 부족으로 지연된 경위를 자기반성한 글이다. 이번 패치 공지가 그 지연된 수정의 실제 배포 시점이라면, "원인 분석"과 "결과물" 두 노트를 나란히 두는 것만으로 ***PHP라는 20년 넘은 코어 언어에서 보안 수정이 실제로 사용자 손에 닿기까지 걸리는 전체 사슬***(발견 → 내부 의사결정 → 패치 → 배포판 전달 → 사용자 업데이트)이 한눈에 들어온다.

**핵심 전이 3 — [[2026-09-24-wordpress-unauthenticated-rce-vulnerability]]가 보여준 "패치가 나와도 적용 전까지는 뚫린다"는 교훈이 PHP 코어 레벨에서 반복된다.** 그 노트는 WordPress 코어의 10년 묵은 경로 검증 누락(CVE-2026-87902)이 공개 몇 시간 만에 실공격으로 이어진 사례였다. 이번 PHP 코어 패치도 ***4개 버전 라인에 걸쳐 배포돼야 하고, Linux 배포판·LTS 공급업체의 패키징을 거쳐야 실제 서버에 닿는다*** — 그 시차가 공격자에게 주어지는 실질적인 창(window)이라는 점에서 같은 구조의 위험이 반복된다.

## 호스피탈리티 / CRS 적용 포인트

**직접 적용 가능성 있음.** 온다 CRS 자체 스택이나 파트너사 연동 시스템 중 PHP 기반 컴포넌트(레거시 PMS 연동, 파트너 WordPress 사이트 등)가 있다면 이 릴리스는 즉시 점검해야 할 항목이다.

- **PHP-FPM·mod_php·php-cgi·FrankenPHP·LiteSpeed 중 어떤 방식으로 PHP를 서빙하는지부터 파악한다.** "애플리케이션 코드와 무관하게" 공격이 성립할 수 있다는 이번 발표의 핵심 위험은, 애플리케이션 보안 점검만으로는 잡히지 않는다.
- **버전 고정(pin) 전략을 쓰는 경우, 이번처럼 4개 라인(8.5/8.4/8.3/8.2) 전체가 패치되는 릴리스는 "어느 라인에 있든 예외 없이 업데이트해야 한다"는 신호로 받아들인다.**
- **파트너사의 PHP 기반 시스템에 대한 패치 적용 여부를 묻는 것도 B2B 관계에서 할 수 있는 실무적 조치다** — [[2026-09-24-wordpress-unauthenticated-rce-vulnerability]]에서 이미 짚었듯, 온다가 직접 운영하지 않는 PHP 시스템이라도 연동 경로를 통한 피해는 온다 쪽으로 번질 수 있다.

## 연관 자료
