# 150만 페이지 웹사이트에서 scraper와 싸운 1년 (PatronView)

> 출처: [99% of My Website Traffic is Bots](https://patronview.com/news/99-percent-of-my-website-traffic-is-bots/) (patronview.com · GeekNews GN⁺ 요약 + HN 큐레이션) · 정리일 2026-08-08

## 한 줄 요약

**150만 개 프로필 페이지를 운영하는 PatronView는 **주간 250만 건 외부 요청·128만 페이지 로드**를 처리하지만, 분석 도구엔 ***"5,977 pageview"***만 기록됐다 — 실제 트래픽과 분석 도구가 보는 트래픽 사이의 격차가 약 214배다. **봇의 진화**를 목격했다 — 단순 SEO 크롤러에서 **중국의 36만 개 IP를 동원한 대규모 크롤링**, AWS/Azure의 headless Chrome, residential proxy botnet으로. **크롤러 평가 기준**은 "크롤링 페이지 수 대비 보낸 방문자 수"다 — ***"Google은 방문자 1명당 46페이지"***를 크롤하는데, **Claude-SearchBot은 35,000페이지, Amzn-SearchBot은 하루 117,000페이지**를 읽으면서 **방문자를 전혀 보내지 않는다.** 방어는 Cloudflare WAF의 국가/UA/ASN/구형 브라우저/요청 속도 조합 — 그런데 **최근 48시간 CAPTCHA 106,437건 중 성공은 252건, 해결률 0.24%**다. ***"봇이 전체 비용의 99%"***를 유발하고, **스크래핑 비용이 방어 비용보다 빠르게 낮아지는** 상황이라 Cloudflare의 pay-per-crawl 같은 경제적 구조가 필요하다는 게 저자의 결론이다. 운영 원칙: ***"방문자를 전혀 보내지 않는 크롤러는 차단."***

## 핵심 포인트

- **트래픽 격차** — 주간 **250만 건 요청·128만 페이지 로드** vs 분석 도구 **5,977 pageview**(약 214배 격차).
- **봇의 진화 경로** — 단순 SEO 크롤러 → **중국 36만 개 IP 대규모 크롤링** → AWS/Azure headless Chrome → residential proxy botnet.
- **크롤러 평가 기준(페이지/방문자)** — **Google 46페이지/방문자** vs **Claude-SearchBot 35,000페이지**·**Amzn-SearchBot 하루 117,000페이지**(둘 다 방문자 0명).
- **CAPTCHA 방어 성과** — 최근 48시간 **106,437건 시도 중 252건 성공, 해결률 0.24%.**
- **비용 구조** — ***"봇이 전체 비용의 99%"*** 유발, **스크래핑 비용이 방어 비용보다 빠르게 하락**하는 비대칭.
- **운영 원칙** — ***"방문자를 전혀 보내지 않는 크롤러는 차단."***

- **실제 사용자 피해** — 오래된 브라우저·JavaScript 비활성화 사용자도 차단 — ***"차단은 성공했지만 사용자는 잃은 셈."***
- **대안 기술** — **Anubis** 같은 도구가 작업 증명(proof-of-work)으로 실제 브라우저와 구분 가능하다는 평가.
- **경제성 논의** — ***"스크래퍼의 비용이 방어 비용보다 빠르게 낮아진 비대칭 구조"***가 근본 원인.
- **사업자 부담** — 개인 프로젝트 운영자들이 ***"예전엔 자체 충당이나 무시할 만큼 저렴했지만, 이제 수입은 0인데 자원 사용량은 증가."***
- **AI 크롤러 문제** — Claude-SearchBot이 ***"출처 표시나 보상 없이 사용자에게 생색내니 착취당한 느낌."***
- **기술적 해법** — 국가 단위 차단 대신 **"/24 IP 대역 집계"** 같은 세분화된 차단이 효과적.

**읽을 때 감안**
- ①**Claude-SearchBot이 이 글에서 직접 이름으로 지목된 "방문자 0명" 크롤러 중 하나**라는 걸 정직하게 짚어야 한다 — 이 노트를 작성하는 도구(Claude) 자체와 관련된 서비스가 문제 사례로 등장한다.
- ②**"214배 격차"라는 계산이 정확히 무엇을 분자·분모로 삼았는지(요청 수 대비 페이지뷰, 혹은 페이지로드 대비 페이지뷰) 이번 정리에서 완전히 명확하지 않다** — 원문의 정확한 산식을 재확인할 필요가 있다.
- ③**PatronView 자체의 운영 규모·산업(팬트론/후원 플랫폼으로 추정)에 대한 배경 정보가 부족**해, 이 수치가 다른 규모의 사이트에도 일반화되는지는 불확실하다.

## 내 생각 · 적용점

### 핵심 전이 1 — 이 노트는 이 세션이 이미 정리한 봇 차단 가이드의 실전 데이터로 채워진 사례연구다

[[2026-08-02-how-to-block-some-bots]]에서 다룬 **일반적 봇 차단 기법**(HTTP 프로토콜·IP 대역·TCP 특성·TLS 지문)이 이론적 가이드였다면, 이 노트는 **실제 1년간의 전투에서 나온 구체적 숫자**(250만 요청·CAPTCHA 해결률 0.24%·214배 격차)로 그 가이드를 실증한다. 그 노트에서 짚었던 핵심 경고 — ***"1~3년치 로그를 먼저 분석하지 않으면 정상 사용자까지 차단할 수 있다"*** — 가 이 노트의 HN 댓글(오래된 브라우저 사용자 피해)에서 정확히 실현된다.

### 핵심 전이 2 — "스크래핑 비용이 방어 비용보다 빠르게 낮아진다"는 재현비용 붕괴 곡선의 어두운 이면이다

[[2026-08-02-frontier-ai-semiconductor-treadmill]]에서 추적해 온 재현비용 붕괴 — AI를 저렴하게 쓰는 게 좋은 일로만 그려졌는데, 이 노트는 **같은 비용 붕괴가 스크래핑·봇 운영에도 똑같이 적용된다**는 걸 보여준다. AI가 저렴해질수록 **방어자만이 아니라 공격자(스크래퍼)도 더 싸게 무장**한다 — 이번 시즌 낙관적으로 다뤄온 비용 붕괴 서사에 중요한 균형추다.

### 핵심 전이 3 — Claude-SearchBot이 지목된 사례는 이 가든 자체의 도구에 대한 자기 성찰을 요구한다

이 노트를 작성하는 도구(Claude)와 관련된 크롤러가 ***"출처 표시나 보상 없이... 착취당한 느낌"***이라는 댓글로 지목된다는 사실은, 이번 시즌 반복해 온 **"이해상충 고지"** 원칙을 이 노트 자신에도 적용해야 한다는 뜻이다. AI 기업들의 크롤러가 방문자를 전혀 보내지 않으면서 대량의 콘텐츠를 소비하는 구조는, [[2026-08-04-devtools-must-be-open-source]]나 다른 AI 낙관 노트들이 다루지 않은 **AI 생태계의 숨겨진 외부효과**다.

### 핵심 전이 4 — 정직한 급소: Cloudflare 의존 우려는 콜드스타트 문제의 방어 인프라 버전이다

[[2026-08-04-github-has-alternatives-no-replacement]]에서 다룬 콜드스타트 문제 — 대안이 있어도 규모의 네트워크 효과 때문에 채택되지 않는다 — 가 이 노트의 HN 댓글(***"웹사이트 열람 권한을 대기업에 넘긴 사람이 많아 우려됨"***)에서 **방어 인프라 버전**으로 반복된다. Anubis 같은 대안이 있어도, 대부분의 운영자는 이미 규모의 경제를 갖춘 Cloudflare에 의존할 수밖에 없다는 게 이 시즌 반복된 "콜드스타트 승자독식" 패턴의 또 다른 사례다.

## 호스피탈리티 / CRS 적용 포인트

- **CRS 웹 서비스의 실제 트래픽과 분석 도구 수치의 격차를 정기 점검(전이 1).** 예약 페이지·API 엔드포인트의 실제 요청 로그와 분석 대시보드 수치를 대조해 214배급 격차가 있는지 확인.
- **AI 크롤러(특히 Claude-SearchBot류)의 방문자 미전달 문제를 robots.txt·rate limiting 정책에 반영(전이 3).** 방문자를 보내지 않는 크롤러를 식별해 접근 정책을 차등 적용.
- **CAPTCHA 같은 단일 방어층에 의존하지 말고 계층적 방어(전이 4).** 0.24% 해결률처럼 CAPTCHA 자체는 효과적이어도, IP 대역·행동 패턴 등 복수 신호를 결합해야 실효성이 유지된다는 걸 CRS 방어 설계에 반영.
