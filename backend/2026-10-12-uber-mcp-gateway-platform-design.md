# MCP Gateway (Uber Engineering) — 기존 API를 감싸는 800개+ MCP 서버를 '등록·검토·게이트웨이'로 표준화해 에이전트 플랫폼의 접근 제어 문제를 해결한다

> 출처: [Designing MCP Gateway](https://www.uber.com/blog/designing-mcp-gateway/) (Uber Engineering) · GeekNews(id=35213) 경유 · 정리일 2026-10-12

## 한 줄 요약

**Uber는 조직 전역에 흩어져 있던 MCP 연동(기존 REST/gRPC API 래퍼 + 네이티브 MCP 서버)을 단일 플랫폼 "MCP Gateway"로 통합했다. 등록·검색을 맡는 Registry(컨트롤 플레인)와 실제 호출을 HTTP/gRPC/TChannel로 변환해 기존 백엔드를 건드리지 않고 실행하는 Proxy Gateway(데이터 플레인)로 나누고, AutoCrawler가 기존 API 정의에서 도구를 자동 발견한다. 현재 800개 이상의 MCP 서버와 5,000개 이상의 도구를 운영 중이다 — 핵심은 "표준 프로토콜"만으로는 해결되지 않는 접근 제어·소유권·거버넌스를 플랫폼 레이어에서 떠안았다는 점이다.**

## 핵심 포인트

- **두 개의 평면으로 분리** — ***MCP Registry***(컨트롤 플레인)가 도구 검색·소유권·활성화 설정을 관리하고, ***Proxy Gateway***(데이터 플레인)가 MCP 요청을 HTTP·gRPC·TChannel 호출로 변환해 실행한다. 기존 백엔드 서비스는 코드 수정 없이 MCP 표면을 얻는다.
- **AutoCrawler로 도구 자동 발견** — 기존 API 정의(OpenAPI 등)와 네이티브 MCP 서버 양쪽에서 도구를 자동으로 찾아내며, no-code 래퍼부터 MCP 스펙에 맞춰 직접 구현한 네이티브 서버까지 폭넓게 수용한다.
- **발견 ≠ 공개** — 새로 크롤링된 도구는 바로 에이전트에 노출되지 않고, ***소유 팀의 검토와 승인***을 거쳐야 활성화된다(2차 보도 기준, 원문 미대조).
- **규모** — ***800개 이상의 MCP 서버, 5,000개 이상의 도구***를 단일 게이트웨이로 운영. 이는 "각 팀이 각자 MCP 서버를 만들고 에이전트가 제각각 연동"하는 방식이 조직 규모에서 깨진다는 것을 보여주는 숫자다.
- **도구 단위 접근 제어 + 응답 새니타이징** — Slack 발췌에 따르면 게이트웨이가 도구 단위 접근 제어와 응답의 개인정보·민감정보 제거를 수행한다는데, 구체적 구현(어떤 필드를 어떻게 마스킹하는지)은 발췌가 끊겨 확인하지 못했다.

## 내 생각 · 적용점

### 핵심 전이 1 — DoorDash 게이트웨이와 거의 동일한 해법, 다른 회사가 독립적으로 수렴

[[2026-08-10-doordash-ai-agent-gateway]]는 "MCP가 도구 설명·탐색·호출은 표준화했지만 인증·권한·자격증명·접근 회수·감사는 해결하지 않는다"고 정확히 같은 문제를 지적하며 "호출자 인증→권한확인→승인된 도구 노출→자격증명 주입→MCP서버 전달→사용기록"이라는 거의 동일한 파이프라인을 만들었다. Uber와 DoorDash가 **서로 다른 회사에서 독립적으로 같은 아키텍처(Registry/컨트롤플레인 + Proxy/데이터플레인, 도구 단위 승인)로 수렴**했다는 것은 이게 우연이 아니라 "MCP를 조직 규모로 쓰려면 반드시 거쳐야 하는 레이어"라는 신호다. DoorDash 노트의 결론 "통제된 경로가 셀프서비스가 아니면 팀은 우회한다"가 Uber의 AutoCrawler(자동 발견이라도 활성화는 팀 승인)에도 그대로 적용된다 — 자동화와 거버넌스를 동시에 만족시키는 게 핵심 난제.

### 핵심 전이 2 — MCP 프로토콜 자체가 이 게이트웨이들을 표준으로 흡수하려는 중

[[2026-08-23-mcp-new-roadmap-five-areas]]는 MCP 공식 로드맵이 "에이전트 신원과 엔터프라이즈 보안"을 5대 영역 중 하나로 다루며 이를 "DoorDash가 이미 직접 구축했던 게이트웨이를 프로토콜 표준으로 흡수하려는 시도"로 읽었다. Uber의 사례는 이 가설을 한 번 더 뒷받침한다 — **대형 테크 기업들이 각자 만든 Registry+Proxy 패턴이 결국 MCP 스펙 자체의 표준 기능이 될 가능성**이 높다. 지금은 회사마다 재발명 중인 게이트웨이가, 1~2년 내 "MCP 표준 준수"만으로 해결될 수도 있다는 뜻.

### 핵심 전이 3 — "MCP가 틀렸다"는 회의론과의 긴장

[[2026-05-29-mcp-is-dead-cli-skills]]와 [[2026-09-22-mcp-was-always-a-bad-idea]]는 각각 "컨텍스트 비용·지연·CLI 중복 문제로 MCP보다 Skills/CLI가 낫다", "모델이 강해질수록 API를 감싼 서버보다 직접 호출이 이긴다"고 주장한다. Uber의 800서버·5000도구 규모는 이 회의론과 정반대 방향의 증거처럼 보이지만, 사실은 **둘 다 맞을 수 있다** — 소규모·개인 워크플로우에는 CLI/Skills가 가볍고, 수백 개 팀·수천 개 내부 API를 가진 대기업 규모에는 중앙 게이트웨이의 거버넌스 가치가 지연 비용을 압도한다. "MCP가 맞냐 틀리냐"가 아니라 "조직 규모와 신뢰 경계가 어디냐"가 진짜 질문이라는 걸 이 사례가 보여준다.

### 핵심 전이 4 — Ask HN의 실전 원칙과 정합

[[2026-09-05-ask-hn-mcp-in-production]]는 "MCP가 실제로 쓸모 있는 지점은 여러 시스템을 함께 조사하거나, 허용할 기능만 좁게 노출할 때"로 수렴한다고 정리했다. Uber의 "도구 단위 접근 제어"와 "팀 승인 후 공개"는 정확히 이 "좁게 노출"의 플랫폼화된 버전이다.

## 호스피탈리티 / CRS 적용 포인트

온다처럼 다수의 호텔·PMS·OTA 연동 API를 가진 B2B 회사에게 이 패턴은 바로 적용 가능한 참조 모델이다. 지금 각 연동을 개별 커넥터로 관리한다면, 에이전트(내부 운영 봇이든 고객 대응 AI든)가 늘어날수록 "이 에이전트가 이 호텔 데이터에 접근해도 되는가"를 커넥터마다 따로 판단해야 하는 문제가 반드시 생긴다. Uber/DoorDash식 Registry(어떤 도구가 있고 누가 소유하고 활성화됐는지) + Proxy(실제 PMS/CRS API 호출로 변환, 응답에서 고객 PII 제거)는 **"MCP를 붙이기 전에 먼저 게이트웨이 레이어를 만들어라"**는 순서를 알려준다. 다만 온다 규모에서 800개 서버급 복잡도는 아직 멀고, 지금 단계에선 "도구 단위 접근 제어 + 응답 PII 마스킹"이라는 원칙만 먼저 설계에 반영하는 게 현실적이다.
