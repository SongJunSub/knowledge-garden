# DuckDB 2.0이 더 빠른 이유 (MotherDuck)

> 출처: [Why DuckDB 2.0 is faster](https://motherduck.com/blog/why-duckdb-20-is-faster/) (MotherDuck 블로그) · GeekNews 경유 [news.hada.io/topic?id=34456](https://news.hada.io/topic?id=34456) · 정리일 2026-09-29

> **출처 한계**: `news.hada.io`·`motherduck.com`·`duckdb.org`·`daily.dev` 전부 이 세션에서 egress 차단(`EGRESS_BLOCKED`)돼 원문을 직접 열람하지 못했다. 아래 내용은 ① 이번 작업 과제로 주어진 GeekNews 발췌(정확한 것으로 전제) ② WebSearch로 교차확인한 다수 매체(BigGo Finance, zeli.app, daily.dev 스니펫, duckdb.org 공식 포스트 제목·저자·날짜)를 재구성한 것이다. **duckdb.org 자체에 이 세 가지 개선을 각각 다룬 원 포스트가 따로 있다**는 것까지는 확인했다 — 비동기 I/O는 [Asynchronous I/O in DuckDB: Work, Thread, Work](https://duckdb.org/2026/07/31/asynchronous-io)(2026-07-31), 재귀 CTE는 [How DuckDB Runs Recursive CTEs Faster](https://duckdb.org/2026/08/25/how-duckdb-runs-recursive-ctes-faster)(2026-08-25, 저자 Denis Hirn)다. MotherDuck 글은 이 셋(+VARIANT)을 한데 묶어 "왜 더 빠른가"로 종합한 3자 요약 성격으로 보이며, **정확한 발행일과 벤치마크 원본 수치를 원문에서 직접 대조하지는 못했다.**

## 한 줄 요약

**DuckDB v1.5 이후 나온 2.0 알파의 속도 개선을 세 갈래로 뜯어본 글이다. ①S3 읽기 — 다운로드 전담 스레드 풀이 데이터를 미리 받아두면서 CPU 연산은 별도 워커가 병행해, 쿼리를 하나도 바꾸지 않고 대형 파일 실험에서 약 2~3배 빨라졌다. ②재귀 CTE — 엔진을 다시 써서 매 라운드마다 전체 테이블을 다시 스캔하는 대신 한 번 만든 조회 구조(키 기반 상태)를 재사용하게 했고, 2만 개 Git 커밋의 조상 탐색이 1.5.5의 1.8~16초에서 0.10초로 줄었다. ③VARIANT — 행마다 다른 모양일 수 있는 JSON류 데이터를 텍스트로 파싱하는 대신, 일관된 필드는 실제 컬럼으로 "분리 저장(shredding)"해서 JSON 필터링·집계를 텍스트 파싱보다 훨씬 빠르게 만든다.**

## 핵심 포인트

- **S3 비동기 I/O**: 별도의 **다운로드 전담 스레드 풀**이 워커보다 앞서 여러 row-group을 미리 받아 버퍼에 쌓아두고, 워커는 디코드에만 집중한다. `read_ahead_depth` 설정(기본값 `-1`, 스레드 수 기준 자동 조정)으로 얼마나 앞서 받을지 조절한다. **핵심은 I/O 계층이 쿼리 처리 계층과 독립적으로 확장된다는 것** — ***"쿼리를 바꾸지 않고도" 대형 파일 실험에서 약 2~3배*** 빨라진다는 게 이 글의 주장이다. 원 duckdb.org 포스트(Work, Thread, Work)는 네트워크 스토리지에서 이득이 가장 크다고 밝힌다.
- **재귀 CTE 엔진 재작성**: 기존 방식은 재귀 라운드마다 전체 테이블(또는 조인 구조)을 다시 읽었다. 새 엔진은 재귀를 ***하나의 장기 실행 연산***으로 취급해, 프론티어(다음 라운드로 넘길 노드 집합) 크기와 실제 작업량에 따라 실행 모드를 고르고, **키 기반 상태를 직접 탐색(probing)**해 반복 스캔을 없앤다. **2만 개 Git 커밋의 조상 탐색이 1.5.5의 1.8~16초에서 0.10초로** 줄었다는 것이 이 글의 핵심 수치다 — 이는 이전에 정리한 [[2026-08-18-duckdb-2-0-cyanoptera-preview]]에서 나온 "100만 엣지 도달 가능성 질의 40배(4.90초→0.12초)" 벤치마크와는 **다른 벤치마크**(그래프 구조·규모가 다름)이니 혼동하면 안 된다 — 둘 다 "재귀 CTE 엔진 재작성"이 낸 결과이되 측정 대상이 다르다.
- **VARIANT 필드 분리 저장**: JSON처럼 행마다 다른 모양일 수 있는 데이터를 담되, ***일관되게 나타나는 필드는 실제 타입이 있는 컬럼으로 분리해서(shredding) 저장***한다. 텍스트로 파싱하는 일반 JSON 방식보다 **필터링·집계가 훨씬 빠르고, 저장 공간도 작다**(WebSearch로 교차확인한 다른 매체 수치로는 대략 텍스트 파싱 대비 수 배, 저장 공간은 약 1/3 수준으로 보고되나, 이 정확한 배수를 원문에서 직접 확인하지는 못했다).
- **세 개선의 공통 방향**: ***"쿼리를 다시 짜지 않아도 빨라진다."*** S3 읽기는 설정만으로, 재귀 CTE는 엔진 재작성만으로, VARIANT는 일반 JSON 타입의 백엔드로 자동 적용된다(2.0 이후 일반 JSON 타입이 VARIANT로 뒷받침됨, [[2026-08-18-duckdb-2-0-cyanoptera-preview]] 참고). **사용자 쪽 코드 변경 없이 인프라 계층에서 속도를 얻는다는 설계 철학이 세 기능 모두에 관통한다.**

## 인상 깊은 문장

> "2만 개 Git 커밋의 조상 탐색이 1.5.5의 1.8~16초에서 0.10초로 줄어듦"
> (과제로 주어진 GeekNews 발췌 인용) — **범위가 "1.8~16초"로 넓다는 점이 눈에 띈다.** 단일 숫자가 아니라 범위를 제시했다는 건, 그래프 형태나 깊이에 따라 기존 엔진의 성능이 들쑥날쑥했다는 뜻으로 읽힌다. 새 엔진이 0.10초로 **그 편차 자체를 없앴다**는 게, 단순 "몇 배 빨라졌다"보다 더 실질적인 개선일 수 있다.

## 댓글

**hada 댓글 수·HN/Lobsters 큐레이션 유무는 이 세션에서 확인 불가**(`news.hada.io` 전면 차단). duckdb.org의 원 재귀 CTE 포스트가 Hacker News에 올라갔던 정황은 WebSearch로 간접 확인했으나(비동기 I/O 포스트의 HN 아이템 ID는 확인, 재귀 CTE 포스트 자체의 HN 스레드는 별도 미확인), 이 세션에서 그 댓글 내용을 직접 읽지는 못했다. **읽을 때 감안**: ①MotherDuck은 DuckDB의 상용 파트너사(클라우드 데이터 웨어하우스 제공)라 DuckDB 호의적 서술의 이해관계가 있다. ②전부 **자체/파트너사 벤치마크**이며 제3자 독립 재현은 확인하지 못했다. ③여전히 **알파** 단계다.

## 내 생각 · 적용점

### 핵심 전이 1 — 이 글은 8월에 정리한 미리보기 노트의 "숫자를 채우는" 후속편이다

**[[2026-08-18-duckdb-2-0-cyanoptera-preview]]**를 정리하며 남긴 회고 항목이 정확히 ***"VARIANT의 쓰기 비용에 대한 보고가 나왔는지"***, ***"우리 분석 워크로드에서 파티션 인식 이득을 재봤는지"***였다. 이 글은 그 회고의 절반에 답한다 — **VARIANT의 읽기 성능 이득은 구체화됐지만, 쓰기 비용은 이번에도 언급되지 않는다.** [[2026-08-10-postgresql-mvcc-tradeoffs]]에서 세운 원칙 ***"비용은 사라지지 않고 자리만 옮긴다"***가 여기서도 미해결 과제로 남는다 — shredded 저장이 읽기를 빠르게 하는 대가로 스키마 변화·쓰기에 어떤 비용을 지우는지는 알파 단계 벤치마크에 아직 없다.

### 핵심 전이 2 — "쿼리를 안 바꿔도 빨라진다"는 설계는 AWS의 DuckLabs 인수 이후 처음 나온 성과물이라는 맥락에서 봐야 한다

**[[2026-08-27-aws-acquires-ducklabs-duckdb]]**에서 정리했듯, DuckLabs 창업자는 ***"하루 100만 건 다운로드를 지원하는 과정에서 소규모 자력 성장 팀이 병목이 될 것"***이라는 이유로 AWS 인수를 택했다. 2.0의 세 가지 개선(비동기 I/O, 재귀 CTE 재작성, VARIANT) 모두 **엔진 내부 재작성이라는 무거운 작업**이다. 인수 발표(2026-08-26)와 2.0 관련 포스트들(2026-07-31, 08-17, 08-25)의 시점이 겹친다는 건, **이 개선들이 인수 이후의 여력이 아니라 인수를 정당화한 그 "병목" 자체의 산물**일 가능성이 높다 — 즉 AWS 리소스가 아니라 기존 팀이 이미 진행 중이던 작업이 인수 시점과 맞물려 나온 것으로 읽는 게 더 정확해 보인다.

### 핵심 전이 3 — 재귀 CTE 벤치마크 두 개를 나란히 놓으면 "그래프 형태에 따라 배수가 다르다"는 게 보인다

이 글의 "2만 개 커밋, 1.8~16초→0.10초"(최대 약 160배)와 미리보기 노트의 "100만 엣지, 4.90초→0.12초"(약 40배)를 나란히 두면, **같은 엔진 재작성이 그래프의 형태(깊고 좁은 커밋 히스토리 vs 넓은 일반 그래프)에 따라 다른 배수를 낸다**는 게 드러난다. [[2026-08-18-duckdb-2-0-cyanoptera-preview]]에서 적었던 ***"40배는 재귀 CTE라는 특정 질의 형태에서 나온 값이고, 일반 워크로드의 배수가 아니다"***라는 경계가 이번 결과로 다시 확인된다 — **깊은 계층 구조(조직도, 커밋 히스토리, 댓글 트리)일수록 이득이 크고, 넓고 얕은 그래프에서는 이득이 상대적으로 작을 가능성**을 이 두 벤치마크의 격차가 시사한다.

## 호스피탈리티 / CRS 적용 포인트

- **재귀 CTE 개선은 CRS와 직접 접점이 있다.** 호텔 체인·브랜드·프로퍼티 계층 구조, 객실 타입의 상속 관계, 요금 규칙의 오버라이드 체인처럼 ***깊은 트리/체인 구조를 재귀 CTE로 순회하는 쿼리***가 CRS에서 드물지 않다. 이번 벤치마크가 보여준 "깊은 체인일수록 이득이 크다"는 패턴이 정확히 이런 워크로드에 들어맞을 가능성이 있다.
- **S3 비동기 I/O는 파트너 데이터 레이크 분석에 그대로 적용 가능하다** — 채널·파트너별 원본 로그를 S3 Parquet로 쌓아두고 배치 분석하는 구조라면, 쿼리 변경 없이 읽기 속도만 얻는다는 설계가 매력적이다.
- **VARIANT는 채널 페이로드 보관 후보라는 평가를 이전 노트에서 이미 남겼다** — 이번 글로 읽기 성능 근거가 좀 더 쌓였지만, **쓰기 비용 미확인이라는 유보는 그대로 유지**한다.
- **여전히 알파다.** 프로덕션 도입 판단은 가을 정식 릴리스와 제3자 재현 벤치마크가 나온 뒤로 미루는 게 안전하다.
