# 1.1.1.1 DNS 캐시 최적화로 메모리 100TB 절감 (Cloudflare)

> 출처: [How we saved 100 terabytes of memory by optimizing 1.1.1.1's DNS cache](https://blog.cloudflare.com/dns-cache-memory-optimization-1111/) (Cloudflare Blog) · 정리일 2026-08-28
> **출처 한계**: `news.hada.io`와 `blog.cloudflare.com` 둘 다 이 세션의 네트워크 egress 프록시에 막혀 직접 열지 못했다(`noise.getoto.net`·`gigazine.net`·`news.ycombinator.com` 등 2차 소스도 전부 동일하게 차단). 아래 내용은 WebSearch가 반환한 검색엔진 요약·스니펫을 여러 차례 교차 조회해 재구성한 것이다 — 핵심 수치(953→420바이트, 100TB, 처리량/지연시간 개선폭)는 서로 다른 검색어로 3회 이상 일관되게 재현돼 신뢰도가 높다고 판단한다. 다만 **"항목당 할당 크기가 1.1KB→461바이트로 줄었다"는 수치는 두 차례 검색에서만 확인됐고 953/420바이트 수치와 정확히 어떻게 다른 지표인지(할당 크기 vs 실사용 바이트) 원문 문단으로 대조하지 못했다** — 참고용으로만 남긴다. 5가지 최적화의 정확한 순서·이름, 코드 스니펫, GitHub 이슈/PR 존재 여부는 원문을 직접 읽지 못해 확인 불가.

## 한 줄 요약

**Cloudflare의 재귀 DNS 리졸버 "Big Pineapple"(1.1.1.1을 구동하는 Rust 기반 시스템)이 2,500억 개가 넘는 DNS 캐시 항목의 메모리 레이아웃을 다섯 차례 손봐 항목당 953바이트에서 420바이트로 56%를 줄였고, 그 결과 전체 서버군에서 약 100TB — Gen 13 서버 130대 분량의 RAM에 해당 — 를 확보했다.** 트릭 하나하나는 "Vec 대신 Box<[T]>를 써라" 수준의 평범한 Rust 관용구지만, 2,500억이라는 항목 수 앞에서는 "1바이트 낭비 = 250GB"라는 등식이 성립해 이 평범함이 곧 파급력이 된다. 더 중요한 건 메모리를 아끼면서 속도도 함께 올랐다는 점 — 삽입 처리량 43% 증가, 조회 지연시간 19% 감소 — 로, "메모리 vs 속도" 트레이드오프를 상정하지 않고 둘 다 잡았다는 게 이 글의 핵심 주장이다.

## 핵심 포인트

- **왜 1바이트가 250GB인가** — 캐시 항목이 2,500억 개 이상 상시 존재하는 규모에서는, 항목 구조체에 붙은 사소한 오버헤드(패딩·포인터·길이 필드) 하나하나가 전체 시스템 관점에서 기가바이트·테라바이트 단위로 증폭된다. 저수준 최적화가 "마이크로 벤치마크에서만 의미 있는 자기만족"이 아니라 **인프라 규모가 그 자체로 최적화의 정당성을 만든다**는 사례.
- **Vec/String → Box<[T]>/Box<str>** — 캐시 항목의 값이 한 번 만들어진 뒤 크기가 바뀌지 않는 필드(레코드 목록, 도메인 이름 등)라면, 향후 재할당 여력을 위해 `capacity`를 따로 들고 있는 `Vec`/`String`은 낭비다. 불변 슬라이스인 `Box<[T]>`/`Box<str>`로 바꾸면 필드당 8바이트(포인터 3개 중 1개, capacity 워드)를 아낀다 — 항목당 8개 필드에 적용해 **64바이트/항목** 절감.
- **DNS 섹션(answer/authority/additional)을 하나의 목록 + 오프셋으로 통합** — 원래 각 섹션마다 별도의 `Box<[T]>`(8바이트 포인터 + 8바이트 길이)를 들고 있던 걸, 레코드 수가 `u16` 범위 안에 들어온다는 사실을 이용해 **섹션 경계를 2바이트 오프셋 2개로 대체** — 리스트 2개(16바이트×2) 대신 오프셋 2개(2바이트×2)로 줄여 **28바이트/항목** 절감.
- **중복되는 레코드 소유자 이름(owner name) 생략** — DNS 압축 포인터와 같은 발상으로, 같은 도메인이 여러 레코드의 owner로 반복될 때 두 번째부터는 값을 다시 들고 있지 않고 최초 등장 위치를 가리키게 한다.
- **큰 Rust enum variant를 박싱** — 레코드 타입을 나타내는 enum의 변형(variant) 중 크기가 큰 것들을 박싱해 enum 전체 크기를 그 최대 variant가 아니라 포인터 크기로 맞춘다. 다만 이 단계만 놓고 보면 각 boxed variant가 힙의 서로 다른 위치에 흩어져 포인터를 따라가야 하는 **지역성 저하**라는 부작용이 남는다 — 그래서 다음 단계로 이어진다.
- **레코드 데이터를 단일 DNS 와이어 포맷 버퍼로 통합** — 파싱된 enum 목록 대신, 레코드 각각을 "2바이트 길이 프리픽스 + 원본 바이트"로 이어붙인 **단일 `Box<[u8]>`**에 저장한다. enum variant별 힙 할당과 태그 오버헤드가 사라지고 데이터가 연속된 메모리에 놓여 **캐시 지역성이 좋아지는 대신, 레코드를 임의 인덱스로 바로 못 찾고 순차 순회해야 하는 트레이드오프**를 명시적으로 감수한다.
- **벤치마크: 속도까지 함께 개선** — 삽입 처리량 +43%, 조회 지연시간 -19%. 할당 횟수가 줄고 메모리가 조밀해진 게 CPU 캐시 미스를 줄인 결과로 읽힌다 — "메모리를 줄이면 보통 속도도 손해 본다"는 통념에 반례를 제시한다.
- **회수한 100TB의 용도** — 단순히 비용을 아끼는 데 그치지 않고, 같은 메모리 예산 안에서 **캐시 용량을 늘려 캐시 히트율을 높이고 업스트림 네임서버로 나가는 쿼리 수를 줄이는 데 재투자**할 계획이라고 밝혔다 — 절감분을 스케일업이 아니라 서비스 품질 개선으로 되돌리는 선택.

## 내 생각 · 적용점

### 핵심 전이 1 — 어제 정리한 "나눗셈을 곱셈+시프트로" 트릭과 같은 축, 그러나 "규모가 정당화를 대신한다"는 점에서 결이 다르다

[[2026-08-27-weekday-calculation-mersenne-bit-tricks]]에서 정리한 요일 계산 비트 트릭은 스스로도 인정했듯 "`% 7` 하나가 병목일 일은 거의 없다"는 한계를 안고 있었다 — 그 글의 진짜 가치는 실무 적용보다 사고 패턴 자체였다. 이 Cloudflare 글은 **같은 종류의 저수준 크래프트(구조체 레이아웃·불필요한 capacity 제거·enum 박싱)를 쓰지만, 정당화 방식이 정반대**다. 요일 계산 글은 "이론적으로 흥미로운 기법"에 머물렀던 반면, 이 글은 **"2,500억 개"라는 구체적 항목 수를 제시해 "필드당 8바이트가 왜 중요한가"를 즉시 증명**한다. 저수준 최적화 글을 읽을 때 물어야 할 질문이 여기서 드러난다 — "이 기법 자체가 우아한가"가 아니라 **"이 시스템에서 곱해지는 수가 몇 자리인가"**다.

### 핵심 전이 2 — SIMD 글의 "기회를 알아보되 두려워 말라"는 원칙이 데이터 구조 레벨에서도 성립

[[2026-07-24-everyone-should-know-simd]]가 CPU 명령어 레벨에서 "연속 데이터를 다루는 루프는 대체로 SIMD 후보"라고 했다면, 이 글은 그 한 단계 위 — **메모리 레이아웃 레벨**에서 같은 태도를 보여준다. `Vec`을 `Box<[T]>`로, 여러 리스트를 오프셋 페어로, 파싱된 enum을 와이어 포맷 원본 바이트로 — 다섯 단계 전부 "이 필드가 정말 가변 길이여야 하나? 이 구조가 정말 임의 접근이 필요한가?"라는 **같은 질문을 반복 적용한 결과**다. 셋 다(요일 계산·SIMD·이 글) 결국 하나의 원칙으로 수렴한다: **불필요하게 일반적인 자료구조(가변 크기·임의 접근을 상정한)를 실제 필요보다 더 좁게 특수화하면, 그 특수화 자체가 성능이 된다.**

## 호스피탈리티 / CRS 적용 포인트

**직접 적용은 멀다.** 온다 CRS의 캐시·데이터 규모는 2,500억 항목·서버군 단위가 아니고, 우리 시스템의 병목은 대개 I/O·DB 쿼리·외부 OTA 연동 지연이지 인메모리 구조체 패딩이 아니다 — 이 정도 규모가 아니면 `Vec`을 `Box<[T]>`로 바꾸는 리팩터링은 가독성만 낮추고 실측 이득은 없을 확률이 높다. 다만 **전이 가능한 원칙 두 가지는 남긴다**: ①**"이 값이 실제로 가변 길이/가변 접근이 필요한가, 아니면 한 번 만들고 다시 안 바뀌는가"**라는 질문은 Rust뿐 아니라 우리가 캐싱하는 예약·요금 스냅샷 구조에도 그대로 적용 가능한 설계 질문이다(예: 확정된 예약 요금 스냅샷을 굳이 가변 컬렉션에 담고 있지는 않은지). ②**"항목 수 × 항목당 낭비 바이트"로 정당화를 계산하는 습관** — 캐시 항목이 수백만~수천만 단위로 쌓이는 예약 가용성 캐시·요금 캐시가 있다면, 이 "곱셈으로 정당화 판단하기" 자체는 규모와 무관하게 옮겨올 수 있는 사고방식이다.
