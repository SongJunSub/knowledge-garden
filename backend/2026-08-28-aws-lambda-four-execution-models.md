# AWS Lambda의 4가지 실행 모델

> 출처: [AWS Lambda의 4가지 실행 모델 – 구조와 선택 기준](https://aws.amazon.com/ko/blogs/tech/aws-lambda-four-execution-models-structure-and-selection-criteria/) (AWS 기술 블로그, Slack `#개발-뉴스-dev-news` TechArticles 봇 직접 공유) · 정리일 2026-08-28
> **출처 한계**: `aws.amazon.com` 전체가 이 세션에서 egress 차단이라 **원문을 한 번도 직접 열지 못했다.** web.archive.org·InfoQ·dev.to·hidekazu-konishi.com·cloudvisor.co·aws.plainenglish.io 등 원문을 인용했을 법한 2차 소스도 전부 차단되어, 이 노트는 **WebSearch 결과 스니펫(구글 인덱스에 걸린 2차 요약 문장들)만으로 재구성**한 것이다. 게시일·저자·원문의 정확한 수치·직접 인용은 확인하지 못했다. 아래 "4가지 모델" 이름과 특징은 검색 스니펫에서 일관되게 반복되는 내용을 종합한 것이라 신뢰도가 있지만, **원문의 표현·강조점과는 다를 수 있다.**

## 한 줄 요약

**AWS Lambda는 2014년 출시 이후 유지해온 "이벤트당 함수 하나(기본 함수)" 모델에 세 가지 실행 모델을 더했다 — 상시 고트래픽용 관리형 인스턴스(Managed Instances), 최대 1년까지 도는 내구성 함수(Durable Functions), Firecracker 마이크로VM 기반 격리·상태보존 실행 환경(MicroVMs, 2026년 상반기 발표).** 넷 다 같은 Firecracker 마이크로VM 기반 위에서 동시성·지속시간·생명주기 제어를 다르게 선택한 변형이며, 글의 핵심 메시지는 "짧고 터지는 이벤트 처리는 기본 함수로 충분하지만, 상시 고트래픽·장기 워크플로우·격리가 필요한 샌드박스 실행은 각각의 특화 모델로 옮겨야 한다"는 워크로드 기반 선택 기준을 세우는 것으로 보인다.

## 핵심 포인트

- **① 기본 Lambda 함수 (Standard Functions)** — 2014년부터 존재해온 원조 모델. S3 업로드·DynamoDB 스트림 같은 **버스트성·예측 불가 이벤트 트리거**의 "최전선". 0에서 초당 1000 요청까지 가장 빠르게 확장. 이미지 리사이징·로그 처리 같은 **소규모 fire-and-forget 작업**에 최적.
- **② 관리형 인스턴스 (Managed Instances)** — 고객 소유 EC2 인스턴스 위에서 함수 코드를 돌리되 운영 부담은 Lambda가 관리하는 모델. **상시 고트래픽 API·백그라운드 워커**를 위한 "steady-state 컴퓨트 레이어" — 계속 도는 워크로드에 요청당 과금은 불필요한 비용이라는 문제의식에서 나온 것으로 보인다. 서버리스 배포 흐름은 유지하면서 **예측 가능한 지연시간의 전용 용량**을 제공.
- **③ 내구성 함수 (Durable Functions)** — 다단계·장기 실행 워크플로우를 Lambda 안에서 직접 구현하는 모델. **분·시간 단위를 넘어 최대 1년**까지 실행 가능하고, 체크포인팅·일시중단·자동 복구가 내장돼 있다는 설명이 검색 스니펫에서 반복 확인된다.
- **④ 마이크로VM (Lambda MicroVMs)** — 2026년 6월경 발표(InfoQ 보도 기준)된 신규 실행 원시타입. **Firecracker 마이크로VM으로 사용자 세션·AI 에이전트가 생성한 코드를 하드웨어 수준 격리**로 실행하고, 스냅샷 기반 즉시 기동·재개, **최대 8시간 상태 보존**을 지원. "격리냐 즉시성이냐 상태 보존이냐 중 하나만 고르던 트레이드오프를 없앴다"는 것이 이 모델의 핵심 주장으로 보인다.
- **공통 기반** — 네 모델 모두 Lambda의 Firecracker 마이크로VM 실행 환경을 공유하되, **동시성·지속시간·생명주기 제어권을 얼마나 세분화해서 노출하느냐**가 다르다. "서버리스 = 함수 하나"라는 등식이 더 이상 성립하지 않는다는 게 이 발전 방향의 함의로 읽힌다.

## 내 생각 · 적용점

### 핵심 전이 1 — "이벤트 기반이 이론상 맞다"는 이유만으로 기본 함수를 고르면 이번 글이 경고하는 실패 사례가 된다

[[2026-08-16-not-tech-debt-just-mess]]가 다룬 예시 중 하나가 정확히 이 지점이다 — 이벤트 기반 경험이 없는 팀이 "이론상의 확장성"을 보고 AWS Lambda 이벤트 기반 아키텍처를 골랐는데, 실제 부하는 **초당 약 0.5 이벤트**였고 대신 추적성 문제와 빈약한 계측만 남았다. 이번 글의 선택 기준("이벤트 기반 처리는 기본 함수, 상시 고트래픽은 관리형 인스턴스, 장기 워크플로우는 내구성 함수")을 거꾸로 읽으면, 그 팀의 실패는 **워크로드의 실제 성격(낮고 꾸준한 부하)과 고른 모델(버스트 대응용 기본 함수)이 애초에 안 맞았던 오판**이었다는 게 더 선명해진다. "서버리스니까 기본 함수"가 아니라 "우리 부하 패턴이 뭔지부터 재고 고른다"는 원칙이 두 글에서 같은 방향을 가리킨다.

### 핵심 전이 2 — Lambda MicroVMs의 "격리된 에이전트 코드 실행"은 로컬 마이크로VM 샌드박스와 같은 문제의 클라우드판 답이다

[[2026-06-08-apple-container-machine]]은 Apple Container Machine(Mac에서 경량 Linux VM)을 **AI 에이전트를 안전하게 격리해 돌릴 로컬 샌드박스**로 다뤘다. 이번 Lambda MicroVMs는 정확히 같은 문제 — "사용자/AI 에이전트가 만든 신뢰할 수 없는 코드를 어떻게 격리 실행할까" — 를 **클라우드·매니지드 인프라 위에서** 푼 것으로 읽힌다. 하나는 "내 컴퓨터에서 로컬 VM으로", 다른 하나는 "AWS가 관리하는 Firecracker VM으로" — 격리 단위를 VM 수준으로 잡는다는 설계 판단 자체는 같다. 에이전트가 생성한 코드를 실행해야 하는 상황이 늘어날수록 "프로세스 격리로 충분한가, VM 격리가 필요한가"를 묻는 이 축이 반복해서 등장할 것 같다.

### 핵심 전이 3 — 관리형 인스턴스는 "서버리스인데 비용 모델이 섞여 있다"는 지적을 정면으로 인정한 결과물로 보인다

[[2026-08-20-aws-scte35-ai-ad-insertion]]은 Lambda·Step Functions(호출 과금)와 관리형 ML 엔드포인트(시간 과금)가 한 파이프라인에 섞이는 걸 두고 "서버리스 아키텍처라고 부르지만 비용 모델이 섞여 있다"고 짚었다. 관리형 인스턴스의 등장 이유로 추정되는 문제의식("계속 도는 함수에 요청당 과금은 불필요한 세금")은 이 지적과 같은 자리에서 출발한다 — 다만 이번엔 그 비용 불일치를 감추지 않고, 아예 **워크로드 성격에 맞는 과금 모델을 골라 쓰라고 새 실행 모델로 공식화**한 셈이다. "서버리스는 균일한 과금 모델이 아니다"라는 관찰이 두 글에서 대구를 이룬다(가벼운 연결).

## 호스피탈리티 / CRS 적용 포인트

- 온다 백엔드가 실제로 AWS Lambda를 쓰고 있다면, 이번 글의 선택 기준은 **직접 적용 가능성이 있다** — 예를 들어 PMS/OTA 연동처럼 호출당 부하가 들쭉날쭉한 이벤트 처리는 기본 함수가, 정산·예약 동기화처럼 상시 트래픽이 꾸준한 백그라운드 워커는 관리형 인스턴스가, 야간 배치 정산·장기 재시도가 필요한 워크플로우는 내구성 함수가 각각 더 맞을 수 있다는 구도다.
- 다만 이 판단은 **원문을 못 읽은 상태에서 워크로드 이름만 대응시킨 것**이라, 실제 비용·지연시간 트레이드오프는 온다 팀이 각 모델의 정식 문서와 요금 정책을 직접 확인해야 확정할 수 있다 — 이 노트가 그 확정까지 대신할 수는 없다.
- Lambda MicroVMs(격리된 에이전트/사용자 코드 실행)는 현재 온다 CRS 도메인에 당장 적용할 유스케이스가 뚜렷하지 않다 — AI 에이전트가 파트너/사용자 코드를 실행해야 하는 기능이 생긴다면 참고할 만한 선례 정도로 남겨둔다.
