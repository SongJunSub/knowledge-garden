# syncular, 로컬 SQLite를 서버 권위형 커밋 로그와 동기화하는 오프라인 우선 엔진

## 한 줄 요약

**syncular는 각 클라이언트에 실제 SQLite DB를 두고, 서버가 관리하는 순서 보장 커밋 로그와 동기화하는 서버 권위형(server-authoritative) 오프라인 우선 데이터 계층이다.** 읽기·조인·집계·인덱스 조회를 전부 네트워크 요청 없이 로컬 SQL로 처리해 오프라인에서도 앱 핵심 기능이 그대로 작동하고, 쓰기는 로컬 DB에 즉시 반영하면서 동시에 내구성 있는 아웃박스에 쌓아 연결 복구 시 멱등 커밋으로 서버에 전송한다. TypeScript·Rust 두 코어가 하나의 프로토콜을 99개 적합성 시나리오로 동일하게 구현하는 것이 특징이며, 아직 **1.0 이전(pre-1.0), Apache 2.0, 개인 메인테이너 1인** 프로젝트다.

## 핵심 포인트

- **아키텍처의 핵심 축은 "서버가 진실의 원천이지만, 클라이언트는 진짜 DB를 갖는다"는 이중 구조** — 흔한 캐시형 오프라인 지원(로컬은 캐시일 뿐, 서버가 유일한 실행 엔진)과 달리, ***"앱은 로컬 SQLite에서 읽고 오프라인 상태에서도 계속 작동한다"***(README) — 조인·집계·인덱스 조회까지 로컬에서 완결된다는 게 다른 지점이다.
- **쓰기 흐름 = 즉시 반영 + 아웃박스 + 멱등 커밋** — 쓰기는 로컬 상태를 먼저 갱신하고, 내구성 있는 아웃박스에 진입한 뒤, 연결이 복구되면 서버로 전송돼 검증받는다. 서버는 애플리케이션이 정의한 사용자별 접근 범위(scope)로 커밋을 검증하고, 승인된 변경만 다른 클라이언트에 전파한다 — **낙관적 로컬 반영 + 비관적 서버 검증**을 결합한 구조.
- **크로스 플랫폼 범위가 넓다** — 웹(OPFS 기반 브라우저 SQLite), Swift/Kotlin/Flutter/React Native/Tauri 네이티브, Rust 공유 코어. 서버는 Bun/Node/Cloudflare Workers 위에서 SQLite·Postgres·D1을 지원.
- **성능 수치(README/공식 사이트 스니펫, 원문 검증은 못함)** — 10만 행 부트스트래핑 30ms, 실시간 전파 p95 0.2ms, 웹 클라이언트 크기 gzip 31.3KB. 벤치마크 방법론·환경은 확인 못했다.
- **CRDT·부가 기능** — 컬럼 단위 협업 텍스트를 위한 CRDT 컬럼(Yjs 통합 언급), 오프라인 FTS5 전문검색 프로젝션, 타입 있는 SQL/SYQL로 TS·Swift·Kotlin·Dart·Rust API 자동 생성, S3/R2 콘텐츠 주소 첨부파일, 선택적 종단간 암호화(portable keyring), 부분 복제를 위한 windowed sync.
- **정직하게 명시된 미성숙도** — README가 직접 ***"pre-1.0이며 현재 Benjamin Kniffler 1인이 유지 중, 공개 API·프로토콜이 1.0 이전 변경될 수 있다"***고 밝힌다. GitHub 스타 264·포크 8(이 세션 확인 시점 기준) — 초기 단계 프로젝트다.

## 내 생각 · 적용점

**핵심 전이 1 — [[2026-08-25-sqlite-for-everything]]가 짚은 "서버가 사라지면 그 서버를 둘러싼 아키텍처 결정도 사라진다"는 원칙이, syncular에서는 정반대 방향에서 재확인된다.** 그 노트는 SQLite로 서버 자체를 단일 파일로 압축해 "배포·스케일링·백업 같은 서버 중심 아키텍처 결정 다수가 통째로 사라진다"고 짚었다. syncular는 서버를 없애는 게 아니라 **클라이언트마다 서버급 데이터베이스를 심어서, "네트워크 왕복"이라는 아키텍처 결정 자체를 없앤다** — 읽기·조인·집계가 로컬에서 끝나니 API 설계·캐싱 전략·로딩 스피너 같은 흔한 프론트엔드 아키텍처 고민 다수가 통째로 사라지는 셈이다. 두 노트를 겹치면, **"SQLite를 어디에 두느냐"에 따라 없어지는 아키텍처 결정의 종류가 서버 쪽이냐 클라이언트 쪽이냐로 갈린다**는 대칭 구조가 보인다.

**핵심 전이 2 — [[2026-08-13-tailscale-sqlite-wal-reset-bug]]가 남긴 "지루한 기술을 비표준으로 쓰면 리스크"라는 교훈을 syncular 채택 여부 판단에 직접 적용할 수 있다.** 그 노트의 핵심은 검증된 SQLite도 남들과 다른 방식(공격적 수동 체크포인트)으로 쓰면 검증 커버리지 밖으로 나간다는 것이었다. syncular는 SQLite 자체는 표준적으로 쓰겠지만, **"클라이언트마다 실제 DB + 서버 커밋 로그 + 아웃박스 + 멱등 커밋"이라는 조합 전체는 syncular라는 pre-1.0·1인 프로젝트가 처음 시도하는 조합**이다. Tailscale 노트의 실무 규칙("이 기능을 우리 말고 또 누가 쓰나")을 그대로 적용하면, 지금 syncular를 프로덕션에 넣는 건 "검증된 SQLite 위에, 아직 검증되지 않은 동기화 프로토콜"을 올리는 것과 같다 — 흥미롭다고 바로 채택할 계층이 아니라 지켜볼 계층이라는 뜻.

**핵심 전이 3 — 아웃박스·멱등 커밋 패턴은 CRS의 예약·정산 도메인과 이름이 같은 문제를 이미 풀고 있다.** "로컬에 즉시 반영 + 내구성 있는 큐 + 재전송 시 멱등 처리"는 분산 시스템에서 낯선 패턴이 아니다 — 다만 syncular는 이걸 **서버-서버가 아니라 서버-클라이언트(모바일 기기, 브라우저) 사이**에 적용한다는 게 다르다. 온다 CRS가 프론트엔드에서 오프라인 내성이 필요한 화면(현장 체크인 기기, 네트워크가 불안정한 호텔 백오피스 단말)을 갖고 있다면, "네트워크가 끊겨도 로컬 SQLite로 계속 동작하고, 복구되면 멱등하게 밀어 넣는다"는 이 패턴 자체는 스스로 구현하든 syncular 같은 기성 엔진을 쓰든 참고할 가치가 있다.

## 호스피탈리티 / CRS 적용 포인트

**전이 가능한 원칙은 분명하지만, syncular 자체의 직접 도입은 아직 이르다.**
- **적용 후보 시나리오**: 호텔 프런트/백오피스 태블릿처럼 네트워크가 간헐적으로 끊기는 현장 단말에서, 예약 조회·재고 확인 같은 읽기 작업과 체크인 상태 변경 같은 쓰기 작업을 오프라인에서도 이어가야 한다면, syncular의 "로컬 실제 DB + 서버 권위형 검증 + 아웃박스" 구조는 정확히 이 문제를 겨냥한다.
- **지금 도입하지 않아야 할 이유**: pre-1.0·1인 메인테이너·프로덕션 채택 사례 미확인이라는 성숙도 문제(위 "댓글" 섹션)에 더해, **예약·정산처럼 중복 처리가 곧 매출 오류로 이어지는 도메인에서는 "동시 오프라인 수정 시 row 단위 충돌을 어떻게 해소하는지"가 명확히 검증되기 전까지 채택 근거가 얇다** — CRDT 컬럼은 텍스트 협업용으로만 언급될 뿐, 일반 데이터 충돌 정책은 이번 리서치로 확인하지 못했다.
- **당장 쓸 수 있는 원칙만 남긴다면**: "쓰기는 로컬에 즉시 반영 + 아웃박스에 적재 + 서버가 scope 기반으로 검증"이라는 흐름 자체는 syncular를 쓰지 않아도 CRS 오프라인 시나리오 설계 시 참고할 수 있는 일반 패턴이다.
