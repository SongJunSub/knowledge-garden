# Stave (sufield) — 개별 설정은 정상이어도 리소스 사이의 '경로'는 뚫려 있을 수 있다

> 출처: [sufield/stave](https://github.com/sufield/stave) (GitHub) · 정리일 2026-09-05

## 한 줄 요약

**Stave는 AWS 계정을 직접 스캔하지 않고, 외부 익스트랙터가 만든 인프라 스냅샷(`obs.v0.1` JSON)을 오프라인·결정론적으로 분석해 리소스 개별 설정이 아니라 "리소스와 리소스, 리소스와 권한 사이의 연결"에서 발생하는 복합 리스크를 찾아내는 보안 검증 도구다. S3 암호화·공개 접근 차단이 개별적으로는 완벽해도, Bedrock 에이전트 → Lambda → 민감한 S3 데이터로 이어지는 경로에 제약이나 감사 기록이 빠져 있으면 그 자체가 취약점이라는 게 핵심 전제다.**

## 핵심 포인트

- **경로 지향 분석** — S3 암호화·퍼블릭 액세스 차단 같은 ***개별 컨트롤이 전부 그린이어도***, Bedrock 에이전트 → Lambda → 민감 S3로 이어지는 접근 사슬에 제약·감사 로그가 없으면 위험으로 잡아낸다. 개별 검사의 합이 시스템 안전을 보장하지 않는다는 관점.
- **유령 참조(ghost reference) 23개 컨트롤** — 삭제된 IAM 역할을 가리키는 정책, 사라진 Lambda를 여전히 호출하는 에이전트, 없어진 S3 버킷을 가리키는 CNAME처럼 ***대상은 사라졌는데 참조만 남아 있는*** 설정을 IAM 정책·리소스 정책·이벤트 트리거·컴퓨트 의존성·네트워크·크로스어카운트 신뢰 전 영역에서 탐지한다.
- **에어갭드(air-gapped) 설계** — AWS 계정에 자격 증명으로 직접 접속해 스캔하지 않는다. 별도 익스트랙터가 만든 `obs.v0.1` 스냅샷을 입력으로 받아 **Extract → Validate → Apply → Act** 파이프라인으로 정적 분석만 수행 — 실계정 접근 권한 없이도 감사가 가능하다는 설계 철학이다.
- **규모** — 73개 도메인(S3·IAM·Lambda·Bedrock 등)에 걸친 2,585개 내장 컨트롤, 30개 이상의 복합 체인(compound chain) 정의로 다단계 공격 경로를 매칭한다.
- **권한 상승 커버리지** — Rhino Security Labs가 정리한 21개 AWS 권한 상승 기법 중 20개를 26개 ESCALATE 컨트롤로 커버.
- **감사 산출물** — HIPAA·CIS AWS v3.0·SOC 2·PCI-DSS v4.0 등 10개 컴플라이언스 프로파일에 맞춘 증거, MITRE ATT&CK 정렬 공격 단계 요약, blast radius(폭발반경) 배수 기반 리스크 랭킹을 만들어낸다.

## 내 생각 · 적용점

### 핵심 전이 1 — 개별 컨트롤의 합은 시스템 안전을 보장하지 않는다

이건 [[2026-08-28-aws-frontier-agents-security-pentest]]와 같은 축의 문제의식이다. 그 글의 AWS Security Agent는 "실행 중인 앱을 실제로 공격"해 다단계 공격 체인(정보 노출 + 권한 상승 등)을 증명하는 **동적·능동적** 접근이었다면, Stave는 **정적·오프라인 스냅샷 분석**으로 같은 문제(개별 컨트롤은 그린인데 사슬은 뚫림)를 다른 축에서 푼다 — 같은 질문에 대한 두 가지 답.

### 핵심 전이 2 — "사라졌는데 참조만 남은 것"이 보안 문제가 되는 일반 패턴

유령 참조(ghost reference) — 삭제된 역할을 가리키는 정책, 없어진 버킷을 가리키는 CNAME 등 — 는 코드베이스의 "죽은 코드가 아니라 죽은 링크"에 해당한다. dangling CNAME이 서브도메인 탈취로 이어지는 것처럼, **인프라 설정에서도 "존재하지 않는 대상을 향한 살아있는 참조"는 그 자체로 공격 표면**이 된다는 원리는 IAM·네트워크·컴퓨트를 넘어 어떤 선언적 설정 시스템에도 적용 가능한 일반 교훈이다.

### 핵심 전이 3 — 에어갭드·자격증명-불필요 설계라는 대안 축

실계정에 직접 붙어 스캔하는 대신 스냅샷을 입력받는 설계는, 보안 도구 자체가 최소 권한(zero standing privilege)을 지향해야 한다는 원칙의 실천이다 — 감사자가 "감사 대상 계정에 대한 권한"이라는 새로운 공격 표면을 만들지 않는다는 점에서, 검증 도구 자체의 신뢰 경계를 좁히는 설계로 읽을 수 있다.

## 호스피탈리티 / CRS 적용 포인트

온다 CRS/PMS도 결제 연동 Lambda → 고객 PII가 담긴 S3(예약자 정보·카드 토큰 메타데이터) 같은 리소스 체인을 갖는다. 개별적으로는 "S3 암호화 O, 퍼블릭 차단 O, IAM 정책 O"로 그린이어도, 그 사이를 잇는 실행 역할·이벤트 트리거·크로스어카운트 신뢰에 감사 로그나 접근 제약이 빠져 있으면 동일한 취약점 패턴이 생긴다. Stave 자체를 그대로 들여오기보다, **분기별 IAM/리소스 정책 리뷰에 "경로 관점" 체크리스트**(누가 이 Lambda를 호출할 수 있는가 → 이 Lambda가 어떤 S3에 접근하는가 → 그 경로 전체에 감사 로그가 있는가)를 추가하는 것과, **삭제된 리소스를 가리키는 참조(유령 참조) 정기 스캔**을 IaC 파이프라인에 넣는 것은 지금 바로 적용 가능한 아이디어다.
