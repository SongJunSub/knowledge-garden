# 테스트 데이터를 걸러내고 실제 서비스 성과 분석하기 (Com2uS Hive)

> 출처: [테스트 데이터를 걸러내고 실제 서비스 성과 분석하기](https://on.com2us.com/tech/metric-filter-management/) (Com2uS ON Tech) · 정리일 2026-08-27
> **출처 한계**: `on.com2us.com`이 이 세션에서 egress 차단으로 직접 접근 불가. WebSearch로 Hive 애널리틱스의 필터·지표 관리 기능 일반 소개는 확인했지만, 이 특정 글의 구체적 문구·수치·저자는 찾지 못했다. Slack TechArticles 봇의 세 문장 발췌가 사실상 유일한 근거다. **저자·게시일 모두 미확인** — [[2026-08-20-hive-internal-user-exclusion]]·[[2026-08-20-hive-common-metric-standard]](저자 김동완 확인됨)와 같은 시리즈일 가능성이 높지만 단정하지 않는다.

## 한 줄 요약

**Hive 애널리틱스의 ***지표 필터 관리*** 기능은 QA 서버나 테스트 앱에서 발생하는 데이터를 서버 ID·앱 ID 단위로 한 번 등록해 대시보드·차트 등 모든 분석 화면에 일괄 필터링하는 것으로 보인다. [[2026-08-20-hive-internal-user-exclusion]]이 "유저 ID·디바이스 ID" 단위로 사람을 제외했다면, 이 글은 "서버 ID·앱 ID" 단위로 ***환경 자체***를 제외한다는 점에서 같은 설계 원칙(중앙 등록 → 전체 화면 자동 적용)을 다른 축에 적용한 사례로 읽힌다.**

## 핵심 포인트

- **문제(추정)** — QA 서버·테스트 앱에서 발생한 데이터가 실서비스 지표와 섞이면 KPI가 왜곡된다. 게임 도메인에서는 QA 서버 자체가 실서버와 같은 이벤트 로그 구조를 공유하는 경우가 많아, 개인(유저) 단위 제외만으로는 걸러지지 않는 오염이 있을 수 있다.
- **필터 단위** — **서버 ID 또는 앱 ID.** 개인이 아니라 환경 전체를 제외하는 더 굵은 단위다.
- **적용 범위** — "한 번 등록하면 대시보드·차트 등 ***모든 분석 화면에 일괄 적용***." [[2026-08-20-hive-internal-user-exclusion]]이 강조했던 "제외를 차트마다 반복하지 않고 한 곳에 정의한다"는 원칙과 표현까지 거의 동일하다.
- **목적** — 테스트 환경 데이터를 분리해 **실제 서비스 성과·핵심 KPI**를 정확하게 측정.
- **자매 글과의 관계 불확실** — 이 서버/앱 단위 필터와 [[2026-08-20-hive-internal-user-exclusion]]의 유저/디바이스 단위 제외가 Hive UI상 같은 메뉴(메트릭 설정) 하위에 있는지, 두 필터가 동시에 걸리는지는 원문 미확인으로 판단 불가.

## 인상 깊은 문장

> "서버 ID나 앱 ID를 한 번 등록하면 대시보드와 차트 등 모든 분석 화면에 일괄적으로 필터가 적용됨"
> (Slack TechArticles 봇 발췌 — [[2026-08-20-hive-internal-user-exclusion]]의 "프로젝트 단위 등록 → 차트마다 필터 반복 불필요"와 사실상 같은 설계 문장이 필터 단위만 바뀌어 반복되고 있다는 인상을 준다.)

## 댓글

- **원문 미확인**으로 댓글 유무·논조를 전혀 확인할 수 없다. 자매 글들의 패턴(자사 기술 블로그, 댓글 없음)을 참고한 추정일 뿐 확인된 사실이 아니다.
- **읽을 때 감안**: Slack 발췌만으로는 ①삭제 방식인지 태깅(집계 단계 제외) 방식인지 ②소급 재계산이 가능한지 ③QA 서버 목록의 소유자·갱신 주기가 있는지 — [[2026-08-20-hive-internal-user-exclusion]]이 자체적으로 짚었던 바로 그 질문들 — 전혀 알 수 없다. 이 글도 같은 한계(제품 소개, 수치 없음, 운영 실무 미기재)를 가질 가능성이 높지만 원문 없이는 단정할 수 없다.

## 내 생각 · 적용점

### 핵심 전이 — 오염 제거의 두 축: "누구"(유저·디바이스) vs "어디"(서버·앱), 그리고 두 축을 다 걸어야 진짜로 깨끗해진다

[[2026-08-20-hive-internal-user-exclusion]]가 세운 명제는 ***"제외 대상의 이벤트는 계속 수집되고 집계에서만 빠진다"***(삭제가 아니라 태깅)였다. 이 글의 서버 ID/앱 ID 필터가 같은 설계를 따른다면(원문 미확인이라 확정은 못 하지만, "일괄 적용"이라는 표현이 같은 계열임을 시사한다), 이제 오염 제거는 두 축으로 완성된다 — **누구의 이벤트인가(유저/디바이스)**와 **어디서 발생한 이벤트인가(서버/앱)**. 둘 중 하나만 필터링하면 여전히 샌다: 실서버에 QA 계정이 로그인해 남긴 이벤트는 유저 필터로 잡히지만, QA 서버에서 실제 테스트 유저인 척 만든 계정으로 남긴 이벤트는 유저 필터를 통과하고 서버 필터로만 잡힌다. **오염원의 차원이 여러 개면 필터도 그 차원 수만큼 있어야 한다**는 원칙을, 같은 블로그가 두 편에 걸쳐 다른 축으로 실증하는 셈이다.

## 호스피탈리티 / CRS 적용 포인트

- [[2026-08-20-hive-internal-user-exclusion]]에서 이미 짚었던 "온다도 테스트 예약·데모 숙소·내부 결제·파트너 교육용 계정이 지표를 오염시킨다"는 문제에, 이 글은 **환경 축**을 더한다. 온다에도 **스테이징/QA 환경에서 실서버와 동일한 형식으로 남는 이벤트**(스테이징 CRS가 프로덕션과 같은 로그 파이프라인을 공유하는 경우)가 있다면, 유저·계정 단위 제외만으로는 못 거른다 — **환경(서버·테넌트·앱 빌드) ID 단위 필터를 별도 축으로 둬야** [[2026-08-20-hive-internal-user-exclusion]]이 말한 "완전히 깨끗한" 상태에 가까워진다.
- **직접 적용은 원문 확인 전까지 원칙 수준에 머문다** — 실제 필터 UI·소급 적용 방식·소유자 운영 모델을 확인 못 한 채로 CRS 설계에 그대로 옮기기는 이르다.
