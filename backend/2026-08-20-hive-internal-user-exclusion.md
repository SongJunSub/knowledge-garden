# 진짜 유저의 데이터만 깨끗하게 골라내어 분석하기 (Com2uS Hive)

> 출처: [진짜 유저의 데이터만 깨끗하게 골라내어 분석하기](https://on.com2us.com/tech/internal-user-exclusion/) (김동완 · Com2uS ON Tech) · 정리일 2026-08-20
> **자사 제품(Hive 애널리틱스) 기능 소개 글**이다. 짧고, **구현도 수치도 없다**(→ 댓글 절).
> **게시일이 페이지와 목록 어디에도 표기되지 않는다.** 출처 한계로 밝힌다.
> **[[2026-08-20-hive-common-metric-standard]]와 한 쌍**으로 읽어야 값이 산다. 둘 다 "지표 정의를 어디에 두는가" 문제다.

## 한 줄 요약

**게임 출시나 업데이트 직후에 QA 담당자와 내부 직원이 로그인·구매·보상 획득을 반복 점검하는데, 그 이벤트가 실사용자 데이터와 같이 집계되면 접속자 수·매출·콘텐츠 참여가 왜곡된다. 그리고 왜곡이 가장 큰 시점이 하필 의사결정이 가장 필요한 시점, 즉 라이브 이벤트 시작 직후다. 기존 대응은 차트마다 테스트 계정을 필터로 지정하는 것이었는데 설정 반복·계정 누락·기존 대시보드 수정이라는 세 가지 비용이 붙었다. Hive 애널리틱스의 지표 제외 유저 관리는 이걸 프로젝트 단위로 한 번 등록해서 모든 차트와 대시보드에 자동 적용한다. 대상은 유저 ID 또는 디바이스 ID 이고 파일로 대량 등록할 수 있다. 그리고 이 기능에서 실제로 배울 점은 UI 가 아니라 한 문장에 있다. 제외 대상의 이벤트는 계속 수집되고 수치에만 반영되지 않는다.**

## 핵심 포인트

- **문제**: 출시·업데이트 시 **내부 직원과 QA 가 로그인·구매·보상 획득을 반복 점검**하고, 그 이벤트가 실사용자와 함께 계산되면 ***"접속자 수와 매출, 콘텐츠 참여 결과가 달라질 수 있다."***
- **기존 방식의 비용 3종**: ①**차트마다 필터 설정 반복** ②**일부 계정 누락** ③**기존 대시보드 수정 필요.**
- **왜곡이 가장 큰 시점 = 판단이 가장 필요한 시점**: ***"이벤트 시작 직후에는 내부 기능 확인으로 인해 참여자 수나 구매 결과가 일시적으로 높아 보일 수 있다."*** 운영자는 정확히 그 직후 데이터로 서비스 상태를 판단한다.
- **기능(지표 제외 유저 관리)**:
  - **프로젝트 단위 등록** → 차트마다 필터 반복 불필요.
  - 대상 구분: **유저 ID 또는 디바이스 ID.**
  - **파일로 대량 등록** 가능.
  - **제외 대상의 이벤트는 계속 수집되지만 수치에는 반영되지 않는다.**
  - **지표를 쓰는 모든 차트·대시보드에 자동 적용.** ***"기존 분석 화면을 각각 수정하지 않고도 실제 서비스 유저를 중심으로 운영 현황을 확인할 수 있다."***
- **활용 사례 3종**:
  - **매출**: 테스트 결제 반복 시 **매출·구매 전환율·ARPU·ARPPU** 가 전부 왜곡된다.
  - **라이브 콘텐츠 참여**: 이벤트 공개 전후 QA·운영자의 반복 로그인·상태 점검을 분리해야 **실제 참여 인원과 리텐션**이 보인다.
  - **동시접속자**: 업데이트·점검 직후 **내부 인력이 먼저 접속**해 기능을 확인한 게 CCU 에 잡힌다. 제외해야 ***"서비스 유저의 복귀 흐름과 운영 안정 여부를 더 명확하게 파악."***
- **위치**: Hive 애널리틱스 > 설정 > 메트릭 설정 > 지표 제외 유저 관리. **제외 계정 목록을 정기적으로 업데이트**하라는 운영 안내가 붙는다.

## 인상 깊은 문장

> ***"제외 대상 유저의 이벤트는 계속 수집되지만 수치에는 반영되지 않는다."***
> **이 글에서 유일하게 아키텍처적인 문장이고, 그래서 가장 중요하다**(→ 전이 1).

> ***"이벤트 시작 직후에는 내부 기능 확인으로 인해 참여자 수나 구매 결과가 일시적으로 높아 보일 수 있다."***
> **오염이 가장 큰 순간과 판단이 가장 급한 순간이 겹친다**(→ 전이 2).

> ***"기존 분석 화면을 각각 수정하지 않고도"***
> 정의를 한 곳에 두면 소급 적용이 공짜가 된다(→ 전이 3).

## 댓글

**댓글 없음.** 자사 기술 블로그 직접 링크.

**읽을 때 감안**
- ①**제품 기능 소개다.** Hive 애널리틱스를 쓰는 게 결론이고, **직접 구현하려면 어떻게 하는지는 없다.**
- ②**수치가 하나도 없다.** ***"달라질 수 있다"***, ***"높아 보일 수 있다"*** 뿐이고 **실제로 내부 트래픽이 지표를 몇 % 왜곡했는지 before/after 가 없다.** 이 기능의 가치를 재려면 그 숫자가 필요하다.
- ③**게시일이 없다.** 페이지에도 목록에도 날짜가 없어서 **최신성 판단이 불가능**하다. 2026-08 로 추정만 한다.
- ④**제외 대상 관리의 어려운 부분을 안 다룬다.** ***"정기적으로 업데이트"***라고만 쓰는데, 실무의 진짜 문제는 **누가 언제 등록하고 퇴사·기기 교체 시 누가 지우느냐**다. **목록 자체가 부패한다.**
- ⑤**디바이스 ID 기반 제외의 한계**가 없다. 재설치·기기 초기화·에뮬레이터에서 ID 가 바뀌면 제외가 풀린다.
- ⑥**"제외했는데 실제로 깨끗해졌는가"를 검증하는 방법이 없다.** 제외 후 지표가 얼마나 움직였는지를 보여주는 화면이 있어야 신뢰가 생기는데 언급이 없다.
- ⑦**게임 도메인 특유의 사정**이 있다. 내부 계정이 **무료 재화를 대량 보유**하는 등, 단순 제외로는 안 풀리는 오염(경제 밸런스 지표)도 있다.

## 내 생각 · 적용점

### 핵심 전이 1: 삭제가 아니라 태깅이다. 원본은 남기고 집계에서만 뺀다

***"제외 대상 유저의 이벤트는 계속 수집되지만 수치에는 반영되지 않는다."***

**이 한 문장이 이 기능의 설계 결정 전부다.** 그리고 **정반대 선택이 흔하다.** 내부 트래픽을 **수집 단계에서 버리는 것**. 그게 더 싸 보이고 저장 비용도 준다.

**그런데 수집 단계에서 버리면 되돌릴 수 없다.**

| | 수집 단계 제외 | **집계 단계 제외(이 글)** |
|---|---|---|
| 저장 비용 | 낮음 | 높음 |
| 기준 변경 | **소급 불가.** 이미 없다 | **소급 가능.** 태그만 바꾸면 과거도 다시 계산 |
| 실수 복구 | **불가** | 가능 |
| QA 자체 분석 | **불가**(QA 행동 데이터도 사라짐) | 가능 |

**"나중에 기준이 바뀐다"는 분석 시스템의 상수다.** 어제 내부로 분류한 계정이 오늘 파트너 계정일 수 있고, 인플루언서 계정처럼 **경계에 있는 것**이 늘 생긴다. **원본을 남기면 그때 다시 계산하면 되고, 버렸으면 못 한다.**

**규칙: 데이터 위생 처리는 삭제가 아니라 표시로 한다.** 로그 마스킹, 봇 트래픽, 테스트 주문, 취소 예약 전부 같다. **원본 불변 + 뷰 레이어 필터**가 기본값이다.

### 핵심 전이 2: 내부 트래픽 오염은 출시 직후에 가장 크고, 그때가 판단이 가장 급한 때다

***"이벤트 시작 직후에는 내부 기능 확인으로 인해 참여자 수나 구매 결과가 일시적으로 높아 보일 수 있다."***

**타이밍이 최악으로 겹친다.**
- **내부 활동 밀도가 최고**인 시점: 출시·업데이트·이벤트 오픈 **직후 몇 시간.**
- **의사결정 압력이 최고**인 시점: **같은 시점.** 롤백할지, 이벤트 보상을 조정할지, 서버를 증설할지.
- **표본은 최소**: 실사용자 유입이 아직 적어서 **분모가 작다.** 그래서 **같은 내부 활동이 비율 지표를 더 크게 흔든다.**

**즉 왜곡률은 (내부 활동량 / 전체 활동량)인데, 분자가 최대이고 분모가 최소인 순간이 정확히 출시 직후다.**

**[[2026-06-27-fake-traction-problem]]과 같은 축인데 원인이 다르다.** 저기는 **외부에서 만들어진 가짜 신호**였고 여기는 **우리가 만든 진짜 활동이 잘못된 통에 담긴 것**이다. **후자가 더 잡기 어렵다.** 악의가 없어서 아무도 의심하지 않는다.

**규칙: 출시 직후 대시보드를 볼 때 "지금 이 숫자에 우리가 몇 명 들어 있나"를 먼저 확인한다.** 그리고 **그 확인이 매번 수동이면 결국 아무도 안 한다** 는 게 이 기능이 존재하는 이유다.

### 핵심 전이 3: 필터를 차트에 두면 정의가 N개가 되고, 설정에 두면 1개가 된다

**차트마다 필터를 거는 방식의 진짜 문제는 귀찮음이 아니라 정의의 분산이다.**

- 차트 30개에 필터를 걸면 **제외 기준이 30벌**이다.
- 새 QA 계정이 생기면 **30군데를 고쳐야 하고**, 실무에서는 몇 개가 빠진다.
- 그리고 **어느 차트에 필터가 걸려 있는지 아무도 모른다.** 두 차트가 다른 숫자를 보여줄 때 원인 추적이 불가능하다.

**이건 코드의 중복과 같은 문제이고, 해법도 같다: 정의를 한 곳에 둔다.** 그래서 이 기능이 **메트릭 설정 하위**에 있는 게 맞다. [[2026-08-20-hive-common-metric-standard]]가 다루는 문제와 **같은 문제의 다른 면**이다.

| | 공통 지표 | 제외 유저 |
|---|---|---|
| 정하는 것 | **어떻게 셀 것인가** | **누구를 셀 것인가** |
| 분산됐을 때 | 같은 이름 다른 숫자 | 차트마다 다른 모집단 |
| 해법 | 메트릭 정의 중앙화 | 제외 목록 중앙화 |

**둘 다 "지표 = 집계 방식 + 모집단"이라는 같은 등식의 항이다.** 하나만 통일하면 여전히 숫자가 안 맞는다.

### 핵심 전이 4: 제외 목록은 부패하는 자산이라 소유자가 필요하다

**글은 ***"정기적으로 업데이트"***라고만 쓰는데, 실무의 실패는 전부 여기서 난다.**

- 퇴사자 계정이 **계속 제외 목록에 남아** 있고,
- 새로 합류한 QA 계정은 **등록이 안 되고**,
- 기기를 바꾼 사람의 **디바이스 ID 가 갈리고**,
- **누가 이 목록을 관리하는지 모른다.**

**그리고 이 부패는 조용하다.** 지표가 틀렸다는 신호가 안 온다. **틀린 채로 계속 맞아 보인다.**

**[[2026-07-20-why-data-teams-fail]]이 지적한 실패 유형이 정확히 이거다.** 도구를 도입하면 문제가 풀린 것 같지만, **운영 주체를 정하지 않으면 도구가 만든 새 부채가 된다.**

**규칙: 제외 목록·화이트리스트·매핑 테이블처럼 사람이 손으로 채우는 자산에는 ①소유자 ②갱신 주기 ③검증 방법을 같이 정한다.** 검증 방법이 가장 자주 빠지는데, 여기서는 **"제외 적용 전후 지표 차이를 보여주는 화면"** 이 그 역할을 한다. 이 글에 없는 게 그거다.

## 호스피탈리티 / CRS 적용 포인트

- **직접 대응이 있다.** 온다에도 **테스트 예약, 데모 숙소, 내부 결제, 파트너 교육용 계정**이 있고, 이게 **예약 건수·GMV·전환율·객단가**에 그대로 섞인다. 게임과 달리 **금액이 정산·리포트에 닿기 때문에 오염 비용이 더 크다.**
- **집계 단계 제외를 기본값으로.** 테스트 예약을 **DB 에서 지우거나 수집을 막지 않는다.** 플래그를 달고 **뷰·집계에서 제외**한다. 기준이 바뀌면 소급 재계산이 되어야 한다.
- **제외 축이 여럿이다.** 게임은 유저 ID / 디바이스 ID 두 축이면 되지만 우리는 **계정(내부 직원), 숙소(데모·테스트 상품), 예약(테스트 결제), 채널(내부 연동 테스트)** 네 축을 각각 표시해야 한다. **하나만 걸면 나머지로 샌다.**
- **오픈 직후 지표를 볼 때 내부 비중을 같이 띄운다.** 신규 파트너 온보딩 직후, 신규 채널 연동 직후가 **내부 활동 밀도 최고 + 분모 최소** 구간이다. **"이 숫자의 N%가 내부"** 를 대시보드에 같이 노출하면 오독이 준다.
- **정산·리포트 경로에는 제외 기준을 코드로 고정한다.** 파트너에게 나가는 리포트는 **대시보드 필터가 아니라 결정적 쿼리**로 만든다. 필터는 빠뜨릴 수 있다.
- **제외 목록에 소유자·갱신 주기·검증 방법을 붙인다.** 그리고 **분기 1회, 제외 적용 전후 차이를 실제로 출력해본다.** 차이가 0 이면 목록이 죽었다는 신호다.
- **[[2026-08-20-hive-common-metric-standard]]와 같이 처리한다.** 모집단만 통일하고 집계 방식이 제각각이면 숫자는 여전히 안 맞는다.
