# AI 기반 SCTE-35 자동 삽입으로 라이브 스트리밍 광고 운영 자동화 (AWS)

> 출처: [AI 기반 SCTE-35 자동 삽입으로 라이브 스트리밍 광고 운영 자동화하기](https://aws.amazon.com/ko/blogs/tech/automate-scte35-ad-insertion-in-live-streaming/) (YoHan Choi, Sr. Media Edge Services Specialist SA · Yongzhe Ren, Solutions Architect · AWS 기술 블로그) · 정리일 2026-08-20
> **AWS 자사 블로그다.** 즉 **AWS 서비스 조합을 권하는 글**이고, 대안 스택과 비용 총액은 안 나온다.
> **댓글 없음. 실제 프로덕션 운영 사례가 아니라 참조 아키텍처**다(→ 댓글 절).
> 그럼에도 **설계 결정 몇 개가 도메인을 넘어서 쓸 만하다.**

## 한 줄 요약

**라이브 스포츠 중계에서 광고 신호(SCTE-35)를 넣는 일은 채널당 24/7 상주 인력이 하거나 사전 스케줄로 하는데, 전자는 인건비가 채널 수에 비례해 늘고 후자는 축구 추가시간이나 야구 이닝 교체처럼 시점이 매 경기 달라지는 이벤트를 못 잡는다. 이 글의 해법은 모델을 키우는 게 아니라 감지 대상을 바꾸는 것이다. 경기 화면을 이해하려 들지 않고, 브레이크에 들어갈 때 방송사가 내보내는 필러 영상(채널 브랜딩 루프, 대기 화면)을 찾는다. 필러는 사업자가 직접 만든 고정 자산이라 매번 똑같이 나오고, 그래서 라벨당 10~20장으로 실용 정확도가 나온다. MediaLive 썸네일 API 로 현재 화면을 1초마다 가져와 Rekognition Custom Labels 로 분류하고, 임계값을 넘으면 BatchUpdateSchedule 로 SCTE-35 를 즉시 삽입한 뒤 30초 쿨다운에 들어간다. 그리고 이 글에서 도메인 밖으로 가장 잘 전이되는 문장은 이거다. 미탐은 스케줄 fallback 으로 보완되지만 오탐은 경기 중 광고 송출이라 사고가 된다. 즉 이 워크로드에서 Precision 과 Recall 의 값어치는 대등하지 않다.**

## 핵심 포인트

- **문제**: SCTE-35 마커가 **정확한 시점에 삽입되어야만 광고 수익화 파이프라인 전체가 동작**한다.
  - **수동**: ***"채널당 24/7 상주 인력이 필요"***, 휴먼 에러, ***"채널 수가 늘어나면 운영 인력과 비용이 선형적으로 증가."***
  - **사전 스케줄**: ***"축구의 추가 시간처럼 브레이크 진입 시점이 경기 상황에 따라 매 경기 달라지고, 야구의 이닝 교체는 시점 예측이 사실상 불가능."*** 광고 기회 상실 또는 **경기 중 광고 송출.**
- **핵심 아이디어: 필러 영상을 감지 대상으로 삼는다.** 브레이크에 들어가면 방송사는 **사전에 준비한 필러**(채널 브랜딩 루프, 대기 화면, 광고 전 안내)를 내보낸다. 필러는 ***"사업자가 직접 준비한 고정 영상 자산이므로 매번 동일한 화면이 반복"***되고 ***"경기 장면처럼 카메라 앵글과 조명이 계속 변하는 대상이 아니라, 사전에 알고 있는 화면을 찾는 문제"***라 ***"컴퓨터 비전 모델 입장에서 매우 안정적인 감지 대상"***이다.
- **AWS 조합 3종**:
  - **MediaLive 썸네일 API**(`DescribeThumbnails`, `CURRENT_ACTIVE`): ***"별도의 프레임 추출 파이프라인 없이, 실행 중인 채널에서 곧바로 '지금 이 순간의 화면'을 얻을 수 있습니다."***
  - **Rekognition Custom Labels**(`DetectCustomLabels`): 소량 데이터셋으로 커스텀 분류 모델. ***"ML 전문 지식 없이도 콘솔에서 학습부터 배포까지 완결."***
  - **MediaLive Schedule API**(`BatchUpdateSchedule` + `Scte35SpliceInsertSettings`, **Immediate Mode**).
- **처리 흐름**: Step Functions 가 **1초마다** Lambda 호출 → 썸네일 조회 → Custom Labels 분류(`filler` / `normal` + 신뢰도) → **임계값(예: 80%)** 이상이면 브레이크 진입 판정 → **SCTE-35 즉시 삽입**(Duration 은 **90kHz 틱**, 15초 = **1,350,000 틱**) → 트리거 썸네일을 **타임스탬프·라벨명·신뢰도를 파일명에 넣어 S3 보관** → **30초 쿨다운.**
- **하류 처리**: 삽입 마커는 **MediaPackage** 를 거쳐 HLS 매니페스트 광고 마커가 되고, **MediaTailor** 가 필러 구간을 **시청자별 맞춤 광고로 치환**한다.
- **데이터셋 규모**: `filler` **10~20장**, `normal` **10장 이상**(다양한 카메라 앵글 포함). 근거는 필러가 고정 자산이고 경기 화면과 **시각적으로 뚜렷이 구별**되기 때문.
- **평가 지표의 비대칭**: ***"미탐(필러인데 감지 못함)은 하이브리드 구성의 스케줄 Fallback 으로 보완할 수 있지만, 오탐(경기 화면을 필러로 오인)은 경기 중 광고 송출이라는 시청자 경험 사고로 직결됩니다. 즉 이 워크로드에서 두 지표의 값어치는 대등하지 않습니다."***
- **Step Functions 상태 7개**: `InitCounter`(Pass) → `CheckTimeout`(Choice, **3,600 이상이면 종료**) → `CheckThumbnail`(Task/Lambda) → `IsMatched`(Choice) → `Wait1s` / `Wait30s` → `IncrementCounter` / `Increment30`.
  - **설계 포인트**: ***"경과 시간을 실제 시계가 아니라 카운터로 관리한다"***. 대기한 만큼 카운터를 더하므로 **Choice 의 숫자 비교만으로 1시간 경과 판정**이 끝나고 타임스탬프 계산·전달이 없다.
- **3중 안전장치**: ①**쿨다운 30초**(중복 삽입 방지) ②**자동 종료 1시간**(***"운영자가 중지를 잊더라도 상태 머신이 스스로 종료"***) ③**증거 보관 S3**(사후 감사 + 오탐 이미지 재학습).
- **지연 시간**: 폴링 최대 1초 + 썸네일 갱신 최대 2초 + 추론 1초 미만 + 삽입 1초 미만 → **수 초 이내.**
- **비용 운영**: Custom Labels 는 **명시적 Start 후 추론 유닛 시간당 과금**이라 ***"24시간 상시 구동이 아니라, 경기 시작 전 모델을 시작하고 종료 후 중지하는 운영 패턴이 비용 효율적."***
- **권장 구성**: **AI 감지를 유일 트리거로 두지 말고 사전 스케줄을 Fallback 으로 함께 운용.** Lambda 역할은 **채널·프로젝트 ARN 한정 최소 권한**, S3·CloudWatch Logs 는 **KMS 암호화**, **CDK 로 정의 후 cdk-nag 검증.**
- **확장 시나리오**: 야구 이닝 교체·농구 쿼터 종료, **방송 사고 화면(컬러바·블랙 프레임) 감지**, 프로그램 시작/종료 그래픽.

## 댓글

**댓글 없음.** AWS 기술 블로그 직접 링크.

**읽을 때 감안**
- ①**AWS 자사 블로그다.** 결론이 **MediaLive + Rekognition + Step Functions** 로 나오는 건 구조적으로 정해져 있다. 같은 문제를 **오픈소스 CV + 자체 폴러**로 푸는 비용 비교는 없다.
- ②**참조 아키텍처이지 운영 사례가 아니다.** ***"실용적인 정확도"***, ***"수 초 이내"***는 있는데 **실제 채널에서 몇 경기를 돌려 오탐이 몇 건이었는지가 없다.** 코드도 ***"개념 코드"***라고 명시된다.
- ③**정확도 수치가 없다.** Precision/Recall 의 **의미는 길게 설명하는데 이 워크로드의 실측값은 안 나온다.** 임계값 80% 도 ***"예"***로 제시된다.
- ④**비용 총액이 없다.** ***"채널당 상주 인력을 대체"***한다는데 **추론 유닛 시간당 요금 + Lambda + Step Functions 상태 전이 비용**의 합계가 없다. Step Functions 가 **1초마다 상태를 도는 구조**라 경기 3시간이면 상태 전이가 만 단위로 쌓인다.
- ⑤**필러가 없는 방송사에는 안 통한다.** 저자도 전제로 명시한다. 브레이크에 **경기 화면을 그대로 두거나 스튜디오로 넘기는 편성**이면 감지 대상이 사라진다.
- ⑥**"AI"라는 단어가 크게 붙었는데 실체는 소량 지도학습 이미지 분류**다. 나쁜 게 아니라 **오히려 그게 이 설계의 장점**인데, 제목이 그걸 흐린다.
- ⑦**Rekognition Custom Labels 의 제품 수명**을 확인해야 한다. AWS 는 CV 제품군을 여러 번 재편해왔고, 참조 아키텍처가 특정 관리형 서비스에 묶이면 그 리스크를 같이 진다.

## 내 생각 · 적용점

### 핵심 전이 1: 모델을 키우기 전에 감지 대상을 고정된 것으로 바꿀 수 있는지 본다

**"지금 경기가 하프타임에 들어갔는가"를 판정하려면 경기 규칙·시계·화면 문맥을 이해해야 한다. 어려운 문제다.**
**"지금 화면이 우리가 만든 그 브랜딩 루프인가"는 이미지 매칭에 가깝다. 쉬운 문제다.**

**그리고 둘은 같은 순간을 가리킨다.** 방송사가 **브레이크에 들어갈 때 필러를 튼다**는 운영 관행 덕분이다.

**이게 ML/LLM 적용에서 가장 자주 놓치는 수순이라고 본다.** 보통은 **어려운 문제를 그대로 두고 모델을 키우는 쪽**으로 간다. 여기는 **문제를 옮겨서 라벨당 10~20장으로 끝냈다.**

**같은 형태를 [[2026-07-05-pxpipe-fable-cost-reduction-image-ocr]]에서 봤다.** 비싼 모델로 전부 처리하는 대신 **처리 대상을 나눠서 값싼 경로로 대부분을 흘린다.** 축이 같다. **모델 성능이 아니라 문제 정의가 비용을 정한다.**

**우리 실무 규칙: "이 판단을 우리가 통제하는 고정 신호로 바꿔 표현할 수 있는가"를 먼저 묻는다.** 우리가 만든 것(마커, 상태 플래그, 정형 이벤트)을 찾는 문제로 바꿀 수 있으면 **모델이 작아지고 검증이 쉬워진다.**

### 핵심 전이 2: 오류 두 종의 값어치가 대등하지 않으면 그걸 먼저 문서에 쓴다

***"이 워크로드에서 두 지표의 값어치는 대등하지 않습니다."***

**F1 score 는 Precision 과 Recall 이 동등하다고 가정한 지표**인데, 실무 워크로드 상당수가 그 가정을 안 만족한다. 여기서는 명확하다.

| 오류 | 결과 | 보완 |
|---|---|---|
| **미탐**(필러인데 못 잡음) | 광고 기회 상실 | **스케줄 Fallback 으로 커버 가능** |
| **오탐**(경기 화면을 필러로 오인) | **경기 중 광고 송출 = 방송 사고** | **커버 불가** |

**그래서 임계값을 보수적으로(80%) 잡고 쿨다운을 건다.** 즉 **비대칭을 알고 나면 파라미터가 자동으로 정해진다.**

**이 구분이 우리 도메인에 그대로 온다.**
- **오버부킹 vs 미판매**: 오버부킹은 게스트 대면 사고이고 미판매는 기회 손실이다. **대등하지 않다.**
- **정산 과지급 vs 과소지급**: 과소지급은 문의로 잡히고 과지급은 회수가 어렵다.
- **자동 취소 판정**: 정상 예약을 취소하는 게 취소 건을 놓치는 것보다 훨씬 비싸다.

**규칙: 임계값을 정하기 전에 "두 오류 중 어느 쪽이 되돌릴 수 없는가"를 한 줄로 적는다.** 되돌릴 수 없는 쪽을 줄이는 방향으로 임계값을 민다. [[2026-08-08-eval-driven-development-airbnb]]가 말하는 eval 설계의 출발점도 같다.

### 핵심 전이 3: 비결정적 판단이 돈에 닿으면 증거 보관이 기능 요구사항이다

***"'왜 그 시점에 삽입되었는가'를 설명할 수 있어야 합니다."***

**그래서 트리거 썸네일을 타임스탬프·라벨명·신뢰도를 파일명에 넣어 S3 에 남긴다.** 용도가 둘이다. **사후 감사**와 **오탐 이미지의 재학습 반영**(MLOps 루프).

**이건 mangolove 방법론이 LLM 위임 경계에서 요구하는 것과 정확히 같은 구조다.** 결정적 스캐폴딩이 판단을 감싸고, **좁은 판단만 모델에 위임하고, 그 판단의 입력과 신뢰도를 남긴다.** [[2026-04-27-ai-agent-deleted-production-database]]가 보여준 실패의 반대편이다.

**그리고 "증거"의 형태가 좋다.** 로그 한 줄이 아니라 **모델이 실제로 본 입력 이미지**를 남긴다. 사후에 ***"모델이 뭘 봤길래"***를 재현할 수 있다.

**우리 규칙: 자동 판정이 금액·재고·게스트 경험에 닿으면, 판정 로그에 ①입력 스냅샷 ②판정값 ③신뢰도/근거 ④적용된 임계값 버전을 남긴다.** 넷 중 하나라도 없으면 사후에 원인 규명이 안 된다.

### 핵심 전이 4: AI 를 유일 트리거로 두지 않는다는 게 이 아키텍처의 성숙도다

***"AI 감지를 유일한 트리거로 두기보다, 사전 스케줄을 안전망(Fallback)으로 함께 운용하는 구성을 권장합니다."***

**AWS 블로그가 자기 AI 서비스를 소개하면서 "이것만 믿지 말라"고 쓴다.** 그리고 그게 구조적으로 옳다. **결정적 스케줄이 바닥에 깔려 있고 AI 는 그 위에서 정확도를 높인다.**

**계층이 이렇게 된다.**

```
[결정적 스케줄]     반드시 광고가 나가야 하는 최소 보장
       ↑ (정확도 개선분만 위임)
[CV 감지]           실제 브레이크 시점을 더 정확히 포착
       ↓ (결정적 API 호출)
[BatchUpdateSchedule]  실제 삽입은 항상 결정적 코드
```

**모델이 죽어도, 정확도가 떨어져도, 최소 보장은 유지된다.** 이게 mangolove 의 3층 구조와 같고, [[2026-08-16-graph-vs-loop-engineering]]에서 정리한 **루프를 결정적 그래프가 감싸는 형태**와도 같다.

**반대 안티패턴이 흔하다.** 모델 감지를 **유일 경로**로 만들고, 모델이 흔들리면 서비스가 흔들린다. **fallback 은 나중에 붙이는 게 아니라 먼저 깔아야 한다.**

### 핵심 전이 5: 실제 시계 대신 카운터로 경과 시간을 관리한 게 재현 가능성을 만든다

***"경과 시간을 실제 시계가 아니라 카운터로 관리한다."***

**대기한 만큼 카운터를 더하니까 Choice 의 숫자 비교만으로 타임아웃 판정이 끝난다.** 타임스탬프 계산도, 상태 간 시각 전달도 없다.

**작아 보이는데 결과가 크다.**
- **상태 머신이 순수 함수에 가까워진다.** 같은 입력이면 같은 경로.
- **테스트에서 시간을 흉내 낼 필요가 없다.** 카운터를 넣으면 끝.
- **재실행·재개가 안전하다.** 벽시계에 의존하면 재개 시점에 판정이 달라진다.

**같은 이유로 워크플로 스크립트에서 `Date.now()` / `Math.random()` 이 금지되는 것**이고, 원리가 동일하다. **결정적으로 재현되어야 하는 오케스트레이션은 비결정적 소스를 끌어들이지 않는다.**

**우리 배치·스케줄러에 그대로 적용된다.** 배치 재실행 시 **"지금 시각"을 다시 읽으면 결과가 달라지는 잡**이 있다면, **기준 시각을 입력으로 받아 넘기는 형태**로 바꾼다.

### 핵심 전이 6: 온디맨드 기동이 관리형 ML 의 실질 비용을 정한다

***"24시간 상시 구동이 아니라, 경기 시작 전 모델을 시작하고 종료 후 중지하는 운영 패턴이 비용 효율적입니다."***

**Custom Labels 는 추론 유닛 시간당 과금이라 놀고 있어도 돈이 든다.** 그래서 **경기 시간에만 켠다.** 자동 종료(1시간)가 **운영자 실수까지 막는 비용 장치**로 같이 설계된 게 좋다.

**그리고 이건 서버리스 서사와 어긋나는 지점이라 짚어둘 만하다.** Lambda·Step Functions 는 호출 과금인데 **관리형 ML 엔드포인트는 시간 과금**이다. **"서버리스 아키텍처"라고 부르지만 비용 모델이 섞여 있다.** 켜고 끄는 책임이 사용자에게 남는다.

**우리 규칙: 관리형 AI/ML 을 붙일 때 "안 쓸 때 0 이 되는가"를 먼저 확인한다.** 안 되면 **켜고 끄는 자동화를 기능과 같이 만든다.** 나중에 붙이면 안 붙는다.

## 호스피탈리티 / CRS 적용 포인트

- **직접 적용은 멀다.** 온다에 라이브 스트리밍 광고 삽입은 없다. **전이 가능한 건 설계 원칙 다섯이다.**
- **"우리가 만든 고정 신호를 찾는 문제"로 바꾸기.** 예: 숙소 이미지 검수를 **"좋은 사진인가"**(어려움)가 아니라 **"플레이스홀더/워터마크/중복 이미지인가"**(쉬움)로 정의하면 소량 데이터로 실용 정확도가 나온다. 실제로 파트너 이미지 품질 문제의 상당수가 후자다.
- **오류 비대칭을 문서 첫 줄에 적기.** 오버부킹 vs 미판매, 정산 과지급 vs 과소지급, 자동 취소 오판 vs 미탐. **어느 쪽이 되돌릴 수 없는지**를 적고 임계값을 그쪽으로 민다.
- **자동 판정에 증거 4종 남기기**: 입력 스냅샷, 판정값, 신뢰도·근거, 적용 임계값 버전. 특히 **요금 자동 조정·자동 취소·자동 배정**처럼 파트너 매출에 닿는 판정.
- **결정적 fallback 을 먼저 깔기.** 추천·예측이 죽어도 **기본 규칙으로 서비스가 돌아가야 한다.** 자동 요금 추천이 실패하면 **직전 확정 요금**이 남는 식.
- **재실행 안전성**: 배치·스케줄 잡이 **벽시계 대신 입력받은 기준 시각**으로 돌게 한다. 정산 배치 재실행에서 특히 크다.
- **쿨다운과 자동 종료를 습관으로.** 중복 발송(알림·정산·웹훅) 방지의 쿨다운, 그리고 **사람이 끄는 걸 잊어도 스스로 멈추는 상한.** 후자가 없어서 생긴 비용 사고가 흔하다.
- **관리형 AI 는 "안 쓸 때 0 인가"를 도입 전에 확인.**
