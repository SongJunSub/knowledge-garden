## 한 줄 요약

**Builder.io가 낸 오픈소스 TypeScript 프레임워크로, 전제가 한 문장이다 ― ***사용자에게 노출할 가치가 있는 액션이면 에이전트에게도 노출할 가치가 있고, 그 역도 참이다.*** 작업을 `defineAction()`으로 한 번 정의하면 그것이 UI 훅, 에이전트 도구, HTTP 엔드포인트, MCP 툴, A2A 대상, CLI 명령이 동시에 된다. 챗봇을 앱 옆에 붙이는 대신, 에이전트와 사람이 같은 액션·같은 상태·같은 UI 표면을 공유하게 만드는 구조다.**

## 핵심 포인트

- **액션이 단일 진실 원천** — `defineAction()` 하나가 ***UI 버튼, 에이전트 도구 호출, HTTP 엔드포인트, MCP 툴, A2A 디스패치, CLI 명령***을 전부 구동한다. 이메일 답장 같은 작업의 입력 스키마와 실행 코드를 하나만 유지하므로 ***인터페이스마다 로직을 다시 구현할 필요가 없다***는 것이 GN⁺ 요약이 짚은 핵심이다.
- **정의 방식은 단순하다** — Zod 스키마와 `run()` 함수, 선택적 메타데이터를 선언하면 프레임워크가 ***`actions/` 아래 파일을 자동으로 발견***해 필요한 모든 표면에 노출한다. React 쪽에서는 `useActionQuery` 같은 타입세이프 훅으로 같은 액션을 쓴다.
- **호출 주체를 코드가 알 수 있다** — ***`ActionRunContext.caller`*** 필드가 이 호출이 UI에서 왔는지, 에이전트 도구 루프에서 왔는지, HTTP·MCP·A2A·CLI에서 왔는지를 비즈니스 로직에 알려준다. 통합의 편의와 분기의 필요를 동시에 인정하는 설계인데, 뒤에서 보듯 이 필드의 존재 자체가 이 프레임워크의 가장 정직한 지점이자 가장 위험한 지점이다.
- **에이전트 런타임이 통째로 포함된다** — 대화, 도구, 스킬, 메모리, 백그라운드 작업, 관측(observability), 그리고 ***사람이나 다른 에이전트로의 인계(handoff)***가 같이 배포된다. UI 표면으로는 에이전트 채팅(위임과 결과 검토), 에이전트 팀(워크스페이스 내 전문 에이전트), 자동화(이벤트 기반·스케줄 실행)를 제공한다. 에이전트가 현재 페이지·선택된 레코드·활성 뷰 같은 ***앱 상태를 UI를 조작하지 않고도 인지***한다는 점이 눈에 띈다.
- **백엔드는 갈아끼울 수 있다** — ***Drizzle이 지원하는 SQL 데이터베이스***(프로덕션 PostgreSQL, 로컬 개발 PGlite)와 Nitro 호환 호스트면 된다. 데이터·LLM·DB·인프라 소유권은 사용자에게 남는다고 명시한다.
- **성숙도** — MIT 라이선스, 2026-09-19 조회 시점 ***GitHub 스타 4.9k, 커밋 5,731개***, 활발한 개발 중. 재사용 가능한 툴킷(협업, 공유, 설정, 팀, 관측)도 제공한다.

## 내 생각 · 적용점

### 핵심 전이 1 — "MCP냐 CLI냐"라는 논쟁을 어댑터 문제로 강등시킨다

[[2026-05-29-mcp-is-dead-cli-skills]]는 MCP의 컨텍스트 비용·지연과 CLI와의 기능 중복을 근거로 ***"MCP는 죽었나"***를 물었고, 대안으로 Skills를 봤다. 그 논쟁의 암묵적 전제는 **하나를 골라야 한다**는 것이었다. Agent-Native는 그 전제를 치운다 ― MCP도, CLI도, HTTP도 전부 같은 액션 위에 얹힌 **어댑터**이고, 어느 것을 쓸지는 아키텍처 결정이 아니라 배포 설정이 된다. 이게 맞다면 저 논쟁은 "어느 프로토콜이 이기는가"에서 "이 호출 경로의 오버헤드가 얼마인가"로 성격이 바뀐다. 다만 **강등이 해결은 아니다.** MCP의 컨텍스트 비용은 어댑터를 자동 생성한다고 사라지지 않는다 ― 액션 100개를 정의하면 MCP 툴 100개가 자동으로 노출되고, 그건 저 노트가 지적한 컨텍스트 팽창 문제를 오히려 **쉽게 악화시키는 구조**다. 자동 노출은 편의이자 위험이고, 이 프레임워크가 그 선택(무엇을 에이전트에게 노출할지)을 어떻게 통제하는지는 이번 조사로 확인하지 못했다.

### 핵심 전이 2 — SSOT 계보의 다음 칸: 지식에서 실행으로

[[2026-08-28-line-llm-wiki-code-driven-ssot]]는 도메인 **지식**의 단일 진실 원천을 코드에서 자동 생성하고 PR 루프로 유지하는 설계였다. Agent-Native는 같은 처방을 **실행**에 적용한다. 두 경우의 병은 똑같다 ― **같은 것의 복제본이 여러 곳에 생기면 시간이 지나며 서로 어긋나고, 어긋난 사실은 아무도 모른 채 쌓인다.** 문서 부패와 "UI에서는 되는데 API로는 안 되는 기능"은 같은 병의 두 증상이다. 다만 실행 쪽이 더 어렵다는 점은 짚어야 한다. 지식은 최신본 하나로 수렴시키면 되지만, 실행은 표면마다 요구가 진짜로 다르다 ― UI는 낙관적 업데이트와 부분 로딩이 필요하고, 에이전트는 멱등성과 확인 절차(되돌릴 수 없는 작업 전 승인)가 필요하며, 공개 API는 레이트 리밋과 버전 호환이 필요하다. `caller` 필드가 존재한다는 사실 자체가 **완전한 통합이 불가능함을 프레임워크가 스스로 인정한 지점**이다.

### 핵심 전이 3 — 그래서 이건 [[2026-06-08-prefer-duplication-over-wrong-abstraction]]의 정면 시험대다

그 노트가 정리한 원칙은 ***잘못된 추상화보다 중복이 낫다***였다. Agent-Native는 정확히 그 반대 방향으로 가장 멀리 간 시도다 ― 여섯 개 호출 경로를 하나의 함수로 통합한다. 어느 쪽이 옳은지는 **액션의 성격에 달려 있다.** "이메일 답장 초안 생성"처럼 부작용이 없고 표면별 요구가 거의 같은 액션이라면 통합이 명백히 이긴다. 반면 "결제 취소"처럼 UI에서는 2단계 확인이 필요하고 에이전트에서는 승인 워크플로가 필요하며 공개 API에서는 멱등 키가 필요한 액션이라면, 하나의 `run()` 안에서 `caller`로 분기하기 시작하는 순간 그 함수는 **잘못된 추상화의 전형**이 된다. 실무 판단 기준을 하나 세워둔다면 이렇다 ― **부작용이 없거나 되돌릴 수 있는 액션은 통합하고, 되돌릴 수 없는 액션은 표면별로 나눠 두되 핵심 도메인 로직만 공유한다.** 이건 이 프레임워크의 주장이 아니라 두 노트를 겹쳐 내가 세운 기준이고, 이번 조사로는 검증되지 않았다.

### 핵심 전이 4 — "에이전트가 잘 다루는가"가 기준이 된다던 관찰의 극단값

[[2026-09-05-ai-asteroid-hitting-frontend]]는 프레임워크 선택 기준이 ***'개발자 경험'에서 '에이전트가 얼마나 잘 다루는가'로 옮겨가고 있다***고 정리했고, [[2026-09-07-geeknews-weekly-374-agent-fit-criterion]]도 같은 주간 관찰을 남겼다. Agent-Native는 그 축의 끝값이다 ― 에이전트 친화성을 기준으로 프레임워크를 **고르는** 게 아니라, 에이전트를 1급 사용자로 놓고 프레임워크를 **다시 짠다.** 이 방향의 시도들이 얼마나 살아남을지는 별개 문제지만, 적어도 축의 이동이 관찰 단계를 지나 제품 단계에 들어섰다는 신호로는 읽을 만하다.

## 호스피탈리티 / CRS 적용 포인트

**프레임워크 채택은 멀지만 개념은 가깝다.** Nitro·Drizzle 기반 TypeScript 스택 전제라 온다의 기존 백엔드에 이 프레임워크를 그대로 들이는 건 현실적이지 않다. 하지만 이 프레임워크가 지적하는 병은 온다에 이미 있다 ― **"예약 변경", "요금 수정", "재고 마감" 같은 핵심 작업이 파트너 어드민 UI, 파트너 공개 API, 내부 CS 툴, 배치 잡에 각각 구현돼 있으면 검증 규칙과 부작용이 서서히 갈라진다.** 어드민에서는 막히는 변경이 API로는 통과하는 상황이 대표적이고, 여기에 에이전트 표면이 하나 더 붙으면 갈라짐은 다섯 갈래가 된다. 전이할 것은 프레임워크가 아니라 **액션 카탈로그**라는 개념이다: 도메인의 핵심 작업 목록을 입력 스키마·전제조건·부작용·되돌림 가능 여부와 함께 한 곳에 정의해두고, 각 표면은 그 정의를 참조만 하게 하는 것. 이건 [[2026-09-18-devsisters-databricks-metric-view]]가 지표 정의를 중앙화해 분석 에이전트까지 같은 정의를 쓰게 만든 것의 **실행 버전**이고, 그 노트가 "분석 에이전트 도입 전 지표 정의 중앙화가 선행조건"이라고 한 것처럼 **운영 에이전트 도입 전 액션 정의 중앙화가 선행조건**이라고 말할 수 있다. 다만 위 핵심 전이 3에서 세운 단서를 그대로 붙인다 ― 되돌릴 수 없는 액션(결제, 취소 수수료 부과, 파트너 노출 중단)까지 한 구현으로 통합하려 들면 안 된다.
