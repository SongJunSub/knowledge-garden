# NVIDIA Run:ai (오픈소스) — GPU 하나를 쪼개 쓰게 하는 것보다, '남는 자원을 동적으로 회수'하는 게 핵심이다

> 출처: GeekNews 토픽 [id=35507](https://news.hada.io/topic?id=35507) (원문 외부 링크 이번 세션에서 미확인) · Slack `#개발-뉴스-dev-news` 경유 · 정리일 2026-10-17

> **출처 한계**: `news.hada.io` 전면 차단으로 원문을 열지 못했다. WebSearch로 배경을 교차확인했다 — NVIDIA는 2025년 4월 Run:ai의 Kubernetes 스케줄링 코어("KAI Scheduler")를 Apache 2.0으로 먼저 오픈소스화했고(현재 CNCF Sandbox 프로젝트), 이후 UI·CLI·API·대시보드를 포함한 Run:ai 플랫폼 전체를 오픈소스로 공개했다는 보도(Nebius, techstrong.ai)가 있다. 다만 전체 플랫폼 오픈소스화의 정확한 날짜는 출처마다 다르거나 불명확해 확정하지 못했고, 이번 Slack 글이 "최초 오픈소스 발표"를 다루는지 "기능 업데이트"를 다루는지도 구분하지 못했다. 한 리뷰 사이트는 "프로덕션 지원에는 여전히 NVIDIA의 상업적 제품이나 파트너가 필요하다"고 적어, 오픈소스 공개와 상용 지원이 분리돼 있을 가능성도 있다.

## 한 줄 요약

**NVIDIA Run:ai는 여러 팀이 공유하는 GPU 인프라 위에서, 작업이 당장 쓰지 않는 할당량까지도 동적으로 회수해 다른 작업에 돌리는 방식으로 유휴 GPU를 줄이는 Kubernetes 기반 오픈소스 스케줄링 플랫폼이다 — 핵심은 "GPU를 잘게 쪼개는 기술"이 아니라 "정적 할당량과 실제 사용량 사이의 간극을 동적으로 메우는 정책"이다.**

## 핵심 포인트

- ***정적 할당량의 비효율을 동적 회수로 해결*** — 부서·프로젝트별로 GPU 할당량을 정해두면 특정 팀의 자원 독점은 막지만, 그 팀이 할당량을 다 못 쓸 때 남는 자원이 그냥 유휴 상태로 묶인다. Run:ai는 이 남는 자원을 다른 작업이 동적으로 가져다 쓰게 해 전체 활용률을 높인다.
- ***GPU 하나를 여러 작업에 분할 할당*** — 학습처럼 GPU 하나를 통째로 쓰는 작업뿐 아니라, 추론처럼 GPU의 일부만으로도 충분한 작업을 같은 GPU에 나눠 배치해 "GPU당 작업 수"를 늘린다(fractional-GPU placement, WebSearch로 교차확인).
- ***작업 우선순위·공정 배분·자원 회수를 함께 고려한 스케줄링*** — 단순 선입선출이 아니라, 우선순위가 높은 작업에 선점권을 주고, 여러 팀 사이의 공정한 배분(fair-share)을 유지하면서, 끝나지 않는 작업에서도 필요시 자원을 회수(preemption)하는 복합 정책을 쓴다.
- ***여러 Kubernetes 클러스터를 한곳에서 관리*** — 온프레미스·클라우드·혼합 환경에 걸친 여러 클러스터의 작업과 자원을 단일 플랫폼에서 관리해, 조직 전체의 GPU 가시성을 하나로 모은다.
- ***개발용(여기서 Slack 발췌 끊김, 확인 못함)*** — 개발/학습/추론 단계별로 다른 정책을 적용하는지 등 구체적인 운영 디테일은 Slack 발췌 범위를 벗어나 확인하지 못했다.

## 내 생각 · 적용점

이 글의 핵심은 "자원을 쪼개는 기술"보다 "정적 할당과 실사용 간극을 동적으로 메우는 정책"이라는 점이다. 이건 [[2026-10-14-intel-d270-inference-gpu-480gb-lpddr5x]]가 다룬 GPU 하드웨어 자체의 메모리 확장 접근과는 다른 레이어의 해법 — 하드웨어를 더 많이 사는 대신 기존 자원의 "배분 정책"을 바꿔 활용률을 높이는 쪽이다. 리소스 낭비를 "성공 여부"가 아니라 "실제 사용량 대 할당량의 간극"으로 추적한다는 점에서는, 같은 날 정리한 [[2026-10-17-salesforce-data360-spark-resource-waste]](Spark 리소스 과다 할당 탐지)와도 같은 철학을 공유한다 — 두 글 모두 "할당받았다"와 "실제로 썼다" 사이의 간극을 드러내는 계측·정책을 다룬다는 공통점이 있다.

## 호스피탈리티 / CRS 적용 포인트

온다가 Kubernetes 기반 GPU 클러스터를 직접 운영하지 않는다면 이 글의 **직접** 적용은 멀다. 다만 "정적으로 할당된 자원이 실제로는 유휴 상태로 묶여 있고, 그 유휴분을 동적으로 다른 작업에 돌린다"는 정책 아이디어 자체는, CRS가 여러 고객사(호텔/체인)별로 API 호출 할당량이나 배치 작업 슬롯을 정적으로 나눠 쓰는 구조라면, "한 고객사가 쓰지 않는 할당량을 다른 고객사의 피크 시간대 요청에 동적으로 돌리는" 자원 정책으로 전이해볼 수 있는 아이디어다.
