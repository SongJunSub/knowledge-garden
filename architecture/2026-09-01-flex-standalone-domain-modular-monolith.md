# 모놀리식인데, 도메인 하나만 따로 띄웁니다 (flex 팀 블로그)

> 출처: [모놀리식인데, 도메인 하나만 따로 띄웁니다](https://flex.team/blog/2026/09/01/backend40) (flex.team 팀 블로그 · Slack #개발-뉴스-dev-news(TechArticles) 공유) · 정리일 2026-09-01
> **출처 한계**: `flex.team` 도메인 자체가 이번 세션 network egress 정책으로 차단돼 원문을 WebFetch로 열지 못했다(도메인 통째 차단 — [[2026-08-25-flex-scheduled-trigger-outside-app-lifecycle]]와 같은 상황). Slack 발췌 3줄이 이 글의 뼈대다. 대신 WebSearch로 flex의 같은 블로그 시리즈("미래를 담아낸 뼈대" backend1~7, 특히 backend6 "AI가 읽을 수 있는 코드베이스")를 검색해 **거의 동일한 내용의 정황 정보**를 확보했다 — flex의 도메인 모듈은 `flex-skeleton` 템플릿 기반이라 Port/Adapter 경계가 명확하고, 실제로 flex-flow-backend의 Issue 도메인에는 `standalone-app`이라는 모듈이 있어 API·Service·Infrastructure·Repository는 그대로 조립하되 프로덕션의 Spring Security+OAuth2 인증 Adapter 대신 단순 헤더 기반 Standalone Security Adapter를 끼워, Gateway도 인증 서버도 다른 도메인도 없이 Issue 도메인만 독립 기동한다는 것까지 확인했다. **다만 이 정황 정보가 검색된 출처는 backend6(2026-04-06자) 게시물로 추정되며, 오늘 자(2026-09-01) backend40이 정확히 같은 내용의 후속·상세화인지 아니면 새로운 진전(빌드 의존성 조립, Vite+React 프론트엔드, Playwright E2E 등 추가 요소)을 다루는지는 원문을 직접 열지 못해 1:1로 확인하지 못했다.** 아래 내용은 이 두 소스(Slack 발췌 + 검색된 정황)를 합쳐 정직하게 재구성한 것이다.

## 한 줄 요약

**flex는 전체를 하나로 배포하는 모놀리식 구조를 유지하면서도, Port/Adapter 경계가 명확한 모듈 설계 덕분에 특정 도메인(예: Issue) 하나만 인증 서버·Gateway·다른 도메인 없이 독립적으로 기동할 수 있는 `standalone-app` 환경을 만들었다 — 빌드 의존성 설정만으로 필요한 모듈을 선택 조립해, 도메인 단위 빠른 기동으로 개발 순환 주기를 단축하고 MSA 수준의 유연한 검증 환경을 모놀리식 안에서 확보했다는 글이다.**

## 핵심 포인트

- flex는 **모듈러 모놀리식** 구조를 쓰며, 전체 애플리케이션을 통째로 기동하는 대신 ***특정 도메인만 독립적으로 기동***할 수 있는 환경을 구축했다.
- (정황 보강) flex의 도메인 모듈은 `flex-skeleton` 템플릿 기반이라 **Port/Adapter 경계가 명확**하고, 이 경계 덕분에 프로덕션 Adapter(Spring Security+OAuth2 인증 등)를 **테스트/개발용 Adapter로 교체**해 조립할 수 있다. flex-flow-backend의 Issue 도메인에 있는 `standalone-app` 모듈이 실제 사례로, 단순 헤더 기반 Standalone Security Adapter를 끼워 Gateway·인증 서버·다른 도메인 없이 Issue 도메인 하나만 띄운다.
- 도메인 단위 빠른 기동으로 ***개발 순환 주기를 단축***하고 불필요한 대기 시간·맥락 전환 비용을 절감한다.
- ***빌드 파일의 의존성 설정***을 통해 필요한 모듈만 선택적으로 조립 — 이 조립 방식 자체가 "필요한 것만 골라 켠다"는 모듈러 아키텍처의 핵심 이점을 실증한다.
- 이 구조로 **MSA와 같은 유연한 검증 환경**을 모놀리식을 유지한 채로 구현했다는 것이 제목("모놀리식인데")의 요지 — 서비스 분리(MSA) 없이도 도메인별 독립 검증이라는 MSA의 이점 일부를 흉내낸다.

## 내 생각 · 적용점

### 핵심 전이 1 — 같은 flex 시리즈, "경합을 없애는" 접근이 두 번째로 나타났다

[[2026-08-25-flex-scheduled-trigger-outside-app-lifecycle]](flex 블로그 backend39, 8/25)에서 flex는 `@Scheduled` 다중 Pod 중복 문제를, 분산 락으로 경합을 조정하는 대신 **트리거 자체를 애플리케이션 생명주기 밖으로 꺼내는** 방식으로 풀었다. 이 글(backend40, 9/1)은 다른 문제(전체 앱을 다 띄워야만 도메인 하나를 검증할 수 있는 답답함)를, **도메인 경계를 애플리케이션 프로세스 경계 밖으로 꺼내는** 방식으로 푼다 — "무언가를 통째로 묶어놓은 단위(생명주기, 배포 단위)에서 필요한 조각만 분리해 꺼낸다"는 같은 설계 습관이 한 팀의 블로그에서 열흘 간격으로 두 번 반복된다. 우연이 아니라 flex 팀의 아키텍처 원칙(Port/Adapter로 경계를 명확히 하고, 그 경계를 따라 무엇이든 분리 가능하게 만든다)이 서로 다른 문제에 같은 패턴으로 적용되는 것으로 읽힌다.

### 핵심 전이 2 — 모놀리식 대 MSA 논쟁에 대한 실용적 중간 답

이 글의 진짜 주장은 "모놀리식이냐 MSA냐"가 아니라, **모놀리식으로 배포하되 개발·검증 단계에서는 MSA급 유연성을 흉내내는 것이 가능하다**는 것이다. 이건 흔한 이분법(배포 단순성 vs 서비스 독립성)에 세 번째 선택지를 제시한다 — 배포는 하나로 묶어 운영 복잡도를 낮추면서, 경계만 명확히 설계해두면 검증·개발 국면에서는 마치 여러 서비스인 것처럼 다룰 수 있다는 것. "분리냐 통합이냐"가 아니라 "경계 설계가 먼저고, 배포 형태는 그 경계 위에서 나중에 고르는 선택"이라는 관점 전환이다.

## 호스피탈리티 / CRS 적용 포인트

CRS 백엔드도 예약·재고·정산·채널연동처럼 여러 도메인이 한 모놀리식 안에 있을 가능성이 높다. 이 글의 핵심 원칙 — **Port/Adapter 경계를 명확히 설계해두면, 특정 도메인(예: 채널 재고 연동)만 인증 서버·다른 도메인 의존성 없이 독립 기동해 로컬에서 빠르게 검증할 수 있다** — 는 직접 참고할 만하다. 특히 CRS처럼 파트너사 채널 연동을 자주 테스트해야 하는 도메인에서, 전체 스택(인증·게이트웨이·다른 도메인 서비스)을 다 띄워야만 한 기능을 검증할 수 있다면 개발 순환 주기가 그만큼 늘어진다. "MSA로 쪼갤 것인가"를 고민하기 전에, "지금 있는 모놀리식의 도메인 경계가 애초에 이렇게 분리 가능하게 설계돼 있는가"를 먼저 점검하는 게 이 글이 주는 실용적 질문이다.
