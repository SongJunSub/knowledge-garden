# Amazon EKS에서 vLLM으로 Gemma 4 서빙 최적화하기 1부: 콜드 스타트 최적화

> 출처: [Amazon EKS에서 vLLM으로 Gemma 4 서빙 최적화하기 [1부: 콜드 스타트 최적화]](https://aws.amazon.com/ko/blogs/tech/eks-gemma4-part1/) (AWS 기술 블로그) · 정리일 2026-09-10

> **출처 한계**: `aws.amazon.com`은 이 세션에서 egress 자체가 차단되어 원문을 열람하지 못했다(WebFetch 시도 즉시 `EGRESS_BLOCKED`). WebSearch로 같은 주제군의 AWS 공식 자료를 교차 확인했다 — 특히 AWS Containers 블로그 "Fast model loading for AI inference on Amazon EKS"(Run:ai Model Streamer로 S3→GPU 메모리 스트리밍, Karpenter의 JIT GPU 노드 프로비저닝, EKS Pod Identity 최소권한 S3 접근, 64GiB 모델 기준 초기 구동 82초→65초·이후 구동 82초→16초로 단축)가 이번 글이 다루는 것과 동일한 기술 스택·문제의식을 담고 있어 신빙성 있는 정황 증거로 삼았다. vLLM 공식 Sleep Mode 문서/블로그로 "sleep/wake" 메커니즘 자체(GPU 메모리 90%+ 반환, 재개 시 전체 재적재 대비 18~200배 빠름, 콜드 스타트 대비 61~88% 빠른 추론 재개)도 확인했다. 다만 "Gemma 4"라는 모델명, "4단계 분석", "47% 단축"이라는 구체 수치는 이번 글 원문에서만 확인 가능한 세부이고 이 세션에서는 검증하지 못했다 — Slack 발췌문에만 있는 값이므로 그대로 신뢰하지 말고 정황상 개연성 있는 범위(동일 계열 AWS 사례의 80~93% 단축 폭 안에 들어가는 숫자)로만 받아들여야 한다. GeekNews가 아니라 Slack TechArticles 경유이므로 hada 댓글·HN/Lobsters 큐레이션은 애초에 해당 사항이 없다.

## 한 줄 요약

**Amazon EKS 위에서 vLLM으로 Gemma 4를 서빙할 때 발생하는 7분 이상의 콜드 스타트를, 노드 프로비저닝 → 이미지/모델 로딩 → 엔진 초기화 → 워밍업까지 4단계로 쪼개 병목을 각각 잡는다는 글이다. 핵심 수단은 세 가지 — ① S3에서 GPU 메모리로 가중치를 곧장 스트리밍해 디스크 경유를 없애고, ② 컴파일 캐시(CUDA 그래프 등)를 재사용해 매 시작마다 반복 컴파일하지 않고, ③ 완전히 죽이는 대신 vLLM의 sleep/wake 전환으로 유휴 상태를 관리한다. 이 조합으로 시작 시간을 47% 줄였다고 주장한다. Karpenter가 GPU 노드를 필요할 때만 즉시 띄우고, EKS Pod Identity로 S3 접근 자격을 파드 단위 최소권한으로 관리하는 것이 이 파이프라인 전체를 지탱하는 기반이다.**

## 핵심 포인트

- **콜드 스타트를 뭉뚱그리지 않고 4단계로 해부한다.** 노드 프로비저닝(Karpenter가 GPU 인스턴스를 새로 띄우는 시간) → 컨테이너/모델 로딩(수십~수백 GiB 가중치를 S3에서 가져오는 시간) → vLLM 엔진 초기화(CUDA 그래프 컴파일 등) → 첫 요청 워밍업까지, 병목이 단계마다 성격이 다르다는 게 이 글의 진단 프레임이다.
- **S3 스트리밍 로더로 "다운로드 후 로딩"을 없앤다.** 디스크에 통째로 내려받은 뒤 GPU로 올리는 대신, S3에서 GPU 메모리로 직접 스트리밍한다. 같은 접근을 쓰는 AWS Containers 블로그 사례에서는 64GiB 모델 기준 최초 구동 82초→65초, 같은 노드에서의 재구동은 82초→16초까지 줄었다 — 설정값 변경만으로, 코드 수정 없이.
- **컴파일 캐시를 재사용해 매번 새로 굽지 않는다.** vLLM이 CUDA 그래프 등을 매 파드 시작마다 새로 컴파일하는 대신 캐시된 산출물을 재사용하도록 해, 엔진 초기화 단계의 반복 비용을 없앤다.
- **완전 종료 대신 sleep/wake로 유휴 상태를 관리한다.** vLLM Sleep Mode는 모델 가중치를 CPU RAM으로 내리고 KV 캐시를 비워 GPU 메모리의 대부분(90%+)을 반환하면서도 서버·컨테이너는 유지한다. 깨울 때는 완전 재적재 대비 18~200배 빠르고, 콜드 스타트 대비 61~88% 빠른 추론 재개가 가능하다는 것이 vLLM 공식 벤치마크다.
- **Karpenter가 GPU 노드 프로비저닝 자체의 지연을 줄이는 전제조건이다.** Pending 상태 파드에 맞춰 Karpenter가 GPU 인스턴스를 즉시(Just-In-Time) 띄우고 스케일다운 시 정리하는 구조가, 위 세 가지 소프트웨어 계층 최적화의 하부 인프라를 이룬다.
- **EKS Pod Identity로 S3 접근을 파드 단위 최소권한으로 좁힌다.** 노드 IAM 역할 공유 대신 워크로드별 자격 증명을 분리해, 대용량 모델 스트리밍 경로의 보안 경계를 명확히 한다.
- **"7분 이상"이라는 기준선 자체가 이 문제의 심각성을 보여준다.** 실제로 유사 사례(vLLM on Kubernetes 커뮤니티 리포트)에서도 L4 GPU 파드가 스케줄링부터 서빙까지 약 6.3분, 여기에 노드 프로비저닝 약 6분이 더해져 총 10분 이상 걸린 사례가 보고돼 있어, 이 글이 잡은 "7분+" 콜드 스타트가 특별히 과장된 숫자는 아니다.

## 내 생각 · 적용점

### 핵심 전이 1 — "요청/시작 경로를 끝까지 따라가 단계별로 쪼갠다"는 같은 방법론

[[2026-07-13-how-an-ai-token-travels-through-a-data-center]]가 강조한 "요청 하나를 15개 정거장으로 끝까지 추적하라"는 방법론과, 이 글이 콜드 스타트를 노드 프로비저닝→로딩→초기화→워밍업 4단계로 쪼갠 것은 같은 사고의 다른 적용이다. 다른 점은 대상이다 — 그 글은 정상 상태(steady state) 추론 요청의 경제학을 다뤘고, 이 글은 시작 시퀀스(cold path)의 지연을 다룬다. 두 글을 겹쳐 보면 "추론 인프라를 이해하려면 정상 경로와 시작 경로를 모두 따로 트레이스해야 한다"는 더 큰 원칙이 보인다. 특히 그 글이 말한 "프리필은 연산 바운드, 디코드는 대역폭 바운드라서 분리해야 한다"는 통찰과, 이 글의 "노드 프로비저닝은 오케스트레이션 지연, 모델 로딩은 네트워크/스토리지 대역폭 바운드, 엔진 초기화는 연산 바운드라서 각각 다른 해법이 필요하다"는 구조가 정확히 같은 결의 관찰이다.

### 핵심 전이 2 — "실행을 결정하는 것은 launch 선언이 아니라 프로비저닝 계층"이라는 반복되는 패턴

[[2026-09-04-aws-ecs-design-01-compute-launch-types]]는 ECS에서 "launch type은 호환성 선언일 뿐, 실제 실행은 용량 공급자(capacity provider)가 결정한다"고 짚었다. 이 글에서 Karpenter가 하는 역할이 정확히 그 자리다 — Pod spec(무엇을 원하는가)과 실제 GPU 노드가 뜨는 방식·타이밍(어떻게 실행되는가)이 분리돼 있고, 그 분리 지점(Karpenter의 JIT 프로비저닝)이 콜드 스타트 4단계 중 첫 단계를 통째로 좌우한다. AWS의 컨테이너 오케스트레이션 스토리 전체(ECS capacity provider, EKS+Karpenter)가 "무엇을 실행할지"와 "어떻게·언제 컴퓨트를 조달할지"를 분리하는 동일한 설계 철학 위에 서 있다는 걸 다시 확인시켜준다.

### 핵심 전이 3 — 같은 시리즈 2부와의 직접 연결

이 글은 "1부: 콜드 스타트 최적화"이고, 같은 배치로 정리한 [[2026-09-10-aws-eks-gemma4-vllm-part2-throughput-slo]]가 "2부: GPU 한 장의 처리량과 지연 SLO"를 다룬다. 콜드 스타트를 줄이는 문제(파드가 얼마나 빨리 서빙 가능 상태에 도달하는가)와 처리량/지연 SLO 문제(서빙 가능 상태가 된 뒤 얼마나 잘 버티는가)는 같은 서빙 파이프라인의 앞뒤 반쪽이라, 두 편을 이어 읽어야 "콜드 스타트만 줄이고 정상 상태 성능은 놓치는" 반쪽짜리 최적화를 피할 수 있다.

## 호스피탈리티 / CRS 적용 포인트

전제부터 정직하게 밝힌다 — 온다가 현재 자체 LLM 추론 서빙 인프라를 K8s 위에서 운영하는지는 이 세션에서 확인할 수 없고, 불확실하다. 그럼에도 CRS/PMS 도메인에서 LLM을 자체 호스팅하는 시나리오(예: 예약 문의 응답, 리뷰 요약, 다국어 번역, 내부 코파일럿을 벤더 API 대신 자체 서빙으로 돌리는 경우)를 상정하면, 이 글의 원칙은 구체적으로 옮길 수 있다.

- 트래픽 패턴이 뾰족한 워크로드일수록 콜드 스타트 비용이 커진다. CRS의 성수기/비수기, 특정 시간대 몰림(체크인 러시) 패턴을 자체 LLM 서빙에 태운다면, 스케일-투-제로 후 재기동 지연이 곧 응답성 SLA를 깨는 지점이 된다 — 이 글의 S3 스트리밍·컴파일 캐시·sleep/wake는 "얼마나 자주 껐다 켜도 되는가"의 경계를 넓혀준다.
- 완전 종료(scale to zero)와 완전 상시 가동(always-on) 사이의 세 번째 선택지. sleep/wake는 GPU 비용을 always-on보다 낮추면서도 콜드 스타트보다 훨씬 빠른 중간 지점을 제공한다. 자체 LLM 인프라를 고려한다면 이 중간 지점을 최우선으로 검토할 가치가 있다 — 순수 온디맨드보다 예측 가능하고, 상시 가동보다 저렴하다.
- Karpenter + Pod Identity 조합은 GPU 워크로드 전용 패턴으로 별도 학습 가치가 있다. [[2026-09-04-aws-ecs-design-01-compute-launch-types]]에서 이미 ECS의 컴퓨트 추상화 원칙을 짚었는데, GPU 노드처럼 비싸고 프로비저닝이 느린 자원일수록 "필요한 순간에만 정확히 띄운다"는 원칙의 값이 커진다.
