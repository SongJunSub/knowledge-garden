# [미리디] 외부 API 장애가 우리 서비스 장애로 이어졌다 (미리디 기술블로그)

> 출처: [[미리디] 외부 API 장애가 우리 서비스 장애로 이어졌다](https://medium.com/miridih/%EC%99%B8%EB%B6%80-api-%EC%9E%A5%EC%95%A0%EA%B0%80-%EC%9A%B0%EB%A6%AC-%EC%84%9C%EB%B9%84%EC%8A%A4-%EC%9E%A5%EC%95%A0%EB%A1%9C-%EC%9D%B4%EC%96%B4%EC%A1%8C%EB%8B%A4-c543b124f522) (미리디 기술블로그, Medium) · Slack `#개발-뉴스-dev-news` 직공유 · 정리일 2026-09-15

> **출처 한계 — 이 노트는 제목 이상의 본문 내용을 확보하지 못한 채 작성됐다.** `medium.com`이 이 세션 egress 프록시에서 도메인 단위로 차단(EGRESS_BLOCKED)돼 WebFetch가 전면 불가능했다. WebSearch로 정확한 제목 문구("외부 API 장애가 우리 서비스 장애로 이어졌다"), 회사명("미리디"·"미리캔버스"·"MIRIDIH") 조합을 10회 가까이 바꿔가며 시도했지만, 이 특정 글의 본문·저자·발행일·어떤 외부 API였는지·구체적 원인·재발방지 대책 중 단 하나도 검색 스니펫으로 확인하지 못했다(발행 직후라 아직 색인되지 않았을 가능성이 높다). 그래서 아래 내용은 **제목이 명시하는 문제 프레임("외부 API 장애 → 자사 서비스 장애로 전파")과, 이 가든이 이미 정리해 둔 같은 패턴의 원칙들을 짚는 수준**에 머문다 — 미리디가 실제로 어떤 API에 의존했는지, 원인이 타임아웃 미설정인지 서킷 브레이커 부재인지 스레드풀 고갈인지는 **전혀 모른다.** 구체 사실을 아는 것처럼 서술하지 않는다.

## 한 줄 요약
**제목만으로 확인 가능한 사실은 "미리디가 의존하던 외부 API의 장애가 격리되지 못하고 자사 서비스 전체 장애로 번졌다"는 것 하나뿐이다. 본문을 읽지 못했으므로, 이 노트는 사건의 구체적 전말이 아니라 "외부 의존성 하나가 전체를 끌어내리는" 이 패턴 자체와 가든에 이미 쌓인 같은 교훈만 정리한다.**

## 핵심 포인트
- **확인된 것은 제목 프레임뿐이다** — 외부 API 장애가 "우리 서비스 장애로 이어졌다"는 것은, 장애가 발생한 지점(외부)과 영향을 받은 지점(자사 전체 서비스) 사이에 ***격리 장치가 없었거나 뚫렸다***는 뜻이라는 추론까지는 제목만으로도 가능하다.
- **미확인 항목이 이 사건의 실질이다** — 어떤 외부 API였는지(결제·인증·이미지 처리·CDN 등 미리캔버스 서비스 특성상 후보는 많다), 장애 전파 경로가 스레드 고갈이었는지 동기 호출 타임아웃 미설정이었는지, 재발방지책으로 서킷 브레이커·타임아웃·폴백 중 무엇을 도입했는지는 ***이 세션에서 전혀 확인하지 못했다.***
- **이 패턴은 이 가든에서 이미 여러 번 다뤄진 일반 원칙과 겹친다** — 아래 "핵심 전이"에서 다룬다.

## 내 생각 · 적용점

### 핵심 전이 1 — "공유 자원에 우선순위가 다른 워크로드를 섞으면 장애가 전이된다"는 원칙의 외부 의존성 버전
[[2026-09-07-channel-corp-dynamodb-user-badge-part3]]는 부가 기능(알림 배지)의 트랜잭션 충돌이 핵심 기능(부트 서비스)까지 마비시킨 사례에서 ***"공유 자원에 우선순위가 다른 워크로드를 함께 두면, 낮은 우선순위 워크로드의 장애가 높은 우선순위 워크로드까지 전이된다"***는 원칙을 뽑아냈다. 이 글의 제목이 말하는 현상은 정확히 그 원칙의 외부 의존성 버전이다 — 공유 DB 테이블 대신 외부 API가 "격리되지 않은 공유 자원" 역할을 했을 가능성이 높다. 다만 미리디 사례에서 실제로 무엇이 공유됐는지(커넥션 풀, 스레드풀, 동기 호출 체인)는 본문 미확인이라 추정에 그친다.

### 핵심 전이 2 — 장애 원인을 사람이 종합해야 했다면, [[2026-09-04-sre-observer-alert-root-cause]]가 자동화하려는 바로 그 작업이다
그 노트는 "메트릭·로그·트레이스가 화면마다 흩어져 있어 셋을 잇는 일이 사람의 몫"이라는 문제의식에서 출발해 상관분석을 자동화했다. 미리디의 장애 대응 과정에서도 "외부 API 응답 지연 → 내부 스레드 고갈 → 전체 응답 지연"이라는 인과 사슬을 누군가 수동으로 재구성했을 가능성이 높은데, 본문을 못 읽어 실제로 그랬는지는 확인할 수 없다 — 다만 이 글이 만약 그 재구성 과정을 다뤘다면 두 노트는 "같은 문제, 사람이 하느냐 도구가 하느냐"로 정확히 짝을 이뤘을 것이다.

## 호스피탈리티 / CRS 적용 포인트
제목이 가리키는 문제 자체는 CRS에 매우 직접적이다. 온다 CRS도 PMS·채널매니저·결제 게이트웨이·OTA API 같은 ***외부 의존성이 많은 통합 플랫폼***이고, 그중 하나(예: 특정 OTA의 재고 동기화 API)가 느려지거나 죽었을 때 그 장애가 예약 확정·정산 같은 핵심 플로우까지 전파되지 않도록 ***타임아웃·서킷 브레이커·벌크헤드(외부 연동별 스레드풀·커넥션 풀 분리)***가 갖춰져 있는지는 이 글과 무관하게도 상시 점검해야 할 항목이다. 다만 이 원칙은 이 글에서 배운 것이 아니라 제목이 시사하는 문제 유형 일반에서 끌어온 것임을 분명히 해둔다 — 미리디가 실제로 어떤 대책을 썼는지 확인했다면 훨씬 구체적인 적용점을 남길 수 있었을 것이다.
